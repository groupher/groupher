# PR Integration Acceptance

Follow [AGENTS.md](../../../../AGENTS.md#branch-and-worktree-ownership): use the current local branch/worktree by default. Missing test tooling, a dirty checkout or parallelism does not authorize a new checkout or branch switch. Before proposing an exception, state the concrete obstacle in the current checkout and the target; proceed only with explicit user authorization within its scope. Loading this skill grants no such permission.

For that authorized exception, prepare a reproducible checkout of the actual PR plus the smallest required test tooling. Check the capabilities of the target revision before choosing its runtime. Use the current checkout directly when it already contains the required code and tools. Reuse an already prepared acceptance checkout when its HEAD/overlay still match; recreating it loses the warm application build.

## Prepare the target checkout

1. Record the PR head/base SHA and each required fixture commit or explicit dirty-file overlay. Check required capabilities first: account creation, scoped grants, sessions, Article creation and `--publish` if the UI lists only public Posts. Use [seed](../../seed/SKILL.md) for the supported commands. Fixture setup can use formal Publisher/Commands; the product action under acceptance must still use its actual UI.
2. Only when the user explicitly authorized creating the isolated checkout, create a detached worktree at the recorded PR SHA and apply only the listed tooling commits/patches. Review `git diff --check` and the resulting diff. Record necessary fixture adaptations such as renamed schema fields; keep them in the disposable checkout. A product conflict requires a product fix rather than an undocumented test overlay.
3. Compare `pnpm-lock.yaml`, `pnpm-workspace.yaml`, relevant package manifests, `backend/api/mix.lock`, `mix.exs` and compile-time config against the candidate cache source. Check Node/pnpm and Elixir/OTP versions, architecture and `MIX_ENV`. Inspect ignored generated files needed by local workspace exports. A matching lockfile alone does not prove a cache or fixture is compatible.

## Reuse caches without mixing checkouts

On revisions shipping multi-worktree support, see the dependency and acceptance criteria in `docs/architecture/dev-hub-multi-worktree.md`. Check compatibility, ownership and target code resolution before accepting a cache.

- **Elixir dependency source:** with a compatible `mix.lock`, prefer a target-owned filesystem clone or copy of existing dependency sources. A shared `MIX_DEPS_PATH` is only for preparation that cannot modify that directory; do not run `deps.get`, `deps.update` or `deps.compile` against it while its owner is using it. Check `mix deps`. Do not relaunch a server outside Hub to pass environment variables; runtime dependencies must be available through target-local paths or Hub's existing supported configuration.
- **Elixir build:** seed a target-owned `_build` from a compatible, quiescent cache; preserve permissions and timestamps. Prefer filesystem clone/copy support where available. Avoid a writable `_build` symlink shared with another active checkout. Run normal incremental `mix compile` against the target source so Mix can invalidate stale application modules and compile-time config. Copying `_build` into a different project path can still trigger a full application compile even with matching locks and source; treat it as dependency-cache reuse until the compile log proves otherwise. Do not keep recopying or rebuilding temporary checkouts to chase a warm cache. Expect compilation for actual source or `elixirc_paths` changes; do not use `--no-compile` or copy BEAM files by hand to hide it. Record whether the reused build covers `dev` or `test` before promising a warm start.
- **pnpm:** use target-owned workspace links and verify that `@groupher/contracts` and Core use the target checkout's code. A source worktree's `node_modules` symlink may resolve workspace packages back to that source and invalidate acceptance. Check the real paths of the package links themselves (for example, `frontend/dash/node_modules/@groupher/frontend-core` and `@groupher/contracts`), not just whether the dependency directory exists; a target-local injected package also needs a code-change check. Reuse the pnpm store with `pnpm install --offline --frozen-lockfile` when target links are missing; this is an explicit dependency preparation step and may run package lifecycle scripts. If offline packages are missing, report the missing dependency before doing an authorized online install. Do not repeatedly start Vite to discover one missing package link at a time.
- Keep `verifyDepsBeforeRun: warn` when the target has that workspace setting. On an older checkout missing it, carry the reviewed setting as a recorded tooling overlay before invoking pnpm scripts; status/log commands must not unexpectedly install dependencies.

Use [db-migration-rehearsal](../../db-migration-rehearsal/SKILL.md) when schema acceptance requires an isolated data clone; do not apply a migration to the shared development database just to make this checkout start.

## Accept and restore

Confirm the target resolves its own code and supports the fixture and database operations required by the test. For a registered secondary environment, operate from B using its Dev Hub commands, verify its dev/test database identities and product URLs, and leave A serving its own checkout. An older revision without isolated-runtime support needs a separately authorized [shared runtime handoff](../../dev-hub/references/shared-runtime-handoff.md) if the test requires that runtime. A detached checkout alone provides no runtime isolation.

Record actual PR SHA, overlay paths/commits, cache source and checks, fixture run/aliases, tested UI actions and retained artifacts. Store screenshots and the non-secret record under `.playwright/`. Use [test-cleanup](test-cleanup.md) to clean the fixture run, restore the original runtime, and remove only the disposable checkout created for this task. Passing unit tests or mock Auth flows does not prove the real multi-account acceptance.
