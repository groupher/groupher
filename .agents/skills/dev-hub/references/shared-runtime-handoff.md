# Dev Hub Worktree Switch

Follow [AGENTS.md](../../../../AGENTS.md#branch-and-worktree-ownership): ordinary work stays in the current local branch/worktree. Use this procedure only when the user explicitly authorized moving the shared local runtime to the specified checkout. Authorization to implement or test, loading this skill, a dirty checkout and parallelism do not authorize a switch. If no applicable authorization exists, explain the concrete obstacle and target before requesting it. Do not create another checkout as an automatic response to a Hub ownership mismatch. Prepare the target with [pr-integration](../../grstack/references/pr-integration.md) before interrupting services. Use [dev-hub](../SKILL.md) for normal service operations and health diagnosis. Read the [local environment guide](../../../../docs/architecture/dev-hub-local-environment.md) for runtime boundaries.

1. Record the original canonical repository root, HEAD, Hub identity and service statuses. Run `pnpm devhub status` from the owning checkout. Record which services were running, stopped or already unhealthy; restoration uses this list rather than starting everything.
2. Confirm the target HEAD and fixture capability. Check that the database schema supports both the target runtime and the restoration plan. Identify the actual dev and test databases before handoff. A legacy shared runtime may reuse the original database. Registered secondary environments have their own targets and use the normal [Dev Hub procedure](../SKILL.md). If a migration is needed, establish the exact approved target, versions and recovery procedure before switching. Do not automatically migrate on startup.
3. Stop the original active services through `pnpm devhub stop <service-id>` in their owning checkout, consumers before dependencies. Stop the Hub through its original terminal/session with Ctrl-C, or Quit if the desktop app owns the server. Quitting an app that attached to an external `make dev` server does not stop that server.
4. If the original session is unavailable, verify the server PID, command, checkout and parent chain against the recorded Hub identity. The server handles SIGINT/SIGTERM gracefully; for this authorized handoff, signal only the verified Hub server PID and wait for it to exit. Killing only the `make` wrapper can leave the Node server alive. Never use broad process-name matching, SIGKILL, or a different port to bypass ownership. A listener without verified ownership requires diagnosis before proceeding.
5. Start `make dev` from the target checkout in a controllable terminal session and retain its session handle. Confirm `pnpm devhub status` succeeds there, then start the required application through Hub's default dependency chain. Verify health and the canonical URL. A health-wait timeout during a live compile means inspect logs and wait on that same process; do not restart the compiler.
6. Finish fixture cleanup and revoke the test sessions while the target code and schema are still available. Stop target services and its Hub through their owning handles. Apply any explicitly planned schema restoration, start the original Hub through `make dev`, and restore the recorded service set. Verify the original repository identity, service health and a canonical page. Remove a disposable checkout only after its processes have stopped and evidence is saved.

Use [test-cleanup](../../grstack/references/test-cleanup.md) for cross-resource teardown and findings. Use [db-migration-rehearsal](../../db-migration-rehearsal/SKILL.md) when a database clone or recovery exercise is part of acceptance.

Report a failed restoration immediately with the exact remaining service/schema state. Keep a non-secret handoff record under `.playwright/` with both roots/HEADs, original service set, session handles, any approved migrations, acceptance results and restoration checks. Never copy Hub credentials or private actor state between worktrees to make identity checks pass.
