# Groupher Service Identity And User Delegation V2

> Status: target contract for authenticated service-to-service communication.
>
> V2 is separate from the Browser Auth and Session Lifecycle defined in
> [`v1.md`](./v1.md). V1 answers who the user is and how a browser login
> continues. V2 answers which service is calling, which resource server it may
> call, which operations it may perform, and whether it is acting for a user.

## Implementation Status

The V2 application-code migration is implemented across Auth, Phoenix,
Dashboard, Content Import, Assets Hub, Press, and the scheduler edge:

- Auth exposes `POST /oauth2/token` and `GET /.well-known/jwks.json`.
- The initial client registry is environment-backed, stores SHA-256 credential
  hashes, supports current/next hashes, and grants only registered
  resource/audience/scope intersections.
- Service access tokens use `RS256`, `typ=service_access+jwt`, a 10-minute
  lifetime, exact audience, bounded scopes, `kid`, and `jti`.
- `@groupher/service/auth` provides the in-memory single-flight client and the
  bounded JWKS verifier used by Node resource servers.
- Phoenix verifies Auth service JWTs locally, attaches a typed `service_actor`,
  and enforces exact audience and operation scope in GraphQL middleware.
- Auth -> Phoenix Browser Session operations use Auth's own scoped service
  identity.
- Dashboard -> Phoenix and Dashboard -> Content Import use Dashboard's scoped
  service identity plus the existing user access credential; Phoenix binds the
  two verified actors into one typed `delegated_actor` context.
- Content Import -> Phoenix uses Content Import's scoped service identity and
  forwards user proof only for delegated operations.
- Assets Hub -> Phoenix callbacks and Phoenix -> Assets Hub deletion use
  direction-specific scoped service identities. Upload capabilities retain a
  separate domain-owned capability secret with no global-secret fallback.
- Press -> Phoenix public projection reads are migrated to scoped service
  tokens.
- Phoenix -> Press cache invalidation is migrated to
  `sub=service:phoenix`, `aud=press:internal-api`, and
  `scope=press:cache:invalidate`; `PRESS_INTERNAL_TOKEN` is no longer used by
  application code.
- Scheduler -> Dashboard -> Content Import uses scheduler- and
  dashboard-specific tokens with job-specific scopes.
- The production `server_trusted` boolean, global Trust Secret middleware and
  endpoint-specific Cron/Press trust paths are removed. A test-only service
  actor adapter remains isolated behind `allow_test_service_identity` and does
  not accept any production credential or legacy Header.

Deployment still requires provisioning each environment's client registry,
client credentials, signing JWK, and the Assets Hub capability secret before
the migrated services are rolled out.

## Problem

Groupher currently has several independent machine-authentication mechanisms:

```text
GROUPHER_SERVER_TRUST_SECRET
  shared by several first-party services calling Phoenix
  Phoenix reduces it to server_trusted: true | false

PRESS_INTERNAL_TOKEN
  used by Phoenix to call Press cache invalidation

CRON_SECRET and other endpoint-specific secrets
  used by scheduled or internal operations

x-groupher-client: press-v1
  identifies Press but is not a credential
```

The global server-trust secret proves only that a request knows one shared
value. It does not prove which service is calling and does not express an
audience, operation scope, expiry, or per-client revocation state. Every holder
has the same cryptographic identity, so one compromised service can impersonate
another and rotating the secret affects every holder.

Endpoint-specific secrets reduce blast radius compared with reusing the global
secret, but they create separate rotation, audit, failure, and deployment
contracts. V2 replaces both patterns with one scoped Service Identity protocol.

## Scope

V2 covers:

- Auth-owned service client registration and credential lifecycle.
- One generic client-credentials exchange for first-party services.
- Short-lived, audience-bound, scope-bound service access tokens.
- Auth signing-key publication through JWKS.
- Local token verification in Phoenix and other resource servers.
- Per-operation service authorization.
- Service-to-service calls in either direction, not only calls to Phoenix.
- User-delegated service operations that require both service and user proof.
- Migration away from `GROUPHER_SERVER_TRUST_SECRET`,
  `PRESS_INTERNAL_TOKEN`, and equivalent static bearer trust.
- Issue, validation, rejection, rotation, and revocation observability without
  logging credentials.

V2 does not replace:

- Browser OAuth login or the Browser Session lifecycle.
- Phoenix Passport, membership, ownership, or business authorization.
- OAuth grants for third-party clients, MCP, agents, or CLI tools.
- Short-lived domain capabilities such as a single bounded asset upload. Those
  capabilities may use Service Identity for transport while retaining their
  narrower resource and purpose constraints.
- Network controls, rate limits, request validation, or output bounds.

## Confirmed Decisions

1. Auth is the only service-token issuer.
2. Phoenix does not add a Press-specific or per-sub-app token-issue endpoint.
3. Auth exposes one generic client-credentials exchange.
4. Every service and environment has a separate client identity and credential.
5. Service access tokens are short-lived JWTs and do not use refresh tokens.
6. Token requests identify the target through the OAuth `resource` parameter;
   issued tokens are bound to an exact audience and bounded scopes.
7. Resource servers validate Auth signatures locally from JWKS; they do not call
   Auth for every request.
8. A service token proves the calling service but never substitutes for user or
   business authorization.
9. User-delegated first-party operations carry one standardized dual-proof
   request: a scoped service access token plus the existing user access
   credential. Phoenix validates both and binds them into one typed
   `delegated_actor`; an arbitrary user reference never creates authority.
10. V2 covers sub-app-to-Phoenix and sub-app-to-sub-app calls.
11. A global administrator or generic `server_trusted` scope is not allowed.
12. The completed migration removes the global Trust Secret and isolated static
    internal tokens rather than maintaining them as a permanent fallback.

## Identity Model

V2 distinguishes three actors:

```text
Browser user
  authenticated by Browser Auth V1
  authorized by Phoenix account, Passport, membership, and domain rules

Service actor
  authenticated by a V2 service access token
  authorized for a target audience and operation scopes

Delegated actor
  one service acting for one authenticated user
  constrained by both service scopes and the user's current permissions
```

The identities are not interchangeable:

```text
service identity != user identity
service scope    != Passport permission
network origin   != authenticated service
header name      != credential proof
```

## Target Architecture

```text
                         +-------------------------+
                         |          Auth           |
                         | client registry         |
                         | credential verification |
                         | token issue             |
                         | signing keys + JWKS     |
                         +------------+------------+
                                      |
                         short-lived service JWT
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
              v                       v                       v
          Phoenix                 Press                 Assets Hub
       verify locally          verify locally          verify locally
       check scopes            check scopes            check scopes
       business auth           route bounds            capability bounds
              ^                       ^                       ^
              |                       |                       |
              +---------- Content Import / other services ---+
```

Auth is on the token-issue path, not on every protected request path. Resource
servers cache the public signing keys and verify tokens locally.

## Resource And Audience Registry

Auth centrally owns the mapping from externally requested OAuth resource URIs
to internal JWT audience identifiers. Callers request a registered `resource`;
they do not choose an arbitrary `aud` value:

```text
https://api.groupher.com/press
  -> phoenix:press-api

other registered service resource URI
  -> exact resource-server audience
```

Fixed first-party flows that do not call the OAuth client-credentials endpoint
still use the same audience registry. Browser Auth V1 therefore issues the
pre-registered `aud=phoenix:browser-api` directly; the browser does not submit a
`resource` parameter. Public resource URI naming and internal audience naming
may differ, but their mapping is unique, environment-scoped, and owned by Auth.

## Service Client Registry

Auth owns one record per service and environment. The logical model includes:

```text
client_ref
service_name
environment
status                  active | disabled
allowed_audiences
allowed_scopes
credential_version
credential_hash
next_credential_hash
created_at
rotated_at
disabled_at
metadata
```

Requirements:

- A production credential is never reused in development or preview.
- Different services never share a client credential.
- Production, preview, and development use isolated Auth issuers and signing
  keysets. A resource server trusts only its own environment's issuer/JWKS and
  audience configuration.
- The same logical `sub=service:<name>` may exist in multiple environments
  because a JWT subject is interpreted together with its issuer. If environments
  ever share one issuer, client subjects and audiences must instead carry an
  explicit environment identity.
- Auth stores verifiers/hashes rather than recoverable plaintext when the
  selected client-authentication mechanism permits it.
- Rotation supports an explicit current/next overlap window.
- Disabling one client prevents new token issue without affecting other clients.
- Allowed scopes are registered server-side; a caller cannot obtain a scope
  merely by including it in the request.
- Registry operations are administrative and audited.

The first implementation may use a client secret. The contract should allow a
future move to `private_key_jwt`, workload identity, or mTLS without changing
resource-server authorization semantics.

## Client-Credentials Exchange

Auth exposes one generic endpoint. The canonical route is fixed during
implementation, but it follows the OAuth client-credentials semantics:

```http
POST <auth-service-token-endpoint>
Authorization: Basic <base64(client_id:client_secret)>
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
resource=https%3A%2F%2Fapi.groupher.com%2Fpress
scope=press:article:read press:rss-feed:read press:site:read
```

The first implementation uses `client_secret_basic`. Auth may support another
registered client-authentication method later, but a request uses exactly one
method and never omits client authentication.

`resource` follows RFC 8707 and is an absolute URI identifying the target API.
Auth explicitly supports this OAuth extension parameter at the token endpoint
and maps it to the JWT `aud` value. An unsupported or disallowed resource is
rejected with `invalid_target`; it is not ignored as an unknown form field.

Example response:

```json
{
  "access_token": "<service-jwt>",
  "token_type": "Bearer",
  "expires_in": 600,
  "scope": "press:article:read press:rss-feed:read press:site:read"
}
```

The granted scope is always a subset of the requested scopes intersected with
the client's registered allowlist. Auth never adds an unrequested scope.

The exact lifetime is finalized before implementation; the target range is
5-15 minutes. Auth enforces a maximum and resource servers reject tokens beyond
that maximum.

Client-credentials tokens do not receive a refresh token. A service caches the
access token in process memory and requests a new token shortly before expiry.
Concurrent requests use a single-flight token acquisition. Credential values
never enter application output, browser code, URLs, logs, metrics, cache keys,
or persisted job payloads.

The token endpoint applies:

- `client_secret_basic` client authentication for the initial implementation.
- Client status and credential-version validation.
- Resource-to-audience and scope allowlists.
- Rate limiting and bounded retry behavior.
- `Cache-Control: no-store`.
- Structured audit events without credential values.

## Service Access Token

The JWT protected header includes:

```text
alg
kid
typ = service_access+jwt
```

Minimum claims:

```text
iss    Groupher Auth issuer
sub    service:<service-name>
aud    exact target resource server or API
scope  space-delimited bounded scopes
iat
nbf
exp
jti
```

Optional claims must have a defined verifier and authorization use. Tokens do
not contain client secrets, browser tokens, arbitrary permission snapshots, or
sensitive request data.

Example:

```text
protected header:
typ    service_access+jwt

claims:
iss    https://auth.groupher.com
sub    service:press
aud    phoenix:press-api
scope  press:article:read press:rss-feed:read press:site:read
```

For this example, Auth maps the requested
`resource=https://api.groupher.com/press` to the internal audience identifier
`phoenix:press-api`. Resource servers validate the mapped `aud`; callers do not
choose an arbitrary JWT audience directly.

An access token issued for Phoenix is rejected by Press, Assets Hub, Content
Import, and other audiences. A token with `press:article:read` cannot perform a
Press configuration mutation or invalidate a Press cache.

## Resource-Server Validation

Phoenix, Press, Assets Hub, Content Import, and future resource servers share
the same validation contract:

1. Parse the bearer credential from the designated server-to-server request.
2. Require the service-token type; never confuse it with a browser or external
   API access token.
3. Select an allowed Auth signing key by `kid`.
4. Verify the signature and allowed algorithm.
5. Validate `iss`, exact `aud`, `iat`, `nbf`, and `exp` with bounded clock skew.
6. Validate the service subject and required operation scope.
7. Attach a typed service actor to request context.
8. Run resource-server business and data-visibility checks.

JWKS is cached with a bounded lifetime. An unknown `kid` may trigger one
rate-limited JWKS refresh before rejection. Resource servers fail closed when a
token cannot be verified; they do not ask Auth to introspect every request.

The target Phoenix context is richer than the current boolean:

```text
current
  server_trusted: true

target
  service_actor:
    subject: service:press
    audience: phoenix:press-api
    scopes:
      - press:article:read
    token_id: <jti>
```

Operation middleware checks a concrete required scope. There is no compatibility
alias that turns any valid service token into unrestricted `server_trusted`.

## Authorization Ownership

Auth owns authentication policy for service clients:

```text
client registration
credential verification and rotation
allowed audience/scope grant
service-token issue
signing keys and JWKS
client disable/revoke
token-issue audit and rate limits
```

The resource server owns authorization over its operations and data:

```text
required operation scope
resource ownership and visibility
community and content bounds
mutation invariants
business rate/result-size limits
final 401 / 403 / 404 decision
```

Auth issuing `press:article:read` does not decide whether a concrete Article is
public. Phoenix continues to apply `CMS.Press` public-stage, audit, archive,
Thread, release, and result-limit rules.

## Pure Service Operations

Pure service operations do not act for a user. Examples include:

```text
Press -> Phoenix
  read bounded current public projections

Phoenix -> Press
  invalidate one community's Press cache

Phoenix -> Assets Hub
  delete a specific stored asset after Phoenix authorizes the lifecycle change

Scheduler -> Content Import
  sweep expired preview records
```

Each direction uses the caller's own identity and the receiving service's
audience:

```text
Press -> Phoenix
  sub: service:press
  aud: phoenix:press-api
  scope: press:article:read

Phoenix -> Press
  sub: service:phoenix
  aud: press:internal-api
  scope: press:cache:invalidate
```

Phoenix must never reuse Press's client credential to call Press. The caller is
Phoenix, so the token subject must be `service:phoenix`.

## User-Delegated Operations

Some workflows require both service proof and a user authority chain:

```text
Dashboard -> Content Import -> Phoenix
Dashboard -> Assets Hub -> Phoenix
Dashboard Server -> Phoenix with a generated BodyBag
future private Press preview
```

A service token alone is insufficient. It proves that the request came from a
service but does not prove that a user may modify the target community or
resource.

The target delegated credential binds:

```text
user subject
service actor
target audience
allowed operation scopes
community/resource constraints where applicable
short expiry
unique token id
```

A JWT representation may use a user `sub` and an `act` claim for the service
actor:

```text
sub       user:<stable-user-subject>
act.sub   service:content-import
aud       phoenix:content-import-api
scope     docs:import:apply
resource_ref  community:<stable-community-subject>
```

`stable-user-subject` is an immutable user-level identifier defined by
Accounts. It is not a login name and is not the Browser Session `publicRef` used
by the V1 device/session UI. The delegated `resource_ref` constraint uses a
separately named stable community identifier; it is not the RFC 8707 token
request `resource`, and these references must not be collapsed into one generic
`publicRef` concept.

Phoenix then requires all of the following:

1. The service is allowed to perform the delegated operation.
2. The user identity is current and allowed to act.
3. Passport/membership permits the concrete action.
4. The community/resource matches the delegated bounds.
5. The target state and business invariants still permit the mutation.

User delegation must not accept arbitrary user-ref headers merely because the
caller has a service token. The delegation credential is minted only after the
user and service authority chain has been validated.

First-party delegation uses one narrowly specified dual-proof transport: the
service token is the HTTP `Authorization` credential and the existing user
access token is carried only in `X-Groupher-User-Authorization`. The resource
server validates both credentials before constructing `delegated_actor`; the
Header cannot carry a user ref, session ref, or other asserted identity. This
avoids minting and propagating a second derived credential while preserving an
explicit, auditable binding between the service actor and current user actor.
A future standards-based token-exchange representation may replace this wire
format without changing the authorization context or middleware contract.

## Press Bootstrap Exception

Until the Press migration reaches V2:

- Press-to-Phoenix reads remain limited to bounded current public projections.
- They do not expose Draft, private, historical, arbitrary revision/release, or
  mutation capabilities.
- `x-groupher-client: press-v1` remains an observability marker and must not be
  treated as authentication.
- Phoenix-to-Press invalidation keeps its independent
  `PRESS_INTERNAL_TOKEN`; it must not reuse the global Phoenix Trust Secret.
- No new unauthenticated Press operation may be added.

Press-to-Phoenix is the preferred first V2 migration because it is read-only,
already has strict public projection bounds, and exercises token issue, JWKS
verification, audience, and operation scopes without beginning with delegated
mutation authority.

## Rotation And Revocation

Client credential rotation:

```text
register next credential
  -> deploy caller with next credential
  -> observe successful token issue
  -> revoke previous credential
  -> confirm no previous-version use
```

Signing-key rotation:

```text
publish next public key in JWKS
  -> start issuing tokens with next kid
  -> retain previous public key through maximum token lifetime + clock skew
  -> remove previous key
```

Disabling a client stops new token issue immediately. Already issued tokens may
remain valid until their short expiry. Per-token `jti` revocation is optional
hardening for emergency or unusually sensitive operations; it must not force
every ordinary request through Auth.

## Failure Semantics

```text
400
  malformed token request or unsupported grant

401
  missing, expired, revoked, or invalid service/delegation credential

403
  valid identity but wrong audience, service, scope, user authority, or
  operation permission

404
  resource absent or not visible to the fully authorized actor

409
  credential rotation or delegation-state conflict requiring reacquisition

429
  token issue or protected operation rate limited

5xx
  temporary Auth or resource-server failure
```

A caller may continue using a still-valid cached service token while Auth is
temporarily unavailable. It cannot bypass expiry or mint a local replacement.
Token acquisition uses bounded retry and single-flight coordination.

## Security Requirements

- Never expose client credentials or service/delegation tokens to browser code.
- Never forward browser Cookies as service authentication.
- Never reuse a credential across services or environments.
- Never use one service's credential when another service is the caller.
- Validate exact audience rather than accepting a platform-wide audience.
- Use allowlisted algorithms and reject unsigned or algorithm-confused tokens.
- Protect token and JWKS endpoints with appropriate cache and transport rules.
- Keep service identity and user authorization separate in middleware and logs.
- Preserve bounded DTOs, rate limits, idempotency, and result-size limits after
  authentication is added.
- Do not put tokens, secrets, authorization headers, or full JWT payloads in
  application logs, metrics, traces, cache keys, or error responses.

## Observability

Record non-sensitive events for:

```text
client credential creation/rotation/disable
service-token issue success/failure
requested and granted audience/scopes
token validation failure category
unknown kid and JWKS refresh
scope and audience rejection
delegation issue and rejection
legacy Trust Secret usage during migration
correlation/request id
```

Logs may include stable service/client references and token `jti` where the
retention policy allows it. They must not include client credentials, token
values, browser credentials, or arbitrary user content.

## Migration Workstreams

Browser Auth V1 does not wait for this migration. If V1 ships first,
Auth-to-Phoenix sign-in/refresh/revoke operations retain the existing bootstrap
trust transport until their V2 edge migrates to `service:auth`. If
`service:auth` is ready first, V1 may consume it without changing the Browser
Session, Cookie, or one-time relogin contract. V2 migrates one service edge at a
time but does not keep the old Trust Secret as a permanent compatibility path.

### Workstream 1: Inventory And Contract

- Enumerate every current Trust Secret, internal token, Cron Secret, caller,
  receiver, operation, user dependency, and environment.
- Classify each edge as pure service or user delegated.
- Define resource-server audiences and operation scopes.
- Confirm which capability tokens remain separate bounded domain credentials.
- Freeze new consumers of the global Trust Secret.

### Workstream 2: Auth Issuer

- Add the service client registry and administrative lifecycle.
- Add the generic client-credentials token endpoint.
- Add short-lived service JWT issue with `kid` and JWKS publication.
- Add current/next credential and signing-key rotation.
- Add rate limits, audit events, and no-secret observability.

### Workstream 3: Shared Verification

- Add Phoenix service-actor context and operation-scope middleware.
- Add equivalent verifier support for Press, Assets Hub, Content Import, and
  future resource servers.
- Keep browser, external-client, service, and delegated token types distinct.
- Add unknown-`kid` refresh, clock-skew, audience, scope, and failure tests.

### Workstream 4: Pure Service Migration

- Migrate Press-to-Phoenix as the first contract proof.
- Migrate Phoenix-to-Press invalidation.
- Migrate Assets Hub and Phoenix callbacks in both directions.
- Migrate scheduled operations to scheduler/job-specific identities.

### Workstream 5: User Delegation

- Define the delegation-issue exchange and claims.
- Migrate Dashboard/Content Import/Phoenix flows.
- Migrate Dashboard/Assets Hub/Phoenix flows where user authority is required.
- Preserve Phoenix Passport and resource-state checks.
- Add confused-deputy, replay, cross-community, and stale-user tests.

### Workstream 6: Cutover And Removal

- Coordinate issuer, resource-server, and caller deployment.
- Revoke and remove `GROUPHER_SERVER_TRUST_SECRET` from every service.
- Revoke and remove `PRESS_INTERNAL_TOKEN` after Phoenix-to-Press migration.
- Remove fallback from domain capability secrets to the global Trust Secret.
- Remove obsolete `server_trusted: boolean` compatibility paths.
- Verify that no static secret silently grants platform-wide trusted-server
  authority.

The workstream order reduces security and operational risk; it is not a plan to
maintain two permanent protocols. Each migrated edge ends on the V2 contract.

## Deferred Hardening

- `private_key_jwt`, workload identity, or mTLS client authentication.
- Automated credential rotation orchestration.
- Emergency per-token `jti` revocation.
- Hardware-backed signing and client keys.
- Risk-based service-token TTLs.
- Full standards-based token exchange for external federation scenarios.

## Acceptance Criteria

- Auth is the only Groupher service-token issuer.
- One generic client-credentials exchange serves all registered first-party
  service clients.
- Every service and environment has a distinct client identity and credential.
- Production, preview, and development use isolated issuer/JWKS trust and
  audience configuration; tokens from one environment fail validation in
  another.
- Every service token has a short expiry, exact audience, bounded scopes, and
  identifiable service subject.
- Resource servers validate Auth JWTs locally through JWKS.
- Resource servers do not call Auth for every protected request.
- No generic administrator or unrestricted trusted-server scope exists.
- A valid service token does not bypass Phoenix Passport, ownership, visibility,
  state, or result-bound checks.
- User-delegated operations bind both the service actor and user actor.
- Delegated user subjects use an immutable user identity distinct from every
  Browser Session/device-list `publicRef`.
- Arbitrary user-ref headers cannot create delegation authority.
- Press cannot use its Phoenix token to call Press, Assets Hub, or another
  audience.
- Phoenix-to-Press invalidation identifies Phoenix as the caller.
- Browser Cookies and browser access tokens are not used as service identity.
- Client credentials and token values never enter browser code, URLs, logs,
  metrics, cache keys, or persisted job payloads.
- Client and signing-key rotation support bounded current/next overlap.
- Disabling one client does not disrupt unrelated services.
- `GROUPHER_SERVER_TRUST_SECRET`, `PRESS_INTERNAL_TOKEN`, and equivalent
  platform-wide static trust paths are removed after their callers migrate.
- No permanent boolean `server_trusted` compatibility path remains.
