# Groupher 浏览器 Auth 与 Session 生命周期 V1

> 状态：浏览器身份验证、Session 连续性和 Phoenix access token 续期的目标合约。
>
> 当前实现：`backend/auth` 拥有 OAuth/Auth.js，并在登录时同时写入 Auth.js
> Session Cookie 和 `groupher-auth.token`。两者当前都使用 14 天有效期。尚无
> 专门的 Phoenix token 续期合约。
>
> 本文档定义目标生命周期，不改变现有的 identity 和 authorization 归属边界。

## 相关文档

- [`docs/sub-apps/auth.md`](../sub-apps/auth.md) 定义已部署的 Auth 子应用、公开
  路由、Cookie 归属和当前实现。
- [`docs/oauth/overview.md`](../oauth/overview.md) 区分浏览器登录和面向 MCP、
  agent、第三方 API client 的 OAuth 授权。
- [`docs/dashboard-to-tanstack/v2.md`](../dashboard-to-tanstack/v2.md) 在 TanStack
  loader、server function、urql 和 Dsb 路由中消费本 Auth 合约，不定义独立的
  refresh 协议。

## 范围

本文档覆盖：

- Main、Dashboard、Dash、Apply 以及未来自研前端应用的浏览器登录连续性。
- Auth.js Browser Session 生命周期。
- Phoenix 浏览器 access token 生命周期和续期。
- Cookie 归属。
- 鉴权后的 SSR、loader、server function 和 GraphQL 行为。
- 过期、无效、撤销或未授权 session 的统一处理。
- 登出、多 tab 行为、重试上限和未来 session 撤销。

本文档在 v1 中不实现：

- 颁发给 MCP、agent 或第三方 client 的 OAuth access token。
- Personal API Token。
- Service-to-service 凭证。其 v2 目标设计记录在下方，以免子应用发明不兼容
  的凭证。
- 面向 Content Import、Assets Hub 或其他 worker 服务的用户 delegation token。
- Community membership 和业务授权规则。

## 原则

1. Auth 拥有浏览器身份验证协议和 session 生命周期。
2. Phoenix 仍然是用户、账号状态、membership 和业务授权的 source of truth。
3. 前端应用消费 Auth 结果，但自身不解码、签发、轮换或撤销 Auth 凭证。
4. Gateway 转发 canonical Phoenix Cookie，但不去解读它。
5. 浏览器凭证保留在 `HttpOnly` Cookie 中，绝不出现在 JSON 中，也不暴露给浏览器
   JavaScript。
6. 过期 Phoenix token 只能在有效的 Auth Browser Session 下进行续期。
7. 每次失败的应用操作最多尝试一次 refresh。
8. `403` 业务授权失败永远不触发 token 续期。
9. 登出使 Browser Session 失效，并清空所有 browser-auth Cookie。
10. 浏览器 auth 与外部 client OAuth 保持为不同的协议。
11. `BroadcastChannel` 只是同源浏览器协调优化，不是跨源或跨设备的身份验证
    authority。

## Authority

```text
Auth
  OAuth/OIDC 登录
  Auth.js Browser Session
  Cookie 生命周期
  Phoenix token 续期 endpoint
  登出

Phoenix Accounts
  用户和 external identity
  账号状态
  browser-session 绑定
  Phoenix access token 签发/重发
  token 校验
  community membership 和业务授权

Gateway
  稳定的公共路由
  Cookie 过滤和转发
  不解析 token

Main / Dashboard / Dash / Apply
  消费身份验证状态
  保护应用路由
  通过共享 Auth consumer 最多重试一次
  渲染登录或无权限状态
```

Auth 证明浏览器拥有有效的 Groupher 登录 session。Phoenix 决定该 session 对应
哪个 Groupher 用户，以及该用户可以做什么。

## 凭证模型

### Auth Browser Session

Cookie：

```text
__Secure-groupher-auth.session-token
```

属性：

- 仅由 `backend/auth` 中的 Auth.js 写入、解码、续期和清除。
- 表达浏览器登录连续性。
- 不得包含 community 权限，也不能成为业务授权的 source of truth。
- 是 Auth 在请求新的 Phoenix 浏览器 access token 时使用的 authority。
- 永不被 Gateway 或产品应用转发给 Phoenix GraphQL。

当前 Auth.js session 策略是基于 JWT 的。session payload 应保持精简，并由
Auth.js 加密/签名。如果未来需求包括按设备撤销、session 清单或跨设备强制登
出，Auth/Phoenix 可以引入持久化的 Browser Session 记录，而不改变本文档中
的前端合约。

### Phoenix Browser Access Token

Cookie：

```text
groupher-auth.token
```

属性：

- 通过 Auth 拥有的 HTTP response 写入和清除。
- 由 Phoenix 通过受信的 Auth-to-Phoenix 操作签发或重发。
- 由 Gateway 和服务端 GraphQL client 以同名 Cookie 转发给 Phoenix。
- 用于 API 身份验证和最终的 Phoenix 授权。
- 一旦引入 refresh 支持，生命周期应短于 Browser Session。
- 不得被浏览器 JavaScript 读取。

该 token 应主要携带稳定的 identity/session claim。业务权限变更仍由 Phoenix
强制执行，不需等待浏览器 token 续期。

### 登录提示

Cookie：

```text
groupher-auth.signed-in
```

属性：

- 不包含凭证。
- 仅可被浏览器代码作为加载优化读取。
- 绝不能视为身份验证的证据。
- 随 Auth Session 和 Phoenix token 一起被清除。

## 当前状态

当前登录流程：

```text
Browser
  -> Auth.js OAuth 流程
  -> Auth 把 provider identity 提交给 Phoenix
  -> Phoenix 返回 groupher-auth.token
  -> Auth.js 签发 Browser Session
  -> Auth 追加 Phoenix token 和 signed-in hint Cookie
  -> Browser 进入 Main / Dashboard / Dash
```

当前约束：

- Auth.js Session 和 Phoenix token 都使用 14 天最大有效期。
- Phoenix token 仅在 Auth.js 实际签发其 Session Cookie 后才追加，避免浏览器
  半登录状态。
- Auth 拥有统一登出，并清空 Auth.js、Phoenix 和 hint Cookie。
- Main、Dashboard、Dash、Gateway 和 Phoenix 不解码 Auth.js Session。
- 还没有 `POST /api/auth/token/refresh` 端点。
- 过期的 Phoenix token 当前需要重新走一次登录流程。

下方的目标 refresh 流程是 Auth 的未来能力。产品应用不得以本地 token 签发作
为临时替代。

## 目标登录流程

Auth-to-Phoenix 登录交换最终应返回：

```ts
type TBrowserSigninResult = {
  accessToken: string
  accessExpiresAt: string
  browserSessionRef: string
}
```

`browserSessionRef` 是一个稳定的、不承载权限的引用，仅供受信的 Auth-to-Phoenix
操作使用。Auth 把它存放在受保护的 Auth.js Session 中。浏览器 JavaScript 和
产品应用永远不直接收到它。

```text
Browser
  -> Auth OAuth callback
  -> Phoenix signin/link identity
  -> Phoenix 检查账号状态
  -> Phoenix 创建或轮换 browserSessionRef
  -> Phoenix 签发短期 access token
  -> Auth 把 browserSessionRef 写入 Auth.js Session
  -> Auth 写入 groupher-auth.token
  -> Auth 跳转到已校验的 returnTo
```

## Refresh 端点

Auth 拥有：

```http
POST /api/auth/token/refresh
```

该端点：

1. 校验 Origin/CSRF 要求。
2. 读取并校验 Auth.js Session。
3. 提取受保护的 `browserSessionRef`。
4. 调用一个受信的 Phoenix browser-session refresh 操作。
5. Phoenix 校验用户、账号、session 和撤销状态。
6. Phoenix 轮换或重发短期 access token。
7. Auth 写入新的 `groupher-auth.token` Cookie。
8. Auth 返回 no-store 响应，不在 JSON 中暴露 token。

成功响应示例：

```http
HTTP/1.1 204 No Content
Cache-Control: no-store
Set-Cookie: groupher-auth.token=<redacted>; HttpOnly; Secure; SameSite=Lax; Path=/
```

如果 consumer 需要，端点可以返回非敏感的元数据如 `expiresAt`，但绝不能返回
凭证值。

### Refresh 响应合约

```text
204
  成功续期

400
  请求格式错误或 CSRF/origin 合约无效

401
  Auth Browser Session 缺失、过期、无效或被撤销

403
  账号被封禁，或 browser session 不再被允许获取 access

409
  session/token family 冲突，需要重新登录

429
  refresh 被限流

5xx
  Auth 或 Phoenix 临时故障
```

产品应用只针对最初的身份验证失败重试 refresh。不能在已重试的请求之后再递
归 refresh。

## 应用 Consumer 合约

Main、Dashboard、Dash、Apply 和未来的自研应用应复用同一个 consumer 合约：

```text
frontend/core/auth/
  refreshSession()
  withAuthRetry()
  resolveAuthFailure()
  clearAuthState()
```

这是一个协议 consumer，不是第二套 Auth 实现。

### 浏览器请求流程

```text
应用操作
  -> 请求 Phoenix/API
  -> 成功
       返回结果
  -> 401 TOKEN_EXPIRED
       进入 single-flight refresh
       POST /api/auth/token/refresh
       refresh 成功
         重试原操作一次
       refresh 失败
         清除本地鉴权相关状态
         携带 returnTo 跳转到登录
  -> 401 TOKEN_INVALID / TOKEN_REVOKED
       不进入循环
       清除本地鉴权相关状态
       跳转到登录
  -> 403
       不 refresh
       渲染权限失败或重新加载 viewer 权限
```

Phoenix 应返回机器可读的身份验证错误码，让 consumer 不必从任意错误信息推断
是否可 refresh：

```text
TOKEN_EXPIRED
TOKEN_INVALID
TOKEN_REVOKED
SESSION_REVOKED
ACCOUNT_BLOCKED
PERMISSION_DENIED
```

### Single-Flight Refresh

在同一个应用 tab/运行时内：

```text
request A -> 401
request B -> 401
request C -> 401

全部等待同一个 refresh promise
  -> 一次 POST /api/auth/token/refresh
  -> 成功之后一次性重试 A/B/C
```

不允许让每个 urql operation、route loader 或 server function 各自触发独立的
refresh 请求。

### 多 tab 行为

将 `BroadcastChannel` 作为可选的同源浏览器优化，用于：

```text
auth:refreshed
auth:logout
auth:invalid
```

完成登出或 refresh 的 tab 在 Auth 请求成功后发布事件。同浏览器源上的其他
tab 收到事件后清除或调和本地状态。

决定是否能这样工作的是浏览器源，而不是部署平台：

```text
https://groupher.com/home
https://groupher.com/home/dashboard
https://groupher.com/home/dash
```

即使 Main 部署在 Vercel、Dash 部署在 Cloudflare，浏览器看到一个源，它们仍能
协调。

不同子域不能使用此 channel：

```text
https://groupher.com
https://dashboard.groupher.com
https://dash.groupher.com
https://auth.groupher.com
```

对于不同源，在页面可见、获得焦点、进入受保护路由或收到身份验证失败时，使
用 Auth Session probe：

```text
GET /api/auth/session
  -> 已认证
       保留本地状态
  -> 未认证/已撤销
       清除受保护的 Valtio 状态
       在需要时返回登录
```

对另一台设备而言，只有服务端 session 撤销和后续的请求或 session probe 才能
让状态收敛。服务端不能直接向另一台设备发布浏览器 `BroadcastChannel` 事件。

这些消息是协调 UI 和重试的提示。Cookie 和服务端 Auth/Phoenix session 仍然
是 source of truth。共享 Auth consumer 拥有该 channel，并调用应用 callback，
如 `clearAuthState()`；Dash 不再定义一套独立的本地广播协议。

## SSR 和服务端运行时流程

SSR loader 和 server function 不能只依赖浏览器侧的重试逻辑。它们使用相同的
Auth consumer 语义：

```text
SSR 请求
  -> 转发 groupher-auth.token 给 Phoenix
  -> Phoenix 接受
       继续 render
  -> Phoenix 返回可 refresh 的 401
       使用该请求的 Auth Cookie 调用 Auth refresh 端点
       从 Auth 接收 Set-Cookie
       转发 Set-Cookie 给浏览器响应
       用续期后的 token 对 Phoenix 重试一次
  -> refresh 失败
       携带已校验的 returnTo 跳转到 Auth 登录
```

共享的服务端 consumer 必须正确传递每一个 Auth `Set-Cookie` 头。产品应用不得
解析或重新签名 Auth.js Session。

如果某个框架无法安全地从当前 SSR 请求传递续期后的 Cookie，应使用经过 Auth
的受控跳转，而不是实现应用本地的 refresh 机制。

## urql、Loaders 和 Server Functions

Auth 生命周期独立于应用的数据归属模型。

```text
TanStack/Next SSR loader
  -> 加载 canonical 数据
  -> 初始化带 scope 的 Valtio store

Core 业务组件
  -> 读取 Valtio
  -> 通过 urql 执行 GraphQL mutation

Auth consumer
  -> 包装底层已鉴权请求
  -> 在允许时 refresh 一次
```

规则：

- Route loader 不拥有 Auth Session 续期。
- Valtio 不存放凭证值。
- urql 不为每个 mutation 实现自己的 refresh 协议。
- Server function 消费相同的共享 Auth 合约。
- Dsb/Main 缓存 revalidation 凭证仍是独立的服务凭证，而不是 Browser Session
  Cookie。

Dashboard To TanStack V2 沿用此模型，并引用本文档，而不是再定义一套 401/refresh
流程。

## 权限变更和 `403`

Token refresh 不是权限 refresh 机制。

```text
401
  鉴权凭证缺失、过期、无效或被撤销

403
  已认证用户不被允许执行该操作
```

`403` 时：

- 不调用 `/api/auth/token/refresh`。
- Phoenix 仍是 authority。
- 在有用处时重新加载 viewer/community 权限数据。
- 清除或禁用受保护的本地 workflow。
- 在安全时保留未保存的草稿。
- 渲染稳定的无权限状态或离开受保护路由。

如果 Phoenix 在浏览器 access token 中嵌入了粗粒度授权 claim，这些 claim 必须
是短期的，并且 Phoenix 必须仍然针对当前服务端状态强制执行敏感授权。

## 登出

登出仍是 Auth 拥有：

```http
POST /api/auth/logout
```

流程：

```text
Browser
  -> Auth 登出
  -> 撤销已持久化的 browser session（若可用）
  -> 清除 Auth.js Session Cookie
  -> 清除 groupher-auth.token
  -> 清除 groupher-auth.signed-in
  -> 返回 no-store 响应
  -> 广播 auth:logout
  -> 产品应用清除 viewer 和受保护的 Valtio store
```

应用不得单独只清一个 Cookie，留下半鉴权状态。

## Cookie 要求

凭证 Cookie 应使用：

```text
HttpOnly
Secure（在生产和 HTTPS 开发环境）
SameSite=Lax
Path=/
仅在需要跨子域共享时显式设置父 Domain
```

额外要求：

- 不要把凭证值放进 `localStorage` 或 `sessionStorage`。
- 不要向浏览器 JavaScript 暴露 refresh 凭证。
- 不要记录 Cookie 值或 token payload。
- 校验所有 return URL 是否在自研 allowlist 内。
- 对 refresh 和登出等状态变更端点加 CSRF 保护。
- Auth/session/token 端点返回 `Cache-Control: no-store`。
- 登录和涉及权限的 session 变更之后轮换标识符。

自定义 community 域名不能直接共享 Groupher 父域 Cookie。它们需要单独的
一次性 code exchange 流程。

## 过期和轮换策略

具体 TTL 仍属于部署/安全决策，但相对关系是固定的：

```text
Phoenix 浏览器 access token TTL
  较短

Auth Browser Session 闲置/绝对生命周期
  较长
```

推荐策略形态：

```text
access token
  短期
  仅能通过 Auth 续期

browser session
  闲置超时
  绝对最大生命周期
  由 Auth.js 续期/轮换

upstream provider refresh token
  仅在需要时由 Auth 存储
  at rest 加密
  按 provider 支持情况轮换/撤销
  永不转发给产品应用
```

如果 Phoenix 使用持久化的 `browserSessionRef`，refresh 应轮换 token family
或版本，以便拒绝被重放的旧凭证。检测 refresh-token 或 session-family 复用
应撤销受影响的 session 并要求重新登录。

## 失败和可用性策略

在静默接受过期或不可校验的凭证和正确性之间，优先正确性。

```text
Auth 不可用，access token 仍有效
  当前 Phoenix 请求可继续

Auth 不可用，access token 已过期
  不要绕过过期
  在安全时展示可恢复的 auth-unavailable 状态或跳转

refresh 期间 Phoenix 不可用
  返回临时失败
  不要在本地签发 token

refresh 反复失败
  达到有限重试后停止
  发出结构化日志/指标
  当失败非临时时要求重新登录
```

Refresh 端点必须限流并可观测，但不能记录 secret。

## 安全和可观测性

记录：

```text
refresh 尝试次数
refresh 成功/失败原因
Auth Session 过期/撤销
Phoenix token 过期/撤销
401 重试成功率
按操作统计的 403 率
登出成功
开放重定向拒绝
CSRF/origin 拒绝
```

绝不记录：

```text
Auth.js Session payload
Phoenix token
provider access/refresh token
Cookie 头
OAuth 授权码
```

使用 correlation/request ID 而不是凭证，在 Gateway、Auth、Phoenix 和产品应
用间追踪一次流程。

## 扩展边界

### 服务身份和 Client Credentials (V2)

Auth v2 将为 Press 和其他受信子应用提供一个统一的服务身份协议。Auth 拥有
凭证生命周期；Phoenix 仍是 service scope、业务授权和数据可见性的 authority。

职责划分：

```text
Auth
  service client registry
  client-credentials 交换
  短期 service-token 签发
  签名密钥、kid、JWKS、轮换和撤销
  token 签发审计和限流

Phoenix
  允许的 service 和 scope 定义
  内部操作的 scope 校验
  community/content 可见性
  业务限速和结果大小限制
  最终的 401/403/404 决策

子应用
  保护自身 client credential
  请求并缓存一个短期 token
  仅把 token 发给其预期 audience
  永不转发浏览器 Cookie 或浏览器 Authorization
```

目标交换：

```text
Press
  -> Auth client-credentials 端点
  -> Auth 校验 service client 和允许的 scope
  <- 短期 service JWT
  -> Phoenix 内部 GraphQL，Authorization: Bearer <service-jwt>
  -> Phoenix 从 Auth JWKS 本地校验签名
  -> Phoenix 校验 service、audience、scope 和域可见性
```

Auth 和 Phoenix 不能为每一个受保护请求互相调用。Auth 通过 JWKS 公开签名密
钥；Phoenix 在本地校验 service JWT。

最低 claim：

```text
iss    = Groupher Auth
sub    = service:<service-name>
aud    = <target-service>
scope  = bounded operation scopes
iat
exp
jti
kid
```

Service token 必须是短期的且绑定 audience。不允许出现泛化的管理员 scope。示
例包括：

```text
service:press
aud: phoenix:press-api
scope: press:article:read press:rss-feed:read press:site:read
```

Auth 拥有 client 注册、凭证轮换、token 签发、撤销、JWKS 和审计。Phoenix 拥
有一个 scope 是否可以访问具体 community 或资源的决定权。把 token 签发移到
Auth 并不会把 CMS 权限或数据过滤从 Phoenix 移走。

Public Press v1 是一个明确的 bootstrap 例外：它不实现应用层 service-token 校
验，其 Phoenix 操作只返回有界的当前公开内容。这些操作不得暴露 Draft、private、
历史、任意 snapshot/release 或 mutation 能力。Press v2 沿用这套 client-credentials
合约。

User delegation 是一个单独的扩展。未来的 private preview 流程必须把 service
身份绑定到 user/session、community、resource scope、audience 和短期过期；它
不能扩展 public Press service 身份。

失败语义：

```text
401
  service token 缺失、过期、撤销或无效

403
  错误的 audience、service 或 scope

404
  资源不存在或对已授权主体不可见

429
  client-credentials 或受保护操作限流
```

运维要求：

- 不要把 service client secret 或 service JWT 放进浏览器代码、Cookie、URL、
  日志、指标或 cache key。
- 不同的服务和环境使用不同的 client credential。
- 支持新旧凭证和签名密钥重叠以进行轮换。
- 记录 client ref、audience、scope、结果和 correlation ID，但不记录凭证值。
- 产品 Gateway 路由流量，但不签发、解码或交换 service 凭证。

### 额外的 Web Identity Provider

GitHub、Google、Apple 和客户 OIDC/SAML provider 都在 Auth 处终结。它们被规
范化为相同的 Phoenix identity 交换和 Browser Session 合约。

### 外部 Client

MCP、agent、CLI 工具和第三方 API client 使用 [`docs/oauth/overview.md`](../oauth/overview.md)
中单独的 OAuth Provider 或 API Token 架构。它们不使用 Browser Session refresh
端点。

### 设备和 Session 管理

未来的需求，例如：

- 列出活跃设备。
- 撤销一台设备。
- 撤销所有 session。
- 要求近期身份验证。
- Step-up authentication。
- 基于风险的 session 撤销。

应扩展 Auth/Phoenix 的 `browserSessionRef` 模型。它们不应要求 Main、Dashboard、
Dash 或 Apply 去解码 Auth.js Session 内部。

## 迁移阶段

### Phase 1: 共享 Consumer 语义

- 标准化 Phoenix 身份验证错误码。
- 加入共享的 401/403 分类。
- 加入 single-flight refresh 抽象，但不启用 refresh。
- 保持当前 fallback：过期的 Phoenix token 跳转到登录。
- 加入跨 tab 登出协调。

### Phase 2: Refresh 合约

- 用 `browserSessionRef` 扩展 Auth/Phoenix 登录交换。
- 把引用存放在受保护的 Auth.js Session 中。
- 加入受信的 Phoenix browser-session refresh 操作。
- 加入 `POST /api/auth/token/refresh`。
- 仅通过 Auth 重发 Phoenix token。
- 为浏览器和 SSR consumer 加入 Cookie 传递。

### Phase 3: 短期 Phoenix Token

- 缩短 Phoenix 浏览器 token TTL。
- 保持更长的有限 Auth Browser Session 生命周期。
- 启用 single-flight refresh 和一次性请求重试。
- 加入 refresh 指标、限流和运维告警。

### Phase 4: 撤销和设备 Session

- 在产品/安全需求需要时持久化 browser session。
- 加入按 session 和全 session 撤销。
- 加入 token/session family 轮换和复用检测。
- 必要时加入面向用户的设备/session 管理。

### Phase 5: Service Identity

- 加入 Auth 拥有的 service client 注册和凭证轮换。
- 加入 client-credentials token 端点。
- 加入短期、绑定 audience 的 service JWT 和 JWKS。
- 加入 Phoenix 本地校验和操作级 service scope。
- 把 Press 和其他子应用从 bootstrap 信任迁移到共享协议。
- 加入签发、校验、撤销和轮换指标，但不记录凭证。

## 验收标准

- Auth 仍然是唯一读取或写入 Auth.js Session 状态的组件。
- 产品应用永远不签发或解码浏览器凭证。
- Phoenix 仍然是用户和业务权限的最终 authority。
- 过期 Phoenix token 最多触发一次 refresh 尝试。
- `403` 永远不触发 refresh。
- Refresh 永远不在 JSON 中返回凭证值。
- 续期后的 `Set-Cookie` 头在 SSR 流程中到达浏览器。
- 并发失败在同一个应用运行时内产生一个 refresh 请求。
- 登出清空所有 Auth 和 Phoenix 浏览器 Cookie。
- 多 tab 登出清空受保护的应用状态。
- 同源登出/refresh 事件使用共享 Auth consumer 的 `BroadcastChannel` 优化；
  跨源和跨设备状态使用 Auth Session probe 或身份验证响应。
- Auth/session/token 端点返回 `Cache-Control: no-store`。
- 浏览器凭证永不进入浏览器存储或日志。
- Dashboard To TanStack V2 引用本合约，而不是定义自己的 token 生命周期。
- Service credential 使用 Auth 拥有的 v2 client-credentials/JWKS 合约，而不是
  产品专属的 token 协议。
- 在 Auth 签发 service token 之后，Phoenix 仍然是 service scope 和业务数据
  可见性的最终 authority。
