## 确认 V1 决策

```text
Phoenix browser access-token TTL
  30 minutes

Auth Browser Session absolute lifetime
  90 days from the initial OAuth sign-in
  never extended by refresh or Auth.js Cookie rotation
  host-only on auth.groupher.com

Phoenix browser access Cookie scope
  Domain=.groupher.com
  shared for at most the token's 30-minute lifetime

Idle timeout
  not enabled in V1

Existing sessions at cutover
  invalidated once
  users complete OAuth sign-in again

GitHub provider token
  used only during sign-in
  not retained after identity establishment

Cookie topology
  90-day Auth Browser Session -> host-only auth.groupher.com
  30-minute Phoenix access token -> Domain=.groupher.com
  non-sensitive signed-in hint -> Domain=.groupher.com, never authentication proof

Endpoint ownership
  OAuth, Session probe/list, refresh, logout, and revoke -> canonical Auth
  browser GraphQL -> current-origin Gateway -> Phoenix
  Session list/revoke in Phoenix -> trusted Auth operations, not browser mutations

Browser state-change CSRF
  exact approved Origin + X-Groupher-CSRF: 1
  required by Auth refresh/logout/revoke and browser GraphQL POST

Origin capabilities
  groupher.com, main, dashboard, and dash -> explicit Auth capabilities
  landing.groupher.com -> public-only, no Auth capability
```

共享前端消费者位于 `frontend/core/lib/auth/` 下，并且是
通过 `~/auth` 别名导出。现有的`frontend/core/lib/oauth.ts`
登录和注销实现在该入口点之后移动
重构。

## 原则

1. Auth 拥有浏览器身份验证协议和会话生命周期。
2. Phoenix 仍然是用户、账户状态、会员资格和信息的真实来源
   业务授权。
3. 前端应用程序消耗 Auth 结果，但不解码、铸造、旋转、
   或自行撤销 Auth 凭据。
4. Gateway 转发规范的 Phoenix Cookie 但不解释它。
5. Browser 凭证保留在 `HttpOnly` Cookies 中并且永远不会返回
   JSON 或暴露于浏览器 JavaScript。
6. 过期的 Phoenix 令牌只能通过有效的 Auth Browser 进行更新
   Session。
7. 每次失败的应用程序操作最多尝试刷新一次。
8. `403`业务授权失败永远不会触发令牌刷新。
9. 注销会使 Browser Session 无效并清除每个浏览器身份验证 Cookie。
10. Browser auth 和外部客户端 OAuth 仍然是单独的协议。
    11、`BroadcastChannel`仅是同源浏览器协调优化；
    它不是跨域或跨设备的身份验证机构。
11. GitHub OAuth 证明在登录期间控制 GitHub 帐户；随后的
    Groupher 登录连续性由 Auth Browser Session 和
    Phoenix 访问令牌，而不是 GitHub 令牌生命周期。
12. V1不创建第二个登录UI。 Main、Dashboard 和 Dash 重复使用
    现有的共享登录模式。## 当局

```text
Auth
  OAuth/OIDC login
  Auth.js Browser Session
  Cookie lifecycle
  Phoenix token renewal endpoint
  logout

Phoenix Accounts
  user and external identity
  account state
  persisted Browser Session records
  Phoenix access-token issue/reissue
  token validation
  community membership and business authorization

Gateway
  stable public routing
  Cookie filtering and forwarding
  no token parsing

Main / Dashboard / Dash / Apply
  consume authentication state
  protect application routes
  retry once through the shared Auth consumer
  render login or no-permission states
```

Auth 证明浏览器拥有有效的 Groupher 登录会话。 Phoenix决定
该会话代表哪个 Groupher 用户以及该用户可以执行哪些操作。

受信任的 Auth 到 Phoenix 传输是独立版本化的。 Browser Auth
V1 可以继续使用现有的引导服务器信任凭证；之后
[`v2.md`](./v2.md) 可用，相同的操作迁移到
`service:auth` 具有确切的 Phoenix 受众和帐户/会话范围。 V1
不需要 V2 来完成其 Browser Session 切换。

## 凭证模型

### Auth Browser Session

Cookie：

```text
__Host-groupher-auth.session-token
```

属性：

- 仅由Auth.js在`backend/auth`内写入、解码、更新和清除。
- 表示浏览器登录的连续性。
- 不得包含社区权限或成为业务授权
  真相的来源。
- 请求新的Phoenix浏览器访问时Auth使用的权限
  令牌。
- 仅在 `auth.groupher.com` 上为主机，没有 `Domain` 属性，并且从不
  发送到产品子域。
- 绝不会由 Gateway 或产品应用程序转发到 Phoenix GraphQL。
- 从首次 OAuth 登录开始计算，具有 90 天的绝对生命周期。
- 仅存储稳定的`browserSessionRef`、绝对到期和其他最小
  Session协调数据；它不存储 Groupher 角色或权限。

当前的 Auth.js 会话策略是基于 JWT 的。会话有效负载应该
保持最小并由 Auth.js 加密/签名。 Auth.js 可能会轮换或更新
Cookie，但必须保留原来的`sessionAbsoluteExpiresAt`；活动
绝不能将 Session 超出其最初的 90 天界限。

### Phoenix Browser 访问令牌

Cookie：

```text
groupher-auth.token
```

属性：

- 通过Auth拥有的HTTP回复编写和清除。
- 由 Phoenix 通过可信的 Auth 到 Phoenix 操作发行或重新发行。
- 由Gateway和服务器端GraphQL以相同的Cookie转发到Phoenix
  客户。
- 用于API身份验证和最终Phoenix授权。
- V1 的最长寿命为 30 分钟。
- 具有稳定的身份和Session声明，包括`iss`，
  `aud=phoenix:browser-api`、`sub`、`sid`、`iat`、`exp` 和
  `typ=browser_access`;它不带有可变的业务权限
  授权事实来源。
- 不得由浏览器JavaScript读取。

令牌应主要承载稳定的身份/会话声明。商务
权限更改仍然可以由 Phoenix 强制执行，无需等待浏览器
令牌更新。 Phoenix 验证预期的发行者、确切的受众、令牌
类型、签名和有效期；浏览器令牌不被另一个浏览器接受
资源服务器。

### 登录提示

Cookie：

```text
groupher-auth.signed-in
```

属性：

- 不包含任何凭证。
- 只能作为加载优化被浏览器代码读取。
- 绝不能被视为身份验证的证明。
- 使用 Auth Session 和 Phoenix 令牌清除。
- 遵循 90 天 Browser Session 生命周期，而不是 30 分钟访问
  令牌生命周期。过时的提示可能会启动探测或刷新，但永远不会授予
  自行访问。

### 坚持Browser Session

Phoenix 帐户为每次独立的浏览器登录保留一条记录。一个
Browser Session 不是物理设备指纹：不同的浏览器或
一台机器上的浏览器配置文件创建不同的会话，而一个位置
同一浏览器中的更改会更新现有的Session。

`browserSessionRef` 是一个不透明的、未经许可的查找引用。它
不包含编码的用户、时间、设备或位置字段。 Phoenix 生成它
来自加密安全的随机字节，例如后面跟着 `bs_` 前缀
由 32 个随机字节编码为未填充的 base64url。

V1 记录包含：```text
ref
public_ref
user_id
status active | revoked
created_at
absolute_expires_at
last_refreshed_at
last_seen_at
revoked_at
revoked_reason

browser_family
os_family
device_family
user_agent_summary

created_country
created_region
created_city
last_seen_country
last_seen_region
last_seen_city

````

用户代理和 IP 派生位置是近似的显示元数据，而不是
认证因素。 V1仅存储所需的最小粗略位置
Session UI，在粗略位置推导后不会保留原始 IP，
并且不引入浏览器指纹识别。 Session 活动元数据是
在成功刷新或显式 Session 探测期间更新，而不是通过
写入每个 GraphQL 请求。

`ref` 和 `public_ref` 都是唯一的、不可猜测的值。坚持
层按 `user_id` 和到期索引活动会话，并运行有界清理
过期/撤销记录的策略，因此设备列表和 Session 表不会
无限期地成长。

内部的`ref`是`browserSessionRef`存储在Auth.js中，访问
令牌`sid`；它永远不会返回到浏览器JavaScript。 Session-管理 API
返回一个单独的随机 `publicRef` 加上服务器计算的 `isCurrent` 标志。
经过身份验证的用户使用 `publicRef` 撤销自己的会话之一，而
Phoenix 解析所有权和内部引用服务器端。

Auth 从实际的回调/刷新请求中派生连接元数据，并
可信平台转发标头，对其进行标准化，并将其传递给 Phoenix
通过可信的操作。 Phoenix 不得接受任意客户端提供的
IP、当前-Session 或所有权字段。

## 当前状态

目前的登录流程是：

```text
Browser
  -> Auth.js OAuth flow
  -> Auth submits provider identity to Phoenix
  -> Phoenix returns groupher-auth.token
  -> Auth.js issues Browser Session
  -> Auth appends Phoenix token and signed-in hint Cookies
  -> Browser enters Main / Dashboard / Dash
````

目前的限制：

- Auth.js Session 和 Phoenix-令牌 Cookies 使用 14 天的 `Max-Age`，但是
  `groupher-auth.token` 内的 Guardian JWT 目前有 30 天的内部
  到期。因此，复制的令牌可以比承载的浏览器 Cookie 更长寿。
  它。
- Phoenix 令牌仅在 Auth.js 实际发出其 Session 之后附加
  Cookie，防止半登录浏览器状态。
- Auth拥有统一注销并清除Auth.js、Phoenix和提示Cookies，但它
  不会撤销持久的服务器端 Browser Session，因为不存在。
- Main、Dashboard、Dash、Gateway 和 Phoenix 不解码 Auth.js Session。
- 当前共享的 Auth.js Cookie 覆盖将父域应用于 CSRF，
  回调、状态、PKCE、随机数和挑战 Cookies 以及 Session；
  V1 使 Session 和协议 Cookies 仅限主机，仅保留
  父域上的短暂 Phoenix 令牌和提示。
- 尚无 `POST /api/auth/token/refresh` 端点。
- 过期的 Phoenix 令牌当前需要新的登录流程。
- 共享帐户UI调用现有的登录模式；没有独立的
  规范的 `/login` 页面。

下面的目标刷新流程是未来的 Auth 功能。产品应用
不得将本地代币铸造作为临时替代品。

## 目标登录流程

现有的共享登录模式仍然是产品 UI，但 OAuth 协议
从规范的 Auth 源开始，因此 Auth.js 协议 Cookies 可以保留
仅主机：

```text
Login Modal on an approved product origin
  -> credentialed GET https://auth.groupher.com/api/auth/csrf
  -> Auth sets a host-only __Host-groupher-auth.csrf-token
  -> top-level POST https://auth.groupher.com/api/auth/signin/<provider>
     with the CSRF token and validated returnTo
  -> Auth sets host-only callback/state/PKCE/nonce Cookies
  -> OAuth provider
  -> https://auth.groupher.com/api/auth/callback/<provider>
  -> Auth validates the host-only protocol Cookies
  -> Auth writes the host-only Browser Session
  -> Auth writes the parent-domain Phoenix token and hint
  -> redirect to validated returnTo
```

Canonical Auth 允许从确切批准的产品来源获得认证 CORS
功能注册表仅适用于 CSRF 引导程序、Session 探测/列表、刷新、
注销，并Session撤销。 OAuth 状态改变 POST 仍然使用 Auth.js
仅主机双重提交 CSRF 合约。产品原产地不代表OAuth
通过自己的 `/api/auth/*` 路径授权启动或回调。

Auth.js协议Cookies包括CSRF，回调URL，OAuth状态，PKCE验证器，
随机数和 WebAuthn 挑战 Cookies。他们使用 `Secure`, `HttpOnly` 其中
协议允许，`SameSite=Lax`、`Path=/`、不`Domain`和`__Host-`
支持的前缀。 Groupher 刷新或注销不会重复使用它们。V1 Auth 到 Phoenix 登录交换返回：

```ts
type TBrowserSigninResult = {
  accessToken: string
  accessExpiresAt: string
  browserSessionRef: string
  sessionAbsoluteExpiresAt: string
  user: User
}
```

`browserSessionRef` 是一个稳定的、无需许可的引用，仅供
可信的Auth到Phoenix操作。 Auth 将其存储在受保护的 Auth.js 中
Session。 Browser JavaScript 和产品应用程序永远不会直接收到它。

### V1 恢复和登录不变量

浏览器恢复路径由显式 Session 探针驱动，而不是由
从可为空的公共身份字段推断身份验证：

```text
browser GraphQL operation
  -> Phoenix sessionState probe
     -> valid token: { isValid: true, user }
     -> no token: { isValid: false } (anonymous; no refresh loop)
     -> invalid/expired token: errors[].extensions.code
  -> TOKEN_MISSING / TOKEN_EXPIRED
     -> one shared canonical-Auth refresh
     -> replay the original operation once
  -> TOKEN_INVALID / TOKEN_REVOKED / SESSION_REVOKED
     -> clear auth-sensitive client state and request login
  -> 403
     -> render the permission failure; never refresh
```

`me` 仍然是可为空的公共身份查询。 `me: null` 结果不得
开始刷新，因为这也是匿名请求的正确结果。
消费者在需要时使用专用的`sessionState`合约
区分匿名状态和无效的浏览器凭据。

OAuth 回调跨越两个独立的持久性边界。 Phoenix
首先创建持久化的 Browser Session； Auth 然后发出仅主机
Auth.js Session Cookie。如果 Auth.js 失败或未发出 Cookie、Auth
必须撤销刚刚创建的 `browserSessionRef` 作为补偿操作
返回失败。这可以防止服务器端 Browser Session 没有
对应浏览器Session并且不引入跨服务事务
或Session权威的第二来源。

连接元数据遵循相同的所有权规则。 Auth 限制传入
可信调用之前的用户代理，并且 Phoenix 在
Browser Session 数据库限制的持久性边界（`255` 个字符
对于 V1 摘要字段）。因此，Phoenix 持久不变量仍然存在
对于每个受信任的调用者都是如此，而不仅仅是 OAuth 回调。

在独立 Service Identity V2 迁移过程中，可信操作
此流程使用 `sub=service:auth`，一个确切的 Phoenix 帐户受众，并且有界
OAuth/会话范围。在此之前，他们保留现有的引导信任
运输而不更改此Browser Session响应合同。

```text
Browser
  -> Auth OAuth callback
  -> Phoenix signin/link identity
  -> Phoenix checks account state
  -> Phoenix creates a persisted Browser Session with a 90-day absolute expiry
  -> Phoenix issues a 30-minute accessToken
     with aud=phoenix:browser-api and sid=browserSessionRef
  -> Auth stores browserSessionRef and the absolute expiry in Auth.js Session
  -> Auth writes groupher-auth.token
  -> Auth discards the GitHub provider token after identity establishment
  -> Auth redirects to validated returnTo
```

Phoenix 作为代币发行者，设置 JWT `iat` 和 `exp` 声明并返回
`accessExpiresAt`。 Auth 不得从 Cookie 配置推断令牌过期。
访问令牌 Cookie 有效期不得超过 `accessExpiresAt` 或
Browser Session绝对到期。

## 刷新端点

Auth 拥有：

```http
POST https://auth.groupher.com/api/auth/token/refresh
```

这是直接发送到规范 Auth 源的浏览器发起的请求
与`credentials: include`。调用时是跨域但同站的
Main、Dashboard 或 Dash。产品来源 Gateway 路由不会代理它，因为
他们无法接收仅限主机的 Auth Browser Session。

请求必须包含准确批准的 HTTPS `Origin` 和非简单
`X-Groupher-CSRF: 1` 标头。 Auth 的认证 CORS 政策允许确切的
来源和标题； Auth 拒绝之前丢失、`null` 或未经批准的来源
阅读Browser Session。该合约不依赖于 Auth.js 的
仅主机 CSRF Cookie 并且不会仅仅因为产品服务器可以
到达Auth。

终点：

1. 验证 Groupher Origin/custom-header CSRF 合约。
2. 读取并验证 Auth.js Session。
3. 提取受保护的`browserSessionRef`。
4. 调用可信的 Phoenix 浏览器会话刷新操作。
5. Phoenix 验证用户、帐户、会话和吊销状态。
6. Phoenix 在 `now >= sessionAbsoluteExpiresAt` 时拒绝请求。
7. Phoenix 更新有界 Session 活动/设备元数据并重新发出
   30 分钟访问令牌，上限为绝对 Session 到期时间。
8. Auth 写入新的 `groupher-auth.token` Cookie。
9. Auth 返回无存储响应，而不暴露 JSON 中的令牌。

成功响应示例：

````http
HTTP/1.1 204 No Content
Cache-Control: no-store
Set-Cookie: groupher-auth.token=<redacted>; HttpOnly; Secure; SameSite=Lax; Path=/; Domain=.groupher.com
```如果消费者
需要它，但它绝不能返回凭证值。

### 刷新响应合约

```text
204
  refreshed successfully

400
  malformed request or invalid CSRF/origin contract

401
  Auth Browser Session missing, expired, invalid, or revoked

403
  account blocked or browser session no longer allowed to obtain access

409
  session/token family conflict that requires a new login

429
  refresh rate limited

5xx
  temporary Auth or Phoenix failure
````

产品应用程序仅针对原始身份验证重试刷新
失败。它们在重试请求后不会递归刷新。

## Browser 状态改变 CSRF 边界

父域 Cookies 是跨 Groupher 子域的同一站点，因此
`SameSite=Lax` 不是它们之间的 CSRF 边界。每个浏览器都经过身份验证
状态更改必须强制执行应用程序级 CSRF 合约：

```text
Auth refresh/logout/Session-revoke
  browser calls the canonical Auth origin directly with credentials: include
  exact approved HTTPS Origin
  X-Groupher-CSRF: 1
  reject missing/null/unapproved Origin

Gateway browser GraphQL route
  for browser requests, accept application/json only
  preserve the browser Origin unchanged
  require X-Groupher-CSRF: 1 on every POST before proxying
  reject form-urlencoded and multipart browser requests

Phoenix GraphQL mutation
  reject mutation over GET
  when authentication came from groupher-auth.token Cookie:
    revalidate exact Origin and X-Groupher-CSRF
  when authentication came from a V2 service/delegation credential:
    use the service/delegation verifier, not browser Origin
```

Gateway 提供早期拒绝边界； Phoenix 仍然是决赛
防御，并且不得相信来自 Gateway 的合成或覆盖的起源或
产品服务器。 Browser-原始服务器功能保留原始
来源和 CSRF 标头。后台 SSR 查询可能会使用浏览器令牌
SSR 规则如下，但背景 SSR 不得引发突变。

自定义标头会阻止纯 HTML 表单满足合同，并且
精确来源验证拒绝未经批准的同级来源。两种机制都没有
防止 XSS 或受损的批准来源。那些起源就在里面
V1 凭证信任边界并需要部署、DNS、CSP、依赖项、
和子域接管控制。 CORS 单独的响应标头不是 CSRF
执行；请求处理程序必须在出现副作用之前拒绝请求。

Auth、Gateway、Phoenix 和规范 Auth 的凭据浏览器 - API CORS
策略使用一个环境范围的确切来源注册表，而不是
维护不相关的硬编码数组。制作匹配方案及主机
没有意外的端口；开发注册显式方案/主机/端口元组
并且不允许任意 `*.localhost` 原点。

## 应用消费者合约

Main、Dashboard、Dash、Apply 和未来的第一方应用程序应重用
单一消费者合同：

```text
frontend/core/lib/auth/
  signIn()
  signOut()
  refreshSession()
  listSessions()
  revokeSession(publicRef)
  revokeOtherSessions()
  withAuthRetry()
  resolveAuthFailure()
  clearAuthState()
  requestLogin()
  sessionChannel()
```

该包通过 `~/auth` 别名导出。现有的
`frontend/core/lib/oauth.ts` 行为在该入口点后面移动
重构。这是一个协议使用者，而不是第二个 Auth 实现。

### Browser 请求流程

```text
application operation
  -> request Phoenix/API
  -> success
       return result
  -> protected operation returns 401 TOKEN_EXPIRED / TOKEN_MISSING
       enter single-flight refresh
       POST https://auth.groupher.com/api/auth/token/refresh
       refresh succeeds
         retry original operation once
       refresh fails
         clear local auth-sensitive state
         request the existing Login Modal with returnTo
  -> 401 TOKEN_INVALID / TOKEN_REVOKED
       do not loop
       clear local auth-sensitive state
       request the existing Login Modal
  -> 403
       do not refresh
       render permission failure or reload viewer permissions
```

Phoenix 应返回机器可读的身份验证错误代码，以便消费者
不要从任意错误消息推断可刷新性：

```text
TOKEN_EXPIRED
TOKEN_MISSING
TOKEN_INVALID
TOKEN_REVOKED
SESSION_EXPIRED
SESSION_REVOKED
ACCOUNT_BLOCKED
PERMISSION_DENIED
```

GraphQL 可以在成功的 HTTP 响应中传输这些失败。乌尔克尔,
接下来，Dash必须保存并分类`errors[].extensions.code`；他们必须
在 Auth 处理之前不要将错误平铺到消息字符串中。

`TOKEN_MISSING` 30 分钟访问 Cookie 过期后出现问题：浏览器
不再发送过期的 Cookie，因此 Phoenix 无法返回 `TOKEN_EXPIRED`
它。消费者仅在经过身份验证的情况下尝试刷新 `TOKEN_MISSING`
路线或运营边界，可选地由非权威机构告知
登录提示。匿名公共操作不得启动刷新循环。

Cookie-损失行为是确定性的：

```text
access Cookie present
  send the authenticated operation normally

access Cookie missing at an authenticated route/operation boundary
  call canonical Auth for one refresh/session check with credentials: include
  the signed-in hint may trigger this earlier but is not required

Auth Session still present and valid
  refresh the access Cookie

canonical Auth reports no Session, and access Cookie and signed-in hint are absent
  treat the browser as anonymous
  do not try to recover identity from device, IP, or server-side Session rows
  request OAuth login when the route/operation requires authentication
```

已清除 Cookies 的持久化 Browser Session 变得无法访问
该浏览器仅保留到撤销、绝对到期或保留为止
清理。无Cookie探测器无法安全地重新发现它。

### 单次飞行刷新

刷新是需求驱动的，而不是间隔驱动的。产品应用不得
仅仅因为访问令牌 TTL 为 30 就启动 30 分钟计时器或轮询 Auth
分钟。仅当经过身份验证的路由/操作到达时，运行时才会刷新
记录的 `TOKEN_EXPIRED` / `TOKEN_MISSING` 边界，或立即
在已知的长时间运行的受保护操作之前，当共享 Auth 消费者
具有可靠的过期元数据。

因为 `groupher-auth.token` 是父域 Cookie，所以一次成功刷新
替换 Main、Dashboard、Dash 和其他 Groupher 子域使用的令牌：```text
Dashboard encounters TOKEN_MISSING
-> calls canonical Auth once
-> Auth writes a new Domain=.groupher.com access Cookie

Main sends its next protected request
-> browser automatically carries the refreshed Cookie
-> Main does not refresh again

````

应用程序不需要读取 HttpOnly Cookie 或通知其他来源
获得这个好处。浏览器的Cookie存储是跨域汇聚
机制。

在一个应用程序选项卡/运行时内：

```text
request A -> 401
request B -> 401
request C -> 401

all await one refresh promise
  -> one POST https://auth.groupher.com/api/auth/token/refresh
  -> retry A/B/C once after success
````

不允许每个 urql 操作、路由加载器或服务器函数触发
独立的刷新请求。

不同的起源无法共享内存中的单次飞行承诺，并且可能会发生竞争
当他们同时遇到到期时。刷新和 Phoenix 令牌
因此，重新发行是幂等的，并且可以容忍小量的等价爆发
请求。添加一个短的服务器端合并窗口，由
`browserSessionRef` 仅当生产指标显示有意义的重复时；
V1 没有添加抢占式分布式锁。速率限制必须容忍这种情况
合法的跨源种族。

Canonical Auth 可能会返回有界的 `Access-Control-Max-Age` 成功
预检响应以减少重复的 CORS 预检。 Auth 仍然验证
每次实际请求来源、CSRF标头、Session和速率限制；缓存的
预检从来都不是身份验证证明。

凭证规范-Auth 路由使用显式的预检合约：

```http
Access-Control-Allow-Origin: <exact-approved-origin>
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: Content-Type, X-Groupher-CSRF
Access-Control-Max-Age: <bounded-seconds>
Vary: Origin
```

`OPTIONS` 处理程序验证请求的 Origin、方法和标头，但是
不需要登录Cookie。实际请求执行完整
来源、CSRF、Session、授权和速率限制检查。通配符的起源
并且不允许使用通配符凭证标头。只读 Session 列表
使用经过认证的 CORS 和 `Cache-Control: no-store`；它不需要
状态更改 CSRF 标头。

### 多选项卡行为

使用 `BroadcastChannel` 作为可选的同源浏览器优化：

```text
auth:refreshed
auth:logout
auth:invalid
```

完成注销或刷新的选项卡在 Auth 之后发布事件
请求成功。同一浏览器源上的其他选项卡接收该事件并
清除或协调他们的当地状态。

浏览器来源，而不是部署平台，决定了这是否有效：

```text
https://groupher.com/home
https://groupher.com/home/dashboard
https://groupher.com/home/dash
```

即使在 Vercel 上部署 Main 且部署 Dash 时，这些也可以协调
在 Cloudflare 上，因为浏览器看到一个来源。

不同的子域不能使用该通道：

```text
https://groupher.com
https://dash.groupher.com
https://auth.groupher.com
```

对于不同的第一方来源，当页面变为
可见、接收焦点、进入受保护的路线或接收身份验证
失败。浏览器直接用`credentials: include`调用规范的Auth；
仅 `auth.groupher.com` 接收仅主机 Browser Session。 Auth 适用
共享的确切来源凭证 CORS 策略并返回无存储响应：

```text
GET https://auth.groupher.com/api/auth/session
  -> authenticated
       keep local state
  -> unauthenticated/revoked
       clear protected Valtio state
       request the shared Login Modal when required
```

对于其他设备，仅服务器端会话撤销和稍后的请求或
会话探测可以收敛状态。服务器不能直接发布
浏览器 `BroadcastChannel` 事件发送到不同的设备。

这些消息是协调 UI 和重试的提示。 Cookies 和
服务器端 Auth/Phoenix 会话仍然是事实来源。共享的Auth
消费者拥有该通道并调用应用程序回调，例如
`clearAuthState()`; Dash 没有定义单独的本地广播协议。

## SSR 和服务器运行时流程

Browser Auth V1 不允许 SSR 渲染器调用浏览器刷新端点
作为 Origin/CSRF 例外。一个SSR页面请求通常没有浏览器`Origin`，
产品服务器不得制作产品作为认证证明。

V1 SSR 流程为：

```text
SSR request
  -> forward groupher-auth.token to Phoenix
  -> Phoenix accepts
       continue render
  -> Phoenix returns refreshable 401
       return a neutral auth-recovery/loading boundary
       start one canonical-Auth browser refresh after hydration
       browser refresh succeeds
         invalidate/retry the protected route once
       browser refresh fails
         enter the signed-out/Login Modal state and preserve a validated returnTo
```

Browser-源自服务器功能的请求可能会保留原始来源
和 CSRF 应用程序突变的证明，但它们不能代理 Auth Session，
刷新或注销请求。 Auth 响应直接到达浏览器，因此
浏览器可以更新仅主机 Session 和父域令牌 Cookies。
背景 SSR 渲染无法通过 Auth 仅主机 Session
产品请求并且不调用刷新。产品应用程序从不解析或
重新签署 Auth.js Session。在 Service Identity V2 之后，可选的反向通道 SSR 刷新可能会使用
调用产品的服务标识加上与原始服务的显式绑定
AuthBrowser Session。这是一份单独的内部合同；它不是一个
V1 中的来源验证绕过。

## urql、加载器和服务器函数

Auth 生命周期独立于应用程序的数据所有权模型。

```text
TanStack/Next SSR loader
  -> loads canonical data
  -> initializes scoped Valtio stores

Core business component
  -> reads Valtio
  -> performs GraphQL mutation through urql

Auth consumer
  -> wraps the underlying authenticated request
  -> refreshes once when allowed
```

规则：

- 路线加载器不拥有AuthSession续订。
- Valtio 不存储凭证值。
- urql 不会针对每个突变实现自己的刷新协议。
- 服务器功能使用相同的共享 Auth 合约。
- Dash/Main 缓存重新验证凭据仍然是单独的服务凭据，
  不是Browser SessionCookies。

Dashboard 至 TanStack V2 遵循此模型并引用此文档
而不是定义另一个 401/刷新流。

## 权限更改和 `403`

令牌刷新不是权限刷新机制。

```text
401
  authentication credential is missing, expired, invalid, or revoked

403
  authenticated user is not allowed to perform the operation
```

关于`403`：

- 不要调用规范的 Auth 刷新端点或输入
  刷新并重试路径。
- Phoenix 仍然具有权威性。
- 在有用的情况下重新加载查看者/社区权限数据。
- 清除或禁用受保护的本地工作流程。
- 在安全的情况下保留未保存的草稿。
- 呈现稳定的无权限状态或离开受保护的路由。

如果 Phoenix 在浏览器访问令牌中嵌入粗略授权声明，
这些声明必须是短暂的，并且 Phoenix 仍然必须执行敏感的
针对当前服务器状态的授权。

## 注销

注销仍属于 Auth 拥有：

```http
POST https://auth.groupher.com/api/auth/logout
```

与刷新、注销和 Browser Session 撤销请求一样，使用确切批准的请求
Origin 加上 `X-Groupher-CSRF: 1` 合约并直接发送到 canonical
Auth 与 `credentials: include`。它们不依赖于 Auth.js 仅主机
CSRF Cookie 或产品来源 Gateway 路线。

流程：

```text
Browser
  -> Auth logout
  -> revoke the current persisted Browser Session through trusted Phoenix
  -> clear Auth.js Session Cookies
  -> clear groupher-auth.token
  -> clear groupher-auth.signed-in
  -> return no-store response
  -> broadcast auth:logout
  -> product app clears viewer and protected Valtio stores
```

应用程序不得仅独立清除一个Cookie并留下一个
半身份验证的浏览器状态。

Phoenix 撤销操作是幂等的。如果Phoenix暂时
不可用，Auth 返回无存储可重试失败并且不报告或
广播成功注销；应用程序保持经过身份验证的状态并且
提供重试。 V1并没有默默地宣称成功，同时留下了可刷新的内容
服务器端 Session 处于活动状态。

注销后导航是一个应用程序问题：

```text
Main
  refresh the current page in place

Dashboard / Dash
  enter a safe signed-out state
  open the existing shared Login Modal
```

V1 没有添加独立的 `/login` 页面。受保护的操作和路线
边界从 `~/auth` 调用 `requestLogin({ returnTo })`；模态提交
现有的 OAuth 流程并返回到已验证的当前产品 URL。

## Cookie 要求

V1 仅保留长期 Auth 凭证，并仅共享
Phoenix 跨 Groupher 产品子域的短期 Phoenix 访问凭证。

Canonical Auth 仅主机 Cookies：

```text
__Host-groupher-auth.session-token
  HttpOnly; Secure; SameSite=Lax; Path=/; no Domain
  sent only to auth.groupher.com

__Host-groupher-auth.csrf-token
__Host-groupher-auth.callback-url
__Host-groupher-auth.state
__Host-groupher-auth.pkce.code_verifier
__Host-groupher-auth.nonce
__Host-groupher-auth.challenge

Secure; SameSite=Lax; Path=/; no Domain
HttpOnly where supported by the Auth.js protocol
sent only to auth.groupher.com
```

父域产品Cookies：

```text
groupher-auth.token
  HttpOnly; Secure; SameSite=Lax; Path=/; Domain=.groupher.com

groupher-auth.signed-in
  Secure; SameSite=Lax; Path=/; Domain=.groupher.com
  browser-readable and never authentication proof
```

90 天的 Browser Session 和 OAuth 协议状态仍受规范约束
Auth。 30 分钟的 Phoenix 令牌和非敏感提示是共享的，因为
基于路径的产品入口点和子域产品入口点共存：

```text
OAuth start and callback
  https://auth.groupher.com/api/auth/*
  -> host-only protocol Cookies

successful Auth callback
  https://auth.groupher.com/api/auth/callback/*
  -> host-only Browser Session
  -> parent-domain access/hint Cookies

Auth-enabled product origins
  https://groupher.com
  https://dash.groupher.com
  -> OAuth bootstrap, Session read/write, and browser GraphQL capabilities

canonical Auth self-origin
  https://auth.groupher.com
  -> OAuth callback and canonical Auth handlers

explicitly public-only origin
  https://landing.groupher.com
  -> no OAuth bootstrap, Session read, refresh, logout, revoke, or browser
     GraphQL state-change capability

browser Auth/API paths
  canonical-origin OAuth protocol paths -> Auth
  canonical-origin /api/auth/session -> Auth, credentials: include
  canonical-origin /api/auth/token/refresh -> Auth, credentials: include
  canonical-origin /api/auth/logout -> Auth, credentials: include
  canonical-origin /api/auth/sessions* -> Auth, credentials: include
  current-origin /api/graphql -> Gateway -> Phoenix
```

确切的起源注册表是基于能力的，而不是单一的许可
列表。 `landing.groupher.com` 仅提供公共页面，例如 `/`、`/pricing`、
和 `/book-demo`，因此规范的 Auth 和浏览器 GraphQL 突变处理程序拒绝
它作为起始原点。 `groupher.com` 保持 Auth 启用，因为相同
origin 还提供经过身份验证的 Main 路径，尽管它的某些路由是
公开。未来的应用程序在其确切来源之前不会收到 Auth 功能
并明确注册所需的功能。

产品请求传输可以携带父域访问令牌和提示，但是
绝不是 Auth Browser Session 或 Auth.js 协议 Cookies。产品应用
因此无法解码或泄露 90 天的 Session。 Gateway 仅转发
浏览器 GraphQL 请求上的规范 Phoenix 令牌。`Domain=.groupher.com` 不限于认可来源注册表：浏览器
向其访问的每个 Groupher 子域发送匹配的 Cookie。因此，
每个可以提供 `*.groupher.com` 流量的主机都在凭证内
信任边界，即使它未被批准启动状态更改。一个
受感染的子域服务器可以接收当前父域30分钟
Phoenix 令牌，并且已批准的受损源通过源验证。它
无法收到仅主机 90 天 Browser Session 或被盗后刷新
如果用户的浏览器未成功调用规范，访问令牌就会过期
再次Auth。来源/自定义标头 CSRF 检查减少跨源请求滥用
但不要将短期访问凭证与受感染的同级凭证隔离
主机。

因此，V1 需要 Groupher 控制的 DNS 和整个部署
命名空间，无用户控制的子域托管，及时删除可索赔的
废弃的记录、确切的状态更改 Origin 允许列表以及同等内容
跨凭证接收应用程序的安全控制。如果这种信任模型
即使使用 30 分钟的访问令牌也无法维护，替换为
仅主机每产品访问 Cookies 加上一次性 Auth 代码交换/BFF；
CSRF 单独检查并不是一种替代方案。

附加要求：

- 请勿将凭证值放入 `localStorage` 或 `sessionStorage` 中。
- 不要向浏览器公开刷新凭据 JavaScript。
- 不要记录 Cookie 值或令牌有效负载。
- 根据第一方白名单验证所有返回 URL。
- 保护每个经过浏览器 cookie 验证的状态更改端点，包括
  Phoenix GraphQL 突变，具有记录的 Origin/custom-header 合同。
- 保持 Auth Browser Session 和 Auth.js 协议 Cookies 仅限主机；从不
  将访问令牌的父域应用于 Session、CSRF、回调、状态、
  PKCE、随机数或挑战Cookies。
- 从 Auth/会话/令牌端点返回 `Cache-Control: no-store`。
- 在登录和权限敏感的会话更改后轮换标识符。

V1 Cookie 的生命周期故意不同：

```text
groupher-auth.token
  no longer than the 30-minute Phoenix access-token expiry

__Host-groupher-auth.session-token
  no longer than the original 90-day Browser Session absolute expiry
  sent only to auth.groupher.com

groupher-auth.signed-in
  follows the Browser Session lifetime
  remains a non-authoritative probe hint
```

自定义社区域无法直接共享 Groupher 父域 Cookies。
它们需要单独的一次性代码交换流程。

## 过期和轮换政策

V1修复了以下策略：

```text
Phoenix browser access token TTL
  30 minutes

Auth Browser Session absolute lifetime
  90 days from the initial OAuth sign-in
  never extended by refresh or Cookie rotation

Auth Browser Session idle timeout
  disabled in V1
```

当 Phoenix 在 Session 末尾附近发出令牌时，它使用：

```text
accessExpiresAt = min(now + 30 minutes, sessionAbsoluteExpiresAt)
```

访问令牌 Cookie 必须在 JWT 之前过期。目前共享的
14 天 Cookie 最长生命周期和 30 天监护人 JWT 生命周期被删除，而不是
被带入新模式。

提供商令牌策略是独立的：

```text
GitHub used only for sign-in
  validate the provider identity during callback
  bind the stable provider account id to the Groupher user
  discard the provider access token after identity establishment

Future GitHub repository/organization integration
  request separate scopes
  store and refresh its provider token independently
  do not couple integration failure to the Groupher Browser Session
```

V1 使用稳定的 `browserSessionRef` 进行查找、撤销和设备列表
所有权。刷新令牌系列/版本轮换和重用检测稍后进行
硬化阶段。裁判本身并不能检测重播； 30 分钟的访问 TTL，
安全 Cookie 传输、服务器端撤销、Origin/CSRF 检查和有界
重试是 V1 重放风险控制。

V1 明确接受 Auth Browser Session 被盗的剩余风险
Cookie 可以获取新的访问令牌，直到 Session 被撤销或达到其
原来的 90 天绝对有效期。仅被盗的访问令牌仍受以下限制
30 分钟到期。空闲超时、刷新秘密轮换和重用检测
是延迟强化而不是隐式 V1 行为。

## 故障和可用性策略

身份验证的正确性优于默默接受陈旧或
无法验证的凭据。

```text
Auth unavailable, access token still valid
  current Phoenix request may continue

Auth unavailable, access token expired
  do not bypass expiry
  show a recoverable auth-unavailable state or redirect when safe

Phoenix unavailable during refresh
  return temporary failure
  do not mint a local token

refresh repeatedly fails
  stop after bounded retry
  emit structured logs/metrics
  require a new login when the failure is non-transient
```

刷新端点必须受到速率限制并且可以在不记录机密的情况下进行观察。

## 安全性和可观察性

记录：

```text
refresh attempt count
refresh success/failure reason
Auth Session expiry/revocation
Phoenix token expiry/revocation
Browser Session creation/revocation
remote Session revocation
401 retry success rate
403 rate by operation
logout success
open-redirect rejection
CSRF/origin rejection
```

从不记录：

```text
Auth.js Session payload
Phoenix token
provider access/refresh token
Cookie headers
OAuth authorization code
```

使用关联/请求 ID 而不是凭证来跟踪跨流
Gateway、Auth、Phoenix 和产品应用。远程 Session 撤销无法删除其他浏览器持有的 Cookie。在V1中
它会立即阻止进一步刷新，而已经颁发的访问令牌
最多可保持 30 分钟可用。所有权转让等操作，
账单更改、API密钥创建、社区删除、域更改和 SSO
更改可能还需要最近的身份验证检查。

## 扩展边界

### 服务身份和客户端凭证（V2）

服务到服务的身份验证和用户委托分别定义在
[`v2.md`](./v2.md)。 Browser Auth V1 未添加服务令牌颁发者，请迁移
全局信任密钥，或更改子应用程序通信凭据。

在 V2 之前，当前的服务凭证仍然是显式引导机制。 V1
不得添加全局信任秘密的新消费者，将客户标记视为
验证，或使媒体预测比有限的当前公众更广泛
内容。 `PRESS_INTERNAL_TOKEN` 保持独立于全局 Phoenix
信任 Secret，直到两者都被范围内的 V2 身份取代。

### 其他网络身份提供商

GitHub、Google、Apple 和客户 OIDC/SAML 提供商均以 Auth 终止。
它们标准化为相同的 Phoenix 身份交换和 Browser Session
合同。

### 外部客户

MCP、代理、CLI 工具和第三方 API 客户端使用单独的 OAuth
来自 `docs/oauth/overview.md` 的提供商或 API 令牌架构。他们不使用
Browser Session刷新端点。

### 设备和Session管理

每个经过身份验证的用户都可以列出和撤销自己的 Browser 会话。的
面向浏览器的表面属于规范Auth：

```http
GET  https://auth.groupher.com/api/auth/sessions
POST https://auth.groupher.com/api/auth/sessions/<publicRef>/revoke
POST https://auth.groupher.com/api/auth/sessions/revoke-others
```

Canonical Auth 读取当前仅主机 Browser Session，获取其内部
`browserSessionRef`，并通过可信的Session-列表/撤销调用Phoenix
操作。这些 Phoenix 操作不是浏览器 GraphQL 突变。 Phoenix
仍然对所有权、当前Session计算和撤销具有权威性
状态； Auth 是浏览器协议边界。

浏览器可能仅提供目标Session的随机`publicRef`。 API
从不公开或接受 Auth.js Session 有效负载，内部
`browserSessionRef`、所有者 ID、当前 Session 声明或凭证值。每个
row 公开 `publicRef` 和服务器计算的 `isCurrent` 标志。列表路线是
经过认证、只读和 `no-store`；撤销路线需要确切的出发地
和`X-Groupher-CSRF: 1`。撤销当前的Session使用正常
`signOut()` 流，因此 Auth 可以撤销它并原子地清除每个 Cookie。

共享帐户 UI 通过现有帐户工具提示公开该功能：

```text
click account avatar
  -> account Tooltip
  -> "Logged in by GitHub        >"
  -> close Tooltip
  -> open the Login And Devices Drawer
```

抽屉显示登录提供程序，标记当前的 Session，并列出
大致浏览器、操作系统/设备系列、粗略位置、登录时间和上次登录时间
活动。用户可以撤销另一个 Session 或撤销所有其他会话，同时
保持当前的Session。现有账户注销仍是结束方式
当前的Session。

仅位置更改就会更新当前记录；它不会创建一个新的
Session。新的 OAuth 登录、浏览器/个人资料、已清除的 Cookie 或私人窗口
创建另一个Session。未知或不可靠的设备/位置值必须具有
稳定的后备 UI。

前端实现属于共享单元，例如
`frontend/core/unit/AccountSessionDrawer/`。它使用现有的全局抽屉
事件边界。打开抽屉首先关闭工具提示和组件
遵循现有的每个文件一个组件和本地 `useSalon()` 约定。

未来的扩展包括最近的身份验证、逐步身份验证、
基于风险的撤销、空闲到期、刷新系列轮换以及更丰富的Session
审计事件。不需要产品应用程序来解码 Auth.js 内部结构。## V1 和 V2 排序

Browser Auth V1 和服务身份 V2 是独立的合约，可以是
并行开发：

```text
V1 Browser Session cutover before V2
  Auth -> Phoenix keeps the existing bootstrap server-trust transport
  V1 completes the coordinated Phoenix/Auth/Gateway/product cutover
  V2 later replaces only the service transport with service:auth

V2 service:auth available before V1 cutover
  V1 sign-in, refresh, revoke, and logout use the scoped service identity
  the Browser Session contract and one-time user relogin remain unchanged
```

V1不得等待完整的多服务V2迁移，并且V2不得重新打开
V1 Browser Session 或 Cookie 型号。 V1 是一个协调的浏览器会话
切换； V2 一次迁移一个边缘并最终迁移服务通信
删除引导程序信任密钥。

## 实施工作流程

Browser Session V1 作为一个合同切换而不是兼容性提供
迁移。现有的 Auth/Phoenix 浏览器会话一旦失效，用户
再次完成OAuth登录； V1 不会回填 `browserSessionRef` 到旧版本
会话或并行维持以前的 14/30 天生命周期。

### 工作流 1：Phoenix Session 和代币合约

- 添加持久的 Browser Session 架构、安全引用生成、设备
  元数据、内部/公共参考分离、所有权规则以及当前/其他
  Session询问。
- 扩展OAuth登录以创建Browser Session并返回
  `TBrowserSigninResult`。
- 将 Guardian 浏览器令牌问题重构为 30 分钟，并达到预期的 `iss`，
  `aud=phoenix:browser-api`、`sid` 和 `typ=browser_access`，上限为
  Session绝对到期。
- 需要 V1 发行者、受众、`sid` 和 `typ=browser_access`
  browser-Cookie 路径，因此旧版 Cookies 在切换期间被拒绝，无需
  轮换由不相关的代币合约共享的秘密。
- 添加具有机器可读错误的可信刷新和撤销操作。
- 添加浏览器-Cookie 突变保护，以验证确切的原始内容
  起源和 `X-Groupher-CSRF` 合同，同时保留 V2 服务/委托
  在其单独的验证者路径上进行身份验证。

### 工作流 2：Auth Session、刷新和注销

- 将 `browserSessionRef` 和不可变的绝对到期时间存储在受保护的
  Auth.js Session。
- 将共享的 14 天生命周期替换为单独的 30 分钟访问和 90 天
  Browser Session政策。
- 拆分Cookie配置：Browser Session和Auth.js协议Cookies是
  规范 Auth 上仅主机；仅 30 分钟访问令牌且不敏感
  提示使用父域。删除现有的共享 `Domain` 覆盖
  每个 Browser Session 和 Auth.js 协议-Cookie 定义；仅改变
  该前缀无效，因为浏览器拒绝包含以下内容的 `__Host-` Cookies
  `Domain` 属性。
- 将重复的 Auth/Gateway/Phoenix 原始数组替换为一个
  CORS 使用的环境范围内、基于功能的精确来源注册表和
  请求拒绝。保持 `landing.groupher.com` 明确仅公开，不
  Auth 或浏览器 GraphQL 状态更改功能。
- 从现有登录模式启动 `auth.groupher.com` 上的 OAuth 协议，
  具有狭窄范围的凭证 CORS 仅用于 CSRF 引导响应。
- 添加规范来源 Session 探针、Session 列表、刷新、注销、单-
  Session 撤销，并撤销具有精确凭证的其他会话路由
  原产地CORS。刷新/注销/撤销需要自定义 CSRF 标头、速率
  限制、无存储响应和 Phoenix 信任调用；只读 Session
  路线仍保持凭证状态且无存储。
- 显式处理经过认证的 `OPTIONS` 请求，包括
  `Access-Control-Allow-Headers: Content-Type, X-Groupher-CSRF`，准确反映
  起源、`Vary: Origin`、允许的方法和有界的预检缓存。
- 注销期间撤销当前保留的Session，然后清除每个Auth，
  访问令牌和提示Cookie。

### Workstream 3: Shared Frontend Consumer And Product UX

- Move the existing OAuth client behind `frontend/core/lib/auth/`, export it as
  `~/auth`, and add shared refresh, retry, failure, login-Modal, logout, state
  cleanup, same-origin channel, `listSessions()`, `revokeSession(publicRef)`, and
  `revokeOtherSessions()` behavior.
- Preserve GraphQL `extensions.code`, single-flight refresh, and a one-time
  original-operation retry across urql, Next, Dash loaders, and server
  functions.
- Keep refresh demand-driven. Do not add per-product or per-tab TTL polling;
  verify that one canonical Auth refresh updates the parent-domain token used by
  the other product origins on their next request.
- Add `X-Groupher-CSRF: 1` to Auth state-changing requests and every browser
  GraphQL POST, and preserve the original browser Origin across same-origin
  Gateway/server-function proxies.
- Keep public SSR anonymous. An authenticated SSR render with a refreshable 401
  returns a controlled boundary for one direct canonical-Auth browser refresh;
  it does not proxy refresh through the product server or bypass Origin/CSRF
  through a V1 backchannel call.
- Main refreshes in place after logout; Dashboard and Dash enter a safe
  signed-out state and open the shared Login Modal.
- Apply route/operation protection at shared boundaries instead of adding a
  second Auth implementation to individual components.

- Add the all-user Login And Devices Drawer and current/other Session actions;

- Add Phoenix, Auth, Gateway, frontend consumer, canonical-Auth CORS/Set-Cookie,
  multi-tab, Session-ownership, missing-access-Cookie refresh, legacy-Cookie

- Coordinate Auth, Phoenix, Gateway, Main, Dashboard, and Dash as one maintenance-

  public flow. Do not add a compatibility feature flag or dual credential path.

## Implementation Incident: OAuth Callback Succeeded But `me` Was `null`

During the Auth V1 cutover, GitHub OAuth completed and returned to the product,
but Phoenix did not establish `current_user`. GraphQL therefore returned
`{"data":{"me":null}}`, even after the browser Cookies were cleared and OAuth
was repeated. This was an Auth V1 implementation defect at the Guardian
boundary, not a GitHub OAuth, database migration, or stale-Cookie failure.

### Browser Access Claim Meanings

The browser access JWT uses standard JWT claims plus V1-specific Session and
token-type claims:

| Claim                                          | Name       | V1 meaning                                                                                                                                                                                                                                                                               |
| ---------------------------------------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `iss`                                          | Issuer     | The authority that issued the credential. Browser access tokens require the exact value `groupher:phoenix`.                                                                                                                                                                              |
| `aud`                                          | Audience   | The resource server allowed to accept the credential. V1 requires `phoenix:browser-api`; a token for another audience must be rejected.                                                                                                                                                  |
| `typ`                                          | Token type | The Groupher credential class. `browser_access` separates this short-lived browser credential from legacy bearer, service, or other token contracts.                                                                                                                                     |
| `sub`                                          | Subject    | The stable identity represented by the token. In V1 this is the Phoenix user id, serialized as a string.                                                                                                                                                                                 |
| `sid`                                          | Session id | The opaque internal `browserSessionRef` of the persisted Browser Session that authorized issuance. Phoenix uses it to bind the token to a Session lifecycle; it is neither the user id nor the `bsp_*` public Session-management handle, and it is never returned to browser JavaScript. | 令牌还带有`iat`（发行时间）和`exp`（到期时间）。没有一个 |
| 这些声明带有可变的社区成员资格或业务许可；     |
| Phoenix 加载当前用户并在令牌后强制执行当前授权 |
| 验证。                                         |

### 根本原因 1：原始声明和监护人资源混淆

Guardian 公开了两种不同的结果形状：

```text
decode_and_verify(token)
  -> verifies signature and registered claims
  -> returns raw JWT claims, including iss/aud/typ/sub/sid

resource_from_token(token)
  -> decodes and verifies the token
  -> calls resource_from_claims(raw claims)
  -> returns the application resource, currently %{id: sub}
```

浏览器Cookie路径使用了资源返回操作但随后进行了处理
`%{id: sub}` 就好像它是原始索赔地图一样。检查如
`claims["iss"]`、`claims["aud"]` 和 `claims["sid"]` 因此永远不可能
成功。令牌本身可以在请求时正确签名和存储
身份验证仍然失败。

实施的修复使边界变得明确：

1. 解码并验证浏览器 JWT，同时保留其原始声明。
2. 验证 V1 `iss`、精确 `aud`、`typ` 和非空 `sid`
   原始地图。
3. 仅在声明验证后，将 `sub` 转换为 Guardian 资源。
4. 从该资源加载 Phoenix 用户和当前护照。

旧的 `Authorization: Bearer` 路径保留其现有的资源返回
合约，并且不会默默地重新解释为浏览器令牌。

### 根本原因 2：Guardian 更换了 Browser 发行人

浏览器令牌发布调用提供了 `iss=groupher:phoenix`，但是 Guardian 的
JWT 模块在构建时应用了 Guardian 实现的全局发行者
最终索赔。因此，签名的令牌承载了遗产
`groupher_server` 发行人未能履行 V1 浏览器索赔合同。

守护者决赛中初始修复恢复`groupher:phoenix`
`build_claims``typ=browser_access`时回调。那个兼容性补丁是
然后通过将浏览器访问分为
`Helper.Guardian.BrowserAccess`。 Browser 访问和遗留承载凭证
现在使用单独的 Guardian 实现/配置，因此每个都有一个
发行者、受众、TTL 和无最终声明的验证合约
覆盖。

### 为什么现有的Browser E2E没有检测到它

隔离的 Auth 浏览器套件使用 opaque 验证浏览器协议行为
测试字符串，例如 `e2e-access-*` 和内存中的 Session/令牌映射。那就是
适用于确定性 Cookie、CORS、刷新、重播、撤销和
多选项卡测试，但它不执行真正的监护人签名、发行人
选择、原始声明解码或资源转换。

因此，修复包括 Phoenix 集成测试，该测试会发出真正的 V1
Guardian 浏览器令牌，通过 `groupher-auth.token` 发送，并验证
GraphQL 解决了预期的 `me`。模拟浏览器套件仍然有用，但是
不得将其视为 Auth 到 Phoenix 令牌的完整验证
合同。

### 被拒绝的补丁式恢复

前端不得将 `me: null` 解释为访问 Cookie 需要的证据
清爽。可为空的公共 `me` 结果可能意味着匿名请求；添加
`me: null -> refresh -> retry` 隐藏后端身份验证缺陷，合并
身份探测与恢复，并可能创建不必要的刷新循环。

恢复仍然由Phoenix机器可读身份验证失败驱动，
例如 `TOKEN_MISSING`、`TOKEN_EXPIRED`、`TOKEN_INVALID` 和
`SESSION_REVOKED`，最多 1 次共享刷新和 1 次重播。如果一个产品
需要区分匿名状态和损坏的凭证，它应该使用
专用身份/Session 探针具有显式结果契约而不是
`me: null`启发式。

### 预防规则

- 仅对原始 JWT 声明验证浏览器协议声明；转换为
  仅在声明验证后才应用资源。
- 在功能和模块中保持浏览器和遗留代币合约的明确性
  边界；不要依赖形状相似的地图。
- 在 CI 中运行至少一个真正的 Guardian Cookie-to-GraphQL 合约测试
  除了有状态的模拟浏览器套件之外。
- 将 `iss`、`aud`、`typ`、`sub` 和 `sid` 视为单一版本合约
  由发布测试和Phoenix验证测试共享。
- 不要使用前端修复后端身份验证失败 `me: null`
  推理或自动刷新启发式。

## Automated Verification

The repository includes an isolated Auth V1 browser stack for Playwright. It
starts Dash, a canonical Auth instance with an independent test secret and
60-second access TTL, and a stateful Phoenix GraphQL test implementation. The
test-only `/api/auth/test-login` Session-signing hook exists only in the E2E
server entrypoint; production Auth does not register it and no real GitHub OAuth
account is required.

The suite does not require `/etc/hosts` entries. Its Chromium project explicitly
maps `dash.groupher.localhost` and `auth.groupher.localhost` to `127.0.0.1` with
browser host-resolver rules; Node-side readiness and protocol probes use
`localhost` or `127.0.0.1`. Consequently, a Node `dns.lookup()` for either test
hostname may still return `ENOTFOUND` without preventing the browser suite from
running.

The `.localhost` suffix is part of the test protocol, not an arbitrary naming
choice: it provides separate Dash/Auth hosts while remaining a potentially
trustworthy HTTP origin, so Chromium accepts the test stack's `Secure` Cookies.
Moving the stack to a non-localhost domain requires HTTPS rather than only a DNS
change.

Run the complete P0/P1/P2 browser matrix with:

```bash
pnpm run test:e2e:auth
```

As with the repository's other Playwright suites, install the matching Chromium
binary first with `pnpm exec playwright install chromium`. A developer who already
has Chrome installed may instead run
`PLAYWRIGHT_USE_SYSTEM_CHROME=1 pnpm run test:e2e:auth`.

The matrix covers missing and expired access-token one-refresh/one-replay
recovery, remote Session revocation, SSR hydration recovery, logout and
same-origin tab synchronization, device listing/current/revoke/revoke-others,
CDP Cookie attributes, real-browser CORS rejection, and the local 10-per-minute
fallback rate limit. The expired-token case uses a test-only clock/control hook
to cross the same `TOKEN_EXPIRED` decision boundary deterministically instead of
adding a 60-second sleep; the isolated Auth stack's normal access TTL remains 60
seconds.

Deployment CSRF and Origin checks remain a non-browser smoke because they need
real deployed Phoenix/Auth endpoints and a disposable V1 access token:

```bash
AUTH_SMOKE_AUTH_ENDPOINT=https://auth.groupher.com/api/auth \
AUTH_SMOKE_PHOENIX_ENDPOINT=https://api.groupher.com/graphiql \
AUTH_SMOKE_TOKEN='<disposable-v1-access-token>' \
pnpm run smoke:auth:v1
```

The smoke sends only safe, intentionally invalid mutations: if Phoenix's CSRF
middleware is absent they fail GraphQL validation rather than mutating data.

## Acceptance Criteria

- Auth remains the only component that reads or writes Auth.js Session state.
- Product applications never mint or decode browser credentials.
- Phoenix remains the final authority for user and business permissions.
- Phoenix access tokens expire after at most 30 minutes and never extend past
  the Browser Session absolute expiry.
- Browser Sessions expire absolutely 90 days after initial OAuth sign-in;
  refresh and Auth.js Cookie rotation never extend that boundary.
- V1 does not implement an idle timeout.
- V1 explicitly accepts that a stolen Auth Browser Session Cookie can refresh
  access until server-side revocation or the original 90-day absolute expiry;
  only canonical Auth receives that host-only Cookie, while refresh-secret
  rotation, reuse detection, and idle timeout are deferred.
- Browser access tokens require the expected issuer,
  `aud=phoenix:browser-api`, and `typ=browser_access`; another resource server
  must reject them.
- The Browser Session and Auth.js CSRF/callback/state/PKCE/nonce/challenge
  Cookies are host-only on `auth.groupher.com`; only the 30-minute Phoenix token
  and non-sensitive hint use `Domain=.groupher.com`.
- Browser tests confirm every `__Host-` Session/protocol Cookie omits `Domain`
  and uses `Secure` plus `Path=/`; the former shared Cookie `Domain` override is
  removed rather than reused under a new prefix.
- The former 14-day Cookie and 30-day Guardian JWT lifecycle is removed during
  the one-time Session cutover.
- Legacy parent-domain Auth.js Session Cookies may remain in browser storage until
  their existing expiry, but V1 never reads them and does not add special cleanup
  code. Their physical presence is not proof of a valid V1 Session.
- Expired or missing Phoenix browser tokens trigger at most one refresh attempt
  at authenticated route/operation boundaries.
- Anonymous public operations do not refresh merely because the access Cookie
  is absent.
- `403` never triggers refresh.
- Refresh never returns credential values in JSON.
- Refresh, logout, Session revoke, and browser-Cookie GraphQL mutations reject
  missing, `null`, or unapproved Origin and require `X-Groupher-CSRF: 1`.
- Credentialed Auth preflight responses reflect only an exact approved Origin,
  allow credentials, declare the required methods and
  `Content-Type, X-Groupher-CSRF` headers, emit `Vary: Origin`, and never treat
  successful `OPTIONS` as authorization for the actual request.
- Browser GraphQL POSTs require `application/json` and `X-Groupher-CSRF: 1`;
  Phoenix rejects mutations over GET, and CORS response policy alone is never
  treated as CSRF validation.
- Background SSR renders do not call the browser refresh endpoint without
  browser Origin/CSRF proof. The browser calls canonical Auth directly and
  applies its host-only and parent-domain `Set-Cookie` responses; product routes
  never proxy the Auth Browser Session.
- When an authenticated SSR request encounters an expired access token, V1
  accepts that the server cannot render authenticated content. It renders a
  neutral auth-recovery/loading boundary, performs at most one canonical-Auth
  refresh after hydration, and invalidates/retries the protected route once;
  implementations must not restore background SSR refresh to hide this state.
- Concurrent failures create one refresh request per application runtime.
- Product applications do not run periodic refresh timers. One successful
  refresh updates the shared parent-domain access Cookie, so another origin's
  next request uses it without performing its own refresh.
- Simultaneous expiry across different origins may produce a small idempotent
  refresh burst; rate limits permit it, and server-side coalescing is added only
  when production metrics justify it.
- Logout clears every Auth and Phoenix browser Cookie.
- Logout revokes the current persisted Browser Session before reporting full
  server-side logout success.
- Multi-tab logout clears protected application state.
- Same-origin logout/refresh events use the shared Auth consumer's
  `BroadcastChannel` optimization; cross-origin and cross-device state uses
  Auth Session probes or authentication responses.
- Auth/session/token endpoints return `Cache-Control: no-store`.
- Browser credentials never enter browser storage or logs.
- `browserSessionRef` remains internal to Auth/Phoenix; device-list operations
  use an owner-checked `publicRef` and server-computed `isCurrent`.
- Every authenticated user can open Login And Devices from the account Tooltip,
  identify the current Session, revoke one other Session, or revoke all other
  Sessions.
- Session list and revoke browser requests use canonical Auth and the shared
  `~/auth` consumer. Phoenix exposes their implementation only as trusted Auth-
  to-Phoenix operations, not browser GraphQL Session mutations.
- Main refreshes in place after logout; Dashboard and Dash reuse the existing
  shared Login Modal rather than a standalone `/login` page.
- GitHub provider tokens are discarded after sign-in unless a future,
  separately authorized GitHub integration needs them.
- Old browser sessions are invalidated once; no legacy Session backfill or
  parallel 14/30-day compatibility path remains.
- V1 has no legacy browser-token feature flag or dual validator. The Phoenix V1
  release therefore ships only inside the coordinated maintenance window, after
  the additive database migration is ready.
- Legacy Phoenix access tokens carried by the browser Cookie without the V1
  `sid` and `typ=browser_access` claims are rejected without requiring a global
  signing-secret rotation.
- Every host that can serve `*.groupher.com` traffic is treated as
  trusted to receive a currently valid 30-minute Phoenix token because
  parent-domain Cookies are sent by domain match, not by the approved-Origin
  list. It never receives the 90-day host-only Auth Session. Approved origins
  alone may initiate browser state changes; custom domains receive no
  parent-domain Cookies and use a one-time exchange.
- `landing.groupher.com` is public-only and is absent from OAuth bootstrap,
  Session read/write, and browser GraphQL state-change origin capabilities. Its
  public routes do not expose login, account, logout, or device-management UI.
  Credentialed Auth CORS does not grant this Origin access, Auth state-changing
  requests fail the exact-Origin check, and Phoenix BrowserCsrf rejects browser-
  Cookie GraphQL mutations from it. A host-agnostic Gateway route match is not an
  authorization or capability decision.
- When canonical Auth reports no Browser Session and the access/hint Cookies are
  absent, the browser is anonymous even if an unreachable server-side Session
  record still exists.
