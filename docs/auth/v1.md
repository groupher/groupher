# Groupher Browser Auth And Session Lifecycle V1

> Status: target contract for browser authentication, session continuity, and
> Phoenix access-token renewal.
>
> Current implementation: `backend/auth` owns OAuth/Auth.js and writes both the
> Auth.js Session Cookie and `groupher-auth.token` during sign-in. The two
> Cookies currently use a 14-day `Max-Age`, while the Guardian JWT carried by
> `groupher-auth.token` has a 30-day internal expiry. There is no persisted
> Browser Session or dedicated Phoenix token refresh contract yet.
>
> This document defines the target lifecycle without changing the existing
> identity and authorization ownership boundaries.

## Scope

This document covers:

- Browser login continuity for Main, Dashboard, Dash, Apply, and future
  first-party frontend applications.
- Auth.js Browser Session lifetime.
- Phoenix browser access-token lifetime and renewal.
- Cookie ownership.
- Authenticated SSR, loader, server-function, and GraphQL behavior.
- Unified handling of expired, invalid, revoked, or unauthorized sessions.
- Logout, multi-tab behavior, retry limits, session revocation, and user-facing
  Session management.

This document does not implement in v1:

- OAuth access tokens issued to MCP, agents, or third-party clients.
- Personal API Tokens.
- Service-to-service credentials. Their v2 target design is recorded below so
  sub-apps do not invent incompatible credentials.
- User delegation tokens for Content Import, Assets Hub, or other worker
  services.
- Community membership and business authorization rules.
- Idle Session expiry. V1 uses only a 90-day absolute Browser Session lifetime.
- Refresh-token family rotation and replay detection.
- Physical-device fingerprinting or authoritative location detection.
- A standalone `/login` page. V1 reuses the existing shared Login Modal.
- GitHub repository/organization integration tokens. GitHub is used only to
  establish the initial Groupher identity in this flow.

## Confirmed V1 Decisions

```text
Phoenix browser access-token TTL
  30 minutes

Auth Browser Session absolute lifetime
  90 days from the initial OAuth sign-in
  never extended by refresh or Auth.js Cookie rotation
  host-only on auth.groupher.com

Phoenix browser access Cookie scope
  Domain=.groupher.com
  shared for at most the token's 30-minute lifetime

Idle timeout
  not enabled in V1

Existing sessions at cutover
  invalidated once
  users complete OAuth sign-in again

GitHub provider token
  used only during sign-in
  not retained after identity establishment

Cookie topology
  90-day Auth Browser Session -> host-only auth.groupher.com
  30-minute Phoenix access token -> Domain=.groupher.com
  non-sensitive signed-in hint -> Domain=.groupher.com, never authentication proof

Endpoint ownership
  OAuth, Session probe/list, refresh, logout, and revoke -> canonical Auth
  browser GraphQL -> current-origin Gateway -> Phoenix
  Session list/revoke in Phoenix -> trusted Auth operations, not browser mutations

Browser state-change CSRF
  exact approved Origin + X-Groupher-CSRF: 1
  required by Auth refresh/logout/revoke and browser GraphQL POST

Origin capabilities
  groupher.com, main, dashboard, and dash -> explicit Auth capabilities
  landing.groupher.com -> public-only, no Auth capability
```

The shared frontend consumer lives under `frontend/core/lib/auth/` and is
exported through the `~/auth` alias. The existing `frontend/core/lib/oauth.ts`
sign-in and sign-out implementation moves behind that entry point during the
refactor.

## Principles

1. Auth owns browser authentication protocols and session lifecycle.
2. Phoenix remains the source of truth for users, account state, membership, and
   business authorization.
3. Frontend applications consume Auth results but do not decode, mint, rotate,
   or revoke Auth credentials themselves.
4. Gateway forwards the canonical Phoenix Cookie but does not interpret it.
5. Browser credentials remain in `HttpOnly` Cookies and are never returned in
   JSON or exposed to browser JavaScript.
6. An expired Phoenix token may be renewed only from a valid Auth Browser
   Session.
7. Refresh is attempted at most once per failed application operation.
8. A `403` business authorization failure never triggers token refresh.
9. Logout invalidates the Browser Session and clears every browser-auth Cookie.
10. Browser auth and external-client OAuth remain separate protocols.
11. `BroadcastChannel` is only a same-origin browser coordination optimization;
    it is not the cross-origin or cross-device authentication authority.
12. GitHub OAuth proves control of a GitHub account during sign-in; subsequent
    Groupher login continuity is governed by the Auth Browser Session and
    Phoenix access token, not by the GitHub token lifetime.
13. V1 does not create a second login UI. Main, Dashboard, and Dash reuse the
    existing shared Login Modal.

## Authorities

```text
Auth
  OAuth/OIDC login
  Auth.js Browser Session
  Cookie lifecycle
  Phoenix token renewal endpoint
  logout

Phoenix Accounts
  user and external identity
  account state
  persisted Browser Session records
  Phoenix access-token issue/reissue
  token validation
  community membership and business authorization

Gateway
  stable public routing
  Cookie filtering and forwarding
  no token parsing

Main / Dashboard / Dash / Apply
  consume authentication state
  protect application routes
  retry once through the shared Auth consumer
  render login or no-permission states
```

Auth proves that a browser owns a valid Groupher login session. Phoenix decides
which Groupher user that session represents and what the user may do.

The trusted Auth-to-Phoenix transport is versioned independently. Browser Auth
V1 may continue using the existing bootstrap server-trust credential; after
[`v2.md`](./v2.md) is available, the same operations migrate to
`service:auth` with an exact Phoenix audience and account/session scopes. V1
does not require V2 to complete its Browser Session cutover.

## Credential Model

### Auth Browser Session

Cookie:

```text
__Host-groupher-auth.session-token
```

Properties:

- Written, decoded, renewed, and cleared only by Auth.js inside `backend/auth`.
- Expresses browser login continuity.
- Must not contain community permissions or become the business authorization
  source of truth.
- Is the authority used by Auth when requesting a new Phoenix browser access
  token.
- Is host-only on `auth.groupher.com`, has no `Domain` attribute, and is never
  sent to product subdomains.
- Is never forwarded to Phoenix GraphQL by Gateway or product applications.
- Has a 90-day absolute lifetime measured from the initial OAuth sign-in.
- Stores only the stable `browserSessionRef`, absolute expiry, and other minimal
  Session coordination data; it does not store Groupher roles or permissions.

The current Auth.js session strategy is JWT-based. The session payload should
remain minimal and encrypted/signed by Auth.js. Auth.js may rotate or renew the
Cookie, but it must preserve the original `sessionAbsoluteExpiresAt`; activity
must never push the Session beyond its initial 90-day boundary.

### Phoenix Browser Access Token

Cookie:

```text
groupher-auth.token
```

Properties:

- Written and cleared through Auth-owned HTTP responses.
- Issued or reissued by Phoenix through a trusted Auth-to-Phoenix operation.
- Forwarded to Phoenix as the same Cookie by Gateway and server-side GraphQL
  clients.
- Used for API authentication and final Phoenix authorization.
- Has a 30-minute maximum lifetime in V1.
- Carries stable identity and Session claims including `iss`,
  `aud=phoenix:browser-api`, `sub`, `sid`, `iat`, `exp`, and
  `typ=browser_access`; it does not carry mutable business permissions as an
  authorization source of truth.
- Must not be read by browser JavaScript.

The token should primarily carry stable identity/session claims. Business
permission changes remain enforceable by Phoenix without waiting for browser
token renewal. Phoenix validates the expected issuer, exact audience, token
type, signature, and expiry; a browser token is not accepted by another
resource server.

### Signed-In Hint

Cookie:

```text
groupher-auth.signed-in
```

Properties:

- Contains no credential.
- May be read by browser code only as a loading optimization.
- Must never be treated as proof of authentication.
- Is cleared with the Auth Session and Phoenix token.
- Follows the 90-day Browser Session lifetime rather than the 30-minute access
  token lifetime. A stale hint may initiate a probe or refresh but never grants
  access by itself.

### Persisted Browser Session

Phoenix Accounts persists one record for each independent browser login. A
Browser Session is not a physical-device fingerprint: different browsers or
browser profiles on one machine create different Sessions, while a location
change in the same browser updates the existing Session.

`browserSessionRef` is an opaque, non-permission-bearing lookup reference. It
contains no encoded user, time, device, or location fields. Phoenix generates it
from cryptographically secure random bytes, for example a `bs_` prefix followed
by 32 random bytes encoded as unpadded base64url.

The V1 record contains:

```text
ref
public_ref
user_id
status                  active | revoked
created_at
absolute_expires_at
last_refreshed_at
last_seen_at
revoked_at
revoked_reason

browser_family
os_family
device_family
user_agent_summary

created_country
created_region
created_city
last_seen_country
last_seen_region
last_seen_city
```

User-Agent and IP-derived location are approximate display metadata, not
authentication factors. V1 stores only the minimum coarse location needed for
the Session UI, does not persist the raw IP after coarse-location derivation,
and does not introduce browser fingerprinting. Session activity metadata is
updated during successful refresh or explicit Session probes rather than by
writing on every GraphQL request.

Both `ref` and `public_ref` are unique, unguessable values. The persistence
layer indexes active Sessions by `user_id` and expiry, and runs a bounded cleanup
policy for expired/revoked records so the device list and Session table do not
grow indefinitely.

The internal `ref` is the `browserSessionRef` stored in Auth.js and the access
token `sid`; it is never returned to browser JavaScript. Session-management APIs
return a separate random `publicRef` plus a server-computed `isCurrent` flag.
Authenticated users use `publicRef` to revoke one of their own Sessions, while
Phoenix resolves ownership and the internal ref server-side.

Auth derives connection metadata from the actual callback/refresh request and
trusted platform forwarding headers, normalizes it, and passes it to Phoenix
through the trusted operation. Phoenix must not accept arbitrary client-supplied
IP, current-Session, or ownership fields.

## Current State

The current sign-in flow is:

```text
Browser
  -> Auth.js OAuth flow
  -> Auth submits provider identity to Phoenix
  -> Phoenix returns groupher-auth.token
  -> Auth.js issues Browser Session
  -> Auth appends Phoenix token and signed-in hint Cookies
  -> Browser enters Main / Dashboard / Dash
```

Current constraints:

- Auth.js Session and Phoenix-token Cookies use a 14-day `Max-Age`, but the
  Guardian JWT inside `groupher-auth.token` currently has a 30-day internal
  expiry. A copied token can therefore outlive the browser Cookie that carried
  it.
- Phoenix token is appended only after Auth.js actually issues its Session
  Cookie, preventing a half-signed-in browser state.
- Auth owns unified logout and clears Auth.js, Phoenix, and hint Cookies, but it
  does not revoke a persisted server-side Browser Session because none exists.
- Main, Dashboard, Dash, Gateway, and Phoenix do not decode the Auth.js Session.
- The current shared Auth.js Cookie override applies the parent Domain to CSRF,
  callback, state, PKCE, nonce, and challenge Cookies as well as the Session;
  V1 makes the Session and protocol Cookies host-only and leaves only the
  short-lived Phoenix token and hint on the parent Domain.
- There is no `POST /api/auth/token/refresh` endpoint yet.
- An expired Phoenix token currently requires a new login flow.
- The shared account UI calls the existing Login Modal; there is no standalone
  canonical `/login` page.

The target refresh flow below is a future Auth capability. Product applications
must not implement local token minting as a temporary substitute.

## Target Sign-In Flow

The existing shared Login Modal remains the product UI, but the OAuth protocol
starts on the canonical Auth origin so Auth.js protocol Cookies can remain
host-only:

```text
Login Modal on an approved product origin
  -> credentialed GET https://auth.groupher.com/api/auth/csrf
  -> Auth sets a host-only __Host-groupher-auth.csrf-token
  -> top-level POST https://auth.groupher.com/api/auth/signin/<provider>
     with the CSRF token and validated returnTo
  -> Auth sets host-only callback/state/PKCE/nonce Cookies
  -> OAuth provider
  -> https://auth.groupher.com/api/auth/callback/<provider>
  -> Auth validates the host-only protocol Cookies
  -> Auth writes the host-only Browser Session
  -> Auth writes the parent-domain Phoenix token and hint
  -> redirect to validated returnTo
```

Canonical Auth allows credentialed CORS from the exact approved product-origin
capability registry only for CSRF bootstrap, Session probe/list, refresh,
logout, and Session revoke. OAuth state-changing POSTs still use Auth.js's
host-only double-submit CSRF contract. Product origins do not proxy the OAuth
authorization start or callback through their own `/api/auth/*` paths.

Auth.js protocol Cookies include CSRF, callback URL, OAuth state, PKCE verifier,
nonce, and WebAuthn challenge Cookies. They use `Secure`, `HttpOnly` where the
protocol permits it, `SameSite=Lax`, `Path=/`, no `Domain`, and a `__Host-`
prefix where supported. They are not reused by Groupher refresh or logout.

The V1 Auth-to-Phoenix sign-in exchange returns:

```ts
type TBrowserSigninResult = {
  accessToken: string
  accessExpiresAt: string
  browserSessionRef: string
  sessionAbsoluteExpiresAt: string
  user: User
}
```

`browserSessionRef` is a stable, non-permission-bearing reference used only by
trusted Auth-to-Phoenix operations. Auth stores it inside the protected Auth.js
Session. Browser JavaScript and product applications never receive it directly.

During the independent Service Identity V2 migration, the trusted operations in
this flow use `sub=service:auth`, an exact Phoenix accounts audience, and bounded
OAuth/session scopes. Until then they retain the existing bootstrap trust
transport without changing this Browser Session response contract.

```text
Browser
  -> Auth OAuth callback
  -> Phoenix signin/link identity
  -> Phoenix checks account state
  -> Phoenix creates a persisted Browser Session with a 90-day absolute expiry
  -> Phoenix issues a 30-minute accessToken
     with aud=phoenix:browser-api and sid=browserSessionRef
  -> Auth stores browserSessionRef and the absolute expiry in Auth.js Session
  -> Auth writes groupher-auth.token
  -> Auth discards the GitHub provider token after identity establishment
  -> Auth redirects to validated returnTo
```

Phoenix, as the token issuer, sets the JWT `iat` and `exp` claims and returns
`accessExpiresAt`. Auth must not infer token expiry from Cookie configuration.
The access-token Cookie expiry must not exceed either `accessExpiresAt` or the
Browser Session absolute expiry.

## Refresh Endpoint

Auth owns:

```http
POST https://auth.groupher.com/api/auth/token/refresh
```

This is a browser-originated request sent directly to the canonical Auth origin
with `credentials: include`. It is cross-origin but same-site when called by
Main, Dashboard, or Dash. Product-origin Gateway routes do not proxy it because
they cannot receive the host-only Auth Browser Session.

The request must contain an exact approved HTTPS `Origin` and the non-simple
`X-Groupher-CSRF: 1` header. Auth's credentialed CORS policy allows that exact
origin and header; Auth rejects missing, `null`, or unapproved origins before
reading the Browser Session. This contract does not depend on Auth.js's
host-only CSRF Cookie and is not bypassed merely because a product server can
reach Auth.

The endpoint:

1. Validates the Groupher Origin/custom-header CSRF contract.
2. Reads and validates the Auth.js Session.
3. Extracts the protected `browserSessionRef`.
4. Calls a trusted Phoenix browser-session refresh operation.
5. Phoenix verifies the user, account, session, and revocation state.
6. Phoenix rejects the request when `now >= sessionAbsoluteExpiresAt`.
7. Phoenix updates bounded Session activity/device metadata and reissues a
   30-minute access token, capped at the absolute Session expiry.
8. Auth writes a new `groupher-auth.token` Cookie.
9. Auth returns a no-store response without exposing the token in JSON.

Example success response:

```http
HTTP/1.1 204 No Content
Cache-Control: no-store
Set-Cookie: groupher-auth.token=<redacted>; HttpOnly; Secure; SameSite=Lax; Path=/; Domain=.groupher.com
```

The endpoint may return non-sensitive metadata such as `expiresAt` if a consumer
needs it, but it must never return the credential value.

### Refresh Response Contract

```text
204
  refreshed successfully

400
  malformed request or invalid CSRF/origin contract

401
  Auth Browser Session missing, expired, invalid, or revoked

403
  account blocked or browser session no longer allowed to obtain access

409
  session/token family conflict that requires a new login

429
  refresh rate limited

5xx
  temporary Auth or Phoenix failure
```

Product applications retry refresh only for the original authentication
failure. They do not recursively refresh after the retried request.

## Browser State-Change CSRF Boundary

Parent-domain Cookies are same-site across Groupher subdomains, so
`SameSite=Lax` is not a CSRF boundary between them. Every browser-authenticated
state change must enforce an application-level CSRF contract:

```text
Auth refresh/logout/Session-revoke
  browser calls the canonical Auth origin directly with credentials: include
  exact approved HTTPS Origin
  X-Groupher-CSRF: 1
  reject missing/null/unapproved Origin

Gateway browser GraphQL route
  for browser requests, accept application/json only
  preserve the browser Origin unchanged
  require X-Groupher-CSRF: 1 on every POST before proxying
  reject form-urlencoded and multipart browser requests

Phoenix GraphQL mutation
  reject mutation over GET
  when authentication came from groupher-auth.token Cookie:
    revalidate exact Origin and X-Groupher-CSRF
  when authentication came from a V2 service/delegation credential:
    use the service/delegation verifier, not browser Origin
```

Gateway provides an early rejection boundary; Phoenix remains the final
defense and must not trust a synthetic or overwritten Origin from Gateway or a
product server. Browser-originated server functions preserve the original
Origin and CSRF header. Background SSR queries may use the browser token under
the SSR rules below, but background SSR must not initiate mutations.

The custom header prevents plain HTML forms from satisfying the contract, and
exact Origin validation rejects unapproved sibling origins. Neither mechanism
protects against XSS or a compromised approved origin. Those origins are inside
the V1 credential trust boundary and require deployment, DNS, CSP, dependency,
and subdomain-takeover controls. CORS response headers alone are not CSRF
enforcement; the request handler must reject the request before side effects.

Auth, Gateway, Phoenix, and canonical Auth's credentialed browser-API CORS
policy consume one environment-scoped exact-origin registry rather than
maintaining unrelated hard-coded arrays. Production matches scheme and host
with no unexpected port; development registers explicit scheme/host/port tuples
and does not allow an arbitrary `*.localhost` origin.

## Application Consumer Contract

Main, Dashboard, Dash, Apply, and future first-party applications should reuse a
single consumer contract:

```text
frontend/core/lib/auth/
  signIn()
  signOut()
  refreshSession()
  listSessions()
  revokeSession(publicRef)
  revokeOtherSessions()
  withAuthRetry()
  resolveAuthFailure()
  clearAuthState()
  requestLogin()
  sessionChannel()
```

The package is exported through the `~/auth` alias. The existing
`frontend/core/lib/oauth.ts` behavior moves behind this entry point during the
refactor. This is a protocol consumer, not a second Auth implementation.

### Browser Request Flow

```text
application operation
  -> request Phoenix/API
  -> success
       return result
  -> protected operation returns 401 TOKEN_EXPIRED / TOKEN_MISSING
       enter single-flight refresh
       POST https://auth.groupher.com/api/auth/token/refresh
       refresh succeeds
         retry original operation once
       refresh fails
         clear local auth-sensitive state
         request the existing Login Modal with returnTo
  -> 401 TOKEN_INVALID / TOKEN_REVOKED
       do not loop
       clear local auth-sensitive state
       request the existing Login Modal
  -> 403
       do not refresh
       render permission failure or reload viewer permissions
```

Phoenix should return machine-readable authentication error codes so consumers
do not infer refreshability from an arbitrary error message:

```text
TOKEN_EXPIRED
TOKEN_MISSING
TOKEN_INVALID
TOKEN_REVOKED
SESSION_EXPIRED
SESSION_REVOKED
ACCOUNT_BLOCKED
PERMISSION_DENIED
```

GraphQL may transport these failures in a successful HTTP response. urql,
Next, and Dash must preserve and classify `errors[].extensions.code`; they must
not flatten the error into a message string before Auth handling.

`TOKEN_MISSING` matters after the 30-minute access Cookie expires: the browser
no longer sends an expired Cookie, so Phoenix cannot return `TOKEN_EXPIRED` for
it. Consumers attempt refresh for `TOKEN_MISSING` only at an authenticated
route or operation boundary, optionally informed by the non-authoritative
signed-in hint. Anonymous public operations must not start a refresh loop.

Cookie-loss behavior is deterministic:

```text
access Cookie present
  send the authenticated operation normally

access Cookie missing at an authenticated route/operation boundary
  call canonical Auth for one refresh/session check with credentials: include
  the signed-in hint may trigger this earlier but is not required

Auth Session still present and valid
  refresh the access Cookie

canonical Auth reports no Session, and access Cookie and signed-in hint are absent
  treat the browser as anonymous
  do not try to recover identity from device, IP, or server-side Session rows
  request OAuth login when the route/operation requires authentication
```

A persisted Browser Session whose Cookies were cleared becomes unreachable from
that browser and remains only until revocation, absolute expiry, or retention
cleanup. A no-Cookie probe cannot safely rediscover it.

### Single-Flight Refresh

Refresh is demand-driven, not interval-driven. Product applications must not
start a 30-minute timer or poll Auth merely because the access-token TTL is 30
minutes. A runtime refreshes only when an authenticated route/operation reaches
the documented `TOKEN_EXPIRED` / `TOKEN_MISSING` boundary, or immediately
before a known long-running protected operation when the shared Auth consumer
has reliable expiry metadata.

Because `groupher-auth.token` is a parent-domain Cookie, one successful refresh
replaces the token used by Main, Dashboard, Dash, and other Groupher subdomains:

```text
Dashboard encounters TOKEN_MISSING
  -> calls canonical Auth once
  -> Auth writes a new Domain=.groupher.com access Cookie

Main sends its next protected request
  -> browser automatically carries the refreshed Cookie
  -> Main does not refresh again
```

Applications do not need to read the HttpOnly Cookie or notify other origins to
obtain this benefit. The browser's Cookie store is the cross-origin convergence
mechanism.

Within one application tab/runtime:

```text
request A -> 401
request B -> 401
request C -> 401

all await one refresh promise
  -> one POST https://auth.groupher.com/api/auth/token/refresh
  -> retry A/B/C once after success
```

Do not allow every urql operation, route loader, or server function to trigger an
independent refresh request.

Different origins cannot share the in-memory single-flight promise and may race
when they all encounter expiry at the same moment. Refresh and Phoenix token
reissue are therefore idempotent and tolerate a small burst of equivalent
requests. Add a short server-side coalescing window keyed by
`browserSessionRef` only if production metrics show meaningful duplication;
V1 does not add distributed locking preemptively. Rate limits must tolerate this
legitimate cross-origin race.

Canonical Auth may return a bounded `Access-Control-Max-Age` for successful
preflight responses to reduce repeated CORS preflights. Auth still validates the
actual request Origin, CSRF header, Session, and rate limit every time; a cached
preflight is never authentication proof.

Credentialed canonical-Auth routes use an explicit preflight contract:

```http
Access-Control-Allow-Origin: <exact-approved-origin>
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: Content-Type, X-Groupher-CSRF
Access-Control-Max-Age: <bounded-seconds>
Vary: Origin
```

The `OPTIONS` handler validates the requested Origin, method, and headers but
does not require a login Cookie. The actual request performs the complete
Origin, CSRF, Session, authorization, and rate-limit checks. Wildcard origins
and wildcard credentialed headers are not allowed. Read-only Session listing
uses credentialed CORS and `Cache-Control: no-store`; it does not require the
state-change CSRF header.

### Multi-Tab Behavior

Use `BroadcastChannel` as an optional same-origin browser optimization for:

```text
auth:refreshed
auth:logout
auth:invalid
```

The tab that completes logout or refresh publishes the event after the Auth
request succeeds. Other tabs on the same browser origin receive the event and
clear or reconcile their local state.

The browser origin, not the deployment platform, determines whether this works:

```text
https://groupher.com/home
https://groupher.com/home/dashboard
https://groupher.com/home/dash
```

These can coordinate even when Main is deployed on Vercel and Dash is deployed
on Cloudflare, because the browser sees one origin.

Different subdomains cannot use this channel:

```text
https://groupher.com
https://dashboard.groupher.com
https://dash.groupher.com
https://auth.groupher.com
```

For different first-party origins, use an Auth Session probe when a page becomes
visible, receives focus, enters a protected route, or receives an authentication
failure. The browser calls canonical Auth directly with `credentials: include`;
only `auth.groupher.com` receives the host-only Browser Session. Auth applies
the shared exact-origin credentialed CORS policy and returns a no-store response:

```text
GET https://auth.groupher.com/api/auth/session
  -> authenticated
       keep local state
  -> unauthenticated/revoked
       clear protected Valtio state
       request the shared Login Modal when required
```

For another device, only server-side session revocation and a later request or
session probe can converge the state. A server cannot directly publish a
browser `BroadcastChannel` event to a different device.

These messages are hints for coordinating UI and retries. Cookies and the
server-side Auth/Phoenix session remain the source of truth. The shared Auth
consumer owns the channel and invokes an application callback such as
`clearAuthState()`; Dash does not define a separate local broadcast protocol.

## SSR And Server Runtime Flow

Browser Auth V1 does not let an SSR renderer call the browser refresh endpoint
as an Origin/CSRF exception. An SSR page request often has no browser `Origin`,
and a product server must not manufacture one as authentication proof.

The V1 SSR flow is:

```text
SSR request
  -> forward groupher-auth.token to Phoenix
  -> Phoenix accepts
       continue render
  -> Phoenix returns refreshable 401
       return a neutral auth-recovery/loading boundary
       start one canonical-Auth browser refresh after hydration
       browser refresh succeeds
         invalidate/retry the protected route once
       browser refresh fails
         enter the signed-out/Login Modal state and preserve a validated returnTo
```

Browser-originated server-function requests may preserve the original Origin
and CSRF proof for application mutations, but they do not proxy Auth Session,
refresh, or logout requests. Auth responses reach the browser directly so the
browser can update both the host-only Session and parent-domain token Cookies.
A background SSR render cannot receive the Auth host-only Session through a
product request and does not call refresh. Product applications never parse or
re-sign the Auth.js Session.

After Service Identity V2, an optional backchannel SSR refresh may use the
calling product's service identity plus an explicit binding to the original
Auth Browser Session. That is a separate internal contract; it is not an
Origin-validation bypass in V1.

## urql, Loaders, And Server Functions

The Auth lifecycle is independent of the application's data ownership model.

```text
TanStack/Next SSR loader
  -> loads canonical data
  -> initializes scoped Valtio stores

Core business component
  -> reads Valtio
  -> performs GraphQL mutation through urql

Auth consumer
  -> wraps the underlying authenticated request
  -> refreshes once when allowed
```

Rules:

- Route loaders do not own Auth Session renewal.
- Valtio does not store credential values.
- urql does not implement its own refresh protocol per mutation.
- Server functions consume the same shared Auth contract.
- Dash/Main cache revalidation credentials remain separate service credentials,
  not Browser Session Cookies.

Dashboard To TanStack V2 follows this model and references this document rather
than defining another 401/refresh flow.

## Permission Changes And `403`

Token refresh is not a permission refresh mechanism.

```text
401
  authentication credential is missing, expired, invalid, or revoked

403
  authenticated user is not allowed to perform the operation
```

On `403`:

- Do not call the canonical Auth refresh endpoint or enter the
  refresh-and-retry path.
- Phoenix remains authoritative.
- Reload viewer/community permission data where useful.
- Clear or disable protected local workflows.
- Preserve unsaved drafts when it is safe to do so.
- Render a stable no-permission state or leave the protected route.

If Phoenix embeds coarse authorization claims in the browser access token,
those claims must be short-lived and Phoenix must still enforce sensitive
authorization against current server state.

## Logout

Logout remains Auth-owned:

```http
POST https://auth.groupher.com/api/auth/logout
```

Like refresh, logout and Browser Session revoke requests use the exact approved
Origin plus `X-Groupher-CSRF: 1` contract and are sent directly to canonical
Auth with `credentials: include`. They do not depend on the Auth.js host-only
CSRF Cookie or a product-origin Gateway route.

Flow:

```text
Browser
  -> Auth logout
  -> revoke the current persisted Browser Session through trusted Phoenix
  -> clear Auth.js Session Cookies
  -> clear groupher-auth.token
  -> clear groupher-auth.signed-in
  -> return no-store response
  -> broadcast auth:logout
  -> product app clears viewer and protected Valtio stores
```

Applications must not independently clear only one Cookie and leave a
half-authenticated browser state.

The Phoenix revoke operation is idempotent. If Phoenix is temporarily
unavailable, Auth returns a no-store retriable failure and does not report or
broadcast successful logout; the application keeps the authenticated state and
offers retry. V1 does not silently claim success while leaving a refreshable
server-side Session active.

Post-logout navigation is an application concern:

```text
Main
  refresh the current page in place

Dashboard / Dash
  enter a safe signed-out state
  open the existing shared Login Modal
```

V1 does not add a standalone `/login` page. Protected operations and route
boundaries call `requestLogin({ returnTo })` from `~/auth`; the Modal submits the
existing OAuth flow and returns to the validated current product URL.

## Cookie Requirements

V1 keeps the long-lived Auth credential host-only and shares only the
short-lived Phoenix access credential across Groupher product subdomains.

Canonical Auth host-only Cookies:

```text
__Host-groupher-auth.session-token
  HttpOnly; Secure; SameSite=Lax; Path=/; no Domain
  sent only to auth.groupher.com

__Host-groupher-auth.csrf-token
__Host-groupher-auth.callback-url
__Host-groupher-auth.state
__Host-groupher-auth.pkce.code_verifier
__Host-groupher-auth.nonce
__Host-groupher-auth.challenge

Secure; SameSite=Lax; Path=/; no Domain
HttpOnly where supported by the Auth.js protocol
sent only to auth.groupher.com
```

Parent-domain product Cookies:

```text
groupher-auth.token
  HttpOnly; Secure; SameSite=Lax; Path=/; Domain=.groupher.com

groupher-auth.signed-in
  Secure; SameSite=Lax; Path=/; Domain=.groupher.com
  browser-readable and never authentication proof
```

The 90-day Browser Session and OAuth protocol state remain bound to canonical
Auth. The 30-minute Phoenix token and non-sensitive hint are shared because
path-based and subdomain product entry points coexist:

```text
OAuth start and callback
  https://auth.groupher.com/api/auth/*
  -> host-only protocol Cookies

successful Auth callback
  https://auth.groupher.com/api/auth/callback/*
  -> host-only Browser Session
  -> parent-domain access/hint Cookies

Auth-enabled product origins
  https://groupher.com
  https://main.groupher.com
  https://dashboard.groupher.com
  https://dash.groupher.com
  -> OAuth bootstrap, Session read/write, and browser GraphQL capabilities

canonical Auth self-origin
  https://auth.groupher.com
  -> OAuth callback and canonical Auth handlers

explicitly public-only origin
  https://landing.groupher.com
  -> no OAuth bootstrap, Session read, refresh, logout, revoke, or browser
     GraphQL state-change capability

browser Auth/API paths
  canonical-origin OAuth protocol paths -> Auth
  canonical-origin /api/auth/session -> Auth, credentials: include
  canonical-origin /api/auth/token/refresh -> Auth, credentials: include
  canonical-origin /api/auth/logout -> Auth, credentials: include
  canonical-origin /api/auth/sessions* -> Auth, credentials: include
  current-origin /api/graphql -> Gateway -> Phoenix
```

The exact-origin registry is capability-based rather than a single permissive
list. `landing.groupher.com` serves only public pages such as `/`, `/pricing`,
and `/book-demo`, so canonical Auth and browser GraphQL mutation handlers reject
it as an initiating Origin. `groupher.com` remains Auth-enabled because the same
origin also serves authenticated Main paths, even though some of its routes are
public. A future application receives no Auth capability until its exact origin
and required capabilities are registered explicitly.

Product request transport may carry the parent-domain access token and hint but
never the Auth Browser Session or Auth.js protocol Cookies. Product applications
therefore cannot decode or leak the 90-day Session. Gateway forwards only the
canonical Phoenix token on browser GraphQL requests.

`Domain=.groupher.com` is not limited to the approved-origin registry: the browser
sends a matching Cookie to every Groupher subdomain it visits. Consequently,
every host that can serve `*.groupher.com` traffic is inside the credential
trust boundary even if it is not approved to initiate state changes. A
compromised subdomain server can receive the current parent-domain 30-minute
Phoenix token, and an approved compromised origin passes Origin validation. It
cannot receive the host-only 90-day Browser Session or refresh after the stolen
access token expires without the user's browser successfully calling canonical
Auth again. Origin/custom-header CSRF checks reduce cross-origin request abuse
but do not isolate the short-lived access credential from a compromised sibling
host.

V1 therefore requires Groupher-controlled DNS and deployments for the entire
namespace, no user-controlled subdomain hosting, prompt removal of claimable
abandoned records, exact state-changing Origin allowlists, and equivalent
security controls across credential-receiving applications. If that trust model
cannot be maintained even for a 30-minute access token, the replacement is
host-only per-product access Cookies plus a one-time Auth code exchange/BFF;
CSRF checks alone are not an alternative.

Additional requirements:

- Do not put credential values in `localStorage` or `sessionStorage`.
- Do not expose refresh credentials to browser JavaScript.
- Do not log Cookie values or token payloads.
- Validate all return URLs against the first-party allowlist.
- Protect every browser-cookie-authenticated state-changing endpoint, including
  Phoenix GraphQL mutations, with the documented Origin/custom-header contract.
- Keep the Auth Browser Session and Auth.js protocol Cookies host-only; never
  apply the access token's parent Domain to Session, CSRF, callback, state,
  PKCE, nonce, or challenge Cookies.
- Return `Cache-Control: no-store` from Auth/session/token endpoints.
- Rotate identifiers after sign-in and privilege-sensitive session changes.

V1 Cookie lifetimes are intentionally different:

```text
groupher-auth.token
  no longer than the 30-minute Phoenix access-token expiry

__Host-groupher-auth.session-token
  no longer than the original 90-day Browser Session absolute expiry
  sent only to auth.groupher.com

groupher-auth.signed-in
  follows the Browser Session lifetime
  remains a non-authoritative probe hint
```

Custom community domains cannot directly share Groupher parent-domain Cookies.
They require a separate one-time code exchange flow.

## Expiration And Rotation Policy

V1 fixes the following policy:

```text
Phoenix browser access token TTL
  30 minutes

Auth Browser Session absolute lifetime
  90 days from the initial OAuth sign-in
  never extended by refresh or Cookie rotation

Auth Browser Session idle timeout
  disabled in V1
```

When Phoenix issues a token near the end of the Session, it uses:

```text
accessExpiresAt = min(now + 30 minutes, sessionAbsoluteExpiresAt)
```

The access-token Cookie must expire no later than the JWT. The current shared
14-day Cookie maximum and 30-day Guardian JWT lifetime are removed rather than
carried into the new model.

Provider-token policy is separate:

```text
GitHub used only for sign-in
  validate the provider identity during callback
  bind the stable provider account id to the Groupher user
  discard the provider access token after identity establishment

Future GitHub repository/organization integration
  request separate scopes
  store and refresh its provider token independently
  do not couple integration failure to the Groupher Browser Session
```

V1 uses the stable `browserSessionRef` for lookup, revocation, and device-list
ownership. Refresh-token family/version rotation and reuse detection are a later
hardening phase. The ref alone does not detect replay; the 30-minute access TTL,
secure Cookie transport, server-side revocation, Origin/CSRF checks, and bounded
retry are the V1 replay-risk controls.

V1 explicitly accepts the remaining risk that a stolen Auth Browser Session
Cookie can obtain new access tokens until the Session is revoked or reaches its
original 90-day absolute expiry. A stolen access token alone remains bounded by
its 30-minute expiry. Idle timeout, refresh-secret rotation, and reuse detection
are deferred hardening rather than implicit V1 behavior.

## Failure And Availability Policy

Authentication correctness is preferred over silently accepting stale or
unverifiable credentials.

```text
Auth unavailable, access token still valid
  current Phoenix request may continue

Auth unavailable, access token expired
  do not bypass expiry
  show a recoverable auth-unavailable state or redirect when safe

Phoenix unavailable during refresh
  return temporary failure
  do not mint a local token

refresh repeatedly fails
  stop after bounded retry
  emit structured logs/metrics
  require a new login when the failure is non-transient
```

Refresh endpoints must be rate limited and observable without logging secrets.

## Security And Observability

Record:

```text
refresh attempt count
refresh success/failure reason
Auth Session expiry/revocation
Phoenix token expiry/revocation
Browser Session creation/revocation
remote Session revocation
401 retry success rate
403 rate by operation
logout success
open-redirect rejection
CSRF/origin rejection
```

Never record:

```text
Auth.js Session payload
Phoenix token
provider access/refresh token
Cookie headers
OAuth authorization code
```

Use correlation/request IDs rather than credentials to trace a flow across
Gateway, Auth, Phoenix, and product applications.

Remote Session revocation cannot delete a Cookie held by another browser. In V1
it prevents further refresh immediately, while an already issued access token
may remain usable for at most 30 minutes. Operations such as ownership transfer,
billing changes, API-key creation, community deletion, domain changes, and SSO
changes may additionally require a recent authentication check.

## Extension Boundaries

### Service Identity And Client Credentials (V2)

Service-to-service authentication and user delegation are defined separately in
[`v2.md`](./v2.md). Browser Auth V1 does not add a service-token issuer, migrate
the global Trust Secret, or change sub-app communication credentials.

Until V2, current service credentials remain explicit bootstrap mechanisms. V1
must not add new consumers of the global Trust Secret, treat a client marker as
authentication, or make Press projections broader than bounded current public
content. `PRESS_INTERNAL_TOKEN` remains independent from the global Phoenix
Trust Secret until both are replaced by scoped V2 identities.

### Additional Web Identity Providers

GitHub, Google, Apple, and customer OIDC/SAML providers all terminate at Auth.
They normalize into the same Phoenix identity exchange and Browser Session
contract.

### External Clients

MCP, agents, CLI tools, and third-party API clients use the separate OAuth
Provider or API Token architecture from `docs/oauth/overview.md`. They do not use
the Browser Session refresh endpoint.

### Device And Session Management

Every authenticated user can list and revoke their own Browser Sessions. The
browser-facing surface belongs to canonical Auth:

```http
GET  https://auth.groupher.com/api/auth/sessions
POST https://auth.groupher.com/api/auth/sessions/<publicRef>/revoke
POST https://auth.groupher.com/api/auth/sessions/revoke-others
```

Canonical Auth reads the current host-only Browser Session, obtains its internal
`browserSessionRef`, and calls Phoenix through trusted Session-list/revoke
operations. Those Phoenix operations are not browser GraphQL mutations. Phoenix
remains authoritative for ownership, current-Session calculation, and revoke
state; Auth is the browser protocol boundary.

The browser may supply only the target Session's random `publicRef`. The API
never exposes or accepts an Auth.js Session payload, internal
`browserSessionRef`, owner id, current-Session claim, or credential value. Each
row exposes a `publicRef` and server-computed `isCurrent` flag. The list route is
credentialed, read-only, and `no-store`; revoke routes require the exact Origin
and `X-Groupher-CSRF: 1`. Revoking the current Session uses the normal
`signOut()` flow so Auth can revoke it and clear every Cookie atomically.

The shared account UI exposes the feature through the existing account Tooltip:

```text
click account avatar
  -> account Tooltip
  -> "Logged in by GitHub        >"
  -> close Tooltip
  -> open the Login And Devices Drawer
```

The Drawer shows the login provider, marks the current Session, and lists the
approximate browser, OS/device family, coarse location, sign-in time, and last
activity. Users can revoke one other Session or revoke all other Sessions while
keeping the current Session. The existing account logout remains the way to end
the current Session.

A location change alone updates the current record; it does not create a new
Session. A new OAuth sign-in, browser/profile, cleared Cookie, or private window
creates another Session. Unknown or unreliable device/location values must have
a stable fallback UI.

The frontend implementation belongs to a shared unit such as
`frontend/core/unit/AccountSessionDrawer/`. It uses the existing global Drawer
event boundary. Opening the Drawer first closes the Tooltip, and components
follow the existing one-component-per-file and local `useSalon()` conventions.

Future extensions include recent authentication, step-up authentication,
risk-based revocation, idle expiry, refresh-family rotation, and richer Session
audit events. None require product applications to decode Auth.js internals.

## V1 And V2 Sequencing

Browser Auth V1 and Service Identity V2 are independent contracts and may be
developed in parallel:

```text
V1 Browser Session cutover before V2
  Auth -> Phoenix keeps the existing bootstrap server-trust transport
  V1 completes the coordinated Phoenix/Auth/Gateway/product cutover
  V2 later replaces only the service transport with service:auth

V2 service:auth available before V1 cutover
  V1 sign-in, refresh, revoke, and logout use the scoped service identity
  the Browser Session contract and one-time user relogin remain unchanged
```

V1 must not wait for the full multi-service V2 migration, and V2 must not reopen
the V1 Browser Session or Cookie model. V1 is one coordinated browser-session
cutover; V2 migrates service communication one edge at a time and ultimately
removes the bootstrap Trust Secret.

application release below is deployed as part of the same coordinated window;
deploying the Phoenix V1 release earlier would immediately reject legacy browser
tokens because strict claim validation is unconditional.

## Implementation Workstreams

The Browser Session V1 ships as one contract cutover rather than a compatibility
migration. Existing Auth/Phoenix browser sessions are invalidated once and users
complete OAuth sign-in again; V1 does not backfill `browserSessionRef` into old
Sessions or maintain the former 14/30-day lifecycle in parallel.

### Workstream 1: Phoenix Session And Token Contract

- Add the persisted Browser Session schema, secure ref generation, device
  metadata, internal/public ref separation, ownership rules, and current/other
  Session queries.
- Extend OAuth sign-in to create a Browser Session and return
  `TBrowserSigninResult`.
- Refactor Guardian browser-token issue to 30 minutes with the expected `iss`,
  `aud=phoenix:browser-api`, `sid`, and `typ=browser_access`, capped at the
  Session absolute expiry.
- Require the V1 issuer, audience, `sid`, and `typ=browser_access` on the
  browser-Cookie path so legacy Cookies are rejected during cutover without
  rotating a secret shared by unrelated token contracts.

  Origin and `X-Groupher-CSRF` contract, while keeping V2 service/delegation
  authentication on its separate verifier path.

### Workstream 2: Auth Session, Refresh, And Logout

- Store `browserSessionRef` and the immutable absolute expiry in the protected
  Auth.js Session.
- Replace the shared 14-day lifetime with separate 30-minute access and 90-day

The repository includes an isolated Auth V1 browser stack for Playwright. It
starts Dash, a canonical Auth instance with an independent test secret and

Run the complete P0/P1/P2 browser matrix with:


## Acceptance Criteria

- Auth remains the only component that reads or writes Auth.js Session state.
- Product applications never mint or decode browser credentials.
- Phoenix remains the final authority for user and business permissions.
- Phoenix access tokens expire after at most 30 minutes and never extend past
  the Browser Session absolute expiry.
- Browser Sessions expire absolutely 90 days after initial OAuth sign-in;
  refresh and Auth.js Cookie rotation never extend that boundary.
- V1 does not implement an idle timeout.
- V1 explicitly accepts that a stolen Auth Browser Session Cookie can refresh
  access until server-side revocation or the original 90-day absolute expiry;
  only canonical Auth receives that host-only Cookie, while refresh-secret
  rotation, reuse detection, and idle timeout are deferred.
- Browser access tokens require the expected issuer,
  `aud=phoenix:browser-api`, and `typ=browser_access`; another resource server
  must reject them.
- The Browser Session and Auth.js CSRF/callback/state/PKCE/nonce/challenge
  Cookies are host-only on `auth.groupher.com`; only the 30-minute Phoenix token
  and non-sensitive hint use `Domain=.groupher.com`.
- Browser tests confirm every `__Host-` Session/protocol Cookie omits `Domain`
  and uses `Secure` plus `Path=/`; the former shared Cookie `Domain` override is
  removed rather than reused under a new prefix.
- The former 14-day Cookie and 30-day Guardian JWT lifecycle is removed during
  the one-time Session cutover.
- Legacy parent-domain Auth.js Session Cookies may remain in browser storage until
  their existing expiry, but V1 never reads them and does not add special cleanup
  code. Their physical presence is not proof of a valid V1 Session.
- Expired or missing Phoenix browser tokens trigger at most one refresh attempt
  at authenticated route/operation boundaries.
- Anonymous public operations do not refresh merely because the access Cookie
  is absent.
- `403` never triggers refresh.
- Refresh never returns credential values in JSON.
- Refresh, logout, Session revoke, and browser-Cookie GraphQL mutations reject
  missing, `null`, or unapproved Origin and require `X-Groupher-CSRF: 1`.
- Credentialed Auth preflight responses reflect only an exact approved Origin,
  allow credentials, declare the required methods and
  `Content-Type, X-Groupher-CSRF` headers, emit `Vary: Origin`, and never treat
  successful `OPTIONS` as authorization for the actual request.
- Browser GraphQL POSTs require `application/json` and `X-Groupher-CSRF: 1`;
  Phoenix rejects mutations over GET, and CORS response policy alone is never
  treated as CSRF validation.
- Background SSR renders do not call the browser refresh endpoint without
  browser Origin/CSRF proof. The browser calls canonical Auth directly and
  applies its host-only and parent-domain `Set-Cookie` responses; product routes
  never proxy the Auth Browser Session.
- When an authenticated SSR request encounters an expired access token, V1
  accepts that the server cannot render authenticated content. It renders a
  neutral auth-recovery/loading boundary, performs at most one canonical-Auth
  refresh after hydration, and invalidates/retries the protected route once;
  implementations must not restore background SSR refresh to hide this state.
- Concurrent failures create one refresh request per application runtime.
- Product applications do not run periodic refresh timers. One successful
  refresh updates the shared parent-domain access Cookie, so another origin's
  next request uses it without performing its own refresh.
- Simultaneous expiry across different origins may produce a small idempotent
  refresh burst; rate limits permit it, and server-side coalescing is added only
  when production metrics justify it.
- Logout clears every Auth and Phoenix browser Cookie.
- Logout revokes the current persisted Browser Session before reporting full
  server-side logout success.
- Multi-tab logout clears protected application state.
- Same-origin logout/refresh events use the shared Auth consumer's
  `BroadcastChannel` optimization; cross-origin and cross-device state uses
  Auth Session probes or authentication responses.
- Auth/session/token endpoints return `Cache-Control: no-store`.
- Browser credentials never enter browser storage or logs.
- `browserSessionRef` remains internal to Auth/Phoenix; device-list operations
  use an owner-checked `publicRef` and server-computed `isCurrent`.
- Every authenticated user can open Login And Devices from the account Tooltip,
  identify the current Session, revoke one other Session, or revoke all other
  Sessions.
- Session list and revoke browser requests use canonical Auth and the shared
  `~/auth` consumer. Phoenix exposes their implementation only as trusted Auth-
  to-Phoenix operations, not browser GraphQL Session mutations.
- Main refreshes in place after logout; Dashboard and Dash reuse the existing
  shared Login Modal rather than a standalone `/login` page.
- GitHub provider tokens are discarded after sign-in unless a future,
  separately authorized GitHub integration needs them.
- Old browser sessions are invalidated once; no legacy Session backfill or
  parallel 14/30-day compatibility path remains.
- V1 has no legacy browser-token feature flag or dual validator. The Phoenix V1
  release therefore ships only inside the coordinated maintenance window, after
  the additive database migration is ready.
- Legacy Phoenix access tokens carried by the browser Cookie without the V1
  `sid` and `typ=browser_access` claims are rejected without requiring a global
  signing-secret rotation.
- Every host that can serve `*.groupher.com` traffic is treated as
  trusted to receive a currently valid 30-minute Phoenix token because
  parent-domain Cookies are sent by domain match, not by the approved-Origin
  list. It never receives the 90-day host-only Auth Session. Approved origins
  alone may initiate browser state changes; custom domains receive no
  parent-domain Cookies and use a one-time exchange.
- `landing.groupher.com` is public-only and is absent from OAuth bootstrap,
  Session read/write, and browser GraphQL state-change origin capabilities. Its
  public routes do not expose login, account, logout, or device-management UI.
  Credentialed Auth CORS does not grant this Origin access, Auth state-changing
  requests fail the exact-Origin check, and Phoenix BrowserCsrf rejects browser-
  Cookie GraphQL mutations from it. A host-agnostic Gateway route match is not an
  authorization or capability decision.
- When canonical Auth reports no Browser Session and the access/hint Cookies are
  absent, the browser is anonymous even if an unreachable server-side Session
  record still exists.
- Dashboard To TanStack V2 references this contract rather than defining its own
  token lifecycle.
