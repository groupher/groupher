## 1. 目标

本审计关注会随数据规模增长而恶化的实现，包括：

- 数据库或外部存储操作位于循环内；
- 可避免的重复全量遍历、嵌套遍历和排序；
- UI 热路径中的重复派生和深树处理；
- 批处理流程中的串行 I/O；
- 从 O(n²) 或 O(n × depth) 降到 O(n)、O(n log n) 或固定数据库往返的机会。

本审计不以代码形式复杂、循环层数多为理由直接判定问题。启发式扫描结果仅作为线索，最终优先级结合调用位置、输入规模、执行频率、数据库或网络往返以及改动风险确定。

## 3. 优先级定义

- P0：已证明会造成生产不可用、数据错误或无法接受的资源耗尽，需要立即处理；
- P1：位于生产热路径或无界增长路径，规模增大后会明显放大数据库、网络或用户等待时间；
- P2：存在明确复杂度问题，但执行频率、数据规模或用户影响较低；
- P3：低风险、低影响的局部改进，通常应在有测量数据后再处理。

## 4. P1 问题

### P1-1 Docs Tree 排序产生 O(n) 次数据库往返

位置：

- `backend/api/lib/groupher_server/cms/doc_tree/write/index.ex:31-70`
- `backend/api/lib/groupher_server/cms/doc_tree/write/index.ex:72-83`
- `backend/api/lib/groupher_server/cms/doc_tree/write/index.ex:117-139`
- 批量落位实现：`backend/api/lib/groupher_server/cms/doc_tree/write/index.ex:181-233`

处理结果：已完成。

- 保留唯一索引要求的临时 index 腾挪；
- 使用 `UPDATE ... FROM UNNEST` 一次写回最终 parent/index；
- 批量 SQL 同时限定 community、branch、draft stage 和 parent scope，并校验影响行数；
- 12 个 siblings 的回归测试直接断言移动过程固定为 3 次 `UPDATE`，不随 S 增长。

原实现：

- `move_node/5` 先整体偏移目标 scope 的 index；
- 随后对 `ordered_nodes` 中的每个 sibling 单独执行一次 `Repo.update_all`；
- 跨父节点移动还会再次 normalize 原 scope；
- `ensure_index/4` 在创建节点前无条件调用完整 normalize，然后再次读取 siblings。

设 sibling 数量为 S：

- 当前数据库往返：O(S)；
- 跨 scope 移动：O(S_target + S_source)；
- 数据库内部需要更新的行数本身仍为 O(S)，但当前额外付出了 O(S) 次客户端到数据库的往返成本。

原建议：

- 使用 `UPDATE ... FROM (VALUES ...)`、CTE、window function 或批量 CASE 一次写回最终 index；
- 如即时唯一索引要求必须先腾挪 index 空间，保留一次批量临时偏移，再执行一次批量最终写入；
- 不要在每次创建前无条件 normalize，可先验证 index 是否已经连续；
- 将 lane 排序规则纳入数据库查询或批量计算，避免数据库排序后再在 Elixir 中完整排序。

目标复杂度：

- 数据库往返由 O(S) 降为 O(1)；
- 数据库行更新仍为 O(S)。

风险：高。必须保持 Tab、Pin、Group、Page、Link 的 lane 顺序、唯一索引、跨父节点移动和事务并发语义。

验证要求：

- 运行 `mutation_test.exs`、`nested_group_test.exs`、`tabs_test.exs` 和 publish release 测试；
- 增加 10、100、1000 个 siblings 的 query-count benchmark；
- 增加并发 move/create 测试，验证不会出现唯一索引冲突或 index 空洞。

### P1-2 Docs 子树进入 Trash 时全量加载 Branch，并存在双重 N+1

位置：

- `backend/api/lib/groupher_server/cms/doc_tree/write/trash.ex:30-90`（入口编排）
- `backend/api/lib/groupher_server/cms/doc_tree/write/trash.ex:92-143`（`subtree_nodes/4`）
- `backend/api/lib/groupher_server/cms/doc_tree/write/trash.ex:152-206`（`persist_nodes/6`）
- `backend/api/lib/groupher_server/cms/doc_tree/write/trash.ex:208-214`（`attach_docs/4`）
- `backend/api/lib/groupher_server/cms/articles/trash.ex:142-198`（`attach_many/6`）
- `backend/api/lib/groupher_server/cms/articles/trash.ex:623-650`（批量代表 Article 读取）

处理结果：已完成。

- `subtree_nodes/4` 改为限定 tenant、branch、stage、root 的递归 CTE，只返回目标子树；
- Tree 快照先逐条走 changeset 校验，再通过一次 `Repo.insert_all(..., returning: true)` 持久化；
- Doc attach 一次批量读取既有 memberships 和代表 Article，去掉每个 Doc 的两次重复读取；
- mentions、可见性统计、membership 写入等必须保序且可回滚的领域副作用仍逐 Doc 执行，因此总领域工作仍为 O(D)，但不再重复执行 O(D) 次 membership/Article 查询。

原实现：

- `subtree_nodes/4` 没有从 root 开始在数据库中过滤子树，而是先加载同一 community、branch、stage 的全部节点，再在内存中 `group_by` 和递归提取目标子树；
- draft 和 public stage 都可能走这条全量加载路径，因此删除一个很小的子树也可能读取整个 Branch 的两套 Tree 节点；
- `persist_nodes/6` 对每个 Tree 节点调用一次 `ORM.create`；
- `attach_docs/4` 对每个 Doc 串行调用一次 `Trash.attach`；
- `Trash.attach` 内还会执行 membership 查询、Article 查询、membership 创建、mentions 状态更新和统计更新。

设目标子树节点数为 N，Branch 中 draft/public 节点总数为 B，Doc 数量为 D，每个 Doc attach 包含 q 个数据库操作：

- 即使 N 很小，读取和内存构树成本仍为 O(B)，内存占用也是 O(B)；
- 当前串行数据库操作约为 O(N + qD)；
- 删除较大的 Group 时，事务持锁时间和接口等待时间都会随子树规模线性放大。

原建议：

- 使用限定 community、branch、stage 和 root node 的递归 CTE，只读取目标子树；如暂不引入递归查询，至少避免 draft/public 两次无界 Branch 全量物化；
- 将 `TrashedDocTreeNode` 快照改为校验后一次 `Repo.insert_all`；
- 一次批量读取现有 memberships 和代表性 Article；
- mentions、stats、审计等领域副作用只有在无法安全批量化时才逐项执行；
- 搜索删除继续通过队列处理，但应确认 enqueue 是否需要批量 API。

目标复杂度：

- Tree 读取从 O(B) 行和 O(B) 内存降为 O(N)；
- Tree 快照写入由 O(N) 次往返降为 O(1)；
- Doc attach 从 qD 次独立查询降为少量批量查询加必要的 D 个领域副作用。

风险：高。优化不能破坏锁顺序、事务回滚、审计、mentions、stats、Trash membership 幂等性和搜索同步语义。

验证要求：

- 增加包含大量 Page、嵌套 Group 和 draft/public 双阶段节点的 Trash 集成测试；
- 增加“大 Branch 中删除小子树”场景，记录数据库返回行数和进程内存；
- 断言任一中间步骤失败时整次 Trash 回滚；
- 通过 Ecto telemetry 记录 SQL 数量，证明其不再随 Tree 节点数线性增长。

- 第一次 sweep 会扫描一次旧布局、幂等回填 index，并仅在全部成功后写 ready marker；此一次性兼容阶段仍为 O(A)；

- 删除时先删 Preview artifact prefix、最后删 catalog record，部分失败可由下一次 sweep 重试；
- record 下载和过期 Preview 删除均限制为最大 8 并发。

原实现：

- `listRecords()` 调用没有 prefix 的 `files.listAll()`；
- 因此会遍历 Preview 下所有 Markdown body、Dataset、Review 和 receipt 对象；
- 找到 `preview-record.json` 后逐个串行等待 `file.text()`；
- 删除阶段对所有过期 Preview 使用无上限 `Promise.all`。

设全部 Artifact 数量为 A，Preview record 数量为 R，过期记录数为 E：

- 当前枚举成本为 O(A)；
- record 下载为 O(R) 个串行网络等待；
- 删除瞬时并发为 O(E)。

原建议：

- 将 Preview root record 放入可独立枚举的公共 prefix/index；
- 或维护按过期日期分区的清理索引；
- record 读取和 Preview 删除都使用有界并发；
- 明确索引写入失败、Preview 创建失败和清理重试时的一致性策略。

目标复杂度：

- 使用独立 record prefix 后，枚举由 O(A) 降为 O(R)；
- 使用到期分区后可进一步接近 O(E)；
- 串行下载延迟降为 O(ceil(R / concurrency)) 个批次。

风险：高。涉及存储 key 兼容、历史 Preview 迁移和索引一致性。

### P2-3 Cover Card 每次全量读取，并逐条删除 descendant cards

位置：`backend/api/lib/groupher_server/cms/doc_cover/write.ex:378-475`

处理结果：已完成。

- 单条递归 CTE 同时计算目标 Group 的 ancestor/descendant node ids；
- 只 join 匹配的 Cover Card，不再加载 community 全部 Card 和 branch 全部 public 节点；
- descendant Card 通过一次 tenant-scoped `delete_all` 删除，并校验影响行数；
- 保留 ancestor 冲突提示和最早 replacement index 语义。

原实现：

- 每次操作都会加载该 community 的全部 Cover Card，并 preload `group_node`；
- 每次操作还会加载目标 Branch 的全部 public `DocTreeNode`，即使只处理一个局部 Group；
- 对每张现有 Cover Card 重新沿 parent map 向上计算 ancestors；
- 找到 descendants 后逐条调用 `Repo.delete!`。

设 Cover Card 数量为 C、目标 Branch 的 public 节点数为 P、Tree 深度为 H、需删除 Card 数量为 D：

- 数据库读取和内存物化为 O(C + P)，且与本次操作实际涉及的子树大小无关；
- CPU 为 O(C × H)；
- 数据库删除往返为 O(D)。

原建议：使用限定 community、branch 和目标 Group 的递归查询得到 ancestor/descendant ids，只查询相关 Cover Card；随后通过 `delete_all where id in ^ids` 批量删除。若仍在内存处理，也应只加载目标路径和子树，而不是全部 public 节点。

目标复杂度：读取和 CPU 降为 O(target subtree + matching cards)，数据库删除为 O(1) 次往返。

风险：中，必须保持 ancestor Cover 冲突检测和 replacement index。

以下模式被扫描器标记，但当前没有足够理由列为问题：

- `filterGroupsByDocTitle`：递归搜索经过 `useDeferredValue` 和 `useMemo`，整体仍为 O(N)；
- SideTree 的多数 `mapGroups` 操作：虽然会复制整棵树，但每个节点只处理一次，当前是 O(N)，需要真实大树交互数据才能判断是否值得改为 path-copy；
- Tag DnD：已经使用 tag-to-group Map、线性 placement comparison 和 animation-frame commit，没有明显 O(N²)；
- VitePress `sourcePathForRoute`：候选路径通过 Map 查询，单个 route 的查找是固定数量的 O(1) lookup；
- Preview Dataset 写入：已经以 16 个对象为一批做有界并发，当前更需要关注 sweep 的无界增长；
- Dev Hub Flow layout：服务数量受本地配置约束，现有 memo/cache 已覆盖主要重复计算。

## 9. 保留的边界与后续测量

- Tree reindex 的数据库往返已经是 O(1)，但唯一 index 下的最终行更新仍为 O(S)，这是连续位置模型的必要成本；
- Trash 的 memberships/代表 Article 读取已批量化，mentions、stats 和 membership 写入仍按 Doc 执行，以保持现有回滚和领域副作用语义；
- Preview 旧布局只在第一次兼容回填时执行一次 O(A) 扫描，ready marker 写入后稳定态为 O(R)；晚到的 legacy record 在按 ref 读取时仍会自愈到 catalog，但滚动发布中的未访问旧写入仍需靠排空旧 writer 或迁移期最终复扫兜底；
- DnD 已消除重复 canonicalize 和整树序列化，但仍会做一次 O(N) source/descendant 查找；只有真实大树 profile 证明仍是瓶颈时，才值得引入完整 path index；
- 本轮未做 wall-clock benchmark。建议后续在 100/1000 siblings、1000/5000 Fumadocs 文件及大 Preview Dataset 上记录 p50/p95，作为进一步优化依据。
