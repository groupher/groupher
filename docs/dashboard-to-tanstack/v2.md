# Dashboard 迁移到 TanStack Start V2

> 状态：第一次 `frontend/dash` 实现之后的架构共识。
>
> `frontend/dash` 和 `frontend/dashboard` 是长期并行的实现。V2 不定义切换
> 或删除条件。V2 的目标不是让 Next.js 模块通过兼容 alias 运行。目标是构建一
> 个可维护的 TanStack Start 应用，具备原生路由、显式的 SSR-to-Valtio 初始化、
> framework-neutral 的 Core 合约，以及跨云的 Main 缓存 revalidation API。
>
> 本文档取代 `v1.md` 中的目标架构部分。V1 文档保留作为初始 spike 的实现历史。
>
> 浏览器身份验证、Session 连续性、Phoenix token 过期、refresh、登出和
> `401`/`403` 行为由 [`docs/auth/v1.md`](../auth/v1.md) 定义。本文档只描述
> Dash 如何消费这份共享合约。

## 决策

- 保留两个公开路由族：

  ```text
  /:community/dashboard/*
  /:community/dash/*
  ```

- 将 `frontend/dashboard` 和 `frontend/dash` 保留为长期并行的实现。V2 不定义
  切换或删除条件。
- 把 Dash 路由重写为基于目录的原生 TanStack file route。
- 将 `routeTree.gen.ts` 视为生成产物，加入 `.gitignore`。
- 在 `$community` 父路由加载一次 community 数据。
- 在 route/provider 边界初始化 request-scoped Valtio store。
- 保留现有 Core store hook，例如 `useCommunity()` 和 `useDashboard()`。
- 对没有 mutation workflow 的只读路由数据（如 Trend）使用 props。
- 保留 urql 作为 GraphQL server-state 客户端；移除未使用的 TanStack Query。
- 用一个通过 `usePlatform()` 暴露的 Core platform 合约，替换框架形态的
  `next/*` 兼容 API。
- 命名 platform 实现为 `nextPlatform` 和 `tanStackPlatform`。
- 把 framework-neutral 合约和纯路由解析器放在 `frontend/core/platform`；把每
  个框架实现放在各应用的顶层 `src/platform` 目录。
- 通过 `platform.navi` 暴露导航。
- 通过 `platform.navi.to(...)` 进行跳转。
- 把 Clipboard 保留为 framework-independent 的 Core 浏览器能力。
- 将 [`docs/widgets-alias-rename.md`](../widgets-alias-rename.md) 视为已实现
  的前置：`~/ui`、`~/shell` 和 `~/render` 是 canonical 的共享 Core namespace，
  `~/widgets` 不能作为兼容 alias 回归。
- 配置 mutation 之后，重新加载当前 Community Valtio 状态，并调用 Main 的
  `/api/dsb/cache/revalidate` API。
- Community 和公开 Dashboard 信息允许匿名读取；Doc Editor 等受保护操作必须
  消费共享 Auth 合约。SSR 可以读取非敏感 theme cookie。
- 复用 `docs/auth/v1.md` 中共享的 Auth consumer 合约；Dash 不得实现独立的
  Phoenix token refresh 流程。
- 对 route pending 状态使用现有的 LavaLamp loading UI。
- 起步阶段使用一个保留稳定 Dash shell 的简单 route error UI。

## 目标路由树

`$community` 是 TanStack Router 对应 Next.js `[community]` 的语法。目录式
`route.tsx` 文件通过 `<Outlet />` 提供嵌套布局行为。

```text
frontend/dash/src/routes/
  __root.tsx
  $community/
    route.tsx
    index.tsx
    dash/
      route.tsx
      index.tsx
      overview.tsx
      info/
        route.tsx
        index.tsx
        logos.tsx
        social.tsx
      appearance/
        route.tsx
        index.tsx
        theme.tsx
        wallpaper.tsx
      cms/
        route.tsx
        post/
        changelog/
        kanban/
        doc/
      aliases/
      assets/
      integrations/
      trend.tsx
```

职责：

```text
__root.tsx
  document shell
  HeadContent
  Scripts
  platform 根
  全局 pending/error 默认

$community/route.tsx
  loadCommunity
  loadLocale
  community metadata/theme CSS
  CommunityProvider

$community/dash/route.tsx
  已鉴权的 Dsb shell
  DsbProvider
  sidebar
  breadcrumbs
  content Outlet

group route.tsx
  一组路由的共享 tab/layout

leaf route
  page 专属 loader
  当数据可变时使用 page-scoped Provider
  最终的 page 组件
```

生成的路由树不手动维护：

```gitignore
frontend/dash/src/routeTree.gen.ts
```

业务模块不应依赖生成的路由节点内部。

## 稳定的父级布局

`/home/dash/appearance/theme` 的路由匹配是：

```text
__root
└── $community
    └── dash
        └── appearance
            └── theme
```

从 `overview` 切到 `appearance/theme` 时，`$community` 和 `dash` 保持匹配。
它们的 Provider、sidebar 和 breadcrumbs 保持挂载，只有 leaf 内容变化。

这是修复 route-content 跳动的关键：

```text
错误做法
  route 切换
  -> 卸载 breadcrumb/content shell
  -> 渲染空的 pending 状态
  -> 挂载新页面

目标
  route 切换
  -> 保持 $community/dash shell 挂载
  -> 只在 content Outlet 中显示 pending UI
  -> 替换 leaf 内容
```

## Community 数据生命周期

Community 配置被 Overview、Info、Appearance、Aliases、CMS 和其他 Dsb 路由
共享。它属于 `$community` 父路由，不能被每条 leaf route 独立加载。

```text
request /home/dash/overview
  -> $community loader 调用 loadCommunity("home")
  -> CommunityProvider 接收 SSR snapshot
  -> 子代使用 useCommunity() 读取

navigate /home/dash/appearance
  -> $community 保持匹配
  -> CommunityProvider 保持挂载
  -> 不会重复 loadCommunity
```

期望的新鲜度策略：

```text
首次 SSR 请求                 加载一次
同 community 的子导航          复用
community 参数变化            加载新 community
成功的 config mutation        显式重新加载
```

V2 覆盖 V1 的 `$community` 新鲜度策略：

```text
V1  staleTime: 300_000
V2  staleTime: 300_000
    + 强制的 mutation 失效
    + focus/visibility 上的轻量版本检查
```

不要使用 `staleTime: Infinity`。有限的 fallback 处理另一名管理员或另一台
浏览器所做的修改，以及用户回到应用时的状态。

### Community 版本前置

版本感知的重新加载是目标能力，不是现有的 Community store 特性。在实现
`syncFromServer()` 之前，Community 配置 payload 必须暴露一个所有 Dsb 可见
的配置 mutation 共享的单调版本。

```ts
type TCommunity = {
  version: number
}
```

该版本必须对 Community profile、theme、wallpaper、navigation、aliases、
threads、SEO 以及 Main 或 Dsb 消费的其他配置的修改都前进。后端能保证它是所
有这些资源的聚合、严格有序的版本时，时间戳也可以接受。优先使用单调整数。

同一来源必须同时驱动：

```text
GraphQL Community payload
CommunityStore.version
reloadDsbCommunity result
loadCommunityVersion result
POST /api/dsb/cache/revalidate body.version
Main revalidation idempotency
```

`syncFromServer()` 也是计划中的 Community store API：

```ts
syncFromServer(next: TCommunity): TSyncResult
```

它的版本语义：

```text
next.version < current.version
  -> 忽略

next.version === current.version
  -> no-op

next.version > current.version
  -> 合并 canonical 字段
  -> 保留显式的本地 draft
```

在后端版本和 store API 出现之前，V2 不能声称版本感知的同步已经实现。

### 外部版本检查

由另一名管理员或另一台浏览器所做的修改使用轻量的版本 probe，而不是在每次
focus 事件上完整重新加载 Community。

```text
触发
  window focus
  visibility hidden -> visible

最小间隔
  60 秒

并发
  每个应用运行时一次 single-flight 请求

缓存
  直接的 no-store server-function fetch
  绕过 $community loader 的 300 秒 staleTime
```

Server function 只查询稳定的 identity 和聚合版本：

```graphql
community(slug: $community) {
  id
  version
}
```

结果处理：

```text
版本未变
  -> no-op

版本更新，没有本地 Community draft
  -> reloadDsbCommunity()

版本更新，存在本地 Community draft
  -> 记录 remote-version 冲突
  -> 不覆盖 draft
```

Probe 不加载 dashboard、theme、wallpaper、moderators 或 leaf 路由数据。

## SSR 到 Valtio 边界

SSR 数据应初始化 Valtio。Core 应继续读取现有 store hook，而不是在组件树中
到处 import TanStack route API。

```text
API / GraphQL
  -> Dash server function
  -> TanStack route loader
  -> scoped Valtio Provider initData
  -> useCommunity / useDashboard / useArticleList
```

路由组件是适配边界：

```tsx
function CommunityRoute() {
  const data = Route.useLoaderData()

  return (
    <CommunityProvider key={data.community.slug} initData={data.community}>
      <Outlet />
    </CommunityProvider>
  )
}
```

不要在 render 期间 commit loader 数据：

```tsx
// 不要保留这种模式。
function PostContentPage() {
  const pagedPosts = Route.useLoaderData()
  const dsb$ = useDashboard()

  if (!dsb$.pagedPosts.entries.length) {
    dsb$.commit({ pagedPosts })
  }
}
```

Render-time store patch 的问题：

- 引入 render 副作用。
- 现有 entry 可能阻止应用新的 community snapshot。
- Route revalidation 和 store 状态可能发散。
- Store 生命周期没有与 route identity 显式绑定。

改用 scoped Provider：

```tsx
function PostContentRoute() {
  const pagedPosts = Route.useLoaderData()

  return (
    <ArticleListProvider initData={{ pagedPosts }}>
      <Posts />
    </ArticleListProvider>
  )
}
```

Provider 生命周期必须跟随其所属资源：

```text
CommunityProvider  按 community keyed/scoped
DsbProvider        按 community Dsb layout scoped
ArticleListStore   按 community + thread scoped
DocEditorStore     按 community + document scoped
```

## 数据归属

Router、urql 和 Valtio 拥有不同的职责。

| 层              | 职责                                                   |
| --------------- | ------------------------------------------------------ |
| Backend/API     | Canonical 持久化数据                                   |
| Server function | 仅服务端的请求、auth、validation 和 orchestration      |
| Route loader    | SSR/preload 生命周期和路由级数据依赖                   |
| urql            | 浏览器 GraphQL 查询、mutation、重试和 GraphQL cache    |
| Valtio          | 当前客户端业务状态、draft、UI 状态和 optimistic update |
| Props           | 没有 mutation workflow 的只读 leaf 数据                |

示例：

| 数据                     | 目标                                       |
| ------------------------ | ------------------------------------------ |
| Community 配置           | `$community` loader -> `CommunityProvider` |
| Dsb shell 配置           | `dash/route.tsx` loader -> `DsbProvider`   |
| Posts/Kanban/Tags        | leaf loader -> scoped Valtio Provider      |
| Editor document 和 draft | leaf loader -> editor Valtio Provider      |
| Trend analytics          | leaf loader -> props                       |
| 客户端 GraphQL mutation  | urql -> commit Valtio -> canonical reload  |

`@tanstack/react-query` 不是因为应用使用 TanStack Router 就必须引入。把它
移除是为了避免在 urql 之外出现第二个浏览器 server-state cache。

V2 保留 GraphQL 业务 mutation 归 urql 所有。Server function 拥有 SSR 读取、
canonical Community 重新加载以及特权服务端到服务端 effect，如 Main 缓存
revalidation 调用。Server function 不是同一业务 mutation 的第二入口。

## Mutation 和 Reload 流程

一次成功的配置 mutation 有两个一致性目标：

```text
当前 Dsb UI
  Valtio 必须收到新鲜的 canonical Community 数据

公开 Main 应用
  Next cache 必须被 revalidate
```

目标流程：

```text
浏览器操作
  -> Dsb mutation
  -> API 持久化配置
  -> Dash 重新加载 canonical Community 数据
  -> Dash 把新数据 commit 到 Community Valtio
  -> Dash 服务端调用 Main revalidation API
  -> Main 失效其 cache tag
```

不要把这件事建模成 `router.refresh()`。

```text
reloadDsbCommunity()
  -> 调用 loadCommunity
  -> community$.syncFromServer(freshCommunity)
  -> await router.invalidate({
       filter: match.routeId === CommunityRoute.id
     })
```

canonical reload 之后必须进行有针对性的 `$community` 失效。当前安装的
TanStack Router API 使用 `filter`；它不使用 `include` 选项。App-local 的
TanStack 实现引用实际的 Community Route ID，而不是把 route ID 暴露给 Core。

不要在 `reloadDsbCommunity()` 中调用无 filter 的 `router.invalidate()`。
无 filter 的失效会重跑 Doc Editor、Article List、Kanban 等 leaf loader，
可能和活跃 draft 或 optimistic 状态冲突。

Provider 必须是 route-scoped 且 version-aware：

```text
新 community
  -> 由 initData 创建 store

同 community，同/旧版本
  -> 保留当前 store

同 community，较新服务端版本
  -> 通过 syncFromServer() 同步 canonical 字段
  -> 不重建 store
  -> 不覆盖未提交的 draft
```

Next.js Dashboard 实现也应重新加载 Community 数据并 commit 到 Valtio。它
不应把 `router.refresh()` 作为主要的状态更新机制。

## Main 缓存 Revalidation API

Dash 预期运行在 Cloudflare 上，而 Main 运行在 Vercel 上。因此缓存 revalidation
是已鉴权的 HTTPS API 调用，而不是共享进程、package、event emitter 或
Vercel 内部机制。

Main 拥有：

```http
POST /api/dsb/cache/revalidate
```

Dash 发送领域信息，而不是 Next.js 缓存实现细节：

```json
{
  "resource": "community",
  "community": "home",
  "communityId": "community-id",
  "version": "updated-version",
  "scopes": ["profile", "theme", "navigation"]
}
```

Main 把请求映射到它自己的 cache tag 和 cache-life 策略：

```text
resource=community
  -> community:<id>

scope=theme
  -> community:<id>:theme
  -> community:<id>:theme-preset

scope=navigation
  -> community:<id>:navigation
```

Dash 不得发送原始 Next tag 或在 `revalidateTag`、`revalidatePath`、
`updateTag` 或 cache-life profile 之间做选择。这些都是 Main 拥有的实现细节。

API 要求：

- 仅 server-to-server。
- Service token 或签名请求。
- Timestamp/replay 保护。
- 幂等请求。
- 短超时。
- 有限重试。
- 结构化日志和指标。

建议的请求元数据：

```http
Authorization: Bearer <service-token>
X-Groupher-Timestamp: <unix-seconds>
X-Groupher-Signature: <hmac>
```

Mutation 和缓存失效有各自的结果：

```text
API mutation 成功
Main revalidation 成功
  -> 完全成功

API mutation 成功
Main revalidation 失败
  -> mutation 仍然成功
  -> Dsb Valtio 仍然更新
  -> 服务端重试并记录一条运维错误
```

后端已经持久化 mutation 之后，不要把 mutation 本身报告为失败。

## Platform 合约

Core 必须依赖 Groupher 应用的语义，而不是直接依赖 `next/navigation` 或
`@tanstack/react-router`。

公开的 Core API：

```ts
const platform = usePlatform()

platform.navi.location
platform.navi.to(target)
platform.navi.to(target, { replace: true })
platform.navi.back()
platform.navi.isActive(target)
```

对 Dashboard 域名使用 `dsb`/`Dsb`：

```ts
TDsbRouteTarget
dsbRoutes
useDsbTabs
```

对 platform 层使用 framework-neutral 的命名：

```ts
usePlatform
TPlatform
PlatformProvider
nextPlatform
tanStackPlatform
```

不要使用：

```ts
useDashboardNavigation

```

### Core 合约

```ts
type TNaviOptions = {
  replace?: boolean
}

type TPlatformNavi = {
  location: {
    pathname: string
    search: string
    searchParams: URLSearchParams
  }
  to: (target: TRouteTarget, options?: TNaviOptions & { preserveSearch?: boolean }) => void
  push: (href: string, options?: { scroll?: boolean }) => void
  replace: (href: string, options?: { scroll?: boolean }) => void
  back: () => void
  forward: () => void
  refresh: () => void
  prefetch: (href: string) => Promise<void>
  isActive: (target: TRouteTarget) => boolean
}

type TPlatform = {
  navi: TPlatformNavi
  components: {
    Link: ComponentType<TPlatformLinkProps>
    Image: ComponentType<TPlatformImageProps>
  }
}
```

`TRouteTarget` 应表达应用路由，而不是 pathname 段：

```ts
type TDsbRouteTarget = InferRouteTarget<typeof DSB_ROUTES>
```

`DSB_ROUTES` 是唯一的路由声明来源。它定义路由名、参数、path 和 search
schema。两个应用共用同一个纯解析器，但 root 段不同：

```text
DSB_ROUTES
  -> TDsbRouteTarget
  -> resolveDsbRoute(target, { rootSegment: 'dashboard' })
  -> resolveDsbRoute(target, { rootSegment: 'dash' })
```

两个应用对同一个 target 的解析可能不同：

```text
nextPlatform
  dsb.overview(home)
  -> /home/dashboard/overview

tanStackPlatform
  dsb.overview(home)
  -> /home/dash/overview
```

不应有 hook 通过字符串替换把 `/dashboard` 改写成 `/dash`。

Route builder 拥有类型化的 query 数据：

```ts
navi.to(
  dsbRoutes.postContent({
    community,
    search: {
      page: 2,
      tab: 'published',
      order: 'latest',
    },
  }),
)
```

Search 合成遵循一条规则：

```text
target.search
  > 保留兼容的 search
  > target 默认值
```

当启用 `preserveSearch` 时：

1. 读取当前 search params。
2. 只保留 target schema 允许的或被显式声明为全局/pass-through 的 key。
3. 使用 `target.search` 显式提供的值覆盖。
4. 删除 target 值为 `undefined` 或 `null` 的 key。
5. 使用 target search schema 校验最终结果。

仅启用 `preserveSearch` 并不把未知 key 带入另一条路由。

示例：

```text
当前
  ?page=3&tab=published&debug=1

target search
  { tab: "draft" }

target schema
  page, tab

结果
  ?page=3&tab=draft
```

`DSB_ROUTES` 可以声明路由专属的保留：

```ts
postContent: {
  path: 'post/content',
  searchSchema: postContentSearchSchema,
  preserveSearchKeys: ['page'],
}
```

Platform 实现必须订阅框架 location/match 状态。Pathname、search param、
浏览器历史或 route match 的变更必须让 `usePlatform()` 的 consumer 重新
渲染，使 SideTree、tab、分页和 Kanban stage 保持最新。

### 归属

Core 拥有 framework-neutral 合约和纯路由语义。每个应用拥有把该合约绑定到
自身 router 的实现：

```text
frontend/core/platform/
  context.tsx
  route.ts
  index.ts

frontend/dashboard/src/platform/
  nextPlatform.tsx

frontend/main/src/platform/
  nextPlatform.tsx
  NextPlatformBoundary.tsx

frontend/landing/app/platform/
  NextPlatformProvider.tsx

frontend/dash/src/platform/
```

不要把 `nextPlatform` 放到 Next.js App Router 路由树下，比如
`src/app/[community]/dashboard/platform`。它是应用级 adapter，而不是
Dashboard 路由或路由本地模块。

不要把 `nextPlatform` 或 `tanStackPlatform` 放到 Core 里。这样做会让 Core
同时依赖 Next.js 和 TanStack Router，并破坏下面描述的静态 framework 隔离。

### Provider 选择

App 根通过普通的静态 import 选择实现。

Next.js Dashboard：

```tsx
import NextPlatformProvider from '../../../platform/nextPlatform'

export default function DashboardClient({ children }) {
  return <NextPlatformProvider>{children}</NextPlatformProvider>
}
```

TanStack Dash：

```tsx
import { TanStackPlatformProvider } from '../platform/tanStackPlatform'

function RootComponent() {
  return (
    <TanStackPlatformProvider>
      <Outlet />
    </TanStackPlatformProvider>
  )
}
```

Core 组件保持完全相同：

```tsx
function DsbOverviewLink({ community }: TProps) {
  const { navi } = usePlatform()
  const target = dsbRoutes.overview(community)

  return <button onClick={() => navi.to(target)}>Overview</button>
}
```

实现由应用的静态 ESM import 图选择：

```text
frontend/dashboard build
  -> import NextPlatformProvider
  -> bundle nextPlatform
  -> 不 import tanStackPlatform

frontend/dash build
  -> import TanStackPlatformProvider
  -> bundle tanStackPlatform
  -> 不 import nextPlatform
```

没有运行时的 `isNext`/`isTanStack` 判断。

如果 Main 之后迁移到 TanStack，它的根切换 platform 实现，但 Core 中
`usePlatform()` 的 consumer 不用改。

## TimeAgo Hydration Seed

`ScriptOnce` 还可以初始化服务端/客户端时间基线。

```text
服务端请求
  -> 创建 renderedAt
  -> SSR TimeAgo 使用 renderedAt
  -> ScriptOnce 把 renderedAt 写入浏览器运行时

浏览器 hydration
  -> 首次客户端渲染使用同一 renderedAt
  -> hydration 完成
  -> 运行时切换到 Date.now()
  -> 定时更新相对时间戳
```

`ScriptOnce` 只初始化基线。它不拥有长生命周期的 TimeAgo 定时器。

## Dynamic 组件和 Script

不要把 `next/dynamic` 和 `next/script` 保留为“默默忽略其语义”的 API。

按意图替换 `next/dynamic`：

| 意图              | 目标                                   |
| ----------------- | -------------------------------------- |
| 路由代码分割      | 原生 file route 分割 / lazy route 文件 |
| 组件代码分割      | `React.lazy` + `Suspense`              |
| 路由仅客户端渲染  | TanStack selective SSR                 |
| 浏览器专属 widget | 显式 client/hydration 边界             |

按生命周期替换 `next/script`：

| 意图                    | 目标                        |
| ----------------------- | --------------------------- |
| 关键 head script        | route `head().scripts`      |
| SSR 专属 hydration seed | `ScriptOnce`                |
| runtime body script     | route script / `Scripts`    |
| post-hydration script   | App 拥有的 effect/component |
| idle script             | App 拥有的 idle loader      |

删除那些声称支持 `ssr` 或 `strategy` 却忽略这些属性的 adapter。

## Auth 生命周期

Dash 不拥有浏览器凭证的签发、续期、轮换或登出。这些职责属于 Auth 和
Phoenix，由 [`docs/auth/v1.md`](../auth/v1.md) 定义。

Dash 消费该共享合约：

```text
浏览器 urql / client 请求
  -> 发送 canonical 的 groupher-auth.token
  -> 可 refresh 的 401
       浏览器通过共享 Auth consumer 直连 canonical Auth，执行一次 refresh
       重试原操作一次

authenticated SSR loader / server function
  -> 发送 request 中已有的 groupher-auth.token
  -> 可 refresh 的 401
       返回中性的 auth-recovery/loading boundary
       hydration 后由浏览器直连 canonical Auth，执行至多一次 refresh
       invalidate 并重试受保护路由一次

无效/被撤销的 session
  -> 清除受保护的本地状态
  -> 携带已校验的 returnTo 返回 Auth

403
  -> 不 refresh
  -> 处理当前 Phoenix 权限结果
```

身份验证失败的分类基于机器可读码。共享的 `resolveAuthFailure()` consumer
区分 `TOKEN_EXPIRED`、`TOKEN_INVALID`、`TOKEN_REVOKED` 和 `SESSION_REVOKED`；
Dash 从不解析人类可读的错误消息。

Dash 的 V1 Auth 集成必须：

- 读取并转发 canonical 的 Phoenix Cookie。
- 在进入 Dash 路由前要求鉴权。
- 为 loader 和 server function 提供 request auth context。
- 在浏览器中使用共享的 single-flight refresh consumer。
- 在 SSR 期间只转发 request 中已有的 Phoenix token；遇到 refreshable 401 时返回
  中性恢复边界，hydration 后由浏览器直连 canonical Auth，并至多重试受保护路由一次。
- 让共享的 Auth consumer 通过 `BroadcastChannel` 协调同源的 `auth:logout`、
  `auth:refreshed` 和 `auth:invalid` 事件。
- 通过共享 consumer 的 callback，在终局身份验证失败后清除 viewer 和受保护
  的 Valtio 状态。

Dash 的 Auth 集成不得：

- 解码或签发 Auth.js Session。
- 签发、签名或在本地扩展 Phoenix token。
- 定义应用专属的 refresh 端点。
- 从 SSR loader/server function 调用 Auth refresh、代理 Auth Browser Session，或传播
  refresh 返回的 `Set-Cookie`。
- 把 `403` 视为 token 过期的信号。
- 把凭证值存进 Valtio 或浏览器存储。

canonical Auth refresh 端点和共享 consumer 已存在。浏览器请求使用该 consumer 的
single-flight refresh；Dash 不得加入本地 refresh 端点或恢复 SSR backchannel refresh。
当前 SSR 错误边界已经避免服务端 refresh，但仍需完成 hydration 后自动执行一次浏览器
refresh、invalidate 并重试受保护路由，才能满足 V1 的完整验收标准。

`BroadcastChannel` 只在同一浏览器源内的 tab 之间协调。它不能跨
`groupher.com` 和 `dashboard.groupher.com`，也不能到达另一台设备。跨源和
跨设备的状态通过 `GET /api/auth/session`、受保护路由进入、focus/visibility
检查或机器可读的身份验证响应来收敛。
