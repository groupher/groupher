# Dashboard 迁移到 TanStack Start

> 状态：第一次 `dash` spike 已完成，并对照当前 Dashboard 路由做了验证。一次评审
> 发现该 spike 的运行时 lazy-loading bridge 会导致首次请求出现空白闪烁。已达成
> 一致的方向是：原生 TanStack file-route 重写——删除 `import.meta.glob` +
> `React.lazy` bridge，把每个 dashboard 页面改成静态路由文件，并用
> `loadCommunity` server function 分层叠加 SSR 数据。现有的 Next.js `dashboard`
> 应用长期保留；`dash` 和 `dashboard` 共存。生产发布仍是独立决策。
>
> 范围：`frontend/dash` 是一个用于社区 dashboard 实验的 TanStack Start 子应用。
> 现有的 `frontend/dashboard` 和 `frontend/main` 应用在重写期间保持不变。

## 实施结果

本地证明现在位于 `frontend/dash`，并保持 `frontend/dashboard` 不变。它的
canonical 路由刻意采用公开路由形态：

```text
https://groupher.localhost/home/dash/overview
```

Dash SSR 使用现有 GraphQL schema 加载已鉴权 viewer 和 community，使用该数据
创建 request-scoped 共享 Valtio store，然后渲染现有的 Dashboard shell、
ThemePreset CSS 和 wallpaper。响应使用 `Cache-Control: private, no-store`。

现有 Dashboard 路由集合现在都在 `/:community/dash/*` 下解析：

```text
/:community/dash/overview
/:community/dash/info
/:community/dash/appearance/*
/:community/dash/post/*
/:community/dash/kanban/*
/:community/dash/changelog/*
/:community/dash/doc/*
/:community/dash/trend
```

大多数路由通过 Dash 的兼容边界复用现有 Dashboard 页面模块。Trend 和 Docs
Editor 因为它们对应的 Next page server code 额外承担了请求数据，所以使用
Dash-native server loader。它们的前后对比记录在 `frontend/dash/docs/rewrites.md`。

Local Dev Hub 把 Dash 视作一个一等公民服务，使用 3005 端口。启动 Dash 需要
和 Dashboard 同样的基础链路：Gateway、Auth 和 Phoenix；Assets Hub、Content
Import 和 Document Converter 是可选支持服务。Dev Hub 卡片使用
`oklch(38.1% 0.176 304.987)`、它的 TanStack Start 图标，并打开上面的
canonical gateway URL。

## 原生路由取代运行时懒加载

第一次 spike 通过 `import.meta.glob` 加 `React.lazy` 复用了现有 Next.js
Dashboard 页面模块。这是一个过渡性的兼容 bridge，不是目标形态。它会带来首
次请求的空白闪烁，将被删除。

### 空白闪烁的根因

第一次刷新某条路由时显示空白内容；第二次刷新直接渲染。根因是
`DashboardRouteLayout.tsx` 这个 bridge 在 `Suspense fallback={null}` 中包装了
`React.lazy` 模块。在 TanStack Start 的 streaming SSR 下，React 先 flush 空的
fallback，然后把已解析的 module 注入。第一次请求时 Vite dev server 还没转译
该模块，所以 `import()` 是一个真正的 async 操作；第二次请求时 module cache
已经热了，`lazy()` 同步解析并直接进入初始 HTML。Next.js 没有这个行为，因为
它的页面图在 build 时就解析好，而不是通过运行时 `import()` 解析。

等价的根因是：bridge 让 React 在 `Suspense` 内等待一次代码获取（`import()`），
而 Next 的 `Suspense` 只等待数据获取。dev server 中的代码加载在首次命中时是
未缓存的。

### 目标形态

删除 glob/lazy bridge：`DashboardRouteLayout.tsx`、`DashboardRoutePage.tsx`
以及 `/$community/dash/$` 通配符路由。把每个 dashboard 页面表达为
`frontend/dash/src/routes/$community.dash.*` 下的原生 TanStack file route，
使用静态 import。Vite 的 code-splitting 仍然按路由文件生效，但不再使用
`React.lazy`。

转换规则：

```text
thin client page（`return <X/>`）  -> 内联进 leaf 路由文件
带 tab 的 `layout.tsx`（Portal + Tabs）-> 父级路由文件渲染 `<Outlet/>`
redirect `page.tsx`              -> 带 loader `redirect()` 的 index route
```

`next/*` adapter 仍然保留：它们服务于 `frontend/core` 中的 120+ Next import，
独立于 Dashboard 应用是否还存在。

## 服务端数据分层

### 布局层

`/$community` 拥有共享 community 数据。一个名为 `loadCommunity` 的 server
function（不是 `loadDashboardShell`：dashboard payload 是从 community 派生的）
返回：

```text
loadCommunity(community, lang?, mode?)
  -> P.community
  -> parseDashboard / parseWallpaper
  -> serializeCommunityThemePresetCss(dashboard.themeTokens)
  -> { community, dashboard, wallpaper, themeCssText, demoMode }
```

外加一个 `loadLocale(lang)` server function 用来加载 locale 数据。路由的
`head()` 从 loader 数据派生 metadata/title。

### Viewer 保持客户端

Viewer（`P.me`）在 SSR 期间不加载。它通过 GraphQL provider 保留在客户端，与
当前 Next.js Dashboard 行为一致。`SSR Account Store Initialization` 重写记录
因此作废，`MainProvider` 不再接收 `account` 初始化 slice。`isModerator` 权限
检查移到客户端；当前 Dashboard UI 都不依赖 SSR 权限分支。

### 页面层

自带数据的页面拥有专属的 server function：

```text
trend             loadTrendOverview      （已有）
doc/editor        loadDocEditorData      （已有）
appearance/theme  loadThemePresets       （新增；全局数据，不在 community 内）
post/content      loadPagedPosts         （新增）
changelog/content loadPagedChangelogs    （新增）
kanban/content    loadKanban             （新增）
tags              loadTagGroups          （新增）
assets            loadAssets             （新增）
communities       loadCommunities        （新增）
post/trash        loadTrash              （新增）
admins            loadAdmins             （新增）
```

配置类页面（info/appearance/header/footer/seo/rss/domain/alias/...）继承布局
payload，没有自己的 loader。

### 纯函数从 Core 复用

TanStack 特有的接线是 app-local 的，但每个纯函数都复用：`parseDashboard`/
`parseWallpaper`（core `~/lib/ssr`）、`serializeCommunityThemePresetCss`、
`loadLocaleFile`、`isDsbDemoMode`，以及 Dashboard route-domain GraphQL schema
（`~/unit/DashboardThread/schema/` 下的对应域模块）。只有 `getThemePresets` 的 fetch+parse 部分
从被 `next/cache` 包装的 core 助手中抽到一个无 cache 的 server function。

## 背景

Groupher 有两种不同的前端产品形态：

```text
main
  匿名优先的公开页面
  公开 SSR 内容必须能在没有 viewer 时工作
  viewer 专属状态通常是客户端增强

dash
  需要鉴权的社区 dashboard 页面
  没有有意义的匿名页面
  SSR 必须在 render 前加载 viewer + community 专属 dashboard 数据
```

当前的 Next.js 模型仍适合 `main`：公开 community 页面、docs、posts、articles、
SEO metadata 以及对 CDN 友好的公开内容。对这些路由而言，server-rendered
匿名 baseline + 客户端个性化是一个有效的产品模型。

社区 dashboard 页面不一样。它们实质上是 all-or-nothing：没有 viewer、权限
scope 和 community dashboard payload，页面就不应渲染。这让 Next.js App Router
的几个特性对这一面变得不那么有价值：

- React Server Component 边界会为高度交互的 dashboard UI 持续带来 `use client`
  摩擦。
- 当页面没有有意义的公开 shell 时，partial rendering 和 streaming 变得不太
  有用。
- Cache Components 与强 viewer-scoped 数据并不天然契合。
- 当每条路由都必须按 viewer 和 community 权限解析时，instant navigation 和
  prefetch 语义可能带来 cache/freshness 噪声。

建议的方向是新增一个 `dash` 应用（灵感来自 Cloudflare 的 dashboard 命名），
用它来评估 TanStack Start，而不打扰现有的 `dashboard` 应用。

## 目标形态

```text
frontend/dash
  TanStack Start 应用
  需要鉴权的运行时
  community dashboard 路由
  SSR 加载个性化 dashboard payload
  TanStack Router loader 拥有路由数据
  TanStack Query 拥有水合的客户端 server-state
  frontend/core 只在已经能工作、且不强制进行 core-wide framework-neutral
  重构的位置被复用
```

`dash` 在起步阶段不是 `frontend/dashboard` 的替代品。它是一个并行的子应用，
用来证明运行时、数据流、部署以及选定的 `frontend/core` 复用边界是否实用。

## 初始路由候选

使用一个具体存在的页面作为第一个对比目标，而不是仅按路由特征筛选。

推荐候选：

```text
/:community/dash
/:community/dash/overview
```

为什么选这个路由：

- 它让新的 TanStack Start 表面远离现有的 `/:community/dashboard` 路径。
- `/:community/dash` 是新入口，可以 redirect 到 `/:community/dash/overview`。
- `overview` 是第一个具体页面，所以 spike 拥有了一个有名字的页面和一个清晰
  的对比目标，而不是只有路由 shell。
- 它是顶层 community dashboard 体验，因此直接验证需要鉴权和 viewer 专属的
  SSR 模型。
- 它需要 community 专属 dashboard payload，但一开始并不承担最重的 editor
  workflow。
- 它具有足够的权限相关 UI，能暴露 cache key 和 SSR 数据形态上的错误。
- 它让 spike 拥有清晰、相对当前 Next.js 实现的并列基线。

第一条路由应避开 docs editor、import flow 以及其他多步 CMS 路由。这些应作
为后续候选，在基础运行时、auth 和 core UI 复用被证明之后。

## 运行时模型

社区 dashboard 路由的目标请求流程：

```text
request /:community/dash/overview
  -> 读取 cookie/header
  -> 校验 viewer session
  -> viewer 缺失：在第一个 spike 中不处理
  -> 解析 community
  -> 检查 viewer 权限/membership
  -> 拉取 community dashboard payload
  -> 完整 SSR 页面
  -> 用同一份私有 payload 水合客户端
```

这和 `main` 有意不同：

```text
main 路由
  -> SSR 渲染公开匿名内容
  -> 水合
  -> 需要时客户端加载 viewer 专属状态

dash 路由
  -> render 前鉴权
  -> 渲染个性化 SSR 输出
  -> 用私有 route/query 数据水合
```

## 缓存模型

TanStack Router loader cache 应主要被视为客户端 route match cache 加 SSR
水合状态。它不等同于 Next.js Cache Components，也不应被视为跨用户的 server
cache。

对于 dashboard 数据，cache key 必须包含 viewer scope：

```ts
queryOptions({
  queryKey: ['community-dashboard', communityId, viewerId],
  queryFn: () => getCommunityDashboard({ communityId, viewerId }),
  staleTime: 30_000,
  gcTime: 5 * 60_000,
})
```

规则：

- 永远不要只用 community 作为私有 dashboard 数据的 key。
- 在 query key 中包含 `viewerId` 或等价的 permission/session scope。
- 把 SSR 输出视为私有。
- 起步阶段优先使用 `Cache-Control: private, no-store`。
- 仅在证明没有跨用户泄漏风险之后，再考虑短期的 `private, max-age=...` 头。
- 不要为个性化 dashboard HTML 或数据使用公共 CDN 缓存。

`dash` 真正有用的缓存层：

```text
route loader cache
  客户端导航期间浏览器持有的路由数据新鲜度。

TanStack Query cache
  水合的 server-state 复用、mutation 失效和后台 refetch。

request-local server cache
  在一次 SSR 请求内对重复的 viewer/community/permission 读取做去重（可选）。

HTTP 私有 cache 头
  对用户专属响应采取保守的浏览器/代理行为。
```

## Server Functions

TanStack Start server function 可以替代部分 app-internal API route 使用，
但不应被视为对公共 HTTP 端点的无差别替代。

将 server function 用于有类型的 dashboard 操作：

```ts
export const updateDashboardLayout = createServerFn({ method: 'POST' })
  .validator(UpdateDashboardLayoutSchema)
  .handler(async ({ data }) => {
    const viewer = await requireViewer()

    return saveDashboardLayout({
      viewerId: viewer.id,
      communityId: data.communityId,
      layout: data.layout,
    })
  })
```

将 route/server handler 用于：

- 第三方回调
- webhook
- 公共端点
- 必须有稳定外部 URL 的端点

## `frontend/core` 边界

主要技术风险不在新 router，而在于第一个 `dash` 页面能否复用选定的
`frontend/core` 片段，同时不继承 Next.js 运行时假设。

适合直接共享的部分：

- UI primitives
- 主题 token 和 CSS 变量
- 纯 UI 组件
- 领域类型
- GraphQL 文档和类型化 helper
- 纯 formatter 和工具
- 不 import Next API 的客户端 store

需要审计或加 adapter 边界：

- `next/link`
- `next/image`
- `next/navigation`
- `next/dynamic`
- `next/server`
- App Router hooks
- React Server Component 假设
- Next metadata API
- Next route handler
- 基于 `useServerInsertedHTML` 的主题插入

初步扫描：

```text
frontend/core 文件 import next 相关 API：约 113 个

主要分组
  next/link
  next/image
  next/navigation
  next/dynamic
  next/script
  next/server
  next/cache
  useServerInsertedHTML
```

这个数字是粗略的，实施前应重新刷新一次。它足以说明 `dash` 不能假设
`frontend/core` 已经是 framework-neutral 的。

不要在本次 spike 中清理 `frontend/core` 现有的 import。它们服务于当前的
Next.js 应用，应保持不动，除非另行明确批准重写。

`dash` 的规则是：

```text
core 模块能直接工作就复用
依赖只涉及 Link/Image/navigation 时，加一个 dash-local 的薄 adapter
core 模块是 Next 专属或耦合过深时，在 frontend/dash 内部重写小而必需的部分
```

应用级 adapter 的可能形态：

```text
frontend/dash/src/adapters/link.tsx
frontend/dash/src/adapters/image.tsx
frontend/dash/src/adapters/navigation.ts
```

这样能保持 spike 的诚实：`dash` 必须自证其运行时模型，而不让现有的 Next.js
表面承担迁移成本。

## Valtio Store

主流的 `frontend/core/stores/*` 状态模型应由 `dash` 复用。Fork 主 store 模型
会带来长期维护成本，不应是默认的迁移策略。

可复用模式：

```tsx
const storeRef = useRef<TStore | null>(null)
storeRef.current ??= setupStore(initData)
```

只要 `initData` 来自 route loader 或 query 水合，并且为每个渲染的 app tree 创
建新的 store 实例，这个 provider 模式就与 TanStack Start 兼容。Valtio 本身
并不绑定 Next.js。

规则：

- 复用现有主流 store 的 `setupStore(initData)` 函数。
- 保持 store 状态形态和 action 与 `frontend/core` 对齐。
- 不要为同一领域另建一套 `dash` 状态模型。
- 不要在 SSR 期间把 viewer/community 专属的 Valtio 状态放到 module-level
  singleton store。
- 仅对 Next 绑定的边缘做适配或重写，例如 provider 接线、route hook、demo-mode
  helper 或 head 插入。

边界示例：

```text
复用
  frontend/core/stores/theme
  frontend/core/stores/community
  frontend/core/stores/locale
  frontend/core/stores/dashboard setupStore/状态形态/action

必要时 dash 专属
  接收 TanStack loader 数据的 provider wrapper
  route/search-param hook
  demo-mode 集成
  first-paint head 插入
```

dashboard store 是重要的情况。`dash` 应尝试复用 store 形态和 action，但如
果当前的 Next-bound provider 或 hook import 了 `next/navigation`，就没必要
复用它们。

## 重写记录

因 Next.js 和 TanStack Start 运行时冲突而产生的每一次重写都必须被记录。目
标不仅是让 `dash` 工作，也是为日后抽取 core 逻辑保留足够背景。

这条规则适用于任何因为原模块依赖 Next.js API，而不得不复制、重写或绕过
`frontend/core` 模块的 `dash` 实现。

必需的记录：

```text
module
  原始的 frontend/core 文件或 hook

background
  原代码承载的产品行为

conflict
  阻止直接复用的具体 Next.js API 或运行时假设

before
  当前 Next.js 实现的工作方式

after
  dash 实现的工作方式

comparison
  保留的行为
  故意丢弃的行为
  变更的行为

extraction path
  哪些逻辑未来可以移入 framework-neutral 的 core 模块
  哪些必须保留为 app 专属

validation
  用于证明保留行为对等的测试、截图或人工检查
```

示例：

```text
module
  frontend/core/shell/ThemeFirstPaintScript

background
  在 hydration 协调 html[data-theme] 之前，插入 first-paint CSS 变量快照

conflict
  使用 Next.js 的 useServerInsertedHTML，在 TanStack Start 中不可用

before
  Next 根 layout 渲染 ThemeFirstPaintScript，Next 把 script 注入 server HTML
  流

after
  dash 根/head 集成通过 TanStack Start 的 document/head 机制输出相同的
  THEME_FIRST_PAINT_VARS_SCRIPT

extraction path
  把 script 生成保留在 frontend/core/lib/ssr/script；把 framework 专属的插
  入保留在 app-local 根组件
```

可能的位置：

```text
docs/dashboard-to-tanstack/v1.md
  用于 spike 级记录和架构决策

frontend/dash/docs/rewrites.md
  用于 frontend/dash 存在之后的实现级记录
```

## 主题 First Paint

`dash` 必须独立验证主题 first paint。以往的 SSR 主题工作表明，这不仅是
一个客户端 store 问题：server-rendered DOM、早 head script、CSS 变量快照
以及 hydration 时机都很关键。

验证要求：

- SSR 输出正确的初始主题相关 markup 和 CSS。
- 早主题检测仍然在 first paint 前运行。
- Community ThemePreset CSS 可以在不依赖 Next 专属 API 的情况下注入。
- Hydration 不会短暂回退 `html[data-theme]`。
- 对 light、dark 和 system mode 测试相同的行为。

建议的验证链：

```text
Playwright 截图对比
  采集 light、dark 和 system 的 first visible frame 和 hydrated frame

Playwright DOM 断言
  验证 hydration 前后的 html[data-theme]、color-scheme 和关键 CSS 变量

Chrome DevTools Performance trace
  若截图检查出现闪烁，检查 first paint 和 hydration 时机

可选 Lighthouse 运行
  仅作为回归的次要信号，不作为主题正确性的主验收门槛
```

如果 `dash` 不能复用现有的 Next 专属插入机制，应建立 TanStack Start 应用级
等价物，而不是把 hack 分散到单个 ui 组件中。

## 本地 Gateway 命名空间

使用和当前本地 Dashboard 路由相同的 namespace 模式，但为 `dash` 分配独立的
upstream。

当前 Dashboard 模型：

```text
browser path
  /home/dashboard/appearance

gateway
  第二段 path 是 dashboard
  路由到 DASHBOARD_SITE
  裁掉 dashboard namespace 段

dashboard 应用收到
  /home/appearance
```

目标 Dash 模型：

```text
browser path
  /home/dash/overview

gateway
  第二段 path 是 dash
  路由到 DASH_SITE
  保留 dash namespace 段

dash 应用收到
  /home/dash/overview
```

这样既能让 `dash` 独立于现有的 `/:community/dashboard/*` 路径，又能保留
相同的 community-first 路由形态。Dash 的 TanStack Start 路由就是 canonical
公开路径：

```text
gateway 和 Dash 路由
  /:community/dash/*
```

最初的 namespace 裁剪设计曾导致 SSR/browser pathname 不匹配以及 hydration
fallback。让 path 完整地穿过 gateway，能让 server render、TanStack Router
hydration、Vite 资源和 HMR 共享一个稳定的 origin。未来的 `dash.groupher.com`
部署可以添加自己的 host 路由，而不必改变这套本地合约。

建议的本地端点：

```text
http://127.0.0.1:3005/health
https://groupher.localhost/home/dash/overview
https://dash.groupher.localhost/home/dash/overview
```

Gateway 的新增项：

```text
DASH_SITE=http://127.0.0.1:3005

GatewayTargetKind += dash
isDashRoute(pathname, host)
getDashUrl(pathname, host, search)
```

路由测试：

```text
/home/dash -> dash upstream /home/dash
/home/dash/overview -> dash upstream /home/dash/overview
/home/dashboard -> dashboard upstream /home
/organizations/settings/dash -> main fallback
dash.groupher.localhost/home/dash/overview -> dash upstream /home/dash/overview
```

TanStack Start dev 资源和 HMR 可能不沿用和 Next.js 相同的 path。第一版应同
时支持 `/:community/dash/*` 和 `dash.groupher.localhost/*`，再在观察运行中
的 Start dev server 后决定是否加入静态或 websocket 特殊处理。

路由和发布选项：

```text
基于 path 的试用
  Gateway 把 /:community/dash/* 映射到 TanStack Start 应用。最便于内部测试
  和回滚。

基于 host 的试用
  dash.groupher.com 直接指向 TanStack Start 部署。Cookie、资源和路由隔离更
  清晰，但需要 DNS 和部署环境配置。

未来替换
  Gateway 之后可以把选定的 /:community/dash 请求路由到 dash，而
  /:community/dashboard 路径仍保留在当前 dashboard 应用。
```

第一次生产证明应包含：

- `/health`
- SSR viewer/community 数据初始化
- SSR GraphQL 访问
- 私有 cache 头
- 静态资源加载
- source map/build 输出合理性
- gateway/proxy 路由隔离
- CI 中包含 type-check/build 的 job
- 部署环境变量（GraphQL/auth 端点）
- 用于浏览器验证的 preview 部署或临时 host

在为 spike 准备好清晰的回滚路径之前，不要把真实 community dashboard 流量
路由到 `dash`。

## 迁移阶段

### Phase 0: 空 App - 完成

使用 TanStack Start、React、TypeScript 和仓库的 package manager 约定创建
`frontend/dash`。只加入一个 health route 和一个最小 index route。

验收：

- 本地 dev server 启动
- 生产 build 通过
- `/health` 返回简单的 readiness 响应

估算：0.5-1 天。

### Phase 1: SSR Auth Probe - 完成

加入请求上下文，使其可以读取 cookie/header 并校验当前 viewer。

验收：

- 已登录请求能在 SSR 期间识别 viewer
- 首次 render 不需要仅在客户端的 auth 拉取
- 匿名访问行为被记录为本次 spike 范围外

估算：1-2 天，取决于当前 auth 逻辑与 Next 运行时 helper 的耦合程度。

### Phase 2: GraphQL Probe - 完成

从 SSR 接入现有后端 GraphQL 服务。

验收：

- route loader 能在服务端调用 GraphQL
- auth cookie 转发与现有 auth 合约一致
- GraphQL 错误通过应用级 error boundary 渲染

估算：现有 GraphQL helper 服务端安全时 1 天；需要独立服务端 helper 时
2-3 天。

### Phase 3: 最小 Community Dashboard 路由 - 完成

加入如下路由：

```text
/$community/dash
/$community/dash/overview
```

loader 应解析 viewer、community、权限和最小 overview payload。

验收：

- SSR HTML 包含个性化 dashboard 内容
- 不同 viewer 不共享 cache
- viewer/权限缺失行为记录为本次范围外，除非完成本地 SSR 数据初始化所必需

估算：2-4 天。

### Phase 4: Core UI 复用 - 对当前 Dashboard 路由已完成

仅在与 `dash` 兼容的位置使用 `frontend/core` 组件渲染一个真实的 overview
表面。

验收：

- 没有意外的 `next/*` import 泄漏到 `dash`
- 不兼容的 `frontend/core` 组件在 `frontend/dash` 中被本地复制或重写，而
  不是修改原 core 模块
- 因 Next.js 冲突产生的每次本地重写都有 background 和 before/after 对比的
  重写记录
- 主题 token 和全局样式渲染正确
- Hydration 没有明显 mismatch

估算：3-6 天。这一阶段最不可预测，因为初步扫描已经显示许多 `frontend/core`
文件 import 了 Next API。

### Phase 5: Query 水合与 Mutation - 延后

为 dashboard payload 和一个 mutation 引入 TanStack Query。

验收：

- SSR 数据水合到客户端 query cache
- mutation 失效正确的 viewer/community query key
- 客户端导航的新鲜度行为是显式且可预测的

估算：1-2 天。

### Phase 6: 真实内部试用 - 本地完成

把 `dash` 暴露在内部路由、临时 host 或仅 staff 入口之后。

验收：

- 本地和生产 health check 通过
- 真实浏览器验证覆盖 first paint、SSR viewer/community 数据加载和资源加载
- 回滚只是路由/代理的变更，而不是代码 revert

估算：1-3 天，取决于首次部署目标是简单的临时 host 还是现有的 Gateway 路径。

### 内容组件 SSR 模式

当前内容页在客户端获取数据（`useMount` + urql）。为了在不让 Next.js
Dashboard 失效的前提下让 SSR 包含真实数据，所选模式是：page 级 server
function 加载第一页数据，路由在 render 期间（或通过 `initialData` props）将
其注入 store，core 组件在 store 已有值时跳过首次 fetch。

```text
由 dashboard-store 驱动（posts、changelogs、tags）
  route loader -> loadPagedPosts/... -> render 阶段 dsb$.commit({ pagedPosts })
  组件：useMount(() => { if (!pagedPosts.entries?.length) loadPosts() })

由 article-list store 驱动（kanban）
  route loader -> loadKanban -> <Kanban initialData> -> ArticleListStoreProvider initData
  组件：在 backlog 已存在时跳过 useEffect

local-state 组件（trash、assets）
  route loader -> loadTrash/loadAssets -> <X initialData>
  组件：useState(initialData ?? EMPTY) / assets 从 initialData 派生

由 props 驱动（theme）
  route loader -> loadThemePresets -> <Theme initialPresetOptions>
```

Next.js Dashboard 保持其客户端 fetch 行为：没有 SSR 注入时，store 是空的，
原始 `useMount` fetch 保持不变。

长期保留：`frontend/dashboard`（Next.js）、`next/*` adapter，以及共享的
`frontend/core` Next import。只有 `frontend/dash` 的路由归属和 server 数据
分层发生变化。

### 客户端导航抖动修复

TanStack 内容路由的 route loader 调用 server function。在客户端导航时，
TanStack 每次都重跑 loader（默认 `staleTime: 0`），并等待其完成后才渲染，
当超过 `pendingMs`（1000ms）时显示默认的 null `pendingComponent`——所以切换
路由时会先闪烁空白内容区，然后才出现数据。Next.js 不会有这个问题，因为它的
内容页在客户端 fetch（`useMount`），使用 loading skeleton，永远不会因为
loader 而阻塞导航。

应用修复：

```text
内容 route loader（post/changelog/kanban/tags/trash/assets/theme/trend/doc-editor）
  staleTime: 60_000  -> 导航复用缓存的 loader 结果

父级路由 $community
  staleTime: 300_000 -> shell loader 在长会话中复用

server/graphql.ts fetchGraphQL
  AbortSignal.timeout(10_000) -> GraphQL 后端宕掉时 SSR 不会再挂起
```

Next.js Dashboard 不受影响（它从不跑这些 loader）。

当前本地验证：

```text
yarn workspace @groupher/frontend-dash build
yarn workspace @groupher/gateway test
yarn workspace @groupher/local-dev-hub test
yarn workspace @groupher/local-dev-hub type-check

browser
  Dev Hub 通过 Gateway 打开 /home/dash/overview
  Overview SSR 包含个性化 Dashboard 数据、wallpaper 和主题 CSS
  Info -> Appearance 客户端导航保留 Dash namespace
  Dashboard 源路由矩阵在 /:community/dash/* 下解析
```

Phase 5 是刻意延后的。当前路由水合了 route-loader 和共享 Valtio 状态；引
入 TanStack Query 需要选定一个 mutation，并定义其 viewer/权限 query key 和
失效语义。它不是建立 SSR 与 Dashboard 对等的必要条件。

剩余的生产决策估算：

```text
小型证明：1-2 周
有意义的内部试用：2-3 周
完整替换决策：仅在内部试用之后
```

## 风险

| 风险                                                    | 影响                                  | 缓解                                              |
| ------------------------------------------------------- | ------------------------------------- | ------------------------------------------------- |
| 运行时 `import.meta.glob` + `React.lazy` bridge         | 首次请求空白闪烁，仅 dev             | 使用静态 import 的原生 file route                 |
| `frontend/core` import Next API                         | `dash` 无法干净地消费共享 UI         | 审计 import 并加入应用级 adapter                  |
| `dash` fork 主流 Valtio store                            | 跨应用状态行为漂移                   | 复用 store setup/state/action；仅适配边缘         |
| auth 绑定到 Next 运行时                                  | SSR auth probe 失败                  | 把 auth 合约隔离在 cookie/header 周围             |
| GraphQL client 假设浏览器优先使用                       | server loader 重复数据逻辑           | 创建 server-safe 的 GraphQL helper                |
| 主题 first paint 依赖 Next 插入 API                      | dark/system 模式闪烁再次出现         | 实现 Start 级 head/style 插入                     |
| 个性化数据仅按 community 缓存                            | 跨用户数据泄漏                       | 在每个 key 中包含 viewer/权限 scope              |
| 生产运行时与 Next/Vercel 假设不同                        | 部署被卡住                           | 在业务路由之前先验证 build 和 health route        |
| 双应用行为漂移                                            | 产品不一致                           | 在路由模型被证明前保持 `dash` 范围狭窄            |

## 非目标

- 不要替换 `frontend/main`。
- 不要删除现有的 `frontend/dashboard`；它被长期保留并与 `dash` 共存。
- 不要重新设计完整 dashboard IA。
- 不要为个性化 dashboard 数据引入公共缓存。
- 不要在第一次证明前把全部 `frontend/core` 组件都变成 framework-neutral。
- 不要在本次 spike 中清理或重写现有 `frontend/core` 的 Next.js import。
- 不要在初始 `dash` 模型中引入 React Server Components。

## 决策门

只有当 spike 证明以下全部条件时，才扩张 `dash`：

```text
auth-required SSR 可工作
community dashboard payload 能在服务端渲染
私有 hydration cache 行为正确
overview 页面可以使用 core 复用、dash-local adapter 或 dash-local 重写来
构建
主题 first paint 稳定
生产部署简单
回滚简单
```

如果这些条件不满足，保持 `main` 和 `dashboard` 继续走当前的 Next.js 路径，
并把 spike 视为研究产出，而不是迁移承诺。
