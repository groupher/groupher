# Sentinel V1：跨领域内容风险检测

> 状态：设计确认，待实施。
>
> Sentinel 是独立 Phoenix Context 和独立 Hono 执行服务。它检测内容风险并输出信号，不直接处罚
> 用户、不直接改变业务资源状态，也不替代 Report、Moderation、Lifecycle 或 Activity。

相关文档：

- [Activity V1](../activity/v1.md)：append-only 业务事件和安全产品视图；
- [Community Report Design](../community/report_design.md)：现有 Report/ReviewCase 方向；
- [Community Lifecycle](../community/lifecycle.md)：资源状态转换边界。

## 1. 背景

当前内容审核链路由 `CMS.Events.Audition` 和 `Helper.AuditBot` 承担：

```text
Article / Comment publish
  -> CMS.Events :audition
  -> AuditBot
  -> 百度内容安全接口
  -> 直接设置 is_legal / illegal / audit_failed
```

这个实现存在根本边界问题：

1. 内容检测被放在 CMS 内，无法自然服务 Account bio、昵称、头像和 Community 资料；
2. `AuditBot` 直接绑定单一 Provider；
3. Provider 响应结构进入 CMS 业务状态；
4. `Audition` 同时抽取内容、调用外部服务、解释结果并修改资源；
5. `is_legal` 把多维风险压成一个布尔值；
6. `audit_failed` 把基础设施失败混成内容状态；
7. AI 检测结果被当成最终处罚，而不是治理信号；
8. 缺少内容版本、规则版本、模型版本和幂等标识；
9. 旧检测结果可能覆盖已经修改的新内容。

V1 不重命名或包装 `AuditBot/Audition`，而是建立新的独立边界并在切换后删除旧链路。

## 2. 命名与定位

统一名称为 Sentinel（哨兵）：

```text
Phoenix Context
  GroupherServer.Sentinel

Hono service
  backend/sentinel

Schema namespace
  Sentinel.Model.*
```

Sentinel 的定位是：

> 对跨领域内容执行自动风险检测，保存可追踪的检测过程，并向业务领域提供结构化风险信号。

Sentinel 不是：

- 内容警察或自动执法者；
- CMS 子模块；
- Resource Lifecycle；
- 人工审核队列；
- 用户举报系统；
- Activity 历史；
- 通用 AI 产品 facade。

## 3. 适用资源

Sentinel 是跨领域 Context，V1 至少允许以下资源接入：

```text
Account
  bio
  nickname / display name
  avatar

CMS
  Article title/body/images
  Comment body/images
  Community title/description/logo
  Press description/config text
```

顶层公共入口保持资源无关：

```elixir
Sentinel.check(resource, opts)
Sentinel.retry(check, opts)
Sentinel.get_check(ref)
```

具体内容抽取和结果应用由资源 adapter 拥有：

```text
Sentinel.Article
Sentinel.Comment
Sentinel.Profile
Sentinel.Community
```

每个 adapter 定义：

1. 提取哪些文本、图片和链接；
2. 如何计算稳定的 `content_hash`；
3. 使用哪些 Sentinel rules；
4. 检测结果完成后通知哪个领域入口；
5. 哪些字段可以保存或写入 Activity；
6. 资源被修改或删除时如何判定旧 Check 已过期。

Sentinel 顶层不通过 case/反射直接修改 Account/CMS schema。

## 4. 两个不同的生命周期

### 4.1 Sentinel Check 生命周期

Sentinel 拥有检测任务的执行状态：

```text
queued
  -> running
  -> completed
  -> failed

queued / running
  -> superseded

failed
  -> queued      explicit retry
```

含义：

- `queued`：已创建，等待 Hono 执行；
- `running`：某个 attempt 正在检测；
- `completed`：已得到结构化风险信号；
- `failed`：基础设施或 Provider 调用失败；
- `superseded`：资源内容已经变化，本次结果不得再应用。

`failed` 不是内容有风险，不能映射成 `illegal`。

### 4.2 资源 Lifecycle

Article、Comment、Profile、Community 等资源的当前状态继续由所属领域拥有。Sentinel 完成后只提供
signals；Moderation/Policy 形成决定，再调用所属领域的正式 command 或 Lifecycle：

```text
Sentinel Check completed
  -> signals
  -> Moderation / domain policy
  -> allow / hold / hide / block / restore decision
  -> resource command / Lifecycle
  -> Activity
```

Sentinel 不直接更新资源的 `pending`、`is_legal`、visibility 或 lifecycle state。

## 5. 数据模型

V1 使用 `Sentinel.Model.Check` 保存一次逻辑检测：

```text
Check
  id
  ref
  resource_type
  resource_ref
  content_hash
  status
  rule_set
  rule_version
  signals
  requested_by_type
  requested_by_ref
  completed_at
  superseded_at
  inserted_at
  updated_at
```

外部调用 attempt 单独保存：

```text
CheckAttempt
  id
  ref
  check_id
  provider
  model
  status
  failure_code
  started_at
  completed_at
  inserted_at
```

分离 Check 与 Attempt 的原因：

- 一个逻辑 Check 可以因为 timeout 或 Provider failure 重试；
- retry 不创建第二个业务检测结论；
- 可以追踪 Provider/model，但不让基础设施状态污染资源；
- callback 可以使用 `check_ref + attempt_ref` 幂等处理。

V1 默认不长期保存完整原文、完整图片或 Provider 原始响应。Check 保存资源 ref、内容 hash、归一化
signals 和必要的调用元数据；短期 payload retention 必须另行定义期限和访问权限。

## 6. 检测分层

Sentinel 不把所有内容无条件发送给通用大模型。

```text
Layer 0 · deterministic rules
  URL / contact / repeated content / frequency / PII pattern

Layer 1 · dedicated moderation model
  harassment / hate / sexual / violence / self-harm / illicit

Layer 2 · general model with structured output
  Groupher rules / Community rules / Chinese context / ambiguous cases
```

### 6.1 Layer 0：确定性规则

优先使用普通代码解决确定性问题：

- 手机号、邮箱、身份证等格式；
- 外链和联系方式；
- 重复内容；
- 高频提交；
- 明确黑名单；
- 文件类型、大小和图片元数据限制。

这些规则不需要 AI，结果稳定、便宜且易解释。

### 6.2 Layer 1：OpenAI Moderation

V1 默认使用 `omni-moderation-latest` 检测通用有害文本和图片，主要分类包括：

```text
harassment / harassment-threatening
hate / hate-threatening
sexual / sexual-minors
violence / violence-graphic
self-harm / self-harm-intent / self-harm-instructions
illicit / illicit-violent
```

它适合作为基础安全分类，不负责判断：

- 广告、SEO spam 和灌水；
- 站外导流和交易；
- 社区自定义禁区；
- 标题党和低质量内容；
- 冒充官方、复杂诈骗；
- 依赖上下文的中文谐音、反讽和引战；
- Groupher 产品规则。

Moderation endpoint 返回固定分类、score 和 flagged，不需要通用 Structured Output SDK。

### 6.3 Layer 2：TanStack AI

只有以下情况进入通用模型：

- Layer 0/1 命中边界区间；
- 需要判断 Groupher 自定义规则；
- Community 配置了额外规则；
- 需要结合上下文；
- 需要为人工处理生成窄、结构化解释。

Hono 使用 TanStack AI 的 provider adapter 和 structured output，将不同模型结果限制为 Sentinel 自己的
schema。模型不得自由生成最终业务 action。

## 7. 统一 Signal 合同

所有 Layer 归一化为 Sentinel 自己的 signal：

```text
Signal
  kind
  score
  source
  rule
  evidence
  input_types
```

示例：

```json
{
  "kind": "harassment",
  "score": 0.82,
  "source": "openai-moderation",
  "rule": "harassment",
  "evidence": [],
  "inputTypes": ["text"]
}
```

规则：

1. `kind` 使用 Groupher canonical value，不直接暴露 Provider 私有枚举；
2. `score` 是风险信号，不是处罚概率；
3. `source` 标明 deterministic/openai/general-model 等来源；
4. `evidence` 默认不保存完整敏感正文；
5. Signal 不能包含 `delete_user`、`hide_article` 等领域 action；
6. Provider/model/rule version 必须可追踪。

## 8. Hono 服务边界

新增独立子项目：

```text
backend/sentinel
```

Hono 负责：

- 执行 Layer 0/1/2；
- Provider adapter、timeout、有限重试和 fallback；
- TanStack AI structured output；
- 将结果归一化为 Signal；
- 使用签名 callback 返回 Phoenix。

Hono 不负责：

- 直接访问 Groupher 主数据库；
- 创建或更新 Account/CMS 业务资源；
- 决定 hold/hide/block；
- 创建 Activity；
- 维护 Report 或 Moderation Case；
- 成为 Check 的业务权威。

Phoenix 是 Check、业务决定和资源状态的唯一权威。

### 8.1 请求协议

Phoenix 创建 Check 后调用：

```text
POST /v1/checks
```

```json
{
  "checkRef": "uuid",
  "attemptRef": "uuid",
  "resourceType": "article",
  "resourceRef": "post:uuid",
  "contentHash": "sha256",
  "content": [{ "type": "text", "value": "..." }],
  "media": [],
  "ruleSet": "default",
  "ruleVersion": "v1",
  "callbackUrl": "https://api.groupher.com/internal/sentinel/callback"
}
```

要求：

- 请求必须签名；
- `checkRef` 标识逻辑 Check；
- `attemptRef` 标识一次外部执行；
- 同一个 `attemptRef` 必须幂等；
- payload 有明确大小上限；
- callback URL 不能由普通用户输入。

### 8.2 Callback 协议

Hono 完成后回调 Phoenix：

```json
{
  "checkRef": "uuid",
  "attemptRef": "uuid",
  "contentHash": "sha256",
  "status": "completed",
  "signals": [],
  "providers": [],
  "completedAt": "UTC timestamp"
}
```

Phoenix 必须：

1. 验证 callback 签名；
2. 锁定 Check；
3. 校验 attempt 是当前有效 attempt；
4. 校验 callback `content_hash`；
5. 重新读取资源的当前 `content_hash`；
6. 内容已改变时把 Check 标记为 `superseded`；
7. 只在当前内容仍匹配时保存 signals 并通知后续 policy；
8. callback 重复到达时幂等返回成功。

Hono 还应提供按 `attemptRef` 查询结果的内部接口，供 callback 丢失时由 Phoenix 主动补偿。

## 9. 与 Report、Moderation、Lifecycle、Activity 的关系

四者形成下面的治理链：

```text
Signal sources
  ├─ Sentinel Check
  ├─ user Report Fact
  ├─ deterministic system rule
  └─ moderator observation
          ↓
Moderation Case
          ↓
Moderation Decision
          ↓
resource command / Lifecycle
          ↓
Activity
```

### 9.1 Report

Report 只记录“哪个用户针对哪个资源提交了什么举报”。它是用户事实，不是风险检测结果，也不是处罚。

Sentinel Check 与 Report Fact 平级，都是 Moderation 的输入：

```text
Report Fact != Sentinel Check
Report count != Sentinel score
```

二者不能互相创建伪事实：AI 命中不能伪装成某个用户举报，用户举报也不能伪装成 AI 判断。

### 9.2 Moderation

Moderation 汇总一个资源的 Sentinel signals、Report Facts 和人工信息，决定是否创建/推进 Case。
Sentinel 不拥有 Case 的 open/claimed/resolved 状态。

正式 Decision 示例：

```text
allow
hold
hide
block
restore
```

自动规则可以形成 system decision，但必须经过与人工决定相同的显式 command，不允许 Sentinel callback
直接更新资源字段。

### 9.3 Lifecycle

资源所属领域执行最终 Decision：

```text
CMS.Articles.Lifecycle
CMS.Comments.Lifecycle
CMS.Communities.Lifecycle
Accounts profile command
```

Lifecycle 只消费正式 Decision，不读取 Provider 原始响应，也不根据最后一条 Sentinel Check 自行推断状态。

### 9.4 Activity

Activity 记录具有产品意义的正式事实，例如：

```text
moderation_review_started
moderation_review_resolved
content_held
content_restored
```

默认不进入 Activity：

- 每一次 Provider attempt；
- timeout/retry；
- 原始 prompt/response；
- 完整敏感正文；
- 内部 score 和 reviewer note。

Sentinel Check 的技术指标进入 telemetry/operations，不把 Activity 当作任务日志。

## 10. V1 策略

V1 使用简单的分流策略：

```text
所有受支持内容
  -> Layer 0
  -> OpenAI Moderation

明确低风险
  -> completed with signals/no signals

明确高风险
  -> 交给 policy / Moderation

边界风险或需要产品规则
  -> TanStack AI Layer 2
  -> 交给 policy / Moderation
```

阈值属于 Sentinel rule set，并带 `rule_version`。不得把 Provider 的 `flagged` 直接等价为删除或封禁。

V1 不实现：

- 自动账号封禁；
- 通用 agent/tool loop；
- 面向用户的 AI 对话；
- 无限制保存原始内容；
- Community 自定义 prompt 编辑器；
- 多模型投票系统；
- 历史内容全量回扫；
- 旧 `is_legal/audit_failed` 数据兼容。

## 11. 切换路径

1. 建立 `GroupherServer.Sentinel` Context、Check/Attempt schema 和状态合同；
2. 新建 `backend/sentinel` Hono 子项目；
3. 接入 OpenAI Moderation Layer 1；
4. 接入 TanStack AI structured output Layer 2；
5. 先接 Article/Comment，再接 Account Profile 和 Community；
6. 建立签名 request/callback、幂等和 content hash guard；
7. 将检测结果接入新的 Moderation command；
8. 用 Sentinel 替换 `:audition` producer；
9. 删除 `CMS.Events.Audition`、`Helper.AuditBot`、旧 scheduler retry 和相关测试；
10. 删除旧 `is_legal/audit_failed/illegal_reason/illegal_words` 运行时合同，不保留双写。

数据库字段删除和 GraphQL 合同变化必须在实施版本中列出具体影响，但不保留旧检测链作为兼容层。

## 12. 验收标准

- Sentinel 是独立 Context，不属于 CMS 或 Account；
- Article、Comment、Profile、Community 可通过 adapter 接入；
- Phoenix 拥有 Check 和业务状态，Hono 只执行检测；
- Check status 与资源 Lifecycle 明确分离；
- content hash 防止旧检测结果覆盖新内容；
- Layer 0/1/2 输出统一 Signal；
- Provider 结果不能直接执行资源处罚；
- Sentinel、Report、Moderation、Lifecycle、Activity 没有双重权威；
- `AuditBot/Audition` 切换后删除，不长期兼容或双写；
- V1 不执行历史内容全量回扫。
