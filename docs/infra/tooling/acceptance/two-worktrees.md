# 双 worktree 主链路验收

> 状态：验收手册。本次结果由实际执行记录填写。

A 是正在使用的本地主环境，B 是已获授权、本轮可回收的 secondary。使用同一台机器上的两套真实运行时。开始时在 checkout 外或 A 的验收目录保存一份脱敏记录，逐步填入观察值、通过或受阻原因；证据须在移除 B 后仍可读取。既有单侧记录见[多 worktree 方案](../../../architecture/dev-hub-multi-worktree.md)。

| 步骤                           | 操作与命令入口                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | 通过条件                                                                                                                                                                                                                                            |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. 记录 A                      | 从 A 记录 checkout 真实路径、HEAD、Hub 实例、活动服务、产品 URL、实际 dev/test 库名及迁移版本。在原浏览器刷新，记下用户和一个可重读的社区 ref。为登录登出测试另外准备一个浏览器 profile、两侧可识别的测试账号（A 使用与原会话不同的账号）和一个新的 B 场景 slug。[状态来源与诊断](../../../architecture/dev-hub-multi-worktree.md#状态来源与日常诊断)                                                                                                                                                                     | A 的页面、用户和社区能重读，两个本地库可区分。记录 B 场景 slug 在 A 的查询结果为不存在。后续对照同一批记录，保留 A 原浏览器会话。                                                                                                                   |
| 2. 准备 B 依赖                 | 登记 B，记录两个 checkout 的 HEAD 和实际测试的未提交差异。比较锁文件、工具链、架构、编译配置及 Mix 环境。复用 pnpm store，为 B 建立自己的 workspace 链接；从无并发写入的兼容缓存克隆或复制 Elixir 依赖与编译产物，在 B 增量编译。[复用规则](../../../architecture/dev-hub-multi-worktree.md#worktree-依赖与构建复用) · [具体准备步骤](../../../../.agents/skills/grstack/references/pr-integration.md#reuse-caches-without-mixing-checkouts)                                                                              | 用两侧可区分的前端 workspace 源码和后端行为，在相应构建或测试中观察 A、B 各自的结果。前端覆盖 B 新增文件的解析，后端确认 B 的可写构建目录独立。并行构建时 A 仍加载 A 的代码。记录复用来源、准备耗时及回退原因；缓存不兼容时在 B 重建。              |
| 3. 建库并启动 B                | 从 B 使用登记、建库和迁移入口分别准备 dev/test 库，确认归属后启动本次所需的受管 Phoenix、Auth 和产品服务。需要 home 数据时使用 B 的 Assets 和本地 home 入口。[Hub 与数据库操作](../../../architecture/dev-hub-multi-worktree.md) · [服务启动](../../../auth/local-test-actors.md#prepare-the-runtime) · [home 准备](../../../../backend/api/dev/seed/README.md#常驻-home)                                                                                                                                                 | 实际连接的两个库都带 B 的登记身份及对应用途，迁移到 B 的预期版本，均与 A 的库不同。浏览器通过 B 的同级 HTTPS 域名到达 B 的产品服务，A 的原 URL 同时可用。仅有 control-only 状态、端口监听或健康响应时，本步仍待验证。                               |
| 4. 同一 profile 登录 A、B      | 在步骤 1 的测试 profile 开两个标签页，分别经两侧 Auth 登录不同测试账号；B 缺账号时先按账号示例创建，将该 run 计入本轮回收清单。记录两侧产品页的实际用户和域名。该验收复用同一浏览器 Cookie 存储；每个 actor 单开 profile 的快捷入口用于下一步角色验收。[账号准备](../../../../backend/api/dev/seed/README.md#账号与社区) · [域名与会话方案](../../../architecture/dev-hub-multi-worktree.md)                                                                                                                              | 两个页面轮流刷新后均保持各自原用户。能从每个页面读回当前身份；仅观察 Cookie 存在不足以通过。                                                                                                                                                        |
| 5. 在 B 建社区、授权并实际写入 | 用 B 的新 run 创建 owner、editor、limited 和社区，通过真实邀请与接受建立权限。保留上一步两个标签页；在 B 的角色专用 profile 打开同一社区，让 editor 保存一个与原值不同的主题设置，再让 limited 尝试更改同一项。[主题权限场景](../../../../backend/api/dev/seed/README.md#主题权限场景) · [角色浏览器操作](../../../auth/local-test-actors.md#bounded-ui-actions)                                                                                                                                                          | 核对社区 ref、owner 的 lord 关系和两名成员的有效权限。editor 保存后刷新仍见新值；limited 使用自身会话发起同一产品操作时服务端拒绝，重新读取仍为 editor 保存的值。如果只能看到按钮隐藏，记录 UI 限制，写入拒绝仍待验证。A 中仍查不到 B 的场景 slug。 |
| 6. 双向登出                    | 回到步骤 4 的同一个 profile。先从 A 登出，刷新两侧；再让 A 重新登录原测试用户，确认 B 仍在线，从 B 登出并再次刷新两侧。[GrStack 会话验收](../../../../.agents/skills/grstack/SKILL.md#reproduce-at-the-reported-entry-point)                                                                                                                                                                                                                                                                                              | 第一轮 A 已登出且 B 仍是原 B 用户；第二轮 B 已登出且 A 仍是原 A 用户。记录四个刷新结果。                                                                                                                                                            |
| 7. 回收 B，复验 A              | B 服务仍在线时预览并执行本轮 fixture 清理，核对会话撤销与保留项。保存报告后停止 B，按登记分别回收 test/dev 库，在 B checkout 仍存在时注销 secondary，最后按授权移除临时 checkout。复查 B 的路由、进程和本轮其他资源，再从 A 原浏览器和数据库重读基线。[Fixture 清理](../../../../backend/api/dev/seed/README.md#归档与清理) · [资源回收顺序](../../../../.agents/skills/grstack/references/test-cleanup.md#finish-in-dependency-order) · [环境注销](../../../architecture/dev-hub-multi-worktree.md#运行时归属与生命周期) | 清理报告列明普通授权已回收、归档社区及初始 lord 等按约保留项；遇到 blocked 或 partial 先保留证据。B 实例、登记、两个临时库和 checkout 已回收。A 原服务、URL、原会话、社区 ref 及两库迁移基线仍可核对；共享依赖缓存仍可用。                          |

**记录验收边界。** 涉及默认测试库、回滚或缓存策略的变更，将专项检查安排在步骤 6 之后、回收 B 之前，或另用专用演练环境。分别按[数据库双环境验收](../../../architecture/dev-hub-multi-worktree.md)和[缓存验收](../../../architecture/dev-hub-multi-worktree.md#worktree-依赖与构建复用)记录结果：并发普通 Mix 测试需观察实际连接的测试库，B 回滚重迁后需复查 A 的两个库；缓存的冷、热准备时间和实际磁盘增量单独测量。需要独立演练目标的项目在该目标上执行。生产隔离沿用同一方案的“生产隔离验收”条件，以配置或构建检查取证，勿向生产执行本地 seed 或清理。
