# Change validation guide

Use this guide to select checks for a change. Commands are starting points, not a guarantee of coverage: trace the affected behavior and consumers, then include the relevant tests and contracts. Run commands from the repository root unless a different directory is specified. Current scripts and workflow configuration remain authoritative.

## Matrix

| Change                                  | Start with                                                                                                                                                                                                                                              | Expand when needed                                                                                                                                                                                                                                                                                  |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Frontend application or shared Core     | Run the owning workspace's `lint` and `type-check`, and focused Vitest tests for changed behavior. For example, `pnpm --filter @groupher/frontend-core run type-check` and `pnpm exec vitest --config frontend/core/vitest.config.mts run <test-file>`. | Trace shared Core consumers and check affected hosts. Validate meaningful UI, routing, responsive, and interaction changes in a browser; use `/home/xx` for data-dependent community flows and put screenshots under `.playwright/`. Route generation may change generated files: review that diff. |
| Phoenix API and CMS                     | From `backend/api`, run focused `mix test <test-file>`, `mix compile --warnings-as-errors`, `mix lint.style`, and `mix lint.context`; check formatting of changed Elixir files.                                                                         | Include affected callers, authorization, persistence, concurrency, and GraphQL tests as appropriate. The backend CI also checks pipeline inventories and fresh-database migrations and runs the broader test suite.                                                                                 |
| GraphQL schema or client contract       | Run `pnpm run contract:graphql` and `pnpm run contract:graphql:generated`; run relevant server and client tests and type-check affected consumers.                                                                                                      | If generated output needs updating, use `pnpm run graphql:codegen`, then review its diff. Check the schema, operation, and consumer together.                                                                                                                                                       |
| Documentation or architecture rules     | Run `pnpm run docs:check` when its documentation or architecture checks apply; review links and changed text.                                                                                                                                           | For a changed scanner, run its focused tests and distinguish report-only inventory from a strict check. `docs:check` aggregates several architecture checks, not just documentation.                                                                                                                |
| Dev Hub local runtime and configuration | Run `pnpm --filter @groupher/local-dev-hub run test` and `pnpm --filter @groupher/local-dev-hub run type-check`; keep real Hub and Portless smoke checks manual.                                                                                        | Cover migration safety, managed environment precedence, service startup contracts, and canonical HTTPS routing.                                                                                                                                                                                     |
| Other workspace or service              | Inspect that workspace's `package.json`, README, and relevant workflow; run its applicable lint, type-check, and focused tests.                                                                                                                         | Include shared contracts and dependent services when their behavior changes. Python and Elixir services have their own toolchains.                                                                                                                                                                  |

For Gate or Lifecycle changes, consult `.agents/skills/gate-lifecycle/SKILL.md` for the additional flow and test boundaries. For frontend work, consult `.agents/skills/fe/SKILL.md`.

## Hooks and CI

`pnpm run report:salon-props` is a report-only frontend inventory for direct `useSalon(...)` bindings passed intact as JSX props. Findings are candidates for review and do not fail the command; parse or scan errors do. It does not follow aliases or object spreads and is not a comprehensive data-flow check. It is not currently connected to hooks or CI.

`lefthook.yml` defines the current local hooks. Pre-commit formats staged JSON/Markdown and frontend files, lints staged frontend files, checks selected TypeScript workspaces, and runs query-invalidation and backend-context checks. Commit-msg runs commitlint. The manually invoked `full-check` runs format, lint, and documentation checks; it is not a test suite. There is currently no pre-push job in that configuration.

Hooks do not cover all tests or all workspaces. Formatter and lint jobs use `stage_fixed`, so inspect `git diff --cached` and `git diff --cached --check` before a commit, particularly for partially staged files. CI runs separately: see `.github/workflows/` for commands, path filters, and target matrices. For example, frontend type-check CI expands Core changes to several hosts; backend CI runs on its configured paths. Do not assume an unrelated workflow ran or that a local hook proves CI passed.

## Reporting

Record the checks actually run and their results. Identify failures caused by pre-existing work or environment limits separately, and state any relevant validation not run. Do not claim full-suite or CI success from a focused check.
