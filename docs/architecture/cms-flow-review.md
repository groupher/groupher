## 优先处理的四项改动

### 1. 按客户端的恢复动作定义冲突

**现状。** WorkingCopy 冲突码 4561 来自生成契约，content-publisher adapter 以生成常量识别 4569 docs_state_conflict，两者都投影为 HTTP 409、revision_conflict。实施中已将 4569 加入生成输入，与 4539、4540、4561 一起生成；此项仍待完整 B1 验收。Docs 的其他操作仍可能将 default revision、queue version、public conflict、preview changed 和部分 owner 异常折叠进 4569；队列副本保存已将队列版本和副本 revision 分别映射为 4582、4583。saveWorkingCopy、saveDocsQueueCopy、文章创建与发布、评论写入等转发操作共享该 HTTP 错误投影。[adapter 与 saveDocsQueueCopy](../../frontend/core/lib/server/content-publisher.ts) · [Docs 错误投影](../../backend/api/lib/groupher_server_web/resolvers/cms/docs.ex) · [生成契约的输入](../../packages/contracts/content-publish.contract.json)

**场景。** 编辑者基于 W7 保存正文，另一标签页已保存 W8，需要读取 W8 并保留本地输入。另一种情况是队列在打开抽屉后被重新编排，正文仍是 W7，用户需要更新的是队列基线。一个 revision_conflict 无法单独指导这两个恢复动作。owner 无效时反复刷新正文也无助于恢复。这是协议表达能力的问题，具体 UI 是否走错分支需通过消费者测试确认。

**改后与验收。** 从 resolver 保留冲突原因，经生成契约透传至操作 adapter，HTTP 可以继续统一为 409。分别构造工作副本推进、队列推进、公开头推进三个响应，断言客户端刷新相应对象、保留未提交输入。owner 错误单独定义可公开的恢复方式。先确定动作，再决定需要几个公开码，避免为每个内部异常制造 API。

### 2. 区分命令已提交与旧结果还能否展示

**现状。** SaveWorkingCopy 的 confirmation 保存工作副本 ID、revision、command_id。present 会重新检查权限，并要求当前工作副本恰好仍是该 revision，否则返回 command_result_unavailable。每次保存 post/blog/changelog 都用 edit_article，present 用 edit；只有前者检查已发布文章的编辑开关。开关关闭后，原结果仍可能可读，具体取决于其余权限与 revision。写权限和结果披露权限应分别验收。[命令及 present](../../backend/api/lib/groupher_server/cms/articles/commands/save_working_copy.ex) · [Article policy](../../backend/api/lib/groupher_server/cms/gate/access/policy/article.ex)

**场景。** A 把 W7 保存成 W8，服务端已提交，浏览器丢响应；B 随后把 W8 保存成 W9；浏览器用原 command_id 重试 A。此时返回 W9 冒充 A 的响应会破坏版本语义。把 A 当作未执行再生成 command_id，则会把网络恢复变成新的业务操作。

**改后与验收。** 将“命令的提交状态”和“当前授权下可展示的数据”分别建模。允许知道提交结果的调用者可收敛到已确认状态，旧版本不可展示时再读当前工作副本；保留浏览器中尚未提交的 W10 编辑。权限已撤销时遵守现有披露边界。用同 ID 同输入重试、同 ID 异输入、后续保存、撤权四组用例检查写入次数、返回身份和编辑器内容，再决定是否需要调整公开响应。先复用现有 Receipt 与 confirmation 协议。[命令确认合同](cms-command-confirmation.md)

**B1 恢复矩阵。** 现行 Receipt 合同 §5 把 identity 相同但缺少 Confirmation 映射为 4534。SaveWorkingCopy.present 还将权限失败、工作副本消失和 revision 推进映射到同一码。基线的 Docs publication_result 将部分查询和命令 atom 错误都映射到 4534。实施中已将查询的未分类失败改为 4581，并让 content-publisher adapter 将 4530、4534、4536 分别映射为明确的 HTTP 422 错误；这些值本身不证明命令提交。完整 B1 验收仍需覆盖网络响应丢失、版本推进及所有消费者。[Receipt 身份与不可变锚点](cms-command-confirmation.md) · [Docs resolver，第 701–713 行](../../backend/api/lib/groupher_server_web/resolvers/cms/docs.ex) · [content-publisher adapter 错误优先级，第 40–60 行](../../frontend/core/lib/server/content-publisher.ts)

Docs 自动保存当前只在编辑器实例内保留待重试命令；切换文章或卸载会清除内存状态。重新打开时需要读取服务器当前副本，但这一机制不保证找回尚未提交的本地编辑，也不保证跨卸载复用原命令身份。跨页面或刷新恢复属于单独待设计的持久化与隐私合同，不能将实例内的重试测试表述为已覆盖该场景。

#### 2.1 Docs 队列、审批与站点发布

在审批与发布路径上，命令入口通过 `Queue.lock_or_create` 在当前事务中取得 Community 级 advisory lock，再锁队列和相关内容。`QueueRelease.run` 沿用调用方持有的站点锁。ApproveQueue 与 ReleaseQueue 各自通过命令确认处理重试。Approval 锁定变更及受影响内容，构建计划并冻结成员 Snapshot，保存批准依据。QueueRelease 按请求 revision 推进队列、锁相关目标及 Lifecycle、重新授权并重建计划；需要审批时核对批准来源，再将文章公开状态、导航、Release 记录和事件意图写入同一事务。一次站点发布可包含目录变更，单篇文章成功不足以证明整站一致。[SiteLock](../../backend/api/lib/groupher_server/cms/doc_tree/publish/site_lock.ex) · [审批冻结，第 50–98 行](../../backend/api/lib/groupher_server/cms/doc_tree/publish/approval.ex) · [发布事务，第 55–128 行](../../backend/api/lib/groupher_server/cms/doc_tree/publish/queue_release.ex) · [Release 命令](../../backend/api/lib/groupher_server/cms/doc_tree/commands/release_queue.ex)

B1 验收分别构造审批前队列变化、审批后来源变化和仅预览失效，记录各自 resolver 与客户端动作；B5 验收同一 release command 丢响应重试、两个管理员竞争发布，以及写入单篇 Public 后整批失败。比较队列 revision、批准的 Snapshot、公开目录、Release 数与 outbox，验证一次成功或整批回滚。

### 3. 将发布编排移到 Articles.Publication

**现状。** Articles.Publication 支持通过引用选择已有 Snapshot，事务还包含编号、首次发布限流、Ticket 校验、mentions、统计、Review、Activity 和事件入队。开发者想修改“重新发布如何影响 Ticket”，可以在 Publication 用例中找到相关约束。[事务中的实际调用顺序](../../backend/api/lib/groupher_server/cms/articles/publication.ex)

**场景。** 用户把已有 S2 设为公开版本，全程可能不需工作副本。若移动代码时只更新公开指针，公开正文仍对应 S1，读者就会看到不一致的数据。若把通知放到提交前直接发送，事务回滚后也可能留下通知。

**改后与验收。** articles/commands 保留发布定义与 confirmation；通用 CMS.Command/Receipt 识别重放，Articles.Publication 拥有发布事务与锁序，WorkingCopy 负责编辑和冻结，Public 维护指针与公开正文。本批只迁移 owner 并保留原编排和锁序；Publication 仍集中编排各副作用，拆分 publication/ 子模块属于后续独立工作，不作为已完成项。基线包含 CreateAndPublishArticle 和 PublishArticle 两个入口、Public.select_snapshot 内部再次加锁、Lifecycle 触发 ReviewBlocks.recompute 与 Revision.bump。锁序和副作用在迁移时保持原样，后续改动须单独验收。[首次发布入口](../../backend/api/lib/groupher_server/cms/articles/commands/create_and_publish_article.ex) · [公开指针](../../backend/api/lib/groupher_server/cms/articles/public.ex) · [Lifecycle](../../backend/api/lib/groupher_server/cms/articles/lifecycle.ex)

发布事务必须保证公开正文、指针、必要状态及事件意图原子提交。Ticket、Review、mentions、统计逐项记录“发布成功时必须可见吗、失败是否回滚、重试怎样去重”。有明确延迟容忍度的消费者才迁移到现有 outbox。验收覆盖首次发布、发布已有 Snapshot、竞争发布及中途失败，比较 Public、Lifecycle 和事件记录。[内容模型与公开读合同](../feature/article/working-copy-snapshot-target.md)

### 4. 拆清 Passport 字段内的定位与授权

**现状。** M.Passport 同时读 Catalog、解析 Article locator、识别前序 middleware 放入的 struct、推导 thread/community，并可将 scope 写进 arguments。communityActivity 与 communityActivityStats 已开启 pass_scope；config、event 等字段的下游 authorize_audit_read 仍重新加载 Store；global 分支不传 scope。实际 SQL 数留待测量。[CommunityLog，第 309–326 行](../../backend/api/lib/groupher_server/activity/community_log.ex) · [Passport middleware](../../backend/api/lib/groupher_server_web/middleware/passport.ex) · [字段内 scope 试点](passport-request-scope.md)

**场景。** 当前 schema 未发现 article_editor 的字段声明。已有 Article struct 的短路是兼容候选，尚无当前字段路径证据。先按 [FrontDesk A0–A2](../migrations/frontdesk-article-unification.md) 核对动态注册，再决定是否删除。若为了减少一次查询，把一个字段的 Community scope 放进整个 operation 的共享上下文，同一请求的另一个社区字段就可能拿到错误事实。

**改后与验收。** 公开 locator 在确定的入口解析一次，middleware 接收规范化目标，内部 typed scope 显式传给同字段下游。事务内 Gate 继续按所需时效检查。先对 communityActivity 和 stats 分别记录 Store 读取次数；只在重复已证实的路径开启复用。用两个社区别名、无权 actor、无效路径、已有 struct 检查隔离性、错误与顺序。

### 举报与 AlertWall：优先收敛同一事务中的往返依赖

**当前链路。** SubmitReport 为 CMS 已解析和授权的目标提交举报，在事务内重新校验并锁定目标、写入 AlertWall 举报记录，由 AlertWall 按 item_id 与 observed_version 统计有效举报人，再将版本、计数及目标事实交给 CMS.apply_report_threshold_in_transaction。CMS.Review.Threshold 按事实施加内容限制；展示 Receipt 时仍需按 ID 读取举报。Resolve 则处理 Wall 条目，并为社区权限直接读取 CMS 的 Community schema。两个域各自拥有数据；独立连接跨阈值及限制写入失败已有回归，其他目标和版本切换仍按下方场景验收。[提交举报](../../backend/api/lib/groupher_server/alert_wall/commands/submit_report.ex) · [阈值与锁](../../backend/api/lib/groupher_server/cms/review/threshold.ex) · [墙内处置](../../backend/api/lib/groupher_server/alert_wall/commands/resolve.ex)

**场景与建议。** 假设两个用户同时举报同一版本，第二笔使有效人数达到阈值。若提前异步计数，会出现举报已提交而限制尚未生效的窗口；若只按条目汇总，新版本可能继承旧版本的计数。当前提交事务按既有锁序校验目标，记录举报并取得与该版本绑定的计数，再由 CMS 应用限制；传入的事实包括条目、观察版本、有效人数及操作标识。写入步骤直接使用返回的举报，Receipt 展示仍按 ID 读回以保持重放语义。独立数据库连接并发跨阈值时，测试核对版本计数和唯一有效限制；限制写入失败回滚另有测试。Wall 自身的“已处理”与内容恢复继续独立。现有两种 owner 的提交条件如下。

| owner               | 已实现                                                                                         | B3 退出条件                                                                                                                |
| ------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| CMS 的内容目标      | 提交事务内复核目标，阈值按观察版本计算                                                         | 目标换版、重复举报和限制写失败均保持原子性                                                                                 |
| Accounts 的用户目标 | resolver 按公开 login 定位用户并拒绝自我举报；事务内通过 Accounts 确认目标存在且不是举报者本人 | 目标不存在时拒绝提交；数据库目前禁止物理删除用户，用户目标没有文章版本。若将来引入删除流程，需重新设计删除与举报的并发合同 |

[用户举报入口，第 251–265 行](../../backend/api/lib/groupher_server_web/resolvers/alert_wall.ex) · [按 owner 校验，第 114–118 行](../../backend/api/lib/groupher_server/alert_wall/commands/submit_report.ex)

**验收。** 同人重复、多人并发跨阈值、举报期间目标换版、施加限制失败回滚、墙条目处理后内容限制仍有效。暂缓独立 Report Context；若后续出现跨产品案件分派、申诉或证据保留，并且有独立生命周期，再以这些用例决定是否拆域。

### Mentions 与 Messaging：关系归属合理，写入参数暴露了存储细节

**当前链路。** CMS.ArtimentMentions 负责捕获内容关系。投递显式用户提及时，Effects.Notifications 锁定来源 endpoint、核对当前 revision 与公开可见性，将捕获的收件人与当前关系取交集，并排除作者。随后 CMS 传递来源事实及已核实的收件人 ID，Messaging 构造含 read、block_linker、inserted_at 等字段的行并在事务内记录，将捕获的完整 recipient_ids 写入 outbox 的 consumed_user_ids。例如捕获乙、丙而仅乙仍符合条件时，只给乙入箱，两人都进入消费标记。迁移前追踪 block_linker 的分组消费者以确定字段 owner。提交后再使 Accounts 邮箱缓存失效。提及关系与消息行初始化分别由 CMS 和 Messaging 负责。[关系捕获](../../backend/api/lib/groupher_server/cms/artiment_mentions/capture.ex) · [投递与消费标记](../../backend/api/lib/groupher_server/cms/artiment_mentions/effects/notifications.ex) · [Messaging 入口](../../backend/api/lib/groupher_server/messaging.ex)

**场景与建议。** 作者在 S1 提及乙，worker 投递前作者发布 S2 并删掉提及。简单消费“曾经 @乙”的事件会发出过时消息；把版本核验移入 Messaging 又会让它理解 Article 与 Comment 的可见性。保留 CMS 对当前关系的复核，将跨域输入缩为已核实的来源、作者、收件人与投递身份，由 Messaging 初始化未读、时间和消息字段。保留消息写入与消费标记的原子性。这样新增邮箱展示字段只需修改 Messaging，新增可提及的内容类型主要修改 CMS 的捕获和可见性逻辑。用“移除提及后延迟投递”“暂不可见后重试”“写入后重试”“标记已读后重试”验证无误投、无丢失和无重复。

### Messaging 的首次发布通知：保留冻结语义，隔离事件存储类型

FirstPublication.deliver 已按事件与收件人去重，使用发布时捕获的作者和名单。它也直接匹配 CMS.Outbox.Event、事件名和 contract_version，并引用 CMS.Model.Embeds。比如管理员乙在首次发布后离职、丙接任，延迟投递仍应使用首次发布时的名单。它与上一节的提及恰好有不同的时间语义，不宜共用一个“投递时刷新所有收件人”的逻辑。[首次发布通知解码及投递](../../backend/api/lib/groupher_server/messaging/notices/first_publication.ex)

建议让 CMS outbox 消费适配层负责从 Ecto event 解码版本化的发布事实，Messaging 接受稳定的事件 ID、文章引用、冻结的作者展示信息和收件人。保留现有幂等键与收件人持久化规则。变更事件存储时只调整解码入口；增加收件箱展示能力时只调整 Messaging。用旧版本事件 fixture、重复投递、名单变化和通知已读后的重试验证。当前已有版本和去重设计，这里的收益是减小未来改动范围。

### ReviewBot 与内容审核：让配置边界与推理边界一样清楚

CMS.Review.Requests 向 ReviewBot.check 传入 payload 和 policy_snapshot；ReviewBot 再调用 AI.check。CMS.Review.Results 通过 AlertWall 更新意见及风险条目。另一路 RequestSubmission 通过 ReviewBot.policy_snapshots 消费版本化策略快照；配置存储变化经该 facade 隔离，但提交参数仍需遵守快照合同。若机器人因延迟在文章改版后才返回，模型意见仍属于提交时的版本；更新墙上的意见、改变内容限制、追溯使用了哪版策略是三个独立的业务要求。[请求提交](../../backend/api/lib/groupher_server/cms/review/request_submission.ex) · [执行审核](../../backend/api/lib/groupher_server/cms/review/requests.ex) · [结果处理](../../backend/api/lib/groupher_server/cms/review/results.ex) · [ReviewBot](../../backend/api/lib/groupher_server/review_bot.ex)

ReviewBot 已提供生成可持久化 policy snapshot 的接口，提交端消费审核所需字段；聚焦测试验证注册后修改社区配置不会改变已保存快照。CMS 继续负责目标版本和最终处置，AlertWall 继续保留用户举报与 AI 意见并存的语义。验收时在请求排队期间变更社区策略，并分别返回旧版与新版目标的意见，核对请求使用的策略、条目版本和内容限制。模型供应商替换可以用同一组意见合同独立验证。

## Accounts、Activity、Analysis 的真实依赖

三者值得保留独立 Context。个人页展示的是用户当前状态，审计日志回答谁对什么资源做过什么，趋势图回答某段时间发生了多少次有效行为。三种数据的主键、时间含义、可见范围和重建方式均不同。代码里也没有一条所有动作都要经过的 Accounts → Activity → Analysis 流水线。下面按实际调用说明依赖方向。

## CMS 内部模块逐组决策

这里的“拆”首先指同一应用内拆出可命名、可测试的业务接口；“合并”优先指统一权威或入口。涉及事务、表或队列的物理迁移需另外论证。各组按共同用例排列，避免按目录数量判断复杂度。

| 模块群                                                                   | 现状、调用场景与边界决定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
