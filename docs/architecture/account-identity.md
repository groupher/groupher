# Account identity and public names

> 状态：current
>
> 更新：2026-10-25

## 结论

Groupher 的 `login` 是用户稳定且唯一的公开身份：创建后不可修改，可用于定位用户。`nickname` 是可修改的展示名称，只用于界面显示。任何持久关联或按用户隔离的客户端状态都不能用 `nickname`。

服务端业务关系继续使用数据库 `user.id`。客户端需要一个稳定的账户范围时使用 `login`。

```text
login       稳定、唯一；定位账户及隔离该账户的客户端状态
nickname    可修改；展示给读者
user.id     数据库主键；服务端关系和持久化
```

## 各名称的使用规则

| 值         | 稳定性               | 用途                                                                    | 不要用于                               |
| ---------- | -------------------- | ----------------------------------------------------------------------- | -------------------------------------- |
| `login`    | 创建后不变，唯一     | 用户主页和公开身份；前端 Query key、Receipt、当前用户本地数据的账户范围 | 展示用户可编辑的昵称；服务端外键       |
| `nickname` | 用户可以修改         | 帖子、评论、头像旁的名称等展示                                          | 查询用户、关联记录、缓存隔离、权限判断 |
| `user.id`  | 数据库生命周期内稳定 | 数据库外键、后端业务关系、服务端授权时的主体 ID                         | 让前端自行判断授权                     |

`login` 是定位用户的身份字段，不是授权凭证。请求是否登录、是否有权限，仍由服务端 Session、Passport 和 Gate 决定。客户端把 `login` 放进缓存键，只是避免不同登录用户共用私有缓存，不会让客户端因此获得权限。

公开的用户操作也传 `login`：例如举报某位用户时，客户端提交 `userLogin`，Accounts FrontDesk 将其解析为内部 `user.id`，AlertWall 再用内部 ID 保存目标关系。客户端不需要为这个操作读取数据库主键。

## 身份流

```text
Phoenix Session
    |
    +--> 当前 User { id, login, nickname, ... }
              |
              +--> AccountStore
                      +--> user.id：服务端关系和资源主体
                      +--> user.login：客户端账户范围、公开定位
                      +--> user.nickname：界面展示

公开内容显示名称 ----------> nickname
用户主页 / 稳定客户端数据 --> login
数据库关系 / 服务端授权 ----> user.id + Session / Passport / Gate
```

客户端在 Query key、本地 Receipt、optimistic 队列和账户本地数据清理中，统一从当前 `user.login` 取得 `user:${encodeURIComponent(login)}` 范围。匿名状态用独立的 `anonymous` 分区，不伪造一个用户身份。账户切换或退出时，按旧账户范围清理临时状态和私有缓存。

## 变更边界

所有服务端关系仍使用 `user.id`，不把 `login` 写入外键。所有展示仍使用 `nickname`，不把 `login` 当作可编辑显示名。任何新增账户字段都必须先说明它解决了 `login`、`nickname` 和 `user.id` 哪个都不能解决的问题，避免再次引入平行身份。

## 场景例子

用户 `alice` 把昵称从“爱丽丝”改成“Alice”。帖子作者显示随之更新；用户主页地址、他自己的收藏状态缓存、未完成的客户端 Receipt 和账户本地草稿仍然归 `alice`。数据库中的作者关系仍指向同一个 `user.id`。这次改名不需要生成或更新另一个账户引用。
