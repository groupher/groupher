## 3. 活动时间与序号的确定合同

### 3.1 单一有效值

在已经通过 owner Community/main 准入的 Doc 列表 SQL 中，定义一次：

```sql
COALESCE(
  CASE WHEN state.is_sunk
    THEN state.active_at
    ELSE GREATEST(article.active_at, state.active_at)
  END,
  public.published_at,
  article.inserted_at
) AS effective_active_at
```

`article` 是稳定 Article，`state/public` 只能来自 owner 当前 main。main 已 sunk 时只取该 main 自身的活动时间，避免稳定 Article 上的旧讨论活动盖过它；其余情形的 PostgreSQL GREATEST 忽略 NULL。CASE 结果为 NULL 时才进入后续兜底。UTC、秒精度，与当前活动写入精度一致；预览分支活动绝不进入表达式。

- ArticleLite 的 `active_at` 和 `doc_active_at`、列表 GraphQL `activeAt`、任何保留的 Article Flop 路径都引用此投影；不能在输出阶段再读 branch 原值。
- 默认/desc_active 排序及 cursor 为 `(effective_active_at DESC, binding_id DESC)`；asc_active 两项均 ASC。cursor 保存已 select 的值，fingerprint 保留 Community、筛选和方向；无 Comment branch 维度。相同时间靠唯一 binding_id 稳定遍历。
- 用同一 Ecto subquery/select projection 供 ORDER BY 与 cursor seek 使用，不复制成不同表达式、不在 Elixir 中先分页后算 max；Article 和 ArticleLite 的 Flop 定义不能再直接绑定 state.active_at。若 Flop 需 custom field，必须以同一 projection 构造器实现并覆盖测试。
- 此 cursor 不承诺并发更新期间的历史快照遍历；测试在固定数据集验证无漏重，发生正常活动时间变化后遵循既有失效/refetch 合同。

### 3.2 writer 与时间窗口

- 评论创建活动更新稳定 Article.active_at，继续沿用 `Articles.States.in_active_period?` 的配置窗口：比较稳定 Article.inserted_at 与当前 UTC 阈值；边界使用当前严格 `:gt`。只改变存储 owner，不扩大活动窗口。
- Doc 正文发布/编辑继续更新对应 DocBranchState.active_at，preview 更新不能抬高公开列表。发布不清零 Article 的评论活动。
- 当前 update_active_timestamp 仅更新 active_at，不能宣称评论会更新 last_active_at。last_active_at 现有其他业务语义保持；去除 branch 评论依赖时逐调用者等价迁移，不凭命名增加写入。
- comments_locked、next_floor、next_comment_inner_id 唯一归稳定 Article；Numbering 已原子 inc。删除 branch 重复字段、RevisionProjection 的旧读源；跨正文分支不能重新分配序号或解除评论锁。

## 4. 单 owner 数据库约束方案（设计，尚未建迁移）

### 4.1 不变量与最小额外字段

不新增 Doc 评论统计表或 owner 表。owner 仍是 ArticleBinding 的 community_id；现有 `(article_id, community_id)` UNIQUE 不足以限制 Doc binding 数量。采用一个数据库可验证的类型判别列 `article_bindings.thread`，用于同表 partial UNIQUE；它是 canonical Article.thread 的受 FK 约束副本，不是 home/mirror role、初始化 marker 或第二份 owner。

稳定 Doc 创建和 draft store 正常在同一事务建立唯一 binding，再写 lifecycle/state/draft；只有尚无任何 Doc membership/public/comment 的裸身份可暂时没有 binding，不得创建公开评论。binding 一旦建立，owner 在该 stable Doc 生命周期内不可搬迁；只有明确稳定 Doc 永久删除才一并删除 binding。

### 4.3 锁顺序与事务

- Doc 创建/变更 canonical 路径：保留并先取得所需 transaction/advisory 锁及既有 Community admission 锁（CommunityLifecycle 按 community_id 升序），再按稳定 Article UUID 排序锁 Article，再取 binding，再按 branch ID 排序锁 branch/membership，最后评论 root/target、reaction projection、统计及 outbox。集合操作必须统一排序；禁止 reader 在 Gate.scope 内执行这些锁/Repo。
- 公共评论写入以同一 Article 锁串行维护 distinct 参与人数；根回复修改按 root_id 再 target_id 固定顺序。Reaction 行锁/版本写入继续 existing projection 顺序；B1/B2 若发现当前 Gate 相反锁序，先统一整条链，不只改一个 helper。
- membership trigger 是存储边界保护，不能代替 canonical Command 预先取锁；直接 SQL UPDATE 可能先锁目标行而与命令反序，允许 deadlock/serialization 失败后整事务回滚，不能自动报告成功。并发验收必须记录结果与错误类型，不能吞错。
- 不允许应用连接禁用 trigger、关闭约束或用复制模式导入。管理员主动绕过数据库约束不在应用正确性承诺内。

### 4.4 Community 物理删除与授权清理

这里区分 CommunityLifecycle 的逻辑 destroy 与真正 DELETE Community。逻辑状态改变仍只阻断公开入口，不清零共享摘要，也不隐式永久删除 stable Doc。

- 直接 DELETE owner Community（包括 production_seed/cleanup 的 Repo.delete!）若仍拥有 stable Doc，必须被数据库 guard 拒绝并整事务回滚；不能只删 owner binding，不能留下无 owner Doc，也不通过 Community FK 自动判定整 Doc 永久删除已获授权。
- 明确授权的整社区永久清理：先取得既有 Community admission 锁，在同一事务中列出并按稳定 UUID 排序锁定所属 Docs，通过具名 stable Doc 永久删除流程清理聚合，再删除 Community。未授权删除的 Doc 必须使整次清理失败；seed 仅可删除 manifest 中被明确拥有的资源，不能顺手删除其他 Doc。
- 稳定 Article 的合法 DELETE CASCADE 到 binding 必须被允许；binding guard 要区分仍存活父 Article 与已经被本事务删除的父 Article，不能使用任意 session flag 绕过。此处是待实施要求，须用真实 FK/trigger 集成测试证明，不假定级联时序正确。
- Community 删除与新 Doc binding 创建竞争时，FK 与锁必须保证仅有合法提交态：拒绝 Community 删除或拒绝失去父 Community 的 binding；不允许提交孤儿。普通 Article 的其他 mirror binding、评论和 ArticleStats 保留，作为同批回归断言。
- B1 建 guard，B2 改 Community/seed/内部永久清理编排，测试见 OWNER-06；仅删正文 branch 的 DEL-01 语义不变。

### 7.3 Case 引用完整性检查

在仓库根目录执行以下 Python（只读文档，不连接 DB）。每次增删用例后检查重复 ID、未定义引用并动态输出数量，不再依赖手写总数。

```python
from collections import Counter
from pathlib import Path
import re

text = Path("docs/migrations/comment-reaction-snapshot-counts-inventory.md").read_text()
definitions = re.findall(r"^\| ([A-Z]+-\d{2}) `", text, re.M)
references = set(re.findall(r"\b[A-Z]+-\d{2}\b", text))
duplicates = sorted(key for key, count in Counter(definitions).items() if count > 1)
missing = sorted(references - set(definitions))
assert not duplicates, f"Duplicate case IDs: {duplicates}"
assert not missing, f"Undefined case references: {missing}"
print(f"Case definitions: {len(definitions)}; undefined references: {len(missing)}")
```

此检查只验证文档引用完整性，不证明测试已实现或通过；源码指纹保留原捕获时间，不因文档修订重写历史证据。
