# Web Analysis v1

> Status: planning.
>
> Goal: prove the self-hosted Umami collection loop for live Groupher pages, then
> introduce a thin Groupher-owned business boundary that can start as transparent
> forwarding and later grow into community isolation, permissions, and product
> analytics.

## Background

Groupher now has a self-hosted Umami deployment:

- App: `https://analysis.groupher.com`
- Vercel project: `groupher/umami`
- Source repo: `groupher/umami`, forked from `umami-software/umami`
- Database: Neon project `umami-dev`
- Umami website created for Groupher:
  - Name: `groupher dev`
  - Domain: `groupher.com`

Umami remains a vendor application. Groupher should not modify Umami source code
for product modeling. Groupher owns the business mapping, permissions, scripts
injection policy, and any product-facing DTOs.

This document is about Groupher's built-in Web Analysis feature. It is not the
same product surface as Dashboard `Integrations / Third-party / Analytics`,
where community admins configure their own external analytics providers such as
Google Analytics, Google Tag Manager, Facebook Pixel, Hotjar, Microsoft Clarity,
or their own Umami instance.

Built-in Web Analysis is a platform capability. Every community has it. There is
no community-level enable/disable switch in v1, and users do not choose a
provider or tracking scope for it.

## v1 Goals

1. Verify that production Groupher pages load the Umami tracking script.
2. Verify that page views from live pages are accepted by `analysis.groupher.com`.
3. Verify that the Umami dashboard shows the resulting traffic for the configured
   website.
4. Use one internal Umami website for `groupher.com` and filter community stats
   by path scope.
5. Start with a transparent server-side forwarding layer so Dashboard can query
   Umami through Groupher without exposing Umami credentials to browsers.
6. Keep the first version compatible with later community isolation,
   permissions, and product-specific analytics.

## Non-goals

- Do not fork or patch Umami internals for v1.
- Do not copy raw Umami events into Phoenix.
- Do not build custom charts before the collection loop and API boundary are
  proven.
- Do not create one Umami website per community in v1.
- Do not expose Umami admin credentials, API keys, or database credentials to the
  frontend.
- Do not make `analysis.groupher.com` part of the public community URL model.
  It is an analytics service origin.
- Do not reuse the Third-party Integrations model for built-in Web Analysis.
- Do not add a user-facing enable/disable switch for built-in Web Analysis in v1.

## Acceptance Checks

### 1. Runtime Script Check

On a live Groupher page, verify the rendered document contains the configured
Umami script:

```html
<script
  defer
  src="https://analysis.groupher.com/script.js"
  data-website-id="<umami_website_id>"
></script>
```

Checks:

- `src` uses `analysis.groupher.com`, not a Vercel deployment URL.
- `data-website-id` matches the website created in Umami.
- The script is present on public community pages as part of the built-in
  analytics capability.
- No PII, body text, email, username, or user-generated raw content is embedded
  as script attributes.
- Staff/internal traffic exclusion should happen before script injection when
  the request context can identify it.

### 2. Network Collection Check

Open a live page and verify browser network activity:

```text
browser
  -> GET https://analysis.groupher.com/script.js
  -> POST https://analysis.groupher.com/api/send
```

Expected:

- `script.js` returns 200.
- `/api/send` returns a successful response.
- The recorded URL is the live Groupher page URL.
- Repeated page navigation records additional page views or route changes as
  expected by Umami's client script.

### 3. Dashboard Data Check

In Umami:

```text
analysis.groupher.com
  -> Websites
  -> groupher dev
  -> realtime / overview
```

Expected:

- Recent visits appear after live page access.
- Page URL, referrer, browser, OS, device, and country fields are populated where
  available.
- The data is associated with the `groupher.com` website, not a temporary Vercel
  domain.

### 4. Backend Forwarding Check

After the Groupher business layer exists, Dashboard should query Groupher first:

```text
Dashboard
  -> Phoenix GraphQL / API
  -> CMS.WebAnalysis
  -> Umami API
  -> bounded DTO
```

Expected:

- Browser never calls Umami API with admin credentials.
- Phoenix validates the current community and viewer before returning data.
- v1 may forward the Umami response nearly transparently, but the public DTO is
  still owned by Groupher.

## Product Boundary

Groupher has two analytics-related surfaces:

| Surface                  | Purpose                                                                        | Owner                                | Data boundary                                    |
| ------------------------ | ------------------------------------------------------------------------------ | ------------------------------------ | ------------------------------------------------ |
| Built-in Web Analysis    | Native community traffic and product analytics shown in Dashboard `Analytics`. | Groupher platform.                   | Groupher-owned Umami deployment.                 |
| Third-party Integrations | User-configured external analytics scripts and provider IDs.                   | Community admin / external provider. | External provider account or user-owned service. |

These surfaces must not share the same persistence model. Third-party
Integrations can have user-facing provider choices and enable switches. Built-in
Web Analysis does not.

## Business Model

v1 should not introduce a community-to-Umami-website mapping table. Groupher's
public route model is path-first:

```text
groupher.com/<community>/...
```

That means one Umami website for `groupher.com` is the right v1 shape. Community
analytics are derived by filtering the global website data by route path.

### Global Website Config

The self-hosted Umami website ID is platform configuration, not per-community
state and not a new domain schema in v1.

Use environment or application configuration first:

```text
WEB_ANALYSIS_ENGINE=umami
WEB_ANALYSIS_BASE_URL=https://analysis.groupher.com
WEB_ANALYSIS_WEBSITE_ID=<umami_website_id>
```

If runtime operations later need admin UI edits, audit history, or multiple
global analytics backends, this can move to a single platform config row. That
is not required for v1.

Invariant:

- v1 uses exactly one Umami website for `groupher.com`.
- Community-level stats are queried with path filters, not separate Umami
  websites.
- There is no `enabled` flag for built-in Web Analysis in v1.
- There is no user-facing provider choice for built-in Web Analysis.
- `WEB_ANALYSIS_ENGINE=umami` expresses Groupher's internal implementation
  engine, not an Integration provider configured by the community.
- `WEB_ANALYSIS_WEBSITE_ID` is a vendor identity. It should not become a public
  Groupher ID.
- The browser may receive the website ID for script collection, but Dashboard
  analytics queries should still go through Phoenix.

### Community Path Scope

The current community's analytics scope should be derived from Groupher routing.
v1 does not need a table unless the route-to-community relationship stops being
derivable.

Examples:

| Community  | Public path scope | Umami website                 |
| ---------- | ----------------- | ----------------------------- |
| `home`     | `/home/**`        | `groupher.com` global website |
| `feedback` | `/feedback/**`    | `groupher.com` global website |
| `docs`     | `/docs/**`        | `groupher.com` global website |

Query shape:

```text
community slug
  -> path prefix
  -> global Umami website ID
  -> Umami stats query with URL/path filter
```

If a community later has aliases, custom domains, or path rules that cannot be
derived from slug alone, introduce a small `community_analysis_scopes` table for
path/domain scopes. That table should store query scopes, not Umami website
identities.

## Runtime Config

v1 uses a global Umami website ID for all public Groupher pages.

```text
request route/community
  -> resolve community
  -> render script with global Umami website ID
  -> later Dashboard queries filter by community path scope
```

For the current Next applications, script injection belongs in the Next root or
community layout path, not Phoenix LiveView. Main and Dashboard share
`RootLayoutShell`; route-aware filtering belongs in the server query layer, not
in separate Umami website IDs.

## v1 Request Flow

```text
Live page render
  -> resolve current community
  -> render Umami script with global website ID
  -> browser sends page view to analysis.groupher.com
  -> Umami stores raw analytics events
```

```text
Dashboard analytics view
  -> current dashboard community
  -> GraphQL asks Phoenix for analytics summary
  -> Phoenix checks viewer permission
  -> Phoenix derives community path scope
  -> Phoenix calls Umami API with global website ID and path filter
  -> Phoenix returns bounded DTO to Dashboard
```

## Phase Plan

### Phase 0: External Service Proof

Current focus.

- Confirm `analysis.groupher.com` points to the new Vercel `umami` project.
- Confirm Neon `umami-dev` contains the migrated Umami schema.
- Create or confirm the Umami website for `groupher.com` manually in the Umami
  UI for bootstrap.
- Record the website ID as the server-side global analytics configuration value.
- Record the website ID in the deployment config used by Main/Dashboard.
- Manually verify script load, `/api/send`, and dashboard data.

Exit criteria:

- `https://analysis.groupher.com/api/heartbeat` returns 200.
- The Umami website ID for `groupher dev` is known and present in server-side
  config.
- A live Groupher page records at least one visible visit in Umami.

### Phase 1: Script Injection

- Add a server-owned way to provide the Umami website ID to live page rendering.
- Load the script from `https://analysis.groupher.com/script.js`.
- Use the same global website ID for every public community page in v1.
- Exclude staff/internal traffic before injecting the script when a trusted
  session is available.
- Avoid custom event payloads until the page-view loop is proven.

Exit criteria:

- Production page view collection works without manual script editing.
- Staff/internal visits do not pollute the first baseline when the request can
  identify them.

### Phase 2: Transparent Dashboard Proxy

- Add a minimal service module, for example `CMS.WebAnalysis`, that resolves
  the current community path scope and calls Umami API.
- Add a small GraphQL/API endpoint for summary data.
- Return a bounded DTO with the first minimum set:
  - 7-day summary: pageviews, visitors, visits/sessions, bounces, total time.
  - Daily timeseries: pageviews and sessions.
  - Top 10 pages.
  - Top 10 referrers.
  - Optional Top 10 browser, OS, device, and country.

Exit criteria:

- Dashboard can show the same basic stats without talking directly to Umami from
  the browser.
- Permission checks happen before any Umami API call.

### Phase 3: Community Isolation

- Keep one Umami website unless path-filtered queries become insufficient.
- Make Groupher's route-derived path scope authoritative for community queries.
- Ensure community admins only see analytics filtered to their community path
  scope.
- Define behavior for disabled, archived, deleted, or domain-changed
  communities.
- Introduce `community_analysis_scopes` only if custom domains, aliases, or
  route rules make slug-derived path scopes ambiguous.
- Consider one Umami website per community only if there is a concrete need for
  Umami-native isolation, per-community sharing, deletion/export, or path filter
  limitations.

Exit criteria:

- A community's analytics data cannot be queried from another community context.
- Community queries apply the correct path/domain scope.

### Phase 4: Product Analytics

- Add custom events only after the page-view pipeline is stable.
- Use stable business event names and low-cardinality properties.
- Consider bounded projections for features that need product-native analytics,
  for example weekly reports or content performance summaries.

Examples:

| Event          | Purpose                                                             |
| -------------- | ------------------------------------------------------------------- |
| `article_view` | Content-level traffic summary.                                      |
| `post_vote`    | Product engagement trend event, not the vote count source of truth. |
| `docs_search`  | Docs search effectiveness and empty-result detection.               |

Phoenix/Postgres remains the source of truth for transactional product data such
as votes, content status, permissions, and moderation. Umami is only for traffic,
trend, funnel, and behavior analytics.

## Security And Privacy

- Umami admin credentials stay in server-side secret storage only.
- Frontend receives only script URL and website ID.
- Do not send email, login, nickname, article body, comment body, or raw search
  query text as event properties in v1.
- Prefer stable categorical properties over user-provided strings.
- Staff/internal traffic should be excluded before script injection when the
  request has a trusted session. Anonymous public traffic cannot be classified by
  email domain.

## Umami API Boundary

`CMS.WebAnalysis` should call the self-hosted Umami API through a provider
adapter. Do not query the Umami database directly.

```text
Base URL: https://analysis.groupher.com/api
Adapter:  CMS.WebAnalysis.Provider.Umami
Auth:     server-side credential only
```

The first provider adapter should target documented website statistics
endpoints, for example:

- `GET /api/websites/:websiteId/stats`
- `GET /api/websites/:websiteId/pageviews`
- `GET /api/websites/:websiteId/metrics`

Authentication details are implementation-specific to the deployed Umami
version. The requirement is that Phoenix owns login/token/API-key handling and
the browser never receives the credential.

## Open Questions

- Which Dashboard role can view analytics: owner only, admin, moderator, or a
  dedicated permission?
- Does Umami's URL/path filtering cover all needed community routes with enough
  precision and performance?
- How should custom domains or community aliases be represented if they stop
  being derivable from `community.slug`?
- Do we need a public traffic page later, or is analytics admin-only for now?
