# Web Analysis v2

> Status: planning.
>
> Scope: Dashboard `Analytics / Trends` built on Groupher-owned UI and DTOs,
> with self-hosted Umami kept as the collection and aggregate-query engine.

## Goal

v2 turns the current thin Dashboard analytics surface into a native Groupher
overview page backed by one Umami website per community. The product should
feel like Groupher, not like an embedded Umami console.

The first implementation should cover the common information visible in Umami
Overview, while tightening the existing v1 boundary:

- Dashboard asks Phoenix for analytics data.
- Phoenix validates the current viewer and community before querying analytics.
- Phoenix resolves the community-owned `umami_website_id`.
- Phoenix maps Umami responses into Groupher-owned DTOs.
- Dashboard renders custom charts and tables from those DTOs.
- Browser code never receives Umami API credentials.

Umami remains a vendor application. Do not fork or patch Umami UI for Groupher
product modeling.

## Current Baseline

v1 defined the built-in Web Analysis model in `docs/web-analysis/v1.md`:

- one global Umami website for `groupher.com`;
- community analytics derived by route path scope, for example `/home`;
- public collection script mounted from Main;
- Dashboard queries go through Phoenix;
- raw Umami response fields do not cross the provider boundary.

The production incident during v1 exposed two limits of that shape:

- The provider had to fan out from one global website and repeatedly derive
  path-scoped rows before querying secondary dimensions. With several scoped
  paths, one Dashboard overview could become dozens of Phoenix-to-Umami calls.
- Dashboard used a temporary `Client` fetch path and an `emptyOverview` fallback
  to recover from auth/loading problems. That made slow data look like real
  zeroes until the request completed.

v2 replaces the global website model with per-community Umami websites and does
not migrate v1 historical data. The trade-off is explicit: v2 Dashboard Trends
starts from traffic collected after the per-community website rollout; old
global-website history remains available only as operator/vendor data unless a
separate migration is designed later.

v2 must also remove the temporary Client-side workaround. The browser may still
hydrate interactive charts, but the initial Dashboard trend payload should come
from the normal server-side GraphQL path.

Current implementation notes to retire:

- `frontend/dashboard/src/app/[community]/dashboard/trend/Client.tsx` is a
  temporary rescue path. It fetches `/api/graphql` from the browser and keeps a
  tab-local `sessionStorage` cache so refreshes do not flash `0`.
- The correct v2 shape is SSR/RSC data loading through `~/graphql/server`
  (`gqFetch`), which already derives `Authorization: Bearer <token>` from the
  current request cookie when one exists, and remains anonymous when there is no
  valid token.
- Loading, empty, partial, and error states must be explicit. Do not use
  `emptyOverview` to represent a request that is still in flight.

## Community Website Model

v2 uses one Umami website per community. The Umami website ID is generated by
Umami and stored by Groupher as the community's analytics identity.

Persist only the vendor identity on the existing one-row-per-community dashboard
record:

```text
community_dashboards.umami_website_id uuid
```

The column should be nullable during rollout so existing communities can be
provisioned gradually. The v2 exit criteria should require every active
community to have a value. Do not put this field on `communities`; the Umami
website ID is not a public community identity.

Do not add `web_analysis_enabled`. Built-in Web Analysis is a platform feature
and is enabled by default. Do not reuse the Third-party Integrations analytics
model; that surface is for user-owned external scripts and provider IDs.

Recommended Umami website attributes:

```text
id:     <Umami-generated UUID>
name:   <community.slug>
domain: groupher.com
```

Use `community.slug` for `name` because it is stable enough for admin display
and avoids churn when the community title changes. If slug changes become a
supported product operation, updating the Umami website name is cosmetic and can
be handled asynchronously.

Keep `domain` as the platform primary domain, `groupher.com`. Tracking
isolation is by `data-website-id`, not by domain. A community custom domain
should still render the same community `umami_website_id`; it does not need a
new Umami website.

Lifecycle:

```text
community created
  -> Phoenix calls Umami POST /api/websites
  -> Phoenix stores returned website.id as umami_website_id

community public page rendered
  -> Main resolves community umami_website_id
  -> script renders data-website-id=<umami_website_id>

dashboard trend loaded
  -> Phoenix resolves community umami_website_id
  -> Phoenix queries that Umami website directly
  -> Phoenix returns Groupher-owned DTO
```

Deletion and rename are product lifecycle decisions, not tracking requirements:

- Deleting a community may delete the Umami website or leave it retained for
  audit/restore windows. v2 does not need to migrate old global website data.
- Renaming the community title does not require Umami changes.
- Changing slug only requires a cosmetic Umami `name` update if the admin UI
  should mirror the new slug.
- Suspending or deactivating a community should stop public script injection.
  Existing Umami website data is retained unless the community is permanently
  deleted under the chosen retention policy.

This model removes the v1 path-prefix isolation problem. Phoenix no longer needs
to query one global website and filter `/home/**` rows to derive community
summary. User filters are still validated by Phoenix, but they are now filters
inside the already isolated community website.

## Product Surface

Keep Dashboard navigation simple:

```text
Analytics
  Trends
  Logs
```

`Trends` is the first v2 page. It is the native overview surface for community
traffic.

`Logs` is out of scope for v2. Keep the navigation item only if the product
already needs a placeholder. The concrete log/event model should move to a
future `v3` document or be marked `TBD` until there is an agreed shape.

Do not expose Umami's full admin navigation in Groupher. Groupher should only
surface the analytics views that are useful to community admins.

## v2 Trends DTO

Design the API as a Trends payload rather than as individual chart endpoints for
the first pass. This keeps SSR simple and gives the Dashboard one coherent
loading/error state.

Suggested top-level shape:

```text
analysisTrends(community, range, filters) {
  status
  provider
  range
  filters
  summary
  timeseries
  pages
  sources
  environment
  location
  traffic
  errors
}
```

Status values:

- `ok`: the full requested Trends payload was loaded.
- `partial`: at least one section failed or was unavailable, but the response
  contains usable data for other sections.
- `unavailable`: no requested section can be loaded.

Use `errors[]` instead of a single loose `error` string once v2 contains several
sections:

```text
error {
  code
  message
  section
  providerStatus
}
```

When a section is unavailable, return a present section object with its own
`status` and an empty `items` or `points` list. Avoid mixing absent keys and
`null` for recoverable provider gaps. Reserve `null` for optional scalar values
inside otherwise valid rows.

### Summary

Fields:

- `visitors`
- `visits`
- `views`
- `bounceRate`
- `visitDuration`

Each summary metric should optionally include comparison against the previous
period:

```text
metric {
  value
  previousValue
  changeRate
}
```

Comparison uses the immediately preceding equal-duration period. For a 7-day
range, compare against the 7 days immediately before `range.startAt`; for a
24-hour range, compare against the previous 24 hours. Do not align to calendar
week or calendar month in v2 unless the range itself is calendar-based.

If Umami cannot return the previous period in the same request, Phoenix may make
a second idempotent read request and merge the result into the DTO. If the
comparison request fails, return the current value and set `previousValue` and
`changeRate` to `null`, with a section-level warning in `errors[]`.

The Dashboard can then render the same five overview cards as Umami without
copying Umami's visual style.

Metric calculation boundary:

- If Umami returns a ready value, Phoenix normalizes the provider field into the
  DTO.
- If Umami returns only count fields, Phoenix computes:
  - `bounceRate = bounces / visits`;
  - `visitDuration = totalTime / visits`.
- Division by zero returns `0` for display metrics and `null` for comparison
  rates where there is no meaningful previous baseline.
- Formulas must be covered by provider adapter tests so Dashboard never
  reimplements provider math.

### Timeseries

The main chart needs a normalized series:

```text
timeseries[] {
  bucket
  timestamp
  visitors
  visits
  views
}
```

`bucket` is required and must be one of:

- `hour`: used for ranges up to 48 hours, including "Last 24 hours".
- `day`: used for ranges longer than 48 hours, including 7, 30, and 90 days.

`timestamp` is the UTC start time of the bucket in milliseconds. The frontend may
format it in the viewer timezone for labels, but grouping is backend-defined and
stable for the whole response.

For v2, render visitors and views by default. Keep visits in the DTO so the UI
can add a metric toggle without changing the backend contract.

### Pages

Expose common page breakdown tabs:

- Path
- Entry page
- Exit page
- Title
- Query

The tab groups do not need to expose exactly the same field set. Use a shared
display pair plus metric fields that are meaningful for that dimension.

Suggested shape:

```text
pages {
  path: pageMetric[]
  entry: countMetric[]
  exit: countMetric[]
  title: pageMetric[]
  query: countMetric[]
}

pageMetric {
  value
  label
  metrics {
    visitors
    visits
    views
    bounceRate
    visitDuration
  }
}

countMetric {
  value
  label
  metrics {
    visitors
    visits
    views
  }
}
```

Use `value` for the stable raw dimension value and `label` for display. Path
rows come from the current community website. They do not need a mandatory
`/<community>` prefix once the collection script is scoped by website ID.

Do not force `bounceRate` or `visitDuration` onto tabs where the provider cannot
produce meaningful values. In v2, `entry`, `exit`, and `query` may return count
metrics only if Umami does not expose duration or bounce semantics for those
dimensions. Use `countMetric` for those tabs instead of returning nullable
`bounceRate` and `visitDuration` fields with unclear meaning.

### Sources

Expose:

- Referrer
- Channel
- Domain

Suggested item shape:

```text
sourceMetric {
  value
  label
  metrics {
    visitors
    visits
    views
  }
}
```

Empty direct traffic should be normalized to a Groupher-owned enum value:

```text
TrafficSource.direct
```

Do not leak a provider-specific empty string convention to Dashboard code.

### Environment

Expose:

- Browser
- OS
- Device
- Language
- Screen

Suggested item shape:

```text
dimensionMetric {
  value
  label
  metrics {
    visitors
    visits
    views
    percentage
  }
}
```

The frontend can map known browsers, OS names, and devices to existing icon
assets if available. Unknown values should render as text-only rows.

### Location

Expose:

- Country
- Region
- City

Suggested item shape:

```text
locationMetric {
  value
  label
  code
  metrics {
    visitors
    visits
    views
    percentage
  }
}
```

`value` and `label` are the standard display pair. `code` is optional provider
or geography metadata, for example an ISO country code. Country data can drive a
custom map, but the backend DTO must not be coupled to a specific map library.
Whether the first v2 UI ships a map is decided by Phase 2.

### Traffic Heatmap

Expose weekly traffic by weekday and hour. v2 uses UTC buckets for this heatmap
so the backend and frontend do not reinterpret the same data differently:

```text
traffic {
  timezone: "UTC"
  cells[] {
    weekday
    hour
    visitors
    visits
    views
  }
}
```

`weekday` is `0..6` with `0` meaning Sunday. `hour` is `0..23`. Both values are
UTC. A future community-configured timezone can add a new versioned field or
query argument; do not silently change v2 bucket semantics.

## API Capability

Umami's website API can supply most v2 overview data through documented
endpoints:

- `GET /api/websites`
- `POST /api/websites`
- `GET /api/websites/:websiteId`
- `POST /api/websites/:websiteId`
- `DELETE /api/websites/:websiteId`
- `GET /api/websites/:websiteId/stats`
- `GET /api/websites/:websiteId/pageviews`
- `GET /api/websites/:websiteId/metrics`
- `GET /api/websites/:websiteId/metrics/expanded`
- `GET /api/websites/:websiteId/sessions/weekly`

The useful metric dimensions include:

- path, title, query, entry, exit;
- referrer, channel, domain;
- country, region, city;
- browser, OS, device, language, screen;
- UTM source, medium, campaign, term, content.

Umami website management is server-side only. Browser code receives
`data-website-id` for collection, but never receives the API token used to create
or query websites.

Umami may not return all overview dimensions in one request. Even with one
website per community, the provider adapter should treat v2 overview as a
bounded fan-out operation:

- stats and comparison stats;
- pageviews timeseries;
- selected metric dimensions;
- weekly sessions for traffic heatmap.

Use a small concurrency limit, bounded timeouts, and no unbounded retries. Do
not re-fetch the same path list per dimension. The provider must build a request
plan once per overview and either query dimensions directly against the
community website or reuse any scoped path list it already has.

Cache identical overview requests for a short TTL when the same Dashboard page
is reloaded or shared across server renders. If one dimension request fails,
return `partial` rather than failing the whole page.

Do not query unsupported Umami dimensions. The v1 incident showed
`metrics/expanded type=url` returning HTTP 400 in the deployed Umami instance.
Do not ship the Dashboard `URL` tab until a supported provider query is proven.

Before enabling a tab or metric dimension, run and record a capability checklist
against the deployed `analysis.groupher.com` instance. The table below is the
required checklist, not just a representative sample:

```text
dimension      endpoint                         required result
path           metrics/expanded?type=path       200, non-empty when traffic exists
title          metrics/expanded?type=title      200 or disabled tab
query          metrics/expanded?type=query      200 or disabled tab
entry          metrics/expanded?type=entry      200 or disabled tab
exit           metrics/expanded?type=exit       200 or disabled tab
referrer       metrics/expanded?type=referrer   200 or disabled tab
channel        metrics/expanded?type=channel    200 or disabled tab
domain         metrics/expanded?type=domain     200 or disabled tab
browser        metrics/expanded?type=browser    200 or disabled tab
os             metrics/expanded?type=os         200 or disabled tab
device         metrics/expanded?type=device     200 or disabled tab
language       metrics/expanded?type=language   200 or disabled tab
screen         metrics/expanded?type=screen     200 or disabled tab
country        metrics/expanded?type=country    200 or disabled tab
region         metrics/expanded?type=region     200 or disabled tab
city           metrics/expanded?type=city       200 or disabled tab
```

Provider request defaults:

- concurrency: at most `3` in-flight Umami API requests per overview request;
- timeout: at most `5s` per Umami API request;
- retry: `0` by default, at most `1` retry for network errors or 5xx responses;
- cache TTL: `30s` to `60s` for identical overview requests.

If these values need to change, update this document and provider tests together
so production behavior is not left to vague "bounded" wording.

Reference docs:

- https://umami.is/docs/api/website-stats
- https://umami.is/docs/api/website-metrics
- https://umami.is/docs/api/sessions

## Filter Model

The advanced selector should be supported through a Groupher-owned filter DSL.
Do not expose raw Umami filter JSON directly to Dashboard components.

Suggested shape:

```text
filter {
  combinator: "and"
  conditions[] {
    dimension
    operator
    value
  }
}
```

v2 supports a flat `and` group only. This covers common cases such as:

```text
path contains "blog" AND country is "US"
```

Boundary cases:

- `conditions: []` means no user filter.
- A single condition still uses `combinator: "and"`; do not omit the
  combinator.
- Unknown dimensions or operators are rejected before any provider request.

UTM dimensions are filter-only in v2. They are listed as valid filter
dimensions because Umami can expose UTM data, but v2 does not ship a UTM
breakdown tab. A future phase can add a `sources.utm` section once there is a
clear Dashboard use case.

Nested `or` groups should not be added until there is a concrete UI and provider
translation plan. If they are needed later, version the input shape rather than
overloading `conditions[]`.

Initial dimensions:

- `path`
- `title`
- `query`
- `referrer`
- `channel`
- `domain`
- `country`
- `region`
- `city`
- `browser`
- `os`
- `device`
- `language`
- `screen`
- `utmSource`
- `utmMedium`
- `utmCampaign`
- `utmTerm`
- `utmContent`

Initial operators:

- `is`
- `isNot`
- `contains`
- `notContains`

Keep the first UI conservative. The selector can visually resemble Umami's
dimension picker, but it should be modeled as Groupher filters so future
providers or projections can reuse the same contract.

## Community Scope Invariant

The most important v2 rule is that user filters are always applied inside the
server-derived community website.

```text
Dashboard selected community
  -> Phoenix loads community.umami_website_id
  -> Phoenix validates viewer permission
  -> Phoenix queries only that Umami website
  -> Phoenix applies user filters inside that website
  -> Phoenix maps provider response into overview DTO
```

Do not trust client-provided website IDs or path scopes. The client may ask for
filters, but Phoenix must own the community boundary and resolve
`umami_website_id` from trusted database state.

Because v2 uses one website per community, community isolation does not depend
on path-prefix or wildcard semantics. Path filters are optional user filters,
not the authorization boundary.

For provider capability research only, keep a small debug script or private
operator page that can verify whether the deployed Umami API supports richer
path filters:

```text
filters={"path":"/home"}
filters={"path":{"operator":"contains","value":"/home"}}
filters={"path":{"operator":"regex","value":"^/home(/|$)"}}
```

Do not put this debug UI in the public Dashboard product surface. If the
operator test proves prefix/regex support, use it only for optional in-community
filters, not for community isolation.

Traffic heatmap follows the same filter semantics as the rest of the Trends
payload in v2. If a provider endpoint cannot apply the requested filter set to
weekly session data, return the heatmap section as `partial` or `unavailable`
instead of silently showing unfiltered traffic beside filtered sections.

## Frontend Implementation

Use custom Groupher components for the analytics surface. The UI should borrow
the information architecture of Umami Overview, not the implementation or visual
system.

Recommended component split:

```text
frontend/dashboard/src/app/[community]/dashboard/trend/
  page.tsx
  components/
    SummaryCards.tsx
    TrendChart.tsx
    DimensionPanel.tsx
    DimensionTable.tsx
    TrafficHeatmap.tsx
    FilterBar.tsx
    RangePicker.tsx
  salon/
    ...
```

Add `helper.ts` only if the route needs local DTO mapping, date/range helpers,
or query constants. Do not create it as an empty convention file.

`Client.tsx` should not own the initial data load. If client components are
needed for charts, range changes, or filter interactions, they should receive
SSR data as initial state and then refetch through the normal GraphQL client.

Temporary v1 rescue code to remove:

- browser-only `fetch('/api/graphql')` in
  `frontend/dashboard/src/app/[community]/dashboard/trend/Client.tsx`;
- `sessionStorage` as a local analytics cache;
- rendering `emptyOverview` before the first response completes.

Use the existing GraphQL/cache layer for client refetches. Loading state should
be `fetching` or explicit DTO status, not hand-written storage.

Follow existing Dashboard constraints:

- keep one component per file;
- do not pass `const s = useSalon()` as props;
- prefer existing global classes from `frontend/core/tailwind/common/utils.css`;
- use `cnMerge` when classes need to override each other;
- avoid arbitrary Tailwind values unless the existing utilities cannot express
  the layout.

## Charting Library

`shadcn/ui` charts are wrappers around Recharts. The current shadcn CLI supports
monorepo projects through per-package `components.json` files, but Groupher does
not need to adopt the whole shadcn component system for this feature.

Reference docs:

- https://ui.shadcn.com/docs/monorepo
- https://ui.shadcn.com/docs/components/chart
- https://ui.shadcn.com/docs/changelog/2026-03-cli-v4

Recommendation:

- use Recharts directly, or copy only the small chart wrapper pattern;
- keep chart primitives in Groupher-owned files;
- do not import shadcn cards, buttons, selects, or theme tokens wholesale;
- keep visual styling aligned with current Dashboard colors, radius, typography,
  and spacing.

This gives us the useful chart ergonomics without binding the Dashboard design
system to shadcn.

## Phase Plan

### Phase 1: Community Website Provisioning

- Add `umami_website_id` to the community-owned analytics/dashboard config.
- On community creation, create an Umami website with:
  - `name = community.slug`;
  - `domain = groupher.com`.
- Store the Umami-returned UUID. Do not derive it from slug.
- Render the Main public collection script from the current community's
  `umami_website_id`.
- Keep existing global `WEB_ANALYSIS_WEBSITE_ID` only as a temporary fallback
  during rollout, then remove it from the public script path.
- Add tests for missing, invalid, and successfully provisioned website IDs.
- Define suspend/deactivate behavior: inactive communities do not inject the
  collection script, but existing analytics data is retained.

Exit criteria:

- New community traffic is collected into that community's own Umami website.
- Dashboard can resolve the trusted `umami_website_id` from the database record.
- Browser code never receives Umami API credentials.
- There is no user-facing enable switch for built-in Web Analysis.
- No historical migration from the v1 global website is required.

### Phase 2: Trends Contract

- Add a v2 GraphQL query for `analysisTrends`.
- Keep the existing v1 summary query until the Dashboard page migrates.
- Implement summary, timeseries, top pages, and top referrers against the
  community's own Umami website.
- Add explicit unavailable and partial-data states.
- Define `hour` and `day` bucket selection for timeseries.
- Define equal-duration previous-period comparison.
- Define UTC semantics for traffic heatmap buckets, even if heatmap rendering
  ships in Phase 2.
- Add tests for range clamping and permission checks.
- Remove the temporary trend Client initial-load workaround and server-render
  the initial overview payload through `~/graphql/server`.

Exit criteria:

- Dashboard can render the top summary and trend chart from Phoenix DTOs.
- No browser code calls Umami API directly.
- Provider failures do not fail the whole Dashboard page.
- DTO tests cover `ok`, `partial`, and `unavailable` states.
- Missing provider fields are represented with present empty sections, not
  inconsistent absent keys.
- Refreshing the Trend page never renders `emptyOverview` fallback data before
  the first request completes. Loading, empty, and error states are separate.

### Phase 3: Overview Breakdowns

- Add Pages tabs.
- Add Sources tabs.
- Add Environment tabs.
- Add Location tabs.
- Add country map data only if the frontend is ready to render it in the same
  phase; otherwise keep map rendering out of the Phase 2 exit criteria.
- Add traffic heatmap.
- Add bounded provider fan-out, request timeout, and short-TTL cache behavior.
- Do not perform one Umami request per path per dimension. Query dimensions
  against the isolated community website, and only use path-specific fan-out
  when a provider endpoint has no website-level equivalent.

Exit criteria:

- The page covers the common Umami Overview information.
- Empty states are useful and visually stable.
- Every breakdown reads only the current community website.
- The backend does not make an unbounded number of provider calls per Dashboard
  request.
- Heatmap output uses documented UTC weekday/hour buckets.

### Phase 4: Filters

- Add the Groupher filter DSL to GraphQL input.
- Add server-side validation for dimension and operator.
- Resolve the mandatory community website before user filters.
- Build the advanced selector UI.
- Support a flat `and` group first; defer nested `or` groups until the UI and
  provider translation are designed.

Exit criteria:

- Users can filter by page, source, location, environment, and UTM dimensions.
- Filters cannot switch or widen the current community website.
- Invalid filters return a typed GraphQL error or safe empty state.
- Multiple filters combine with explicit `and` semantics.

### Phase 5: Logs And Events TBD

Logs and events are not part of v2 implementation. Keep this phase as a marker
only.

Before a later phase begins, define:

- whether `Logs` means raw analytics events, sampled events, product events, or
  audit-like activity;
- API shape, pagination, retention, and privacy policy;
- whether the data comes from Umami, a Groupher projection, or another product
  event stream.

## Open Questions

Phase 2 blockers:

- Which Dashboard roles can read analytics: owner only, admin, moderator, or a
  dedicated permission?
- Should v2 ranges be fixed presets only, or allow custom date ranges?

Deferred questions:

- Is country map rendering worth shipping in v2, or should it wait until there
  is enough traffic density?
- Do we need nested `or` filters in the first production UI, or is flat `and`
  enough for v2?
- Should community deletion delete the Umami website immediately, after a
  restore window, or never automatically?
- Should slug rename update the Umami website `name` synchronously or through a
  best-effort background job?
- Should the old global v1 website stay available only in Umami admin, or should
  Phoenix expose an operator-only diagnostic for it during rollout?
