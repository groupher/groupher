# Web Analysis v2

> Status: planning.
>
> Scope: Dashboard `Analytics / Trends` built on Groupher-owned UI and DTOs,
> with self-hosted Umami kept as the collection and aggregate-query engine.

## Goal

v2 turns the current thin Dashboard analytics surface into a native Groupher
overview page. The product should feel like Groupher, not like an embedded
Umami console.

The first implementation should cover the common information visible in Umami
Overview, while preserving the existing v1 boundary:

- Dashboard asks Phoenix for analytics data.
- Phoenix validates the current viewer and community before querying analytics.
- Phoenix maps Umami responses into Groupher-owned DTOs.
- Dashboard renders custom charts and tables from those DTOs.
- Browser code never receives Umami API credentials.

Umami remains a vendor application. Do not fork or patch Umami UI for Groupher
product modeling.

## Current Baseline

v1 already defines the built-in Web Analysis model in `docs/web-analysis/v1.md`:

- one global Umami website for `groupher.com`;
- community analytics derived by route path scope, for example `/home`;
- public collection script mounted from Main;
- Dashboard queries go through Phoenix;
- raw Umami response fields do not cross the provider boundary.

Current implementation is still a minimal slice:

- `GroupherServer.Analysis` exposes a summary query.
- `GroupherServer.Analysis.Provider.Umami` queries path metrics and aggregates
  rows under the current community path prefix.
- Dashboard renders summary cards plus Top pages and Referrers.
- `timeseries` and most overview breakdowns are empty or not exposed yet.

That is enough to keep the boundary stable, but not enough for a complete
overview UI.

## Product Surface

Keep Dashboard navigation simple:

```text
Analytics
  Trends
  Logs
```

`Trends` is the first v2 page. It is the native overview surface for community
traffic.

`Logs` is out of scope for v2. Keep the navigation item only if the product
already needs a placeholder. The concrete log/event model should move to a
future `v3` document or be marked `TBD` until there is an agreed shape.

Do not expose Umami's full admin navigation in Groupher. Groupher should only
surface the analytics views that are useful to community admins.

## v2 Overview DTO

Design the API as an overview payload rather than as individual chart endpoints
for the first pass. This keeps SSR simple and gives the Dashboard one coherent
loading/error state.

Suggested top-level shape:

```text
webAnalysisOverview(community, range, filters) {
  status
  provider
  pathScope
  range
  filters
  summary
  timeseries
  pages
  sources
  environment
  location
  traffic
  errors
}
```

Status values:

- `ok`: the full requested overview was loaded.
- `partial`: at least one section failed or was unavailable, but the response
  contains usable data for other sections.
- `unavailable`: no requested section can be loaded.

Use `errors[]` instead of a single loose `error` string once v2 contains several
sections:

```text
error {
  code
  message
  section
  providerStatus
}
```

When a section is unavailable, return a present section object with its own
`status` and an empty `items` or `points` list. Avoid mixing absent keys and
`null` for recoverable provider gaps. Reserve `null` for optional scalar values
inside otherwise valid rows.

### Summary

Fields:

- `visitors`
- `visits`
- `views`
- `bounceRate`
- `visitDuration`

Each summary metric should optionally include comparison against the previous
period:

```text
metric {
  value
  previousValue
  changeRate
}
```

Comparison uses the immediately preceding equal-duration period. For a 7-day
range, compare against the 7 days immediately before `range.startAt`; for a
24-hour range, compare against the previous 24 hours. Do not align to calendar
week or calendar month in v2 unless the range itself is calendar-based.

If Umami cannot return the previous period in the same request, Phoenix may make
a second idempotent read request and merge the result into the DTO. If the
comparison request fails, return the current value and set `previousValue` and
`changeRate` to `null`, with a section-level warning in `errors[]`.

The Dashboard can then render the same five overview cards as Umami without
copying Umami's visual style.

### Timeseries

The main chart needs a normalized series:

```text
timeseries[] {
  bucket
  timestamp
  visitors
  visits
  views
}
```

`bucket` is required and must be one of:

- `hour`: used for ranges up to 48 hours, including "Last 24 hours".
- `day`: used for ranges longer than 48 hours, including 7, 30, and 90 days.

`timestamp` is the UTC start time of the bucket in milliseconds. The frontend may
format it in the viewer timezone for labels, but grouping is backend-defined and
stable for the whole response.

For v2, render visitors and views by default. Keep visits in the DTO so the UI
can add a metric toggle without changing the backend contract.

### Pages

Expose common page breakdown tabs:

- Path
- URL
- Entry page
- Exit page
- Title
- Query

The tab groups do not need to expose exactly the same field set. Use a shared
display pair plus metric fields that are meaningful for that dimension.

Suggested shape:

```text
pages {
  path: pageMetric[]
  url: pageMetric[]
  entry: countMetric[]
  exit: countMetric[]
  title: pageMetric[]
  query: countMetric[]
}

pageMetric {
  value
  label
  metrics {
    visitors
    visits
    views
    bounceRate
    visitDuration
  }
}

countMetric {
  value
  label
  metrics {
    visitors
    visits
    views
  }
}
```

Use `value` for the stable raw dimension value and `label` for display. For path
rows, `value` should stay within the current community path scope.

Do not force `bounceRate` or `visitDuration` onto tabs where the provider cannot
produce meaningful values. In v2, `entry`, `exit`, and `query` may return count
metrics only if Umami does not expose duration or bounce semantics for those
dimensions. Use `countMetric` for those tabs instead of returning nullable
`bounceRate` and `visitDuration` fields with unclear meaning.

### Sources

Expose:

- Referrer
- Channel
- Domain

Suggested item shape:

```text
sourceMetric {
  value
  label
  metrics {
    visitors
    visits
    views
  }
}
```

Empty direct traffic should be normalized to a Groupher-owned enum value:

```text
TrafficSource.direct
```

Do not leak a provider-specific empty string convention to Dashboard code.

### Environment

Expose:

- Browser
- OS
- Device
- Language
- Screen

Suggested item shape:

```text
dimensionMetric {
  value
  label
  metrics {
    visitors
    visits
    views
    percentage
  }
}
```

The frontend can map known browsers, OS names, and devices to existing icon
assets if available. Unknown values should render as text-only rows.

### Location

Expose:

- Country
- Region
- City

Suggested item shape:

```text
locationMetric {
  value
  label
  code
  metrics {
    visitors
    visits
    views
    percentage
  }
}
```

`value` and `label` are the standard display pair. `code` is optional provider
or geography metadata, for example an ISO country code. Country data can drive a
custom map, but the backend DTO must not be coupled to a specific map library.
Whether the first v2 UI ships a map is decided by Phase 2.

### Traffic Heatmap

Expose weekly traffic by weekday and hour. v2 uses UTC buckets for this heatmap
so the backend and frontend do not reinterpret the same data differently:

```text
traffic {
  timezone: "UTC"
  cells[] {
    weekday
    hour
    visitors
    visits
    views
  }
}
```

`weekday` is `0..6` with `0` meaning Sunday. `hour` is `0..23`. Both values are
UTC. A future community-configured timezone can add a new versioned field or
query argument; do not silently change v2 bucket semantics.

## API Capability

Umami's website API can supply most v2 overview data through documented
endpoints:

- `GET /api/websites/:websiteId/stats`
- `GET /api/websites/:websiteId/pageviews`
- `GET /api/websites/:websiteId/metrics`
- `GET /api/websites/:websiteId/metrics/expanded`
- `GET /api/websites/:websiteId/sessions/weekly`

The useful metric dimensions include:

- path, URL, title, query, entry, exit;
- referrer, channel, domain;
- country, region, city;
- browser, OS, device, language, screen;
- UTM source, medium, campaign, term, content.

Umami may not return all overview dimensions in one request. The provider
adapter should treat v2 overview as a fan-out operation with bounded parallel
requests:

- stats and comparison stats;
- pageviews timeseries;
- selected metric dimensions;
- weekly sessions for traffic heatmap.

Use a small concurrency limit, bounded timeouts, and no unbounded retries. Cache
identical overview requests for a short TTL when the same Dashboard page is
reloaded or shared across server renders. If one dimension request fails, return
`partial` rather than failing the whole page.

Reference docs:

- https://umami.is/docs/api/website-stats
- https://umami.is/docs/api/website-metrics
- https://umami.is/docs/api/sessions

## Filter Model

The advanced selector should be supported through a Groupher-owned filter DSL.
Do not expose raw Umami filter JSON directly to Dashboard components.

Suggested shape:

```text
filter {
  combinator: "and"
  conditions[] {
    dimension
    operator
    value
  }
}
```

v2 supports a flat `and` group only. This covers common cases such as:

```text
path contains "blog" AND country is "US"
```

Nested `or` groups should not be added until there is a concrete UI and provider
translation plan. If they are needed later, version the input shape rather than
overloading `conditions[]`.

Initial dimensions:

- `path`
- `url`
- `title`
- `query`
- `referrer`
- `channel`
- `domain`
- `country`
- `region`
- `city`
- `browser`
- `os`
- `device`
- `language`
- `screen`
- `utmSource`
- `utmMedium`
- `utmCampaign`
- `utmTerm`
- `utmContent`

Initial operators:

- `is`
- `isNot`
- `contains`
- `notContains`

Keep the first UI conservative. The selector can visually resemble Umami's
dimension picker, but it should be modeled as Groupher filters so future
providers or projections can reuse the same contract.

## Community Scope Invariant

The most important v2 rule is that user filters are always narrower than the
server-derived community scope.

```text
Dashboard selected community
  -> Phoenix derives pathScope, for example /home
  -> Phoenix validates viewer permission
  -> Phoenix adds mandatory scope filter
  -> Phoenix applies user filters inside that scope
  -> Phoenix maps provider response into overview DTO
```

Do not trust client-provided `pathScope`. The client may ask for filters, but
Phoenix must own the community boundary.

Because v1 uses one global Umami website, path-prefix isolation is not the same
as a simple exact path filter. Before exposing v2 analytics broadly, prove the
prefix behavior with at least two communities under the same website:

```text
/home/...
/feedback/...
```

Required checks:

- `/home` queries do not include `/feedback` rows.
- aggregate summary matches the filtered path set.
- top pages, referrers, environment, and location do not leak rows from another
  community.
- filter combinations cannot widen the server-derived scope.

If Umami's filtering cannot satisfy prefix isolation with acceptable correctness
or performance, add a bounded Groupher-side projection before building more UI.

## Frontend Implementation

Use custom Groupher components for the analytics surface. The UI should borrow
the information architecture of Umami Overview, not the implementation or visual
system.

Recommended component split:

```text
frontend/dashboard/src/app/[community]/dashboard/analysis/
  page.tsx
  Client.tsx
  helper.ts
  components/
    SummaryCards.tsx
    TrendChart.tsx
    DimensionPanel.tsx
    DimensionTable.tsx
    TrafficHeatmap.tsx
    FilterBar.tsx
    RangePicker.tsx
  salon/
    ...
```

Follow existing Dashboard constraints:

- keep one component per file;
- do not pass `const s = useSalon()` as props;
- prefer existing global classes from `frontend/core/tailwind/common/utils.css`;
- use `cnMerge` when classes need to override each other;
- avoid arbitrary Tailwind values unless the existing utilities cannot express
  the layout.

## Charting Library

`shadcn/ui` charts are wrappers around Recharts. The current shadcn CLI supports
monorepo projects through per-package `components.json` files, but Groupher does
not need to adopt the whole shadcn component system for this feature.

Reference docs:

- https://ui.shadcn.com/docs/monorepo
- https://ui.shadcn.com/docs/components/chart
- https://ui.shadcn.com/docs/changelog/2026-03-cli-v4

Recommendation:

- use Recharts directly, or copy only the small chart wrapper pattern;
- keep chart primitives in Groupher-owned files;
- do not import shadcn cards, buttons, selects, or theme tokens wholesale;
- keep visual styling aligned with current Dashboard colors, radius, typography,
  and spacing.

This gives us the useful chart ergonomics without binding the Dashboard design
system to shadcn.

## Phase Plan

### Phase 1: Overview Contract

- Add a v2 GraphQL query for `webAnalysisOverview`.
- Keep the existing v1 `webAnalysisSummary` until the Dashboard page migrates.
- Implement summary, timeseries, top pages, and top referrers first.
- Add explicit unavailable and partial-data states.
- Define `hour` and `day` bucket selection for timeseries.
- Define equal-duration previous-period comparison.
- Define UTC semantics for traffic heatmap buckets, even if heatmap rendering
  ships in Phase 2.
- Add tests for range clamping and permission checks.

Exit criteria:

- Dashboard can render the top summary and trend chart from Phoenix DTOs.
- No browser code calls Umami API directly.
- Provider failures do not fail the whole Dashboard page.
- DTO tests cover `ok`, `partial`, and `unavailable` states.
- Missing provider fields are represented with present empty sections, not
  inconsistent absent keys.

### Phase 2: Overview Breakdowns

- Add Pages tabs.
- Add Sources tabs.
- Add Environment tabs.
- Add Location tabs.
- Add country map data only if the frontend is ready to render it in the same
  phase; otherwise keep map rendering out of the Phase 2 exit criteria.
- Add traffic heatmap.
- Add bounded provider fan-out, request timeout, and short-TTL cache behavior.

Exit criteria:

- The page covers the common Umami Overview information.
- Empty states are useful and visually stable.
- Every breakdown respects community path scope.
- The backend does not make an unbounded number of provider calls per Dashboard
  request.
- Heatmap output uses documented UTC weekday/hour buckets.

### Phase 3: Filters

- Add the Groupher filter DSL to GraphQL input.
- Add server-side validation for dimension and operator.
- Apply the mandatory community scope before user filters.
- Build the advanced selector UI.
- Support a flat `and` group first; defer nested `or` groups until the UI and
  provider translation are designed.

Exit criteria:

- Users can filter by page, source, location, environment, and UTM dimensions.
- Filters cannot widen the current community's analytics scope.
- Invalid filters return a typed GraphQL error or safe empty state.
- Multiple filters combine with explicit `and` semantics.

### Phase 4: Logs And Events TBD

Logs and events are not part of v2 implementation. Keep this phase as a marker
only.

Before a later phase begins, define:

- whether `Logs` means raw analytics events, sampled events, product events, or
  audit-like activity;
- API shape, pagination, retention, and privacy policy;
- whether the data comes from Umami, a Groupher projection, or another product
  event stream.

## Open Questions

- Which Dashboard roles can read analytics: owner only, admin, moderator, or a
  dedicated permission?
- Should v2 ranges be fixed presets only, or allow custom date ranges?
- Is country map rendering worth shipping in v2, or should it wait until there
  is enough traffic density?
- Do we need a bounded projection before exposing advanced filters in production?
- Do we need nested `or` filters in the first production UI, or is flat `and`
  enough for v2?
