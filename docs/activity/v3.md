# Activity V3：规模化与治理

> 状态：规划中（2026-08-22）。V3 建立在 Activity V2 已完成的 CommunityLog 产品读取面之上，专注于规模、长期统计、治理和更多事件来源；不改变 V1/V2 的事实写入边界与安全投影原则。

## 1. 目标

V2 已解决“能否安全查看和追溯 Activity”的产品问题。V3 解决数据量增长后的稳定性、长期分析和运营治理问题：

- 在真实性能证据支持下提升列表与统计查询的规模上限；
- 支持长期趋势和多维统计，而不把 rollup 变成事实来源；
- 建立 retention、归档、告警和审计报告能力；
- 扩展 Accounts、Jobs 等领域的 Activity producer。

## 2. 候选范围

### 2.1 分页与查询规模

- 在 offset pagination 出现重复、遗漏或响应时间问题时，引入 cursor/keyset pagination；
- 继续使用稳定排序键，处理相同 `occurred_at` 下的确定性顺序；
- 根据 `EXPLAIN (ANALYZE, BUFFERS)` 和代表性数据调整聚合查询与索引；
- 不为尚未出现的筛选组合预先创建索引。

### 2.2 长期统计

- 只有实时七表聚合达到性能阈值后，才增加可重建的 daily rollup/projection；
- 增加周/月趋势；
- 增加星期 × 小时热力图等二维统计；
- rollup 必须能从原始 Activity 重算和校正，不能替代原始事件。

### 2.3 治理与运营

- retention 与归档策略；
- 告警规则和周期审计报告；
- 明确敏感事件、导出权限和审计留痕；
- 大规模导出改为异步任务，并定义任务状态、下载有效期和权限边界。

### 2.4 Producer 扩展

- Accounts、Jobs 等领域接入统一 Activity producer；
- 新 producer 必须遵守 action contract、surface、classification、high-risk 和 retention 声明；
- 保持 `Activity.log/3` 为统一写入口，不由 Dashboard 直接写日志。

## 3. 进入条件

V3 的每项能力都应由可复现证据触发，而不是按预估规模提前实现：

- 以 30/90 天代表性数据记录 list/stats 的响应时间、排序和 IO；
- 证明实时聚合已经成为数据库热点后，再引入 rollup；
- 证明导出规模超过同步接口边界后，再切换异步任务；
- 为 retention、归档和告警先定义权限、审计和恢复边界。

## 4. 非目标

- 不复制 CommunityLog 建立无法重算的第二事实源；
- 不把所有维度组合预先物化成万能统计表；
- 不因为新增 producer 而绕过现有 CMS、Community 和 Article 权限；
- 不在没有性能或治理证据时提前引入复杂基础设施。
