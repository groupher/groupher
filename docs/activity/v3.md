## 1. 背景

V1 已解决 Activity 事实从哪里写、如何分表保存、如何通过安全 surface 读取：

```text
领域 command / writer
  -> Activity.log(resource, action, opts)
  -> activity.<resource>_logs
  -> ArticleLog / CommunityLog safe projection
```

V2 已把 CommunityLog 产品化：

- `/[community]/activity` Dashboard 页面；
- 自然语言事件时间线；
- resource、action、category、actor、source、subject 和时间筛选；
- Activity Overview 日统计；
- `operation_ref` 分组、`parent_event_ref` 关系和事件深链接；
- JSON / CSV 导出；
- `audit.read` 权限和 action-owned payload / metadata 投影。

V2 回答的是：

```text
管理员能否安全查看、筛选和追溯已经记录的 Activity？
```

V3 回答的是：

```text
当管理员、安全负责人或审计人员拿着一个具体问题来时，
现有事件是否完整、可查询、可解释、可导出，并且其保留与完整性是否可以证明？
```

典型问题不是“让我看看日志”，而是：

```text
谁执行过永久删除？（默认查看最近 30 天，可由用户调整）
一次 Community 销毁包含哪些步骤，是否全部成功？
哪些高风险操作被 Gate 或 Passport 拒绝？
谁修改过发布、Press 或权限配置，具体改了哪些字段？
某个成员被移除后，是否仍尝试访问或操作 Community？
谁导出了 Activity，导出的范围是什么？
```

这些问题暴露了 V1/V2 尚未覆盖的能力：被拒绝的尝试、更多 actor 类型、可索引的变化字段、覆盖起点、审计自身、保留与擦除，以及从问题到结构化 filter 的稳定映射。

### 1.1 外部文章具体带来了什么

V3 不是从“证据语义”“治理控制”等抽象分类出发另造一套架构。它直接回应参考文章提出的五个具体问题：

| 文章的论点                                               | Groupher 当前情况                                                                                    | V3 的具体动作                                                                                                                                   |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 每个 schema 字段都应帮助回答未来的问题                   | 已有 actor、action、subject、target、operation 和时间，但不能查询拒绝结果、拒绝原因和变化字段        | 增加受控的 `outcome`、`denial_code`、`changed_fields`、actor type 和 operation 内顺序                                                           |
| 事件必须在 service / domain 写入，并与业务变更一起提交   | V1 已要求领域层通过 `Activity.log/3` 原子追加                                                        | 保持现有成功路径；逐个验证 producer 与 transaction；Gate / Passport / Auth 只返回 typed decision，围绕 decision 的领域 command 负责写入拒绝事件 |
| 没有 denied attempts 的日志只有一半                      | 当前 Activity 主要记录已经成功发生的业务事实                                                         | 首批记录破坏性操作、Activity 导出和关键权限操作的拒绝，不把所有普通 read miss 写成日志                                                          |
| 秘密必须在写入前排除；snapshot 需要独立擦除生命周期      | 当前 contract 已限制 payload / metadata，但 actor snapshot 的 PII 擦除和数据库权限尚未形成可证明方案 | 增加 secret rejection tests，拆分稳定 ref 与显示身份，并在字段拆分或 per-subject encryption 之间做出实现选择                                    |
| 审计日志是拿着具体问题查询的产品，而不是供人浏览的一堆行 | V2 已有结构化 filter、详情和导出，但入口仍然主要是资源/action 筛选器                                 | 增加“谁永久删除过内容”“一次 Community 销毁发生了什么”“哪些高风险操作被拒绝”等内置问题预设                                                       |

文章末尾另外提出 no backfill、retention、clock discipline、持续监看、数据库强制 append-only 和 offboarding evidence。它们分别对应 V3 的 coverage 起点、retention policy、`occurred_at / recorded_at`、高风险告警、数据库 role，以及 offboarding 问题预设。

因此后文几组能力不是四个彼此独立的大项目，而是一条连续链路：

```text
管理员提出一个具体问题
  -> 问题预设展开成结构化 filter
  -> filter 需要 outcome / actor / changed fields 等可查询事实
  -> producer 必须在正确的业务或拒绝边界完整写入这些事实
  -> snapshot、retention 和数据库权限保证这些事实长期安全可用
  -> 数据量真正增长后，再优化分页、统计和导出
```

## 2. V3 设计结论

V3 固定以下决策：

1. `GroupherServer.Activity` 继续是唯一顶层 Phoenix Context，公共业务写入口继续是 `Activity.log(resource, action, opts)`；
2. 成功业务事件继续由领域 command / writer 在与权威业务变更相同的数据库事务中追加；
3. Gate、Passport 和 Auth 继续只返回 typed decision，不直接依赖 Activity；围绕该 decision 的领域 command / service 负责同步追加需要审计的拒绝事件，不能由 Dashboard、Resolver 或事后数据库扫描补写；
4. `action` 表达尝试执行的领域动作，拒绝不能退化成统一的 `permission_denied` action；拒绝原因进入稳定 `denial_code`；
5. Activity 继续只记录需要长期证明的产品与安全事实，不吸收 Logger、Telemetry、普通 page view、轮询、健康检查或全部 Oban 执行明细；
6. V3 扩展现有 action contract，而不建立独立的全局 DTO、任意事件 API 或第二套 action registry；
7. `payload` 继续由 action 显式声明安全字段；V3 不增加所有 action 共用的无约束 `before / after` JSON；
8. 对确实需要回答“什么字段发生变化”的 action，增加受 contract 约束、可索引的 `changed_fields`，具体旧值和新值仍留在 action-specific payload；
9. `source` 表达入口，`actor_type` 表达责任主体，两者不能互相替代；
10. Account、API key 和 job 等已有执行主体进入统一 actor 模型，不再全部压成 `system`；delegation 与 impersonation 通过 `on_behalf_of` 表达，不伪装成 actor type；没有真实 producer 的 actor type 不提前进入 closed enum；
11. Groupher 已有 `subject / target` 语义继续承担“动作影响了谁或什么”，不复制外部产品的通用 `affected_user` 字段；Account 事件以 User / API Key 作为 subject 或 target，并提供对应精确筛选；
12. V3 的核心产品入口是“审计问题预设”：每个预设由后端声明稳定问题、所需事件与结构化 filter，不建立 payload / metadata 全文搜索；
13. 预设最终展开为普通 Community Activity filter；列表、统计和导出继续复用同一权限、surface 与 filter normalization；详情按 event ref 使用现有安全 projection；
14. Activity 导出、retention 修改、身份擦除和告警配置修改本身也是需要记录的 Activity；普通列表、详情读取、翻页和轮询在首版不写 self-audit；
15. 不伪造 V1 之前的历史事件。V3 明确每个 action / producer 的可证明覆盖起点，并在查询和导出中暴露覆盖限制；
16. append-only 不能只靠代码约定；V3 定义 runtime、migration、maintenance 三类数据库能力边界，并验证普通运行角色不能更新或删除 Activity；
17. 身份 snapshot 与业务事实使用不同生命周期。秘密在写入前排除或脱敏；个人显示信息只能通过受审计的精确擦除或密钥销毁失效；
18. retention 由 action contract 引用稳定 policy，不在每条 event 中复制会变化的天数；归档或过期不能让产品投影成为第二事实源；
19. 高风险告警是 Activity 的提交后消费者，不能阻塞或反向修改原始 Activity；
20. cursor、rollup、异步导出和归档存储只在可复现性能或容量证据出现后进入实现，不提前建立复杂基础设施。

### 2.1 首轮实现只跑通一条基础链路

V3 第一轮只交付：

```text
业务 command
  -> allowed / denied Activity 事实
  -> CommunityLog.Filter.resolve
  -> list / stats / detail / export
  -> activity_exported
```

必须完成最终 event envelope、`user / system` actor normalization、现有 allowed 与首批 `user` denied producers、统一 applied filter、简单 preset、Dashboard 基本交互以及 fail-closed export manifest。首轮直接使用最终 `actor_type + actor_ref` envelope，不保留旧 `actor_id` 过渡模型；`anonymous / api_key / job` 在各自真实 producer 接入时于 V3.1 内逐步补齐。详情读取审计、新 retention 分类和所有规模化能力不进入首轮；数据库 roles、identity lifecycle、retention executor 与告警在基础链路跑通后进入治理硬化。

首轮是横跨 V3.1 事实层与 V3.2 查询层的最小竖切片；§12 描述能力演进顺序，不是另一份独立交付计划。V3.3 治理与 V3.4 规模化不进入首轮。

实现状态（2026-08-24）：最终 envelope、`user / system` actor、首个 Article Gate denied producer、统一 selection / applied filter、五个简单问题 preset、list / stats / detail、Dashboard 入口以及带 manifest 的 fail-closed export 已接通。数据库 roles、identity lifecycle、retention executor、告警和规模化能力仍未实现，不能从首轮状态推断这些治理保证已经成立。

## 3. 用户拿着问题来：问题预设与查询

### 3.1 问题预设不是静态快捷按钮

V2 已提供结构化筛选器。V3 在其上增加面向取证问题的 preset registry：

```text
Activity question preset
  -> immutable semantic key
  -> product question / description
  -> required permission
  -> required actions and query fields
  -> base CommunityActivityFilter
  -> list / stats / export
```

预设不维护自己的查询实现，也不能绕过 CommunityLog：

```text
Dashboard preset
  -> server resolves preset to normalized filter
  -> audit.read + Community boundary
  -> active :community_log actions
  -> CommunityLog list / stats / export
```

Preset 不建立版本状态机或保存视图模型。运行时只有一条解析链路：

```text
preset key
  -> immutable preset base filter
  -> AND optional user narrowing filter
  -> permission + coverage + filter normalization
  -> applied filter
```

用户条件只能与 preset base filter 取交集，不能扩大 preset。用户需要任意修改核心 action / outcome 时，应显式清除 preset 后使用普通自定义筛选；不建立额外的 preset 状态机。

每个 preset 至少声明：

```text
key
question_key
description_key
default_time_range
filter
required_actions
required_query_fields
required_permission
coverage_note_key
```

Preset key 是不可变的语义 ID。翻译和非语义说明可以更新；required actions、核心 filter 或问题含义变化时必须发布新 key，例如 `destructive_actions_v2`，不能原地改变旧 key。旧 key 不再提供时返回 `PRESET_UNAVAILABLE`。证据稳定性由 `preset key + question_key + applied_filter + coverage` 保证，不建立额外修订协商协议。

`default_time_range` 只是缺省查询窗口，不是 preset base filter 的强制条件：只有用户同时未提供 `occurredAfter` 和 `occurredBefore` 时，后端才将它物化为具体 UTC 边界并返回 `appliedFilter`；用户提供任一时间边界后，不再部分套用 preset 默认窗口。Question 文案不能把默认窗口写成不可变问题语义，实际时间范围始终以 AppliedQuery 展示的 applied filter 为准。

### 3.2 首批问题预设

#### Destructive actions

```text
问题：谁执行或尝试执行了永久删除、终止 blocker 或 Community destroy？

filter:
  actions = permanently_deleted, blocker_terminated, destroyed
  outcomes = allowed, denied
```

#### Community destruction trail

```text
问题：一次 Community 销毁包含哪些步骤，执行者和最终结果是什么？

入口：operation_ref 或 destroy_scheduled event_ref
结果：destroy_scheduled / destroy_cancelled / destroyed / lifecycle_reconciled
展示：operation 分组 + parent / child relationship
```

#### Publishing and configuration changes

```text
问题：谁修改过发布、Press 或 Docs 配置，具体改变了哪些字段？

filter:
  categories = publishing, community
  actions = config_updated, published, publish_restored,
            released, release_rescheduled, release_withdrawn
  changed_fields = optional exact field names
```

#### Denied high-risk attempts

```text
问题：哪些高风险动作被系统拒绝，由哪条 policy 拒绝？

filter:
  outcomes = denied
  high_risk = true
  denial_codes = optional stable codes
```

#### Actor trail

```text
问题：某个 User、API key 或 job 直接做过什么，某个 User 又曾被谁代表操作？

filter:
  actor_ref
  actor_types
  on_behalf_of_ref
  occurred_after / occurred_before
```

#### Offboarding evidence

```text
问题：成员何时被移除、其 session 何时失效、之后是否仍有被拒绝的尝试？

事件来源：
  Accounts membership removal
  Auth session revocation
  Gate / Auth denied attempts

关联：
  同一 offboarding command 共享 operation_ref；
  后续 denied attempts 通过 subject ref 和时间范围查询，不伪造 parent 关系。
```

#### Activity export

```text
问题：谁导出过 Activity，导出的范围是什么？

actions:
  activity_exported
```

普通 Activity 列表、详情、翻页和 30 秒轮询不写 self-audit，否则审计写入会成为取证读路径的可用性依赖。V3 首版只审计会产生产物的 export command；详情读取审计等真实安全需求出现后再单独设计。

### 3.3 查询规则

- preset 只组合已声明的结构化字段，不能生成任意 SQL 或 JSON path；
- 未知 preset key 返回稳定 `PRESET_UNAVAILABLE`；未知 action、actor type、denial code 或 changed field 同样必须被拒绝；
- preset 所需 action 尚无 active producer 时，页面必须显示 coverage limitation，不能用空结果暗示“从未发生”；
- preset、手动筛选与 URL 可以组合，但组合规则必须由后端规范化并返回最终 applied filter；
- preset base filter 与用户条件在任一结构化维度上的交集为空时，请求仍是合法零结果，但 `queryContext.presetIntersectionEmpty = true`；Filter 可以直接短路而不执行 SQL，UI 必须提示用户清除冲突筛选或退出 preset，不能只展示无法解释的空白列表；
- 空交集只能在 enum / ref validation 与 contract-derived filter 展开完成后计算，例如先将 `high_risk / category` 展开为当前 surface 的 action 集合，再与用户 actions 求交集；不能在语义展开前比较原始输入并误判；
- URL 使用公开 ref、稳定 enum 和 preset key，不暴露数据库 ID；
- Subject 模糊查询仍只作用于 contract 允许的 snapshot title；User、API key 和 operation 查询使用精确 ref；
- 不增加跨 payload、metadata、snapshot 的任意全文搜索。

## 4. 为了回答这些问题，事件还缺哪些字段

下面八个字段不是为了“多存一些信息”，而是分别回答八个不同问题：

| 字段              | 回答的问题                                           | 写入规则                                                                                                                                                                                                                                               | 示例                                                                              | 不能表达什么                                                |
| ----------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `outcome`         | 这次动作尝试被允许还是被拒绝？                       | 持久化 envelope 必填 closed enum：`allowed / denied`；调用 `Activity.log/3` 未传时由 facade 规范化为 `allowed`，数据库列本身不设默认值。`allowed` 表示该 producer 所负责的权威动作已经提交；异步动作被接受时，只表示“调度成功”，不表示后台任务最终成功 | `community_destroy_scheduled + allowed`                                           | 不是资源当前状态，也不是 job 的生命周期状态                 |
| `denial_code`     | 为什么这次动作被拒绝？                               | `allowed` 时必须为空；`denied` 时必须是该 action contract 声明过的稳定 machine code，由 Gate / Passport / Auth decision 提供                                                                                                                           | `insufficient_role`、`community_locked`                                           | 不是本地化文案、异常 message、HTTP status 或 stacktrace     |
| `changed_fields`  | 这次成功动作改变了哪些可查询字段？                   | action-owned、有限集合；只保存 contract allowlist 中的字段名。无字段 diff 语义的 action 使用空数组                                                                                                                                                     | `["role", "expires_at"]`                                                          | 不是完整 diff，不保存字段值、正文、secret 或任意 JSON path  |
| `actor_ref`       | 哪个直接执行主体应对这次动作负责？                   | 与 `actor_type` 组成 typed ref；使用可公开、稳定的领域 ref，不使用 User DB id。系统 actor 也必须有稳定 ref                                                                                                                                             | `actor_type=user, actor_ref=u_xxx`；`actor_type=job, actor_ref=community-destroy` | 不是入口来源；`source=api` 不能代替 actor，也不表示被代表者 |
| `on_behalf_of`    | 直接 actor 是代表谁行动的？                          | 可选的 `type + ref + snapshot` 三元组；delegation 或 impersonation 时填写。实际 operator / credential 始终留在 actor 中                                                                                                                                | 支持人员代用户操作：`actor=user:operator`，`on_behalf_of=user:customer`           | 不是第二个共同 actor，也不能覆盖或隐藏实际执行者            |
| `recorded_at`     | 这条证据何时真正进入 Activity？                      | 数据库生成的 UTC 时间，producer 和客户端不能指定                                                                                                                                                                                                       | worker 10:05 补记 10:00 发生的事实：`recorded_at=10:05`                           | 不是领域事实发生时间；后者由 `occurred_at` 表达             |
| `operation_index` | 同一个 command 产生的多条事件，其领域顺序是什么？    | command owner 从 `0` 开始稳定分配；单事件 command 为 `0`。跨表一致性由 producer contract 和测试保证                                                                                                                                                    | destroy command：scheduled=`0`、resources_removed=`1`、destroyed=`2`              | 不是数据库全局顺序，也不能用于比较两个不同 operation        |
| `record_sequence` | 七张资源表中的事件在数据库层如何获得稳定 tie order？ | 共享数据库 sequence 自动生成；全局单调、允许有空洞，producer 和客户端不能指定                                                                                                                                                                          | 两条事件 `occurred_at` 相同时，以较大的 sequence 排在后面                         | 不是无间断计数器、领域时间、operation 顺序或公开业务 id     |

其中 `on_behalf_of` 在数据库中不是一个 JSON 字段，而是以下 nullable typed identity：

```text
on_behalf_of_type
on_behalf_of_ref
on_behalf_of_snapshot
```

type 与 ref 必须同时存在或同时为空；snapshot 只用于受控显示，不参与身份判断。

### 4.1 Outcome 与拒绝原因

V3 为需要审计拒绝的 action 增加：

```text
outcome
  allowed
  denied

denial_code
  nil for allowed
  stable domain decision code for denied
```

约束：

- `allowed` 事件必须 `denial_code = nil`；
- `denied` 事件必须具有 action contract 允许的 `denial_code`；
- `denial_code` 使用 Gate / Passport / Auth 已有稳定领域原因，不保存本地化文本、异常 message 或 stacktrace；
- 拒绝事件描述“谁尝试对什么做什么”，不能创建不存在的成功业务 snapshot；
- 对恶意高频认证流量，Accounts / Auth 先定义聚合、限流和 retention 边界，不能把无限攻击流量未经控制地写入 CMS Activity 表；
- 业务写入在事务内失败时，不写一条伪造的 `allowed` Activity；是否记录领域 validation denial 由该 action contract 显式决定。

V3 不把所有 `{:error, reason}` 自动转成 Activity。只有权限、身份、敏感配置、数据导出、破坏性操作或正式治理流程中需要证明的拒绝才进入 Activity。

### 4.2 Actor 模型

V3 actor 类型候选集合：

```text
user
anonymous
system
api_key
job
```

含义：

- `user`：用户直接执行；
- `anonymous`：尚未认证的外部请求，只允许用于 action contract 明确声明、具有容量保护的认证或高风险拒绝；使用固定稳定 ref `anonymous`，不伪装成 `system`；
- `system`：无独立外部身份的 Groupher 系统行为；
- `api_key`：明确的机器 credential，snapshot 包含稳定 key ref 和受控名称；
- `job`：正式后台 command 的执行主体，snapshot 包含稳定 job type，不保存原始 args；

`impersonation` 不是 actor type，而是代表关系：支持或运维人员进入另一用户上下文时，`actor` 保存实际 operator，`on_behalf_of` 保存被代表用户。UI 可以根据该关系展示“operator 代表 customer 操作”，但不能把事件显示成 customer 本人直接操作。

`source` 继续使用 `api / admin / worker / scheduler / maintenance` 等入口值。未来出现具有稳定身份、真实 producer 和责任语义的新执行主体时，再扩展 closed actor enum；不能因为示例或潜在功能提前加入类型。

Actor snapshot 必须具有按 type 定义的 schema 和暴露 surface。禁止把完整 token、job args、OAuth profile 或 request headers 放入 snapshot。

匿名请求不保存原始 IP、完整 User-Agent、登录凭据或可逆设备指纹；受控 request ref 可以进入声明过的 metadata。高频攻击仍进入限流、聚合安全事件或 telemetry，不能逐条灌入 Activity。平台级 login denied 只有在 Accounts Activity stream 具备独立表与读取权限后才能进入正式 Activity。

### 4.3 Subject、Target 与被影响主体

V3 不新增通用 `affected_user` 列。现有语义足以表达：

```text
成员角色修改
  resource = community
  subject = member user
  actor = administrator

API key scope 修改
  resource = community
  subject = api key
  actor = owner

impersonation
  actor = operator user
  on_behalf_of = customer user
  subject = accessed customer resource
```

查询层增加精确 `subject_ref / target_ref` 能力，并可在产品文案中将特定 subject type 展示为“受影响成员”。领域 action contract，而不是公共 envelope，决定 subject 和 target 的含义。

### 4.4 Changed fields

`changed_fields` 是可查询的字段名集合，不是新的状态事实或任意 diff：

```text
action = member_role_updated
changed_fields = [role]
payload = %{old_role: :member, new_role: :admin}
```

约束：

- action contract 声明允许的 changed field enum；
- 写入值必须是该 allowlist 的子集；
- payload 中的 old/new 字段继续单独声明 accepted / exposed fields；
- password、token、secret、完整正文、完整 request body 永远不能进入 old/new payload；
- 正文变化记录 revision ref、hash 或安全摘要，正文版本继续由 Draft / Revision / Snapshot owner 保存；
- 不要求 `created`、`trashed`、`comment_pinned` 等没有字段 diff 语义的 action 填充 changed fields。

### 4.5 时间与顺序

V3 区分：

```text
occurred_at
  领域事实发生时间；默认由 Activity facade 使用服务器 UTC 时间生成

recorded_at
  Activity 在数据库实际追加时间；由数据库生成

operation_index
  同一 operation_ref 内的稳定事件序号

record_sequence
  由 activity schema 的共享数据库 sequence 生成，
  表达跨 resource table 的全局追加顺序
```

当前实现用于确定 event ref 的 `event_sequence` 在 V3 收口为持久化 `operation_index`，以证明一个复合 command 内事件的顺序。它不是跨全部分表的全局 sequence。

Action contract 必须声明 `occurred_at_policy`：

```text
server_now
  默认策略；api / admin / 普通 command 不接受调用方时间

bounded_producer(max_past, max_future)
  仅供明确声明的 worker / scheduler 使用；允许根据权威业务事实补记
```

规则：

- 普通同事务事件的 `occurred_at` 与 `recorded_at` 通常接近，但读取协议不能假定两者永远相等；
- GraphQL、REST 和浏览器客户端不能指定 `occurred_at` 或 `recorded_at`；
- 默认 `server_now` 在 `Activity.log/3` 内生成 `occurred_at`，不能直接采用 payload 中的时间；
- `bounded_producer` 只接受已通过 actor、source 和 action contract 校验的内部 producer；每个 action 单独声明最大回溯窗口，不能共享一个无限的“可信”豁免；
- 所有策略都必须满足 `occurred_at <= recorded_at + 60 seconds` 的数据库约束，允许有限 clock skew，但不能写入任意未来时间；
- 超出 contract 回溯窗口或未来容差时拒绝 append，并记录 operation telemetry，不静默截断时间；
- `operation_index` 由拥有整个 command 的 producer 从明确起点递增分配；跨七张资源表的一致性由 contract 与 producer tests 保证，不伪装成单表数据库约束；
- `record_sequence` 由数据库生成，producer 和客户端都不能指定；
- Community 全局列表使用 `(occurred_at, record_sequence)` 作为稳定排序基础；`record_sequence` 解决跨七表 tie order 和未来 cursor 身份，不冒充领域发生时间。

## 5. 在哪里写，怎样保证没有漏记

### 5.1 Allowed event

```text
BEGIN
  authoritative business mutation
  Activity.log(... outcome: allowed ...)
COMMIT
```

- 业务写入成功但 Activity append 失败：事务回滚；
- 业务写入失败：不产生成功事件；
- Notification、Search、告警和 report projection 是提交后消费者，不能反向修改 Activity；
- 跨数据库或跨服务写入只在真实需要出现时引入 outbox；outbox 必须保证 mutation 与待发送事实同事务提交。

### 5.2 Denied event

```text
request / command
  -> Gate / Passport / Auth decision
  -> denied
  -> domain command appends denied Activity
  -> return original domain denial
```

Gate、Passport 和 Auth 保持纯 decision owner；收到 typed decision 的领域 command / service 是 denied Activity producer。这样既避免 Controller 重复记录，也避免 `CMS.Gate -> Activity -> CMS.Gate` 的上下文循环依赖。要求：

- 相同拒绝不能被 Resolver、Context 和 Gate 重复写三次；
- Gate / Passport 不能为了审计产生数据库副作用，也不能反向依赖 Activity；
- 高风险 command 必须在同一个服务入口统一处理 allowed 与 denied，不能让 REST、GraphQL、job 等入口各自补日志；
- 审计 append 失败时的产品行为必须按 action 风险定义：高风险管理操作默认 fail closed；高容量认证拒绝可以进入受控安全事件管道，但不能静默假装已经审计；
- denied event 不改变业务状态，也不能为了复用成功 action handler 构造不存在的 resource；
- Gate / Passport 继续拥有授权语义；Activity 只记录 decision fact，不成为第二个授权系统。

### 5.3 Producer coverage

V3 为每个 active action 建立 producer coverage：

```text
action
producer module / command
allowed producer status
denied producer status
atomicity
coverage_started_at
coverage_deploy_ref
required actor types
query fields
```

Coverage registry 可以由 contract 与测试生成，但不能手写一份会独立漂移的宣传清单。

规则：

- 不把当前数据库状态反推为历史事件；
- 未覆盖的时间段在页面、preset 和 export manifest 中明确标记；
- action 只有在 producer 已接入并通过 atomicity / projection 测试后才能标记 active；
- denied coverage 与 allowed coverage 分开声明，不能因为成功路径 active 就声称拒绝路径完整；
- actor coverage 只覆盖 contract 与 producer 已实际支持的 actor types；`user` 路径 active 不能推导 `anonymous / api_key / job` 已覆盖；
- deploy ref 用于证明覆盖从哪个可部署版本开始，不作为业务查询条件。

## 6. 敏感信息怎样安全保留或擦除

### 6.1 Write-time redaction

秘密必须在 Activity 写入前被排除或替换：

```text
never store
  token
  password
  session cookie
  complete authorization header
  webhook secret
  OAuth credential
  complete private document body
```

UI display-time masking 不是安全边界。Action contract 必须在 accepted payload / metadata / snapshot 层拒绝未声明字段，测试覆盖典型 secret key 和嵌套 payload。

### 6.2 Identity lifecycle

Activity 必须在用户、API key 或资源删除后仍可解释，因此稳定 ref 与显示身份分开处理：

```text
stable ref
  保留，用于证明多条事件属于同一历史主体；它仍可能是 pseudonymous identifier

display identity
  nickname / login / avatar / key name 等受控 snapshot，具有独立擦除生命周期
```

Identity lifecycle 覆盖全部可能承载显示身份的 snapshot，而不只覆盖 actor：

```text
actor_snapshot
on_behalf_of_snapshot
subject_snapshot
target_snapshot
stream_snapshot
```

每种 snapshot contract 必须声明其中的 display-identity slots。Stable ref 不进入这些 slots，也不参与显示身份擦除。可擦除 display identity 不能为了绕过生命周期规则随意进入 payload / metadata；确需保存时，action contract 必须显式声明其 identity classification 和相同的擦除路径。

当前 snapshot 是 map，数据库无法仅靠列级权限证明只能擦除其中的 PII 而不能改写 stable id。V3 在实现擦除前必须为上述全部位置选择并验证一种精确模型：

1. 将全部 stable refs 与可擦除 display identity 拆为独立持久化字段，并让 maintenance role 只能更新声明过的 display-identity slots；或
2. 使用 per-subject key 加密 display identity，擦除时销毁密钥，Activity row 不更新。

在选择完成前，不宣称现有 JSON snapshot 已具备合规的精确擦除能力。

每次身份擦除必须产生独立 Activity，记录执行人、subject ref、擦除字段类别和 operation ref，但不能再次保存被擦除的原值。

### 6.3 Database roles

目标权限模型：

```text
migration role
  owns schema and migrations

runtime role
  SELECT + INSERT Activity
  no UPDATE
  no DELETE

maintenance / erasure role
  only the selected narrow identity-lifecycle operation
  no row DELETE
  every use produces Activity

retention executor
  no normal application access
  execute-only access to reviewed retention procedure / partition operation
  cannot delete rows outside the resolved policy and cutoff
  every execution produces a manifest and longer-retained Activity
```

迁移、部署和本地开发是否暂时共用连接不是产品保证。生产环境必须有可验证的 grant / revoke、自动检查和失败测试，使 append-only 从代码约定升级为数据库支持的事实。

Retention 不复用 maintenance / erasure role，也不给 runtime Repo 临时升级权限。初期按行过期时，由独立 retention executor 调用受控数据库 procedure；未来采用分区时，由同一边界执行已验证的 partition archive / drop。执行 manifest 至少记录 policy、cutoff、Community / table 范围、归档与删除数量、executor、operation ref 和执行结果，并进入保留期更长的治理流。

### 6.4 Retention 与归档

Action contract 的 retention 从单一 `:long_term` 扩展为稳定 policy ref，例如：

```text
security_critical
product_history
```

首版只保留两档：denied、Activity export、retention、identity 和其他安全治理事实进入 `security_critical`；普通成功业务历史进入 `product_history`。具体 action 出现可证明的独立保留期或访问边界后，再新增 policy key，不能预先建立 taxonomy。

Policy 定义：

- 在线查询窗口；
- 总保留期；
- 是否允许归档；
- 归档访问权限；
- 擦除方式；
- 到期执行和验证方式。

具体天数属于 policy 配置，不复制进每条 event。修改 policy 必须记录 Activity，但不改写历史 event 的 action contract snapshot。

归档仍是原始 Activity 的生命周期阶段，不是新的产品事实源。任何 rollup 或 CommunityLog projection 必须可以从仍在保留范围内的原始事实重算；归档读取能力和恢复边界在执行删除前完成验证。

## 7. 谁导出了 Activity，以及何时需要告警

### 7.1 Self-audit

首批 self-audit action：

```text
activity_exported
```

Retention、identity erasure 和 alert rule 修改仍分别记录为治理事实，但它们不是 Activity 读取 self-audit。V3 首版不记录详情查看事件，也不把详情 query 改造成写 command。

`activity_exported` payload 只保存：

```text
format
query context summary:
  preset key + question key, if any
  applied filter
exported_count
coverage summary ref
```

它不能保存导出的 CSV / JSON 内容或用户无权再次读取的 snapshot。Export 是产生产物的 command：只有内容生成与 `activity_exported` append 都成功才返回下载结果，审计 append 失败时 fail closed。

列表、Timeline、OperationGroup 和详情继续使用 safe query projection，不产生写入副作用。若未来出现“谁查看了敏感详情”的真实安全需求，再单独决定 action 范围、容量、fail-open / fail-closed 和告警策略。

### 7.2 高风险告警

告警候选包括：

- destructive action allowed / denied；
- Community destroy scheduled / cancelled / completed；
- blocker terminated；
- API key scope widened；
- impersonation started；
- Activity export；
- retention、identity erasure 或 alert rule 修改。

告警规则消费已提交 Activity：

```text
committed Activity
  -> post-commit alert consumer
  -> alert rule
  -> delivery record / retry
```

首版复用现有事务型 job 或本地 post-commit projector，不因告警单独引入跨服务 outbox。只有出现跨数据库可靠投递需求并具备可复现失败证据时，才按 §5.1 的边界增加 outbox。

告警投递失败不能删除、更新或回滚原始 Activity。Delivery、retry 和 provider error 属于告警子系统的 operation record / telemetry；只有最终、具有产品或治理意义的结果才选择性进入 Activity。

### 7.3 Evidence export

V3 export 不只是 CSV / JSON rows，还要返回或附带 manifest：

```text
generated_at
generated_by
community_ref
preset                       nullable; immutable key + question_key
applied_filter               exact custom or resolved preset filter
preset_intersection_empty    derived warning; never coverage
timezone and time range
event count
coverage_started_at / limitations
schema version
```

Manifest 直接复用请求返回的 `queryContext { preset, appliedFilter, coverage, presetIntersectionEmpty }` 语义。使用 preset 时记录 immutable key 与 question key；纯手工查询使用 `preset = null`。Canonical evidence 是 `preset key + question_key + applied_filter + coverage`；空交集标记只解释为什么结果为零，不能冒充 coverage limitation。Manifest 不依赖可变化的翻译文本，也不保存 preset 修订号、状态机或生成时的本地化文案。

空交集不禁止用户显式导出：export 可以跳过 row query、生成合法零行文件，并按正常 fail-closed 边界记录 `activity_exported`；manifest 的 `presetIntersectionEmpty = true` 解释零行原因。List、stats 和 export 必须返回一致的 applied filter 与空交集标记。

Manifest 证明“这份结果回答了什么问题、使用了什么条件、覆盖从何时开始”，但不声称 Groupher 因此自动满足某个合规标准。

当同步导出超过 V2 的 5,000 条上限或响应时间目标时，再切换为异步 export job。异步导出需要：

- stable operation ref；
- requester 与 `audit.read` 权限快照；
- 生成时再次执行权限和 Community boundary；
- 明确状态、失败原因和重试；
- 有效下载期与撤销；
- 导出完成和下载的审计记录；
- 不把完整导出文件写回 Activity payload。

## 8. 从审计要求到可执行查询

V3 可以建立“控制陈述到事件证据”的内部映射，但不建设通用 compliance 产品：

```text
control statement
  -> required actions
  -> required fields
  -> producer coverage
  -> question preset
  -> sample evidence export
```

示例：

```text
权限变更可追溯
  -> member_role_updated / api_key_scopes_updated
  -> actor + subject + changed_fields + payload old/new
  -> privilege_changes preset

访问撤销可证明
  -> member_removed / auth_sessions_revoked
  -> shared operation_ref
  -> offboarding_evidence preset

破坏性操作受控制
  -> permanently_deleted / destroyed
  -> outcome + denial_code
  -> destructive_actions preset
```

每条 mapping 必须诚实说明 Activity 不能证明的部分。例如 Activity 可以证明“角色被谁改成什么”，不能证明这次变更经过了组织外部审批；若审批存在，正式 approval / ticket ref 必须在 command 时通过受控 metadata 写入。

自动测试至少验证：

- mapping 引用的 action 存在；
- required action 具有 active producer 或明确 coverage limitation；
- preset 可通过公开 filter 表达；
- required fields 对 CommunityLog surface 可见；
- sample query 对 fixture 返回预期 allowed、denied 和空覆盖结果。

## 9. 数据量增长以后再做什么

### 9.1 Cursor / keyset pagination

V2 继续使用 offset pagination。只有出现以下证据时，V3 才实现 cursor：

- 翻页期间新事件导致可复现的重复或遗漏；
- 深分页超过响应时间目标；
- `UNION ALL + count(*) + OFFSET` 的排序或 IO 成为热点。

Cursor 必须包含完整稳定排序 tuple，覆盖相同 `occurred_at` 和跨 resource table 的情况。不能只编码 timestamp，也不能把 opaque cursor 解释成公开业务 ref。

最终切换协议需要：

- 直接用 cursor 替换 page 参数和 offset 查询，不保留双参数兼容窗口；
- list 与 export 不共享错误的分页上限；
- 新事件提示不会重置或重复当前 cursor window；
- 相同 filter 下无重复、无遗漏的并发插入测试。

### 9.2 Query 与索引

使用 30 / 90 / 365 天代表性数据测量：

- 全 resource 与单 resource；
- 单 action、多 action、category；
- actor type / actor ref；
- allowed / denied 与 denial code；
- changed fields；
- subject / target exact ref；
- operation ref；
- preset 的真实组合。

所有索引由 `EXPLAIN (ANALYZE, BUFFERS)` 和目标延迟驱动。不能为所有维度排列组合提前创建索引，也不能仅因为查询倒序就重复一个 PostgreSQL 已能 backward scan 的 B-tree。

### 9.3 Stats 与 rollup

只有实时七表聚合达到性能阈值后，才增加可重建 rollup：

- 周 / 月趋势；
- allowed / denied 趋势；
- category / actor type / high risk 分布；
- 星期 × 小时热力图；
- preset 所需的稳定统计。

Rollup 必须：

- 从原始 Activity 重算；
- 支持窗口重建和定期校正；
- 继承 Community、surface 和 action visibility；
- 不保存比原始安全投影更宽的数据；
- 不成为当前状态或审计事实来源；
- 不预先物化所有维度组合。

## 10. 还需要接入哪些业务来源

V3 优先扩展能够回答治理问题的 producer，而不是追求 action 数量：

### 10.1 Accounts / Auth

- member invited / joined / removed；
- role updated；
- session revoked；
- MFA / SSO 等安全设置变化；
- 受控 login denied / blocked；
- API key created / scope updated / revoked；
- impersonation started / ended。

Accounts / Auth 继续拥有 credential、session 和 membership 状态。Activity 只保存受控责任事实。

### 10.2 Gate / Passport denied decisions

- 破坏性 CMS action denied；
- Community management permission denied；
- audit read / export denied；
- API key scope denied。

不能把所有普通资源不可见或 public read miss 写入 Activity。Denied registry 必须逐 action 明确审计价值和容量边界。

`audit.read / export denied` 只覆盖能够解析到真实 Community 的尝试：command 可以在授权前解析公开 Community ref，拒绝事件写入该 Community 的 `community_logs`，但响应仍返回原始 denial，不能泄露 Community 是否存在。Community ref 不存在或无法解析时不创建 Activity row，只进入限流安全事件 / telemetry。

V3 不允许以 nullable `community_id` 把平台事件混入七张 Community-scoped 表。真正不属于任何 Community 的 Account / platform admin 事实，必须等独立 handler、表和平台读取权限一起设计后再启用 producer。

### 10.3 Jobs

只记录正式业务结果或责任交接：

- setup 最终失败与重试发起；
- Community destroy 完成；
- import apply 完成或最终失败。

Oban attempt、调度延迟、临时 provider error 和每次 retry 继续属于 Jobs / Telemetry，除非某个最终结果本身是产品事实。

## 11. V3 最终实现架构

### 11.1 当前实现需要改变什么

V1/V2 的主干边界是正确的，V3 不重建 Activity：

```text
保留
  Activity Phoenix Context
  Activity.log(resource, action, opts)
  resource-specific append-only tables
  handler-owned action contracts
  ArticleLog / CommunityLog safe surfaces
  CMS-owned Gate / Passport
```

当前实现与 V3 目标之间的差异如下：

| 当前实现                                                                        | V3 问题                                                                           | 目标改动                                                                                                                             |

| Base schema 只有成功业务 envelope                                               | 不能记录或查询拒绝、变化字段、跨表稳定追加顺序                                    | 一次性加入 outcome、denial、changed fields、actor ref、delegation、operation index、record sequence 和 recorded time                 |

### 11.2 最终读写链路

Allowed command：

```text
GraphQL / internal API / job
  -> domain command
  -> Gate / Passport typed decision
  -> authoritative mutation transaction
       -> business state change
       -> Activity.log(... outcome: allowed)
  -> commit
  -> post-commit alert / projection
```

Denied command：

```text
GraphQL / internal API / job
  -> same domain command
  -> Gate / Passport typed decision = denied
  -> Activity.log(... outcome: denied, denial_code: decision.reason)
  -> return the original domain denial
```

Question preset read：

```text
Dashboard chooses ActivityQuestionPreset
  -> CommunityActivitySelectionInput
       optional preset key
       user narrowing filters
  -> CommunityLog.Filter.resolve
       -> lookup immutable preset base filter
       -> validate enums / refs
       -> expand contract-derived filters to action sets
       -> AND user narrowing filters
       -> normalize time and remaining fields
       -> audit.read + Community boundary
       -> Coverage.evaluate
  -> applied filter
       -> Query.list / Query.stats
       -> safe projections
  -> applied query + coverage + result
```

Export：

```text
Dashboard export command
  -> CommunityLog.Export.create
       -> resolve the same selection
       -> read bounded rows
       -> build content + evidence manifest
       -> append community.activity_exported
  -> return downloadable result
```

List、stats 和 export 不能各自实现 preset merge。`CommunityLog.Filter.resolve` 返回的 applied filter 是它们唯一共享的请求级派生结果，不额外建立持久化或公开的查询对象类型。

### 11.3 最终表结构

继续保留七张 resource-specific tables：

```text
activity.post_logs
activity.blog_logs
activity.changelog_logs
activity.doc_logs
activity.community_logs
activity.doc_tree_logs
activity.press_logs
```

不新增一张万能 `audit_events` 表。Community member、API key、Activity export、retention 等 Community-scoped action 优先进入 `community_logs`，通过 subject / target 表达受影响对象。七张表的 `community_id` 均为非空；能够解析到真实 Community 的 denied attempt 仍归入目标 Community，不存在或无法解析的 Community ref 不产生 Activity row。只有出现不属于任何 Community 或现有 resource stream 的正式产品事实时，才连同独立读取权限一起增加 handler 和表，不能把平台事件塞入 nullable Community envelope。

每张表的最终公共 envelope：

```text
id                         bigint local primary key, never public
community_id               Community scope
<stream>_ref               resource-specific stream ref
stream_snapshot

subject_type
subject_ref
subject_snapshot

target_type                nullable pair
target_ref
target_snapshot

actor_type
actor_ref                  stable public responsibility ref
actor_snapshot             display-only snapshot
on_behalf_of_type          nullable delegation / impersonation pair
on_behalf_of_ref
on_behalf_of_snapshot

action
outcome                    allowed | denied
denial_code                required only for denied
source

event_ref                  public event id + idempotency key
operation_ref
parent_event_ref

record_sequence            database-global append order

changed_fields             bounded string array
payload                    action-owned safe business data
metadata                   action-owned safe audit context

occurred_at                domain occurrence time
recorded_at                database append time
```

`outcome` 在最终 row 中始终非空，但默认值只存在于 `Activity.log/3` facade：现有成功 producer 可以省略并被规范化为 `allowed`；denied producer 必须显式传入 `denied + denial_code`。数据库列不设置 default，绕开 facade 的直接 insert 必须失败。

清理现有冗余：

- 删除 `hash_id`；GraphQL `id` 与深链接统一使用 `event_ref`；
- 删除只适用于 User 的 `actor_id`；公开、跨 actor 类型的稳定身份统一为 `actor_ref`；
- 删除 `inserted_at` 命名，直接使用只读 `recorded_at`；
- 不恢复已删除的 `correlation_ref`；command 归组继续使用 `operation_ref`，直接因果继续使用 `parent_event_ref`；
- retention policy 和 coverage 属于 contract / registry，不复制到每条 event row。

共享数据库 sequence：

```text
activity.record_sequence
  -> every resource table record_sequence DEFAULT nextval(...)
```

它只表示数据库追加顺序。业务时间仍由 `occurred_at` 表达；同一 command 内产品顺序由 `operation_index` 表达。

数据库约束至少包括：

- action、source、actor type 与 outcome 的 closed enum CHECK；
- `(outcome = allowed AND denial_code IS NULL) OR (outcome = denied AND denial_code IS NOT NULL)`；
- target type / ref 同时为空或同时存在；
- on-behalf-of type / ref 同时为空或同时存在；
- `occurred_at <= recorded_at + interval '60 seconds'`；数据库只提供统一的未来时间硬防线，不表达过去回溯窗口；action-specific 最大回溯窗口由 changeset / contract 收紧；
- `operation_index >= 0`；
- `changed_fields` 只能由 changeset / contract 写入允许值；
- 每表 `event_ref` unique；共享 record sequence 由数据库 sequence 保证跨表唯一来源。

首批必要索引：

```text
community_id + occurred_at DESC + record_sequence DESC
stream_ref + occurred_at DESC + record_sequence DESC
community_id + action + occurred_at DESC + record_sequence DESC
community_id + actor_type + actor_ref + occurred_at DESC
community_id + subject_type + subject_ref + occurred_at DESC
operation_ref + operation_index
GIN(changed_fields)
```

Outcome / denial code 的组合索引仍以首批 preset 的 query plan 决定；不能因为新增字段就预先物化所有组合。

### 11.4 Action contract 最终形状

Handler 的 `@contracts` 继续是单一声明源，但 positional `Event.contract/4` 改为显式 contract：

```elixir
@contracts %{
  permanently_deleted:
    Event.contract(:permanently_deleted,
      category: :lifecycle,
      high_risk: true,
      message_key: "activity.permanently_deleted",
      target: :none,
      actor_types: [:user, :api_key],
      occurred_at_policy: :server_now,
      payload: [],
      metadata: [],
      changed_fields: [],
      outcomes: %{
        allowed: %{producer_status: :active, coverage: :from_launch},
        denied: %{
          producer_status: :active,
          denial_codes: [:permission_denied, :article_not_mutable],
          coverage: :from_launch
        }
      },
      surfaces: [:community_log],
      retention: :security_critical
    )
}
```

最终 canonical contract 至少包含：

```text
write
  accepted payload / metadata
  accepted changed fields
  accepted actor types
  occurred_at policy
  target contract: :none | {:optional, types: [...]} | {:required, types: [...]}

outcomes
  allowed producer status + coverage
  denied producer status + denial codes + coverage

surfaces
  article_log exposed fields / payload / metadata
  community_log exposed fields / payload / metadata

classification
  category
  high_risk

presentation
  message_key

retention
  policy ref
```

调整原则：

- 删除 `Event.classify_contracts/1` 的事后补全；handler 返回的 contract 已经完整；
- `contract_only` 收口到具体 outcome 的 `producer_status`，不再含糊表示整个 action；
- contract validation 一次性验证 surface、classification、presentation、actor、outcome、coverage、denial code、changed fields 和 retention；
- `target` 不能继续使用含义不明的 `nil` 或任意 map；`:none` 禁止 target，optional / required 同时约束存在性与允许的 target types；subject 若由 action 自由选择，也使用相同形状；
- `high_risk` 是 action contract 分类，不复制到 event row。Preset filter normalization 将 `high_risk = true` 展开为当前 surface 中对应的有限 action 集合，并把展开结果返回 applied filter / export manifest；
- 仍不创建独立 `Contract`、DTO 或 Presenter namespace。

### 11.5 Actor 与 delegation

新增 `GroupherServer.Activity.Actor`，只负责把受支持 actor 规范化为 envelope 和安全投影：

```text
User
  -> actor_type = user
  -> actor_ref = public user ref

Anonymous
  -> actor_type = anonymous
  -> actor_ref = anonymous
  -> only for contract-declared, capacity-controlled denied flows

System
  -> actor_type = system
  -> actor_ref = stable system name

API key
  -> actor_type = api_key
  -> actor_ref = public key ref

Job
  -> actor_type = job
  -> actor_ref = stable job type

Impersonation
  -> actor_type = user
  -> actor_ref = operator user ref
  -> on_behalf_of_type = user
  -> on_behalf_of_ref = represented user ref
  -> impersonation session ref enters declared metadata
```

`Activity.Actor` 提供内部 constructor / normalization，不把任意 actor map 直接视为可信输入。`Activity.log/3` 仍是唯一公共 event append facade。

Stable refs 与全部 display-identity slots 分离后，查询只依赖 ref；nickname、login、avatar 或 key name 的擦除不会破坏 actor、subject、target、delegation 或 stream trail。精确擦除通过受控 maintenance command 或 per-subject encryption 实现，runtime Repo 不获得普通 UPDATE / DELETE。

### 11.6 Denied producer 接入方式

当前 Gate 已返回 typed `CMS.Gate.Decision`，Passport 已返回稳定 ErrorCat reason。V3 不在 Gate / Passport 内调用 Activity，而由具体 command 同时拥有成功与拒绝的 producer：

```elixir
case CMS.Gate.access_check(actor, :delete, article) do
  {:ok, canonical} ->
    Repo.transaction(fn ->
      # authoritative delete / lifecycle mutation
      # Activity.log(... outcome defaults to :allowed)
    end)

  {:error, %CMS.Gate.Decision{} = decision} ->
    with {:ok, _event} <-
           Activity.log(article, :permanently_deleted,
             actor: actor,
             outcome: :denied,
             denial_code: Decision.primary_error(decision).reason
           ) do
      {:error, Decision.primary_error(decision)}
    end
end
```

这段只是边界形状，不要求每个 command 手写重复 case。实现时可以由 CMS command-local helper 封装“执行 typed decision、记录声明过的 denial、返回原错误”，但该 helper 属于 CMS command 层，不提升为全局 Gate 或 Activity authorization API。

Passport middleware 仍可保护普通 list / stats。需要 self-audit 的 export 不能只依赖会在 resolver 前短路的 middleware；`CommunityLog.Export.create` 必须在领域 command 内再次执行 `Authorization.check/3`，从而统一记录 allowed export 或声明过的 denied export。

Auth Hono 服务当前把 session / identity mutation 委托给 Phoenix GraphQL。对应 Activity producer 应落在真正改变 session / account 状态的 Phoenix Accounts command 中；Hono route 不额外 fire-and-forget 写第二条日志。

### 11.8 GraphQL 最终协议

由于尚未上线，直接删除 V2 的 page-inside-filter 和两套重复 filter，使用共享 selection：

```graphql
input CommunityActivityFilterInput {
  resourceTypes: [String!]
  actions: [String!]
  categories: [String!]
  outcomes: [String!]
  denialCodes: [String!]
  actorTypes: [String!]
  actorRef: ID
  onBehalfOfRef: ID
  subjectRef: ID
  targetRef: ID
  changedFields: [String!]
  source: String
  occurredAfter: DateTime
  occurredBefore: DateTime
  operationRef: ID
}

input CommunityActivitySelectionInput {
  presetKey: String
  filter: CommunityActivityFilterInput
}
```

Config 只返回选择 preset 所需的稳定描述：

```graphql
enum CommunityActivityRelativeTimeUnit {
  DAY
  WEEK
  MONTH
}

type CommunityActivityDefaultTimeRange {
  amount: Int!
  unit: CommunityActivityRelativeTimeUnit!
}

type CommunityActivityPresetDescriptor {
  key: String!
  questionKey: String!
  descriptionKey: String!
  coverageNoteKey: String
  defaultTimeRange: CommunityActivityDefaultTimeRange!
}
```

未知 preset key 不执行查询，GraphQL error extensions 返回唯一稳定错误 `PRESET_UNAVAILABLE` 和 requested key。Preset base filter 与用户 filter 只做交集；需要任意修改核心条件时，前端显式清除 presetKey 后发送普通 custom filter。

读取与 command：

```graphql
communityActivity(
  community: String!
  selection: CommunityActivitySelectionInput!
  page: Int = 1
): PagedCommunityActivity!

communityActivityStats(
  community: String!
  selection: CommunityActivitySelectionInput!
): CommunityActivityStats!

communityActivityConfig(
  community: String!
): CommunityActivityConfig!

exportCommunityActivity(
  community: String!
  selection: CommunityActivitySelectionInput!
  format: CommunityActivityExportFormat!
): CommunityActivityExport!

communityActivityEvent(
  community: String!
  eventRef: ID!
): CommunityActivityEvent
```

- list、stats 和 export 返回相同 shape 的 `queryContext { preset, appliedFilter, coverage, presetIntersectionEmpty }`；preset 只含 immutable key 与 question key，纯 custom query 时为 null；`presetIntersectionEmpty` 是派生布尔值，没有 preset 时恒为 false，不进入 coverage，也不形成新的 preset 状态；
- config 返回 active actions、sources、actor types 和 built-in preset descriptors；每个 descriptor 包含 `key / questionKey / descriptionKey / coverageNoteKey / defaultTimeRange`，分别对应 registry 的 `key / question_key / description_key / coverage_note_key / default_time_range`；
- preset config 不根据 cookie、header 或请求 locale 返回已翻译文案。前端使用现有 i18n `t(key)` 解析 question / description / coverage note；
- `exportCommunityActivity` 是 mutation，并在内容生成成功时记录 self-audit；
- `communityActivityEvent` 保持普通安全 query，不产生 Activity 写入。Community `audit.read` 失败时返回现有授权错误；通过 Community 授权后，event 不存在或不属于可见 surface 时都返回 null，不暴露隐藏事件是否存在。列表、OperationGroup、Timeline 和详情都复用现有 Community / surface projection；
- 删除旧 `communityActivityExport` query、`CommunityActivityStatsFilter` 和旧 filter 内的 page；
- 不保留 deprecated aliases、双参数协议或 Resolver 兼容分支；
- schema 修改后一次性更新 resolver、测试、前端 documents 和 GraphQL codegen。

### 11.9 前端最终边界

当前约 600 行的 `Activity/index.tsx` 拆为：

```text
frontend/core/unit/DashboardThread/Activity/
├── index.tsx                    # page composition only
├── Overview.tsx
├── QuestionPresetPicker.tsx
├── AppliedQuery.tsx             # question, chips, coverage limitation

├── OperationGroup.tsx
```

状态链路：

```text

  -> useQueryState
  -> {presetKey, user filters, page, selected event}

  -> AppliedQuery / Overview / Timeline / Export
```

规则：

- 前端不维护 preset-to-action 映射；它只消费 config 返回的 question descriptor；

- `presetIntersectionEmpty = true` 时展示明确冲突提示和“清除冲突筛选 / 退出 preset”入口；它不能复用 coverage limitation 文案；
- list、stats 和 export 传同一个 selection object；page 和 selected event 不进入 selection；
- export 使用 mutation，不再通过 `browserQuery` 包装有副作用的 read；
- 每个文件只定义一个组件；下层需要 salon 时自行调用 `useSalon()`，不传递父级 `s`。

### 11.10 无兼容迁移策略

Activity 尚未上线，V3 不增加 `add_v3_fields`、backfill、双写或 deprecated GraphQL 字段。实施时：

1. 将当前 `create_activity_v1`、`add_activity_management_indexes`、`align_activity_v1_envelope` 收敛成一份最终 create migration；

5. 删除 `hash_id / actor_id / inserted_at` 及其代码、GraphQL 和测试引用；
6. 删除旧 GraphQL input / export query，不提供 alias；
7. 重新生成 GraphQL types，并更新前端 URL/query state；

- changed fields allowlist；
- mutation + allowed Activity rollback；
- typed decision + denied Activity，且 Gate / Passport 无 Activity side effect；
- preset base filter 不能被用户条件扩大；
- preset default time 只在两个用户时间边界都缺失时物化；提供任一边界后不混入部分默认值；
- preset 与用户条件交集为空时返回合法零结果和 `presetIntersectionEmpty = true`，且不误报 coverage limitation；
- high-risk / category 等 contract-derived 条件先展开为 action 集合，再计算 preset intersection；
- 清除 preset key 后同一筛选器可以执行普通 custom query；
- list / stats / export applied filter 完全一致；
- 空交集 export 跳过 row query、生成零行文件并记录 `activity_exported`，manifest 与 list / stats 返回相同的空交集标记；
- zero rows 与 incomplete coverage 的区别；
- record sequence 跨表 tie order；
- export self-audit 与内容生成共同成功，且不把导出内容复制回 Activity；
- runtime database role 无 UPDATE / DELETE；
- migration / schema / Const / contract parity；
- GraphQL 不暴露 local id、原始 metadata 或未声明 snapshot。
- `communityActivityEvent` 在 Community 授权失败时返回权限错误；已授权但 event 不存在或不可见时返回无 GraphQL error 的 null；Repo / 系统故障返回 internal error，不能被吞成 null；三条路径都不产生 Activity 写入。

前端测试覆盖 preset 选择、条件缩小、URL 恢复、显式清除 preset 后的 custom query、coverage 提示、三类独立 loading/error、详情 query 和 export mutation。

## 14. 非目标

- 不把 Activity 改造成 Event Sourcing；
- 不通过最后一条 Activity 或 rollup 推导当前业务状态；
- 不恢复旧 `cms.audit_logs` 或伪造 V1 之前历史；
- 不建立一张替代现有 resource-specific tables 的万能 AuditEvent 表；
- 不为所有 action 强制保存通用 before / after；
- 不保存 secret、完整正文、完整 request 或任意错误堆栈；
- 不把所有 Gate denial、login traffic、page view、polling、reaction 或 job retry 写入 Activity；
- 不让 Dashboard、GraphQL Resolver 或外部客户端直接构造任意 Activity 行；
- 不建立无 Community / Article / audience 权限约束的全局查询；
- 不把问题 preset 做成任意 SQL、JSON path 或全文检索语言；
- 不为 preset 增加修订协商、生命周期状态或保存视图；
- 不在没有明确访问审计需求时记录详情查看或把详情 query 改成 mutation；
- 不为没有真实 producer 的执行主体预留 actor type；
- 不把 controls mapping 宣称为 SOC 2、ISO 或其他认证本身；
- 不在没有性能、容量或治理证据时提前实现 cursor、rollup、归档集群或密码学 hash chain。

## 15. 验收标准

### 15.1 事实完整性

- 每个 active action 都能定位 allowed producer、事务边界、覆盖起点和 deploy ref；
- denied coverage 单独声明，不因 allowed producer 存在而被假定完整；
- producer 只声明已实现的 actor types；新增 actor constructor 之前不得提前声称对应 coverage；
- 成功 mutation 与 allowed Activity 同事务提交；
- 高价值拒绝由实际 decision owner 写入且不重复；
- action 表达领域尝试，denial code 表达稳定拒绝原因；
- 默认 producer 不能指定发生时间；bounded producer 超出 contract window 或全局未来容差时 append 失败；
- 七张 Community-scoped 表不存在 nullable `community_id`，无法解析的 Community probe 不制造 Activity row；
- Activity 不拥有或重建当前业务状态。

### 15.2 Contract 与隐私

- `outcome / denial_code` 组合具有数据库和 changeset 约束；
- actor type 具有明确 snapshot schema，source 不冒充 actor；
- actor / on-behalf-of / subject / target / stream snapshot 使用同一 display-identity 生命周期，payload / metadata 不能绕过其分类与擦除路径；
- changed fields 是 action allowlist 的子集；
- target 的 none / optional / required 与允许类型由 contract 校验；
- old/new 只进入 action-specific 安全 payload；
- secret 与未声明字段在写入边界被拒绝，不依赖 UI masking；
- identity erasure 不删除事实 row、不改写 stable ref、不重新保存被擦除原值；
- 擦除自身可通过 Activity 追溯。

### 15.3 问题式查询

- 每个 preset 具有不可变 semantic key、question / coverage i18n key、base filter 和 required fields；核心语义变化使用新 key；
- preset 展开后继续经过 Community、`audit.read`、active surface 和 filter normalization；
- 页面明确显示 coverage start 与缺失能力；
- preset、手工筛选、统计和导出使用同一 applied filter；
- preset base filter 与用户条件只取交集；切换 custom query 必须显式清除 preset key；
- default time range 只在用户未提供任何时间边界时进入 applied filter；
- 空交集在 contract-derived filter 展开后计算，返回 `presetIntersectionEmpty` 提示而不是静默空白，也不能污染 coverage 语义；
- URL 可恢复相同 preset key 和结构化用户条件；
- 未知 key 返回唯一稳定错误 `PRESET_UNAVAILABLE`；
- config preset descriptor 返回 question / description / coverage i18n keys 和 typed default time range，不依赖后端请求 locale 获取翻译；
- 不提供任意 payload / metadata 全文搜索；
- 首批 destructive、destroy trail、configuration、denied high-risk、actor trail、offboarding 和 Activity export 问题可以直接查询。

### 15.4 Self-audit 与治理

- Activity export 自身被记录且不把导出内容复制进 Activity；
- Export content 与 `activity_exported` append 必须同时成功，append 失败时不返回产物；
- 普通列表、Timeline、OperationGroup、详情和轮询都是无 Activity 写入副作用的 safe query；
- 已授权 Community 内不存在与不可见的 event 都返回无 GraphQL error 的 null，不形成 event-existence oracle；内部故障仍返回 error，不能降级成 null；
- runtime database role 无 UPDATE / DELETE；
- maintenance / erasure role 无 row DELETE；retention executor 只能执行符合 resolved policy / cutoff 的受控操作并生成 manifest；
- retention policy、归档、擦除和 alert rule 修改可追溯；
- 告警消费已提交 Activity，投递失败不修改原始事实；
- evidence export 包含生成者、时间、preset key / question key、applied filter、coverage 和 schema version；
- controls mapping 明确能够证明和不能证明的边界。

### 15.5 规模

- 所有新增索引都有代表性 query plan 证据；
- cursor 使用完整稳定排序 tuple，并覆盖并发插入下的无重复 / 无遗漏；
- rollup 可以从原始 Activity 重建和校正；
- 异步 export 保持权限、operation、状态、有效期和 self-audit 边界；
- 归档执行前已经证明恢复和受权读取路径；
- 规模化能力不建立第二个当前状态或审计事实来源。
