# Activity V1：统一业务活动与安全日志读取

> 状态：实现已同步（2026-08-21）。本文同时作为 Activity V1 的模块边界、写入协议、存储模型、权限和产品读取接口规范。

实施决策：旧 `cms.audit_logs` 与无调用路径的 `log.user_activities` 选择直接销毁，不导出应用可读冷存储；`cmsAuditLogs` 的删除是已接受的 breaking API change。仓库内没有旧 GraphQL 字段消费方，但这不构成对仓库外消费者的兼容保证。

## 1. 背景

实施前，后端的持久化日志能力分散在多个位置：

- `GroupherServer.CMS.Audit` 和 `cms.audit_logs` 记录部分 Article、DocTree、Community 与 Press 操作；
- `GroupherServer.Logs` 是未形成有效公共能力的顶层空壳；
- `log.user_activities` 缺少明确调用路径和产品边界；
- Elixir `Logger` 负责运行时日志；
- Oban 负责后台任务状态、执行和重试；
- `CMS.Events.Audition` / `AuditBot` 表达内容审核，不是业务活动记录；
- `CMS.Interactions.Audit` 表达数据一致性检查，也不是用户操作历史。

这些能力都使用了“日志”或 “audit” 一类词汇，但实际回答的问题不同：

```text
Activity
  谁或哪个系统行为，对什么业务资源造成了什么业务事件？

ArticleLog
  一篇文章的读者可以看到哪些公开操作记录？

Logger / Telemetry / Error Reporting
  代码为什么失败、请求耗时多久、异常堆栈是什么？

Jobs / Oban
  后台任务何时执行、重试了几次、当前状态是什么？

CMS 内容审核
  内容是否违规、需要什么审核决定？
```

V1 将持久化业务活动提升为与 CMS、Accounts、Jobs 平级的 `GroupherServer.Activity`，同时保留各领域对自身资源、权限和当前状态的所有权。

## 2. 设计结论

V1 固定以下决策：

1. 顶层模块命名为 `GroupherServer.Activity`，不使用 `Logger`、`Logs` 或全局 `Audit`；
2. 唯一公共写入口是 `Activity.log(resource, action, opts)`；
3. `resource` 始终是第一个参数；
4. Article 调用方可以传入抽象 Article，不感知 Post、Blog、Changelog 或 Doc；
5. Article thread 识别复用现有 `CMS.Artiment.Matcher`，不新增 `resolve_thread`；
6. `CMS.Artiment.Matcher` 继续属于 CMS，不提升到全局 `Helper`；
7. 数据库使用 `activity` prefix；
8. Article thread 分表存储：`post_logs`、`blog_logs`、`changelog_logs`、`doc_logs`；
9. `<thread>_logs` 保存该 thread stream 的完整正式业务事件，不只是产品可见事件；
10. 产品 `ArticleLog` 是完整 Activity 的公开、鉴权、脱敏子集，不单独双写一张表；
11. CMS Gate 继续属于 CMS；Activity 不引入全局 Gate；
12. Activity append 与其描述的权威业务变更保持原子性；产品投影、导出和其他派生工作可以异步；
13. `CommunityLog` 按 Community 范围聚合 Activity；`audit.read` 只是读取权限，不进入领域接口命名；
14. 新 Community Activity 读取完成并验证后，删除旧 `cmsAuditLogs` GraphQL 表面和 `cms.audit_logs`，不迁移旧历史数据，不长期兼容或双写；
15. Activity 不拥有当前业务状态，不能通过最后一条日志推导当前状态；
16. `GroupherServer.Activity` 是 Phoenix Context，只公开 `log/3`、`list_article_logs/3`、`list_community_logs/3` 三个领域 facade；
17. 公共 envelope、append 和安全投影由 `Activity.Event` 统一实现；各资源事件模块在同一 action contract 中声明写入校验与 surface 投影，不建立独立 Contract、DTO 或 Presenter 模块；
18. `source` 和 `actor_type` 由 `Activity.Const` 提供单一声明源，并由 Ecto Enum 与数据库 CHECK 再次约束；
19. 关联标识只保留 `event_ref`、`operation_ref` 和 `parent_event_ref`，V1 不预留没有生产者和消费者的通用 correlation 字段；
20. GraphQL 分页输入只允许客户端传 `page`，page size 由服务端固定配置决定；ArticleLog 不提供 action filter。

## 3. 目标与非目标

### 3.1 目标

- 为 CMS、Accounts、Community、后台任务等模块提供一个稳定的业务活动写入边界；
- 让抽象 Article 调用方无需手写 thread 分支；
- 为不同 thread 提供独立 action、字段、索引和保留策略；
- 让产品 ArticleLog 从完整事件流安全派生；
- 保留 Community 维度的 Activity 聚合读取能力，但使用 Activity 的统一安全返回结构和新读取边界；
- 让用户触发和系统触发的业务事件使用同一关联模型；
- 使用 `operation_ref` 归组一次 command，并用 `parent_event_ref` 表达 Activity event 之间的直接父子关系；
- 在资源被永久删除后保留必要且受控的责任快照。

### 3.2 非目标

- 不用 Activity 替代 Event Sourcing；
- 不通过 Activity 重建当前业务状态；
- 不记录全部 Logger、Telemetry、HTTP 或 Oban 技术事件；
- 不把普通 page view、高频 reaction 明细全部写入 Activity；
- 不用 Activity 替代 Draft、Revision、Snapshot 或 Interaction fact；
- 不建立一个跨 CMS、Accounts、Operations 的全局 Gate；
- 不让 Resolver 或外部客户端直接构造任意日志行；
- 不在 V1 为产品 ArticleLog 建立独立复制表或 projection。
- 不长期保留 `cmsAuditLogs`、旧 AuditLog GraphQL 类型或兼容 SQL view；
- 不回填或兼容 `cms.audit_logs` 历史记录；
- 不在 V1 引入 cursor/keyset pagination；所有公开分页 filter 只接收 `page`，page size 由服务端固定。

## 4. 术语

### 4.1 Activity event

Activity event 是由领域模块正式接收和持久化的 append-only 业务事实，例如：

```text
Post 被创建
Changelog 被发布
Comment 被置顶
最佳回复被采纳
Community 被激活
Community setup 最终失败
Press 配置被修改
```

“完整事件”表示所有已经接入 producer、通过 Activity contract 并实际持久化的正式业务事件，不表示所有运行时信号。仅声明为 `contract_only` 的 action 在 producer 接入前不算 V1 已记录事件。

### 4.2 Activity stream

Stream 是事件所属的产品资源流。例如：

```text
activity.post_logs 中 post_ref = post-123 的所有记录
```

一条 Comment 操作可以属于其父 Post 的 stream：

```text
stream  = post-123
subject = comment-456
action  = comment_pinned
```

### 4.3 Subject 与 Target

`subject` 是实际发生动作或状态变化的对象；`target` 是该动作涉及的第二个对象。

采纳最佳回复：

```text
stream  = post-123
subject = post-123
target  = comment-456
action  = solution_accepted
```

置顶评论：

```text
stream  = post-123
subject = comment-456
target  = nil
action  = comment_pinned
```

### 4.4 ArticleLog

ArticleLog 是产品接口，不是完整 Activity 的别名：

```text
完整 <thread>_logs
  -> action surface allowlist
  -> Article 读取权限
  -> payload 白名单投影
  -> 产品 ArticleLog 返回结构
```

### 4.5 CommunityLog

CommunityLog 是按 Community 范围聚合的安全 Activity 读取面，不是“管理员产生的日志”，接口命名不使用当前的鉴权方式：

```text
Community 范围内七类 Activity 表
  -> community_log surface allowlist
  -> audit.read 权限
  -> payload / metadata 白名单投影
  -> CommunityLog 返回结构
```

### 4.6 Payload、Metadata 与 Snapshot

- `payload` 是 action 自身允许产品读取面看到的结构化业务数据，例如 `title_changed` 的新标题、`body_updated` 的正文 hash 和安全摘要；它不是统一的 `from/to` diff；
- `metadata` 是 revision、batch、审核 case、后台流程等审计上下文，只能进入明确允许的 CommunityLog 投影；
- `snapshot` 是 resource、subject、target 在事件发生时的受控显示快照，不是当前状态。

若未来某个 action 的审计确实需要前后值，应在该 action 的 payload 中显式声明成对字段；不能因此恢复所有 action 共用的通用 `from/to` diff 结构。

```text
backend/main/lib/groupher_server/
├── activity.ex
└── activity/
    ├── artiment.ex
    ├── const.ex
    ├── event.ex
    ├── event_ref.ex

        ├── doc_log.ex

        ├── doc_tree_log.ex
        └── press_log.ex
```

`GroupherServer.Activity` 本身是 Phoenix Context；`CMS` 则是包含 `CMS.Articles`、`CMS.Communities` 等多个 Context 的 namespace，因此 CMS 没有对应的 `cms.ex`。Activity 需要提供已确定的 `Activity.log/3` facade，所以 context 文件是 `activity.ex`。

实现时使用 Phoenix 1.8 `phx.gen.context` 建立 `Activity` Context，并以嵌套 schema 名生成 `Activity.Model.*Log`；生成后删除通用 CRUD facade，只保留本节声明的三个领域函数。Ecto 建表 migration 继续位于标准 `priv/repo/migrations`，Activity 模块内部不建立 `migration/` 目录。

### 5.1 依赖方向

```text
CMS / Accounts / Jobs / other domain
              |
              v
           Activity

Activity.Artiment
  -> CMS.Artiment.Matcher

Activity.list_article_logs/3
  -> CMS Article Reader / Gate Scope

Activity.list_community_logs/3
  -> CMS Passport audit.read
```

Activity 依赖 CMS 公开的 Artiment 识别和权限能力是正常领域依赖。不能为了避免该依赖，把 CMS Model、foreign key、preload 和 reaction model 等知识移动到全局 Helper。

### 5.2 Context facade

`GroupherServer.Activity` 只公开三个领域函数：

```elixir
Activity.log(resource, action, opts)
Activity.list_article_logs(article, actor, filter)
Activity.list_community_logs(community, actor, filter)
```

`Activity.Artiment`、`Activity.Const`、`Activity.Event`、各资源事件模块、`Activity.ArticleLog`、`Activity.CommunityLog` 和 `Activity.Model.*Log` 都是 Context 内部实现。Phoenix generator 产生的 `list_post_logs`、`get_post_log!`、`create_post_log`、`update_post_log`、`delete_post_log`、`change_post_log` 等通用 CRUD 不属于 Activity 业务 API，生成后必须删除。

业务模块不能直接调用 `Activity.Post.log/3`、直接查询 Log schema 或绕过 Context facade。

## 6. 公共写接口

### 6.1 签名

```elixir
@spec log(struct() | map(), action(), keyword()) ::
        {:ok, struct()} | {:error, GroupherServer.ErrorCat.Error.t()}
def log(resource, action, opts \\ [])
```

资源始终位于第一个参数：

```elixir
Activity.log(article, :archived,
  actor: actor,
  operation_ref: operation_ref
)
```

```elixir
Activity.log(post, :solution_accepted,
  actor: actor,
  target: comment,
  operation_ref: operation_ref
)
```

```elixir
Activity.log(community, :setup_failed,
  actor: :system,
  source: :worker,
  operation_ref: operation_ref,
  metadata: %{stage: :create_defaults, reason_code: :seed_failed}
)
```

### 6.2 调用约束

- Resolver、Controller 和客户端不能直接插入 Activity 表；
- 领域 command 在完成自身 Gate/authorization 后调用 `Activity.log/3`；
- `Activity.log/3` 不重复判断“actor 能否执行该业务动作”；
- `Activity.Event` 必须验证 action、resource、target 和允许字段；
- 调用方不能自由选择目标表；
- 调用方不能传入最终产品文案；
- 任意 metadata 不能原样写入，必须经过 action contract 规范化。

## 7. Artiment 路由与 Matcher

### 7.1 使用现有 Matcher

现有 `CMS.Artiment.Matcher.match/1` 已经能够从以下形状取得 canonical thread：

```elixir
%{thread: thread}
%{meta: %{thread: thread}}
```

因此 Activity 不实现新的 thread 识别函数：

```elixir
defmodule GroupherServer.Activity.Artiment do
  alias GroupherServer.Activity
  alias GroupherServer.CMS.Artiment.Matcher

  @event_modules %{
    post: Activity.Post,
    blog: Activity.Blog,
    changelog: Activity.Changelog,
    doc: Activity.Doc
  }

  def log(resource, action, opts) do
    with {:ok, %{thread: thread}} <- Matcher.match(resource),
         {:ok, event_module} <- Map.fetch(@event_modules, thread) do
      Activity.Event.append(event_module, resource, action, opts)
    else
      :error -> {:error, Activity.ErrorCat.unsupported_resource("unsupported Activity thread")}
      {:error, _reason} = error -> error
    end
  end
end
```

### 7.2 Matcher 与 Activity 事件模块的所有权

`CMS.Artiment.Matcher` 回答：

```text
这个 CMS resource 属于哪个 thread、对应哪个 CMS model/FK/preload？
```

Activity event module registry 回答：

```text
已经识别出的 thread 应由哪个 Activity 事件模块和表处理？
```

不能给 CMS Matcher 增加 `activity_log_model` 或 `activity_event_module`，否则 CMS 会反向依赖顶层 Activity 存储实现。

Activity event module keys 必须通过 contract test 与 `CMS.Artiment.Threads.article_enums()` 保持一致。

### 7.3 Comment 路由

Comment 自身包含父 Article thread。`Matcher.match(comment)` 应把 Comment activity 路由到所属 thread stream：

```text
Post Comment      -> activity.post_logs
Blog Comment      -> activity.blog_logs
Changelog Comment -> activity.changelog_logs
Doc Comment       -> activity.doc_logs
```

V1 不默认建立 `comment_logs`。Comment 是 event subject，其所属 Article 是 stream。

`Matcher.match(comment)` 返回的是父 Article thread 的 `match_info`，其中 `model`、`foreign_key` 和 `preload` 都描述父 Article，不描述 Comment。Activity 只能使用其中的 `thread` 完成 stream 路由：

```text
stream_ref
  来自 comment.article_hash_id

subject_type
  comment

subject_ref
  来自 Comment 自身的稳定 identity
```

Comment 事件模块禁止使用 `match_info.model`、`match_info.foreign_key` 或 `match_info.preload` 推导 subject，否则会把 Comment 静默写成父 Article。

### 7.4 非 Artiment 资源

Community、Account、DocTree、Press 和 System 不通过 Artiment Matcher。顶层 `Activity.log/3` 根据明确资源类型委托对应事件模块，最后才把 Article-like resource 交给 `Activity.Artiment`。

DocTree 不是 Doc Article，PressConfig 也不是 Community。不能仅因为它们拥有 `community_id` 就写入 `doc_logs` 或 `community_logs`。

## 8. Action contract 与强类型

### 8.1 公共 action

业务代码使用 atom，不手写自由字符串：

```elixir
Activity.log(article, :archived, opts)
```

禁止：

```elixir
Activity.log(article, "article.archived", opts)
```

即使字符串拼写正确也禁止使用；业务调用方只使用受约束的 atom action。

公共 `Activity.action()` 是有限 atom union。每个资源事件模块再声明自己的合法 action 集合。

### 8.2 Thread-specific action

示例：

```text
Post
  created
  title_changed
  body_updated
  archived
  restored
  trashed
  comment_pinned
  comment_unpinned
  solution_accepted
  solution_replaced
  solution_revoked

Changelog
  created
  title_changed
  body_updated
  released
  release_rescheduled
  release_withdrawn
  archived
  restored

Doc
  created
  title_changed
  draft_updated
  published
  publish_restored
  archived
  restored
```

上面只是 thread 自身 action 的简写。完整 contract 必须同时声明 stream、subject、action、owner 和 surface，不能只维护一份 Article action 列表：

Action contract、现有 producer 改接和 V1 新写入口是三个不同维度。`V1 producer` 使用以下状态：

```text
existing_rewire
  Phase 2 将现有 CMS.Audit 调用点改接到 Activity，不迁移历史数据。

new_v1
  V1 必须在对应业务 owner 中新增 Activity.log/3 调用。

contract_only
  只声明合法 contract，V1 不承诺产生该 action 的数据。
```

`contract_only` 是 V1 producer 能力声明，不是 `Activity.Event.log/4` 的运行时拒绝开关。若未来有内部工具或新 producer 显式调用该 action，仍必须通过完整 contract、权限和事务校验；正式接入 V1 前，代码、测试和产品都不能把它宣称为已记录事件。

| Stream | Subject | Target | Action | Owner | V1 surface | V1 producer |
| --- | --- | --- | --- | --- | --- | --- |
| Post/Blog/Changelog/Doc | Article | - | `created` | CMS Articles | `article_log` | `new_v1` |
| Post/Blog/Changelog/Doc | Article | - | `title_changed` | CMS Articles | `article_log` | `new_v1` |
| Post/Blog/Changelog/Doc | Article | - | `body_updated` | CMS Articles | 按产品决策进入 `article_log` | `new_v1` |
| Post/Blog/Changelog/Doc | Comment | - | `comment_created` | CMS Comments | internal | `contract_only` |
| Post/Blog/Changelog/Doc | Comment | - | `comment_updated` | CMS Comments | internal | `contract_only` |
| Post | Comment | - | `comment_pinned` / `comment_unpinned` | CMS Comments | `article_log` | `new_v1` |
| Post | Post | Comment | `solution_accepted` / `solution_replaced` / `solution_revoked` | PostSolution | `article_log` | `new_v1` |
| Changelog | Changelog | - | `released` | CMS Changelog | `article_log` | `new_v1` |
| Changelog | Changelog | - | `release_rescheduled` / `release_withdrawn` | CMS Changelog | `article_log` | `contract_only` |
| Doc | Doc | - | `draft_updated` | CMS Docs | internal | `contract_only` |
| Doc | Doc | - | `published` / `publish_restored` | CMS Docs | `article_log` | `new_v1` |
| 任意 Article stream | ReviewCase | - | `moderation_review_started` / `moderation_review_resolved` | Moderation | `community_log` | `contract_only` |

上表只列新增的 Article Activity contract。§16.1 中现有 `article.*`、`community.*`、`doc_tree.*` 和 `press.*` producer 均属于 `existing_rewire`。

Moderation 继续拥有 ReviewCase、决定和当前状态；Activity 只记录已经形成正式状态转换或决定的历史。Risk score、模型原始响应、扫描尝试和内部审核备注不是公开 ArticleLog。Search enqueue、retry 和 failure 默认属于 Jobs/Operations；除非它们正式改变产品业务状态，否则不进入 Article Activity。

合法性示例：

```text
Post + archived          -> valid
Changelog + released     -> valid
Post + released          -> invalid
Doc + solution_accepted  -> invalid
```

抽象 Article 的具体 thread 只能在运行时确定，因此 `thread + action` 组合必须由资源事件模块在运行时完成最终验证。V1 使用四层约束：

1. 公共 action atom typespec；
2. thread event module action allowlist；
3. Ecto `Ecto.Enum`；
4. PostgreSQL `CHECK` constraint。

数据库表已经提供 thread 上下文，表内 action 保存 `archived`、`released` 等值，不重复保存 `article.archived` 字符串。

### 8.3 Action payload contract

每个 action 必须声明：

```elixir
%{
  title_changed: %{
    write: %{
      target_type: nil,
      accepted_payload: [:title],
      accepted_metadata: [:revision_ref]
    },
    surfaces: %{
      article_log: %{
        exposed_fields: [:actor, :subject, :payload, :occurred_at],
        exposed_payload: [:title],
        exposed_metadata: []
      },
      community_log: %{
        exposed_fields: [
          :actor,
          :subject,
          :source,
          :payload,
          :metadata,
          :occurred_at
        ],
        exposed_payload: [:title],
        exposed_metadata: [:revision_ref]
      }
    },
    retention: :long_term
  }
}
```

Action contract 是每个资源事件模块内的一组声明，不对应独立的 `Activity.Contract` 模块。`Activity.Post`、`Activity.Changelog`、`Activity.Community` 等模块分别拥有自身合法 action，并在同一处声明写入规则与各读取 surface 的投影规则：

- `write.target_type` 约束 target；
- `write.accepted_payload` 是写入侧允许的 `payload` keys；`Activity.Event` 必须拒绝未声明 key；
- `write.accepted_metadata` 是写入侧允许的 `metadata` keys；`Activity.Event` 必须拒绝未声明 key；
- `surfaces.<surface>.exposed_fields` 是该读取 surface 可以返回的顶层字段；
- `exposed_payload` 和 `exposed_metadata` 是该 surface 可以返回的 payload keys。

`actor`、`source`、`event_ref`、`operation_ref`、`occurred_at` 等公共 envelope 字段由 `Activity.log/3` 统一校验，不在每个 action 的 `write.accepted_*` 中重复声明；读取侧仍须按各 surface 在 `exposed_fields` 中显式声明是否返回。对应 Log schema 的 `Ecto.Enum` 和数据库 `CHECK` 再提供持久化约束。

每个读取清单必须是对应写入清单的子集：

```text
surface.exposed_payload  ⊆ write.accepted_payload
surface.exposed_metadata ⊆ write.accepted_metadata
```

写入校验和读取投影是两层独立保护。读取侧不能因为写入侧已经拒绝未知 key，就直接返回完整 `payload` 或 `metadata`。

复杂 payload 可以使用专用 struct 或 changeset。调用方不能传入未经约束的完整 schema、request body、正文、token、header、IP 或内部审核信息。

### 8.4 Source contract

`source` 表达事件从哪个执行入口产生，与 actor 分开：

```elixir
@type source ::
        :api
        | :admin
        | :worker
        | :scheduler
        | :maintenance
```

示例：

```text
actor=user, source=api
actor=admin_user, source=admin
actor=system, source=scheduler
actor=system, source=worker
```

`source` 的合法值由 `Activity.Const.source_values/0` 单点声明。公共 envelope 使用该声明校验，Log schema 使用同一声明配置 `Ecto.Enum`，数据库 CHECK 提供持久化兜底；每个 action 不能自由声明字符串或复制一份 source 列表。

### 8.5 Actor contract

写接口只接受用户和系统两类 actor：

```elixir
Activity.log(resource, action, actor: %User{})
Activity.log(resource, action, actor: :system)
```

持久化 `actor_type` 只有 `:user | :system`，合法值由 `Activity.Const.actor_type_values/0` 单点声明，并由 Ecto Enum 与数据库 CHECK 再次约束。V1 不接受 `:operations` 别名；未传 `actor` 时默认 `:system`，但显式传入 `nil` 必须返回 `{:error, %ErrorCat.Error{}}`，不能静默转换为系统行为。

## 9. 数据库模型

### 9.1 Prefix 与表

```text
activity.post_logs
activity.blog_logs
activity.changelog_logs
activity.doc_logs
activity.community_logs
activity.account_logs
activity.doc_tree_logs
activity.press_logs
activity.system_logs
```

只在对应领域确实产生正式 Activity 时创建表。V1 不为了名称完整提前创建空表。

### 9.2 为什么按 thread 分表

- CMS 的 Post、Blog、Changelog、Doc 本身独立存储；
- 各 thread action 集合不同；
- Doc branch/release 信息与 Changelog release 信息不同；
- 查询和索引可以围绕具体 stream 优化；
- retention 和产品安全字段投影可以独立演进；
- 避免把全部差异重新塞进无约束 `resource_type/resource_ref/metadata`。

代价是 Community 范围的跨 thread Activity 需要聚合查询。V1 接受该代价，不通过双写 `community_logs` 解决。

### 9.3 公共字段

各表共享以下语义，但不要求用宏隐藏所有字段：

```text
id
hash_id
action

community_id                 # 适用时

stream_ref
stream_snapshot

subject_type
subject_ref
subject_snapshot

target_type
target_ref
target_snapshot

actor_type
actor_id
actor_snapshot

source

event_ref
operation_ref
parent_event_ref

payload
metadata

occurred_at
inserted_at
```

`id` 使用每张表自己的 bigint 自增主键，承担表内排序和分页；`hash_id` 是稳定公开引用，不承担分页顺序。Community 跨表聚合使用 `occurred_at DESC, log_type ASC, id DESC`，其中 `log_type` 是 union 查询补充的稳定表类型。V1 不引入共享全局 sequence 或 cursor。

具体表使用具体 stream 字段代替抽象 `stream_ref`：

```text
post_logs.post_ref
blog_logs.blog_ref
changelog_logs.changelog_ref
doc_logs.doc_ref / branch_ref
community_logs.community_ref
account_logs.account_ref
```

资源引用和必要 snapshot 不依赖强外键，以便资源永久删除后仍能保留受控历史。Snapshot 不是实时资料，也不是当前状态来源。

### 9.4 时间字段

```text
occurred_at
  权威业务事件实际发生时间，由 command/event producer 提供。

inserted_at
  Activity 行写入数据库的时间，由数据库生成。
```

- Lifecycle event 使用同一次 transition 的 `changed_at`；
- 同步 command 在入口生成一次时间，业务状态和 Activity 共用；
- worker 真正完成业务转换时使用该转换成功时间；
- worker 重放较早发生的 outbox event 时携带原始 `occurred_at`；
- retry 不能把旧事件的 `occurred_at` 重置为当前时间。

`Activity.log/3` 不应无条件在内部用 `DateTime.utc_now/1` 覆盖 producer 传入的时间。

V1 遵守项目现有时间约定，Ecto schema 使用 `:utc_datetime`，数据库使用 `:timestamptz`。新写入不把微秒精度作为分页正确性的前提；相同 `occurred_at` 的确定性顺序由 `log_type` 和表内 bigint `id` 共同保证。微秒精度也不能解决 offset pagination 在并发插入下的页偏移，因此不能替代完整 tie-breaker。

### 9.5 关联 ID

```text
event_ref
  一条正式 Activity event 的稳定标识；同一事件 retry 时必须保持不变。

operation_ref
  一次业务 command 的稳定标识；由 command 入口创建并向下传递。

parent_event_ref
  直接触发当前事件的上一条 Activity event_ref；没有事件父节点时为 nil。
```

一个 command 可以在不同表产生多条事件，但必须共享同一个 `operation_ref`。禁止每个下游事件模块自行生成彼此无关的 operation ref。`parent_event_ref` 只引用 Activity event，不引用申请、任务或任意业务资源；V1 不保存额外 correlation/flow 字段，未来出现明确跨 operation 消费需求时再单独设计。

写侧只校验 `parent_event_ref` 是合法 UUID，不额外执行 SELECT 验证对应 Activity 行存在。引用存在性和 ref 类型由 producer contract 保证：producer 只能传入自己已持有的父 Activity `event_ref`。这样保留快速 append，并避免在无 FK 的 snapshot 设计中引入竞态存在性检查。

## 10. 完整 Activity 与产品 ArticleLog

### 10.1 完整 Activity

`<thread>_logs` 保存该 stream 的完整正式业务事件，例如：

```text
post.created
post.title_changed
post.body_updated
comment.created
comment.updated
comment.pinned
solution.accepted
moderation.review_started
moderation.review_resolved
post.archived
post.restored
```

其中 `comment.*` 和 `moderation.*` 用于展示目标完整模型；它们在 V1 中当前标记为 `contract_only`，不代表已经接入 producer 或已有 Activity 数据。

这不意味着 Activity 记录每次 view、reaction、worker retry、HTTP 请求或 Logger error。

### 10.2 ArticleLog 是公开子集

ArticleLog 面向所有能够读取该 Article 的用户，包括公开 Article 的匿名读者。

可以进入 ArticleLog 的事件示例：

```text
created
title_changed
published / released
comment_pinned / comment_unpinned
solution_accepted / solution_replaced / solution_revoked
archived / restored
```

不能进入公开 ArticleLog 的事件示例：

```text
moderation risk score changed
内部审核备注
search index retry failed
worker exception details
数据一致性修复细节
IP、token、header
```

### 10.3 Surface contract

Action contract 在 §8.3 的同一声明中使用 `surfaces` 定义产品出口。读取字段使用 `exposed_*` 命名，与写入侧的 `accepted_*` 明确区分：

```elixir
%{
  created: %{
    write: %{
      target_type: nil,
      accepted_payload: [],
      accepted_metadata: []
    },
    surfaces: %{
      article_log: %{
        exposed_fields: [:actor, :subject, :occurred_at],
        exposed_payload: [],
        exposed_metadata: []
      }
    }
  },
  title_changed: %{
    write: %{
      target_type: nil,
      accepted_payload: [:title],
      accepted_metadata: [:revision_ref]
    },
    surfaces: %{
      article_log: %{
        exposed_fields: [:actor, :subject, :payload, :occurred_at],
        exposed_payload: [:title],
        exposed_metadata: []
      }
    }
  },
  moderation_review_started: %{
    write: %{
      target_type: nil,
      accepted_payload: [],
      accepted_metadata: [:case_ref]
    },
    surfaces: %{
      community_log: %{
        exposed_fields: [:actor, :subject, :source, :metadata, :occurred_at],
        exposed_payload: [],
        exposed_metadata: [:case_ref]
      }
    }
  }
}
```

V1 实现 `:article_log` 和兼容现有 Community 审计能力所需的 `:community_log`。未来可以增加 `:security_log`。Surface 是读取与展示 contract，不控制事件是否写入完整 Activity。写入侧按 `accepted_payload/accepted_metadata` 拒绝未知 key；读取侧仍按对应 surface 的 `exposed_fields/exposed_payload/exposed_metadata` 再次投影。

### 10.4 安全字段投影

ArticleLog 不能把数据库行直接返回给产品。`Activity.ArticleLog` 根据各资源事件模块声明的 article-log action 集合和字段白名单投影统一安全返回结构；V1 不建立独立 DTO 或 Presenter 模块，也不提供按 action 过滤的读取参数。

`body_updated` 的 `payload` 和返回结果不得包含正文全文、HTML、document JSON 或未脱敏 diff。产品 payload 只允许 `body_hash`、`schema_version` 和安全 `summary`；`revision_ref` 属于 metadata，只能在明确允许时进入 CommunityLog。Activity 不能成为正文或 Revision 的替代存储。

内部 Activity：

```elixir
%{
  action: :title_changed,
  payload: %{title: "新标题"},
  metadata: %{revision_ref: "revision-ref"}
}
```

产品返回结构：

```elixir
%{
  action: :title_changed,
  payload: %{title: "新标题"}
}
```

### 10.5 CommunityLog

CommunityLog 是按 Community 范围聚合的受控 Activity 读取入口。它承接现有 `cmsAuditLogs` 对切换后新增事件的审计查询能力，但命名只表达资源范围，不表达调用者角色；任何读取者都必须通过 `audit.read`。它返回 action contract 允许的安全子集，不承诺返回原始完整数据库行；`cms.audit_logs` 历史数据不迁移，也不复用旧 AuditLog 返回结构：

```elixir
@spec list_community_logs(Community.t(), User.t(), map()) ::
        {:ok, map()} | {:error, term()}
def list_community_logs(community, actor, filter \\ %{})

Activity.list_community_logs(community, actor, %{
  page: 1,
  action: :archived,
  resource_type: :post
})
```

CommunityLog：

- 使用 CMS Passport `audit.read` 验权；
- 跨 Community、Post、Blog、Changelog、Doc、DocTree、Press 等 Activity 表聚合；
- 只返回 action contract 允许进入 `:community_log` 的字段；
- 使用 Activity 统一安全返回结构，不返回原始数据库 metadata；
- filter 只接受 `page`，服务端固定 page size 为 30，不引入 cursor；
- 按 `occurred_at DESC, log_type ASC, id DESC` 确定排序。

CommunityLog 使用统一 envelope，不复用旧 AuditLog 返回结构：

```elixir
%{
  id: "activity-hash-id",
  action: :config_updated,
  resource: %{type: :press, ref: "press-ref"},
  subject: %{type: :press_config, ref: "press-config-ref"},
  target: nil,
  actor: %{
    id: "account-ref",
    nickname: "张三",
    avatar: "..."
  },
  source: :admin,
  payload: %{feed_enabled: true, sitemap_enabled: true},
  metadata: %{revision: 42},
  occurred_at: ~U[...]
}
```

- `id` 等于 Activity 行的 `hash_id`，本地 bigint `id` 不对外暴露；
- `resource` 是数据库 stream identity 的统一返回表达：thread 表的 `<thread>_ref`、`community_logs.community_ref`、DocTree stream ref 和 Press stream ref 分别映射到对应的 `resource.ref`，`resource.type` 由 Activity 表/stream 类型确定；
- `resource` 不是另一套独立持久化 identity；`subject` 仍表示实际发生动作或状态变化的对象，不能与 stream resource 混用；
- `resource`、`subject` 和 `target` 使用稳定公开 ref，资源删除后仍可依赖受控 snapshot 展示必要上下文；
- `payload` 和 `metadata` 都必须经过所属资源事件模块的 action 白名单投影，不能返回原始数据库载荷；
- 不同 action 可以拥有不同的安全字段，但统一 envelope 的字段语义保持不变；
- Phase 2 必须为每个声明 `surfaces.community_log` 的 action 定义安全字段投影规则。

## 11. ArticleLog 读取接口

### 11.1 签名

Article 始终是第一个参数：

```elixir
@spec list_article_logs(struct(), User.t() | nil, map()) ::
        {:ok, map()} | {:error, term()}
def list_article_logs(article, actor, filter \\ %{})
```

调用：

```elixir
Activity.list_article_logs(article, current_user, %{page: 1})
```

公开 Article 的匿名读取：

```elixir
Activity.list_article_logs(article, nil, %{page: 1})
```

后端 Context 和 GraphQL filter 都只支持 `page`，不支持 `size` 或 `action`；ArticleLog 的 page size 由服务端固定为 20。

### 11.2 读取流程

```text
Activity.list_article_logs(article, actor, filter)
  -> CMS Article Reader / Gate Scope 验证 actor 可读取 article
  -> Matcher.match(canonical_article)
  -> 选择 Activity.<Thread> 事件模块
  -> 查询 activity.<thread>_logs
  -> 只保留声明 surfaces.article_log 的 action
  -> 按 action 白名单投影安全字段
  -> 稳定分页与排序
  -> 返回统一 map
```

### 11.3 权限

ArticleLog 的权限是两层交集：

```text
actor 可以读取 Article
AND
event 允许进入 article_log surface
```

- 公开 Article：匿名和登录用户均可读取公开 ArticleLog；
- 私有、草稿或 branch-scoped Doc：继续遵守 CMS 对该资源的读取规则；
- Trash/删除资源：普通读者不能通过 Activity 绕过 CMS；
- 管理后台读取内部事件必须使用 V1 `Activity.list_community_logs/3`；
- Resolver 禁止直接调用底层 Activity Reader。

Activity 不复制 CMS 权限规则，也不把 CMS Gate 提升为全局 Gate。

V1 切换全程复用现有 Passport action `audit.read` 保护 `Activity.list_community_logs/3`。现有 `audit.read` 的 grant 是 `community.update`；CommunityLog 必须通过 CMS Passport 检查该权限，不能因为 V1 暂无 GraphQL 字段而省略授权。

删除旧 `cmsAuditLogs` 不等于删除 `audit.read`。权限重命名或删除是切换后的独立工作：只有替代权限已经定义、grant 完成调整且所有 Elixir/未来 GraphQL 调用方原子切换后才能执行；没有替代权限时继续保留 `audit.read`，避免 CommunityLog 权限悬空。

### 11.4 产品返回结构

```elixir
%{
  id: "...",
  action: :solution_accepted,
  actor: %{
    id: "...",
    nickname: "张三",
    avatar: "..."
  },
  subject: %{type: :post, ref: "post-123"},
  target: %{type: :comment, ref: "comment-456"},
  payload: %{},
  occurred_at: ~U[...]
}
```

后端返回稳定结构，前端根据 action 本地化文案。后端不保存或返回最终自然语言句子。

产品返回结构的 `id` 必须等于 Activity 行的 `hash_id`。每张表本地的 bigint `id` 只用于数据库内部排序和分页，不作为产品稳定引用暴露。

### 11.5 GraphQL

产品只暴露 ArticleLog 安全返回结构，不暴露 Activity Ecto schema 或原始 metadata：

```graphql
articleLogs(
  article: ArticlePathInput!
  filter: ArticleLogFilter
): PagedArticleLogs!

input ArticleLogFilter {
  page: Int = 1
}

type PagedArticleLogs {
  entries: [ArticleLog!]!
  totalCount: Int
  totalPages: Int
  pageNumber: Int
  pageSize: Int
}

type ArticleLog {
  id: ID!
  action: String!
  actor: ActivityActor!
  subject: ActivityResourceRef!
  target: ActivityResourceRef
  payload: JSON!
  occurredAt: DateTime!
}

type ActivityActor {
  type: String!
  id: ID
  login: String
  nickname: String
  avatar: String
}

type ActivityResourceRef {
  type: String!
  ref: ID!
  title: String
  innerId: ID
}
```

GraphQL 请求不提供 `size` 或 `action`：page size 由服务端配置统一决定；返回结构中的 `pageSize` 只是服务端分页元信息，不允许客户端控制。当前产品没有按原始 action 筛选日志的需求，避免以自由字符串把前端绑定到各 thread 的内部 action 集合。`ArticleLog.action` 仍作为每条返回事件的类型标识，用于前端选择本地化文案；删除的是输入过滤参数，不是输出字段。

V1 不提供无权限约束的任意 Activity 查询。现有 `cmsAuditLogs` 不作为历史数据来源：新 Activity 写入、Community 聚合和 CommunityLog 完成并验证后删除该字段，不迁移旧 AuditLog 数据，也不长期兼容旧返回结构。

V1 不新增 CommunityLog GraphQL 字段。当前仓库前端没有 `cmsAuditLogs` 消费方，因此 V1 只提供受权限保护的 `Activity.list_community_logs/3` Elixir API；未来管理后台产生真实读取需求时，再定义新的 CommunityLog GraphQL 字段、filter 和返回结构，不恢复旧 AuditLog schema。

删除 `cmsAuditLogs` 是有意的 breaking API change。“Community 范围读取不发生能力回退”仅表示后端聚合、权限、page-only filter、固定 page size 和安全字段投影能力由 CommunityLog 保留，不表示旧 GraphQL surface 或历史数据原样保留。仓库内无消费方不能证明不存在外部消费者，切换前必须单独确认并接受外部 API 影响。

## 12. 权限与 Gate 所有权

### 12.1 写权限

```text
CMS Command
  -> CMS.Gate
  -> 权威业务写入
  -> Activity.log(...)
```

Activity 信任已经通过领域准入并成功执行的 command，不重复判断 actor 是否有权归档、发布或删除资源。

Accounts、CommunityApplication 和 Jobs 同样先经过自己的授权或受信任执行边界，再调用 Activity。

### 12.2 读权限

```text
Activity.list_article_logs/3
  -> CMS Article Reader / Gate Scope

Activity.list_community_logs/3
  -> CMS Passport audit.read
```

不同领域拥有自己的权限。Activity 只拥有 surface、payload allowlist、脱敏和日志字段规则。

## 13. 事务、异步与幂等

### 13.1 Activity append

描述权威业务成功结果的 Activity 必须与业务变更处于同一事务：

```text
业务写入成功 + Activity 失败 -> 整体回滚
业务写入失败                 -> 不产生成功 Activity
```

示例：

```elixir
Multi.new()
|> Multi.update(:article, changeset)
|> Multi.run(:activity, fn _, %{article: article} ->
  Activity.log(article, :archived,
    actor: actor,
    operation_ref: operation_ref
  )
end)
|> Repo.transaction()
```

`Activity.log/3` 应是一次快速、受控的数据库 append，不执行外部 HTTP、搜索、通知或复杂 projection。

事务行为是公共 contract：

- `Activity.log/3` 不开启独立事务；
- 不 spawn Task、不切换进程、不使用另一条 Repo 连接；
- `Repo.insert` 必须参与调用方当前进程中的外层事务；
- 返回值固定为 `{:ok, log}` 或 `{:error, reason}`，可直接用于 `Ecto.Multi.run/3`；
- `Activity.Event` 不能吞掉写入错误后返回成功；
- Activity 写入失败必须能使业务事务回滚。

### 13.2 异步工作

以下能力可以异步：

- ArticleLog cache/projection（只有实际性能证据后才建立）；
- 导出、归档、retention、匿名化；
- Notification；
- Search；
- 下游分析。

不能使用无保障的“业务提交后 fire-and-forget worker 再补 Activity”替代事务内 append。如果未来必须异步持久化，应使用与业务写入同事务的 transactional outbox，并保证消费幂等。

### 13.3 Worker 产生的 Activity

后台任务可以产生正式业务 Activity：

```elixir
Activity.log(community, :destroyed,
  actor: :system,
  source: :worker,
  operation_ref: operation_ref,
  parent_event_ref: destroy_scheduled_event_ref
)
```

这里的 `destroy_scheduled_event_ref` 必须是 producer 已持有的既有 Activity event `event_ref`。Activity 写侧只检查 UUID 格式，不查询其存在性；如果 worker outcome 没有直接父 Activity event，则不传 `parent_event_ref`，不能用 application、job 或其他业务资源 ref 冒充。

但以下信号继续属于 Jobs/Logger/Telemetry：

```text
worker started
attempt 2/3
HTTP timeout stacktrace
queue latency
execution duration
```

只有对产品状态、责任调查或正式业务结果有意义的 worker outcome 才进入 Activity。

### 13.4 幂等

幂等分为两层：

1. 业务 command 自身必须首先保证幂等，识别“该操作已经成功”；
2. Activity 数据库约束防止 command retry 或 worker retry 追加重复结果。

事务内 append 只保证业务状态与 Activity 不会半成功，不能单独防止整个 command 成功后被再次执行。

可重试操作必须提供稳定 `operation_ref`，其中的每条正式事件还必须提供或确定性生成稳定 `event_ref`。`operation_ref` 用于归组一次 command，`event_ref` 用于区分该 command 内的事件实例。

Activity contract 在 producer 没有显式传入 `event_ref` 时，根据以下 identity 确定性生成非空 UUID `event_ref`：

```text
operation_ref
resource_type
stream identity
subject identity
action
event_sequence（默认 0）
```

Snapshot、payload 和 metadata 不参与事件身份派生；它们可能在 retry 前发生漂移，不能破坏同一逻辑事件的去重。同一稳定 identity 内确实需要多条正式事件时，只使用由 command 确定性分配的 `event_sequence` 区分。

每张 Activity 表建立：

```sql
CREATE UNIQUE INDEX ... ON activity.<thread>_logs (event_ref);
```

`event_ref` 本身就是行级稳定事件身份，V1 不再引入一个包含 `event_ref` 的冗余 `dedupe_key`。单列非空唯一索引也不存在 nullable 组合索引的 NULL 语义问题。

同一 operation 可以合法产生多条 action、stream、subject、target 和 payload 均相同的正式事件。这种 producer 必须传入不同且稳定的 `event_sequence`；同一事件 retry 时复用原 sequence，不能在 retry 时重新计数。Producer 也可以直接传入稳定 `event_ref`。Activity 行的随机 `hash_id` 不能作为 retry 幂等依据。

## 14. Activity 不拥有当前状态

```text
Article 是否 archived
  -> Article Lifecycle

当前最佳回复
  -> PostSolution

当前置顶 Comment
  -> PinnedComment / pin owner

当前 ReviewCase
  -> Moderation owner

当前 reaction
  -> Interaction fact

正文历史
  -> Draft / Revision / Snapshot
```

禁止：

```text
读取最后一条 archived/restored Activity 推导 Article 当前状态
读取最后一条 solution Activity 推导当前最佳回复
从 body_updated Activity metadata 恢复正文
```

Activity 只解释历史，不成为可变状态权威。

## 15. Community 范围聚合

`activity.community_logs` 只保存 primary resource 为 Community 的事件，不复制社区内全部 Article Activity。

V1 必须实现 Community 对切换后新增 Activity 的范围聚合读取，以承接现有 `CMS.Audit.list/2` 和 `cmsAuditLogs` 的查询能力；这里的范围只描述新 Activity 数据，不包含旧 `cms.audit_logs` 历史记录，也不表示绕过 action contract 返回原始数据库行：

```text
Community Activity View
  -> activity.community_logs
  -> activity.post_logs where community_id = ?
  -> activity.blog_logs where community_id = ?
  -> activity.changelog_logs where community_id = ?
  -> activity.doc_logs where community_id = ?
  -> activity.doc_tree_logs where community_id = ?
  -> activity.press_logs where community_id = ?
```

`activity.account_logs` 和 `activity.system_logs` 没有 Community scope，不进入 Community Activity View。长期规则不是只记住固定七张表：任何新增表只要具有 `community_id`，且其 action contract 允许进入 `:community_log`，就必须纳入聚合；没有 `community_id` 的表不得通过猜测 resource snapshot 归入某个 Community。

不能通过每次 Article Activity 再双写一条 CommunityLog 来规避聚合查询设计。

跨表聚合只接收 `page`，服务端固定 page size 为 30，不引入 cursor。查询必须先 `UNION ALL` 为统一 Activity 返回行，再按以下顺序分页：

```text
occurred_at DESC
log_type ASC
id DESC
```

`log_type` 解决不同表本地 id 重复时的稳定排序问题。不能分别分页后在应用层随意拼接。

### 16.2 旧 GraphQL `cmsAuditLogs`

现有 `cmsAuditLogs(community, filter)`、`AuditLogFilter`、`AuditLog` 和 `PagedAuditLogs` 是待删除的旧表面，不是需要长期兼容的 Activity API。

切换顺序：

1. 建立 Activity Context、分表、资源事件模块、ArticleLog 和 CommunityLog 内部读取；
2. 使用 `audit.read` 验证 `Activity.list_community_logs/3` 的 Community 聚合、page-only filter、固定 page size、action/resource type 过滤和安全字段投影；
3. 将 §16.1 的现有 producer 从 `CMS.Audit.record/2` 一次性改接到 `Activity.log/3`；
4. 验证新写入的 transaction、route、action、source、event/operation ref 和时间字段；
5. 确认仓库内无消费方并单独接受外部 breaking impact 后，删除 `cmsAuditLogs` 字段、Resolver、旧 GraphQL 类型/过滤器、测试和 schema/codegen 产物；
6. 在明确接受历史数据销毁影响后，删除 `CMS.Audit.list/2`、旧写入口和 `cms.audit_logs` 表，不执行历史数据回填。

删除 `cms.audit_logs` 会移除既有 Trash、Restore、Archive、DocTree、Press 和 Community lifecycle 等责任记录。删除前可以选择将旧表一次性导出到外部冷存储，但该导出不是 Activity 历史迁移：V1 不为冷存储数据提供 Elixir API、GraphQL、CommunityLog 查询或恢复路径。删除旧表后，这些记录无法从 V1 应用和主数据库恢复；如果没有外部冷存储或独立备份，则数据不可恢复。这是明确接受的 V1 产品与运维影响，不是实现遗漏。

不建立长期兼容 SQL view，不长期双写，也不继续暴露原始 metadata。

`audit.read` 在上述切换完成后继续保护 CommunityLog，不随旧 GraphQL 或旧表删除。权限重命名/删除按 §11.3 作为后续独立调整处理，不属于核心切换步骤。

### 16.3 `GroupherServer.Logs`

现有空壳 `GroupherServer.Logs` 和缺少有效调用路径的 `Logs.UserActivity` 不作为 Activity V1 基础。实施时应确认数据价值后清理或退役，避免同时存在 `Logs` 与 `Activity` 两套顶层语义。

### 16.4 `CMS.Interactions.Audit`

Interaction 数据一致性 report/repair 继续属于 Interactions。只有修复过程形成正式业务结果且确有责任追踪价值时，才额外写一条 Activity；不能把 report/repair 模块整体迁入 Activity。

### 16.5 Logger 与 Jobs

- Elixir `Logger` 继续拥有运行时 debug/info/warning/error；
- Telemetry/Error Reporting 继续拥有指标、trace 和异常调查；
- Jobs/Oban 继续拥有任务执行状态和 retry；
- Activity 只接收正式业务事件。

## 17. 渐进落地

### Phase 1：Context、Schema 与 action contract

1. 使用 Phoenix 1.8 `phx.gen.context` 建立 `GroupherServer.Activity` Context，定义 `Activity.log/3`、`Activity.list_article_logs/3`、`Activity.list_community_logs/3` 三个 facade；Phase 1 先实现写入口，两个读取入口分别在 Phase 2/3 完成；
2. 建立 `Activity.Artiment` 并复用 `CMS.Artiment.Matcher`；
3. 建立 `Activity.Const`，集中声明 source 与 actor type；
4. 建立 `Activity.Event`，统一公共 envelope、append、payload/metadata allowlist 和 surface 投影；
5. 建立 Post、Blog、Changelog、Doc、Community、DocTree、Press 资源事件模块，并在各模块内定义 action contract；
6. 在 `Activity.Model` 下建立 Log schemas，定义 `activity` prefix 与首批实际需要的表；
7. 不改 GraphQL 产品表面。

### Phase 2：改接现有 CMS Activity

1. 按 §16.1 完成全部现有调用点到新表/action 的映射；
2. 保持 Activity 与当前业务事务的原子性，并传递 event ref、operation ref、parent event ref、occurred at 和原始 source；
3. 实现受 `audit.read` 保护的 `Activity.list_community_logs/3`，包括跨表聚合、page-only filter、固定 page size、稳定排序和安全字段投影；
4. 严格按 §16.2 一次性改接现有 producer，并验证 Community 后端范围读取能力；
5. 确认没有仓库内消费方并接受外部 breaking impact 后，删除 `cmsAuditLogs`、旧 GraphQL 类型/过滤器/Resolver/测试、`CMS.Audit` 和旧表；
6. 不实现历史回填、watermark、legacy mapper 或 Activity 内部 migration 模块。

Phase 2 的 producer 范围仅包括 §16.1 列出的 `existing_rewire` 现有写入口，不因为 §8.2 已声明 action contract 就自动新增 Comment、Moderation 或其他业务写入。

Phase 2 不新增 CommunityLog GraphQL surface。CommunityLog 的 V1 交付物是受权限保护的 Context facade 和统一安全返回结构。

### Phase 3：ArticleLog

1. 实现 `Activity.list_article_logs(article, actor, filter)`；
2. 接入 CMS Article 读取权限；
3. 为首批 action 定义 `:article_log` surface；
4. 接入 §8.2 标记为 `new_v1` 的 producer，并验证与权威业务状态处于同一事务；
5. 实现 action-specific 安全字段投影；
6. 定义统一返回结构、GraphQL `articleLogs` schema、分页和排序；GraphQL filter 只包含 `page`，不包含 `size` 或 `action`；
7. 删除 ArticleLog 后端 action filter，保留 action contract 对可见事件集合和字段投影的约束；
8. 确认产品侧只读取 ArticleLog 安全返回结构，不读取内部 Activity metadata。

标记为 `contract_only` 的 action 不属于 V1 验收范围。只有 producer 实际接入后，文档和产品才能宣称对应事件已包含在完整 Activity stream 中。

当前 Changelog 领域只有立即发布 command，没有定时发布、改期或撤回的权威业务状态。`release_rescheduled` 与 `release_withdrawn` 因此保留为强类型 contract，但不得由 Activity 自行伪造 producer；未来必须先由 CMS Changelog 建立真实 command 和当前状态 owner，再与 Activity 原子接入。

### Phase 4：其他领域

1. 根据真实需求接入 Account、System、CommunityApplication；
2. 按证据决定是否增加 security surface；
3. 按查询和容量证据决定是否建立 projection；
4. 清理 `GroupherServer.Logs` 和其他遗留表面。

## 18. 测试与验收

### 18.1 Matcher 与路由

- Post、Blog、Changelog、Doc 抽象 Article 能路由到正确表；
- Comment 根据父 thread 路由到对应 Article stream；
- Comment 的 stream ref 来自 `article_hash_id`，subject ref 来自 Comment 自身；
- Comment 路由只读取 Matcher 的 thread，不使用父 Article model/foreign key/preload 构造 subject；
- ArticleLifecycle 等含 canonical thread 的结构能正确路由；
- Community、DocTree、Press 不错误进入 Artiment event module registry；
- Activity event module keys 覆盖 `Threads.article_enums()`；
- 未支持资源和 thread fail closed。

### 18.2 Action contract

- 合法 thread/action 组合成功；
- 跨 thread 非法 action 被拒绝；
- string action 被拒绝；
- 未包含在 `accepted_payload` 的 payload key 被拒绝；
- 未包含在 `accepted_metadata` 的 metadata key 被拒绝；
- 每个 surface 的 `exposed_payload` 是 `accepted_payload` 的子集；
- 每个 surface 的 `exposed_metadata` 是 `accepted_metadata` 的子集；
- 即使存储行包含内部合法字段，读取投影仍只返回对应 surface 的 `exposed_*` 清单；
- `Activity.Const`、Ecto Enum、公共 envelope 和数据库 CHECK 使用同一 source/actor type 集合；
- source enum 拒绝未声明来源；
- actor 只接受 `%User{}` 或 `:system`，显式 `nil` 和 `:operations` 被拒绝；
- target 类型与所属 stream 不匹配时失败；
- `solution_*` 的 subject 是 Post、target 是 Comment，不能形成双 subject；

### 18.3 事务和幂等

- 业务写入成功但 Activity 失败时事务回滚；
- 业务写入失败时没有成功 Activity；
- worker retry 不产生重复正式结果；
- command retry 被业务幂等和 Activity `event_ref` 唯一约束共同拦截；
- 同一 operation 的多条事件共享 operation ref；
- `parent_event_ref` 写侧校验 UUID 格式，非 UUID 拒绝；存在性和 ref 类型由 producer contract 保证，没有直接父事件时允许为空；
- schema、公共 envelope 和 ErrorCat 不再声明 correlation/flow ref；
- 同一 operation 内相同 action/subject/target 的多条事件具有不同 event ref；
- 同一事件 retry 时复用 event ref 并命中唯一约束；
- Activity 写入不执行外部副作用；
- `Activity.log/3` 复用外层 Repo 事务连接且返回 `{:ok, _} | {:error, _}`；
- occurred at 在 retry/replay 时保持原始业务发生时间。

### 18.4 ArticleLog

- 公开 Article 的匿名读者可读取公开子集；
- 无权读取 Article 的 actor 不能通过 ArticleLog 绕过 CMS；
- internal-only action 不进入产品结果；
- 安全字段投影不泄露原始 metadata 和内部字段；
- `body_updated` 返回结构不包含正文、HTML、document JSON 或未脱敏 diff；
- 不同 thread 返回统一结构；
- 稳定分页在相同 occurred_at 下仍有确定顺序；
- Trash/草稿/Doc branch 遵守 CMS 现有权限；
- GraphQL 字段名为 `articleLogs`，相关类型使用 `ArticleLog` / `PagedArticleLogs`；
- GraphQL filter 只接受 `page`，客户端不能传 `size` 或 `action`；
- 后端 ArticleLog 不支持 action filter；

### 18.5 CommunityLog 与旧表面删除

- Community 聚合至少覆盖 Community、四张 thread、DocTree 和 Press 七类表；
- Account/System 等无 `community_id` 的表不进入 Community 聚合；
- CommunityLog 统一返回结构使用 `hash_id`，resource/subject/target 使用稳定公开 ref；
- 每个 `:community_log` action 都声明安全字段投影，且 payload/metadata 不泄露未声明字段；
- `Activity.list_community_logs/3` 在切换前后都由 `audit.read` 保护；
- 聚合按 `occurred_at DESC, log_type ASC, id DESC` 稳定排序；
- 聚合 filter 只接受 `page`，服务端固定 page size 为 30，不引入 cursor；
- action/resource type 过滤在分表后仍正确；
- Post/Blog/Changelog/Doc、Community、DocTree 和 Press 的新写入使用正确 stream/subject identity；
- `article.trashed`、`article.permanently_deleted` 等改接 action 使用 §16.1 明确声明的 surfaces；
- 改接前后新业务操作的 action、operation ref、resource、source 和 occurred at 正确；
- 不实现历史回填、watermark、legacy mapper 或 Activity 内部 migration 模块；
- CommunityLog 只承接切换后新增事件，不返回旧 `cms.audit_logs` 历史记录；
- 删除旧表前记录“导出冷存储”或“直接销毁”的明确运维决策；
- 如果选择冷存储导出，V1 不为归档数据提供应用读取或恢复路径；
- 新 CommunityLog 完成后删除 `cmsAuditLogs`、`AuditLogFilter`、`AuditLog`、`PagedAuditLogs` 和 Resolver；
- V1 不新增 CommunityLog GraphQL 字段，旧字段删除被记录为已接受的 breaking change；
- 删除旧 GraphQL 和旧表时不删除仍被 CommunityLog 使用的 `audit.read`；
- 删除旧 GraphQL 后同步更新测试、schema 和 codegen；
- 不保留长期兼容 view、双写或原始 metadata GraphQL 表面。

## 19. V1 验收标准

- 顶层业务模块为 `GroupherServer.Activity`；
- 唯一公共写入口为 `Activity.log(resource, action, opts)`；
- resource 是第一个参数；
- 抽象 Article 调用方不知道具体 thread event module；
- Article 路由复用 `CMS.Artiment.Matcher`；
- Matcher 留在 CMS，不移动到全局 Helper；
- 数据位于 `activity` prefix，并按真实 resource/thread 分表；
- `<thread>_logs` 保存完整正式业务事件；
- ArticleLog 是所有可读 Article 用户可见的安全子集；
- ArticleLog GraphQL 入口为 `articleLogs`，分页输入只包含 `page`，不提供 action filter；
- CommunityLog 保留 Community 范围聚合读取能力，filter 只接受 `page`，服务端固定 page size 为 30；
- V1 CommunityLog 只提供受 `audit.read` 保护的 Elixir API，不新增 GraphQL 字段；
- Activity 切换后删除旧 `cmsAuditLogs` 和 `cms.audit_logs`，不迁移历史数据；
- 已明确接受旧责任记录从 V1 应用和主数据库不可恢复的影响；没有外部归档或备份时，删除即为不可恢复的数据销毁；
- 原始 metadata 和内部事件不直接暴露给产品；
- action 业务数据统一命名为 `payload`，不把它定义为通用 `from/to` diff；
- `Activity.Const` 是 source 与 actor type 的单一声明源；
- `Activity.Event` 统一实现公共事件校验、append 和安全投影；
- 关联标识只保留 event、operation 和可选 parent-event 三层；
- Activity 写入与权威业务结果保持原子性；
- 异步 worker 只记录有业务意义的正式结果；
- Gate、Lifecycle、Revision、Interaction 等 owner 不被 Activity 取代；
- 不通过 Activity 推导当前状态；
- 不引入全局 Gate、全局 Matcher、统一大表或长期双写。
