# Activity V2：Dashboard 社区活动记录

> 状态：V2.1 / V2.2 已完成（2026-08-22）。本文记录 Activity V2 的产品入口、读取接口、页面结构、筛选能力和验收边界；V2 复用 V1 的 Activity 事实与安全投影，不改变 `Activity.log/3` 写入边界。规模化与治理工作已移至 [Activity V3](./v3.md)。

## 1. 背景

Activity V1 已完成统一业务事件的写入、分表存储和安全读取边界：

```text
领域业务变更
  -> Activity.log/3
  -> activity.<resource>_logs
  -> ArticleLog / CommunityLog 安全投影
```

V1 已提供：

- `Activity.log/3` 统一写入口；
- Post、Blog、Changelog、Doc、Community、DocTree、Press 的正式业务事件；
- 面向单篇 Article 的 `ArticleLog` 产品读取面；
- 面向 Community 管理范围的 `CommunityLog` Elixir 读取面；
- `audit.read` 权限和 action-specific payload / metadata 投影。

V1 没有为 CommunityLog 提供 GraphQL 字段，也没有 Dashboard 产品页面。V2 的核心任务是把已有 CommunityLog 安全读取面产品化，形成可检索、可追溯的社区 Activity 页面，而不是建立第二套日志存储。

## 2. 产品定义

Activity 回答：

```text
谁或哪个系统，在什么时候，对什么业务资源，执行了什么正式业务操作？
```

典型事件包括：

```text
Alice 发布了 Changelog「Activity V1」
Bob 将 Post「GraphQL Migration」移入回收站
System 执行 Community setup 失败
Carol 修改了 Press 配置
```

Activity 不是：

- Logger、Telemetry 或异常堆栈；
- Oban 执行和重试明细；
- 页面访问、地理位置、流量来源等 Web Analysis 数据；
- Notification Inbox，不提供天然的已读/未读语义；
- 当前业务状态的事实来源；
- 用于回滚或重放业务状态的 Event Sourcing 系统。

参考产品中的时间流、自然语言事件句式和关联事件折叠可以借鉴，但匿名 page view、访问地点和高频浏览行为继续属于 Analysis，不写入 Activity。

## 3. Dashboard 信息架构

### 3.1 菜单位置

V2 将 Activity 放在 Dashboard 的 CMS 分区末尾：

```text
CMS
├── Assets
├── Communities
├── Tags
├── Posts
├── Kanban
├── Changelog
├── Docs
├── ...
└── Activity
```

原因：

- Activity 当前主要服务社区内容管理、配置管理和责任追溯；
- CommunityLog 由 `audit.read` 保护，使用者与 CMS 管理者一致；
- Activity 不是访问趋势或转化分析，不应继续放在 Analysis；
- V2 只有一个治理页面，暂不为它新增只有一项的 Operations / Governance 分区。

未来出现 Moderation、Applications、Jobs、Risk Center 等更多治理产品后，可以整体抽成 Operations 或 Governance 分区。

### 3.2 路由

产品路由使用：

```text
/{community}/activity
```

不继续使用 `/{community}/log`：`Log` 容易与技术日志、流量日志混淆。V2 删除旧 `/log` 占位路由，不维护两个产品入口。

### 3.3 前端目录

Activity 使用独立产品目录，Dashboard route 只负责挂载：

```text
frontend/core/unit/DashboardThread/Activity/
├── index.tsx
├── List/
├── Item/
├── Filters/
├── Detail/
├── EmptyState/
├── query/
├── helper/
├── spec.d.ts
└── salon/

frontend/dashboard/src/app/[community]/activity/
├── layout.tsx
└── page.tsx
```

目录已经提供 Activity 上下文，内部组件不重复使用 `ActivityList`、`ActivityItem`、`ActivityFilters`、`ActivityDetail` 前缀。一个文件只定义一个组件；下层组件需要 salon 时自行调用 `useSalon()`，不从父组件传递 `s`。

## 4. 页面模型

### 4.1 主体布局

页面主体是倒序活动时间流，不使用传统审计表格作为默认视图：

```text
[头像] Alice 发布了 Changelog「Activity V1」
       2 分钟前 · Changelog

[头像] Bob 将 Post「GraphQL Migration」移入回收站
       今天 14:32 · Post

[系统] Community setup 最终失败
       昨天 22:10 · System
```

每条记录的稳定结构为：

```text
Actor + Action + Subject [+ Target]
时间 · 资源类型 · 来源
```

交互规则：

- 左侧显示用户头像、System 图标或事件类型图标；
- 主句使用产品自然语言，不直接显示 `title_changed` 等内部 action；
- Subject、Target 当前仍可访问时使用平台原生链接；
- 已永久删除的资源只显示安全 snapshot，不生成失效链接；
- 次要行显示相对时间、资源类型和必要的来源信息；
- 列表按今天、昨天或具体日期分组；
- 点击事件打开详情 Drawer；
- 列表不直接展开原始 payload 或 metadata JSON。

### 4.2 事件文案

事件文案不能由前端简单拼接 action 字符串。每个可见 action 需要稳定的文案模板和参数定义，例如：

```text
created          -> {actor} 创建了 {subject}
title_changed    -> {actor} 修改了 {subject} 的标题
published        -> {actor} 发布了 {subject}
trashed          -> {actor} 将 {subject} 移入回收站
solution_accepted -> {actor} 将 {target} 设为 {subject} 的最佳回复
setup_failed     -> {actor} 执行 {subject} setup 失败
```

未知 action 不由前端猜测语义。后端新增一个 CommunityLog-visible action 时，必须同时提供产品文案 key、分类和展示测试，或者通过共享生成结果同步给前端。

当前实现由 action contract 提供 `presentation.message_key`，GraphQL 暴露 `messageKey`，前端只消费显式文案模板；未知 key 使用安全通用文案，不回退显示内部 action。

### 4.3 Operation 分组

同一次 command 产生的多条事件共享 `operation_ref`。V2.1 允许逐条展示，V2.2 在当前列表页按 operation 折叠：

```text
Alice 更新了 Post「Activity V2」
├── 修改标题
├── 更新正文
└── 调整发布时间
```

只能按相同 `operation_ref` 分组，不能仅凭 actor 相同或时间接近合并事件。`parent_event_ref` 用于详情中的直接父子关系，不替代 operation 分组。

### 4.4 Activity Overview

页面最上方提供一整行 Activity Overview，V2.1 使用按日柱状图：

```text
┌────────────────────────────────────────────────────┐
│  Activity                                         │
│      ▂  ▅        ▃                                 │
│   ▃  █  █  ▂  ▆  █  ▄  ▁  ▃  ▇  ▅  ▂  ▄  ▆       │
│  08/08       08/14       08/20                    │
└────────────────────────────────────────────────────┘

[时间] [内容类型] [事件分类] [操作者] [更多筛选]

Activity 时间流……
```

每根柱子表示一个 UTC 自然日内、当前 Community 和当前筛选条件下可见的 Activity 数量。交互规则：

- Hover 显示完整日期和精确数量；
- 点击某一天，为下方 Activity List 增加该日时间范围；
- 再次点击同一天取消日期筛选；
- 选中柱使用明确的视觉高亮；
- 切换内容类型、事件分类、Actor 或 source 时，图表同步重新统计；
- 列表分页不触发图表重新统计；
- 图表 loading、empty 和 error 独立于列表；
- 移动端允许横向滚动，不把大量柱子压缩成不可点击的细线。

图表统计窗口与选中日期是两个独立状态：

```text
range
  决定图表展示的完整时间窗口，例如最近 30 天

selectedDay
  用户点击的某个 bucket，只过滤下方 Activity List
```

例如：

```text
/{community}/activity?range=30d&resourceTypes=post&selectedDay=2026-08-20&page=1
```

点击柱子后将列表页码重置为 1，但不能把图表统计窗口缩成选中的一天。前端使用后端 bucket 返回的 `[startedAt, endedAt)` 过滤列表，不自行拼接日期边界。

V3 可以在同一 Overview 位置增加周/月趋势或热力图，但新的展示形式不改变 Activity 事实模型。星期 × 小时热力图属于二维统计结果，不要求 V2.1 的日级 bucket 提前抽象成通用分析引擎。

## 5. 筛选与查询状态

### 5.1 V2.1 常驻筛选

- 时间：V2.1 当前交付为固定最近 7 天；今天、最近 30 天和自定义范围不进入本次 V2 验收；
- 内容类型：Post、Blog、Changelog、Doc、Community、Doc Tree、Press；
- 事件分类：内容、发布、回收与生命周期、互动与管理、审核、社区与系统；
- 操作者：当前 Community 范围内的用户或 System；
- 具体事件：该资源类型下允许在 CommunityLog surface 展示的 action。

底层 `resource_type` 和 Article `thread` 在当前模型中部分重叠。产品层统一使用“内容类型”，不同时暴露两个含义近似的技术筛选器。

### 5.2 高级筛选

- 来源 source；
- Subject / 资源关键字；
- operation ref 精确定位；
- 只看高风险操作。

`event_ref`、`operation_ref` 和 `parent_event_ref` 不作为默认筛选项，只进入高级搜索或事件详情。

### 5.3 URL 状态

筛选和分页进入 URL search params，使刷新、前进后退和复制链接保持同一视图：

```text
/{community}/activity?resourceTypes=post&categories=lifecycle&actorRef=user-ref&page=2
```

URL 使用稳定公开 ref 和产品枚举，不暴露数据库内部 ID。

## 6. 事件分类

底层 action 会持续增长，筛选器不能平铺全部 action。V2 增加稳定的产品分类。下表只列同时具有 `:community_log` surface 且 `producer_status = :active` 的当前可用 action：

```text
内容
  created
  title_changed
  body_updated

发布
  published
  released

回收与生命周期
  trashed
  restored
  archived
  permanently_deleted

互动与管理
  comment_pinned
  comment_unpinned
  solution_accepted
  solution_replaced
  solution_revoked

审核
  blocker_created
  blocker_released
  blocker_terminated

社区与系统
  activated
  setup_failed
  setup_retried
  config_updated

回收与生命周期
  destroy_scheduled
  destroy_cancelled
  destroyed
  lifecycle_reconciled
```

`draft_updated`、`comment_created`、`comment_updated` 等无 `:community_log` surface 的 internal action 不进入产品；`release_rescheduled`、`release_withdrawn`、`moderation_review_*` 等仅声明 contract、尚无 active producer 的 action 也不进入当前筛选配置。它们在 surface 或 producer 状态变化后，才能成为可用 action。

分类只决定产品筛选和展示，不改变存储 action 或 surface allowlist。为了让分类与 CommunityLog-visible action 使用同一声明源，V2 扩展各 resource action contract：

```text
classification
  category
  high_risk
```

约束：

- 每个具有 `:community_log` surface 的 action 必须声明 classification；
- `category` 使用受控 enum；
- `high_risk` 必须显式声明为 true 或 false，不使用隐式默认值；
- contract 测试验证所有 CommunityLog-visible action 的 classification 完整且合法；
- Dashboard 可用 action 取 `:community_log` visible actions 与 `producer_status = :active` 的交集；
- 前端不根据 action 字符串猜测 category 或 high risk；
- classification 是 V2 对 V1 contract 的兼容扩展，不改变 `Activity.log/3` facade 和既有事件数据。

## 7. 事件详情 Drawer

点击事件后展示：

- 完整事件描述；
- 操作者头像、昵称、登录名或 System；
- 绝对发生时间和明确时区；
- Subject 与可选 Target；
- 事件发生时允许展示的 snapshot；
- action contract 允许展示的 payload 变化；
- 允许展示的来源和 metadata；
- 同一 operation 下的关联事件；
- 可复制的 event ref。

Drawer 分期：

```text
V2.1
  当前事件详情
  同 operation_ref 的关联事件列表
  不在主列表折叠
  不展示 parent / child tree

V2.2
  根据 parent_event_ref 展示直接父子关系（由详情 API 独立读取并在 Drawer 展示）
  主列表按 operation_ref 折叠（已实现）
  提供稳定事件深链接（`eventRef` URL 参数已实现）
```

V2.1 返回 `eventRef`、`operationRef`；当前 V2.2 已将 `parentEventRef` 加入 CommunityLog SQL row、安全投影、GraphQL 和详情 API，并完成当前页按 `operationRef` 折叠、`eventRef` URL 深链接和文章管理表格跳转。

安全边界：

- Drawer 继续消费 `:community_log` surface 投影；
- GraphQL 不返回数据库原始行、完整 metadata 或内部字段；
- UI 不根据最后一条 Activity 推断资源当前状态；
- 若需要显示当前资源状态，应通过对应 CMS Reader 单独读取并明确标注；
- 已删除资源使用事件 snapshot，不能尝试通过私有 ID 恢复当前资源。

## 8. GraphQL 读取接口

### 8.1 Community Activity Query

V2 增加受保护的 Community Activity GraphQL query。产品字段使用 Activity 命名，领域内部继续使用 `CommunityLog`：

```graphql
communityActivity(community: String!, filter: CommunityActivityFilter): PagedCommunityActivity!
```

读取链路：

```text
Dashboard
  -> communityActivity GraphQL query
  -> login + audit.read + Community boundary
  -> Activity.list_community_logs/3
  -> CommunityLog UNION ALL query
  -> per-handler :community_log safe projection
  -> GraphQL response
```

返回分页结构：

```text
entries
pageNumber
pageSize
totalCount
totalPages
```

单条事件至少包含：

```text
id / eventRef
action
category
source
resourceType
actor
subject
target
payload
metadata
occurredAt
operationRef
```

其中 payload、metadata、snapshot 字段仍由 V1 action contract 的 `:community_log` surface 决定；V2 不能为了页面方便扩大为原始字段透传。

V2.2 为单条事件增加 `parentEventRef`，用于直接父子关系展示；该字段不属于 V2.1 Community Activity GraphQL 基础返回结构，当前已在 V2.2 API 中开放。

### 8.2 Filter

V2 读取协议增加：

```text
page
resourceTypes
actions
categories
actorRef
source
occurredAfter
occurredBefore
subjectQuery
operationRef
```

约束：

- page size 继续由服务端固定；
- 时间统一使用 UTC datetime，客户端只负责按用户时区展示；
- `occurredAfter` 和 `occurredBefore` 必须形成受控时间窗口；
- list、stats 和 export 的时间窗口必须满足 `after < before`，且不超过 366 天；
- 未知 resource type 或 action 在 GraphQL / 领域边界被拒绝；
- `categories` 先按 contract classification 展开成 active CommunityLog-visible actions；同时传 `categories` 与 `actions` 时，两者取交集；
- `resourceTypes × actions` 使用交集语义：每个 handler 只查询同时属于客户端 actions 与自身 active `:community_log` actions 的 action；
- resource type 与 action 都合法但组合没有交集时，返回合法空结果；
- 不支持所选 action 的 handler 不进入 UNION，不能退化为无 action 条件查询；
- Actor 和 Subject 查询不能绕过 Community 范围与 `audit.read`；
- filter 拒绝未知字段，不静默忽略错误条件。

`subjectQuery` 不对整段 snapshot、payload 或 metadata 执行任意全文搜索。当前 `Event.contract/4` 对 CommunityLog-visible action 明确声明 `subject_search: [:subject_ref, :subject_snapshot_title]`，因此支持 `subject_ref` 精确匹配和 `subject_snapshot.title` 模糊匹配；未来限制某 action 时必须收紧 contract，并保留精确 ref 匹配。

### 8.3 可用筛选配置

前端不能假定所有资源支持相同 action。V2 需要提供受控配置或共享生成结果：

```text
可见 resource types
每种 resource 的可见 actions
action 的 category
action 的 `messageKey`
action 是否属于高风险操作
```

其中 category 和 high risk 从 action contract 的 `classification` 派生，文案从 contract 的 `presentation.message_key` 派生；可用 action 还必须满足 `producer_status = :active`。不能维护一份会独立漂移的前端手写 action 全量表。

V2.1 提供独立的 `communityActivityConfig(community)` 查询返回当前可读 CommunityLog surface 的 resource、active action、`messageKey`、category 和 high-risk 标记。列表与统计查询仍各自独立；配置查询只负责筛选器选项，不能替代服务端的 filter 校验。

### 8.4 Community Activity Stats

顶部 Overview 使用独立统计查询，不把统计结果放进 `communityActivity` 分页响应：

```graphql
communityActivityStats(
  community: String!
  filter: CommunityActivityStatsFilter!
): CommunityActivityStats!
```

页面并行读取：

```text
Activity page
├── communityActivityStats -> 顶部 Overview
└── communityActivity      -> 下方 Activity List
```

独立接口保证：

- 列表翻页不会重复计算统计；
- 图表可以使用独立缓存和加载状态；
- 图表失败不阻断 Activity List；
- 图表的统计窗口与列表的选中日期可以独立表达；
- V3 增加热力图时不污染分页协议。

V2.1 统计 filter 支持：

```text
occurredAfter
occurredBefore
resourceTypes
actions
categories
actorRef
source
granularity = day
```

V2.1 只提供 `metric = count` 和 `granularity = day`，不实现任意 `groupBy + metric + dimensions` 分析引擎。

返回结构：

```text
granularity
timezone
totalCount
buckets
  startedAt
  endedAt
  count
```

后端必须补齐统计窗口内没有事件的日期并返回 `count = 0`，不能让不同前端图表分别推导缺失日期。时间 bucket 使用半开区间：

```text
occurred_at >= startedAt
AND occurred_at < endedAt
```

V2.1 以 UTC 自然日统计并返回 `timezone = Etc/UTC`。Activity 仍以 UTC 存储和查询；页面应明确统计时区，避免柱状图日期与列表范围不一致。未来若 Community 拥有正式 timezone 设置，后端可以把该时区自然日转换为 UTC 查询边界，同时继续返回明确的 timezone、`startedAt` 和 `endedAt`。

Stats 必须复用 CommunityLog 的权限和安全边界：

```text
login + audit.read + Community boundary
  -> handler / resource filter
  -> :community_log action allowlist
  -> actor / source / UTC time window
  -> daily count buckets
```

统计数字只包含当前读取面允许看到的事件，不能绕开 surface allowlist 统计底层原始 Activity 行。

后端领域入口增加：

```text
Activity.list_community_logs/3
Activity.get_community_log_stats/3
```

内部由 `CommunityLog.list/3` 与 `CommunityLog.stats/3` 承担。具体七表查询、filter normalization、handler/action 交集和 bucket 聚合可以下沉到 `Activity.CommunityLog.Query`；它不是新的顶层 Context，也不改变 `Activity.log/3` 写入 facade。

## 9. 权限

- 页面只对拥有 `audit.read` 的 Community 管理者可见；
- Sidebar 在无权限时隐藏 Activity 菜单；
- GraphQL 服务端始终执行登录、Community boundary 和 `audit.read` 校验；
- 隐藏菜单不是安全边界；
- Actor 搜索只返回当前 Community 范围内允许检索的主体；
- Community Activity 不进入公开社区页面；
- Article 页面未来若展示公开操作记录，继续使用 ArticleLog，不复用 CommunityLog；
- Action、payload 和 metadata 必须先通过 `:community_log` surface 才能进入 API。

## 10. 分页与性能

V2.1 延续 V1 的服务端固定 page size 和 offset pagination，避免在产品首版同时扩大存储与分页协议。

Activity 是持续增长的倒序事件流。offset pagination 存在两个长期问题：

- 翻页过程中插入新事件可能导致重复或遗漏；
- `UNION ALL + count(*) + OFFSET` 会随历史数据增长变慢。

V1 七张表已经具有普通索引：

```text
community_id + occurred_at + id
community_id + action + occurred_at DESC + id DESC
```

PostgreSQL B-tree 可以 backward scan，因此现有 `community_id + occurred_at + id` 通常已经能够支持无 action 的 Community 时间范围和倒序查询。不能仅因为查询使用 `ORDER BY occurred_at DESC` 就盲目增加一个 DESC 变体。

V2.1 应使用代表性数据对最近 7/30/90 天、全部或单一 resource、单 action / 多 action、带 Actor 的 list 和 stats 查询执行 `EXPLAIN (ANALYZE, BUFFERS)`。只有实际 plan、排序或 IO 证明现有索引不足时才调整索引。

需要重点评估而非预先创建的组合包括：

```text
community_id + actor_id + occurred_at + id
```

统计查询应复用与 CommunityLog 相同的七表 handler 集合，通过 `UNION ALL` 读取满足 Community、surface、筛选和时间范围的 `occurred_at`，再由 PostgreSQL 按日分组。resource type 筛选通过减少参与 UNION 的 handler 实现，不新增冗余的统一 resource type 字段。

索引是否落地以实际 query plan 和基准为准，不为每个筛选组合盲目增加索引。

当前同步导出限制为 5,000 条，使用一次 count 加一次批量 UNION 读取，不按 30 条产品分页循环查询；超过同步边界的异步导出属于 V3。

当真实数据量或实时体验超过阈值后，V3 再升级为基于稳定排序键的 cursor/keyset pagination。排序必须继续处理相同 `occurred_at` 下的确定性顺序。

V2.1 不新增每日统计表。Activity 原始事件已经包含 `community_id`、`occurred_at`、action、actor 和 source 等统计维度，优先直接聚合以保持单一事实来源，并避免双写、补偿和重算协议。

只有出现以下性能证据后，V3 才考虑 `activity.community_daily_stats` 一类可重建 projection：

- 30/90 天统计超过响应时间目标；
- Activity 规模使七表实时聚合不可接受；
- Dashboard 请求使统计查询成为数据库热点；
- 热力图等长期多维统计具有稳定、明确的查询模式。

持久化 rollup 不能成为 Activity 权威事实来源。它需要支持从原始 Activity 重算和定期校正；维度必须按真实查询模式设计，不能预先建立包含 actor、action、source 等全部组合的万能统计表。

## 11. 页面状态与可访问性

V2 页面必须覆盖：

- 首次加载骨架；
- 筛选切换 loading；
- 无任何 Activity 的初始空状态；
- 当前筛选无结果；
- 权限不足；
- 查询失败及重试；
- 已删除或不可访问的 Subject / Target；
- Drawer 的键盘关闭、焦点归还和可访问标题；
- 筛选控件的键盘操作和明确标签；
- 时间的绝对值 tooltip，避免只显示模糊相对时间。

## 14. 验收标准

- Dashboard 使用 `Activity / 活动记录` 产品命名和 `/activity` 路由；
- Activity 位于 CMS 分区，不归入 Analysis；
- 页面读取现有 CommunityLog 安全投影，不建立第二套日志；
- 页面顶部提供完整宽度的 UTC 日 Activity 柱状图；
- 图表通过独立 `communityActivityStats` 查询读取，不进入分页响应；
- 每个 bucket 返回明确的 `startedAt`、`endedAt`、count 和 timezone；
- 没有 Activity 的日期由后端补齐为零；
- 点击 bucket 只过滤列表，不缩小图表统计窗口；
- 图表统计遵守 Community、`audit.read` 和 `:community_log` surface；
- 页面和 API 由 `audit.read` 保护；
- UI 清楚表达 Actor、Action、Subject、Target 和 occurred at；
- 时间、内容类型、事件分类、Actor 和 action 筛选可组合使用；
- `resourceTypes × actions` 使用交集语义，空交集返回空结果，未知值被拒绝；
- `categories` 从 contract classification 展开，与显式 `actions` 同时存在时取交集；
- 不支持 action 的 handler 不进入 UNION，也不会退化为无 action 筛选；
- 筛选状态可通过 URL 恢复；
- URL 与 GraphQL 统一使用 `resourceTypes`、`actions`、`categories`、`actorRef` 等领域名称；
- 未知或不可见 action 不泄露内部数据，也不由前端猜测展示；
- 筛选配置只包含 active CommunityLog-visible actions；
- 每个 CommunityLog-visible action 都有 contract-owned category 和显式 high-risk 标记；
- Detail Drawer 只展示 action contract 允许的字段；
- 已删除资源使用安全 snapshot 并取消失效导航；
- 相同 operation 可追溯，且不会按时间接近误合并；
- V2.1 返回 event ref 和 operation ref，V2.2 额外返回 parent event ref 并展示基础父子关系；
- GraphQL 不暴露数据库内部 ID、原始 metadata 或完整 payload；
- 时间查询使用 UTC，页面按用户时区展示；
- 当前状态仍由业务 owner 读取，不从最后一条 Activity 推断；
- V2.1 对七表聚合查询具有可复现的性能基准；
- 索引调整以实际 EXPLAIN 为依据，不重复创建仅排序方向不同的索引；
- ArticleLog 与 CommunityLog 继续保持各自产品和权限边界。
