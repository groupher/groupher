## 0. 无兼容前提

旧 Audit 全链路先按退役清单删除，为本设计清理基础；不包装 AuditBot，不复用旧
legal/illegal/audit_failed、pending 占位、旧 facade、provider payload 或旧状态到新状态翻译层。

新实现复用通用 Gate/Lifecycle/Command 和资源存储能力，业务行为完全按本文重新定义。

## 1. 产品定位与归属

AlertBoard 是管理员查看风险、举报和待处理事项的事务公告板，不是普通用户公告发布工具。
ReviewBot 是自动检测执行者。二者面向 CMS、Accounts 等领域，采用顶层 Context：
`GroupherServer.AlertBoard`、`GroupherServer.ReviewBot`，不放在 CMS 内。

```text
帖子 / 评论提交      用户举报内容 / 用户      平台 Doc 检测
       |                     |                     |
       +---------------------+---------------------+
                             v
                        AlertBoard
              待处理 / 自动处理 / 已处理
              规则、举报事实、事项、正式决定
                             |
                     ReviewBot 自动检查
                 词库 / Jev / 图文模型
                             |
                   自动决定或人工处理
                             v
                  资源所属领域正式 Command
                    Gate + Lifecycle
                             |
                 Activity + 可靠派生效果
```

Board 只呈现值得处理或追踪的事项，普通检测通过不必生成公告条目。
执行任务状态和 provider 日志归 ReviewBot，不把公告板变成技术日志。

| Owner               | 拥有                                                        | 不拥有                             |
| ------------------- | ----------------------------------------------------------- | ---------------------------------- |
| AlertBoard          | 平台/社区审核配置、举报事实、事项聚合、处理决定、管理员视图 | 直接修改 CMS/Accounts 资源状态     |
| ReviewBot           | 内容检查、Check/Attempt、provider adapter、归一化信号       | 权限授权、直接处罚、资源可见性权威 |
| 领域 Command        | canonical resource、授权、并发保护、事务、执行决定          | 调用 AI 并等待外部请求完成的长事务 |
| Lifecycle           | 资源状态、有效限制、允许转换及独立解除                      | 审核队列、模型分数、操作者角色判断 |
| Gate                | actor/action admission、可组合读取过滤                      | AI 调用、逐行检查外部审核服务      |
| Activity / 操作审计 | 正式业务事实与责任历史                                      | 从最后一条日志推导当前可见性       |

Moderator 是已有管理员身份/关系；不能因为删除旧 Moderation 名称而删除管理员能力。
CMS Gate 保持 CMS-owned，不因 AlertBoard 跨领域而建立全局万能 Gate；Accounts 通过其正式领域准入执行。

## 2. UGC 发布模式

帖子、评论分别配置；默认模式为提交后可见。社区不能关闭平台强制规则。

| 模式          | 当前提交对普通用户               | ReviewBot                                       | 公开条件                   |
| ------------- | -------------------------------- | ----------------------------------------------- | -------------------------- |
| 默认可见      | 立即可见                         | 平台/社区违禁词规则始终执行；社区可开关模型检查 | 命中后施加限制             |
| AI 初审后可见 | 检查期间仅作者与有权限审核员可见 | 必须开启                                        | 自动通过；不确定转人工     |
| 强制先审后发  | 审批期间仅作者与有权限审核员可见 | 可辅助初审                                      | 人工批准且没有其他有效阻断 |

“普通用户可见”仍需满足社区访问权限与父资源 Lifecycle，不表示私有社区内容全网公开。
管理员身份不自动等于所有社区的审核权限；作者能看自己的内容不等于能批准自己。

违禁词词库检查与模型检查是两个独立通道：平台及社区已配置词库始终执行，社区开关只控制模型后台检查。
自动检测开关与发布模式是两个维度。AI 初审模式不能配置成没有任何可用检查执行者；
配置校验应拒绝这种组合。强制人工模式下 AI 通过不能代替人工审批。
明确违禁词命中时应阻止或撤销普通可见性；默认可见模式不能承诺异步 AI 返回前零曝光。

### 2.1 编辑

首次发布模式与编辑模式分开。编辑可选择立即可见并按配置检查，或 AI 通过后可见。
首次发布要求人工批准，不自动意味着以后每次编辑都要人工批准。命中、不确定或人工要求时复审。

```text
当前内容 A -> 作者提交 B -> 当前内容 B
                               |
                +--------------+---------------+
                |                              |
          编辑立即可见                  编辑 AI 检查后可见
          B 可见，后台检查               整篇暂时普通不可见
          命中后限制                     检查通过后 B 可见
```

普通 Article/Comment 不存在“普通用户继续看 A，作者和管理员看待审 B”的产品逻辑。
不新增待审版本列表、双公开头、Comment 版本体系或普通 Article 历史恢复能力。
已有内部 ArticleRevision/Draft/Public 存储结构保留，不因为其存在就扩展产品版本语义。
已有待审/违规/人工限制不能通过再次编辑直接清除。

### 2.2 Doc

Doc 由有权限的管理员发布，沿用已有 Draft/Branch/Release/历史机制，不套用社区 UGC 三种发布模式。
Doc 对应平台自己的内容安全检测；社区关闭 ReviewBot 不关闭平台检测。
Doc 平台检查需绑定具体 branch/content identity，preview 结果不得影响 main；整资源平台限制须显式表达。
Doc 下的普通用户评论仍遵守评论 UGC 审核模式。
V1 平台 Doc 固定发布后检测，命中限制相应 branch；社区 UGC 开关不影响平台执行。

## 3. 当前内容与过期结果保护

不创建产品版本体系，但检测和人工审批必须指向确切的当前内容：

```text
ReviewBot 开始检查 B
作者修改为 C
B 的结果回来 -> 当前不是 B -> 标记过期，不修改 C 的状态
```

内容标识使用现有 revision/body identity 与规范化内容、不可变资产版本计算 hash，具体字段与并发 epoch 见实施合同 §3.3。
仅保存 URL 不能证明图片内容未变化。评论不为此增加可浏览的历史版本。
管理员打开 B 后作者改成 C，批准 B 返回内容已变化，要求重新查看。
正在处理的 payload 必须对应提交时的确切内容，不能任务标为 B 却临时抓取 C；
使用不可变内容引用与短期检测 payload；payload 最长 24 小时、终态清空，访问仅限执行身份，不永久复制正文历史。

Check 执行状态（排队、执行中、完成、失败、过期）与 Case 处理状态分开。
失败不是违规，也不是通过。AI 初审失败继续限制并有限重试/转人工；
默认可见模式不能仅因 provider 超时自动标违规。强制人工模式保留人工待审条件。

结果应用需要同时校验内容标识、有效 attempt、适用规则版本、当前人工决定和 Lifecycle 状态。
重试/重复回调幂等；旧 AI 结果不能撤销较新的人工限制，也不能恢复 deleted/destroy 资源。

## 4. ReviewBot 与规则

```text
平台词库 + 社区词库 -> 确定性命中
平台规则 + 社区自然语言规则 + 必要上下文 -> Jev / 其他模型
图片 -> 具备覆盖能力的图文检测，必要时 OCR
                                |
                    统一信号 + 检查覆盖情况
                                v
                   AlertBoard Policy 正式决定
```

支持管理员自定义 Prompt/规则，并记录规则版本。标准与执行权限分开：
自然语言定义“什么算推广”，产品配置定义“此类命中可否自动限制”。Prompt 不授予账号封禁权限。
被审正文和举报文本是待分析数据，不能改变检查指令或可执行动作集合。
确定性规则、模型分类、未覆盖项目和调用失败分别记录；不支持图片的 adapter 不得把图片判为通过。

Jev 作为优先验证的判断引擎候选，支持把多个窄问题组成检查标准；不在本文承诺具体速度、准确率或多模态覆盖。
OpenAI 等 provider 同样通过 adapter 接入，统一业务信号，不假设兼容 API 等于能力相同。
执行编排固定在 Phoenix/Oban；Jev 使用 judge_http wire adapter，OpenAI 使用独立 adapter，配置与能力验收见实施合同 §7。旧 Sentinel 的服务形态不继承。

外部调用在数据库事务外执行。提交事务保存当前内容、必要限制和可靠任务；
提交成功可以返回“检查中”，不必在 HTTP 请求内等待 AI。请求/回调应认证、幂等并绑定执行身份。

Policy 只消费已加载 facts，不查库、不调用 provider、不修改状态；自动和人工决定都经正式 Command。
平台限制只能由平台授权解除，社区不能以自定义 Prompt 覆盖平台规则。
多社区 Article 的社区规则适用范围须显式携带 community，不能把社区命中无条件写成全局限制；
物理落点为资源 Lifecycle-owned review_restrictions 表。Article 与 Comment 的 Gate 查询直接读取 Lifecycle 和限制事实；ArticleBinding、ArticlePublic 不保存可见状态。Doc 仍使用 branch-scoped DocPublic 发布投影，详见实施合同 §3.3/§5。
Article 的正文修订由多个 Binding 共享，因此编辑时对平台和每个现存社区 scope 分别执行编辑策略；镜像/迁移新建目标 Binding 时，先按目标社区首次发布策略检查当前修订，迁移同时结束源社区 scope 的有效限制。

## 5. 举报与事项聚合

内容举报、用户举报和 ReviewBot 信号统一在 AlertBoard 管理，但事实来源独立：

```text
举报人 A 的举报 ─┐
举报人 B 的举报 ─┼-> 一个相关审核事项 -> 正式决定
ReviewBot 结果 ──┘
```

举报事实记录提交者、对象、原因、撤销；AI 结果不能伪装成用户举报。
聚合应区分对象、社区/平台范围与相关内容标识，不能把不同社区或已过期结果混在一起。
举报数量可触发优先级或检查，不直接等于违规结论。
Report submit/withdraw 与重复举报约束由 AlertBoard 从零实现；旧举报记录、viewer_has_reported 与旧统计投影随旧链删除，不做历史回填。
撤销举报不自动撤销已经生效的正式决定。

内容限制交给 CMS；社区禁言交给成员管理领域；平台账号限制交给 Accounts。
V1 用户举报支持受理、驳回和人工处理记录；不提供封号/禁言命令或 AI 账号处罚。此范围已冻结，接口不得暴露未实现处罚动作。

## 6. 可见性与限制

Reader/FrontDesk 继续现有资源读取合同，不增加一套审核专用加载框架。
Gate Load/typed Context 仅按需增加权威 facts；Scope 在 SQL 中组合可见性，不逐行请求 ReviewBot。

```text
父资源与社区可读
  AND 资源 Lifecycle 允许
  AND 当前读取身份满足审核限制
       -> 返回当前内容
```

评论可见性必须叠加父 Article/Doc 与社区权限。作者/管理员的特许读取不能写入共享公共缓存。
公共列表、详情、批量、count、搜索、Feed、通知摘要、图片访问均需覆盖；不能只遮挡 UI。
批准只解除对应限制，不撤销其他人工/平台 blocker，也不恢复删除资源。
普通 Article 的 ArticlePublic/ArticleBinding 不保留 `visible` 投影列，也不维护第二份可见性事实；列表、详情、搜索、计数和副作用统一复用 Gate Scope。DocPublic 的 `visible` 只表达 Doc branch 发布合同，不替代 DocLifecycle 或 DocReviewRestriction。
