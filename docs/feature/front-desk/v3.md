## 1. 问题

当前同时存在四种名字相近但职责不同的 FrontDesk：

```text
GroupherServer.FrontDesk
GroupherServer.CMS.FrontDesk
GroupherServer.Accounts.FrontDesk
GroupherServerWeb.Middleware.FrontDesk
```

其中 Root FrontDesk 已经转发大部分 User、Community、Article、Comment 和稳定关系读取，
但上层调用方仍混用 Root 与领域 FrontDesk。CMS FrontDesk 还平铺了 Revision projection、
ViewTracker 事务锁和 Article Insights 等专用 workflow 能力，导致“单资源入口”和“所有与资源有关的
函数”边界不清。

审计时的主要偏差是：

1. GraphQL middleware、resolver、schema projection 既调用 Root FrontDesk，也直接调用
   `CMS.FrontDesk`；
2. Accounts、Messaging 等跨领域消费者直接依赖 `CMS.FrontDesk`；
3. Web Context 直接依赖 `Accounts.FrontDesk`；
4. `CMS.FrontDesk` 暴露 projection builder、transaction lock 和产品专用 admission；
5. User cache/revalidation 位于 Root FrontDesk，但 `Accounts.FrontDesk` 反向依赖 Root cache，
   Root 还不是纯委托层；
6. `GroupherServerWeb.Middleware.FrontDesk` 是 transport loader，不是资源读取 facade，重名进一步增加
   了阅读成本；
7. Root 与 CMS facade 仍暴露无生产调用者的 `comment(article_path, inner_id[, opts])` 双参定位形状；
8. Root `comment/1` 只接受 map，integer 等非法 locator 会触发 `FunctionClauseError`，没有委托 CMS
   facade 返回 fail-closed error tuple；
9. `user(login)` 使用完整 User cache，`user(id)` 直接读取数据库；同名 API 的缓存行为随 locator 分化，
   但此前文档没有明确记录。

本次修复默认只改变模块所有权、调用方向和命名，不改变 public/management/internal 可见性、
Gate action、Lifecycle 状态矩阵、SQL 过滤、锁强度、GraphQL contract 或错误协议。任何行为变化必须
另立合同和测试，不能夹带在 FrontDesk 迁移中。

## 2. 决策摘要

### 2.1 Root 是上层统一入口

Application、GraphQL transport 和跨领域调用统一使用扁平的 Root FrontDesk：

```elixir
GroupherServer.FrontDesk.user(ref)
GroupherServer.FrontDesk.community(ref, actor_or_opts)
GroupherServer.FrontDesk.article(ref, actor_or_opts)
GroupherServer.FrontDesk.comment(ref, actor_or_opts)
GroupherServer.FrontDesk.article_author(resource)
GroupherServer.FrontDesk.article_of(comment)
GroupherServer.FrontDesk.thread_of(resource)
```

Root FrontDesk 只负责稳定 API、参数分发和领域委托：

```text
GraphQL / application / cross-domain caller
  -> GroupherServer.FrontDesk
  -> CMS.FrontDesk | Accounts.FrontDesk
  -> resource-owned FrontDesk implementation
  -> Gate Scope / stable internal lookup / Repo
```

Root 不重新实现 CMS 或 Accounts 的读取规则，不直接拥有 CMS Gate/Lifecycle 语义，也不把所有领域
专用函数镜像成全局 API。

### 2.2 Owner 领域内部使用领域 FrontDesk

领域内部不为形式统一绕到 Root 再回到自己：

```text
CMS internal       -> CMS.FrontDesk
Accounts internal  -> Accounts.FrontDesk
CMS -> Accounts    -> GroupherServer.FrontDesk -> Accounts.FrontDesk
Accounts -> CMS    -> GroupherServer.FrontDesk -> CMS.FrontDesk
```

允许直接使用领域 FrontDesk 的代码必须属于对应 owner context。Command、Event、Writer、Gate 等模块
读取本领域顶层资源时继续遵守 V2 的单资源入口规则，但使用本领域 FrontDesk，不产生
`CMS -> Root -> CMS` 的反向跳转。

### 2.3 保持扁平资源 API

本次不引入第二套 `FrontDesk.Article.get/1`、`FrontDesk.Comment.get/1` 公共 API。稳定通用入口继续是：

```elixir
FrontDesk.article(...)
FrontDesk.comment(...)
FrontDesk.community(...)
FrontDesk.user(...)
```

Elixir namespace 若使用资源子模块应写成 `FrontDesk.Article.xxx`，不是
`FrontDesk.article.xxx`；但只把少数特殊方法放进资源子模块、同时保留根模块普通读取，会形成两套
公共入口，因此本次明确不采用。

### 2.4 专用 workflow 回到 owner context

以下能力不因“与 Article 有关”就自动属于 FrontDesk：

- immutable Revision projection；
- 已加载 parts 的 result assembly；
- ViewTracker transaction lock/revalidation；
- Article Insights 专用 admission 和指标查询；
- list、page、search、count、aggregate、maintenance scan。

FrontDesk 的判断标准是“根据稳定引用加载一个通用 canonical resource 或稳定业务关系”，不是
“函数参数或返回值里出现了 Article”。

## 3. 调用边界

| 调用方                                    | 目标入口                                       | 禁止依赖                                           |
| ----------------------------------------- | ---------------------------------------------- | -------------------------------------------------- |
| GraphQL middleware/resolver/schema helper | `GroupherServer.FrontDesk` 或明确的产品 facade | `CMS.FrontDesk`、`Accounts.FrontDesk`              |
| CMS 外的 application/context              | `GroupherServer.FrontDesk`                     | `CMS.FrontDesk`                                    |
| Accounts 外的 application/context         | `GroupherServer.FrontDesk`                     | `Accounts.FrontDesk`                               |
| CMS owner 内部                            | `CMS.FrontDesk`                                | 为读取 CMS 资源而绕经 Root                         |
| Accounts owner 内部                       | `Accounts.FrontDesk`                           | 为读取 Accounts 资源而绕经 Root                    |
| Revision recovery/projection              | `CMS.Articles` 的 Revision owner               | FrontDesk projection helper                        |
| ViewTracker transaction                   | `CMS.ViewTracker` 内部 loader/lock             | FrontDesk transaction lock                         |
| Article Insights                          | `Analysis.ArticleInsights`                     | 通用 public Article loader 预先收窄 Insights scope |

`GroupherServerWeb.Middleware.FrontDesk` 仍是 Absinthe middleware，不属于上述资源 facade 层级。
本次可保留模块名以控制迁移范围；若后续改名，应单独迁到 `Middleware.ResourceLoader`，不能与资源
facade 重构混为一次行为修改。

## 4. 遗留 FrontDesk surface 处置

V2 §2.4 曾保留 ViewTracker 和 Insights 的三个具名 FrontDesk 入口。V3 根据实际调用链重新分类：

| 当前入口                           | 当前行为与调用者                                                                     | V3 处置              | 目标边界                                                                 |
| ---------------------------------- | ------------------------------------------------------------------------------------ | -------------------- | ------------------------------------------------------------------------ |
| `article_revision/4`               | 根据 Article/Revision ID 加载历史 projection；无生产调用者                           | 删除，不保留 wrapper | 未来需要时由 `CMS.Articles.RevisionProjection.load/4` 明确拥有           |
| `article_revision_parts/4`         | 从已加载 Article、Community、Revision 构造 result；由 `Articles.RevisionResult` 调用 | 迁移后删除           | `CMS.Articles.RevisionProjection.build/4`                                |
| `article_for_view_tracking/1`      | 只是默认 public `article` read 的别名；resolver 调用                                 | 删除                 | 上层使用 Root `FrontDesk.article/1` 后调用 `CMS.ViewTracker.track/4`     |
| `lock_article_for_view_tracking/1` | ViewTracker 事务内 `FOR KEY SHARE`、重新加载与 public revalidation                   | 迁移后删除           | `CMS.ViewTracker.ArticleLock.lock_and_revalidate/1` 或 `Record` 私有实现 |
| `article_insights/3`               | path load 加 `:read_insights` admission；GraphQL middleware 调用                     | 迁移后删除           | `Analysis.ArticleInsights.trend_by_path/3` 统一 orchestration            |

### 4.1 Revision projection

目标调用链：

```text
Command Confirmation
  -> CMS.Articles.RevisionResult.build/2
  -> CMS.Articles.RevisionProjection.build/4
  -> ArticleTransportResult.decorate/3
```

`RevisionProjection.build/4` 接收已加载的 Article、Community 和 ArticleRevision，负责 BodySnapshot、
author preload、revision metadata 与 projection assembly。它不伪装成资源 lookup；旧的
`CMS.FrontDesk.article_revision/4` 与 `article_revision_parts/4` 已删除。
BodySnapshot 读取、revision metadata、stable lifecycle/tags/extensions 和 Article result assembly
现在都由 `CMS.Articles.RevisionProjection` 内部 helper 完成，`CMS.FrontDesk.Article` 只保留资源
读取与 stable visibility/projection 的 FrontDesk 职责。

`article_revision/4` 当前没有调用者，直接删除。未来只有出现真实的产品级 Revision locator 合同后，
才新增 `RevisionProjection.load/4`；不得预留无调用者的 FrontDesk compatibility API。

### 4.2 ViewTracker public load

`article_for_view_tracking/1` 当前等价于默认 public Article 读取，没有专用 admission。resolver 已统一为：

```text
ArticlePath
  -> GroupherServer.FrontDesk.article/1
  -> CMS.ViewTracker.track/4
```

Root FrontDesk 只负责 public canonical Article；RequestActor classification、dedupe、计数和 MetricEvent
仍由 ViewTracker 拥有。

### 4.3 ViewTracker transaction lock

`lock_article_for_view_tracking/1` 是 ViewTracker 写事务的内部步骤，不是公共资源读取。迁移必须保持：

- `FOR KEY SHARE` 的锁时机与强度；
- 同一事务内重新确认目标 Article；
- 当前 public/Lifecycle/moderation 可见性；
- `branch_id` 保留；
- `received_at` 的 UTC 秒精度与生成时机；
- 失败时由 ViewTracker transaction rollback；
- 不引入额外 query 或事务外 revalidation。

迁移后的 Record 私有 loader 仍通过 Article stable public path 完成 revalidation，保留原有 admission、
SQL、Lifecycle 与并发语义；锁不再暴露为 FrontDesk API。

### 4.4 Article Insights

目标链路：

```text
GraphQL ArticlePath + viewer + filters
  -> Analysis.ArticleInsights.trend_by_path/3
  -> Insights 专用 path resolution + :read_insights admission
  -> canonical Article
  -> hourly projection query
  -> trend DTO
```

已删除 middleware load；`Analysis.ArticleInsights.trend_by_path/3` 先用 typed Insights Scope 完成
path resolution，再执行趋势查询。`trend/3` 仍保留对已解析 Article 的最终 Gate admission，供内部调用和
legacy projection 使用。
Insights 不得先经过只支持普通 public lifecycle 的 Article read，再执行 `:read_insights`；否则可能在专用
Gate action 前提前排除 management-readable Article/Community。

`trend_by_path/3` 保持 typed Article/Doc Scope Context、explicit actor、fail-closed 和现有 passport
grant 语义。Analysis 只组合 CMS 的 path/Gate 能力，不复制 Article public visibility policy。

### 4.5 Comment locator 与 fail-closed

Root 和 CMS facade 当前同时暴露：

```elixir
FrontDesk.comment(article_path, inner_id)
FrontDesk.comment(article_path, inner_id, opts)
```

这组公开 overload 已无生产调用者，而且与 canonical `CommentPath`、internal stable comment id 两种
locator 合同重复。V3 直接删除 Root/CMS facade 的双参和三参 overload，不保留 compatibility wrapper。

`CMS.FrontDesk.Comment.read(article_path, inner_id, actor, opts)` 仍可作为结构化 CommentPath 解析后的
内部实现；它不构成 caller-visible locator contract。

Root `comment/1` 必须像 CMS facade 一样对非法 locator 返回标准 error tuple，不得抛出
`FunctionClauseError`。目标行为至少覆盖：

```elixir
FrontDesk.comment(comment_path)                   # public CommentPath
FrontDesk.comment(comment_id, mode: :internal)   # trusted stable id
FrontDesk.comment(comment_id)                    # fail-closed error tuple
FrontDesk.comment(invalid_ref)                   # fail-closed error tuple
```

Root/CMS facade 的双参、三参 comment locator 已删除；CMS Comment reader 内部仍可使用结构化
`CommentPath` 解析后的实现函数。

## 5. Root 与领域 facade 的目标形状

Root 保留扁平稳定 API，并尽量使用纯 `defdelegate` 或薄 pattern-matched dispatch：

```elixir
def article(ref), do: CMS.FrontDesk.article(ref)
def article(ref, opts) when is_list(opts), do: CMS.FrontDesk.article(ref, opts)
def article(ref, actor), do: CMS.FrontDesk.article(ref, actor)
def article(ref, actor, opts), do: CMS.FrontDesk.article(ref, actor, opts)
```

Root 不接受以下形状：

```elixir
FrontDesk.article_revision(...)
FrontDesk.article_for_view_tracking(...)
FrontDesk.lock_article_for_view_tracking(...)
FrontDesk.article_insights(...)
FrontDesk.Article.get(...)
```

领域 facade 继续拥有资源读取语义：

```text
CMS.FrontDesk
  -> CMS.FrontDesk.Article
  -> CMS.FrontDesk.Comment
  -> CMS.FrontDesk.Community
  -> CMS.FrontDesk.Relation

Accounts.FrontDesk
  -> User lookup/cache owner
```

`CMS.FrontDesk.Article` 是 CMS FrontDesk 的资源实现模块，不作为上层第二套公共入口。上层不能通过
模块路径绕过 `CMS.FrontDesk` 或 Root FrontDesk。

## 6. User cache 与 revalidation 所有权

当前依赖方向是：

```text
Root FrontDesk
  -> Root FrontDesk.Cache
  -> Root FrontDesk.Revalidate
  -> Accounts.FrontDesk

Accounts.FrontDesk
  -> Root FrontDesk.Cache
```

该结构让 Root 同时承担路由和 Accounts 基础设施所有权。目标是把 User cache/revalidation 下沉到
Accounts：

```text
GroupherServer.FrontDesk.user/revalidate
  -> Accounts.FrontDesk
  -> Accounts.FrontDesk.Cache / Revalidate
```

当前缓存行为必须显式保留为已知 locator 差异：

```text
user(login) -> 完整 User cache，可返回缓存值
user(id)    -> 当前数据库读取，不经过完整 User cache
fresh_user  -> 当前数据库读取，绕过完整 User cache
```

V3 的 ownership 搬迁不静默改变这一一致性行为。是否为 integer id 建立完整 User cache key 属于独立的
行为与 invalidation 设计；在完成 key、login/id 双向映射和写后失效审计前，不把 `user(id)` 描述成
cache-enabled。V1/V2 中“`user/1` 允许返回缓存”的表述仅适用于 login locator。

迁移要求：

- `user/1`、`fresh_user/1`、`revalidate().user/1` 的一致性合同不变；
- cache pool/key、missing/error mapping 与 `ORM.fill_meta` 语义不变；
- User 写后 cache invalidation 仍在成功提交后发生；
- Root 可以保留 `revalidate/0` 作为稳定跨领域 API，但实现只委托 Accounts；
- 不借此把 cache option、preload 或 ORM shape 暴露给 Root 调用者。

  `pnpm docs:check` 仍报告其他既有 CMS Command/DocTree 文档问题。

## 9. 静态约束

至少建立以下 protected-boundary 规则：

1. `groupher_server_web/**` 不得直接 alias/call `CMS.FrontDesk` 或 `Accounts.FrontDesk`；
2. `groupher_server/accounts/**` 不得直接依赖 `CMS.FrontDesk`；
3. `groupher_server/cms/**` 不得为读取 CMS 资源绕经 Root FrontDesk；跨 Accounts 读取除外；
4. `CMS.FrontDesk` 不得新增 lock、write、list、aggregate、product report 或已加载 parts assembly；
5. `CMS.FrontDesk.Article` 等实现模块不得被 Web、跨领域模块或 support helper 直接调用；
6. GraphQL/HTTP/CLI/MCP 输入不得选择 `mode: :internal`；
7. 未知 mode/view、非法 locator/mode 和 actor/mode mismatch 继续 fail closed。

静态规则只保护依赖方向，不能替代行为测试。

## 10. 验证矩阵

### Root/领域委托

- Root User/Community/Article/Comment 的 public、management、internal 合法组合与领域 FrontDesk 等价；
- Root 只改变入口，不改变 ErrorCat reason/code/details；
- CMS/Accounts owner 内部无 Root 反向跳转；
- Web 和跨领域代码无领域 FrontDesk 直接依赖；
- CommentPath 与 internal comment id 进入同一 mode-aware API，非法 locator 返回 error tuple；
- Root/CMS facade 不再暴露 Comment article-path + inner-id overload。

### Revision

- create/update/publish 首次执行和 receipt recovery 返回同一 revision-rooted result；
- recovery 不读取当前 ArticlePublic head；
- Doc branch metadata、publication version、published_at 和 BodySnapshot 保持一致；
- 无 `article_revision/4`、`article_revision_parts/4` 残留调用。

### ViewTracker

- counted、duplicate、excluded 和 rollback 行为不变；
- transaction lock 与 revalidation 仍处于同一事务；
- lifecycle/moderation 变化时保持迁移前可见性结果；
- query count 与 lock SQL 不回退；
- resolver 只通过 Root FrontDesk 获取初始 public Article。

### Insights

- author、moderator/passport grant、global god 与无权限用户矩阵；
- suspended/archived/management-readable lifecycle 不被普通 public loader 提前过滤；
- Post/Blog/Changelog 使用 Article Scope Context，Doc 使用 Doc Context；
- 每次请求只有一条明确的 Insights admission 链；
- trend bucket、metric filter、actor type 与 authentication filter 不变。

### User cache

- `user(login)` 可命中完整 User cache；
- `user(id)` 保持当前数据库直读，不被 ownership 搬迁静默改成 cache hit；
- `fresh_user` 绕过完整 User cache；
- `revalidate().user` 刷新缓存；
- 写后 invalidation/revalidation 时机不变；
- Root 与 Accounts 返回同一稳定 User projection。

## 11. 非目标

V3 不处理：

- 改变 public/management/internal 的语义；
- 修改 Gate action、Lifecycle 状态矩阵、moderation 或 passport policy；
- 把 Gate 提升成全局 facade；
- 将 Draft、Revision、Lifecycle、Receipt 或 ViewTracker state 提升为顶层 FrontDesk 资源；
- 把列表、分页、搜索、计数或报表塞进 FrontDesk；
- 全面重命名 `GroupherServerWeb.Middleware.FrontDesk`；
- 改变 GraphQL schema、客户端 contract 或 ErrorCat numeric code；
- 为旧入口保留 compatibility layer。

## 12. 完成定义

满足以下条件后，FrontDesk V3 才能标记 implemented：

- Web、transport 和跨领域调用只通过 Root FrontDesk 或明确的产品 facade；
- CMS/Accounts owner 内部直接使用领域 FrontDesk，不经过 Root 回跳；
- Root 保持扁平 User/Community/Article/Comment 与稳定关系 API；
- `article_revision/4`、`article_revision_parts/4`、`article_for_view_tracking/1`、
  `lock_article_for_view_tracking/1`、`article_insights/3` 已从 FrontDesk surface 删除；
- Comment 双参/三参 facade overload 已删除，Root `comment/1` 对非法 locator fail closed；
- Revision projection、ViewTracker lock/revalidation、Insights orchestration 各归 owner context；
- Insights 没有普通 public load 加专用 admission 的双重/提前过滤；
- User cache/revalidation 不再由 Root 反向拥有 Accounts 基础设施；
- protected-boundary 检查覆盖新的依赖方向；
- 聚焦测试与 warnings-as-errors compile 通过；FrontDesk 相关文档检查通过，仓库级 docs check 的既有
  CMS Command/DocTree 问题已明确列出；
- 没有 deprecated wrapper、双路径 fallback 或未分类 FrontDesk surface。
