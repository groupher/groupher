# Ticket T0 出口合同

> 状态：合同已执行（2026-11-01）。

> 本文记录第一版合同，已由当前运行时 [Ticket V2](./v2.md)取代。V2 移除了 held/独立公开状态、TicketEvent 和 TicketPost，使用 ArticleLifecycle 与 TicketSource / cms.ticket_sources；来源字段为 type，首批仅 POST。以下内容仅保留历史决策与第一版证据，不作为现行代码合同；本地与环境级验收分别见 [V2 实施追踪](./inventory.md#v2-实施追踪)。

本文记录第一版 Ticket 领域选择及其运行时落点。`type` 是 User / Worker / Case 的业务分类字段；`:ticket` 是唯一 Article thread，`:kanban` 仍是页面导航值。通知通过关联公开 Post 的作者、公开评论参与者与 Messaging inbox 投递；不向无关的 Community subscriber 扩散。Ticket 状态/公开更新先写 CMS Domain Outbox，并按 source/recipient 去重。

## 0. Article 身份与普通内容能力的边界

`CMS.Artiment.Config.threads()` **继续只列普通内容** `post/blog/changelog/doc`；`CMS.Artiment.Threads.identity_values_list/0` 和 `identity_enums/0` 在普通内容 thread 上增加 `ticket`，只供 `CMS.Model.Article.thread` 的 Ecto enum 与 Ticket 身份校验使用。`Threads.article_enums/article_values_list` 保持普通内容语义；Ticket 路由与 GraphQL 使用专用类型和校验。这样 Ticket 是真正的 `Article.thread`，但不会自动获得普通内容能力。

| 由普通 thread 集合驱动的面                                                                                                                               | Ticket 决定                                                                                                                                                                                        |
| -------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schema/helper/queries.ex` 的 `ticket` / `pagedPublishedTickets`、`objects.ex` 的 `ticket_lite/ticket_page`、`imports.ex` 的通用 Ticket mutations import | **禁用自动生成**；通过 Ticket 专用 GraphQL query、object、mutation 暴露，状态使用独立 `ticket_status_enum`。                                                                                       |
| `community_meta.ex` 的 `tickets_count/ticket_inner_id_index`、`communities/count.ex`、用户发布计数                                                       | **禁用自动计数/字段**；Ticket 分列数量由 Ticket 查询计算。公开 User Ticket 复用现有 `CommunityInnerIdCounter`，与 Post 共享社区编号空间。                                                          |
| `dashboard/thread_emotions.ex`、`interactions/*`、ArticleStats、评论、点赞、收藏                                                                         | **禁用**；仅引用关联 Post 的 stats。                                                                                                                                                               |
| `view_tracker/*`、`search_artiments/*`、`press/*`、`artiment_mentions/*`、RSS、普通 feed                                                                 | **禁用通用入口**；第一版仅有内部 Ticket PostgreSQL 标题查询，不建独立搜索索引，也不提供公开 Ticket 搜索。`search_artiments/artiment.ex` 的封闭 thread 类型不加入 Ticket。                          |
| `helper/permission_config.ex`、`gate/*`、`articles/{lifecycle,mutation_lock}.ex`、`scheduler/*`、`analysis/*`、assets/insights 查询                      | **显式适配或拒绝**：Ticket 使用专用权限、写锁与内容入口；通用 Article 生命周期/定时发布和普通分析不接纳 Ticket。内容资产引用如需支持，按 Ticket 专用内容命令接入，不因 thread 集合扩展而自动开启。 |

User Ticket 在管理员确认创建时即公开；专用命令在同一事务创建 `Article`、唯一 `ArticleBinding`、初始 `ArticleRevision`、指向它的 `ArticlePublic`、公开 `ArticleBinding.inner_id` 和 `TicketState(TODO, published)`。公开编号调用现有 `Articles.Numbering.assign_binding_inner_id` / `CommunityInnerIdCounter`，与 Post 共用 `(community_id, inner_id)` 唯一空间，不设 Ticket 独立编号器。初始标题、摘要（`digest`）和正文快照从 Post 拷贝，创建前须预览公开内容；当前工作台支持独立编辑标题和摘要，正文快照保留创建时内容。仅当标题或摘要的规范化值实际变化时才创建新 revision；Ticket revision 的 `content_hash` 是规范化标题、摘要、正文快照 hash 与 schema version 的 canonical fingerprint。已发布 Ticket 的内容更新原子更新 `TicketState.current_revision_id` 与 `ArticlePublic.revision_id`；held Ticket 编辑只更新当前 revision，重新发布时在同一事务选择该 revision。Worker/Case 建 `Article`、唯一 binding、revision 和 TicketState 当前 revision 指针，**不建** ArticlePublic、公开 inner_id 或公开 URL。三类 Ticket 都不建 `ArticleLifecycle`、`ArticleStats`，不走 `Articles.Commands.Create`、`Articles.Publish.Target`、通用 trash/restore 或普通 Article mutation；Ticket 的工作状态与公开状态由 TicketState 管理。内部内容版本仍由 ArticleRevision 保留，状态变化不生成内容 revision。

新增迁移扩展 `cms.articles` 的 `articles_thread_check`，允许 `post/blog/changelog/doc/ticket`；保留既有 `article_lifecycles`、`article_stats`、`trashed_articles` 等普通内容约束，不把 Ticket 纳入这些表。`TicketState.current_revision_id` 建立指向 `ArticleRevision` 的 FK，且 Revision Cleanup 必须把它当作保留根：Worker/Case 当前版本即使 `cleanup_after` 到期也不得删除，旧且无引用的版本仍可清理。已执行历史迁移不改写。

`TicketState(type,status)` 的数据库 check 固定 User/Worker 只能 `TODO/WIP/DONE`，Case 只能 `OPEN/RESOLVED`；另有独立 `public_visibility`（User: `published/held`；Worker/Case: `internal`）及相应 check。T1 须用直接 SQL 负向测试分别验证错误的 `type/status`、`type/public_visibility` 组合被拒绝。GraphQL 仅用独立 `TicketStatus`，不复用含 backlog/reject 且缺 OPEN 的 `article_status_enum`。

## 1. Post 进度与 Ticket 计数读模型

| 问题                           | 第一版决定                                                                                                                                                                                                                                             | 验收                                                                                                                                                                            |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Post 详情和列表的处理进度      | 独立 `PostTicketProgress` 批量查询，按当前 Community 的可见 User Ticket 关联读时计算；不写 `PostState`、`ArticlePublic` 或持久化进度表。详情单条使用同一计算规则。无关联返回 `null`。                                                                  | 一页 Post 不逐条查询；Ticket 状态、link/unlink、重开后下一次查询立即正确。                                                                                                      |
| 进度规则                       | 全 TODO 为 TODO，全 DONE 为 DONE，其他为 WIP；返回 `completed/total` 和关联 Ticket 的公开摘要。Case/Worker 不直接参与。                                                                                                                                | 一篇 Post 关联两 Ticket 时能显示「处理中 · 已完成 1/2」。                                                                                                                       |
| 旧 Post `status/statuses` 筛选 | 从 Post GraphQL filter、列表 UI、URL 参数、query key/store 中删除。第一版不提供按进度筛 Post；后续若需要，另定义以 Ticket 关系为依据的筛选。                                                                                                           | 旧参数不会被解释为新的 Ticket 状态；Post 分类筛选仍可用。                                                                                                                       |
| DONE 文案                      | Post 上保留分类语境：Bug 显示「已修复」、QA 显示「已解决」、其余显示「已完成」；这些是同一个 DONE 投影的文案，不是额外状态。Ticket 卡片统一显示「已完成」。                                                                                            | 不再读取 `Post.status`；现有 `aliasGTDDoneStatus` 的用户可理解文案保留。                                                                                                        |
| Ticket 卡片票数/评论数         | Ticket 列表返回关联的**可见** Post refs，不在 Ticket 保存计数。客户端与 SSR 均将当前卡片集合去重后的 Post refs 按 `ArticleStats.statsBatch` 每次最多 100 个 ID 分片查询，再按关联关系简单求和；SSR 将全部分片结果加入 hydration 并在 HTML 中输出计数。 | 单张 Ticket 或一页卡片关联超过 100 篇 Post 时仍正确；已挂载卡片随 stats cache 更新；link/unlink 后重新计算；同一 Post 在同一 Ticket 只计一次；SSR CDN 标签被投票/评论事件失效。 |

Post 进度是从 Ticket 事实得出的公开读投影，Ticket 票数/评论数是从 Post `ArticleStats` 得出的展示值。两个方向都只有一个写入事实源。由于 Ticket 卡片不直接投票，现有 `articleStatsCache.apply` 只需继续修补 Post stats batch；Ticket 卡片须从 refs 与 stats query **组合**，不能把聚合数字作为不会被修补的 Ticket 查询缓存字段。

## 3. 关系约束与生命周期

| 事件                               | 第一版处理                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 建立 `TicketPost`                  | 仅同 Community 的**公开可读 Post**与**管理员可管理的公开 User Ticket**；唯一 `(ticket_id, post_id)`。命令事务内锁定并验证两端，数据库 FK/唯一索引保护基础关系。跨表 type 与 Community 约束由事务锁加数据库约束/触发器共同保护，T1 选择具体 SQL 实现，不能只靠前端筛选。                                                                                                                                                                                        |
| 建立 Worker 父项                   | 一张 Worker 恰有一张同 Community 的 User Ticket 父项；创建时同时建立，第一版不允许重挂父项。                                                                                                                                                                                                                                                                                                                                                                   |
| 建立 `CaseMember` / `CaseWorker`   | 两端同 Community；CaseMember 唯一配对，User 可参与多个 Case；CaseWorker 只可引用属于该 Case 某个成员 User Ticket 的 Worker。                                                                                                                                                                                                                                                                                                                                   |
| 从 Case 移出 User Ticket           | 同事务移除以该 User Ticket 的 Worker 为来源的 `CaseWorker` 引用，保留 Worker 和 User Ticket 本身；Case 汇总立即重算。                                                                                                                                                                                                                                                                                                                                          |
| 取消 Post↔Ticket 关联              | 只删关系，不删 Post/Ticket；Post 进度、Ticket 公开 refs 与计数在下一次读取重算，并失效受影响缓存。                                                                                                                                                                                                                                                                                                                                                             |
| Post soft trash / 审核隐藏         | 内部关系保留；公开 Post 进度消失，Ticket 公开 refs/计数排除该 Post。Post soft trash 与 `ArticleReviewBlock` apply 都在同一事务将仍为 `published` 的关联 User Ticket 置为 `held`，并写 Ticket cache invalidation Outbox；已 `held` 的 Ticket 不重复转换。公开读取同时校验所有关联 Post 仍公开，防止漏掉新隐藏入口。ReviewBlock resolve 只清关联 Ticket 的公共缓存，不自动发布。内部工作状态不变；工作台显示未公开的关联 Post，并列出仍生效的 ReviewBlock 类型。 |
| Post restore / ReviewBlock resolve | 保留的关联重新进入权限投影，但 Ticket 不自动从 `held` 恢复；管理员须审核独立摘要并显式重新发布。ReviewBlock resolve 同事务清除关联 Ticket 的公共缓存。                                                                                                                                                                                                                                                                                                         |
| Post physical delete               | FK 清理 `TicketPost`；Ticket 保留，公开 refs/计数和相关 Post 投影重算。                                                                                                                                                                                                                                                                                                                                                                                        |
| Ticket trash / physical delete     | 第一版不提供 Ticket 删除或通用 Article trash；管理员可取消 Post 关联并关闭/重开工作流。未来增加删除时须单独定义对子 Worker、Case 与通知的影响。                                                                                                                                                                                                                                                                                                                |
| Worker 完成后重开                  | 若父 User Ticket 已 DONE，先显式重开父项，再重开 Worker；不隐式修改父状态。                                                                                                                                                                                                                                                                                                                                                                                    |

`ArticleBinding` 不为 Ticket 重做。Ticket 只有一条规范 Community binding；通用 mirror/move/unmirror 不得接纳 `:ticket`。`TicketState.article_id` 唯一和 binding FK 不足以阻止第二条 binding，T1 须用事务锁加数据库约束/触发器封住直接写入，并以绕过命令的直接 SQL 插入第二条 binding 失败为验收。关系表的删除策略不得只靠 Ecto `on_delete` 猜测，迁移需写出 FK 行为和对应命令副作用。

### User Ticket 公开状态

`published -> held` 由 Post soft trash/审核隐藏命令或 Post `ArticleReviewBlock` apply 在同一事务触发，也允许具备 `ticket.manage_visibility` 权限的人以专用 `holdTicket` 命令主动触发；发生实际转换时记录原因和操作者。Post soft trash 沿用原 Post 命令的 actor 与 `command_id`；人工 ReviewBlock 沿用审核 actor，自动审核可令 `actor_id` 为 `nil`，但系统事件都必须记录非空的 `source_kind/source_id` 和原因。ReviewBlock resolve 会在同一事务写关联 Ticket 的缓存失效 Outbox，但不改变 Ticket visibility。若 Ticket 已是 `held`，后续另一关联 Post 的隐藏只保留该 Post 自身的审核/隐藏事实：不新增 Ticket visibility event、不递增 TicketState.version、不再次发送 Ticket 通知；工作台从所有当前隐藏的关联 Post 计算阻断原因。`held -> published` **只能**由同权限管理员调用 `publishTicket`：确认所有关联 Post 已公开或已取消隐藏关联，预览并审核 Ticket 的独立标题/摘要，然后在一个事务内更新公开状态、版本、事件与 Outbox。取消关联或恢复 Post 本身不自动发布 Ticket。公开状态变化不改 TODO/WIP/DONE，也不删除 ArticlePublic 或编号。

`held` 的 User Ticket 不出现在公开 Kanban、Post 进度、公开 Ticket 详情或公开通知中；第一版无公开 Ticket 搜索，公开直访返回 404。内部搜索、内部详情、Worker 和状态事件仍可按权限读写。公开 `TicketUpdate` 在 held 期间也不可公开读取；此时只允许创建 `internal` 更新，且状态事件不排队面向普通用户的通知。重新发布只通知可见性恢复，不补发 held 期间的历史状态/更新通知。公开读权限检查与缓存失效必须覆盖上述所有入口。

## 4. 状态转换、版本和排序

| type   | 起点 → 终点                                   | 条件/副作用                                                                      |
| ------ | --------------------------------------------- | -------------------------------------------------------------------------------- |
| User   | 新建 → TODO；TODO → WIP                       | WIP 前至少一张真实 Worker；首次进入 WIP 记录 `started_at`。                      |
| User   | WIP → DONE                                    | 所有 Worker 已 DONE，管理员确认用户侧结果；记录 `completed_at`，可附对外更新。   |
| User   | DONE → WIP                                    | 显式重开；保留首次 `started_at`，清空当前 `completed_at`，保留状态变更历史。     |
| Worker | 新建 → TODO；TODO → WIP → DONE                | Worker 状态独立；DONE 不自动结束 User。父 User 已 DONE 时不能新建或重开 Worker。 |
| Worker | DONE → WIP                                    | 父 User 已显式重开；清空当前 `completed_at`。                                    |
| Case   | 新建 → OPEN；OPEN → RESOLVED；RESOLVED → OPEN | Case 状态独立，不向成员 User Ticket 推送状态。                                   |

不允许跳过 WIP 直接把 User Ticket 设 DONE；不允许 WIP 退回 TODO 作为“重开”。User/Worker/Case 的优先级和排期各自独立。所有命令携带 `command_id`；create 不带旧版本，状态/字段/内容更新及人工 `holdTicket/publishTicket` 携带目标 `TicketState.version`，Post link/unlink 与 Worker 创建携带所属 User Ticket 版本，CaseMember/CaseWorker 更新携带所属 Case 版本。Post 隐藏命令自动 hold 时沿用已锁定的 Post 与关联 Ticket，在同一事务逐张锁定 Ticket 并递增其版本；不允许覆盖并发人工 publish。关系变更也递增所属 Ticket 版本；重复命令按 receipt 重放，不因版本变化失败。冲突返回明确错误。看板拖动顺序走独立 reorder 命令，以目标 Ticket 版本和列排序锁保证一致性，更新 rank 不改状态；跨列拖动先验证合法转换，再在同一事务设置目标 rank。Timeline 拖动只改计划日期，不改 `started_at/completed_at`。

每次合法工作状态或公开状态转换都在同一事务插入不可变 `TicketEvent(ticket_id, event_type, from_status?, to_status?, from_visibility?, to_visibility?, reason?, actor_id?, source_kind?, source_id?, command_id, occurred_at)`，`(ticket_id, command_id)` 唯一。`event_type=work_status` 时只填工作状态前后值；`event_type=visibility` 时只填公开状态前后值及非空原因，数据库 check 阻止混填。`actor_id` 原则上非空；系统事件允许为空但 `source_kind/source_id` 必填。T1 须用直接 SQL 负向测试验证两种事件字段混填、visibility 事件缺原因和系统事件缺来源都被拒绝。Post soft trash 自动 hold 的事件以原 Post 命令为来源；ReviewBlock 自动 hold 使用 `source_kind=post_review_block` 和 Post ID 作为来源；重新发布通知以 `visibility` 事件 ID 为 Outbox source，不补发 held 期间历史事件。内部历史可见，普通用户只能读 `published` User Ticket 的当前状态及公开更新。`TicketUpdate(ticket_id, event_id?, body, visibility, author_id, published_at, supersedes_id?)` 的 `visibility` 仅为 `public/internal`；同表 check 规定 `public` 必须有 `published_at`、`internal` 必须没有 `published_at`，T1 直接 SQL 负向测试覆盖两种反例。新建公开 Update 还须属于当时 `published` 的 User Ticket：这是跨表限制，由数据库触发器或等效数据库约束保护，T1 直接 SQL 插入 held/非 User 的公开 Update 必须失败。已发布的公开 Update 在 Ticket 后续 held 时保留记录，公开查询同时过滤 Ticket `public_visibility=published` 和 Update `visibility=public`；不能以删除旧 Update 来满足写入限制。`internal` 更新不对外返回，也不产生对外通知。公开说明发布后不原地编辑，修正时追加一条 superseding update，保留审计历史。工作状态转换可不附说明，也可同时发布一条；独立进展发布不要求状态变化。通知以 `TicketEvent.id` 或独立 `TicketUpdate.id` 为源，Outbox 的 `(source_id, recipient_id, channel)` 唯一；同一收件人即使作者或公开评论参与多个关联 Post，也只收到一条通知。Activity 仅由这些事实投影，不作为第二事实源；通知不使用全社区订阅关系作为 Ticket 受众。

## 5. 筛选字段与 Dashboard 配置

第一版 `TicketTag(ticket_id, community_tag_id)` **复用所属 Community 的 Post 标签词表**：引用的 `CommunityTag` 必须与 Ticket 同 Community 且 `thread=:post`，由命令层和数据库约束/触发器共同保证；后台从现有 Post 标签管理中选择，不新增 `:ticket` tag thread。TicketTag 不使用 `ArticleBindingTag`，其赋值不增加普通社区 tag stats，也不进入公开 tag 缓存。`TicketFacet(ticket_id,key,value)` 保存版本、操作系统、模块，固定键 `version/os/module`，值经 trim/大小写规范化；同一 Ticket、键和值唯一。标签与 facet 第一版只在内部 Ticket 工作台显示和筛选，不在公开 User Ticket 字段矩阵或公开缓存中暴露，也不从关联 Post 继承。筛选在同键多值间 OR、不同键间 AND，先按权限缩小作用域再分页。`type/status/assignee/priority` 和计划时间为明确类型字段或关系，不进入任意 JSON。

Ticket Kanban 仅有 TODO/WIP/DONE。Dashboard 已存的 `kanbanBoards` 在一次性配置迁移中移除 BACKLOG/REJECTED，保留剩余列原顺序，允许 `[TODO, DONE]` 等子集；结果为空则设为默认三列。旧 `kanbanBgColors` 是零基五元素数组 `[BACKLOG, TODO, WIP, DONE, REJECTED]`；迁移为**恰好三个元素** `[old[1], old[2], old[3]]`，分别对应 TODO/WIP/DONE。旧数组缺失、长度不等于 5 或任一选中值非法时，整体重置为三列默认色；迁移后后端与 `useKanbanBgColors` 均校验长度 3。读色/写色一律按固定状态键映射 `{TODO: colors[0], WIP: colors[1], DONE: colors[2]}`，不能用 `kanbanBoards` 中的显示位置取色。之后后端 enum、校验、前端 `INIT_KANBAN_BOARDS`、Boards/颜色设置、SSR parse 和 i18n 只接受三列。不保留运行时旧值兼容。Post 的拒绝/审核仍由 Post/AlertWall 处理，不变成 Ticket 的 REJECTED 列。

### 第一版 Ticket 搜索

「关联已有工单」和内部工作台使用**专用 PostgreSQL 查询**，不接普通 `search_artiments`，也不新增外部搜索索引。查询只对有 `ticket.read_internal` 权限的成员开放，先按 Community 和可管理的 Ticket 范围过滤，再按当前 `ArticleRevision.title` 的规范化前缀匹配；**精确社区编号仅匹配 User Ticket 的 `ArticleBinding.inner_id`**，Worker/Case 没有公开编号，只按标题和类型搜索，内部详情仍可通过 UUID 直达。T1 migration 须显式增加 `ArticleRevision.title` 的规范化标题前缀索引，搜索 SQL 的规范化表达式与索引表达式一致；T3 用 `EXPLAIN` 验证目标查询计划实际利用索引。结果以稳定 `(title, ticket_id)` 排序并分页，可按 `type` 缩小范围。内部结果可包含 held User Ticket、Worker 和 Case；关联 Post 的选择器只返回可管理且 `published` 的 User Ticket。公开 Ticket 搜索第一版不提供；公开 Kanban 与直接详情仍按各自公开规则读取。输入、排序与索引需以查询计划和分页测试验收。

## 6. 浏览器与 CDN 缓存

| 事件                                       | 浏览器查询失效                                                                  | 公共 CDN 失效范围                                                                                                                                                        |
| ------------------------------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| User Ticket 创建、状态/公开内容/可见性变化 | Ticket 详情与板列、关联 Post 的进度 batch/详情/列表                             | Ticket board/详情；所有受影响公开 Post 的详情与列表                                                                                                                      |
| TicketPost link/unlink                     | Ticket 详情/板列/关联 refs 与计数、受影响 Post 进度                             | Ticket board/详情；受影响 Post 详情与列表                                                                                                                                |
| Post 投票或评论                            | Post `ArticleStats` detail/batch 即时 patch；Ticket 卡片从相同 stats batch 重算 | **新增** interaction/comment 到关联 Ticket 的缓存失效投影；对受影响的 Ticket 详情和所在 board SSR 标签执行合并去重的 purge。现有 Post stats 失效不足以覆盖 Ticket HTML。 |
| Post trash/restore/physical delete         | Ticket 公开 refs/计数、Post 进度、相关板列                                      | Ticket board/详情、受影响 Post 详情与列表                                                                                                                                |

Ticket 事件在业务事务内写入 **CMS Domain Outbox**；浏览器失效与 CDN purge 是两个独立执行边界。Outbox 记录写入失败时业务事务回滚，避免成功变更永久漏失效；提交后的 Cloudflare 投递失败重试，不回滚业务事实。T3 须扩展 Phoenix `PublicCache.scope_tags` 的 Ticket 语义和 Community SSR 的 Ticket cache tag；Post interaction/comment 事件也须投影关联 Ticket 的失效，不复活历史独立 `PublicCache.Invalidation` 写路径。按事件和 cache tag 合并去重，测量高频投票下每分钟 purge 数与队列延迟；若超过既有 CDN/Outbox 预算，必须在 T3 明确改为 SSR 不输出实时计数并同步修改验收，不能带着失控 purge 上线。具体 tag 字符串服从当前共享合同；T0 消费者清单覆盖 Community 和 Dash 两套 loader。

## 7. 切换验收

1. Post 列表、详情、筛选 URL、GraphQL filter 和 Dashboard 不再读取或写入旧 Post 状态；已存在的 `?status=` 参数不被解释成新的 Ticket 进度。
2. Ticket 状态变化、Post 关联/取消关联、重开、Trash/restore 后，Post 详情和已加载列表的进度一致；无关联显示空状态。
3. 关联 Post 被投票/评论时，已挂载 Ticket 卡片的简单求和即时正确；同一 Post 在同一 Ticket 仅计一次；SSR 刷新也正确。
4. User/Worker/Case 的直接 URL、内部 Ticket 搜索、feed、通用 Article mutation 与 `ArticleStats` 行为符合可见性矩阵；公开 Ticket 搜索无入口。
5. Case 移出成员后共同 Worker 引用清理；跨 Community、错 type、重复关联和不合法转换稳定失败，无部分写入；绕过命令直接 SQL 插入错误 type/Community 的关系、错误 Community 或 `thread != post` 的 TicketTag，以及 Ticket 的第二条 ArticleBinding，均必须被数据库拒绝。TicketState 的 type/status/public_visibility 组合、TicketEvent 的字段混填/缺失和 TicketUpdate 的 visibility/published_at 组合均有直接 SQL 负向测试；held/非 User 上新建公开 Update 也须被数据库拒绝。
6. 已存 Dashboard 配置含 BACKLOG/REJECTED 时迁移后只剩合法列；五色 `[BACKLOG, TODO, WIP, DONE, REJECTED]` 取零基 `old[1..3]` 变成恰好三色，非法旧值整体重置；`[TODO, DONE]` 子集仍分别取 `colors[0]` 和 `colors[2]`，无运行时兼容分支。
7. Ticket 变更提交后，浏览器失效与 CDN purge 覆盖 Ticket 及受影响 Post；Outbox/Cloudflare 失败路径可重试且不丢事件。
8. 某 Ticket 关联 A、B 两个公开 Post 时，隐藏 A 会使 B 暂时失去该 Ticket 进度、Ticket 直访 404；取消 A 关联并审核摘要或恢复 A 后，Ticket 与 B 进度重新出现，相关 SSR 缓存已失效。
9. 创建 Ticket 只走专用命令：新迁移允许 `articles.thread=ticket`；User 通过社区共享 counter 获得不冲突的 ArticleBinding.inner_id，Worker/Case 只有内部 revision；三者均无 ArticleLifecycle/ArticleStats 或普通内容自动生成查询。到期 Cleanup 保留 Worker/Case 当前 revision，旧无引用 revision 可清理；状态/说明历史、去重通知和并发版本冲突有测试。
10. `held` Ticket 不出现在任一公开查询、通知或 Update 读取中；恢复 Post 或取消关联不会自动发布。实际可见性变更产生独立类型的 TicketEvent，重新发布通知引用该事件 ID；并发 hold/publish 受 TicketState.version 保护。Ticket 已 held 时再隐藏另一关联 Post 不新增 visibility event、不递增 Ticket 版本或重复通知，但内部仍可看到两篇隐藏 Post 的阻断原因。TicketTag 只能引用同 Community 的 Post 标签，内部字段不会进入公开 Ticket 查询或缓存。SSR 超过 100 个关联 Post 时分片并完整 hydration；高频投票 purge 量和延迟符合实际预算。
