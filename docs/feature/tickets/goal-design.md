# Goal 与 Ticket 组织关系讨论稿

> 状态：产品设计讨论，尚未实现；不改变 [Ticket V2 当前合同](./v2.md)。
>
> 本文记录 Goal、Case、Ticket、来源、权重和公开界面的产品方向。未定的状态枚举、数据结构和计算方法留待实施合同确定，不作为现行 API 或迁移合同。
>
> [交互原型：Goal 公开进展页面](./goal-ui-prototype.html)（2026-11-23 更新）：独立 HTML，使用浏览器打开即可预览，无需启动项目服务。包含 Overview、Roadmap、People，以及进入 Goal 后的 Ticket Kanban / Timeline。

## 1. 现有基础

当前 Ticket 有 User、Worker、Case 三种业务类型。User Ticket 表达面向用户的处理事项，Worker Ticket 承载内部执行，Case 将有共同问题的 User Tickets 组织起来，并可引用共同修复的 Worker。Case 有独立的 OPEN/RESOLVED 工作状态。三者使用 Ticket 自身的状态、优先级、负责人和计划时间；Kanban、Timeline 展示 Ticket，而非来源内容。现有关系与状态以 [Ticket V2](./v2.md) 和 [第一版关系设计](./implementation.md#3-资源与关系)为准；第一版文档中已被 V2 替换的发布状态、TicketPost 等规则不再适用。

来源内容保留在其原有资源中。管理员处理来源时新建 User Ticket，或关联已有 User Ticket；一条来源可关联多张 Ticket，一张 Ticket 可汇集多条来源。现行 `TicketSource` 首批仅支持 Post；Comment、Survey、Email、IM 等仍是后续扩展方向，不视为已经接入。来源不进入 Ticket Kanban，也不因尚未关联 Ticket 而进入额外的 Inbox。[来源关联合同](./v2.md#4-ticketsource-与首批-post-规则)

## 2. 组织模型

```text
来源（Post；其他类型待接入） <--多对多--> User Ticket <--归属-- Worker Ticket
                                            |
                         +------------------+------------------+
                         |                                     |
                    Case：共同问题                      Goal：更大的具体任务
```

**Case 与 Goal 是不同的组织视角。**Case 按共同问题聚合相关 User Tickets，支持分析问题、共同修复和解决状态。Goal 按一项更大的具体任务组织贡献它的 Tickets，也有自己的负责人、状态和排期。两者可以交叉：同一张 User Ticket 可以属于某个 Case，同时贡献某个 Goal；关联不改变该 Ticket 的身份或工作状态。

例如，多张用户反馈分别形成“iOS 登录失败”和“登录后跳转错误”的 User Tickets，它们可以进入“移动端登录异常”Case；这些 Ticket 也可以与“移动端反馈入口改造”Ticket 一起贡献“新版移动端反馈流程上线”Goal。Case 说明共同问题，Goal 说明团队准备完成的更大任务。

**Case 保留为内部组织视角，不进入公开界面。**Case 的价值在于把散落在 Post、IM、Email、Survey 等来源中的同一问题归并、统一分析和修复；它天然包含内部调查、客户身份和重复反馈明细。公开页只呈现 Goal 与 Ticket，Case 的结果通过它们体现，不暴露 Case 本身及其归属关系。这样既保留 Case 作为内部工作台的核心卖点，也避免公开面承担额外的解释和泄漏成本。

Goal 倾向作为 Ticket 体系中的一种新业务类型，以复用稳定身份、内容、负责人、排期、工作台等基础能力；具体关系约束和工作状态须在实施合同中确定，不能直接套用 Case 的成员及状态规则。Goal 不是通用 Project 中间层，也不要求所有 Ticket 都必须属于 Goal。

“长期提升用户体验”等持续方向更适合未来的 Vision；Goal 应足够具体，能够由负责人判断本阶段何时完成。Vision 仅是后续可能的更高层视角，本轮不引入实体或强制层级。

以上是组织工作时的使用建议，不对 Goal 的命名、范围或粒度做强制校验。工具负责把各类信息表达清楚，使用者可以自行选择如何组织目标。

Cycle 暂不加入组织模型。Ticket 已有独立计划时间；只有当团队需要共同选择每轮承诺的工作并进行复盘时，Cycle 才有超出日期范围的独立价值。

## 3. 负责人和 Team 展示

延续现有以**具体人**作为 Ticket assignee 的方式，不为每张 Goal、Case、User 或 Worker Ticket 强制存一份 Team assignee。Goal 可以指定一位主要推进人，并允许其他人参与；现有 Ticket 已支持多位 assignee。界面可展示这些人所属的 Team；一人属于多个 Team 时，优先显示与当前工作相关的 Team，其余按需展开。

当前 Ticket assignee 关系只连接用户，仓库尚无可直接复用的 Ticket Team 归属合同。将来若出现依 Team 派单、权限或容量规划的明确需求，再单独设计 Team 归属，避免把人员与团队混成一种含义不清的 assignee。

## 4. 权重与进度

**权重首先表示一张 Ticket 对某个 Goal 的相对贡献。**它属于 Goal 与成员 Ticket 的关系，不是 Ticket 的全局属性。同一张 Ticket 对不同 Goal 可以有不同权重。权重不等于实现工作量、优先级或完成状态：耗时很长的低影响任务可以权重较低；耗时很短但决定 Goal 能否达成的任务可以权重较高。

这个概念应先成为设计的一部分，默认分配方法留待试验。初始值可以等分，也可以参考工作量等信息，但负责人始终可以调整。Goal 可为尚未明确的工作保留份额。界面方向是在 Goal 的分段视图中拖动每张 Ticket 的边界，直观看到贡献比例；交互细节和大规模成员时的呈现方式待验证。

**Goal 进度不由成员 Ticket 状态机械计算。**Ticket 的 TODO/WIP/DONE 可以标出哪些贡献已完成、正在推进或尚未开始，但 WIP 不自动等于完成一半。进度还包含负责人对实际结果、未知工作和预留的判断；Goal 是否完成也由负责人确认。权重提供判断结构，不把工作量点数或已完成 Ticket 数包装成精确的目标进度。Goal 的具体完成条件可以由负责人随工作明确和调整，不要求每个 Goal 都有量化指标。

来源侧也可能需要关联权重，但语义不同：它表示某条来源对 Ticket 判断的影响或证据价值，不表示工程进度。点赞、评论和来源的紧急优先级可以作为设置权重的参考；紧急程度不必自动等于更高的目标贡献。来源权重的粒度、默认值和是否进入首批实现尚未决定。

## 5. 公开界面与交互方向

### 5.1 原型与预览

[goal-ui-prototype.html](./goal-ui-prototype.html)保存公开版交互原型的独立 HTML，可直接用浏览器打开，不依赖本机对话目录或项目开发服务。

可操作路径：

1. 在 Overview 查看正在推进的 Goals、公开时间轴和最近进展。
2. 切换 Roadmap，查看「正在做 / 接下来 / 探索中」的完整产品方向。
3. 切换 People，查看成员负责、参与的公开 Goals 及公开事项状态；点击 Goal 进入详情。
4. 进入具体 Goal 后，在 Kanban / Timeline 间切换，查看同一批公开 Tickets；点击 Ticket 查看公开说明及相关公开反馈。
5. 在目标页或 Roadmap 模拟关注进展，或打开「最近交付」查看已可用的改进。

原型中的人物、日期、数量、反馈与交付记录均为示例数据；导航和关注只用于本地交互演示，不连接业务 API，也不创建真实订阅或发送通知。原型不展示团队内部的来源依赖编辑器；第 5.6 节记录的自动阻塞方向仍待实施。

原型保存的是较早一轮的完整导航探索（Overview / Roadmap / People + Goal 内 Kanban / Timeline），用于讨论而非最终信息架构；第 5.3 节已收敛公开入口，原型尚未同步更新。原型中的 Gantt、People 计数和 3/9 不作为产品承诺。

### 5.2 公开面模型

公开面的最小模型是 **Goal + Ticket**：Goal 回答“为什么做、做到哪”，Ticket 回答“具体在做什么”。来源不单独构成公开导航的一极；可公开的来源内容作为 Ticket 的讨论入口直接可见，不可公开的来源留在内部。来源包括 Post、Comment、Survey、Email、IM、Twitter/Spark 等；其中公开 Post 及其讨论串本来就是社区内容的一等公民，应作为 Ticket 下的“相关讨论”直接可见、可搜索、可继续回复，而不是被折叠成一条来源记录。

公开页优先呈现来源内容，而不是把来源类型做成结构。来源类型（这条 Ticket 来自 Post 还是 Email）属于内部归类，不作为公开筛选或导航维度；是否标注具体来源，由该内容的公开策略决定。

来源能否公开按**受众域**判断，而不是按有没有 URL：

- 公开互联网（Post、Twitter 等）：默认公开，保留链接与引用。
- 社区内（论坛讨论）：本来就在公开面，直接作为讨论串。
- 私域（Email、IM、Survey 回答等）：默认不公开；需要公开时，由 AI 摘要并过滤敏感信息，再经运营确认或来源方同意，公开需求而不是原话，且默认不带身份。

AI 摘要解决信息泄漏，不解决预期违背；私域来源的公开需要单独的同意或审核步骤。外部内容按引用处理，不镜像复制：Twitter 会删除、问卷会失效，保留摘要、来源类型与链接即可。

公开条目以需求为单位，而不是以来源消息为单位：一张 Ticket 对应一个公开讨论串，可以是已有的公开 Post，也可以是由多条私域来源合成的摘要；其他公开来源作为该讨论串的引用和数量，不重复开帖。这样既做到能公开都公开，也避免同一问题刷屏。

### 5.3 页面层级与入口

公开页面面向子社区普通用户，也面向从站外来源进入的反馈者。公开界面的定位是**对外告知，对内只是辅助**：它不复制项目管理工具的能力；判断一个元素是否该出现在公开页，标准是它能否让关心这个项目的用户在 30 秒内知道“在做什么、什么时候能用、最近有什么变化”。

入口收敛为 **Goals 列表 + Goal 详情 + 一条从来源进入的链接**，不让用户在多个一级栏目之间做选择。

| 页面        | 回答的问题                             | 主要内容                                                                                   |
| ----------- | -------------------------------------- | ------------------------------------------------------------------------------------------ |
| Goals 列表  | 现在在做什么、最近有什么变化           | 一行一个 Goal：用户收益、阶段、计划窗口、最近更新、关注入口。                              |
| Goal 详情   | 这件事做到哪、什么时候能用、有哪些讨论 | 目标说明、阶段与计划窗口、公开 Ticket 列表、更新流（含计划变更与交付说明）、相关公开讨论。 |
| Ticket 详情 | 具体在做什么、进展如何                 | 公开说明、阶段/状态、相关公开讨论、关注。                                                  |
| 从来源进入  | 我提的问题怎么样了                     | 来源帖或摘要 → 关联 Ticket / Goal 的当前状态与更新。                                       |

**Roadmap 和 People 不作为首批一级入口。**Roadmap 的内容可以由 Goals 列表按阶段分组表达，如果后续确实需要按时间轴浏览，再作为可选视图恢复；People 是独立的团队透明产品赌注，涉及个人工作量和隐私，放到后续单独验证。原型中的 Overview / Roadmap / People 是较早的完整导航探索，当前方向以本节为准。

Goal 详情默认以事项列表 + 更新流为主；Kanban / Timeline 作为可选视图，不作为首屏默认。公开页也不引入 Gantt 或百分比进度，避免把计划表达成精确承诺。

### 5.4 默认公开、来源可见性与进度表达

协作心智仍以**默认公开**为方向，Ticket 和 Source 均允许按需设置为仅内部可见。公开页面和团队工作台使用同一份业务事实，按访问者权限返回不同可见范围，不维护两套独立状态。

公开 Ticket 可以关联内部 Source；来源设为内部可见不要求该 Ticket 一并隐藏。公开用户可以继续追踪 Ticket，但不能因此读取内部来源、关系明细或内部说明。这里记录未来的产品方向，不改变 Ticket V2 目前仅支持 Post 来源及其已有发布、关联与 Gate 规则。

汇总数字和人员参与信息同样需要明确可见性合同，不能仅隐藏标题却仍通过总数暴露内部事项。公开页的事项进度与数量只统计公开可见 Tickets；最终聚合、分页与缓存规则在实施合同时确定。

进度表达只回答三个问题：**在做什么、大概什么时候能用、最近有什么变化。**时间条表示计划窗口或已发生的推进时段；`3/9` 表示事项完成数，不直接命名为 Goal 完成百分比，也不引入 Gantt 式假精确。计划调整时，公开页表达对用户的影响、可公开的说明及下一次更新时间；完成时给出公开的交付说明或 Changelog 链接，而不是只改状态。

Goal 的权重与完成判断仍沿用第 4 节的方向，具体如何组织和使用由团队决定。公开页的核心体验是“自上次访问以来变了什么”，关注是首要动作，而不是藏在详情页里的次要按钮。

### 5.5 维护、通知与链接

公开路线图的主要失败模式是过期，维护机制因此是产品的一部分，而不是运营补丁。

- **链接闭环**：来源 → Ticket → 更新 → 回到来源作者和关注者。更新回到原讨论串回复，或通过站外通知（Email、IM 等）送达；只做页面而不做回路，公开页只是公告栏。
- **公开事件白名单**：开始处理、计划变更、进入验证、已交付、暂停/取消。commit、内部评论、负责人变更等默认不进入公开流；是否公开由事件类型决定，而不是逐条人工判断。
- **订阅粒度**：Goal 级摘要优先，而不是每条 Ticket 推送；允许用户选择“仅交付时通知”或“每次进展”。
- **维护责任**：每个公开 Goal 有明确维护人；过期未更新要提示；能从 Ticket / Changelog 自动带出的更新不要手工重写。
- **渠道节奏**：先打通用户已经在的渠道（社区 Post 加一个站外渠道），不一开始铺满所有来源。

这套机制要嵌入客户已有的开发流程，而不是要求客户迁移到新的管理工具；公开页只负责把内部进展翻译成用户能理解的状态。

### 5.6 Source 状态与自动阻塞方向

Source 指 Post、Comment、Email、IM 等平级来源，不是执行子任务；现有首批运行时仍仅支持 Post。来源可能有各自的处理状态，Ticket 可以汇集多条处于不同状态的来源。

为了避免反复维护 Ticket 的独立阻塞标记，讨论方向是：**人定义来源与 Ticket 的前置依赖关系，系统根据关系和来源状态自动推导、解除 Ticket 的阻塞提示。**

- 普通关联反馈处于 blocked 时，可以显示来源处理摘要，不直接把整张 Ticket 判为 blocked。
- 若来源是该 Ticket 当前推进必需的前置依赖，且处于 blocked，则自动显示该 Ticket 受阻；前置阻塞解除后，提示自动解除。
- 前置性属于 Source 与 Ticket 的关系。同一来源可以是某张 Ticket 的必需前置，同时只是另一张 Ticket 的关联反馈。
- 保留 Ticket 本身的 TODO/WIP/DONE 工作状态，阻塞作为派生维度；来源状态变化不直接将 Ticket 置为 DONE，也不自动重开已完成事项。
- Goal 可以汇总受阻 Ticket，但不会因一张 Ticket 受阻而自动判定整个 Goal 停摆。公开说明按第 5.4 节的可见范围展示。

来源处理状态的事实归属、当前阶段的前置条件、多个来源可互相替代时的规则，以及状态转换与通知合同，均尚未冻结；本节不表示现有 Source 已实现独立工作状态或自动依赖编排。

## 6. 仍需通过真实场景确定

- Goal 允许直接关联哪些 Ticket 类型，以及 Goal、Case、Worker 交叉出现时如何避免进度重复计入。
- Goal 的状态枚举、负责人确认完成的具体操作，以及是否支持重开。
- 权重的默认建议、预留份额、拖动方式与进度展示；先用真实 Goal 验证可理解性，再冻结算法和字段。
- 公开面的权限合同：Goals 列表与详情的聚合、公开 Post 与 Ticket 的关联展示、私域来源的同意与审核流程，以及 People 是否以及何时进入公开面；新增组织关系不能自动扩大现有 Draft、Worker、Case 或来源内容的公开权限。
- 公开事件白名单、订阅粒度、站外通知渠道，以及来源更新回流到原讨论串的合同。
- 首批范围建议：Goal + 公开 Ticket + 关注/更新 + 来源关联；People、权重和自动阻塞是否进入首批，待真实场景验证。
- 第 5.6 节的来源处理状态、前置依赖与自动阻塞规则，以及它们对公开投影和通知的影响。

这些是后续产品与实施决策；本文不授权修改现有 Ticket V2 的生命周期、来源范围或公开读取合同。
