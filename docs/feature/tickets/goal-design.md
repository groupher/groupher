# Goal 与 Ticket 组织关系讨论稿

> 状态：产品设计讨论，尚未实现；不改变 [Ticket V2 当前合同](./v2.md)。
>
> 本文记录 Goal、Case、Ticket、来源和权重的产品方向。未定的状态枚举、数据结构、计算方法及界面细节留待真实场景验证，不作为现行 API 或迁移合同。

## 1. 现有基础

当前 Ticket 有 User、Worker、Case 三种业务类型。User Ticket 表达面向用户的处理事项，Worker Ticket 承载内部执行，Case 将有共同问题的 User Tickets 组织起来，并可引用共同修复的 Worker。Case 有独立的 OPEN/RESOLVED 工作状态。三者使用 Ticket 自身的状态、优先级、负责人和计划时间；Kanban、Timeline 展示 Ticket，而非来源内容。现有关系与状态以 [Ticket V2](./v2.md) 和 [第一版关系设计](./implementation.md#3-资源与关系)为准；第一版文档中已被 V2 替换的发布状态、TicketPost 等规则不再适用。

来源内容保留在其原有资源中。管理员处理来源时新建 User Ticket，或关联已有 User Ticket；一条来源可关联多张 Ticket，一张 Ticket 可汇集多条来源。现行 `TicketSource` 首批仅支持 Post；Comment、Survey、Email、IM 等仍是后续扩展方向，不视为已经接入。来源不进入 Ticket Kanban，也不因尚未关联 Ticket 而进入额外的 Inbox。[来源关联合同](./v2.md#4-ticketsource-与首批-post-规则)

## 2. 组织模型

```text
来源（Post；其他类型待接入） <--多对多--> User Ticket <--归属-- Worker Ticket
                                            |
                         +------------------+------------------+
                         |                                     |
                    Case：共同问题                      Goal：更大的具体任务
```

**Case 与 Goal 是不同的组织视角。**Case 按共同问题聚合相关 User Tickets，支持分析问题、共同修复和解决状态。Goal 按一项更大的具体任务组织贡献它的 Tickets，也有自己的负责人、状态和排期。两者可以交叉：同一张 User Ticket 可以属于某个 Case，同时贡献某个 Goal；关联不改变该 Ticket 的身份或工作状态。

例如，多张用户反馈分别形成“iOS 登录失败”和“登录后跳转错误”的 User Tickets，它们可以进入“移动端登录异常”Case；这些 Ticket 也可以与“移动端反馈入口改造”Ticket 一起贡献“新版移动端反馈流程上线”Goal。Case 说明共同问题，Goal 说明团队准备完成的更大任务。

Goal 倾向作为 Ticket 体系中的一种新业务类型，以复用稳定身份、内容、负责人、排期、工作台等基础能力；具体关系约束和工作状态须在实施合同中确定，不能直接套用 Case 的成员及状态规则。Goal 不是通用 Project 中间层，也不要求所有 Ticket 都必须属于 Goal。

“长期提升用户体验”等持续方向更适合未来的 Vision；Goal 应足够具体，能够由负责人判断本阶段何时完成。Vision 仅是后续可能的更高层视角，本轮不引入实体或强制层级。

Cycle 暂不加入组织模型。Ticket 已有独立计划时间；只有当团队需要共同选择每轮承诺的工作并进行复盘时，Cycle 才有超出日期范围的独立价值。

## 3. 负责人和 Team 展示

延续现有以**具体人**作为 Ticket assignee 的方式，不为每张 Goal、Case、User 或 Worker Ticket 强制存一份 Team assignee。Goal 可以指定一位主要推进人，并允许其他人参与；现有 Ticket 已支持多位 assignee。界面可展示这些人所属的 Team；一人属于多个 Team 时，优先显示与当前工作相关的 Team，其余按需展开。

当前 Ticket assignee 关系只连接用户，仓库尚无可直接复用的 Ticket Team 归属合同。将来若出现依 Team 派单、权限或容量规划的明确需求，再单独设计 Team 归属，避免把人员与团队混成一种含义不清的 assignee。

## 4. 权重与进度

**权重首先表示一张 Ticket 对某个 Goal 的相对贡献。**它属于 Goal 与成员 Ticket 的关系，不是 Ticket 的全局属性。同一张 Ticket 对不同 Goal 可以有不同权重。权重不等于实现工作量、优先级或完成状态：耗时很长的低影响任务可以权重较低；耗时很短但决定 Goal 能否达成的任务可以权重较高。

这个概念应先成为设计的一部分，默认分配方法留待试验。初始值可以等分，也可以参考工作量等信息，但负责人始终可以调整。Goal 可为尚未明确的工作保留份额。界面方向是在 Goal 的分段视图中拖动每张 Ticket 的边界，直观看到贡献比例；交互细节和大规模成员时的呈现方式待验证。

**Goal 进度不由成员 Ticket 状态机械计算。**Ticket 的 TODO/WIP/DONE 可以标出哪些贡献已完成、正在推进或尚未开始，但 WIP 不自动等于完成一半。进度还包含负责人对实际结果、未知工作和预留的判断；Goal 是否完成也由负责人确认。权重提供判断结构，不把工作量点数或已完成 Ticket 数包装成精确的目标进度。Goal 的具体完成条件可以由负责人随工作明确和调整，不要求每个 Goal 都有量化指标。

来源侧也可能需要关联权重，但语义不同：它表示某条来源对 Ticket 判断的影响或证据价值，不表示工程进度。点赞、评论和来源的紧急优先级可以作为设置权重的参考；紧急程度不必自动等于更高的目标贡献。来源权重的粒度、默认值和是否进入首批实现尚未决定。

## 5. 仍需通过真实场景确定

- Goal 允许直接关联哪些 Ticket 类型，以及 Goal、Case、Worker 交叉出现时如何避免进度重复计入。
- Goal 的状态枚举、负责人确认完成的具体操作，以及是否支持重开。
- 权重的默认建议、预留份额、拖动方式与进度展示；先用真实 Goal 验证可理解性，再冻结算法和字段。
- Goal 的内部与公开展示范围。新增组织关系不能自动扩大现有 Draft、Worker、Case 或来源内容的公开权限。

这些是后续产品与实施决策；本文不授权修改现有 Ticket V2 的生命周期、来源范围或公开读取合同。
