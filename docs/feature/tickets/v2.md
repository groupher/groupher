## 1. 必须保持的边界

| 能力                        | 唯一事实源与职责                                                        | Ticket 的使用方式                                                                                                                                                                 |
| --------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 稳定身份、Community binding | Article / ArticleBinding                                                | `thread=:ticket`，沿用稳定 ID；Ticket 不进入普通 Post feed 或通用互动自动生成面。                                                                                                 |
| 草稿、内容版本、公开投影    | Article Draft、Revision、ArticlePublic                                  | Ticket 的内容命令通过共享边界保存草稿、选择公开 revision；标题、摘要、正文不在 Ticket State 另存一份。                                                                            |
| 发布生命周期                | ArticleLifecycle                                                        | `:draft` / `:published` 等基础状态与转换只在此处保存；新模型只使用 `:draft`，不保留 `:draft_only` 别名。                                                                          |
| Ticket 工作生命周期         | `CMS.Tickets.Lifecycle`                                                 | User/Worker 的 TODO/WIP/DONE、Case 的 OPEN/RESOLVED，含转换规则、版本和状态阻断。它是 Ticket 领域 Lifecycle，不替代 Article 发布 Lifecycle。                                      |
| Ticket 业务事实             | `CMS.Model.TicketState`                                                 | type、工作状态、优先级、排期、排序等；负责人等业务关系由 Ticket 专属关系模型管理。不保存第二份公开状态或 `current_revision_id` 内容指针。数据库表可以继续叫 `cms.ticket_states`。 |
| 读取与操作准入              | `CMS.Gate`、Article Gate、Ticket Gate                                   | Gate 管 actor、action 和可组合读取 scope；Lifecycle 管状态与合法转换。Ticket Gate 依赖 Article Gate，Article Gate 不引用 Ticket。                                                 |
| 来源关系与公开引用          | TicketSource，首批 `type=:post`；组合 Article Gate 的 Post public scope | 完整替换 TicketPost；关系记录不因审核隐藏而删除，公开投影只返回当下可见 Post。                                                                                                    |
| 历史与异步效果              | `Activity.Ticket`、CMS Domain Outbox、Receipt                           | TicketLog 记录状态前后值和来源；Outbox 承载缓存/通知意图；Receipt 处理需重试的命令。目标模型没有 `TicketEvent`；TicketUpdate 保存进展内容。                                       |

依赖方向固定为 `Ticket Commands / Query / Gate -> Article 基础设施及 Article Gate`。Article 的 Lifecycle、Draft、Revision、Public、Gate 不包含 Ticket 工作状态字段或 Ticket 专属关系逻辑。Ticket 的 `State` 只是领域扩展；不得把 `public_visibility` 换名后继续作为并行发布事实。现有 `TicketState.current_revision_id` 也须由共享 Draft / ArticlePublic 取代，不留另一份“当前内容”权威。

GraphQL、CLI、API、Agent、Bot 等入口的协议适配由[统一接入层](../../architecture/cms-multi-entry-boundary.md)处理，不新增 Ticket 专用 transport 或接入框架。Ticket 只提供自身业务查询和命令；来源关联与提交后的异步联动属于 Ticket 领域合同。

## 2. Gate 与两个 Lifecycle 如何协作

```text
公开 Ticket 列表/详情
  -> CMS.Gate.scope(query, actor, :read, %Scope.Ticket{...})
  -> Ticket Scope 先组合 Article Gate 的基础公开条件
  -> 再附加 Ticket type、Community、关系等专属条件
  -> 返回一条可组合的 Ecto.Query，由 Reader 执行

Ticket 写命令
  -> 加载并锁住规范资源
  -> CMS.Gate.with_check(actor, action, resource, callback)
  -> ArticleLifecycle 或 Tickets.Lifecycle 校验并执行目标转换
  -> Persist 写入 + Activity + Outbox（同一事务）
  -> Receipt 确认 / 提交后效果投递
```

“先 Article Gate，再 Ticket Gate”是 **查询组合顺序**；调用方只调用 Ticket Gate。代码依赖箭头为 `Ticket Gate -> Article Gate`，通常生成一条 SQL，而不是执行两次数据库读取。通用 Gate 只根据 Ticket 的强类型 Context 分发；它不认识 TODO、WIP 等字段。Ticket Gate 消费 Ticket State / Lifecycle 提供的事实。Post 引用过滤也复用 Article Gate 的 Post public scope，不在 `Tickets.PublicPosts` 等辅助模块复制 moderation、trash、ReviewBlock 条件。Article Gate 本身仍负责 Ticket 的基础公开资格（ArticleLifecycle、审核限制等）；Ticket Gate 追加业务条件。

写路径按 [CMS Command、Gate、Lifecycle 与 Persist 边界](../../migrations/cms-command-gate-lifecycle-persist-boundary.md)执行：Resolver 只做协议转换；`CMS.Tickets` facade 委托 `Commands.<Action>.execute`；Command 在一个事务内完成锁、Gate、Lifecycle、Persist、Activity 和 Outbox；Persist 不另开事务。需要 ambiguous-commit 恢复的创建、发布、转 Draft 等命令接 `CMS.Command` Receipt。

## 3. Draft 与发布

这里有两个不同概念：**Lifecycle `:draft`** 表示“当前不公开”；**内容 Draft 工作区**保存尚未发布的编辑内容。已发布 Article 可以有内容 Draft，Lifecycle 仍是 `:published`。新模型在 ArticleLifecycle 设置只写一次的 `first_published_at`（Ecto `:utc_datetime`、数据库 `:timestamptz`）：`draft + nil` 表示从未发布，`draft + 非 nil` 表示发布后撤回；Doc 分支在自己的 DocLifecycle 保存同名首次发布时间，不借 Article 全局状态判断 branch。`ArticlePublic.published_at` 表示最近一次发布，不承担首次发布时间。Post/Blog/Changelog/Ticket 首次发布都写 `published` Activity；`first_published_at` 是状态判断权威，不依赖 Activity 是否可查询。

首次时间由数据库拥有：为 ArticleLifecycle、DocLifecycle 分别建立 `article_lifecycle_first_publication_guard`、`doc_lifecycle_first_publication_guard`。新生命周期默认为 null；首次进入 published 时，BEFORE trigger 在字段仍为 null 的条件下写 `date_trunc('second', transaction_timestamp())`，普通 SQL/应用不得自行传入非 null 的首次时间。另设同表 check：`state = 'published'` 时 first_published_at 必须非 null。已有非 null 值后，任何 UPDATE 将其清空或改为不同时间都拒绝，撤回/重发/Trash Restore 和 Doc 分支转换保留原值；相同值更新合法。Draft 状态不得单独补写该字段。Persist 通过 RETURNING/`read_after_writes` 读取实际 UTC 值，再构造 Activity/Confirmation；应用层 guard 不替代数据库约束。

两个 guard 不提供运行时 SQL 维护旁路，`cms_ticket_write` 也不能改写首次时间。全量内容重建删除旧生命周期后，新内容身份从 null 开始；完整环境快照恢复按第 7.2 节执行。若以后需要修正错误的首次时间，应制定独立数据修复方案，不能把日常 UPDATE 或关闭 trigger 作为产品入口。R01/R08 的证据须包含普通角色及受控写入角色的直接 SQL 正负向用例。

1. 直接用 `:draft` 取代旧 `:draft_only`；ArticleLifecycle 增加 `:published -> :draft`，`draft -> published`、`deleted -> draft` 等合法转换。`TrashedArticle.restore_state` 同步改名；DocLifecycle 的 branch 状态也改名，但 Doc 的发布/撤回能力仍由 Doc branch/release 合同单独控制。所有数据库 check、Ecto enum、GraphQL enum 与调用方只接受新值，不加旧值别名。
2. Ticket 新建先有 Draft。预览确认后发布：保存当前 Draft，创建/选择不可变 Revision，更新 ArticlePublic，执行 ArticleLifecycle 转换；全部在同一事务。MoveToDraft 若尚无内容 Draft，须从当前公开 Revision 建立工作区；再次发布必须使用当前 Draft，不能意外重用撤回前的旧公开内容。
3. 已发布 Ticket 首次编辑经第 3.4 节 EnsureDraft 建立共享 Draft 工作区；未发布修改不影响 ArticlePublic。明确发布后才替换公开 revision。只变更优先级、排期或工作状态不创建内容 Revision；只有规范化内容实际改变才创建 Revision，`content_hash` 按共享规则重新计算。Worker/Case 也使用 Draft 保存内部内容，不通过 Ticket State 指向私有 Revision。
4. 已发布 Ticket 转 Draft 后，Article ID、binding、Revision、ArticlePublic 指针与已有互动事实保留；公开读取和写入由 Gate 拦截。再次发布从当前内容 Draft 选择 Revision，并原子更新 ArticlePublic 与 Lifecycle。
5. Ticket 工作状态与发布状态互不代替：TODO/WIP/DONE 都可处于 Draft 或 Published。只有 Published User Ticket 且自身无任何 active ReviewBlock 时，才允许新建 PUBLIC TicketUpdate 或公开通知；`awaiting_ai` 也阻止这两项能力。已有 PUBLIC Update 在 Draft 或 active ReviewBlock 期间隐藏；再次发布时预览**全部将恢复展示的公开 Update**，管理员确认后一起恢复。含违规内容的 Update 须先按 supersede 规则修正；Ticket 自身有任何 active ReviewBlock 时拒绝 Publish。

普通 Article 撤回后，已有 upvote/comment 的数据继续绑定稳定 Article ID，不删除。技术合同默认 Draft 期间阻止公开读取和新互动，重新发布后原互动恢复可见；是否向作者提供撤回按钮、旧评论是否重新露出，是各 Article 产品入口的后续决定，不阻塞底层转换能力。上线前各入口须明确 Gate 和 UI 策略。

### 3.1 Ticket 内容读模型与搜索

公开 Ticket 只读 `ArticlePublic -> ArticleRevision/ArticleBodySnapshot`；内部 Ticket 优先读 `ArticleDraft -> ArticleBodyDraft` 作为当前工作内容，若没有 Draft 则读 ArticlePublic。内部详情同时单独返回已发布内容及 `hasUnpublishedChanges`，避免把工作标题误认为公开标题。Worker/Case 的内部内容始终走 Draft。`TicketState.current_revision_id` 从模型、查询和数据库约束中删除；内容版本由 ArticleDraft/ArticlePublic 唯一决定。

内部搜索以**当前工作标题**为准：有 Draft 搜 `ArticleDraft.title`，无 Draft 搜 `ArticlePublic.title`；两个索引各自支持规范化前缀，不使用跨表 `COALESCE` 表达式索引。结果按 `(规范化工作标题, article_id)` 稳定排序并分页。公开列表与详情始终搜/排公开内容。原 Revision 标题索引不再是内部搜索的权威；Ticket Query、Worker/Case 子项、GraphQL `title/digest/body` 都遵守同一选择规则。

### 3.2 并发版本与编号

| Command                                  | 必须提交的版本                                                                                   | 事务内再校验                                                                                                             |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| EnsureDraft                              | `expectedLifecycleVersion`                                                                       | 锁内检查当前公开 revision；没有工作区则复制，有工作区则返回现有 Draft，绝不覆盖。                                        |
| SaveDraft                                | `expectedDraftVersion`、`expectedLifecycleVersion`                                               | 同时匹配工作区和发布生命周期；防止 Publish 后重新建 Draft 时版本号复用，旧 autosave 写入新工作区。不改变工作状态或关联。 |
| Publish                                  | `expectedDraftVersion`、`expectedLifecycleVersion`、`expectedWorkflowVersion`、`expectedPreview` | 内容、公开状态、关联集合与可见 Post；三个版本和预览锚点都与已审核快照一致。                                              |
| MoveToDraft                              | `expectedLifecycleVersion`                                                                       | 当前仍为 Published；状态转换与效果原子执行。                                                                             |
| 工作状态/优先级/排期/负责人、link/unlink | `expectedWorkflowVersion`                                                                        | Ticket State 及关联关系；关系变化递增 workflow 版本。                                                                    |
| PUBLIC Update                            | `expectedLifecycleVersion`、`expectedWorkflowVersion`                                            | Ticket 仍为 Published User Ticket，且自身没有任何 active ReviewBlock；INTERNAL Update 只需 workflow 版本。               |

GraphQL 按第 3.5 节返回三个版本、发布状态与内容。移除含混的单个 `version`、`visibility`、`events` 字段，不保留别名。Ticket 自身 ReviewBlock apply/end 即使不改变发布状态，也递增 `lifecycleVersion`；关系和来源可见性变化递增受影响 Ticket 的 `workflowVersion`，自动降级同时递增 `lifecycleVersion`。PUBLIC/INTERNAL Update 的追加或 supersede 递增 workflow 版本，旧预览必须重新读取。Publish 预览同时携带三个版本、可见来源的 Post ID/公开 revision ID 和将展示的 PUBLIC Update ID；事务内逐项重查，变化则拒绝旧预览，不新增第四个持久化版本。内部查询返回 `publicationPreview`，由按 ID 排序的可见来源关系 ID / Post ID / 当前公开 revision ID 与有效 PUBLIC Update ID 计算 SHA-256；它是临时比对锚点，不是数据库字段。Publish 必须提交该值为 `expectedPreview: String!`，在来源 Post 与 Ticket 锁内重新计算比对。

新建 Draft User Ticket 只有稳定 UUID 和唯一 Community binding，**不占 `inner_id`**、没有公开 URL。首次发布才通过共享编号 primitive 分配社区编号；转回 Draft 后保留编号，公开直访 404，再发布复用原编号。Worker/Case 不获得公开编号。`ticket_state_article_guard` 对 User 创建即需编号的旧约束必须替换。

### 3.3 共享 Publish 的使用边界

Ticket Publish 通过第 3.6 节 `Tickets.Content` 适配层复用从 Draft/Revision 提取的基础内容 primitive、ArticlePublic.select、ArticleLifecycle 和编号 primitive；由 Ticket Command 编排 Gate、来源校验、Ticket Activity、审核、Outbox 与通知。**不得直接调用现有 Draft.Store 的整条创建/保存/恢复流程，或普通 Article Publish.Target/Effects.Publish 的整条流程**；前者会进入 typed extension/tag 分支，后者还会产生 ArticleStats、PostState/标签、普通文章计数、搜索/feed 或管理员新文章通知。普通 Article 的 `published -> draft` 也须在 Command 事务及效果层同步撤下搜索/feed、修正社区/作者计数、purge 公开缓存、写 Activity；重发仅恢复一次，不重复计数。Article ID、评论与互动事实保留，但 Draft 期间 Gate 阻止公开读写。

### 3.4 Published Ticket 首次编辑

`CMS.Tickets.Commands.EnsureDraft.execute` 是内部编辑入口，由 Workbench 在进入编辑时调用；接 Gate、Command Receipt 和 `expectedLifecycleVersion`。它遵守第 4 节先取得 Community admission，再在同一事务锁定 Ticket Article/Lifecycle 并检查 Draft：存在则返回其真实版本及内容；不存在且为 Published User Ticket 时，通过 `Tickets.Content` 从锁内读取的 ArticlePublic Revision 复制工作区。该能力提取自 `Draft.Store.ensure_from_public` 的基础 body/refs/head 逻辑，不能直接调用其现有 typed extension/tag 路径。初始 `draftVersion=1`，不改变 ArticlePublic、publicationState 或 workflowVersion，不创建 Revision，也不发送公开通知。primitive 必须加入调用方事务，不另开提交边界。

Create 总是建立版本 1 的 Draft；Draft User 和 Worker/Case 缺少工作区是完整性错误，不能从公开内容回退。MoveToDraft（含系统自动降级）缺少工作区时也使用同一创建 primitive。Publish 最终为 Published 时删除已消费的 Draft 工作区；若同事务审核使最终状态为 Draft 则保留工作区。删除后首次编辑再次 EnsureDraft。每次 Publish（包括 Published→Published 的内容重发）及 MoveToDraft 都递增 lifecycleVersion；SaveDraft 校验该版本，避免旧工作区 version=1 与重建后的 version=1 相撞。其他删除/重建 Draft 的新增入口也须遵守此 guard。两次并发 EnsureDraft 在相同 Article 锁和唯一约束下返回同一个工作区；相同生命周期版本但已有 Draft 时不覆盖内容。EnsureDraft 的 Receipt 确认首次结果；再次打开编辑器须重新读取内部详情，不能以旧 Receipt 的版本覆盖后续 autosave。

SaveDraft 不接受 `null`、0 或虚构的 Draft 版本，也不隐式创建工作区。无 Draft 返回明确的 `draft_not_found`，客户端重新读取并 EnsureDraft；Draft 或 Lifecycle 版本冲突均要求重新读取，不静默覆盖。EnsureDraft 与 Publish/MoveToDraft 并发时，Lifecycle 版本和 Article 锁保证复制的公开 revision 与提交时状态一致。

### 3.5 GraphQL enum、权限与 nullability

Ticket 专用 `TicketPublicationState` 只有 `DRAFT | PUBLISHED`，映射 ArticleLifecycle 的同名状态；不保留 `HELD/INTERNAL`。User 可为两者；Worker/Case 的 ArticleLifecycle 始终为 `DRAFT`，Gate 与数据库均拒绝其 Publish。普通 Article 的 archived/deleted/destroy 不经 Ticket 产品命令暴露。公开查询只返回通过 Ticket Gate 的 Published User Ticket；不满足时详情为 null/404、列表排除整行，不能以空字段对象泄露 Draft。

以下是 Ticket GraphQL 对象的字段声明；nullable 字段在内部读取仍有表中保证。公开查询固定返回私有字段 null，不因 viewer 恰有管理员身份而自动切成内部结果；调用内部 query 必须通过 `ticket.read_internal`。`TicketContent` 沿用共享内容表示，`title/digest/body` 均非 null（空摘要/正文使用现有规范化空值），对象是否存在由下表决定。

| 字段及 GraphQL 类型                             | public User | internal User                                                                 | internal Worker/Case               |
| ----------------------------------------------- | ----------- | ----------------------------------------------------------------------------- | ---------------------------------- |
| `publicationState: TicketPublicationState!`     | `PUBLISHED` | `DRAFT` 或 `PUBLISHED`                                                        | `DRAFT`                            |
| `lifecycleVersion: Int`、`workflowVersion: Int` | null        | 非 null、正整数                                                               | 非 null、正整数                    |
| `draftVersion: Int`                             | null        | 有 ArticleDraft 时非 null，否则 null                                          | 非 null                            |
| `publicationPreview: String`                    | null        | 非 null 的 64 位十六进制预览锚点                                              | 非 null，但不开放 Publish          |
| `draftContent: TicketContent`                   | null        | 有 ArticleDraft 时返回；否则 null，不把 Public 伪装成 Draft                   | 非 null                            |
| `publishedContent: TicketContent`               | 非 null     | 有 ArticlePublic 则返回，包括撤回后保留的上次发布内容；从未发布为 null        | null                               |
| `hasUnpublishedChanges: Boolean`                | null        | 非 null；无 Draft 为 false，无 Public 为 true，其余比较规范化内容 fingerprint | null（内部内容不提供对外发布差异） |
| `innerId: ID`                                   | 非 null     | 从未发布为 null，曾发布后保留                                                 | null                               |
| `activity: TicketActivityConnection`            | null        | 经内部 Gate 的分页结果，空结果为 `entries=[]`                                 | 同 internal User                   |

`title/digest/body` 的公开值取 publishedContent，内部值取 draftContent，否则取 publishedContent；内部 User 两者都缺失是完整性错误。GraphQL SDL、resolver、生成类型、Workbench 初始化和 public query 字段拒绝/置空用例一起验收。版本 1 的新 Draft 存在不必然意味着内容已改变；内部 User 的 `hasUnpublishedChanges` 必须比较内容，不能只判断 Draft 行有无。Worker/Case 的 autosave 提示依据本地未保存输入和 Draft 版本，不显示对外发布差异徽章。

### 3.6 Ticket 的共享内容、标签与资产适配

目标选择固定为：**User/Worker/Case 都使用不带 typed extension 的通用 ArticleDraft/ArticleRevision；不新增 TicketDraft/TicketRevision。**正文仍归 ArticleBodyDraft/ArticleBodySnapshot；Ticket State 只保存业务事实。现有 Draft.Store、Revision.Persist 的 typed model 映射仅适用于普通 Article/Doc，直接传 `:ticket` 会进入 Map.fetch!/标签/typed 写入路径；“复用”要求先提取基础 primitive，不能把 Ticket 塞入任意普通 thread 分支。

`CMS.Tickets.Content` 是 Ticket Command 调用的事务内内容适配层，接收已授权并锁定的 Article、规范 Community 和版本，不另开事务、不取代 facade/Gate。它组合共享的 Draft body/head、规范化 fingerprint、Revision snapshot/head、ArticlePublic 和 `Assets.Refs` primitive。共享基础模块不引用 TicketState/TicketTag/TicketAssetRef；普通 Article/Doc 的 typed orchestration 留在原 owner，未知 thread/能力组合继续拒绝。具体共享函数签名在 V2-0 盘点并冻结；V2-1/2 必须用真正的 `thread=:ticket` 跑通 Create/Save/Ensure/Publish/删除工作区，不能只证明普通 Post primitive 可运行。

## 4. TicketSource 与首批 Post 规则

### 4.1 关联身份与最小字段

**TicketSource 是 Ticket 与一条来源信息之间的持久化关联。**一张 User Ticket 可以关联多个来源，同一来源也可以关联多张 User Ticket；同一 Ticket 与同一来源只保留一条关系。Worker/Case 继续通过已有 Ticket 内部关系组织工作，首批不直接建立 TicketSource。来源内容、权限和生命周期由来源资源拥有；Ticket 内容与来源内容各自独立，创建时复制内容不意味着后续自动同步编辑。

目标模型为 `CMS.Tickets.Model.Source`，表为 `cms.ticket_sources`。现有 `CMS.Model.TicketPost` / `cms.ticket_posts` **完整退役**：模型、表、查询、命令、GraphQL、约束、Activity 动作及消费者一起替换，不保留两套关联事实、旧入口别名、兼容读取或双写。第 7.2 节先清空旧关系，再按新结构重建，不回填旧关联。

| 字段          | 含义                        | 首批约束                                                               |
| ------------- | --------------------------- | ---------------------------------------------------------------------- |
| `id`          | 这次关联的身份              | UUID 主键；与来源 Post ID 区分，重新关联生成新 ID                      |
| `ticket_id`   | Ticket 的稳定 Article ID    | 非 null、FK；必须是具有唯一规范 Community binding 的 User Ticket       |
| `type`        | 来源类型                    | 非 null；Ecto `:post` / DB `post` / GraphQL `POST`，首批只接受这一个值 |
| `post_id`     | 来源 Post 的稳定 Article ID | 非 null、FK；必须为 Post，满足同 Community 和建立时公开可读约束        |
| `inserted_at` | 建立关联的时间              | UTC；Ecto `:utc_datetime`、migration 使用项目的 `timestamps()`         |
| `updated_at`  | 项目统一时间字段            | 同上；不作为内容或 workflow 的独立版本                                 |

**来源分类字段固定命名为 `type`。**`Ticket.type` 的 USER/WORKER/CASE 与 `TicketSource.type` 的 POST 属于不同对象、不同 enum。来源类型采用显式闭集，新增类型随实际接入的 schema/约束一起实施，不预建其他来源的空字段或通用参数袋。

基础约束包括：唯一 `(ticket_id, post_id)`；反向 `(post_id, ticket_id)` 索引；`type=post` check；两端 FK 与跨表 type/thread/Community guard。TicketSource 的 `ticket_id/type/post_id` 建立后不可原地替换，换来源须显式 unlink/link。Community 从 Ticket 的规范 binding 确定，不在关系里再保存一份 Community 权威。关联人、操作原因、触发入口和 commandId 使用 Activity/Receipt 记录。

### 4.2 建立与解除关联

目标入口为 `CMS.Tickets.Commands.LinkSource.execute` / `UnlinkSource.execute`，替换旧 `link_post/unlink_post` 命令、GraphQL mutation 及前端调用。LinkSource 明确提交 `type=POST` 和 `postId`；UnlinkSource 使用所属 Ticket 下的关联 ID。两者都携带 commandId 和 `expectedWorkflowVersion`，沿用 Command Receipt、Gate 与版本冲突合同，不增加来源版本。

CreateFromPost 在自己的创建事务内建立第一条 TicketSource，复用相同的来源校验与持久化 primitive，并一次提交 Ticket 内容、关系、Activity 和 Outbox；不嵌套调用另一个 LinkSource Command 或保留旧 TicketPost 写入路径。创建结果返回最终 workflowVersion。

| 动作          | 同一事务内的事实与效果意图                                                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 建立关联      | 按第 4.5 节锁序加载、授权、校验两端；插入 TicketSource；按首批 Post 规则 reconcile；递增 workflowVersion、写 source_linked Activity 和 Outbox                                  |
| 解除关联      | 校验 Ticket 管理权限、版本与关联归属；捕获旧关联 ID、Post locator 和受影响集合；删除 TicketSource；按剩余 Post 关系 reconcile；递增版本、写 source_unlinked Activity 和 Outbox |
| Post 永久删除 | 原删除 Command 显式清除该 Post 的全部 TicketSource，按同一规则处理每个 Ticket，再删除 Post；不能靠 FK cascade 跳过状态/Activity/Outbox                                         |

重复建立已有关系或重复解除时，实际未变化就不重复递增版本、写 Activity 或生成效果；既有版本冲突与 Receipt 重放规则仍有效。任一步失败整笔事务回滚。解除关联不删除来源 Post，历史由 Activity 保留；重新关联是新关系，不复用已解除的关联 ID。Draft Ticket link 不自动发布，unlink 也不自动重新发布。

### 4.3 来源读取与反向查询

来源查询返回关联 ID、`type`、关联时间和当前可读取的 Post 摘要。标题、链接、公开编号来自 Post 当前内容及 binding，不复制为 TicketSource 的内容权威；创建时拷入 Ticket Draft 的内容由 Ticket 后续独立编辑。

GraphQL 来源对象的 `id: ID!` 是关联 ID，`type: TicketSourceType!` 使用独立 enum，当前只含 POST；与 Ticket.type 使用的 enum 分开。公开与内部来源字段按各自查询显式选择，不因 viewer 是管理员就把公开来源查询切换为内部结果。

| 查询                      | 范围与用途                                                                                                                   |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Ticket 公开来源列表       | 只返回通过 Article Gate 的关联 Post，供公开详情和卡片展示；来源计数按公开可见集合计算                                        |
| Ticket 内部来源列表       | 通过 ticket.read_internal 后返回完整关联及有权读取的来源状态/阻断原因，供 Workbench 管理；总持久化关系数与可见引用数明确区分 |
| Post 内部关联 Ticket 查询 | 返回该 Post 的内部关联 User Ticket，包含 Draft，用于管理弹窗已有工单提示                                                     |
| Post 公开 progress 查询   | 只聚合当前可公开的关联 User Ticket，沿用第 5.3 节读时计算；不承担内部去重提示                                                |

列表/反向查询采用分页或批量读取，不逐行 Gate；statsBatch 继续按最多 100 个 Post ID 分片。第 4.4 节降级判定使用持久化关系数，不能使用公开来源列表长度。

### 4.4 首批 Post 的 ReviewBlock 与发布规则

本节只规定 `TicketSource.type=:post` 的首批产品规则。模型扩展不改变已确认的 Post 发布/降级合同；其他来源接入时再确定各自的可见性、发布和删除行为，不把此处按 Post 关联数计算的规则推广为通用来源规则。

这里的“单 Post Ticket”按 **该 Ticket 在本次变更完成后仍存在的全部持久化 `TicketSource(type=:post)` 行数为 1** 判定；包含已被 ReviewBlock、Trash 或其他 Article Gate 条件隐藏的 Post，不按公开可见引用数计数。同一 Post 是否还关联其他 Ticket 不影响该 Ticket 的判断。ReviewBlock apply/end 不删关系行，所以前后行数相同；unlink/物理删除先改变关系，再按变更后的行数核对。所有影响同一 Ticket 的操作在锁内串行，避免并发 link/unlink 改变判定。

| 场景                                                | 事件提交后的状态与公开投影                                                                                                                             | 解除限制 / 来源重新公开                                                                                                    |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| Ticket 关联多篇 Post，其中一篇隐藏                  | Ticket 保持 Published；只从公开 refs、聚合计数和该 Post 的公开 progress 中过滤隐藏 Post。其他公开 Post 继续显示 Ticket。                               | 被过滤引用自动回到公开投影；Ticket 发布状态不变。                                                                          |
| Ticket 仅关联一篇 Post，该 Post 隐藏                | 同一事务执行 Ticket `Published -> Draft`，记录来源、Activity 和失效意图。公开 Ticket 与进展消失。                                                      | Ticket 仍为 Draft；管理员检查当前独立标题/摘要和公开更新后显式发布。                                                       |
| 多篇 Post 全部隐藏                                  | Ticket 仍为 Published，但公开 refs 与 Post 派生计数为 0；Ticket 自身内容仍须独立满足公开审核。                                                         | 各引用随各自 Post 恢复而返回。                                                                                             |
| Post Trash 或普通 Post 撤回为 Draft                 | 来源经 Article Gate 不公开；单关联 Ticket 转 Draft，多关联 Ticket 保持原发布状态并过滤来源。                                                           | Restore/重发只恢复来源；已转 Draft 的 Ticket 不自动发布。                                                                  |
| Community 从 public-readable 变为非公开             | 先写新 Community 状态，再按同一来源规则 reconcile；单关联 Published Ticket 转 Draft，多关联保持 Published；整个 Community 的公开读取同时由 Gate 关闭。 | Community 恢复仅恢复 Gate/引用及缓存；单关联已 Draft 的 Ticket 仍需显式发布，多关联仍 Published 的 Ticket 可随 Gate 恢复。 |
| Post 永久删除或显式 unlink                          | 先改 TicketSource，再按全部剩余行计数；零关联或唯一剩余来源隐藏时转 Draft，其他情况不自动发布。                                                        | 删除无自动恢复；重新 link 不自动发布。                                                                                     |
| Ticket 自身 `awaiting_ai`                           | 保持原 publicationState；若原为 Published，仅由 Gate 暂时隐藏。任何 active Ticket ReviewBlock 均阻止 PUBLIC Update 和公开通知。                        | 仍 Published 且所有限制都已结束时可随 Gate 恢复；原为 Draft 时继续 Draft，限制存在时 Publish 拒绝。                        |
| Ticket 自身 `awaiting_human/ai_suspect/manual_hold` | Published Ticket 同事务转 Draft；原为 Draft 时保持。未知类型 fail closed，按需要人工审查的规则降级。                                                   | 解除限制不自动发布；全部限制结束且来源满足 Publish 条件后，预览并显式发布。                                                |

公开 Ticket 不得泄露被隐藏 Post 的标题、链接、原文片段、作者或从该 Post 派生的计数；内部工作台仍能按权限看到关联及 ReviewBlock 原因。Ticket 独立内容若复制或概括了违规 Post，必须走 **Ticket 自身的审核**，不能寄望于过滤引用解决内容泄露。创建关联时 Post 必须公开、Community 一致；后续审核隐藏只改变公开投影和上述单 Post 转换，不删除 TicketSource 事实。

**唯一来源降级规则**：若 Ticket 已是 Draft，保持 Draft；若仍 Published，持久化关联数为 0 时转 Draft；为 1 且唯一 Post 在 Ticket 所属 Community 不公开时转 Draft；为 2 及以上时不因 Post 可见性转 Draft，即使全部隐藏。关系变更、Post ReviewBlock/Trash/撤回和 Community public-readable 状态变化均执行此规则；**绝不自动重新发布已转 Draft 的 Ticket**。因此 A、B 都隐藏时仍 Published；随后 unlink A，剩下隐藏 B，则在 unlink 事务中转 Draft。反过来先 unlink A、再隐藏 B，最终也为 Draft。Post Restore、重发和 Community 恢复只恢复引用；先前自动转 Draft 的 Ticket 仍需显式发布。若恢复后最后一条关系被解除，Ticket 仍为 Draft。本版 User Ticket 不允许零关联发布。

**Draft User Ticket 的内部 link 允许**关联当前公开、同 Community 的 Post，且 link 不自动发布；公开“关联已有工单”选择器只列 Published。Publish 以提交时的持久化关系重查：零关联拒绝，唯一关联隐藏拒绝，**多关联也至少需要一篇当前可见 Post**；同时要求 Ticket 自身无活跃 ReviewBlock、当前 Draft 与全部将公开的 Update 已预览确认。已 Published 的多 Post Ticket 后来全部来源隐藏，仍保持 Published；这不授权在全部来源隐藏时执行一次新的 Publish。Draft 上 unlink 仍更新关系与 workflow 版本，不自动恢复发布。

Publish 的“无活跃 ReviewBlock”指锁内校验时的现存限制；选定新 revision 后的首次送审也在该事务内完成，新产生的限制立即按本节处理，不先提交一次可读内容再补审核。若产生 awaiting_ai，最终可为 Published 但 Gate 隐藏、无公开通知；若产生其他需人工审查的限制，则最终为 Draft 并保留工作区。first_published_at 记录首次已提交的发布事实，不承诺曾有外部请求实际读到内容；最终工作区/状态与版本由 Command 结果返回。

**Community binding 移动/解除的硬约束**：只要一个 Post 存在任意持久化 `TicketSource(type=:post)` 关联，无论 Ticket 是 Draft/Published、Post 当前是否被审核隐藏，也无论待移动/解除的是该 Post 的哪一个 Community binding，Post 的 `move` 与 `unmirror` 都必须拒绝，不能隐式 unlink 或让 TicketSource 指向缺失/跨 Community 的 binding。Ticket 自身仍禁止普通 Article 的 move/unmirror；其唯一规范 binding 另受原有约束保护。当前 `BindingPersist.ensure_no_ticket_link` 和旧 `article_binding_ticket_post_guard` 只检查**待变更来源 Community** 的 TicketPost 关联；V2 须以 `article_binding_ticket_source_guard` 查询新表并扩大保护范围，旧迁移文件不改写。若未来允许移动已关联 Post，须另立合同，明确同一事务中的显式 unlink、上述降级规则、编号/Community 归属和 Ticket/Post 缓存失效；本版不开放。

### 4.5 事务入口、锁序与数据库写权限

事务入口与复用边界固定如下：

- 人工审核由现有 `CMS.Review.Commands.Decide.execute` 的 `change` 持有事务；recheck 的首次限制由 `CMS.Review.Commands.Recheck.execute` 持有事务；发布/编辑时的首次送审由对应 Article Publish/Edit Command 持有事务。AI 结果由 `CMS.Review.Requests.run_current` 经 `CMS.Review.apply_result_internal` 调用 `CMS.Review.Commands.ApplyResult.execute`，由该内部系统 Command 持有事务并在 `change` 调用 `CMS.Review.Results.apply_in_transaction`。以 review request ID、当前请求校验与 applied 标记保证重试幂等；Requests 不另开结果应用事务。`Review.Target` 与 Gate Loader 均在 Article 锁前取得全部 binding Community 的 admission。
- 上述 Command 经 `CMS.Review.Restrictions` 在已有事务内调用 `CMS.ReviewBlocks.apply/end_blocks`；目标是 Post 时调用唯一的 **`CMS.Tickets.PostVisibility.reconcile_in_transaction`**。目标是 Ticket 自身时调用 **`CMS.Tickets.Publication.reconcile_restrictions_in_transaction`**，与 MoveToDraft 共用 ArticleLifecycle 转换、EnsureDraft、Activity 和 cache primitive；不调用工作状态 `Tickets.Lifecycle` 改发布状态。Review 层只编排，不持有第二份降级或缓存规则。`ReviewBlocks` 不再直接调用 `CMS.Tickets.Commands.Mutate.hold_linked_to_post`、Ticket cache 或其他 Ticket 模块；`Articles.Lifecycle.apply_review_block/end_review_blocks` 的直通入口必须改为该编排或移除，不能绕过 Ticket 处理。Ticket 自身限制 apply/end 即使只影响 Gate，也必须写第 5.2 节效果。
- Post Trash 由 `CMS.Articles.Commands.Trash` 的 `change` 持有事务；Restore 由 `CMS.Articles.Commands.RestoreTrashed` 持有事务；永久删除由 `CMS.Articles.Commands.PermanentlyDeleteTrashed` 持有事务。三者调用共享的 **`CMS.Tickets.PostVisibility.reconcile_in_transaction`**（新增 Ticket 领域函数），与 Review 层使用同一降级规则。Trash/Restore 要先写入目标 ArticleLifecycle/trash 事实，再在同一事务按新状态 reconcile；不能在旧公开状态下预判。永久删除先在同一事务显式清理 TicketSource、核对关联数和记录 Outbox，再删除 Post；不能仅依靠 FK cascade。`Tickets.Commands.LinkSource/UnlinkSource` 先变更关系行，再在自己的事务中 reconcile。
- 普通 Post 发布、重发或 Published→Draft 的 Article Command 也在写完公开事实后接上述 reconcile；不能只清 Article 缓存。状态仍 public-readable（例如普通 Article archive）的转换不强制降级，但公开投影变更仍写缓存意图。
- Community 状态矩阵唯一来源是 [Community Lifecycle](../lifecycle/contract.md) 的 `readable_states(:public)`。所有可能改变该判定的 Community Command、Blocker apply/end、系统 reconcile 和销毁 workflow 都经同一事务编排：锁定 Community Lifecycle、写入新状态后，若 public-readable 判定改变，调用 **`Tickets.PostVisibility.reconcile_community_in_transaction`**。该批量函数从全部持久化关系枚举本 Community 的 User Ticket，按同一个 reconcile 规则执行；来源可见性通过组合 Article Gate 的批量 query 求值，不逐行 Gate 查询。Community Lifecycle 模块仍只拥有自身状态，不直接依赖 Ticket；事务所有者负责跨领域调用、Ticket Activity 与 Outbox。恢复时不发布 Draft Ticket；`active ↔ read_only` 不改变 public-readable 判定，不作来源降级。
- Post binding 的 `move/unmirror` 由 `CMS.Articles.Commands.Move/Unmirror` 的现有事务边界负责，在 `BindingPersist` 检查所有持久化 TicketSource 关系；存在关联时命令和数据库 trigger 均拒绝，事务不写 Ticket 状态或 Outbox。显式 unlink 成功后才可重试 move/unmirror；unlink 自身按上述降级与失效规则执行。
- 全局锁序为 **Community Lifecycle（按 Community ID）→ Post Article/Lifecycle（按 Post ID）→ Post ReviewBlock → Ticket Article/Lifecycle/State（按 Ticket ID）→ TicketSource 写入**。普通 Post/Ticket Command 在锁 Article 前取得涉及 Community Lifecycle 的 admission `FOR SHARE`；改变 Community 状态的所有者直接取 `FOR UPDATE`，不得持有 Post/Ticket 锁后升级 Community 锁。Community 批量 reconcile 持有 Community 写锁后，按序锁定全部受影响 Post、Ticket，再执行唯一降级规则；Ticket 自身审核/内容动作不需要 Post 写锁时直接从 Community 锁进入 Ticket 锁，后续不得反向等待 Post。审核路径在 Post 锁后锁/写 ReviewBlock；Trash/Restore 与 link/unlink 不锁 ReviewBlock。
- Ticket Publish 先读取关联/Community 集合用于按序预锁，再锁**全部当前关联 Post**及 Ticket，锁后重读集合；关系或 Community 集合变化则整笔事务重试，不能持有 Ticket 锁补锁另一篇 Post。全局 Post 审核覆盖多个 Community 时同样先按序预锁相关 Community 并重读 binding 集合。关系计数、来源可见性和版本复查在 Ticket 锁下完成。V2-0 必须核对现有 Gate Loader 是否提前持有相反顺序的锁，并用并发原型验证 Community 隐藏/恢复、Post 审核和 Publish/link/unlink；不能仅在新函数内部调换顺序。
- Community 变为非公开的状态、全部必要 Ticket 降级、Activity 与 Outbox 必须同事务提交；恢复同样写覆盖其范围的缓存意图。按真实 Ticket 数量测量锁时间，规模过大时 V2-0 需先评审保持 Community 非公开直至批量处理完成的 workflow；不得先恢复公开再异步降级，也不得提交部分 Ticket 后宣称该 Community 转换完成。

数据库 `ticket_source_scope_guard` 的 INSERT/键 UPDATE 必须取得相同 Community admission 与 Post→Ticket 锁，并允许内部 Draft User Ticket 关联公开 Post。binding guard 与关系插入必须协调同一 Post 锁；直接 SQL binding 变更与 link 并发也要验证，不能靠一次无锁 EXISTS 保证硬约束。关系删除采用**独立写入角色**：普通运行时 DB role 无 `ticket_sources` DELETE/键 UPDATE 权限；`CMS.Tickets.Commands.UnlinkSource` 与 Post 永久删除 Command 使用仅在这些 Command 配置的 `cms_ticket_write` 连接，整笔 Gate/Lifecycle/Persist/Activity/Outbox 事务使用**同一连接**，不跨 Repo 拼事务。Post 物理删除须先显式 unlink/reconcile，FK 改为限制直接 cascade；不能以级联删除绕过效果。直接 SQL 负向测试使用普通运行时角色验证 DELETE/键 UPDATE 被拒绝，并用受控写入角色验证 FK/trigger 不能被绕过；拥有写入角色的受控 Command 完成全套事实。超级用户维护操作不属于产品合同。角色/单连接、Community admission 和 trigger 锁序原型是 V2-0 出口，任一无法落地则不得进入 V2-3 切换。

apply 的单 Post 转 Draft、Activity 和缓存 Outbox 必须与 ReviewBlock 写入同一事务；多 Post 的引用过滤和缓存 Outbox 也在同一事务落意图。end/restore 时为恢复引用写入缓存失效；已转 Draft 的 Ticket 不自动发布。原有“任一 Post 不公开就 hold 全 Ticket”的旁路全部移除。

### 4.6 后续来源与外部集成的边界

以下仅记录扩展场景，不属于本轮实现或已冻结的渠道产品合同。首批闭集仍只有 POST；新增类型时再确定目标身份、FK/约束、读取授权、公开引用、状态变更与删除行为。通过 Bot/Agent 创建 Post 后再关联 Ticket，TicketSource.type 仍为 POST，接入入口记录于共享 Activity 上下文。

| 场景                                           | 后续接入方向                                                                                                                            | 本轮边界                                                                              |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Comment，包括 Article 选中文字后提交的 Comment | Ticket 关联 Comment，选区锚点与父 Article 上下文由 Comment 拥有；Comment 上的 Ticket 引用按公开展示方向考虑                             | 展示细节、权限及父 Article 变化后的行为接入时确定，不新增另一种选区来源类型           |
| Survey                                         | 具体响应 SurveyResponse 作为候选来源粒度，Survey 本身提供上下文                                                                         | 不预建 Survey 模型、字段、发布或通知规则                                              |
| Email、IM、Agent 对话                          | Conversation 的消息或会话片段作为候选粒度，渠道由对应资源/集成维护                                                                      | 不预定转录内容、参与者、回复地址和可见性合同，也不要求这些资源全部成为 Article thread |
| Gong 等客户通话工具                            | 从通话/转录提取反馈并关联 Ticket，保留来源上下文；参考 [Gong 集成](https://help.featurebase.app/help/articles/2512395-gong-integration) | 不新增独立通话来源模型或 AI 提取流程                                                  |
| Linear 等 issue tracker                        | 关联外部执行事项、同步状态等；参考 [Linear 集成](https://help.featurebase.app/help/articles/6970004-linear-integration)                 | 外部执行关联是否属于 TicketSource、同步方向/映射/冲突规则，实际接入时再定             |
| 飞书、IM、支持 @bot 的文档平台                 | 从原位置创建/查询/关联/更新 Ticket，接收异步进展回复                                                                                    | 协议入口由统一接入层负责；Bot 不是预设的来源类型                                      |

外部 Issue、应用内反馈、访谈记录、测试缺陷、错误告警、人工事项等当前可由 Post 承载，无需逐项增加来源类型。收集来源、外部任务同步和交互入口可由同一平台同时提供，具体集成按实际能力实现。保持明确模块与函数边界，不引入运行时插件注册中心、通用规则引擎或可配置来源工作流。

未来可在 Ticket 变更后按模板回复原邮件线程、IM 会话或其他原始位置；模板、目的地、启用条件、投递记录属于对应集成。来源条数、反馈用户数和 Post 投票数分别统计；来源关联不自动授权通知所有参与者。上述渠道的发布资格、审核降级和同步冲突规则留待接入时评审，不因本节改变第 4.4 节 Post 合同。

## 5. 效果、缓存与界面

### 5.1 Activity 与 Workbench 历史

新增 `GroupherServer.Activity.Ticket`、`GroupherServer.Activity.Model.TicketLog` 和 `activity.ticket_logs`，接入 `Activity.Artiment` 的封闭 handler。动作至少包括 `created`、`published`、`moved_to_draft`、`work_status_changed`、`source_linked`、`source_unlinked`、`public_update_published`、`public_update_superseded`；来源动作替换旧 post_linked/post_unlinked 命名，不保留别名。手动内容 Draft 自动保存不逐次写 Activity；公开内容发布记录 revision。状态动作的受约束 payload 保存 `from/to`、reason；来源动作保存 `ticket_source_id`、`source_type` 与首批 `post_id`，解除后仍可审计。共用字段保存 user/system actor、source、`operation_ref=commandId`、`event_ref`、时间与 Community；共用 source 表示操作入口上下文，与 TicketSource 关联身份区分。通知引用 Activity event_ref 或 PUBLIC Update ID，不引用 TicketEvent。

PUBLIC Update 的 Activity 与 TicketUpdate、workflowVersion、通知及缓存 Outbox 在同一个现有 Command 事务中写入。普通公开进展追加一条 `public_update_published`，payload 为 `{update_id}`；修正只追加一条 `public_update_superseded`，payload 为 `{update_id, supersedes_id}`，引用新 Update 和被替代的旧 Update，不再额外写发布事件、不复制正文。INTERNAL Update 不写这两类公开进展动作。User/Worker/Case 创建都在新 Ticket 自己的 stream 写一条 `created`；Worker 的创建记录不能只落在父 User Ticket。所有事件沿用 actor、Community 和 `operation_ref=commandId`；同 commandId 重试不重复写入，Activity 失败须回滚领域写入、版本及效果意图。

数据库动作闭集通过新增 `20261102090000_align_ticket_activity_actions.exs` 对齐，不修改已执行的创建迁移。迁移锁内发现旧 `update_added/update_superseded` 记录则拒绝升级，留待独立历史核查；不改写 append-only 记录，也不从现有 Update 补造遗漏历史。回滚若存在新动作记录同样拒绝。当前代码和数据库均不接受旧动作别名。

需要消费所有 PUBLIC Update 的消费者必须同时处理 `public_update_published` 和 `public_update_superseded`；不能假设每个新公开 Update 都有 published 动作。当前通知按 TicketUpdate 写 Outbox，不依赖这两个 Activity 动作触发，不应另外订阅它们重复通知。改变修正事件数量或语义须先修改本合同及消费者测试。

#### Activity 动作迁移部署清单

以下步骤针对 `20261102090000`，不能替代第 7.2 节的数据切换清单；当前授权与执行证据仅限本地/测试库。部署目标库的计数、迁移版本和恢复验证必须单独记录，不能沿用本地零行结果。

1. 在目标库只读预检并记录下列计数、目标环境、执行时间及当前 migration version。预先确定失败后的恢复方案，保留可验证的快照；不得删除或重命名旧 Activity 以强行通过迁移。

   ```sql
   SELECT
     count(*) FILTER (WHERE action IN ('update_added', 'update_superseded')) AS legacy_actions,
     count(*) FILTER (WHERE action IN ('public_update_published', 'public_update_superseded')) AS current_actions
   FROM activity.ticket_logs;

   SELECT max(version) AS migration_version,
     coalesce(bool_or(version = 20261102090000), false) AS activity_actions_migration_applied
   FROM public.schema_migrations;

   SELECT conname, pg_get_constraintdef(oid), convalidated
   FROM pg_constraint
   WHERE conrelid = 'activity.ticket_logs'::regclass
     AND conname = 'ticket_logs_action_check';
   ```

2. 升级前停止所有 Ticket 写入口及可能写入 Ticket Activity 的后台任务，等待在途事务结束，再次执行计数。只有 `legacy_actions = 0` 才可执行升级；非零则停止发布并独立核查历史。应用侧停写覆盖迁移结束到新版本启动之间的窗口；迁移本身在同一 DDL 事务内取得表锁、检查数据并替换 CHECK，防止检查与 DDL 之间出现竞态。
3. 完成 migration 后验证 `activity.ticket_logs` 的 `ticket_logs_action_check` 对公开进展仅接受新动作名、其他动作保持原闭集，再启动新应用，验证 PUBLIC 追加、修正和内部历史读取，最后恢复写入。记录实际迁移版本、约束和 smoke 结果。
4. 数据库回滚前同样停写并重新计数；只有 `current_actions = 0` 才可回滚此 migration，旧动作会阻止升级，新动作会阻止回滚。任一失败都应中止发布流程、核对数据及约束，不能绕过保护继续启动不兼容应用。
5. 一旦产生新动作，默认采用向前修复。旧应用的 Ecto.Enum 不认识新动作，单独回退应用也可能使历史读取失败；若需回退应用，须事先准备并验证能读取新动作、写入符合当前 CHECK 的回退版本。不能把应用回退等同于数据库可回滚，也不能为回退改写 append-only 历史。

`activity_migration_test.exs` 在测试库事务内执行真实 migration 的 up/down：分别验证两种旧动作阻止升级、两种新动作阻止回滚，失败后日志全行及数据库约束不变；无不兼容动作时往返成功且动作约束随方向切换。测试不更改 `schema_migrations`，不代表目标环境已完成部署。

Ticket Activity 的动作仅供**内部历史**，不注册 `article_log` / `community_log` 公开 surface；Workbench 通过 `ticket.read_internal` Gate 后按 `(occurred_at, record_sequence)` 分页读取。TicketEvent 表、模型、GraphQL `events` 和写入口直接删除；不回填旧事件、不合并读取旧表。普通 Article 首次发布也补 `published` Activity，发布后撤回补 `moved_to_draft`，但“是否曾发布”的状态判断以 `ArticleLifecycle.first_published_at` 为准。

### 5.2 浏览器与 CDN 失效

Ticket 页面继续有独立 `ticket_list`/`ticket_detail` 标签；这**不免除** Ticket 变化对 Post 标签的 purge。任一来源事件若使 Ticket 转 Draft，必须同时执行第一行的全部关联 Post 效果；不能只清事件目标 Post。删除/unlink 前捕获旧 locator、Ticket ID 与关联集合，使用变更前后集合的并集生成意图；提交后不再从已删除关系反查目标。Community 级事件必须确认 SSR 实际附带覆盖标签，否则枚举详情标签。所有 durable purge 意图在领域事务中写 Outbox，按标签去重、失败可重试；浏览器 query 失效与 CDN purge 分别验收。`useKanbanTickets`、Workbench、Post 管理弹窗与公开页面使用同一 query key 合同。

跨 Context 调用只进入 `PublicCache` facade，不直接使用 `PublicCache.Tags` 或 `PublicCache.DeliveryConfig`；缺少的能力由 PublicCache 公开边界提供。Ticket cache/notification 意图由对应 Effects owner 写 CMS.Outbox，Workflow 负责投递。R10/R11 同时验证这些结构门禁，不以缓存标签结果正确替代调用边界。

- 计数：只累计当下可见的关联 Post；SSR board 和详情的 `statsBatch` 都按最多 100 个 ID 分片，去重后求和，所有分片加入 hydration。超过 100 个引用不能使详情失败。
- 发布 UI：先 EnsureDraft/保存，再展示**即将公开的 revision** 的标题、摘要、正文、可见来源和将恢复的全部 PUBLIC Update；管理员确认后发布。未保存编辑不能偷偷使用旧 revision。Draft 或存在任何 active Ticket ReviewBlock 时，禁用 PUBLIC Update 并说明原因；INTERNAL Update 仍按内部 Gate/版本合同处理。
- Post 管理弹窗使用内部关联查询显示已有 Ticket，包含 Draft Ticket；公开 `postProgress` 不能承担内部去重提示。公开“关联已有工单”选择器不列 Draft，内部工作台可向 Draft Ticket link 公开 Post。
- 通知是效果：`tickets/effects/notifications.ex` 决定可见关联 Post 的作者/公开评论参与者与去重；`tickets/effects/cache.ex` 生成失效意图；`outbox/workflow/ticket.ex` 投递。公开通知入 Outbox 和投递时都检查 Ticket 为 Published User、其 Community 可公开且 Ticket 自身无任何 active ReviewBlock（包括 awaiting_ai）；投递时还重查来源 Post public scope。隐藏 Post 不参与收件人或内容。条件不满足的公开通知意图记为已抑制，不在解除限制/重发时补发；正常显式重发可产生自己的新通知 source。审核限制 apply/end 仅写审计/缓存效果，不发送公开审核原因通知。

### 5.3 首批异步联动：相关 Post 的处理进度

Ticket Command 在事务内提交工作状态、来源关联、必要的发布降级、Activity 和 Outbox 意图；提交后由已有 CMS Outbox/Workflow 异步处理关联 Post 的进度展示刷新、缓存失效和符合资格的通知。发布资格与 ReviewBlock reconcile 仍按第 4 节同步提交，不能延迟到异步消费者才撤回公开资格。

浏览器在已确认命令后按第 5.2 节失效对应 query key；Outbox 负责 durable cache/notification 效果。首批沿用现有查询刷新机制，不把新增浏览器推送通道作为该闭环的前提。

Post progress 继续从当下可公开的关联 User Ticket 读时批量聚合，不写 PostState、ArticlePublic 或新的持久化进度表。所谓“同步状态给 Post”指刷新这个投影及其消费面，Ticket 工作状态仍是唯一事实源。

| 当前可公开的关联 User Ticket         | Post 进度    |
| ------------------------------------ | ------------ |
| 无关联                               | null，无进度 |
| 全部 TODO                            | TODO         |
| 全部 DONE                            | DONE         |
| 其余组合，包括只有 WIP 或 TODO + WIP | WIP          |

结果同时返回 completed/total 和 Ticket 公开标题、编号/链接、状态；Case/Worker 不直接参与聚合。来源 link/unlink、Ticket 工作状态、公开内容/可见性和审核资格变化均失效相关 Post 的 progress/detail/list 消费面。Post 互动/评论反向失效 Ticket 聚合计数，沿用第 5.2 节矩阵。

消费者按事件与效果目标幂等、可重试；旧事件延迟到达时读取当前事实或仅执行失效，不能把 Post 展示回写成旧状态。unlink/删除的旧 locator 在原事务中捕获，失效覆盖变更前后集合；通知投递时重查当前关联和资格。首批不建设外部渠道的同步配置或投递实现。
