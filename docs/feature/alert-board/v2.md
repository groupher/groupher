## 1. 已确认要求与命名

| 名称                                     | 含义与约束                                                                                                                                |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `ReviewBot`                              | 顶层业务 Context；根据提供的内容、系统和社区策略，使用 AI 等工具判断潜在违规并返回意见；不管理资源版本、可见性、人工待办或 AlertWall item |
| `ReviewBotMode`                          | `immediate`、`ai_first`、`human_first` 三种模式的枚举；模式用于调用方组织流程，不是 AI 的判断输入                                         |
| `ReviewBotConfig` / `review_bot_configs` | ReviewBot 拥有的配置模型与表；系统、各社区分别保存                                                                                        |
| `review_mode`                            | 唯一的模式字段；不再配置 `publish_mode`、`edit_mode`、`background_check`                                                                  |
| `ban_words`                              | 违禁词或短语，交给 AI 结合上下文综合判断；不做精确、模糊或正则命中后自动认定违规                                                          |
| `prompt`                                 | 系统或社区自定义的审核要求；由可信系统指令约束，不授予业务执行权限                                                                        |
| `sus_notes`                              | 潜在违规意见列表；空列表表示在完整覆盖的成功检查中没有发现嫌疑，不等于人工批准                                                            |
| `AlertWall`                              | 顶层业务 Context；系统级风险/举报展示墙，提供 item 增加、查询、消除接口；社区数据仍需按权限隔离                                           |
| `AI.check`                               | 通用基础能力；选择 AI 服务、模型、调用及解析，不是新增业务 Context                                                                        |
| `type`                                   | 新模型和 DTO 的类型字段使用 `type`，不用 `kind`；既有框架字段不做无关全仓替换                                                             |

三种模式的已确认行为：

| `review_mode` | 首次发布                                 | 修改后提交发布                              | AI 检查                                            |
| ------------- | ---------------------------------------- | ------------------------------------------- | -------------------------------------------------- |
| `immediate`   | 立即显示                                 | 修改立即显示                                | 发布和修改都后台执行系统、社区检查；发现嫌疑转人工 |
| `ai_first`    | AI 检测没问题后显示                      | AI 检测没问题后修改生效                     | 两层检查均执行                                     |
| `human_first` | 人工批准后显示；管理员能看到两层 AI 意见 | AI 检测没问题后修改生效，不再次要求人工批准 | 首发也必须执行，不能仅把 AI 当作可选能力           |

保存草稿不等于提交发布。上述公开资格仍需满足社区访问权限、资源及父资源 Lifecycle。
社区配置不能覆盖系统要求。ReviewBot 不创建 AlertWall item；CMS、Accounts 等调用方决定如何消费结果。

## 3. 领域边界与依赖方向

```text
CMS / Accounts 等业务 Context
    |
    +-- ReviewBot 配置接口：获取适用的系统、社区配置
    |
    +-- 本领域 Command：保存内容/状态 + 可靠 Effect
    |                                      |
    |                                      v
    |                                  ReviewBot.check
    |                                      |
    |                                      v
    |                                   AI.check
    |                                      |
    |                                      v
    |                                返回两层 sus_notes
    |                                      |
    +<-- 本领域 Command：接受当前有效结果 <--+
    |
    +-- 更新本领域状态
    +-- AlertWall.add / resolve：增加或消除风险 item
    +-- 本领域 Effect：缓存、搜索、通知

管理员 -> AlertWall 查询/查看
       -> CMS / Accounts 的业务 Command
       -> 本领域状态变化 + AlertWall 处理记录
```

| Owner       | 拥有                                                                 | 明确排除                                                               |
| ----------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| ReviewBot   | 审核配置、检查输入/输出、两层意见的结构化表达                        | CMS/Accounts 表、Revision/Body 版本、发布模式执行、Case、Effect worker |
| AI 基础模块 | 受运维批准的 provider/model、HTTP、协议校验、超时与诊断              | 审核配置表、review_mode、资源状态、告警、领域授权                      |
| CMS         | 提交内容、版本关联、审核等待与人工批准、有效结果应用、Gate、公开效果 | provider 选择实现、AlertWall 内部持久化                                |
| Accounts    | 自己的账号业务、有效性与授权、账号处理                               | CMS Gate；由告警数量或 AI 意见直接推导封禁                             |
| AlertWall   | 风险 item、用户举报事实、关联 AI 意见、处理历史、授权查询            | 普通发布审批队列、业务处罚、内容公开状态、ReviewBot 配置               |

所有跨 Context 写入通过公开接口；不新增万能 Gate。Accounts 初期只接入举报、驳回和人工处理记录能力，不导入旧记录，不顺带新增封号/禁言能力。
`human_first` 的正常首次发布待办属于 CMS，不因等待审批就创建“涉嫌违规”item。
AI 故障也是运行问题，不构造虚假的违规 item；CMS 可在自己的人工待办展示“检查不可用”。

## 4. 已冻结的产品决策

下列 P1–P7 已在 R0 按用户确认的发布/修改语义冻结，当前实现与测试以此为准。

| 编号 | 已冻结决策                                                                                                 | 实施约束                                     |
| ---- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| P1   | immediate 命中后隐藏对应 scope 并转人工；其他未命中 scope 不自动隐藏                                       | 由 CMS 资源 Gate 与 Lifecycle 执行           |
| P2   | 非 immediate 编辑审核期间不保留旧内容公开；沿用单一当前内容                                                | CMS 以当前提交和 Lifecycle 为准              |
| P3   | 不确定转 CMS 人工待办；仅具体嫌疑建 Wall item；故障有限重试，不伪造违规意见                                | 严格模式故障不放行；immediate 不仅因故障隐藏 |
| P4   | 新 clear 只结束被新内容替代的自动嫌疑/等待；不解除人工禁止或其他 scope 的问题                              | 人工决定由 CMS 资源限制保留                  |
| P5   | resolve 保留 Wall 历史；过期/失效使用 superseded                                                           | 不提供物理删除接口                           |
| P6   | Article/Comment 分别配置；Doc 保留 platform-only、发布后检查                                               | 三模式只用于 Article 与 Comment              |
| P7   | 系统和社区层分别满足策略；首发任一层 human_first 需要该层人工批准，修改时非 immediate 层 AI clear 自动放行 | 不做社区覆盖系统或只取一个模式               |

P1/P2/P3/P4/P7 直接影响公开语义，已由 R4/R5 按此实现；配置与 AI 能力分别归 ReviewBot 和 AI。

### R0 冻结记录

本次实施按上述决策冻结 P1–P7：immediate 命中在对应 scope 隐藏并转人工；非 immediate 修改期间不展示旧内容；AI uncertain 转 CMS 人工待办，故障有限重试且不伪造违规；新 clear 只结束自动嫌疑/等待、不覆盖人工禁止；Wall resolve 保留历史、过期项 supersede；Article/Comment 分别配置、Doc 维持平台-only 发布后检查；系统与社区分别满足策略，首发任一层 human_first 都需要该层人工批准，修改时各层 AI clear 可自动放行。后续实现和测试均以此为冻结合同。

## 5. ReviewBotConfig 与配置表

### 5.1 存储合同

PostgreSQL 表：`review_bot.review_bot_configs`，模型 `ReviewBot.Model.ReviewBotConfig`。
这里的 namespace 是实施落点；用户确认的表名是 `review_bot_configs`。

| 字段            | 类型 / 约束                        | 用途                                                         |
| --------------- | ---------------------------------- | ------------------------------------------------------------ |
| `id`            | UUID 主键                          | 配置身份                                                     |
| `community_id`  | bigint FK，可空                    | NULL 为系统配置；有值为所属社区；引用实际 Community 主键类型 |
| `subject_type`  | text CHECK article/comment/doc     | 内容类别；doc 只允许系统配置（P6）                           |
| `review_mode`   | community 行必填；system 行为 NULL | 仅决定该社区内容的发布审核模式；doc 没有社区行（P6）         |
| `ban_words`     | text[]，非空列，默认空数组         | scope 行自己的审核线索；系统值仅后端读取，社区值由管理员编辑 |
| `prompt`        | text，非空列                       | scope 行自己的审核要求；系统值仅后端读取，社区值由管理员编辑 |
| `version`       | bigint > 0，初始 1                 | 乐观并发控制及检查配置快照标识                               |
| `updated_by_id` | 现有用户 ID FK，可空               | 人工修改者；系统初始化可为空                                 |
| 时间字段        | `inserted_at`、`updated_at`        | UTC；Ecto `:utc_datetime`，DDL 默认 `timestamps()`           |

系统配置部分唯一索引：`UNIQUE(subject_type) WHERE community_id IS NULL`。
社区配置部分唯一索引：`UNIQUE(community_id, subject_type) WHERE community_id IS NOT NULL`。
不能仅用普通 nullable 组合 UNIQUE 假设系统行不会重复。社区删除遵循既有清理流程，不级联删除历史检查/告警依据。
不存冗余 `scope_key`；运行时 scope 由服务端通过 community_id 构造。对外用 `type`，不新增 `subject_kind`。
DB 使用 scope 行上的通用 `ban_words`、`prompt` 列：`community_id IS NULL` 行就是服务端系统规则，非空行就是社区规则，不复制全局值。GraphQL 只映射并返回社区配置字段 `review_ban_words`、`review_prompt`。

推荐沿用现有限额：ban_words 最多 10,000 条、每条最多 128 字符、prompt 最多 8,000 字符；另设整次 AI 输入预算。
超过 AI 上下文预算应返回可诊断的输入过大错误，不能截掉后半份词库却宣称完整通过。

### 5.2 配置读取、保存与检查快照

以下为已实施的公开接口；具体 GraphQL 调用见 §11。

```elixir
ReviewBot.configs(community_id, subject_type)
# {:ok, %{system: config, community: config}} | {:error, error}

# 内部读取；system 值不得经 GraphQL 返回

ReviewBot.update_config(
  %{type: :community, community: community},
  subject_type,
  expected_version,
  %{review_mode: mode, ban_words: words, prompt: prompt},
  actor,
  command_id
)
# {:ok, config} | {:error, error}
```

这是社区配置的 Command 接口；GraphQL 的 `review_ban_words`、`review_prompt` 会映射为内部字段 `ban_words`、`prompt`。系统配置不走这个社区管理员接口。

`configs` 是供领域内部调用的配置读取能力，不接受浏览器传入的任意 community_id 充当授权。系统策略只在服务端配置表中读取；任何 GraphQL 查询或 mutation 都不返回/修改系统审核词和系统 prompt，Dash 也没有系统策略页面。
社区管理页只读写 `review_mode`、`review_ban_words`、`review_prompt`，每次操作仍需检查对应社区权限。系统值由服务端部署/数据库运维修改，不授予社区管理员或普通后台用户查看权限。
保存配置使用通用 CommandPipeline + Receipt；创建或补齐默认配置用同事务内部接口，不启动第二个 Receipt。
初始化系统 article/comment/doc 审核词与 prompt；system 行不设置 `review_mode`。为已有社区按 V2 默认值初始化 article/comment，创建新社区同事务初始化。系统默认审核 prompt 必须有明确版本化模板，不能生成空配置后声称系统检查已启用。
社区默认 `review_mode=immediate`、`review_ban_words=[]`、`review_prompt=""`；空社区规则表示无附加要求，不影响系统 AI 必查。
不读取 V1 publish_mode/edit_mode/background_check 推导新值：旧配置的公开语义和 AI 成本不作为 V2 等价要求。V2 每次发布/修改都执行 AI，不能因旧后台开关关闭而跳过；系统配置和社区自定义规则按新合同明确设置。

提交时由 CMS 在自己的可靠检查记录中固定完整配置值及 version，两层分别保存。系统层快照只在 CMS/ReviewBot/AI 的服务端链路中传递，绝不返回给浏览器。运行途中更改配置不改变已排队任务输入；管理员明确重查才读取最新配置。
先读取配置可获得该次一致快照；若产品要求配置提交瞬间生效，则 R0 改为事务内锁/校验版本，不能隐式混用两个版本。
不再建立独立 RuleSet 业务模型；当前任务快照保存在领域执行记录，配置修改历史可复用既有操作记录。
provider/model 由 AI 运维配置管理，不开放社区自填 endpoint、凭据或模型参数。旧 rule_sets.provider_profile、required_modalities 不转换为新字段。
AI 基础配置必须指定一个明确的审核用途 profile，供系统和社区检查使用；不按社区、旧 RuleSet 或未声明的 provider 顺序选择。若配置了多个 profile 但没有明确选择，返回配置错误。
检查所需模态从实际输入推导：非空标题/正文需要 text，存在图片需要 image；混合内容两者都要。CMS 固定完整图片清单，AI 不依靠旧 required_modalities 或客户端声明忽略图片。
所选 profile 缺失、凭据不可用或缺少所需模态能力时，不调用低能力 provider 假装通过；执行前返回配置/能力错误，执行后 coverage 不完整返回 uncertain 或协议错误，按 P3 处理。
启用 V2 的前置条件是系统策略、明确选定的 AI profile 和声明的 text/image 能力校验通过；没有后台检查开关可跳过系统审核。

## 6. ReviewBot 与 AI 的输入输出

### 6.1 检查合同

```elixir
ReviewBot.check(content, policies)
# {:ok, %{system: layer_result, community: layer_result}} | {:error, invalid_input}
# layer_result = {:ok, opinion} | {:error, error}；Doc 的 community 为 nil

ReviewBot.check(content, policy)
# 单层输入：{:ok, opinion} | {:error, error}；以不同 typed input 区分，不依靠自由 map 猜测

AI.check(input, profile)
# {:ok, normalized_output} | {:error, error}
```

`content`：规范化 title/plain_text、所需图片的不可变引用及短时授权读取信息。
`policies`：由调用方通过配置接口得到并固定的系统/社区策略值，仅带 ban_words、prompt、配置 id/version 和本层标识。
ReviewBot 不接收 actor、revision_id、content_token、review_epoch、Case、Lifecycle 或可执行动作。
底层请求 ID 属于 AI 关联诊断；领域检查 ID 在调用方包装结果，不让 AI 选择它要更新的资源。

每层 `opinion`：

| 字段        | 固定含义                                                                                                                      |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `status`    | `clear` / `suspect` / `uncertain`；仅成功响应中使用                                                                           |
| `sus_notes` | 数组，每项 `{type, evidence, explanation}`；type 为受控问题分类，evidence 为有限长度引用/图片关联位置，explanation 为判断说明 |
| `coverage`  | 所需 text/image 的 complete/unsupported/failed；不支持的模态不能当通过                                                        |
| `summary`   | 管理员可读的有限长度意见；human_first 的 clear 结果也需保存展示                                                               |

`clear` 必须 sus_notes=[] 且要求的覆盖完整；`suspect` 至少有一条具体嫌疑；`uncertain` 允许没有具体嫌疑。
初始 sus_notes.type 建议固定为 spam/harassment/illegal_content/impersonation/other，独立于用户举报枚举；未知值或额外可执行动作均按协议错误拒绝。最多 20 条，每条 evidence 最多 500 字、explanation 最多 1,000 字、summary 最多 2,000 字；不持久化模型原始推理过程。
协议错误、超时、无凭据、输入过大等返回 tagged error，不伪造成 suspect；可用的单层结果由领域分别保存，避免社区故障丢掉已得到的系统意见。
生产执行可每个 Effect 调用一个层的检查入口，汇总接口复用同一实现；系统和社区不要求同一次模型请求或串行等待。

### 6.2 系统 prompt 与 ban_words

```text
可信审核模板（指令与输出结构）
    + 本层 ban_words（审查线索）
    + 本层 prompt（系统/社区要求）
    + 待审内容（明确标记为数据）
    -> AI.check
    -> 结构、枚举、长度、覆盖校验
    -> 本层意见
```

正文、举报详情、社区 prompt 都不能覆盖系统安全要求或产生业务动作。系统与社区用各自输入独立评估；不把两份规则拼到同一 prompt 后仅返回一个无法归属的结论。
例如“赌博开户链接”与“防范赌博诈骗”都含 ban_words，但须得到不同的上下文判断。
多图片必须逐项证明覆盖，不能只看封面。图片 URL 执行时短时签发，凭据/长期签名不持久化；CMS/Assets 负责授权媒体读取，AI 不加载 CMS 数据。
provider adapter 迁入基础 `ai/` 模块；保留可用 HTTP 解析能力，删掉旧规则 action 到资源限制的映射。
当前 `ReviewBot.Media` 中的 CommentBody 解析、资产查询和签发不能整文件搬进 AI：领域提取/授权回 CMS/Assets，AI 只接收已授权的图片输入及检查所需的基础媒体能力。

## 7. CMS 的可靠执行、版本与可见性

### 7.1 领域检查记录

为避免把旧 ReviewBot Check 原封不动改名搬家，明确最小执行记录由谁使用：

```text
CMS 保存当前提交 -> 固定输入及策略 -> 产生检查 Effect
                                         |
                                         v
                                    ReviewBot.check
                                         |
CMS 应用有效结果 <------------------------+
```

建议 `cms.artiment_reviews` 为本轮领域执行记录（实施方案，不是新增用户业务概念），一条记录对应一个资源、一个 scope 的一次检查。
字段：UUID id；article_id/comment_id/Doc branch 的有效组合；community_id?（本层归属，NULL=系统）；`subject_ref` UUID；固定策略 JSON；短期输入 payload；state；result JSON；applied_at?；outdated_at?；payload_expires_at；UTC 时间。
Article/Comment 目标 CHECK 保证一个有效目标；Doc 是 article_id + branch_id。resource 引用实际 ID 类型。
`subject_ref` 是 CMS 为同一公开内容启动的系统/社区检查共同生成的标识。审核记录不保存 Article revision、Comment body version 或 Doc branch version；每次公开发布或修改会在资源 Command 中淘汰旧检查，旧结果凭 `outdated_at` 判过期。本轮不新增统一的 Article/Comment Draft 或 edit history；未来方向见 §12.3。
同一资源+scope 仅一条 outdated_at=NULL 的当前记录，使用部分唯一索引；创建新记录前使该 scope 的旧记录失效，包含已完成的旧记录。
state 仅为执行状态 queued/running/completed/failed；失效用 outdated_at，应用成功用 applied_at；不能拿技术 state 直接给 Gate 判断公开。
资源锁下先加载本领域 canonical 内容；payload 不得是 worker 执行时重抓的“最新正文”。不可变引用可重建则存引用；Comment 当前正文原地覆盖时，短期输入单独存此表，最长 24 小时，终态/失效清空。该 payload 仅保证本轮审核输入，不构成可供用户查看的历史版本。
Outbox 只存 request_id 等有限元数据，不把正文和完整词库塞进 `cms.outbox_events.data`。
锁/版本保护、当前指针及失效逻辑留在 CMS；ReviewBot 只收到实际内容与策略。

### 7.2 当前版本与失效

```text
CMS 提交 A -> request A -> Effect -> ReviewBot 检查 A
CMS 提交 B -> request A 失效；建立 request B
ReviewBot 返回 A 意见
    -> CMS 发现 request A 已失效
    -> 不修改 B，不新建 A 的 Wall item，不发送 A 的公开通知
```

人工查看、处理也关联 CMS 当前提交。资源变更后分两条路径处理：CMS 结束自己的旧检查资格与旧审批等待，按新提交建立等待；只有实际存在 Wall item 时，才调用 AlertWall.supersede 结束该 item 的当前工作资格。
正常 human_first 审批从未创建 Wall item，其结束和重建不调用 AlertWall。两类历史分别留在 CMS、AlertWall，不互相代存。
V2 中举报事实不因编辑被删除；旧举报仍属于旧 Wall item，内容重新发布后标记 `outdated_at`，新内容的举报创建在新 item 上，不搬动旧举报。
手动重查同一 scope 建立新 request、淘汰该 scope 旧任务，不令其他社区或系统的检查失效。
人工决定使对应 scope 的在途 request 失去应用资格；不额外增加全局 epoch。批准后的迟到 AI 不能反转人工决定。
首次 human_first 的批准入口默认要求两层意见已经完成；检查不可用时若允许人工越过检查，应作为 P3 的显式授权动作并保留说明，不能把未返回意见显示为 clear。

### 7.3 Gate 使用的状态

不以 AlertWall item 是否 open 或 sus_notes 是否为空直接推导公开状态。
CMS 沿用现有 Lifecycle-owned 限制存储的归属与结构作为重构基础，不表示保留或忽略 V1 活动行；旧活动限制/待审目标必须按 §12.1 的零计数门槛处理完毕，才允许替换存储与 Gate。本批不为命名新建第二份公开状态表。
V2 内部 type 表达 awaiting_ai、awaiting_human、ai_suspect、manual_hold 四种情况；不用 V1 的 rule_hit 词命中语义。
使用可空 item_id、CMS `artiment_review_id`、CMS 管理的 subject_ref；source_ref 是受控的审核/人工操作关联，不解释为案件。不保留 case_id/check_id/content_token/cause_key 字段或兼容读取。
资源关联直接使用 article_id/comment_id，Doc 为 article_id+branch_id，建立 FK/唯一约束；Lifecycle 仍拥有写入和锁。不回填旧审核行，目标字段由 V2 写入入口产生；不回填的前置条件是旧活动限制及待审目标为零，不能以此删除仍生效的限制。
结束限制的元数据改为 resolved_at/resolved_by_ref/resolution，三者成组；表示一次等待或限制何时解除，不是 SusNote 的状态。保留既有活动行唯一约束的等价 source_ref 防重复能力。
R0 需输出目标字段、约束及旧存储退役 DDL，不写旧行字段映射，不把讨论中否定的名称继续暴露给产品 API。

活动限制按系统与当前社区分别评估，任一未满足就不公开；一个 scope 的批准不解除其他 scope。
已人工禁止的内容不能靠编辑或 AI clear 自动恢复（P4）；不改变 deleted/destroy/archived 的资源基础语义。
审批待办查询由 CMS 读取等待人工事实，关联 request.result 获取 AI 意见，不需要 AlertWall Case。
公共列表、详情、嵌入回复、计数、搜索、Feed、图片与通知全部消费同一 Gate；作者/审核员特许读取不写公共缓存。

## 8. AlertWall item、举报与处理记录

### 8.1 item 不是自动检查，也不是一条嫌疑

```text
CMS 检查意见 -----+
用户甲举报 -------+-> 同对象、同范围、同公开内容的 item
用户乙举报 -------+           |
                              +-- ai_source_ref + sus_notes + summary
                              +-- user_reports（每条举报直接指向一个 item）
                              +-- actions（处理/过期等墙上操作）
```

多个 sus_notes 不生成多个 item；系统和社区分 scope，权限与处理不互相覆盖。
human_first 且无嫌疑/举报：只有 CMS 发布审批，没有 Wall item。
无问题的通过、AI 请求重试、检查失败不进“违规墙”；真实举报即使尚未证实也可产生 item，但不等于业务处罚。

### 8.2 数据合同（实施建议）

目标 schema `alert_wall`；`items`、`user_reports`、`actions` 归 AlertWall，不导入 V1 Case/Report/Decision。
本轮不设 priority，列表按状态和 opened_at/id 稳定分页；不为旧字段增加 legacy_decision_id、原 Case ID 或旧 signals 转换字段。

| 表             | 记录什么                                                         | 关键字段与约束                                                                                                                                            |
| -------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `items`        | AlertWall 上一个待处理事项；同一公开内容可汇集 AI 意见和多条举报 | `owner`、`target_type`、`target_id`、`community_id`、`subject_ref`、`status`；每对象/范围/公开内容最多一条 open item                                      |
| `user_reports` | 一个人针对当时公开内容提交的一条举报                             | `item_id` 直接指向唯一事项；另存 reporter、举报类型/详情、目标快照、`withdrawn_at`、`outdated_at`、`resolved_at`、`resolution`；不通过关联表搬到其他 item |
| `actions`      | 墙上事项被创建、处理或因内容变化过期的历史                       | `item_id`、`action`、actor/source、幂等 operation_ref、结果；资源批准/封禁仍记在 CMS/Accounts 自己的历史                                                  |

target_id 不强行给不同领域做跨表通用 FK；创建时由 owner 公开入口验证实际目标，销毁时 owner 标记 tombstone。
subject_ref 是 owner 给出的不透明上下文关联，不由 AlertWall 解释 Revision。Accounts 可使用自己的处理关联值，不强制套内容版本。
一个 item 已限定对象、scope、subject_ref，当前 AI 意见来源放在整份意见的 ai_source_ref 上；sus_notes 每条仍只含 {type,evidence,explanation}，不重复加入 source/request_id。
CMS 将自己的 `artiment_reviews.id` 作为 ai_source_ref；其他领域提供自己的稳定检查关联。ai_source_ref 由调用方附加，不能从 AI 输出中接受；AlertWall 不解释内容版本，也不建立指向 CMS 的跨领域 FK。
新有效结果在 item 锁内整体替换 ai_source_ref/sus_notes/summary，三者来自同一次检查；不能按 note 文本去重，也不能只替换 summary。仅举报的 item 可以 ai_source_ref=NULL，但此时 sus_notes 必须为空。
同一 ai_source_ref 重复结果返回原结果；同来源携带不同内容返回冲突，不覆盖既有意见。新旧资格由 owner 在本领域资源锁下校验，并在同事务更新 Wall；Wall 不按 UUID 或到达顺序猜测哪个 request 更新。
更新 AI 意见不覆盖其他 scope 的 item，也不改写举报。clear 意见在 owner 中保存；若需关闭原嫌疑 item，由 owner 明确判断尚有无有效举报并调用 resolve，不单凭空 sus_notes 自动关闭。
add 的 source_ref 必须是稳定 UUID 操作标识，作为 actions.operation_ref 在同事务记录；先查询既有 add 结果再 upsert item。即使原 item 后来已关闭，重放同一 source_ref 仍返回原结果，不能重新开 item。一次领域操作需更新多个 item 时，为每项生成确定、不同的操作标识。
存在真正新来源且同 subject_ref 的 item 已关闭时，创建新的 open item；其新 source_ref 与历史动作分开。新上下文使用新 subject_ref。来源幂等动作需保存稳定请求摘要与既有结果，重复调用先比对，不能在旧 add 重放时把原 ai_source_ref 写回当前 item。
AI 完整 clear 意见保存在 CMS request.result；Wall 仅在 item 详情需要时通过授权领域接口组装，不复制整份内容。

### 8.3 公开能力与处理语义

```elixir
AlertWall.add(item_input, source_ref)
AlertWall.resolve(item_id, resolution, operation_ref)
AlertWall.supersede(item_id, operation_ref)
AlertWall.list(scope, filter, pagi, actor)
AlertWall.get(item_id, actor)
AlertWall.submit_report(target, report_type, details, actor, command_id)
AlertWall.withdraw_report(report_id, actor, command_id)
```

以上为目标名称；内部 add/resolve/supersede 接口接受可信领域调用，需校验 owner/目标/范围/操作来源，不作为可由浏览器任意写入的通用 Mutation。
list/get 在分页前按权限过滤；只返回有权查看的 AI 说明、举报人信息和内容安全摘要。正文、图片通过 owner 正式读取接口获取。
add 幂等 upsert open item；已 resolved 的新独立来源可形成新 item，不重写旧历史。无效 subject_ref 应先由 owner 拒绝。
resolve 表示墙上事项已处理，不自动恢复内容或解除账号限制；仅整理告警的动作与“批准/恢复内容”必须在 UI 分开。
资源处罚成功后才写对应 action/resolve；失败不得出现“内容已恢复”的记录。仅关闭 Wall item 的操作则明确不产生资源变更。
supersede 表示原上下文不再是当前工作项。人工页面用 expected item version 防覆盖；资源 Command 再校验本领域当前内容。
撤回举报只更新该 `user_reports.withdrawn_at`。资源内容更新会把旧 item 上尚未过期的举报标成 `outdated_at`；Wall 处理完成会写 `resolved_at` 和 `resolution`。`outdated_at` 与 `resolved_at` 是两个独立事实：前者说明举报针对旧内容，后者说明这条举报已处理。新举报必须关联新公开内容对应的 item。
账号举报只显示受理、驳回、记录处理；不暴露未实现封号动作。
Wall actions 仅记录墙上 add/resolve/supersede 操作；批准、禁止、恢复内容的动作及依据归 CMS，账号动作归 Accounts，重查归领域 request/Effect。领域成功处理时可以同事务生成对应 Wall action，但不能把领域动作直接塞进 Wall action 枚举。

### 8.4 举报历史在产品中的呈现

```text
文章 42 初次公开 -> item I1 -> 举报 R1
文章 42 编辑后重新公开 -> item I2 -> 新举报 R2

I2 / R2 作为当前内容显示在上方
---------------- 编辑前 ----------------
I1 / R1 折叠显示，标记 outdated
```

每条 `user_reports` 只指向提交时对应的一个 `items.id`。内容编辑不会把旧举报复制或搬到新 item；旧 item 与举报保留，UI 折叠旧内容并显示 `outdated` 标签。该举报后来被管理员或自动流程处理时，再独立记录 `resolved_at`/`resolution`，UI 可显示已解决标签。
提交举报时，在同一个资源 Command 中创建/获取当前 item 并插入 user_report。唯一约束按 reporter、目标、scope 和 subject_ref 限制当前内容上的重复举报；`outdated_at` 或 `resolved_at` 后，用户可以对新公开内容再次举报。
管理员无需在编辑后手动重新关联旧举报。打开历史记录时查看的仍是原举报和原提交内容；Article/Comment 通用 edit history 尚未实现，未来可按 §12.3 展示 diff。

## 9. Command、Receipt、Effect 与原子性

### 9.1 外部用户命令与内部执行

| 操作                         | 顶层入口                 | 执行机制                                                                |
| ---------------------------- | ------------------------ | ----------------------------------------------------------------------- |
| 发布/编辑/批准/禁止/恢复内容 | CMS 对应资源 Command     | 既有 receipt_pipeline + CMS adapter，canonical load/lock/Gate           |
| 更新审核配置                 | ReviewBot 配置 Command   | 通用 receipt_pipeline；适配配置权限与既有 Receipt 能力，不复制执行引擎  |
| 举报/撤回/仅整理 Wall item   | AlertWall Command        | 通用 receipt_pipeline + Wall adapter；保留既有举报幂等                  |
| 调用 AI                      | 领域 Effect worker       | 短事务领取/加载 request，事务外调用 ReviewBot/AI                        |
| 应用 AI 结果/最终失败        | CMS 对应资源内部 Command | direct_pipeline + 明确内部执行身份；artiment_review_id 幂等，不伪造用户 |

`CommandPipeline.DefaultAdapter` 当前不支持 receipt_pipeline；`CMS.Command` 当前要求 User；Receipt.Runner 还依赖 CMS 的 IntentCodec/Confirmation/ErrorCat。因此不能只换 use 名称就声称复用成功。
R1 的基础接线采用以下实施方案（不是增加一套 Receipt）：

1. 保留 `CMS.Command.Receipt` 作为 CMS 命令回执 owner；通用 `CommandPipeline` 只负责 Pipeline 编排并通过 CMS adapter 调用，不让通用执行器反向依赖 CMS 表/错误，也不复制 Receipt 算法或新增回执表。
2. 通用输入为 initiator_type/key、command_id、带 namespace 的 operation、领域已规范化 target/params、Confirmation codec 和事务 callback。CMS 的目标解析与意图编码仍由 CMS adapter 提供；ReviewBot/AlertWall adapter 各自提供自己命令的规范化值和错误映射。
3. 保持既有 user initiator_type/key、唯一索引、intent 比较、Confirmation payload、超时和过期语义。`cms.command_receipts`、Key/Runner/Store 继续由 CMS 命令回执拥有；CMS 对外入口和现有业务 Commands 维持原机制。
4. ReviewBot/AlertWall 的用户 Command 通过各自 adapter 调用 CMS 暴露的 Receipt 能力；Gate 阶段调用各自的权限接口。内部 AI 结果路径继续 direct_pipeline，使用 worker 可信入口，不能让 GraphQL 传一个字符串假装系统身份。
5. 共享基础抽离用新创建的 CMS、ReviewBot、AlertWall 命令验证重放/冲突/恢复，再接业务入口。不要求 V2 重放 V1 已存在的审核 Receipt，不增加历史 payload 解码器；业务幂等、失败重试和结果恢复能力本身不能削弱。

一个外部业务意图只有一个顶层 Receipt；跨 Context join-only 持久化不再领取第二张 Receipt。

### 9.2 跨 Context 同库事务

通用 Runner 拥有顶层事务；领域 Command 的 change 中通过其他 Context 的 join-only 公开接口写配置/Wall 事实。
join-only 要求已在事务内，不自行启动 Receipt/顶层 Pipeline；对外 Command 调用内部同一个业务函数，不复制持久化逻辑。
资源变化、Wall item/action、领域 Activity、传播 Outbox 在同一数据库事务提交。未来异库后才考虑独立领域事件，不在本次假装具备跨库原子性。
锁序统一：父 Article（评论需要时）-> 目标资源/Lifecycle -> CMS artiment_review -> CMS blocks（ID 升序）-> Wall items（ID 升序）-> user_reports/actions。
Wall item 预读仅解析 owner/target；需要变更资源的路径不能先锁 item 再调用 CMS。举报/撤回也要遵守相同顺序或改用确定无循环的单对象事务。
submit_report、withdraw_report 都涉及相同目标：先由 owner 的目标锁串行化提交/撤回，再按 item 后 report 的固定顺序写入。每条举报只有一个 item_id，不存在跨 item 的关联写入。

### 9.3 可靠执行

CMS 提交事务：内容+request+等待事实+Effect 一起提交，入队失败则回滚。
worker 从 request 固定输入重建检查，不临时读取新内容代替旧任务；外部 HTTP 不在数据库锁内。
成功/失败返回后短事务重锁 canonical resource、request；检查未失效、目标未销毁、未被更新人工决定取代；已 applied 则恢复既有结果。
同一 request 多次 AI 调用只允许一次业务结果落地；外部调用可能重复，不承诺 exactly-once 模型请求。
重试复用既有 Outbox lease/attempt/recovery 机制；沿用最大 3 次、HTTP 30 秒、worker 45 秒的基线预算，adapter 不叠加重试；预算调整单独记配置。
孤儿执行与 24 小时过期输入由恢复任务调用同一 CMS 最终失败入口，不能只标技术失败留下永久等待。
Receipt 负责业务请求重放；AI 请求耗时/错误由基础诊断记录，不新建一套 AIRequest 业务 Receipt。

## 10. 发布、修改、人工处理的完整例子

### 10.1 首发 human_first，两层检查无嫌疑

```text
作者发布帖子 P
  -> CMS 发布 Command / Receipt
  -> 保存本次内容 + 读取并固定两层策略
  -> CMS 写等待人工事实 + AI 检查 Effect
  -> 提交
  -> Effect 分别调用 ReviewBot -> AI.check
  -> CMS 应用并保存系统/社区 clear 意见
  -> CMS 待审页显示内容 + 两层意见（不建 Wall item）
  -> 管理员调用 CMS 批准 Command
  -> Gate 权限 + 当前提交校验
  -> 解除对应人工等待 + 公开 Effect
  -> 普通读者可见
```

### 10.2 human_first 帖子修正 typo

```text
作者提交修改 B
  -> CMS 判断为 edit：非 immediate 改走 AI 通过后生效
  -> 新 request；旧提交的检查/审批由 CMS 失效
  -> 系统和社区 AI clear
  -> CMS 结束当前 AI 等待；没有其他人工禁止则公开
  -> 不要求管理员因 typo 再批准一次
```

修改检查期间是否保留旧版公开按 P2；不能把 Revision 当作已经确认的双版本产品能力。

### 10.3 immediate 评论发现广告嫌疑

```text
作者发评论 C -> CMS 保存并立即显示 + Effect
  -> ReviewBot 返回社区 sus_notes：疑似广告导流
  -> CMS 接受有效结果
  -> 按 P1 转人工并限制相应范围
  -> AlertWall.add（社区 item）
  -> 管理员在墙上看到嫌疑及依据
       +-- 排除嫌疑 -> CMS 批准/恢复 -> Wall.resolve
       +-- 确认禁止 -> CMS 写人工决定 -> Wall.resolve（记录已处理）
```

Wall resolved 后内容可能仍被禁止，二者含义不同。账号处理同理，关闭账号 item 不等于解封。

### 10.4 两层组合与多社区

系统 immediate、社区 human_first：首次需社区人工；修改两层 AI 检查后，系统层无需等待、社区层通过即可自动放行。
系统发现嫌疑、社区 clear：系统问题仍需系统权限处理；社区批准不覆盖。
一篇 Article 绑定 A/B：系统只检查一次，各社区分别检查；A 的嫌疑只影响 A，系统嫌疑影响所有绑定。
编辑重检当前所有 binding 的适用策略；新增 binding 采用目标社区首发模式；移走 binding 由 CMS 结束源 scope 检查/等待并使源 item 失效。
Doc 仍是平台-only、branch 隔离，不从本文推导新的 Doc release 审批；Doc 评论按普通评论三模式。

## 12. 无兼容替换与实施记录

### 12.1 目标初始化与切换原则

V2 不承担 V1 配置、Case、Report、Decision、Check/Attempt 或审核限制的语义转换、ID 保留、历史回填。历史文档只是代码基线，不是新表必须保留字段的理由。
不新增 legacy_decision_id、Case ID 映射、signals/safe_summary 转换，也不要求重现 V1 的模式组合、词匹配结果或调用成本。items.summary/sus_notes 由 V2 新检查或新举报流程写入。
SQL migration 仍使用新增正向迁移，不修改已执行 migration；其职责是目标建表、必要的共享基础调整和旧审核存储退役，不编写兼容转换脚本。

**切换安全态固定采用零计数门槛（方案 3）**：V1 活动审核限制、待审目标及事实不一致均为零，才允许启用 V2 Gate 或退役旧审核存储。事实不一致包括无法由当前权威事实解释的隐藏投影；不能只看 restriction/pending 为零。该门槛独立于 P1–P7，不通过“无需兼容”豁免；不新增只读 legacy blocker，也不把旧目标批量转换为 V2 manual_hold。

```text
R0 只读清单：记录初始限制/待审目标及处理范围
    |
    v
维护窗口：停旧写入口、cron、worker，取消/排空在途任务
    |
    v
同一一致性快照复核旧限制、待审及隐藏投影一致性
    |
    +-- 任一非零 / 统计失败 / 事实不一致
    |     -> 停止切换，不退役旧存储，不启用 V2 Gate
    |     -> 退出切换，由 V1 正式审核入口处理后重新检查
    |
    +-- 全部为零
          -> 保持旧写停用
          -> 目标 DDL / 初始化 / Gate 与代码切换
```

R0 清单必须列明实际表、查询谓词、scope 和去重目标规则，不能只统计“当前页面可见”的内容：

- `active_restriction_count`：V1 Article/Comment/Doc 三类限制表中 ended_at IS NULL 的全部行数，按表、type/scope 细分；对应 V1 列名仍为 kind 时按真实列读取。
- `restricted_target_count`：这些行覆盖的去重目标数；Article/Comment 以各自资源 ID，Doc 以 article_id+branch_id 识别，不能把不同 branch 合并。
- `pending_target_count`：V1 权威等待事实覆盖的去重目标数，包括 awaiting_ai/awaiting_human，及当前有效内容上未完成的正常 human_first 审批；核对实际 Case/提交关联，不把所有 open 举报 Case 都当作发布待审。
- `hidden_projection_count`：实际存在的 ArticlePublic/ArticleBinding/DocPublic.visible=false 行数，按表/目标/社区或 branch 列出。它是诊断数量，不要求所有合法隐藏投影为零；每条必须有核对分类。
- `unexplained_hidden_projection_count`：visible=false 且无活动限制/待审事实，同时无法由当前基础 Lifecycle、branch/publication 或其他明确保留的权威隐藏条件解释的行数。计入 `fact_inconsistency_count`，任一非零即预检失败；不能因它没有 restriction/pending 就忽略。
- 活动行的孤儿关联、缺失/无法解释的等待事实必须单列并使预检失败；不能因目标已隐藏、删除或不在公共列表而从计数排除。
- `fact_inconsistency_count`：异常关联、无法解释的等待、隐藏投影不一致等异常的汇总；子类分别计数并给出目标清单，不靠汇总去重掩盖某类异常。
- 记录统计时间、数据库/部署标识、查询版本、上述计数和受影响目标清单，以及旧生产者、cron、worker 已停止的证据。目标清单只需 ID/范围/状态，不记录正文。

隐藏投影核对必须同时确认 schema 与业务事实，不能假定 V1 已自动保证投影一致：

1. R0 和最终预检通过实际数据库元数据确认三张表及 visible 列是否存在，记录 migration 版本、运行代码版本和查询适用性。当前源码的 ArticlePublic/ArticleBinding 不声明 visible，`20261023120000_remove_article_visibility_projection_flags.exs` 删除这两列；DocPublic 仍有 visible。此源码事实不证明目标库已执行对应 DDL。
2. 列确实已按已核实的 schema 合同删除时，标注该表检查为 N/A（列已删除及其证据），不执行引用不存在列的 SQL，也不把 N/A 伪装成“查到零行”。按合同本应存在的列缺失、schema 版本未知或查询失败，均作为预检失败，不能静默跳过。
3. 对仍存在的 visible=false，使用同一快照核对当前关联事实。ArticleBinding 必须保留其 community 范围，DocPublic 必须保留 article_id+branch_id；不拿其他 scope 的限制解释本范围隐藏。若待执行切换包含删除 visible 的 DDL，必须在删列前完成此检查，不能先删列再用 N/A 绕过。
4. Article、ArticleBinding、Doc 的合法基础隐藏不等于审核异常：Article/Doc 基础 Lifecycle 不允许公开，或 Binding 对应社区的权威状态禁止公开时，visible=false 可以由该事实解释，但需证明 V2 同样保留这一隐藏条件。ArticleBinding 的解释必须限定在对应 community，不能推成整个 Article 全局隐藏。比较前后 Gate 时固定同一读者身份和 scope，不能用作者特许读取或其他社区的结果作证。缺失父事实、错误 branch/社区关联、投影与 Lifecycle 不符或无法解释的隐藏均失败，不可用“也许是已处理”排除。
5. 已 ended 的限制、已完成审批不能作为当前隐藏的有效依据。只有这些历史记录且仍 visible=false、当前其他事实均允许公开时，必须计入 unexplained_hidden_projection_count。反之，ended/processed 且投影已与当前事实一致的正常目标不误计为活动限制、pending 或异常。

隐藏投影核对是只读的异常检测，不是 V1 数据转换；发现异常时中止切换，通过所属领域正式入口查明和处理后重检，不自动把 visible 改 true、不重算后覆盖旧值，也不凭空生成 V2 hold。投影已在此前合法部署中删除的环境，本次证据仅覆盖当前切换基线，不反推或伪造已丢失的历史列值。

R0 初始计数非零不阻止独立开发批次，但必须暴露切换阻塞项；R7 的最终预检要求 active_restriction_count=0、restricted_target_count=0、pending_target_count=0、unexplained_hidden_projection_count=0、fact_inconsistency_count=0，且所有适用检查成功，N/A 均有实际 schema 证据。
最终预检发生在停旧写/worker之后、破坏性 DDL和新 Gate 启用之前；之后保持写入冻结，不能把开发时或 R0 的零计数当作切换凭证。旧任务或写入口一旦恢复，凭证失效，必须重新预检。
非零目标仅通过 V1 正式审核/撤回发布等业务入口处理，保留其原有授权和状态规则；禁止为了过门槛直接删限制、批量填 ended_at、清 pending 或把业务结果伪装为“已处理”。无法完成则不切换；若以后要采用 legacy blocker 或批量 hold，必须先另行修改本合同。
**验收不变量：任何旧活动限制、待审目标或无限制但无法解释的隐藏投影，都不得仅因 V2 切换变成可公开。** 本方案通过拒绝带有这些目标或事实不一致的切换满足该不变量；合法基础隐藏也必须继续由 V2 Gate 保持，而不是依赖事后重查补救。

R0 只读列出受影响的表、FK、队列和消费者，确定替换范围；不以“无需兼容”推导清空整个数据库。实施时限定到已列明的旧审核存储和依赖，不触碰无关内容、账号或操作历史。
维护窗口停旧写与旧 worker、最终零计数预检通过后，完成目标建表、初始化、部署和生成物切换，不执行旧新数据差量同步。数据库 snapshot/恢复属于切换保障，不构成 V2 历史数据兼容入口。
失败回退：未开放 V2 写入前可恢复整套切换快照；开放写入后需先停写并选择整套恢复或前向修复，不能只回滚代码去读取旧表。

### 12.3 延后：Article 与 Comment 的 Draft 和公开 edit history

本节记录后续方向，**不属于本轮 V2 实施范围**：不新增表、不修改 Article/Comment 写入流程，也不提供 diff API 或界面。

Article 与 Comment 后续应共用 CMS 的公开内容编辑历史机制。Draft 与 edit history 是两件事：Draft 是作者正在修改、尚未提交公开的工作内容；edit history 只记录一次内容被接受并成为公开内容后的变化。保存或反复修改 Draft 不产生公开历史记录。Comment 后续需要与 Article 一致的 Draft 提交流程；不能把当前 `CommentBody.version` 递增当作 Draft 或历史快照。现有 Article Draft 保持其 CMS 流程，本节不要求为 ReviewBot/AlertWall 重构改造它。

```text
当前公开内容
    |
    v
作者编辑 -> CMS 保存 Draft -> 按 review_mode 检查/审批
                                      |
                                      v
                         CMS 接受后发布新公开内容
                                      |
                                      +--> edit history 保存前后公开内容
                                      +--> 新举报/审核记录关联这次公开内容
```

edit history 属于 CMS，至少要能识别 Article/Comment 目标、保存编辑前和编辑后的公开正文，并记录编辑者与公开时间；首发没有“编辑前”正文。diff 可基于这两份快照按需计算，不要求预存 diff 文本。Article 与 Comment 使用同一套业务合同；Docs 继续使用其 branch/release 版本模型，不强行合并进来。

ReviewBot 仍只检查调用方提交的正文并返回意见，不创建 Draft、revision 或 edit history。CMS 发布新内容时关联本轮举报/审核记录与对应的公开历史记录；界面可将不对应当前公开内容的旧记录标为 `outdated` 并折叠展示。`outdated` 表示内容已被新公开版本取代，`resolved_at` 表示举报或审核意见已处理，两者可以同时成立。具体表结构、保留期限、Comment Draft 的命令与失败恢复合同，需在实施 edit history 时另行设计；本轮 `subject_ref` / `CommentBody.version` 只服务异步审核的当前提交校验，不替代该设计。
