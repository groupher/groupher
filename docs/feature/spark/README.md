# Spark 概念设计

> 状态：planned

本文记录 Spark 的产品概念与讨论方向，不代表已有实现，也不是数据模型或实施合同。

## 目标

社区的反馈散落在邮件、Slack、Discord 等渠道。一条消息可能包含多个需求，同一个需求也可能被多人反复提及。Spark 帮助社区管理团队发现和评估这些信号，并决定是否将它们用于社区讨论或内部工作。

## 核心概念

**一个 Spark 是一条可以独立评估的反馈信号。** 它可以对应一条消息，也可以对应邮件或对话中的一段话。Spark 保留来源上下文，默认不对外展示。

- 一份来源可以产生零个、一个或多个 Spark；按独立反馈划分，而不是按邮件或消息数量划分。
- 多个相似 Spark 仍然是多个独立对象，可以共同关联一个 Post 或 Ticket。
- Spark 是信号，不是聚合后的需求，也不是自动生成的 Post 或 Ticket。
- Inbox 是管理和评估 Spark 的交互视图，不是 Spark 本身的定义。

例如，一封邮件同时提出“按项目关闭通知”和“导出账单明细”，可以提取两个 Spark，分别指向邮件中相应的片段。之后，另外四位用户也提出通知问题，则这些反馈各自保留为 Spark，团队可以将相关 Spark 一起关联到同一个 Ticket。

## 对象与关系

```text
来源：邮件 / 消息 / 对话
  └─ 0..多个 Spark：各自对应一条独立信号和来源片段
        └─ owner 评估、选择
             ├─ 关联已有 Post / Ticket
             └─ 一个或多个 Spark 整理成新的 Post / Ticket
```

Spark 至少应能够表达摘要、原文片段、来源类型与定位、来源时间、处理状态，以及关联的 Post / Ticket。具体字段、状态集合、关联基数与持久化方式留待详细设计。

来源定位应尽可能回到具体消息或原文片段；外部来源未提供稳定片段链接时，保留原文片段和可用的消息或邮件定位信息，并允许回看完整上下文。来源被编辑、删除或权限撤销后的表现需要在实现设计中明确。

Post 适合整理成社区可讨论的内容；Ticket 适合需要内部跟进的工作。关联已有对象和创建新对象都应保留 Spark 来源关系，避免原始反馈在处理后丢失。

## 产品闭环与 Survey

未来 Survey 是与 Spark、Post、Comment 并列的产品能力，用于主动向用户收集反馈。Spark 关注外部渠道中的独立反馈信号；Survey 不依赖 Spark，也不以生成 Spark 为前提。Post、Comment、Spark 和 Survey 等都可以成为 Ticket 的来源，供团队结合上下文评估和跟进。

```text
Post / Comment / Spark / Survey 等反馈来源
                     ↓
               Ticket 跟进
                     ↓
             向用户反馈进展和结果
                     ↓
              持续讨论与收集反馈
```

这是 Groupher 整体产品的目标闭环，不表示 Survey、自动反馈或所有环节之间的联动已经实现。Survey 的问题形式、匿名性、结果和 Ticket 来源关联方式均需单独设计。

## 工作流程

1. **连接和收集**：社区授权来源并选择范围。接收新增内容，或按来源能力定时获取内容。
2. **提取**：AI 建议从来源中提取零个或多个独立 Spark；团队也可以手动选择原文片段创建 Spark。
3. **评估**：在内部视图查看摘要、原文和上下文，判断是否值得跟进。AI 可以建议相关 Spark 或已有 Post / Ticket，建议需要人工确认。
4. **转化或关联**：选择一个或多个 Spark，关联已有对象，或整理成新的 Post / Ticket；也可以暂时保留或忽略。
5. **回溯**：从目标对象查看相关 Spark，并在有权限时回到原始来源。

初期以人工决策为主，不自动把相似 Spark 合并，也不自动公开发布。具体处理状态和是否允许重新打开、解除关联等操作需要进一步设计。

## AI 与隐私

AI 可以协助发现反馈、拆分多个需求、生成摘要、建议关联，以及在转化时整理和脱敏。AI 可能漏掉反馈、拆分不准确、错误匹配或遗漏敏感信息；团队应能查看原文、修正建议并决定最终内容。

Spark 默认不对外展示。转化为公开 Post 时，建议先生成可编辑的脱敏草稿，提示被移除或改写的信息，由 owner 审核后发布；私有来源链接和原文不能因关联自动公开。Ticket 的可见范围也应遵循目标对象的权限，不能因为其与 Spark 关联而扩大来源访问范围。内部具体角色、源数据保存期限和删除规则待确定。

## 来源接入方向

- **Slack**：可通过授权的 Slack App 和 Events API 接收指定范围的新消息；历史回填需要单独设计权限、API 和限流。
- **Discord**：可通过安装 Bot 和 Gateway 接收授权频道的新消息；自动读取正文涉及 Message Content intent 和 Discord 的审核规则。
- **邮件**：一封邮件可能包含多个独立需求；接入方式、授权和原文片段定位待设计。
- **X**：前期可由外部监测工具转发到已接入的渠道；直接使用官方 API 需要评估访问条件和费用。

以上均为接入方向，不表示已经实现。实时事件收集与定时汇总可以并存；收集过程需考虑重复投递、断线或来源不可用，以及扫描范围和失败的可见性。

## 初期范围建议

先验证单个社区、少量授权来源下的完整闭环：收集内容、提取或手动创建 Spark、内部评估、选择多个 Spark 关联或创建 Post / Ticket，并保留来源。优先验证提取质量、噪音、可追溯性和 owner 的处理体验，再决定自动化程度与来源扩展顺序。具体首批来源尚未确定。

## 待讨论

- 内部可见的具体角色与权限，以及不同来源权限如何传递。
- Spark 的处理状态、忽略与恢复，以及与多个目标的关联规则。
- 邮件、线程和长对话的片段定位、来源变更及删除策略。
- 来源授权、数据保留期限、AI 处理范围与脱敏审核体验。
- 首批连接器、回填范围、调度频率和费用控制。
- Survey 作为独立能力及 Ticket 来源的具体设计。
- 与现有 Post / Ticket 写入、权限和生命周期的具体衔接方式。
