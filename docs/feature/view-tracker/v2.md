## 1. 结论

View 已经是独立的高频事件和异步投影模型，当前总数不再适合保存在 Post、Changelog、Doc、Blog 的内容宽表中。
V2 建立由 `CMS.ViewTracker` 独占的窄表 `cms.article_view_summaries`，作为 Article 当前浏览总数的唯一权威：

```text
ViewEvent
  -> ViewTracker.EventProcessor
       -> ViewSummary views/revision
       -> mark ViewEvent projected

Article content query
  -> CDN/public cache
  -> 不再承载 views

ArticleStats query
  -> Phoenix GraphQL
  -> public Article scope + ArticleStats
  -> ArticleStats cache policy
```

V2 的内部 Article identity 统一使用：

```text
{thread, article_id}
```

其中 `article_id` 是各 Article 物理表主键，不是 Community 内公开的 `inner_id`。公开 API 仍使用
`community + thread + inner_id`，由后端在一次 scoped query 中关联 Summary。

## 2. 为什么不能继续把 views 放在 Article 内容中

V1 的投影虽然已经由 ViewTracker 独占写入，但物理字段仍位于 Article 宽表：

```text
ViewTracker.EventProcessor
  -> cms_posts.views / views_revision
  -> cms_docs.views / views_revision
  -> cms_changelogs.views / views_revision
  -> cms_blogs.views / views_revision
```

这产生三个边界问题：

1. 每批有效阅读都会更新包含正文、meta 和内容状态的宽行；
2. `views` 被打包进可 CDN 缓存的 Article 内容响应；
3. 列表与 Drawer 使用不同内容 query/cache key，可能同时显示同一 Article 的不同 `views` 快照。

典型错误状态：

```text
database views                 159
article.posts cache            158
article.detail cache           159

刷新列表后：
article.posts cache            159
article.detail cache           158
```

`trackArticleView.accepted = true` 和浏览 receipt 不能修复这个问题。Receipt 只证明事件已接收并覆盖
`viewer_has_viewed`；窗口内 duplicate 和 event replay 也可以 accepted，receipt 不代表本次一定增加总数，
也不携带投影后的 `views`。

## 3. Ownership 与数据模型

### 3.1 唯一权威

```text
CMS.ViewTracker owns
├─ view_events                       浏览判定事实
├─ article_view_dedupe_states        滑动窗口状态
├─ article_viewer_states             authenticated viewer state
└─ article_view_summaries            当前浏览总数

Article content owns
├─ title / body / digest
├─ lifecycle / stage
├─ author / tags / category
└─ 其他内容语义

Analysis owns
├─ metric_events
└─ article_hourly_metrics            历史趋势
```

Article 物理表不再包含 `views` 或 `views_revision`。Analysis 趋势也不能反向求和成当前总数；当前总数唯一读取
`ViewSummary`。

### 3.2 ViewSummary

建议 schema：

```text
ViewSummary
  id                 bigint primary key
  thread             closed Article thread vocabulary
  article_id         physical Article table primary key
  views              bigint, not null, default 0
  revision           bigint, not null, default 0
  inserted_at        timestamptz
  updated_at         timestamptz
```

约束：

```sql
UNIQUE (thread, article_id)
CHECK (views >= 0)
CHECK (revision >= 0)
```

表只服务 Article，因此字段使用项目业务术语 `thread/article_id`，不使用通用的
`target_type/target_id`。不同物理表可以出现相同 id，由 `thread` 消除歧义：

```text
(post, 42)  !=  (doc, 42)
```

`community_id` 和 `inner_id` 不属于 Summary identity。它们是公开 locator，Article move/mirror 或路由语义
变化时可能需要重新解释；把它们复制进 Summary 会形成第二套 Article locator。公开读取通过 scoped Article
关联 Summary。

### 3.3 零行语义

Summary 使用 lazy creation：

```text
Article 尚无 counted view
  -> 不存在 Summary row
  -> public query 返回 views=0, revision=0

第一次 counted view 投影
  -> INSERT Summary
```

不要求 Article 发布时预建空行。

### 3.4 ViewTracker 内部命名

ViewTracker 是 Article 专属领域。V2 不考虑兼容旧字段，因此 ViewTracker 自己的表和 typed key 一并收敛：

```text
V1 target_type / target_id
  -> V2 thread / article_id

V1 {article_type, article_id}
  -> V2 {thread, article_id}
```

Analysis 的 `article_type` 是跨领域指标维度，可以保留；ViewTracker 在 append MetricEvent 的边界把 `thread`
映射为 Analysis vocabulary。

## 4. 阅读资格、写入与投影协议

### 4.1 浏览器阅读资格

内容预取、列表滚动和仅完成 Article 内容请求都不算阅读。详情页、Drawer 和 Doc 等可阅读 surface 复用同一套
browser admission 状态机；不能只依赖 `IntersectionObserver` 的首次回调：

```text
Article wrapper intersects viewport
  + document.visibilityState == visible
  + 两个条件连续保持至少 1 秒
  -> track exactly once for the mounted Article identity
```

实现必须同时监听 intersection 与 `visibilitychange`。后台标签页打开时不计数；用户之后切换到该标签页且 Article
仍可见时开始计时。隐藏、离开 viewport、切换 Article 或卸载都会取消并重置尚未满足的 1 秒计时器。满足条件并
开始 tracking 后，同一 mounted Article identity 不重复触发；请求重试继续复用同一个 `event_id`。

`IntersectionObserver` 不可用时也不能绕过前台条件；fallback 仅在页面可见且 wrapper 已挂载时开始同样的最小
停留计时。这里的 1 秒是 ViewTracker 的产品语义常量，不是各 surface 可自行覆盖的 UI 参数。Agent、crawler
或其他非浏览器 producer 通过显式 tracking 边界进入，不伪造浏览器 visibility。

### 4.2 正常投影

[`RequestActor`](../../architecture/request-actor.md) classification、Identity、Policy、event id、滑动去重和
MetricEvent append 沿用 V1。只有 counted event 进入当前总数投影：

```text
trackArticleView
  -> insert/resolve ViewEvent
  -> dedupe decision
  -> counted=true
       -> append Analysis MetricEvent
       -> enqueue ViewProjection

ViewProjection
  -> transaction
       resolve {thread, article_id} from the job event
       lock canonical Article row
       lock pending counted events for {thread, article_id}
       aggregate batch_count
       UPSERT ViewSummary
       mark the same ViewEvents projected
  -> commit
```

UPSERT 语义：

```sql
INSERT INTO cms.article_view_summaries
  (thread, article_id, views, revision, inserted_at, updated_at)
VALUES
  (:thread, :article_id, :batch_count, 1, :now, :now)
ON CONFLICT (thread, article_id)
DO UPDATE SET
  views = article_view_summaries.views + EXCLUDED.views,
  revision = article_view_summaries.revision + 1,
  updated_at = EXCLUDED.updated_at;
```

Summary UPSERT 与 `projected_at` 标记必须处于同一数据库事务。事务失败时两者一起回滚；worker 重试重新锁定
pending events，不得重复增加总数。

`revision` 表示成功提交的当前总数投影版本，不等于 views，也不按 event 数递增。一次批处理无论合并多少事件，
只增加一次 revision。

Projector 不再更新任何 Article 内容字段。`article_viewer_states` 仍在同一 projection transaction 中按 V1
协议合并 authenticated human viewer；它与当前总数是两个独立投影。

counted ViewEvent 使用独立的 closed projection state，不再用 `projected_at IS NULL/NOT NULL` 单独表达完整
生命周期：

```text
ViewEvent (counted=true)
├─ pending           尚未投影
├─ applied           已累加进 ViewSummary
├─ article_deleted   Article 已永久删除，不再投影
├─ dead_letter       自动重试耗尽，等待 operations 处理
└─ dropped           operations 确认永久放弃，允许 retention 删除
```

`applied` 与 `article_deleted` 都是自动产生的 terminal projection outcome。`article_deleted` 表示 Article
已永久删除、当前总数无需再投影；它不是可重试失败，不能计入 `projection_failures`。具体字段使用 ViewTracker
自己的 closed enum，不复用业务 `decision_reason`。

### 4.3 重试耗尽与 dead letter

Oban 的有限重试不能让 counted ViewEvent 永久停留在普通 pending，也不能在最后一次失败后把事件伪装成
`projected_at` 已成功并交给普通 retention 删除。投影状态至少区分：

```text
pending
├─ applied
├─ article_deleted
└─ dead_letter
```

worker 使用当前 Job 的 `attempt/max_attempts` 判断最后一次尝试：

```text
load current ViewEvent projection state
  -> applied / article_deleted / dropped
       -> :ok
  -> job generation != current projection_generation
       -> :ok
  -> current generation + pending
       -> execute projection

attempt < max_attempts
  -> record failure metadata
  -> return retryable error

attempt == max_attempts
  -> mark ViewEvent dead_letter
  -> preserve counted fact and failure reason
  -> emit alert / metric
  -> stop automatic retry
```

已终态或代次过期的 worker 是幂等 no-op 成功，不是 projection failure。典型场景是数据库事务已经提交
`applied`，但 worker 在 Oban 记录 completed 前退出；重试发现 conditional update 影响 0 行时，必须重新读取当前
projection state 和 generation。若状态已经是 `applied/article_deleted/dropped`，或 Job generation 已不再是当前
代次，立即返回 `:ok`。只有“同一当前代次仍为 `pending`，且投影确实失败”才能增加 retry count、返回错误或最终
进入 `dead_letter`。

上述 worker 分支只覆盖正常返回 `{:error, reason}` 的失败，不能作为唯一保障。异常型失败必须有两层兜底：

```text
worker 内可捕获的 raise / throw / exit
  -> try/rescue/catch
  -> record failure
  -> 最后一次尝试时 mark dead_letter

worker 未能执行收尾，Oban 最终将 Job 标记 discarded/cancelled
  -> bounded DeadLetterReconciler 检查 terminal Oban Job + pending ViewEvent
  -> conditionally mark dead_letter
```

实现若使用当前 Oban 版本可靠的 discarded callback，可以用它缩短收敛时间，但不能只依赖 worker 自身的
`rescue`：进程 kill、节点退出或超时可能绕过进程内收尾。`DeadLetterReconciler` 只把已经由 Oban 判定为终态的
失败显式分类，不补计 Summary，因此不是 repair job。

Reconciler 不能用“任意旧 terminal Job + 当前 pending ViewEvent”作为充分条件。每个 counted event 必须记录当前
投影代次，例如 `projection_generation` 与 `current_projection_job_id`；初次 enqueue 和 replay 都在同一数据库
事务内推进代次、写入当前 Job identity 并设置代次启动时间/重试截止时间。worker、discarded callback 与
Reconciler 只能更新 Job identity 和 generation 都匹配的当前代次：

```text
old discarded Job (generation=1)
replay active Job    (generation=2)
current ViewEvent    (pending, generation=2)
  -> generation=1 绝不能把事件重新标成 dead_letter
```

若实现不保存 Job id，而只保存 generation token，Reconciler 还必须证明同一 `event_id + generation` 不存在
`available/scheduled/executing/retryable` Job。状态更新始终带
`projection_state = pending AND projected_at IS NULL AND projection_generation = expected_generation` 条件或等价
行锁，不能覆盖并发成功的 `applied`。

Reconciler 也不能把 Oban terminal Job 行永久存在当成正确性前提。除优先处理仍可关联的 discarded/cancelled Job
外，还必须有与 Job retention 无关的有界兜底：当前代次保持 `pending`、不存在同代活跃 Job，并且已经超过该代次
的 `projection_retry_deadline_at` 时，收敛为 `dead_letter`。截止时间由最大尝试次数、backoff 上界和安全余量计算；
replay 必须重置代次启动时间与截止时间，不能直接使用原始 `occurred_at`，否则很久以前的事件会在 replay 后被
立即误判超时。该兜底同样只分类失败，不补计 Summary。

`dead_letter` 不计入普通 pending age，也不能进入常规 ViewEvent retention。它必须通过显式的 operations
`replay` 或 `resolve_as_dropped` 命令收口：replay 重新进入幂等投影；只有人工确认永久放弃后才标记 dropped 并允许
retention 删除。V2 不建立定时 repair job，但异步投影必须保留可审计的 dead-letter 与显式恢复能力。

两个 operations 命令都使用 compare-and-set，只允许从 `dead_letter` 出发：

```text
replay
  UPDATE ...
  SET projection_state = pending,
      projection_generation = projection_generation + 1,
      current_projection_job_id = new_job_id,
      projection_retry_deadline_at = new_deadline
  WHERE event_id = :event_id
    AND projection_state = dead_letter

resolve_as_dropped
  UPDATE ...
  SET projection_state = dropped, ...
  WHERE event_id = :event_id
    AND projection_state = dead_letter
```

replay 的状态迁移、generation 推进和新 Job enqueue 必须在同一数据库事务中提交。条件更新影响 0 行时，命令不得
改写当前状态：重复调用可以返回 already-resolved，状态不符合则 fail closed。并发 replay/drop 只有一个命令能从
`dead_letter` 抢占成功；因此已 replay 的 `pending/applied` 不能随后被旧 drop 请求覆盖，也不能推进两个新代次。

ViewProjection 的 Oban unique identity 必须同时包含 `event_id` 和 `projection_generation`。不能只按 `event_id` 去重：
旧代次的 discarded Job 在 Oban retention 窗口内仍可能存在，replay 的新代次必须能够成功 enqueue。初次 enqueue 与
replay 都使用当前 generation；同一 `event_id + generation` 的重复 enqueue 才允许由 Oban unique 合并。

`dead_letter` 必须存在：它把“自动重试已经耗尽但事实仍可恢复”与普通 pending 分开，并阻止故障被 retention
静默删除。`dropped` 也必须存在，但只能由 operations 显式决策产生；没有它，系统只能永久保留已确认无法恢复的
dead letter，或错误地把“主动接受丢计数”伪装成成功投影。

`article_deleted`、成功 replay 后的 `applied` 和人工确认的 `dropped` 都是 terminal outcome；`dropped` 必须单独
计数和告警，不能混入成功 projected 指标。

`counted=false` 的 `duplicate_in_window` / `excluded_by_policy` 事件没有投影增量，因此写入时直接落到
`projection_state=applied` 且设置 `projected_at`。这里的 `applied` 只表示“该事件的 terminal 处理已经完成”，不表示它
增加了 Summary；任何投影成功、失败或 drift 指标都必须同时限定 `counted=true`，不能把 uncounted 事件当成成功浏览。

V2 对 counted ViewEvent 的 retention 谓词为：只有 `applied`、`article_deleted` 或 `dropped` 且超过 retention
边界的事件可以删除；`pending` 和 `dead_letter` 不可删除。V1 中仅依赖
`projected_at IS NOT NULL AND occurred_at < retention_boundary` 的谓词不再适用于 counted ViewEvent。
uncounted ViewEvent 的既有 terminal retention 语义不变。

## 5. 批量读取边界

### 5.1 GraphQL 合同

产品页面不会在一次请求中混合 Post、Changelog、Doc 或 Blog，因此 API 明确接收一个 Community、一个
thread 和一批 inner ids：

```graphql
query ArticleStats($community: String!, $thread: Thread!, $innerIds: [ID!]!) {
  articleStats(community: $community, thread: $thread, innerIds: $innerIds) {
    community
    thread
    innerId
    views
    viewsRevision
    upvotesCount
    commentsCount
    snapshotAt
  }
}
```

这里的 GraphQL SDL `Thread!` 复用现有 Absinthe `:thread` enum，不新增第二套 ViewTracker thread enum。

输入要求：

```text
inner_ids
├─ 去重后再执行
├─ 保持调用方可关联的 inner_id
├─ hard limit: 100
└─ 空列表直接返回 []
```

不存在、不可公开读取或不通过 Gate/Lifecycle 的 Article 不返回。存在但没有 Summary row 的 Article 返回
`views=0, revision=0`，不能把“不可读取”和“尚无浏览”混成同一种结果。

### 5.2 一次 scoped SQL

Resolver 先解析 Community，再通过对应 thread 的 public Gate scope 执行一个 indexed `LEFT JOIN`：

```sql
SELECT
  article.inner_id,
  COALESCE(summary.views, 0) AS views,
  COALESCE(summary.revision, 0) AS revision
FROM public_article_scope(:community, :thread) AS article
LEFT JOIN cms.article_view_summaries AS summary
  ON summary.thread = :thread
 AND summary.article_id = article.id
WHERE article.inner_id = ANY(:inner_ids);
```

`public_article_scope` 表示复用 Article Reader / Gate 已有的 Community locator 与 Lifecycle 语义，不是要求实现
一个同名 SQL function。它必须包含 canonical ownership、mirror relation 和当前 Community admission；上面的
SQL 只表达 scope 输出 Article row 后如何关联 Summary，不能照抄为裸
`article.community_id = :community_id`。`(community_id, inner_id)` 索引服务 canonical locator，mirror 路径继续
使用既有 relation 索引和 Reader 语义。

这是一次数据库 query，不是应用层先查 N 篇 Article、再逐篇读取 Summary。它同时完成：

```text
Article Gate/Lifecycle admission
  + public locator resolution
  + Summary batch read
```

必须新建并验证以下索引；现有 `(original_community_raw, inner_id)` 不能替代 public scope 使用的
`community_id` locator：

```text
cms_posts             (community_id, inner_id)
cms_blogs             (community_id, inner_id)
cms_changelogs        (community_id, inner_id)
cms_docs              (community_id, inner_id)
ViewSummary           UNIQUE(thread, article_id)
```

一页 20 篇 Article 的查询只能随输入行数线性返回，不能随全表大小扫描。实施前后使用生产代表性数据执行
`EXPLAIN (ANALYZE, BUFFERS)`；预期计划为 Article locator index + Summary unique index lookup。小型测试表因成本
估算选择 Seq Scan 不单独视为失败，验收以代表性数据的读取行数、buffers 和耗时为准。

### 5.3 内部 canonical Article 入口

已经持有 canonical Article struct 的调用方不应重新走公开 locator：

```text
CMS.ViewTracker.summaries(thread, articles)
  -> %{{thread, article_id} => %{views: integer, revision: integer}}
```

`summaries/2` 不是授权入口，也不能直接暴露给 GraphQL。调用方必须先通过自己所属的 Gate/Lifecycle 边界加载
canonical Article，再把这些已授权 struct 交给 ViewTracker。接口验证所有 Article 都属于显式传入的
`thread`；空列表返回空 map，混合 thread 或不匹配时 fail closed，不能在内部静默分组。

合法输入按单一 thread 执行一次：

```sql
WHERE thread = :thread AND article_id = ANY(:article_ids)
```

缺失行填充零值。调用方不得逐篇调用单条 summary。

### 5.4 Management、Trash 与 Export

Dashboard、Trash、审核和 export 不调用 §5.1 的 public GraphQL query，也不新增绕过 Gate 的 ViewTracker
management endpoint。它们沿用各自已有的 owner scope：

```text
Dashboard resolver
  -> Article management scope
  -> canonical draft / illegal / suspended Articles
  -> ViewTracker.summaries(thread, articles)
  -> merge into Dashboard DTO

Trash resolver
  -> Trash/Lifecycle scope
  -> canonical soft-deleted Articles
  -> ViewTracker.summaries(thread, articles)
  -> merge into Trash DTO

Export
  -> export owner scope
  -> canonical authorized Articles
  -> explicitly partition by thread
  -> ViewTracker.summaries(thread, articles)
```

ViewTracker 信任上游传入的 canonical structs，只读取 `{thread, article_id}` 对应 Summary；它不扩大上游已经
授予的访问范围。存在 canonical Article 但缺少 Summary 时注入 `views=0, revision=0`；Article 本身缺失或无权
读取时由上游 loader 处理，ViewTracker 不伪造 DTO。

当前实现的消费路径对应如下：Dashboard 的公开 Post/Changelog 列表先读取 Article 内容，再由前端按当前页一次调用
`articleStats` 批量填充本地 ArticleStats entity；Trash 与 AbuseReports 已在后端 canonical DTO assembly
阶段调用 `ViewTracker.summaries/2` 并注入嵌套 `ArticleStats`。如果未来 Dashboard 要展示 draft、illegal 或
suspended Article，必须把它接到该 Dashboard 自己的 management scope 后再调用同一内部 API，不能把 public
`articleStats` 改成绕过 Gate 的万能入口。

## 6. 前端缓存与内容边界

### 6.1 内容响应删除 views

Community 的 Post/Changelog/Doc/Blog 列表和详情内容 fragment 删除：

```text
views
viewsRevision
```

SSR 与 CDN 内容响应继续包含标题、摘要、正文、作者和同步业务字段，但不再是当前浏览总数的读取来源。

### 6.2 SSR 首屏与 hydration

> 本节的原始 placeholder 方案已被
> [ArticleStats 与公共页面缓存](../../architecture/article-stats-and-public-cache.md) supersede。
> 当前合同是：公开 SSR 在同一 request-scoped QueryClient 预取 ArticleStats，并将它和 HTML 一起 hydration；
> `snapshotAt` 与统一 10 分钟 freshness 决定客户端是否 refetch。以下旧内容仅保留为 V2 实施历史，不作为当前
> 前端缓存实现依据。

当前公共 SSR 首屏、ArticleStats hydration、HTML/CDN TTL、`snapshotAt` 和计数展示边界统一见
[ArticleStats 与公共页面缓存](../../architecture/article-stats-and-public-cache.md)。
ViewTracker V2 在这里仅保留一个后端要求：内容读取和 tracking admission 分离，Article content response 不得
重新承载 `views/viewsRevision`。

### 6.3 网络批量、本地按实体归一化

> 当前公共实体名称是 `ArticleStats`；`ViewSummary` 只表示后端持久化的 views 来源。列表由
> `usePagedPosts` / `usePagedChangelogs` 消费 `articleStatsBatch`，不是把 ArticleStats 写回 Article entity。

列表使用一次 `articleStats` 批量 transport：

```text
articleStats(home, POST, [1..20])
```

批量响应写入按公开 Article ref 归一化的单篇 cache：

```text
article-stats/home/POST/18
article-stats/home/POST/19
article-stats/home/POST/20
```

Drawer 读取同一个 `article-stats/home/POST/20`，不能建立另一份只属于详情页的 `views` 快照。若列表已经加载该
ArticleStats，Drawer 直接复用；需要刷新时更新同一个 entity cache，所有订阅该 Article 的列表卡片和 Drawer
同时重渲染。

不能把数组本身作为唯一缓存权威：

```text
错误：article-stats/[18,19,20]
错误：article-stats/[20]
```

这两组 key 会重新制造列表与 Drawer 的双快照。批量 query 可以有 transport 状态，但当前值必须归一化到
单篇 cache key。

Mirror 共享同一物理 Article row 时，一个后端 Summary 可以对应多个公开 locator cache entry：

```text
ViewSummary(post, article_id=42)
  -> community-a/POST/18
  -> community-b/POST/7
```

这些 locator alias 各自维护 revision guard，但值同源于同一 Summary。当前产品不会在一次请求中混合 Community；
同一 Community 内的列表和 Drawer 必须复用同一 locator key。V2 不向前端暴露物理 `article_id`。

### 6.4 缓存与一致性语义

> 当前 public HTML、ArticleStats freshness、snapshotAt 和 cache-tag 规则以
> [ArticleStats 与公共页面缓存](../../architecture/article-stats-and-public-cache.md) 为准。以下旧的 15 秒
> Summary-only cache 描述不再是实施合同。

当前公共 HTML、ArticleStats freshness、`snapshotAt`、cache tag 和高频计数失效规则以
[ArticleStats 与公共页面缓存](../../architecture/article-stats-and-public-cache.md) 为准。这里保留的后端一致性要求是：

```text
相同 Article ref
  -> 只有一个 ArticleStats entity cache
  -> revision 较小的响应不能覆盖 revision 较大的响应
```

View 仍是异步投影，因此 tracking accepted 后允许短暂显示旧总数；V2 保证列表与 Drawer 共享同一个旧值或
同一个新值，不承诺 mutation 返回时总数已经增加。V2 不做本地 `views + 1`：accepted 不等于 counted，窗口内
duplicate 和 event replay 不能产生乐观增量。

tracking receipt accepted 后，客户端必须把对应 ArticleStats entity 标记 stale，并在短延迟后对同一 entity key
触发一次 refetch；不能立即假设 projector 已完成，也不能建立一份 mutation-local Summary。最终 transport 重试
仍失败时，hook 可以保持 analytics 式非阻断体验，但必须发送不包含 Cookie、`event_id` 或 tracking key 的客户端
failure counter，至少区分 timeout、network 和 GraphQL error category。

tracking mutation 不返回 Summary 快照。异步 projector 尚未提交时，该快照仍是旧值，不能代替 stale/refetch
协议，还可能与已经缓存的较高 revision 竞争。

如果为 ArticleStats 增加独立 microcache，缓存的业务 identity 必须是单篇公开 ArticleStats entity，批量请求只负责组装：

```text
错误：cache articleStats([18, 19, 20]) as one authoritative snapshot
正确：cache article-stats:{community}:{thread}:{inner_id}, then batch compose
```

公开 locator 与内部 identity 的映射仍由 scoped Article query 完成。批次参数不同不能制造多份权威快照；任何缓存
响应写入前端时仍经过 `snapshotAt`/revision guard。具体 TTL 和最坏可见延迟以 ArticleStats 文档为准。

浏览 receipt 继续只覆盖 `viewer_has_viewed`，不进入 ViewSummary 当前总数计算。

现有 `frontend/core/query/revisionGuard.ts` 中 Article 级
`copyIfOlder(..., 'viewsRevision', ['views'])` 必须删除。新的 revision guard 只属于 ArticleStats entity cache；
Article content structural sharing 不再识别或保留 views 字段。

`articleViewSummaries`、`article_view_summary` 和 `view-summary/*` 是被直接替换的旧公共合同；实施完成后不得保留
alias、fallback、双读或旧 generated operation。`CMS.ViewTracker.Model.ViewSummary` 仅是后端持久化 views owner，
不是前端公共查询或 cache identity。

## 7. 排序与已知消费方

移除 Article `views` 字段会影响所有直接读取或排序该字段的消费方。V2 实施至少覆盖：

```text
Community
├─ Post list card
├─ Changelog list
├─ Doc detail
└─ Article Drawer/detail base stats

Dashboard
├─ CMS Post/Changelog tables
├─ Trash Article display
└─ 其他 Article 当前 views 列

Backend
├─ public Article GraphQL fragments
├─ CMS Article DTO/export
├─ AbuseReports Article projection
├─ QueryBuilder :views / most_views / least_views
├─ frontend/core/query/revisionGuard.ts 的旧 views merge
└─ tests, seeds and fixtures
```

Community 总访问、Account profile views、Umami pageviews 和 Analysis trend 中同名字段不是 Article 当前 views，
不迁移到本表。

`most_views/least_views` 不再对 Article 宽表直接 `ORDER BY views`，必须通过 ViewSummary join，并用
`COALESCE(summary.views, 0)` 保留零行语义。不得因为排序方便而恢复 Article 双写。

join 与排序表达式由 `CMS.ViewTracker.Query.order_by_views/3` 统一提供：

```text
CMS.ViewTracker.Query.order_by_views(query, thread, :most_views | :least_views | :views)
```

`CMS.QueryBuilder` 与 `Helper.QueryBuilder` 只识别 `:views/:most_views/:least_views` 并委托 ViewTracker；不得在
两个 QueryBuilder 中复制 join、alias 或 `COALESCE` 逻辑。模块名不使用 `ViewTracker.Scope`，避免与 Gate
Scope 混淆。

`views` 是高频更新字段，V2 默认不创建 `views` 排序索引。若真实产品查询需要社区内大规模按 views 排序，
必须用代表性数据证明 join + sort 不满足预算后，再单独设计 rank projection 或索引；不能未经测量就在高频列上
增加持续写放大的索引。

## 8. 生命周期、删除与观测

由于 `thread + article_id` 是跨物理 Article 表的多态 identity，数据库不能使用一条普通 FK 同时指向四张表。
Projector 与永久删除必须使用相同锁顺序，关闭“删除提交后 projector 又创建 Summary”的窗口：

```text
ViewProjection
  -> read job ViewEvent identity without changing it
  -> try to lock canonical Article row
  -> missing Article
       -> lock pending ViewEvents for {thread, article_id}
       -> terminal no-op current projection
       -> mark locked ViewEvents projected with deleted-target outcome
  -> existing Article
       -> lock pending ViewEvents
       -> UPSERT Summary / viewer state
       -> mark projected

permanent delete
  -> lock canonical Article row
  -> delete ViewSummary(thread, article_id)
  -> delete viewer state
  -> delete article_view_dedupe_states rows for {thread, article_id}
  -> terminalize pending current projections
  -> delete Article
```

Projector 先获得锁时，delete 等待并在随后删除已提交 Summary；delete 先完成时，Projector 找不到 Article，
不得重新创建 Summary。Analysis MetricEvent 表示历史上已经发生的 counted view，可以按其 retention 保留；
“target deleted”只终止当前总数投影，不篡改历史趋势。

Community 物理回收不能只依赖 Article FK cascade。回收 Job 必须在删除 Article/Community 前，按 thread 和
`article_id` 分批调用 ViewTracker 清理协议：

```text
Community reclamation
  -> resolve canonical Article ids by thread in bounded batches
  -> lock with the same ViewTracker ordering
  -> delete Summary / viewer state / dedupe state
  -> terminalize pending projection as article_deleted
  -> delete Article / Community
```

orphan sampler 只检测回收协议遗漏，不承担正常级联清理。

公开查询始终从 scoped Article `LEFT JOIN`，因此意外孤儿 Summary 不会泄漏已删除 Article；Maintenance 仍增加
只检测不修复的 orphan sampling 和指标，但它不承担正常竞态的修复职责，也不建立永久 repair job。

Summary consistency audit 不能直接比较 lifetime `summary.views` 与仅保留 30 天的 ViewEvent 数量。检测分为：

```text
状态完整性
  counted event 必须属于 pending / applied / article_deleted / dead_letter / dropped

retention 下界
  summary.views >= 当前 retention 内 applied counted events
  只能发现明显少计，不宣称能发现多计

双向精确采样
  checkpoint.base_views
    + checkpoint_at 之后 applied counted events
    = sampled current summary.views
```

需要双向检测时建立 bounded audit checkpoint，checkpoint 与参与比较的事件必须处于同一时间边界。Audit 只输出
drift，不自动改 Summary。不得用 MetricEvent 90 天 retention 或 ViewEvent 30 天 retention 直接重算 lifetime
current total。

当前 `Maintenance.sample_consistency/1` 是 bounded sampler，不扫描全表也不修复数据：它从最近更新的 Summary
取样，按 thread 批量确认 canonical Article 是否存在，并在 ViewEvent retention 窗口内比较
`summary.views` 与 `applied AND counted=true` 事件数的 lower bound。它输出 `sampled_orphan_summaries`、
`summary_consistency_sampled` 和 `summary_drifted`；后者只表示“Summary 明显少于窗口内已应用事件”，不表示能
发现 lifetime 多计，也不触发回写。checkpoint 双向核对仍是后续需要在有真实审计需求时增加的更强检测协议。

Projector 获取 canonical Article lock 时记录 lock wait、transaction hold 和 timeout/failure telemetry。若代表性流量
证明它与编辑/发布形成显著争用，再单独设计 ViewTracker-owned transaction advisory lock；V2 不在无数据时提前
引入第二套锁机制。

至少观测：

```text
summary_rows
summary_zero_or_missing_rate
projection_pending_events
projection_oldest_pending_age
projection_failures
projection_dead_letter_events
projection_dropped_events
sampled_orphan_summaries
summary_consistency_sampled / drifted
projection_article_lock_wait / hold
public_summary_query_count / duration
client_tracking_failed_after_retry
```

匿名 Cookie 在生产应使用 `__Host-groupher-viewer`，同时满足 `Secure`、`Path=/` 且不设置 `Domain`。不支持 Secure
Cookie 的本地 HTTP 环境可以使用明确的 development-only 名称；不得让生产回退到弱约束 Cookie。应用内按
session/user 的限流不能防护无 Cookie 脚本，Edge/IP/WAF 规则及其真实环境验证是发布门槛，不是文档假设。

## 9. 直接切换实施

本版本不考虑历史数据和兼容逻辑，实施时直接到达终态：

1. 新建 `cms.article_view_summaries` 及 `(thread, article_id)` 唯一索引和非负 CHECK；
2. 将 ViewTracker 的内部 identity、表字段和 typed key 从 `target_type/target_id` 收敛为
   `thread/article_id`；直接重建或清空现有 ViewTracker runtime 数据，不迁移旧行；
3. 将 projector 改为同事务 UPSERT Summary + viewer state + mark projected，不再更新 Article；
4. 将浏览器 hook 改为 visible + intersecting + 连续 1 秒的统一状态机，补后台标签切换、快速关闭和 fallback
   测试；
5. 为投影增加 closed state、dead-letter、operations replay/resolve 命令及告警；正常错误、异常退出以及 Oban
   terminal job 都必须收敛，不把 exhausted event 交给普通 retention；
6. 建立 public batch query、canonical Article batch API 与 management DTO assembly；为 `cms_posts`、
   `cms_blogs`、`cms_changelogs`、`cms_docs` 明确新增 `(community_id, inner_id)` 定位索引；
7. 前端增加归一化 ArticleStats cache，列表和 Drawer 使用相同单篇 key；SSR 预取 ArticleStats 并随 HTML hydration；
   使用统一 10 分钟 snapshot freshness；accepted 后 stale + delayed refetch；删除 Article
   `revisionGuard.ts` 中旧 views merge；
8. 从 Article GraphQL fragments、DTO、schema 和物理表删除 `views/views_revision`、`upvotesCount`、`commentsCount`
   及其公共 revision/overlay/fallback；三个公开 count 只通过 ArticleStats 读取；
9. 将 Dashboard、Trash、export、AbuseReports 和其他已知消费方改为在各自 scope 后调用
   `ViewTracker.summaries/2`；将所有 views 排序委托给 `CMS.ViewTracker.Query`；
10. 将 Article permanent delete 与 Community reclamation 接入 Summary、viewer state、dedupe state 与 pending
    projection 的有界清理；删除所有 Article views 旧 writer、旧字段 fallback、双读和兼容测试；
11. 增加 bounded orphan、状态完整性与 retention lower-bound sample；如需 lifetime 双向核对，再建立带时间边界的
    checkpoint drift 协议；同时增加 projector lock 与客户端 tracking failure telemetry；
12. 生产启用 `__Host-` Cookie，并以真实请求验证 Edge/WAF 对无 Cookie tracking 滥用的防护；
13. 不从旧 Article 字段、ViewEvent、MetricEvent 或 Analysis hourly metric 回填当前总数；新 Summary 从零开始；
14. 在 V1 标明 §4 的投影终态/retention、§5 的当前计数以及 §6 的 worker 失败协议由 V2 supersede；除 V2
    明确修订的部分外，V1 其余协议保持有效。

不允许出现以下迁移状态：

```text
Article.views + Summary.views 双写
Summary miss -> fallback Article.views
后台回填旧 views
定时比较并修复两份总数
```

## 10. 验收

### 10.1 数据与并发

- 第一次 counted event 创建 Summary，`views=batch_count`、`revision=1`；
- 已有 Summary 的批量投影原子累加，revision 每个成功 batch 只增加一次；
- duplicate、excluded、replayed event 不增加 Summary；
- 相同 Article 的并发 worker 不重复计数；
- Summary UPSERT 或 viewer-state projection 失败时，ViewEvent 不得标记 projected；
- worker retry 最终只产生一次增量；
- worker 在投影事务已提交但 Oban 尚未标记 completed 时崩溃，重试读取到 terminal state 后以 `:ok` 收敛，不产生
  额外 retry/discarded 噪音；旧 generation worker 同样以 no-op `:ok` 收敛；
- 最后一次自动重试失败后事件进入 dead-letter，不再计入普通 pending、不被常规 retention 删除；显式 replay 成功
  后仍只产生一次增量，显式 dropped 有独立审计与指标；
- `{:error, reason}`、可捕获异常和 worker 未能收尾的 Oban discarded/cancelled 都能将仍为 pending 的事件收敛为
  dead-letter，且兜底不能覆盖并发成功的 applied；
- replay 原子推进 projection generation 并登记新 Job；旧代次的 discarded Job 不能把新代次 pending 重新标成
  dead-letter；
- Oban terminal Job 被 pruning 后，超过当前代次 retry deadline 且不存在同代活跃 Job 的 pending event 仍能收敛
  为 dead-letter；replay 后的 deadline 从新代次重新计算；
- replay 与 resolve-as-dropped 都只允许 `dead_letter` 条件迁移；重复或并发调用最多一个成功，不能出现双 generation
  或 replay 成功后被旧 drop 覆盖；
- 缺失 Summary 返回零，不能插入 read-time 空行；
- Article 永久删除后对应 Summary 被清理，orphan sampler 可检测故意制造的孤儿行；
- Article 永久删除在同一业务操作中清理对应 viewer state 与 dedupe state，不等待 retention；
- Projector 与 permanent delete 并发时不产生删除后孤儿 Summary，missing Article 被视为 terminal current
  projection；
- Community 物理回收按 thread 分批清理 Summary、viewer state、dedupe state 与 pending projection，不依赖 orphan
  sampler 代替正常清理；
- consistency sample 不把 lifetime Summary 与 retention event 直接等值比较；当前 lower-bound sample 只检测不修复，
  如启用 checkpoint 双向核对则必须使用同一时间边界；
- projector 的 Article lock wait、hold 和 timeout 指标可观测；

### 10.2 查询与缓存

- ArticleStats 对 1、20、100 篇同 thread Article 都只发一个 GraphQL batch request；返回每篇完整的
  `views/upvotesCount/commentsCount`，后端 owner reads 有明确固定上限，查询数不随 N 或 count 类型增长；
- ArticleStats 禁止按 Article 或按 count 类型拆分查询；代表性数据的 `EXPLAIN (ANALYZE, BUFFERS)` 和 select-count
  验证 Article locator、ViewSummary 及 count owner 读取使用预期索引；
- public endpoint 不返回 draft、illegal、deleted 或不通过 Community lifecycle 的 Article；
- Dashboard management scope 可以为已授权的 draft、illegal、suspended Article 注入 Summary，Trash scope 可以为
  soft-deleted Article 注入 Summary，二者都不调用 public endpoint；
- management canonical Article 缺失 Summary 时返回零值，未授权或不存在 Article 仍由 owner loader 拒绝；
- 列表批量结果和 Drawer 单篇结果写入同一 entity cache；
- 较低 revision 的迟到响应不能覆盖较高 revision；
- tracking 后即使 projection 尚未完成，列表和 Drawer 也不能同时显示两个不同的本地 ArticleStats 快照；
- 后台标签页打开不触发 tracking；切换到前台并连续可见 1 秒后恰好触发一次；不足 1 秒关闭、隐藏或离开 viewport
  不计数；
- tracking accepted 后只将同一 ArticleStats entity 标记 stale 并延迟 refetch，不本地加一，mutation 不返回旧 Summary
  冒充投影结果；
- 客户端最终重试失败产生无身份信息的 failure telemetry；
- Article content query/fragment 不含当前 `views/viewsRevision/upvotesCount/commentsCount`，预取内容不会触发 ViewTracker
  写入；public HTML 若展示计数，只能通过独立 ArticleStats hydration 进入；
- public SSR 首屏输出 ArticleStats，HTML 与 hydration state 使用同一份 `snapshotAt` 快照；
- SSR hydration 使用真实 ArticleStats，不显示 placeholder；仅 SPA 客户端导航在 ArticleStats pending 时使用固定加载槽位：
  list/card 至少 `4ch`，Drawer/detail 至少 `5ch`，加载完成前后 icon、行高和槽位起点的 bounding rect 保持稳定；
- private/no-store management SSR 如需 seed `ArticleStats`，必须写入同一 entity cache；
- mirror locator alias 分别拒绝较低 revision，同一 Community 的列表与 Drawer 不产生第二份 key；
- mixed-thread `summaries/2` fail closed，export 必须显式按 thread 分组；
- `:views/:most_views/:least_views` 都由 `CMS.ViewTracker.Query` 编译 join/order，两个 QueryBuilder 不保留旧
  `order_by(:views)` 或复制表达式；
- GraphQL 合同复用现有 Absinthe `:thread` / SDL `Thread` enum，不产生 ViewTracker 私有副本。
- 默认 ArticleStats snapshot freshness 为 10 分钟；启用 5–15 秒 entity microcache 时有独立配置、revision guard 和最坏可见延迟
  验收，批量参数组合不成为权威缓存 identity；
- 生产 Cookie 满足 `__Host-` 约束，真实环境验证无 Cookie 请求受到 Edge/IP/WAF 防护。

### 10.3 清理证明

发布前全仓确认：
