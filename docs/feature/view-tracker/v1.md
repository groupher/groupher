# ViewTracker V1：有效阅读追踪

> 状态：V1 主体已实现；生产环境仍需按本文的 Cookie、密钥和观测清单完成部署验收。
>
> [V2](./v2.md) 修订本文 §4 中 counted ViewEvent 的投影终态与 retention 谓词、§5 的当前计数存储与读取，
> 以及 §6 的 worker 投影、失败和重试协议。上述边界以 V2 为准；本文其他协议继续有效。
>
> 本文只设计 ViewTracker。跨 View、Upvote、Collect、Comment 等指标的趋势由独立的
> [Article Insights V1](../analysis/article-insights-v1.md) 定义并消费 ViewTracker 的指标事件。

## 1. 结论

`view` 不是普通 Reaction。它没有用户主动创建/撤销的事实，写入频率高，还需要身份分类、时间窗口
去重和异步计数。因此把现有 `CMS.Interactions.ViewEvents` 迁出 Interaction，建立 Article 专属的
`CMS.ViewTracker`：

```text
Article request
  -> GraphQL trackArticleView(article, event_id)
  -> RequestActor.classify/1
       -> Classification  human / agent / crawler / unknown
  -> CMS.ViewTracker.track(article, classification, event_id, opts)
       -> Identity    生成 ViewTracker 私有 viewer_tracking_key
       -> Policy      这次访问是否算有效阅读
       -> Event       幂等地保存判定结果
       -> EventProcessor  异步更新当前 views 与 viewer state
       -> Analysis    产生 article_view 指标事件
```

公开入口：

```text
CMS.ViewTracker.track(article, classification, event_id, opts)
CMS.ViewTracker.viewer_state(article, viewer)
CMS.ViewTracker.viewer_states(articles, viewer)
```

`viewer_states/2` 是列表与 response assembly 的主读取入口，返回
`%{{article_type, article_id} => %{viewer_has_viewed: boolean}}`；`viewer_state/2` 只是单元素包装。调用方不得在 Article
列表中逐篇调用单条接口。

`Identity`、`Policy`、`Event`、`Project`、`Cleanup`、`Metrics` 都是 ViewTracker 内部能力，
不是新的公共写入口。

human/agent/crawler/unknown 分类由平台级
[`GroupherServer.RequestActor`](../../architecture/request-actor.md) 唯一负责。ViewTracker 不解析 User-Agent、
agent credential、delegation 或 crawler 信号，也不保留自己的 Classifier。

## 2. event id 与匿名身份接线

当前没有使用浏览器指纹。浏览器端在文章内容实际进入可见区域时生成随机 UUID；独立 tracking 请求及其网络重试复用
同一个 UUID，成功后丢弃，不写入 `sessionStorage`，也不在整个 tab/session 内绑定到一篇 Article：

```text
一次逻辑读取                     -> 生成一个 event_id
同一次读取的超时或网络重试       -> 复用 event_id
刷新、重新进入或窗口到期后的读取 -> 新 event_id，由服务端滑动窗口决定是否计数
```

这个 UUID 只是“请求重试幂等键”，不是稳定 viewer identity，也不能证明多个 UUID 来自同一个人。
后端当前以 `event_id` 唯一约束接收 durable event，再由 Oban worker 异步增加 Article views、合并
authenticated viewer state；事件保留 30 天。

匿名跨请求身份不由 JavaScript 或 `event_id` 承担。Phoenix 请求 Plug 负责签发和验证 first-party Session
Cookie，`RequestActor.classify/1` 将唯一分类结果放入可信 request context；TanStack 只负责 `event_id`。浏览器同源 GraphQL proxy
仅转发 auth Cookie 与 `groupher-viewer` Cookie，并完整回传 Phoenix 的 `Set-Cookie`。SSR 内容读取不转发
viewer Cookie，也不承担计数。该 Cookie 链路必须在 Local、Preview 和 Production 真实验证 credentials、
Cookie domain、`SameSite` 以及代理的 `Set-Cookie` 保留。

### 1.1 内容面与计量面

```text
内容面（可 CDN / public cache）
browser or SSR -> loadPost / post query -> public Article content
                                      \-> 不签 visitor Cookie、不计数

计量面（user/session specific，不缓存）
hydrated ArticleViewer becomes visible
  -> browser POST trackArticleView(article, event_id)
  -> same-origin GraphQL proxy forwards auth + viewer cookies only
  -> Phoenix verifies/issues visitor Session Cookie
  -> public Gate admission -> ViewTracker
```

详情页 SSR 与 Drawer 的内容装载方式可以不同，但都在客户端共享 `ArticleViewer` 的可见性边界触发同一个
tracking mutation。预取、hover、后台请求或仅调用 `loadPost` 不构成阅读；没有执行客户端 tracking 的
纯 CDN crawler 不进入业务 views。已验证 Agent 若需要进入业务统计，应显式调用 tracking endpoint；CDN、
来源、设备与 crawler 总流量继续属于 Umami / Edge Analytics 口径。

## 3. V1 身份模型

V1 明确拆开两个 ID：

```text
event_id             每次逻辑读取的幂等键；仅供网络重试和并发重复提交复用
viewer_tracking_key  服务端归一化后的 opaque 访问者键；参与产品去重策略
```

不建立浏览器指纹。`viewer_tracking_key` 的来源按可信度排序：

```text
authenticated user    HMAC(pepper, "user:" + account_id)
authenticated agent   HMAC(pepper, "agent:" + credential_id)
anonymous browser     HMAC(pepper, "anonymous:" + signed session id)
known crawler         HMAC(pepper, "crawler:" + verified crawler family)
unknown               viewer_tracking_key = nil
```

匿名 ID 由服务端签发 first-party、带签名的随机值；数据库只保存不可逆 hash，不组合 canvas、字体、
硬件等指纹信号。Cookie 或可信凭据不可用时降级为 `unknown` 且 `viewer_tracking_key = nil`：每个不同的
`event_id` 都可以计数，不做跨请求去重。禁止用 IP、IP + User-Agent 或其他请求特征派生
unknown viewer tracking key，避免形成隐式指纹或错误合并 NAT 后的多个访问者。

AI Chat 读取按凭据与可验证信号分类：

- 使用 Groupher agent credential 且带登录主体：`actor_type = agent`、`is_authenticated = true`；匿名但带 agent credential 或 delegation 凭据的 Agent
  均为 `is_authenticated = false`；
- 代表已登录用户、且可验证委托：`actor_type = agent`、`is_authenticated = true`，同时保留 `user_id`；匿名但带委托凭据的 Agent
  仍为 `is_authenticated = false`，但使用独立的 `delegation_credential` 分类来源；
- 可验证的搜索/训练 crawler：`actor_type = crawler`、`is_authenticated = false`；
- 只有普通 User-Agent 自报、无法验证：`unknown`，不能冒充可信 agent。

`actor_type`、`classified_by` 和 confidence 由跨领域的 `GroupherServer.RequestActor.Const` 管理；decision reason
和 read purpose 由 ViewTracker 自己的 Const/enum 管理，均不能保存任意字符串：

```text
actor_type
  human / agent / crawler / unknown

is_authenticated
  true / false

classified_by
  account_session / agent_credential / delegation_credential / verified_crawler / self_reported / fallback

actor_confidence
  verified / probable / unknown

decision_reason
  counted / duplicate_in_window / excluded_by_policy

read_purpose
  public_read / author_preview / moderation_review / operations_inspection / internal_probe
```

RequestActor 的公共输出只包含分类判断：

```text
RequestActor.Classification
  type
  is_authenticated
  classified_by
  confidence
```

ViewTracker 在消费分类结果后建立自己的 identity；匿名与登录用户共享同一算法，但不共享同一个 key：

```text
ViewerIdentity
  viewer_tracking_key
  actor_type
  is_authenticated
  user_id?
  classified_by
  actor_confidence
```

Agent credential、可验证委托可以标记为 `verified`。Crawler 只有在反向 DNS 后再做正向确认，或命中
受维护的官方发布 IP 段时才是 `verified`。只凭 User-Agent 自报时使用
`classified_by = self_reported`、`actor_confidence = probable`，并按 `unknown` 进入产品统计；完全没有可信
分类信号时使用 `classified_by = fallback`、`actor_confidence = unknown`。

匿名 ID 由 Phoenix 请求 Plug 签发为 opaque、带 key version 和签名的 Session Cookie：`HttpOnly`、
生产环境 `Secure`、`SameSite=Lax`、`Path=/`，不设置 `Max-Age` 或 `Expires`。只有浏览器 tracking 请求经
同源 GraphQL proxy 携带该 Cookie；SSR 内容请求不转发它。raw ID 不暴露给 JavaScript。签名验证支持 current + previous
key 轮换（对应 `VIEW_TRACKER_COOKIE_SECRET` 与轮换期间的可选
`VIEW_TRACKER_COOKIE_PREVIOUS_SECRET`）；数据库只保存使用独立生产 pepper 生成的 HMAC。生产缺失 pepper
必须启动失败，RequestActor 和 ViewTracker
都不得内置 development fallback。raw ID 不进入日志、MetricEvent 或长期事实；Maintenance 分别按 ViewEvent
和 dedupe state retention 删除所有 `viewer_tracking_key`。长期聚合只保留 `actor_type` 与
`is_authenticated`。浏览器 session 结束后允许匿名身份重置并重新计数。

## 4. 有效阅读策略

V1 使用配置化滑动窗口。默认 `dedupe_window_seconds = 600`；可以调整为 300、180 等值。改变窗口或其他
统计语义时必须同时提升 `policy_version`，不能让同一版本代表两种规则。

同一 `viewer_tracking_key` 对同一 Article，只有距离上一次 counted View 达到配置窗口后，新访问才可
`counted = true`：

```text
09:09 counted
09:11 duplicate
09:19 counted
```

`occurred_at` 使用服务端接收时间，不接受客户端提供的时间作为计数窗口依据。`policy_version` 固化事件
当时使用的规则；未来改为 30 分钟时，不会悄悄改变旧数据含义。

请求幂等与业务去重由两个边界保护：

```sql
UNIQUE (event_id)

UNIQUE (target_type, target_id, viewer_tracking_key)
  ON article_view_dedupe_states
```

事务必须先占有 `event_id`，再根据 `read_purpose` 和 identity 决定是否触碰 dedupe state。不能依赖捕获
unique violation 后在同一事务继续，也不能让重试请求更新 `last_counted_at`：

```text
event_id already exists
  ├─ same Article + same normalized identity -> idempotent success
  └─ different Article or identity           -> view_event_identity_mismatch

new event_id + read_purpose != public_read
  -> insert terminal event
     counted=false
     decision_reason=excluded_by_policy
     projected_at=inserted_at
  -> do not touch dedupe state

new event_id + public_read + viewer_tracking_key=NULL
  -> keep counted=true
  -> do not touch dedupe state

new event_id + public_read + viewer_tracking_key present
  -> insert provisional event
     counted=true
     decision_reason=counted
     projected_at=NULL
  -> execute conditional dedupe UPSERT
```

```text
INSERT article_view_dedupe_states (..., last_counted_at = server_received_at)
ON CONFLICT (target_type, target_id, viewer_tracking_key)
DO UPDATE SET last_counted_at = server_received_at
WHERE last_counted_at <= server_received_at - dedupe_window
RETURNING ...

returned row     -> counted=true
no returned row  -> update this event in the same transaction:
                    counted=false
                    decision_reason=duplicate_in_window
                    projected_at=inserted_at
```

只有新插入的 `public_read` event 才能进入 dedupe UPSERT；已存在的 `event_id` 和非公开读取绝不更新
dedupe state。provisional event、dedupe UPSERT、terminal update、MetricEvent append 和 Job enqueue 都在同一
事务内完成，因此 provisional 状态不会对外可见。实现不得用 rescue unique violation 代替该协议。

uncounted ViewEvent 是不需要 consumer 的终态事件：插入时直接令 `projected_at = inserted_at`，不 enqueue
projection Job，也不产生 Analysis MetricEvent。counted ViewEvent 插入时保持 `projected_at = NULL` 并入队。
数据库约束必须保证：

```text
counted = false       -> projected_at IS NOT NULL
projected_at IS NULL  -> counted = true
```

相同 `event_id` 并发时保留现有 V4 语义：Article、viewer identity 和 actor identity 全部相同则
幂等成功；任一身份不同则返回 `view_event_identity_mismatch`，不能把已有事件重新绑定。

建议事件字段：

```text
ViewEvent
  event_id                 # 请求幂等键
  target_type / target_id / community_id
  viewer_tracking_key
  user_id?
  actor_type
  is_authenticated
  actor_confidence
  occurred_at             # server received time
  policy_version
  counted
  decision_reason
  read_purpose
  classified_by
  projected_at / failed_at / retry_count / failure_reason
```

IP、原始 Cookie、完整 User-Agent 不进入长期业务事实；确有安全诊断需求时应另设短保留、受限访问的
运维数据边界。

`decision_reason` 与 `counted` 必须一致：`counted = true` 只能对应 `counted`；`counted = false` 只能对应
`duplicate_in_window` 或 `excluded_by_policy`。身份无效且无法安全降级为 unknown 时直接返回错误，不保存
伪造的拒绝事件。

`read_purpose` 由服务端根据已通过的 Reader/Gate context、服务身份和请求入口推导，客户端不能提交或
覆盖。调用 `track` 时必须显式提供，缺失时 fail closed 并返回 `missing_read_purpose`，不得默认成
`public_read`。只有 `public_read` 允许计数；author preview、moderation review、operations inspection 和
internal probe 记录为 `excluded_by_policy`，或者由明确不追踪的管理 Reader 完全跳过 ViewTracker。

新模型的 counted 与 uncounted ViewEvent 都保留 30 天。Cleanup 只删除已完成投影且已过期的事件；pending、
失败待重试或仍被 projection worker 锁定的事件不因到期被删除。

因此 Cleanup 可以统一使用 `projected_at IS NOT NULL AND occurred_at < retention_boundary`，不需要为
uncounted 增加第二套删除条件。

`article_view_dedupe_states` 不能永久保留。Maintenance 按 `last_counted_at` 删除超过
`dedupe_state_retention_days` 的行，并把总量、过期量、最老 `last_counted_at` 与其年龄纳入 metrics。必须保证：

```text
dedupe_state_retention_days * 86_400 > dedupe_window_seconds
```

因此仍处于滑动窗口内、可能影响下一次判定的 state 绝不删除；过期清理后不再保留该匿名 session、用户
或 Agent 的 `viewer_tracking_key`。ViewEvent 和 dedupe state 使用独立配置，允许未来按诊断与隐私需求分别
调整，但默认都为 30 天。

Maintenance 按 `last_counted_at` 做范围删除，因此 dedupe state 表必须另建普通索引：

```sql
CREATE INDEX article_view_dedupe_states_last_counted_at_index
ON article_view_dedupe_states (last_counted_at);
```

该索引只服务过期扫描与最老 state metrics；业务并发正确性仍由
`UNIQUE (target_type, target_id, viewer_tracking_key)` 保证。若未来基于实际表量级决定取消 cleanup 索引，
必须用生产代表性数据的 `EXPLAIN (ANALYZE, BUFFERS)` 证明定时删除不会退化为不可接受的全表扫描。

`view_events(viewer_tracking_key, occurred_at)` 只用于按访问者键的短期诊断/清理查询，不参与业务计数正确性；
若部署版本没有这类查询，应删除该索引，避免无用途的写入成本。

运行参数使用明确命名，不与 Analysis Aggregator 混用：

```text
dedupe_window_seconds: 600
view_event_retention_days: 30
dedupe_state_retention_days: 30
view_projection_batch_size: 100
```

`policy_version` 是随统计规则和代码发布提升的语义版本，不是可由运维人员任意热修改的运行时旋钮。
窗口、身份分类或有效阅读判定改变时必须显式提升；规则未变时也不得无意义递增。

匿名 viewer 在同一窗口登录后，`viewer_tracking_key` 会从 anonymous 变为 user，V1 明确接受可能计数
两次。首版不保存
anon → user 关联，也不为严格去重扩大身份追踪范围。

### 4.1 去重窗口与 Insights 时间桶

ViewTracker 的去重窗口与 Insights 的聚合时间桶是两个独立概念：

```text
滑动窗口 = 决定一次访问是否 counted
固定时间桶 = 决定 counted 事件显示在哪个时间段
```

例如默认滑动窗口为 10 分钟：09:55 counted、10:01 duplicate、10:06 counted；Insights 的固定 UTC
小时桶最终显示 09:00–10:00 为 1、10:00–11:00 为 1。跨过整点不会绕过去重，展示分桶也不反向改变
ViewTracker 判定。

## 5. 投影归属与批量读取

ViewTracker 不读取或写入 Interaction 的 `post_reaction_infos.viewed_user_ids`：

```text
CMS.ViewTracker owns
├─ view_events
├─ cms.article_viewer_states authenticated viewer-state projection
├─ pending event overlay
└─ view projection revision

Article schema owns
└─ articles.views 字段语义
唯一合法 writer：CMS.ViewTracker.EventProcessor
```

`articles.views` 和对应 `views_revision` 由 ViewTracker.EventProcessor 在投影事务中受委托更新；这不意味着
ViewTracker 拥有 Article 的其他字段。V1 不读取或写入旧 Interaction bitmap。

V1 的 `viewer_has_viewed` 只服务已登录用户：authenticated viewer 使用 projection + pending overlay；
anonymous、agent、crawler 和 unknown 一律返回 false，且不查询 pending overlay。匿名 ID 只用于有效阅读
去重，不建立“你读过”状态。

ViewTracker 内部和批量接口统一使用 `{article_type, article_id}` 作为 key，不能只用物理 `article_id`，
否则跨 thread 的相同物理 id 会静默覆盖。Article response assembly 持有 canonical Article，负责与
Interactions 的 `{artiment_type, id}` 状态合并；调用方不得逐项扫描 typed articles 反查类型，组装复杂度
必须保持 O(n)。

assembly 在第一次遍历 canonical articles 时一次性计算 key，并在合并阶段直接读取：

```text
typed_articles = [{article, {article_type, article.id}}, ...]  # O(n)
states = ViewTracker.viewer_states(articles, viewer)

for {article, key} <- typed_articles
  state = Map.get(states, key, default_viewer_state)
```

禁止在每次 `Map.get` 前重新扫描 articles 或 Matcher 结果寻找 type。

Article 列表 response assembly 使用两路批量读取并按 Article id 合并：

```text
Articles.Response
  ├─ Interactions.viewer_states(articles, viewer)
  └─ ViewTracker.viewer_states(articles, viewer)
       ├─ projection row membership        最多 1 次批量查询
       └─ pending counted-event overlay    最多 1 次批量查询
```

authenticated pending overlay 使用 partial index，避免在列表读取中扫描已完成或匿名事件：

```sql
CREATE INDEX pending_view_events_by_user
ON view_events (user_id, target_type, target_id)
WHERE projected_at IS NULL
  AND counted = true
  AND user_id IS NOT NULL;

CREATE INDEX pending_view_events_for_projection
ON view_events (target_type, target_id, occurred_at)
WHERE projected_at IS NULL
  AND counted = true;
```

`article_viewer_states` 同时保留 `(target_type, target_id, user_id)` 唯一索引保证投影正确性，以及
`(user_id, target_type, target_id)` 普通索引服务 authenticated viewer 的列表读取；前者负责写入冲突判断，
后者避免批量读取只能从 target 维度开始扫描。

一页 Article 不得逐篇查询 ViewTracker。查询预算分为两个统计边界：

```text
Interaction + ViewTracker 投影读取
  常态 SELECT <= 4
  含 pending/额外分组的硬上限 SELECT <= 5

完整 Articles.Response.list assembly
  上述投影读取 + solution_by_post
  硬上限 SELECT <= 6
```

所有预算都不得随 Article 数量 N 增长。测试分层约束：现有 Interactions ReadState 单测继续保持
`select_count <= 3`；ViewTracker viewer_states 单测保持 `select_count <= 2`；Articles.Response.list 集成测试
统计完整 assembly 的全部 SELECT 并保持 `select_count <= 6`，分别覆盖单篇和一页 N 篇 Article。如果集成
测试不能稳定按 SQL owner 归因，以完整 assembly 上限为硬断言，由两个 owner 单测保证局部预算。

## 6. 可靠写入链路

```text
GraphQL trackArticleView(article, event_id)
  -> canonical public Article from Gate.scope(Article, nil, :read, public_context)
  -> consume RequestActor.Classification from trusted request context
  -> derive ViewTracker Identity
  -> require server-derived read_purpose
  -> evaluate Policy
  -> transaction
       insert event by event_id                # provisional only for new public read
       if event_id already exists
         -> same identity: idempotent return
         -> different identity: mismatch error
       else if read_purpose != public_read
         -> terminal excluded event; no dedupe state
       else if viewer_tracking_key is NULL
         -> counted event; no dedupe state
       else
         -> atomically update dedupe state     # configurable sliding window
         -> returned row: keep counted
         -> no row: terminal duplicate update
       if final counted=true
         -> append Analysis metric event
         -> enqueue durable projection job
  -> commit

worker
  -> lock pending events for one Article
  -> increment current views by counted events
  -> merge authenticated viewer state if needed
  -> mark projected_at
  -> commit
```

事件、计数增量和完成标记必须具备同一个可重放边界。worker 重试不得重复增加 `views`。
如果沿用“锁事件、更新计数、标记完成都在一个事务”的当前模型，它已经满足这个要求。
投影失败后的 `record_failure` 在事务外更新，但必须带 `projected_at IS NULL` 条件；成功投影会清空失败字段，
因此迟到的失败记录不能覆盖已成功状态。

Gate 使用现有读取 action `:read`，不为计数伪造 mutation action `:view`。独立 tracking resolver 必须先通过
`Gate.Context.Scope.Article` 得到 canonical public Article，再调用 `track/4`；内容 Reader 永不隐式调用
ViewTracker。Gate 的“允许读取”与 Policy 的
“是否计入 views”分开：public/published 允许普通访客读取并参与计数；
draft 只允许作者或管理员读取且默认不计公开 views；suspended/deleted 拒绝普通读取；管理或审核用途的
授权读取默认不计数。archived 使用 Article Reader 的现有读取规则，再由 Policy 决定是否计数。

ViewTracker 是 V5 “同步 Reaction”规则的显式例外：View 天然允许短暂最终一致；它有 durable event、
幂等键、重试与可观测性，因此不需要 `Interactions.Align`，也不由全库 repair job 兜底。

## 7. 与 Analysis 和 Umami 的边界

```text
ViewTracker                         Analysis.ArticleInsights
识别 + 分类 + 去重 + 当前计数  --->  小时聚合 + 趋势 + actor/auth filter

Umami / Analysis.Web
页面流量、访客、会话、来源、设备、地域；使用 Umami 自己的口径
```

`ViewTracker` 不变成通用统计系统。设备、外链、地域等成熟 Web Analytics 维度继续来自 Umami；
Groupher 的有效阅读则按自己的产品规则统计。两套结果可能不同，UI 必须明确口径，不能混成一个数字。

独立 tracking mutation 还带有轻量的每访问者写入限流（默认每分钟 120 次），用于降低无身份脚本的写放大；
它不是业务去重，也不是完整的反作弊系统。生产环境仍应在 Edge/API 层配置更强的 IP、WAF 或 bot 防护，且不把
原始 IP 写入长期 ViewEvent。

限流状态由 `GroupherServer.CMS.ViewTracker.RateLimit` supervised process 持有，不在请求进程中 lazy 创建 ETS；
状态按时间桶定期清扫。它是单个 Phoenix instance 的轻量保护，集群级防护仍由 Edge/WAF 负责。

推荐文案：

> 有效阅读按访问者和时间窗口去重，可能与第三方流量统计存在差异。

## 8. 迁移与验证

V1 仍处于预发布阶段，迁移采用直接切换：不迁移历史数据、不双写、不回填、不设兼容读取，也不保留
迁移期 facade。旧 `views`、`views_revision`、`viewer_has_viewed` 和 ViewEvent 从新模型重新开始。

实施与清理清单：

1. 增加 Phoenix visitor Plug：签发/验证匿名 Session Cookie，并把匿名 ID 放入可信 context；浏览器
   GraphQL proxy 只转发 auth 与 viewer Cookie，并回传 `Set-Cookie`；SSR 内容 loader 不转发 viewer Cookie；
2. 建立独立 `trackArticleView(article, event_id)` mutation；内容 query 删除 `view_event_id`。共享
   `ArticleViewer` 仅在内容实际可见后触发，详情页 SSR hydration 与 Drawer 使用同一路径，预取、hover 和
   `loadPost` 不计数；一次 tracking 请求及其重试复用同一 `event_id`；
3. 生产环境缺失 `VIEW_TRACKER_PEPPER` 时启动失败；RequestActor 与 ViewTracker 删除重复 development fallback；
4. 建立新的 ViewEvent、滑动窗口 dedupe state 与 authenticated viewer-state projection；
5. 将 record/project/cleanup/metrics、Job 和 telemetry 切到 ViewTracker；Maintenance 同时清理 terminal
   ViewEvent 与过期 dedupe state，并将两类 retention、projection batch 等“默认值”接入明确配置；
6. 建立 `CMS.ViewTracker.ErrorCat`，ViewTracker 不再依赖 `CMS.Interactions.ErrorCat`，Query 也不得混用裸
   atom 与声明式错误；
7. 接入 Article Insights 指标事件；两项设计仍可分版本实施；
8. 更新 GraphQL 和 Article response assembly，批量状态保持 typed key、O(n) 组装和既定查询预算；
9. 删除 `CMS.Interactions` facade 中的 `record_view` 与整个 `CMS.Interactions.ViewEvents`；
10. 删除 `ReadState.Query.viewer_has_viewed`、`pending_viewed_ids` 和对应 select；
11. 删除 `ReadState.Sync.merge_viewed_users`、`DefaultViewerState.article()` 中的旧 view 字段；
12. 已将 `Actor.Const` 与 `CMS.ViewTracker.Classifier` 直接迁移为 `GroupherServer.RequestActor`，所有生产入口只消费
    request context 中的 `RequestActor.Classification`，不保留旧 delegate/alias；
13. 删除 `Interactions.Config.view_*`、旧 View Job、telemetry 名称及其测试和 mock；
14. 删除 reaction info 表中的 `viewed_user_ids` 和旧 `view_events` 表，由新表直接替代。

必须验证：批量读取查询预算、相同/不同 event id 并发与 identity mismatch、滑动窗口边界与配置变化、
unknown 无跨请求去重、匿名 viewer state 恒 false、匿名登录后允许双计、agent 分类降级、read purpose
不可伪造且缺失时 fail closed、worker 失败重试、事务回滚、策略版本切换、零状态切换，以及 retention
不删除尚未投影的事件。dedupe state 测试必须证明窗口内行不删除、过期行会删除，且重放既有 event id
不会更新 `last_counted_at` 或制造幽灵窗口。匿名路径还必须验证 SSR 内容首读计数为零、hydration 可见后
恰好发起一次 tracking、Drawer 预取不计数但真正打开可计数、网络重试复用 event id、关闭 browser session
后允许重新识别。Session Cookie 必须通过浏览器同源 GraphQL proxy 的真实环境验收。
