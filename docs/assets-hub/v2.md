## v2 定位

v1 证明的是可信上传链路：

```text
Phoenix -> assets-hub -> R2 -> assets-hub -> Phoenix
```

v2 要证明的是资产进入产品主流程后仍然可管理：

```text
Upload -> Library -> Insert/Use -> Public Read -> Delete/GC
```

v2 不改变 v1 的核心边界：

- Phoenix `CMS.Assets` 继续拥有权限、社区范围、asset public ref、DB 写入、
  文章引用、容量和生命周期事实。
- `assets-hub` 继续拥有对象存储执行、对象校验、公共 origin resolution、variants、
  删除和清理任务。
- Dashboard 继续拥有产品 UI 和浏览器直传，不持有 provider secret，不拼 object key。

## Current Deployment Guardrails

当前 Cloudflare 接入只代表 public-read origin 已经接通，不代表完整 `assets-hub`
已经迁到 Worker。

- `assets.groupher.com` 当前只承载 Worker public-read 入口：
  - `GET /health`
  - `GET /a/:assetPublicRef/:variant`
- v1 上传链路仍在 Node/Hono `assets-hub`：
  - `POST /uploads`
  - `POST /uploads/:uploadRef/finalize`
- 本地 Dev Hub 启动 `Assets Hub` 时会同时启动：
  - upload-api / Hono on `8002`
  - read-worker / Wrangler on `8787`
- 本地 Dashboard 应通过 Portless 访问 upload-api 和 read-worker：
  - `NEXT_PUBLIC_ASSETS_HUB_ENDPOINT=https://assets-hub.groupher.localhost`
  - `NEXT_PUBLIC_ASSETS_HUB_READ_ENDPOINT=https://assets.groupher.localhost`
- 在 Worker 实现或代理 `/uploads` 和 `/finalize` 前，不要把
  `NEXT_PUBLIC_ASSETS_HUB_ENDPOINT` 直接切到 `https://assets.groupher.com`。
- 这不是两套上传流程，而是当前本地和生产职责拆分：
  - Hono upload-api 继续承接写链路：创建 upload intent、生成 PUT presign、
    finalize 后校验 R2 object 并回写 Phoenix。
  - Worker read-worker 只承接读链路：拿 public ref 查 Phoenix，再从 R2 stream
    original。
  - “迁移 `/uploads` 和 `/finalize` 到 Worker” 的意思是未来可以把写链路也搬到
    Cloudflare Worker，让 `assets.groupher.com` 同时处理读写；这会减少一个长期 Node
    服务，但会把上传写链路绑定到 Cloudflare Workers runtime。当前 v2 不需要做，
    是否迁移应作为 v3 架构取舍单独评估。
- 当前 Worker R2 binding 指向 `groupher-assets-dev`，只用于验证 custom domain 和
  public-read original。生产 public read 前必须切到生产 bucket，或明确当前环境只读
  dev bucket。
- Worker runtime secret 不能写入 `vars`。`wrangler.jsonc` 只声明
  `secrets.required = ["GROUPHER_SERVER_TRUST_SECRET"]`；本地用 `.dev.vars`，远端用
  `wrangler secret put GROUPHER_SERVER_TRUST_SECRET --config wrangler.jsonc` 注入。
- GitHub Actions 自动部署需要 repository secret：

```text
CLOUDFLARE_API_TOKEN
```

- 手动部署入口：

```text
make fe.assets-hub.deploy
```

- public read 输出 R2 对象前，必须先走 Phoenix internal lookup：

```text
assetPublicRef
  -> status / deletedAt
  -> storage / storageKey
  -> filename / mimeType / sizeBytes / width / height
  -> meta
```

这个 lookup 不是索要凭证。它只回答“这个 public ref 当前对应哪个可读取源对象，以及
业务生命周期是否允许公开读取”。Worker 不能只根据 URL 推导 R2 object key，因为 R2
只知道对象是否存在，不知道 asset 是否已删除、是否可公开读、是否迁移过 storage key、
是否允许某个 variant。

- logical variants 只能由服务端 preset 驱动。前端不能自由传 `width/height/quality`
  这类 transformation 参数。

## 分阶段

### v2a: Public Read

目标：让 v1 写入的 canonical URL 成为真实可访问地址。

推荐路径：

- 建立 `assets.groupher.com` 的 origin resolution。
- URL 形态继续使用：

```text
https://assets.groupher.com/a/<asset_public_ref>/<variant>
```

- `variant = original` 时解析到 `community_assets.storage/storage_key` 指向的对象。
- `variant = thumbnail/card/...` 且 asset 是位图图片时，优先映射到 Cloudflare Images
  Transformations，而不是读取 R2 中的实体 variant 文件。
- R2 bucket 继续保持 private，外部访问经过 Groupher 控制的 assets origin。
- 找不到 asset、asset 已删除或 variant 不存在时返回结构化 404。
- v2a 源码只支持 `original` + `storage = "r2"`。若 Phoenix 返回 active asset 但 storage
  provider 不是当前 Worker 支持的 provider，Worker 返回结构化 502，不伪装成 404。
- 当前 production origin 已先落到 Cloudflare Worker custom domain；dev 环境可以继续用
  `assets-hub.groupher.workers.dev` 或本地 mock 验证。

边界：

- Phoenix 仍然是 asset metadata source of truth。
- `assets-hub` 可以通过 Phoenix internal API 读取 public ref 对应的 storage mapping。
- 不把 R2 public URL 写入正文、cover 或外部 API。
- Cloudflare Images 只作为图片 transformer/optimizer，不作为资产主存储。

验收：

- Worker 不再返回 `asset_lookup_not_ready`。
- v1 上传成功后的 canonical URL 可以打开 original。
- public read 只基于 Phoenix internal lookup 的 active asset metadata 输出对象。
- 删除或不存在的 public ref 不泄露 provider 错误；unsupported storage provider 返回
  origin 层错误，不能伪装成 asset missing。
- 浏览器响应带正确 `content-type`、`content-disposition`、`etag/cache-control`
  基础 header。

### Phoenix internal origin info

Worker 不直接查询 Phoenix 数据库，也不从 URL 推导 object key。它必须通过
server-trusted GraphQL query 查询 `assetPublicRef` 对应的公开读取源对象信息。

Query 命名：

```graphql
query CommunityAssetOriginInfo($publicRef: String!) {
  communityAssetOriginInfo(publicRef: $publicRef) {
    publicRef
    status
    deletedAt
    filename
    storage
    storageKey
    mimeType
    sizeBytes
    width
    height
    meta
  }
}
```

`OriginInfo` 不是授权凭证。它是 Worker 公开读取 asset 时需要的源对象解析信息：
lifecycle、storage、storage key、filename、MIME、尺寸和 metadata。

网络路径：

```text
Cloudflare Worker
  -> PHOENIX_GRAPHQL_ENDPOINT
  -> server-trusted GraphQL query
  -> Phoenix/Fly
```

Worker 请求 Phoenix 时带 `GROUPHER_SERVER_TRUST_HEADER` / server trust secret。首版走
Phoenix 的公网 GraphQL endpoint，不引入 Fly private network。

最小 response：

```json
{
  "asset": {
    "publicRef": "asset_xxx",
    "status": "ACTIVE",
    "deletedAt": null,
    "filename": "cover.png",
    "storage": "r2",
    "storageKey": "communities/groupher/assets/2026_07/29_xxx/original",
    "mimeType": "image/png",
    "sizeBytes": 123456,
    "width": 1200,
    "height": 630,
    "meta": {}
  }
}
```

约束：

- 只返回 active、未删除、允许公开读取的 asset。
- deleted asset 可以返回 `status = DELETED`，也可以直接返回 not found；Worker 对外
  都必须输出 404 或 tombstone。
- 不返回 uploader、内部 DB id、权限细节或用户信息。
- internal API 使用 service-to-service trust，不暴露给普通 Dashboard 调用。
- Phoenix lookup 失败时，Worker 返回 `502` 或 `503`，并带 `cache-control: no-store`；
  不能把 Phoenix 故障伪装成 404。

### Public read cache policy

v2 首版不缓存 `communityAssetOriginInfo`。每次 public read 都先让 Phoenix 判断
business lifecycle，再由 Worker 读 R2 或做图片 transformation。这样删除、tombstone
和 storage mapping 的正确性最简单。

后续可按访问量逐步加缓存：

```text
1. Worker response cache / Cache API
   - 缓存最终 public-read response。
   - original 使用短 TTL，例如 1h。
   - thumbnail/card 可以使用更长 TTL，但必须考虑删除后的 purge 或短 lifecycle lookup。

2. Cloudflare KV
   - 缓存 publicRef -> origin info。
   - 适合减少 Phoenix lookup。
   - KV 是最终一致，不适合强依赖删除即时生效；deleted/not found 只能短 TTL。

3. Purge / invalidation
   - Phoenix 标记 deleted 后，应触发 assets-hub purge 或让短 TTL 快速失效。
   - 未建立 purge 前，TTL 必须保守。
```

推荐 v2 起步策略：

- `communityAssetOriginInfo`：不缓存。
- `original` response：短 TTL，例如 1h，且返回 `Access-Control-Allow-Origin`。
- `thumbnail/card` response：可以较长 TTL，但只针对服务端 preset。
- `deleted/not found/lookup failed`：`no-store` 或极短 TTL。

### v3: Library UI And Delete

目标：把社区资产从 demo 变成 Dashboard 中可管理的资源。该阶段不属于当前 v2
交付边界；v2 继续在 Dashboard Overview demo 上测试上传和 public read。

Dashboard 最小能力：

- 资产列表：filename、type、size、dimensions、created time、uploader、usage count。
- 资产详情：canonical URL、storage metadata、content hash、variants、引用列表。
- 操作：复制 URL、复制 Markdown、删除未引用资产。
- 状态：active、deleted、processing、failed。

Phoenix 能力：

- `pagedCommunityAssets` 支持基础 filter：
  - asset type
  - status
  - referenced / unreferenced
  - filename keyword
- `communityAssetRefs` 展示文章引用位置。
- `deleteCommunityAsset` 已实现领域删除结果：校验权限、锁定 asset、拒绝已引用资产、
  soft-delete active asset。
- 删除 intent 或 deletion capability 仍未实现；后续必须限 community、asset public ref、
  variant scope 和 TTL。

`assets-hub` 能力：

- 接收删除任务或删除 capability。
- 删除 original。若后续存在物理化 variants，也一起删除。
- 删除过程幂等：对象不存在视为已删除。
- 删除失败保留 diagnostics，并允许重试。

边界：

- 删除前的引用检查只能在 Phoenix 做。
- `assets-hub` 不直接查询 `article_document_asset_refs`。
- Dashboard 不能绕过 Phoenix 直接请求删除 object key。
- Phoenix 标记 deleted 后，public read 必须立即不可访问；R2 object 删除可以异步重试。

验收：

- Phoenix 层未引用 asset 可 soft-delete，删除后不再计入 active storage usage。
- Phoenix 层已引用 asset 删除失败，并返回可读原因。
- Dashboard Library 删除入口和引用详情仍未接入。
- R2 object 删除 task 仍未接入。
- 删除后公共访问应返回 404 或 tombstone；当前依赖 Phoenix active lookup 过滤 deleted。
- R2 删除失败不能让 deleted asset 重新变成可访问；后续 provider deletion task 必须保持
  这个幂等语义。

### v2b: Orphan Cleanup

目标：处理 v1 已接受的残留状态。

问题状态：

```text
Dashboard PUT R2 成功
Dashboard 关闭页面或网络中断
finalize 没有发生
R2 中留下没有 community_assets 记录的 object
```

实现方向：

- Phoenix intent 写入短期 upload intent 记录，或在 `assets-hub` 记录最小 upload task。
- 记录字段至少包含：
  - upload ref
  - community ref
  - asset public ref
  - object key
  - expires at
  - finalized at
  - cleanup status
- sweeper 按 prefix 和 expires at 查找未完成对象。
- 清理只允许删除 capability 生成的 object key。
- finalize 与 cleanup 必须避免竞争：cleanup 前再次确认 completion 状态。

验收：

- PUT 成功但未 finalize 的对象在 TTL 后被清理。
- 已 finalize 的 asset 不会被 sweeper 删除。
- sweeper 运行失败有日志和可重试状态。

### v3: Docs/Cover Integration

目标：让 Assets Hub 成为 Docs editor、cover 和 image block 的统一资源入口。该阶段不属于
当前 v2 交付边界。

前端写入方式：

- cover 上传使用 v1/v2 上传链路，而不是旧 URL 注册。
- editor image block 插入时可以：
  - 上传新文件并插入 asset 引用。
  - 从资产库选择已有 asset。
- editor block 保存 asset identity，而不是 provider URL。

推荐 block payload：

```json
{
  "type": "image",
  "attrs": {
    "assetPublicRef": "asset_xxx",
    "variant": "original",
    "alt": "Hero image",
    "caption": "..."
  }
}
```

如果当前 editor/GraphQL 仍以 DB id 作为引用输入，前端可以在保存前把
`assetPublicRef` 解析为 asset id；但正文中不应长期依赖 provider URL。

Phoenix 保存链路：

- body 中的 image/attachment/embed block 进入 `asset_refs`。
- cover 进入 `cover_asset_id`。
- dark cover 进入 `cover_asset_dark_id`。
- 保存文章、发布、预览、草稿复制时继续使用现有 refs copy/sync 边界。

验收：

- 上传 cover 后保存文章，`article_document_asset_refs` 有 `cover` 引用。
- 上传 dark cover 后保存文章，`article_document_asset_refs` 有 `cover_dark` 引用。
- editor image block 保存后有 `inline` 引用。
- 从正文删除 image block 后，对应 ref 被移除，但 `community_assets` 不被删除。
- 发布、预览、草稿复制不会丢失 asset refs。

### v3: Image Delivery And Logical Variants

目标：让图片资产有可用于列表、卡片和正文展示的派生输出，但不在 v2 默认提前
生成并持久化实体 variant 文件。

最小 variants：

```text
original
thumbnail
card
```

v2 默认存储形态：

```text
communities/<community_ref>/assets/YYYY_MM/DD_<asset_uid>/original
```

`thumbnail`、`card` 是 logical variants，不一定对应 R2 中的实体 object key。

推荐出口映射：

```text
GET /a/<asset_public_ref>/original
  -> R2 original, 原样受控输出

GET /a/<asset_public_ref>/thumbnail
  -> R2 original + Cloudflare Images Transformations
  -> width/height/fit/format/quality preset

GET /a/<asset_public_ref>/card
  -> R2 original + Cloudflare Images Transformations
  -> width/height/fit/format/quality preset
```

Cloudflare Images 在这个架构里只负责图片 transformation 和 edge cache。R2 继续保存
original，Phoenix `community_assets` 继续保存资产身份、权限、引用、删除、容量和
审计事实。

variant preset 固定在服务端：

```text
thumbnail
  width: 320
  height: 180
  fit: cover
  format: auto

card
  width: 960
  height: 540
  fit: cover
  format: auto
```

具体尺寸可以实现时调整，但 variant 名称必须是枚举。Worker 不接受前端自由拼接的
`?width=...&height=...&quality=...` 参数。

metadata 归属：

- Phoenix `community_assets` 保存 original 的基础事实和可查询 summary。
- logical variant preset 可以先放代码配置，或在 `community_assets.meta.variants`
  中记录覆盖项。
- 如果未来需要固定产物审计、离线迁移、逐 variant 重试或不依赖 Cloudflare 动态转换，
  再把 variants 物理化到 R2，并拆 `community_asset_variants` 表。

生成策略：

- v2 默认按需转换：首次请求某个 logical variant 时由 Cloudflare Images 生成并缓存。
- 未访问过的尺寸不生成，也不占 R2 存储。
- `format=auto` 这类输出格式选择不改变 original 的 content hash。
- variants 不改变 original 的 content hash。

验收：

- image asset finalize 后，`thumbnail/card` URL 可请求。
- Dashboard 列表优先使用 thumbnail。
- Docs/card 场景可以请求 card variant。
- transformation 失败不会让 original 上传回滚。
- 删除 asset 后，original 和 logical variants 都不能继续访问。

Cloudflare 开通要求：

- 只使用 R2 原图 + Images Transformations 时，不需要购买 Cloudflare Images storage。
- Cloudflare Images Free plan 默认包含 transformations，每月有免费 unique
  transformations 额度。
- 超过 Free plan 的 unique transformations 额度后，需要购买 Images Paid plan；仍然
  只按 Images Transformed 计费，不按 Images Stored / Images Delivered 计费。
- 不建议 v2 使用 Hosted Images 存储，除非后续明确要把图片主存储也迁到
  Cloudflare Images。

## 风险与延后项

- Public read 当前已先选择 Cloudflare Worker 作为 `assets.groupher.com` origin，并已完成
  Phoenix `communityAssetOriginInfo` lookup 和 R2 original stream；后续重点是补 Images
  Transformations。
- 当前 Worker 只覆盖 public read original 和 variant route shell，上传/finalize 仍由 Node/Hono assets-hub
  承担。迁移上传 endpoint 到 Worker 是单独决策，不属于 public read 前置。
- 当前 Worker binding 指向 `groupher-assets-dev`，生产上线前必须切换或拆分环境。
- Cloudflare Images Transformations 是图片出口端能力，不覆盖非图片附件、SVG 原样归档、
  原图 hash、删除审计和 provider migration。
- dynamic transformation 会引入 Cloudflare Images unique transformations 成本；v2
  需要控制 logical variant 数量，避免把任意尺寸暴露给前端自由拼接。
- 删除如果先标记 Phoenix deleted，再删除 provider object，可能出现短暂 tombstone
  状态；公共访问层必须以 Phoenix lifecycle 为准。
- `meta.variants` 足够记录 v2 的覆盖项，但长期 provider migration、固定产物审计和逐
  variant 重试可能需要独立表。
- risk-center、multipart、私有资源和 provider migration 都不进入 v2，避免把资产库
  基础闭环拉得过大。
