# Assets Hub v3

> 状态：thread 归属与 stats/quota 设计已确认，实施中
>
> 前置：v2a public read original 已完成；上传仍由 Hono upload-api 承接，public read
> 由 Cloudflare Worker 承接。
>
> 目标：把 Overview demo 升级并迁移为当前 community 的正式 Assets Hub 管理工具，先完成
> 展示、图片预览和删除闭环，再接 Docs/Cover identity、provider deletion task 和 logical
> variants。

## v3 定位

v2 证明的是 canonical public read：

```text
Dashboard upload demo
  -> Hono upload-api
  -> R2
  -> Phoenix community_assets
  -> Worker public-read original
```

v3 证明的是资产进入 Dashboard 的产品管理闭环：

```text
Dashboard Assets tab
  -> current community asset list
  -> preview / copy / open / delete
  -> Phoenix ref guard
  -> public read blocked immediately after soft-delete
  -> assets-hub queue deletes provider object
```

v3 不急着把 `/uploads` 和 `/finalize` 迁到 Worker。写链路 runtime 统一是独立取舍，不是
Assets tab、删除保护或 Docs/Cover identity 的前置。

## Thread 归属与引用链

v3 明确区分两条链路：

```text
community_assets
  -> asset belongs to community
  -> asset belongs to thread
  -> storage bytes / quota / library filtering

article_document_asset_refs
  -> where an asset is used by article document blocks or covers
  -> delete guard / detail references
```

`thread` 是 asset 自己的归属维度，语义类似 `community_id`，不是从 refs 推导出来的。

因此：

- `All / Post / Changelog / Doc` 按 `community_assets.thread` 过滤。
- `article_document_asset_refs.thread` 只用于说明该 asset 被哪个 article/document 使用。
- 删除链路仍以 refs 为准；只要有 active refs，`deleteCommunityAsset` 必须拒绝。
- 不做历史数据 backfill。旧 asset 的 `thread` 可以为空，仍出现在 `All`，不出现在具体 thread tab。
- 新上传链路必须带上 thread；AssetsHub 临时上传入口首版可固定写入 `post`，正式入口由文章/设置所在
  thread 传入。

后端字段：

```elixir
field(:thread, Ecto.Enum, values: existing_thread_values)
```

GraphQL 复用现有 `:thread` enum，不新增 AssetsHub 专用 enum。

## Filter / Stats Contract

列表查询使用 asset 专用 filter，不再只依赖通用 `PagiFilter`：

```graphql
input CommunityAssetFilter {
  page: Int
  size: Int
  query: String
  thread: Thread
  assetType: CommunityAssetType
  subtypes: [String!]
}
```

过滤语义：

- `query`: 搜索 `title` / `filename`。
- `thread`: asset 归属 thread。
- `assetType`: 大类，复用 `CommunityAssetType`，即 image / audio / video / file。
- `subtypes`: 小类，首版由 MIME subtype 或文件扩展名归一化，例如 png / jpg / webp / mp4 / docx / pptx。

统计接口独立提供：

```graphql
communityAssetStats(community: String!, filter: CommunityAssetFilter): CommunityAssetStats
```

返回：

```graphql
type CommunityAssetStats {
  totalCount: Int!
  storageBytes: BigInt!
  storageLimitBytes: BigInt!
  byThread: [CommunityAssetThreadStat!]!
  byAssetType: [CommunityAssetTypeStat!]!
}
```

其中：

- `storageBytes` 是当前 community active assets 的真实占用。
- `storageLimitBytes` 首版可以写死；字段设计按 plan-aware quota 预留，后续切换为不同 plan 阈值。
- `byThread` 使用 `community_assets.thread` 统计，不使用 refs。
- `byAssetType` 使用 `asset_type` 分组，并附带 subtype 分布。

首版容量展示只需要：

```text
storageBytes / storageLimitBytes
```

后续 plan 化时，只替换 stats resolver 的 limit 计算来源。

## 删除链路

### 当前已实现的删除保护

权威删除入口是 Phoenix GraphQL：

```graphql
mutation DeleteCommunityAsset($community: String!, $id: ID!) {
  deleteCommunityAsset(community: $community, id: $id) {
    id
    publicRef
    status
    deletedAt
  }
}
```

当前领域链路：

```text
Dashboard
  -> deleteCommunityAsset(community, id)
  -> CMS.Assets.delete(community, asset_id)
  -> Repo.transaction
  -> find_active_asset_for_update(community_id, asset_id)
  -> referenced?(asset)
  -> if referenced: rollback {:custom, "asset is still referenced"}
  -> if unreferenced: status = :deleted, deleted_at = DateTime.utc_now(:second)
```

`referenced?(asset)` 当前通过 `article_document_asset_refs` 做存在性检查：

```text
article_document_asset_refs.asset_id == asset.id
```

这意味着“能否删除”的最终判定已经在 Phoenix 领域层实现了：只要 asset 仍被任意
article document ref 引用，删除就会失败。

软删除后的 public read：

```text
Worker GET /a/:assetPublicRef/original
  -> communityAssetOriginInfo(publicRef)
  -> CMS.Assets.origin_info(publicRef)
  -> active + deleted_at is nil + storage/storage_key exists
  -> deleted asset 查不到
  -> Worker 返回 404 asset_not_found
```

所以 Phoenix 标记 deleted 后，即使 R2 object 还没物理删除，public read 也会立刻被
业务生命周期挡住。

### Assets Facade 命名收敛

早期命名：

```elixir
CMS.Assets.register(...)
CMS.Assets.sync_article_refs(...)
CMS.Assets.copy_article_refs(...)
CMS.Assets.purge_article_refs(...)
```

当前已在 `CMS.Assets` facade 收敛为产品语义更清楚的一组函数：

```elixir
CMS.Assets.register_to_community(community, attrs, user \\ nil)
CMS.Assets.link_refs(article, attrs)
CMS.Assets.link_refs(article, attrs, community: community)
CMS.Assets.copy_refs(source_article, target_article)
CMS.Assets.cleanup_refs(thread, article_id)
```

语义边界：

- `register_to_community`：上传 finalize 后，把已验证的 R2 object 登记到
  `community_assets`。这一步是产品上传完成的一部分；正常产品链路不应存在“R2 已上传成功但未登记为
  community asset”的成功状态。若 PUT 成功但 finalize/register 失败，应视为 orphan object，由后台
  cleanup 处理。
- `link_refs`：文章保存时，根据当前正文/封面内容建立这篇文章当前使用的 asset refs。它不是
  append-only；它以当前保存后的内容为准更新该 article 的 refs。第一个参数固定是 article；
  已解析的 community 通过 `community: community` 传入，避免双 arity 第一参数语义不一致。
- `copy_refs`：draft/public/preview/publish 版本流转时，把 source article 已有 refs 复制到 target
  article。它不重新扫描内容，也不表达用户新增引用。
- `cleanup_refs`：父体永久删除后，清理该 article 留下的 asset refs。软删除不调用，永久删除才调用。

当前迁移状态：

- `CMS.Assets` facade 已增加新函数名，内部委托现有 Write 实现。
- article draft/publish/preview/trash 调用点已切到新函数名。
- tests 已切到新函数名。
- 旧 facade 函数作为 deprecated wrapper 短期保留。

当前链路与新命名的对应关系：

```text
上传完成 / finalize:
  complete_upload -> register_to_community

编辑保存:
  body / cover -> link_refs(article, attrs)
  body / cover with resolved community -> link_refs(article, attrs, community: community)

从 public 创建 draft:
  copy_refs(public_article, draft)

preview promote:
  copy_refs(preview_draft, main_draft)

preview/fork from public:
  copy_refs(public_article, draft)

publish:
  copy_refs(draft, public_article)

soft delete:
  refs unchanged

permanent delete:
  cleanup_refs(thread, article_id)
```

`link_refs` 的测试已体现集合更新语义：

```text
article initially links [A, B]
article later saves [B, C]

expected:
  A refs -> 0
  B refs -> 1
  C refs -> 1
  article refs contain B/C only
```

### refs count 与 Drawer

列表上应该展示当前 asset 的引用状态，例如 `3 refs`。点击后打开 Drawer，展示引用它的文章列表。

产品口径：

- `refs` 表达“内容父体正在使用这个 asset”，不表达重复上传或 dedupe。
- 上传 finalize / `register_to_community` 只创建 community asset，不直接创建 article ref。
- 只有文章、cover 或 editor block 保存后通过 `link_refs` 建立引用，才产生 refs。
- soft delete 父体不减少 refs，因为父体可恢复。
- permanent delete 父体通过 `cleanup_refs` 减少 refs。

`usageCount` 应直接作为 `pagedCommunityAssets.entries` 的字段返回：

```graphql
pagedCommunityAssets {
  entries {
    id
    filename
    usageCount
  }
}
```

实现不建议每行 N+1 resolver。推荐在 `Read.page` 中：

```text
1. 正常分页读取 assets
2. 收集当前页 asset ids
3. 用一个 batched query 按 asset_id 统计 refs count
4. merge usage_count 到 entries
```

count 口径需要在实现前确认：

- `refCount`：`article_document_asset_refs` 行数。同一篇文章多处使用同一 asset 会计多次。
- `articleUsageCount`：distinct `(thread, article_id)` 数。同一篇文章多处使用同一 asset 只算一次。

如果 Drawer 展示的是“文章 list”，默认更推荐 distinct article count，否则同一篇文章插入多次会出现
`3 refs` 但 Drawer 里只有一篇文章，容易误解。若后续需要展示 block 级影响面，可以在 Drawer
文章项下再显示 block usages。

Drawer 计划：

```text
AssetsHub/List/RefsBadge/
  index.tsx
  salon/index.ts

AssetsHub/RefsDrawer/
  index.tsx
  Item.tsx
  useAssetRefs.ts
  salon/index.ts
  salon/item.ts
```

交互：

- `usageCount == 0` 默认不显示 badge，减少列表噪音。
- `usageCount > 0` 显示 `1 ref` / `n refs`。
- 点击 badge 打开 Drawer。
- Drawer 使用现有 `communityAssetRefs(community, assetId, filter)` 拉分页详情。
- Drawer item 展示 article title、thread、usage、block/source 辅助信息。
- 删除按钮仍以 Phoenix `deleteCommunityAsset` 的权威 guard 为准。

### v3 删除 UX

推荐交互：

- 未打开详情时，列表行 delete 可以采用两步确认，不使用浏览器 `confirm`。
- 详情面板中显示 References 区：
  - `communityAssetRefs` 第一页。
  - 如果有引用，显示 thread、articleId、usage、blockType、source、title/alt。
  - 有引用时删除按钮 disabled，文案说明必须先从文章、cover 或 editor block 中移除引用。
- 没有引用时，删除按钮可用。
- 调用 `deleteCommunityAsset` 失败时直接展示后端错误；最常见错误是
  `asset is still referenced`。
- 如果首版暂时不做 preflight，也必须处理 `deleteCommunityAsset` 返回的 referenced error；不能只依赖
  前端列表状态判断能否删除。

### v3 provider object deletion

Phoenix soft-delete 是第一阶段，provider object 删除是第二阶段。当前首版使用 assets-hub
Worker internal endpoint + Cloudflare Queue；不引入 assets-hub DB。

推荐后续链路：

```text
Phoenix deleteCommunityAsset
  -> mark community_assets.status = deleted
  -> mark deleted_at
  -> POST assets-hub /internal/assets/delete
  -> public read immediately blocked by Phoenix origin_info

Assets Hub internal endpoint
  -> verify server trust header
  -> enqueue Cloudflare Queue message

Assets Hub queue consumer
  -> delete R2 original object
  -> delete physical variant objects if they ever exist
  -> missing object counts as success
  -> throw on retryable failure so Queue retries
```

Queue message 首版字段：

```text
asset id
asset public ref
community id/ref
storage provider
storage key
```

失败处理：

- Phoenix 删除成功后不因为 R2 删除失败回滚。
- Queue consumer 抛错后由 Cloudflare Queue 自动重试。
- 超过 Queue retry 后进入 Worker logs / DLQ；首版不在 assets-hub 持久化状态。
- 后续若需要 Dashboard 展示 cleanup failure，再补 delete_result 持久化。

已发现的 timeout 问题：

- 本地 mock 删除测试中，Phoenix 已经把 `community_assets` 行 soft-delete，但随后 provider delete
  enqueue 失败；R2 object 仍保留。
- 单独请求 `assets-hub /internal/assets/delete` 时，链路耗时约 4s。原因不是 R2 delete 本身必然慢，而是
  Phoenix -> public assets-hub Worker 经过公网、Worker 调度/冷启动、Queue send 后才返回。
- 原先 Phoenix 侧 `Tesla.Middleware.Timeout` 只有 3s，容易在 Worker 冷启动或网络抖动时提前放弃，导致
  Queue 没收到删除任务。

当前处理：

- Phoenix provider delete enqueue timeout 调整为 10s。
- enqueue 成功日志记录 `asset_id / public_ref / duration_ms`。
- enqueue 失败日志必须把 `reason` 写进 message 文本；mock console format 不展示 logger metadata。
- delete notification 是 best-effort：即使 endpoint 超时、401/500 或 adapter 抛异常，也不能影响
  Phoenix 已完成的 soft-delete 结果。

后续优化方向：

- assets-hub internal endpoint 只做参数校验、server trust 校验、Queue enqueue，然后尽快返回。
- R2 物理删除全部放 Queue consumer；consumer 失败通过 Cloudflare Queue retry 处理。
- 如果 10s 仍不稳定，再考虑 Phoenix 侧异步 fire-and-observe 或补 reconciliation，而不是拉长用户请求。

运行时配置：

```text
Phoenix:
  ASSETS_HUB_DELETE_ENDPOINT=https://assets.groupher.com

assets-hub Worker:
  ASSET_DELETE_QUEUE -> groupher-asset-delete-dev
  ASSETS_BUCKET -> groupher-assets-dev
```

边界：

- 删除前引用检查只在 Phoenix 做。
- Assets Hub 不直接查询 `article_document_asset_refs`。
- Dashboard 不能把 storage key 直接交给浏览器删除。
- R2 删除失败不能让 deleted asset 重新可读。
- deletion task 必须幂等；object 不存在视为已删除。

### orphan object cleanup

PUT 成功但 finalize/register 失败时，R2 可能留下没有 `community_assets` 成功登记的 object。这个
cleanup 可以延期实现，但策略需要提前固定：

```text
periodic cleanup job
  -> build keep-set from community_assets storage keys
  -> list R2 object keys under community asset prefixes
  -> delete R2 keys that are not in keep-set
```

keep-set 不能只等于 `status = ACTIVE`，否则可能误删仍处于业务生命周期中的资源。推荐口径：

```text
keep-set:
  active assets
  deleted assets still inside a restorable / grace window lifecycle
  any future pending-delete rows that still need reconciliation

delete candidates:
  R2 objects not represented by keep-set storage_key
```

首版不需要实现这个 job；先保留明确边界，后续做 reconciliation 或 delete_result 可视化时再落地。

## 引用链与 Docs/Cover

当前引用投影表是 `article_document_asset_refs`，usage 覆盖：

```text
inline
cover
cover_dark
attachment
embed
```

v3 中 Assets tab 的引用详情只消费这张投影，不直接解析 editor document body。

Docs/Cover integration 的目标：

- cover 上传走 Assets Hub 上传链路。
- dark cover 上传走 Assets Hub 上传链路。
- editor image block 保存 asset identity，而不是 provider URL。
- 保存文章时通过 `link_refs` 写入当前内容使用的 `article_document_asset_refs`。
- 预览、发布、草稿复制等版本流转通过 `copy_refs` 复制 `article_document_asset_refs`。
- 删除正文 image block 时只移除对应 ref，不删除 `community_assets`。

推荐 editor image block payload：

```json
{
  "type": "image",
  "attrs": {
    "assetPublicRef": "asset_xxx",
    "variant": "original",
    "alt": "Hero image",
    "caption": "..."
  }
}
```

如果保存 API 当前仍需要 DB id，前端可以在保存前把 `assetPublicRef` 解析为 asset id；正文长期
不应保存 provider URL 或 R2 signed URL。

## Image Preview And Variants

v3 首版图片预览使用：

```text
GET /a/<asset_public_ref>/original
```

后续再接 logical variants：

```text
GET /a/<asset_public_ref>/thumbnail
GET /a/<asset_public_ref>/card
```

约束：

- `thumbnail/card` 是服务端 preset，不接受前端自由传 `width/height/quality`。
- Cloudflare Images Transformations 只做输出转换和 edge cache，不做主存储。
- R2 继续保存 original。
- 删除 asset 后，original 和 logical variants 都必须不可读。

  `totalCount == 0` 时仍调用 `deleteCommunityAsset` 做权威检查。

Backend / lifecycle:

- Phoenix 权威引用检查继续保留。
- soft-delete 后 public read 返回 404。
- article soft delete 不改变 asset refs。
- article permanent delete 调用 `cleanup_refs`，使对应 asset refs 下降。
- 多个 article 使用同一个 asset 时，永久删除其中一个 article 只减少该 article 对应 refs，不影响其他
  article 的 refs。
- provider object deletion 通过 assets-hub Queue 首版接入。
- provider deletion 失败不影响 deleted 状态。

Validation:

- `yarn workspace @groupher/frontend-core type-check`

  - referenced delete error 展示
  - refs preflight 禁用删除按钮
  - successful delete reload 和 selected asset cleanup
- 后端已有 deletion guard 与 lifecycle focused tests：
  - `link_refs` 初次建立 refs。
  - `link_refs` 覆盖 `[A, B] -> [B, C]`，A 消失、B 保留、C 新增。
  - article soft delete 不改变 asset refs。
  - article permanent delete 触发 `cleanup_refs`，asset refs 变 0。
