# Assets Hub v5：Revision Usage 与资源生命周期重构

> 状态：目标方案。
>
> 前置：Article Revision / Draft 新模型视为已经完成；本文不保留旧
> `article_documents`、`article_document_asset_refs` 或 physical draft/public row 兼容层。
>
> Source of truth：本文覆盖 [`v4.md`](./v4.md) 中 `Refs 生命周期`、
> `Assets List 引用可见性` 与 `Orphan Cleanup` 的目标设计。上传、公共读取和 logical
> variant 继续分别遵循 V1-V4 已建立的边界；Article/Draft/Revision ownership 以
> [`revision-draft-target.md`](../feature/article/revision-draft-target.md) 为准。

## 1. 结论

Assets Hub v5 不再把引用理解成“某个物理 Article row 使用了资源”，而是把资源引用视为
Article 内容版本的一部分：

```text
CommunityAsset
      ^
      |
ArticleAssetRef
      |
      +-- mutable ArticleBodyDraft
      |
      `-- immutable ArticleRevision
```

核心决策：

- `ArticleAssetRef` 是唯一的 Article 内容资源关系，不再建立第二套 Media Usage 表。
- Draft refs 可随编辑替换；Revision refs 与 Revision 一起不可变。
- Publish 从 Draft 固化 Revision 时，同时固化正文、cover 和全部 refs。
- Usage Projection 只负责把权威 refs 投影成用户可理解的“在哪里使用”；它不拥有引用事实。
- “替换当前使用”修改一个 Draft；“全局替换”创建跨 Article replacement plan，不能修改历史 Revision。
- 删除 guard 与列表 `usageCount` 分离：前者保证安全，后者服务产品展示。
- GC 必须同时考虑数据库 Asset、provider object、上传意图和受保护 Revision，不能用“零 refs”直接删除。

## 2. 当前实现基线

### 2.0 与 EmDash Media Library 的能力映射

| EmDash 能力                        | Groupher v5 落点                                        | 结论                            |
| ---------------------------------- | ------------------------------------------------------- | ------------------------------- |
| Used in / usage tracking           | `ArticleAssetRef` + Usage Projection + Drawer           | 采用，并区分 Draft/live/history |
| Replace this use                   | `CMS.Assets.replace_use` 委托 Article Draft command     | 采用                            |
| Replace/edit globally              | immutable `AssetReplacementPlan`，逐 Article 生成 Draft | 采用，但禁止改历史 Revision     |
| 删除前引用保护                     | 全量 `blockingUsageCount` + 权威 delete guard           | 采用                            |
| focal point 属于某次使用           | `ArticleAssetRef.meta.presentation`                     | 采用，不全局修改 Asset          |
| usage tracking activation/backfill | legacy audit -> staged backfill -> completeness receipt | 采用，仅迁移旧内容时需要        |
| backfill write fence               | ref mutation fence 或变更日志追赶                       | 采用，防止扫描期间漏引用        |
| 外部媒体 provider                  | 保留现有 Assets Hub provider adapter 边界               | 不在 v5 扩大范围                |

Groupher 不照搬“直接全局修改所有内容”。由于 Revision 不可变，所谓全局替换只能作用于当前
Draft，或基于 live Revision 为每篇 Article 创建新的 Draft；历史 Revision 继续指向旧 Asset。

本文把下列当前实现和 Revision 目标文档中尚未完全落地的部分统一视为基线：

### 2.1 Asset identity 与上传

```text
Browser checksum
  -> Phoenix create upload intent
  -> short-lived capability
  -> Assets Hub presign
  -> Browser PUT provider object
  -> Assets Hub finalize
  -> Phoenix complete upload
  -> CommunityAsset active
```

`CommunityAsset` 是社区范围内稳定资源身份；产品数据保存 `assetPublicRef` 和受控 variant，
不保存 provider URL、R2 key 或 signed URL。

### 2.2 Version-owned refs

`ArticleAssetRef` 当前表达：

```text
owner: body_draft_id XOR revision_id
asset: community_asset
usage: inline | cover | cover_dark | attachment | embed
location: block_id | block_type | position
presentation: title | alt | source | meta
```

数据库必须继续保证 exactly-one-owner。删除 Draft、清理 Revision 时只释放该内容版本拥有的 refs。

Cover 的编辑态和发布态分别归属于 Draft 与 Revision：

```text
DraftCoverEdit       mutable editor state
RevisionCover        immutable selected asset
RevisionCoverEdit    immutable editor snapshot
```

### 2.3 当前删除保护

当前 `CMS.Assets` 已能通过任意 `ArticleAssetRef` 是否存在阻止删除。这是正确的最后一道 guard，
但还不足以解释：

- 引用来自当前 Draft、live Revision 还是历史 Revision；
- 用户应去哪里移除引用；
- 是否可以归档但保留公共读取；
- 全局替换会影响哪些 Article；
- 哪些零引用对象只是尚未 finalize/link 的暂态。

## 3. 权威模型与 Projection

### 3.1 写入权威

```text
ArticleBodyDraft ----\
                      -> ArticleAssetRef -> CommunityAsset
ArticleRevision -----/
```

禁止增加一个独立、可写的 `asset_usages` 作为第二事实源。产品查询需要的信息通过 join/projector
生成：

```text
ArticleAssetRef
+ owner Draft/Revision
+ Article stable identity
+ live_revision_id/current draft
+ Lifecycle visibility
--------------------------------
AssetUsageProjection
```

### 3.2 Usage Projection DTO

```text
AssetUsage {
  refId
  assetRef
  usage
  location { blockId, blockType, position, label }
  article { ref, thread, title, path }
  owner {
    kind: DRAFT | REVISION
    ref
    revisionNumber?
    state: CURRENT_DRAFT | LIVE | HISTORICAL
  }
  articleState: ACTIVE | TRASHED
  canEdit
  canReplace
}
```

权限过滤必须发生在 Phoenix Query/Gate 边界：

- 没有 draft read 权限的用户不能从 Assets Hub 推断 Draft 内容。
- 没有历史版本权限的用户不能看到 historical usage 的正文位置。
- `usageCount` 与 Drawer 必须使用同一可见性口径，但删除 guard 仍检查全部权威 refs。

### 3.3 三种计数

不要用一个 `usageCount` 同时回答三个问题：

| 字段                 | 含义                      | 用途                     |
| -------------------- | ------------------------- | ------------------------ |
| `articleCount`       | 去重后的稳定 Article 数   | Assets 列表 badge        |
| `visibleUsageCount`  | 当前用户可见的 usage 数   | Drawer/UI                |
| `blockingUsageCount` | 会阻止物理删除的全部 refs | 删除决策，仅返回安全摘要 |

同一 Article 的 Draft、live 和历史 Revision 可以贡献多个 usage，但 Assets 列表默认显示去重后的
`articleCount`，避免 badge 显示 8 而 Drawer 只有一篇文章。

### 3.4 Per-use presentation metadata

裁切、焦点和 caption 等展示选择默认属于“这一次使用”，不属于 Asset 全局事实：

```text
CommunityAsset
  width / height / mime / storage identity

ArticleAssetRef.meta.presentation
  focalPoint { x, y }
  crop?
  objectFit?
  caption?
```

在某篇文章中调整 focal point 只更新该 Draft-owned ref。Publish 时它随 ref 固化到 Revision；之后
修改 Asset 默认展示配置也不能让已有 Revision 的渲染发生漂移。

## 4. Publish、Discard、Restore 与 Cleanup

### 4.1 Publish

Publish transaction 固化一个一致内容版本：

```text
lock Article + Draft
  -> validate expected Draft version
  -> create ArticleRevision
  -> create immutable body snapshot
  -> copy Draft ArticleAssetRefs to Revision ownership
  -> create RevisionCover / RevisionCoverEdit snapshot
  -> update Article.live_revision_id
  -> finalize lifecycle/activity
  -> commit
```

正文 snapshot 成功而 refs 失败时必须整体回滚。公开 runtime 只能从 live Revision 读取正文与资源。

### 4.2 Discard Draft

```text
discard Draft
  -> delete Draft-owned ArticleAssetRefs
  -> delete DraftCoverEdit
  -> delete/reset ArticleBodyDraft
  -> keep every Revision and Revision-owned ref unchanged
```

Discard 后变成零引用的 Asset 只进入 orphan candidate，不同步物理删除。

### 4.3 Restore Revision to Draft

```text
select historical Revision
  -> replace mutable Draft body
  -> replace Draft-owned refs from selected Revision refs
  -> restore DraftCoverEdit from Revision snapshot
  -> keep selected Revision immutable
```

### 4.4 Revision cleanup

Revision retention cleanup 删除一个 Revision 时，由 FK/cascade 或同事务显式删除其 refs。被保护的
Revision（live、release、audit/retention hold 等）不能清理，因此其 Assets 也继续受保护。

## 5. 产品能力

### 5.1 Used in Drawer

```text
hero.png
2.4 MB · 1920 x 1080

当前使用
  LIVE       产品介绍 / v18 / 封面
  DRAFT      产品介绍 / 当前草稿 / 正文第 3 张图
  HISTORICAL 发布说明 / v7 / 正文第 1 张图

[替换当前使用] [全局替换...] [归档]
```

Drawer 支持按 `LIVE | DRAFT | HISTORICAL | TRASHED` 过滤，并明确哪些项目只是历史保留、哪些会影响
当前线上内容。

### 5.2 Replace one use

`Assets.ReplaceUse` 输入稳定位置而不是前端传任意 ref attrs：

```text
actor
articleRef
expectedDraftVersion
usage locator { usage, blockId/position/theme }
fromAssetRef
toAssetRef
```

执行：

```text
load canonical Article + Draft
  -> Gate edit check
  -> lock Draft / expected version
  -> verify locator still points to fromAsset
  -> update Draft body/cover and Draft-owned ref together
  -> create normal Draft change result
```

如果 usage 只存在于 live Revision，先基于 live Revision 创建/打开 Draft，再替换 Draft。任何场景都不
原地修改 Revision-owned ref。

### 5.3 Replace globally

全局替换是跨 aggregate 的计划式操作，不是一条 SQL update：

```text
Asset A
  -> analyze visible/current usages
  -> create AssetReplacementPlan
  -> classify each Article
       editable
       permission denied
       concurrent Draft conflict
       historical only
  -> user Review
  -> apply one Article command per selected target
  -> each Article receives a Draft change
  -> user publishes separately or invokes explicit batch publish
```

计划项至少固定：

```text
articleRef
observedLiveRevisionRef
observedDraftVersion
usageLocators[]
fromAssetRef
toAssetRef
decision
result
```

Apply 必须重新验证 observed version 和 locator；过期项标记 conflict，不能误改用户之后的编辑。
历史 Revision 永远保持原样。

### 5.4 Archive 与 delete

```text
Archive
  从选择器和默认列表隐藏
  现有 Draft/Revision 继续渲染
  可恢复

Delete
  要求 blockingUsageCount = 0
  创建 provider deletion intent
  对外 origin 先失效/tombstone
  provider object 异步幂等删除
```

用户尝试删除被引用 Asset 时返回可行动结果：

```text
不能永久删除：仍被 3 篇文章引用
[查看使用位置] [归档资源]
```

不泄露用户无权读取的标题或 Draft 内容，只返回阻断数量。

## 6. GC 与 Reconciliation

### 6.0 Usage completeness 与旧内容回填

新 Revision 写链路必须同步维护 refs，不依赖后台扫描。但旧正文 URL、旧 cover 字段或其他历史业务
引用迁移到 `ArticleAssetRef` 时，需要显式 completeness 状态：

```text
NOT_STARTED -> SCANNING -> CATCHING_UP -> COMPLETE
                         `-> FAILED / resumable cursor
```

在 `COMPLETE` 之前：

- delete guard 不能因为 refs 查询为空就允许永久删除；
- UI 必须显示“引用索引仍在准备”，不能把零结果声明为未使用；
- GC 禁止处理受扫描范围覆盖的 Asset。

扫描期间必须防止漏写，二选一：

```text
短期 write fence
  暂停目标范围内的 ref mutation，完成一致扫描后开放

或

snapshot watermark + mutation log
  扫描稳定快照，再追赶 watermark 之后的 ref changes
```

首期迁移优先采用短期、有界 write fence；数据量证明不可接受时，再升级为 watermark/catch-up。
完成后写入带 schema version、scope 和 completed-at 的 completeness receipt，不能只依赖一次 Job 的
`completed` 状态。

### 6.1 两类 orphan

```text
Database orphan
  CommunityAsset 存在，但没有任何业务引用

Provider orphan
  provider object 存在，但没有成功登记的 CommunityAsset
```

二者必须分别扫描。

### 6.2 Database orphan candidate

只有同时满足以下条件才进入候选：

```text
no ArticleAssetRef
AND no wallpaper/application/plugin-owned reference
AND no pending upload/finalize/import/replacement command
AND created/finalized before safety window
AND not archived-retained/legal-held
```

候选先标记并经过 grace period，再创建 delete intent；不在扫描事务中直接删除对象。

### 6.3 Provider reconciliation

```text
list bounded provider prefix
  -> compare CommunityAsset storage identity
  -> exclude active upload sessions and recent objects
  -> mark provider orphan candidate
  -> grace period
  -> enqueue idempotent delete
```

扫描必须分页、可恢复、记录 cursor，不能一次把整个 bucket 构造成内存 keep-set。

### 6.4 Retention 与审计

记录：

```text
candidate reason
first observed at
last verified at
retention deadline
delete intent/result
provider diagnostics
```

GC 不能删除 domain facts、Revision 历史或 Activity；它只回收已经不再被任何受保护事实引用的资源。

## 7. API 与 Command 边界

读模型：

```text
CMS.Assets.page
CMS.Assets.usage_summary
CMS.Assets.usages
CMS.Assets.replacement_preview
```

写模型：

```text
CMS.Assets.archive
CMS.Assets.restore
CMS.Assets.delete
CMS.Assets.replace_use
CMS.Assets.create_replacement_plan
CMS.Assets.apply_replacement_plan
```

`replace_use` 最终委托 Article Draft 领域命令，因为 Draft body 与 refs 必须一起更新。Assets 模块负责
Asset 合法性和 replacement orchestration，不越权成为 Article 内容 Writer。

`CMS.Command` 不与每个插件或 transport 一一对应。它是共享执行器：具体命令拥有业务语义，
`CMS.Command` 只在需要时提供 transaction、command receipt、幂等和 ambiguous-commit recovery。

## 8. 分阶段实施

### Phase 0：收口新 Revision refs

- 删除 v4 旧 physical article refs 的剩余运行时假设。
- 验证 Draft/Revision exactly-one-owner、publish copy、discard/restore 和 cleanup。
- GraphQL ref DTO 增加 owner state，但不暴露无权限 Draft。

### Phase 1：Usage Projection 与产品可见性

- batched usage summary，无 N+1。
- Used in Drawer 与 LIVE/DRAFT/HISTORICAL/TRASHED 标签。
- 删除失败返回 blocking summary 和可行动入口。

### Phase 2：单点替换

- `replace_use` 的 locator/version contract。
- 正文、cover、dark cover 的 focused tests。
- 并发 Draft 变更返回 conflict。

### Phase 3：全局替换计划

- immutable replacement plan 和逐 Article results。
- Review UI。
- 有界 worker 并发；每个 Article 独立 command，失败不伪装成全局原子事务。

### Phase 4：Archive、GC 与 provider reconciliation

- archive lifecycle。
- database/provider orphan candidates、grace period、delete intents。
- provider cursor、重试、DLQ 与 reconciliation observability。

## 9. 验收标准

- Draft 和 Revision refs 只有一个写入权威。
- Publish 后 live Revision 的正文、cover 和 refs 属于同一个事务结果。
- 历史 Revision 不能被替换操作修改。
- 没有 Draft 权限的用户无法从 Assets API 推断 Draft usage。
- Used in Drawer 能区分 current Draft、live 和 historical usage。
- 删除保护覆盖全部权威 refs，不依赖 UI 的可见 usageCount。
- 单点替换使用 expected Draft version，过期 locator 不会误改内容。
- 全局替换先 Review，再为每篇文章创建 Draft 变更，并报告逐项 conflict/result。
- zero-ref recent uploads、pending finalize 和受保护 Revision 不会被 GC。
- provider delete 幂等、可重试；删除后所有 logical variants 都不可读。

## 10. 非目标

- 不可变 Revision 的原地资源替换。
- 用第二套可写 Usage 表复制 `ArticleAssetRef` 事实。
- 把跨 Article replacement 声称为单数据库事务。
- 在首个版本实现资源二进制去重、跨 community 共享或完整 DAM 工作流。
- 让 Assets Hub Worker 直接查询 Phoenix 数据库或绕过 Phoenix lifecycle/capability。
