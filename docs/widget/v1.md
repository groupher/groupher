# Groupher Widget v1

> 状态：前端 mock-first 原型在 2026-08-07 完成。
> 生产 API 集成、真实反馈持久化、Rich Editor 和部署路由延后到 v2。
>
> 范围：建立 Groupher Widget 的前端运行时、构建合约、脚本安装流程、Lit 和
> Shadow DOM UI shell、Tailwind 样式，以及 Dashboard 中一个真实的 mock 加载
> 体验。

## 目标

Groupher Widget 让 community owner 可以把一个 Groupher 托管的脚本加到一个
外部网站，并暴露一个小型启动入口和一个可展开的 panel。该 panel 在不要求宿主
应用采用 Groupher 前端栈的前提下，演示公开的 Posts、Changelogs、Docs 和
Feedback 视图。

v1 是前端原型里程碑。它证明 Groupher 可以：

- 从现有 monorepo 构建一个 framework-neutral 的 custom element；
- 从一个稳定的开发或公开脚本 URL 加载它；
- 用 Shadow DOM 隔离其 UI；
- 用一个专属的 Tailwind build 为 Shadow DOM 加上样式；
- 使用 mock 数据渲染真实的 loading、content、empty、error、retry 和 feedback
  状态；
- 提供一个与 queue 兼容的命令和生命周期 API。

v1 原型刻意不要求后端 API 或持久化的反馈提交。这些都是 v2 的内容。

公开产品名称是 **Groupher Widget**。这个名字在 Dashboard 菜单、外部脚本、
前端 workspace、公开 API 和后端领域中保持一致。`frontend/core/ui` 下现有的
可复用 UI 组件仍是通用 Core UI 组件；嵌入式产品运行时是 `frontend/widget`
下一个独立构建的应用。

## v1 产品范围

安装后的体验包含：

```text
Groupher Widget
  launcher
    -> open / close

  panel
    Home
    Posts
    Changelog
    Docs
    Feedback
```

内容模块每页只展示一小段。默认页大小应保持在 5 到 10 条。`View all` 在
新浏览器 tab 中打开对应的 Groupher community 路由。

Feedback 视图支持：

- title 输入框；
- 纯文本 body 输入框；
- 模拟的提交延迟；
- validation、success 和 failure 状态；
- 一个 mock 链接代表未来创建的 Groupher Post。

v1 UI 不需要复刻完整 Main 应用。它应使用 Widget 专属的 DTO 和组件，而不要从
`frontend/core` 导入 PostThread、DocThread、Dashboard store、routing 或页面
layout。

## 范围外

以下内容被刻意延后：

- 客户平台 SSO；
- 自动识别已有 Groupher 登录；
- Groupher 登录弹窗或跳转；
- 生产身份验证和账号领取；
- 完整的匿名滥用防护；
- AI 生成的反馈 title；
- 页面元素选择和实时标注 marker；
- 全页和局部区域截图捕获；
- 宿主页面变化后的响应式标注重放；
- 多条标注渲染在同一张全局截图上；
- Widget 内的直接回复、投票、reaction 或消息；
- 管理员配置 UI；
- 实时更新；
- iframe 兜底；
- 超出“报告测量输出”的生产 bundle-size 门槛。

这些都是后续阶段，不是 v1 中隐藏的需求。

## 主要决策

### 产品和代码命名

在产品和集成边界处统一使用 `widget`：

```text
product:       Groupher Widget
workspace:     frontend/widget
package:       @groupher/widget
custom element:<groupher-widget>
global API:    window.GroupherWidget
Dashboard:     /dashboard/widgets
REST prefix:   /api/widgets/v1
public key:    widgetKey
```

不要把应用放在 `frontend/core/ui` 下。Widget 是一个独立构建的应用，可以从
Core 复用合约和窄工具，但 Core 不拥有它的运行时。产品专属的符号应保持显式，
例如 `CommunityWidget`、`WidgetBootstrap` 和 `useCommunityWidget`，以免裸
`Widget` 名称产生歧义。

### Lit Shell

Lit 拥有 Widget 主要运行时：

- custom element 注册；
- Shadow DOM 根；
- launcher 和 panel 状态；
- content tab 和列表渲染；
- REST API 客户端；
- feedback title 和提交状态；
- 懒加载的 Rich Editor 宿主；
- 未来的 annotation overlay。

宿主页面不需要 React、Lit、Tailwind 或任何 Groupher 包。Widget 所需的一切
都由 Groupher 提供。

### Loader 和运行时格式边界

安装片段是一个 classic script，刻意不要求 `type="module"`。因此稳定的
`v1.js` loader 不能包含静态 ESM 语法或 `import.meta`。

Build 把 Widget 应用输出为一个带 hash 的 ES module。Classic loader 从
`document.currentScript.src` 解析自己的 public base，通过一个临时的
`<script type="module">` 注入带 hash 的运行时，然后把队列中的命令分派给已
注册的运行时工厂。这在保留小段复制粘贴安装合约的同时，让运行时和后续 Rich
Editor chunk 可以使用普通的 ESM code splitting。

如果稳定 loader 包含 `import.meta`、保留未解析的运行时文件名占位符，或
manifest 没有同时标识 loader 和运行时 entry，生产 build 必须失败。

### Shadow DOM 优先

v1 把完整 panel 渲染在 `<groupher-widget>` 的 ShadowRoot 中。初始实现不要
使用 iframe。

Shadow DOM 提供了必需的第一道边界：

- Widget 样式不会泄漏到宿主页面；
- 大多数宿主页面的 selector 不会影响 Widget 内部；
- Widget 运行时仍可在后续 annotation 阶段检查宿主 DOM；
- v1 中没有 `postMessage`、iframe 尺寸、focus bridge 或 second-document
  生命周期。

如果 Rich Editor portal 或恶意的宿主页面行为无法可靠被收容，iframe 仍是后
续的兜底方案。

### Shadow DOM 内的 Tailwind

Widget 拥有专属的 Tailwind entry 和 content scan。它不能加载 Main、
Dashboard 或 Landing 的 Tailwind 产物。

建议的源文件：

```text
frontend/widget/src/styles.css
```

生成的 CSS 被注入到 ShadowRoot。只挂到 `document.head` 的普通 stylesheet
不能为 ShadowRoot 内的节点加样式。

对 v1 来说，优先使用 custom element 拥有的 `<style>` 元素：

```text
Vite 把 Widget CSS 作为 text import
  -> <groupher-widget> 创建 ShadowRoot
  -> append <style>
  -> append Lit application root
```

Constructable stylesheets 和 `adoptedStyleSheets` 之后再评估。POC 应先
使用兼容性最好的浏览器路径。

Widget 的 Tailwind 规则沿用现有的前端约束：

- 优先使用现有的 spacing、size、typography 和 color token；
- 标准工具类足够时避免任意 Tailwind 值；
- 默认不要 import 整个 Core utility graph；
- 不需要 class conflict 解决时使用 `clsx` 风格的组合；
- Rich Editor 的 CSS 保持在懒加载 editor 边界内。

### React Rich Editor Island（v2）

`@groupher/rich-editor` 仍基于 React。不能用 `preact/compat` 跑它，也不能用
Lit 重写它。这个 island 不是已完成的 v1 mock-first 原型的一部分。

Lit 渲染一个专属的 editor 宿主：

```text
<groupher-widget>
  #shadow-root
    <div id="widget-app">
      ...
      <div id="rich-editor-root"></div>
    </div>
```

当用户进入 Feedback 视图并激活 body editor 时：

```text
Lit feedback view
  -> 动态 import editor island
  -> import React 和 ReactDOM createRoot
  -> import @groupher/rich-editor
  -> mount 到 rich-editor-root
  -> 把 value 变化 emit 回 Lit
```

POC 必须验证：

- editor 挂载和卸载不泄漏 React root；
- Plate value 变化能到达 Lit feedback model；
- editor CSS 被注入到同一个 ShadowRoot；
- 菜单、tooltip、combobox、popover 等 portal 保持可见；
- 键盘 focus 保持在 panel 内；
- 在 Feedback editor 激活之前不会请求 editor chunk。

如果 portal 默认挂到 `document.body`，POC 应先尝试提供 ShadowRoot 拥有的
portal 容器。如果当前 editor 包没有这个边界，先记录下这个包差距，再考虑
iframe。

即使 POC 之后需要 editor 包做小的修改，它仍是成功的。这是 v2 的需求，不
会阻塞 v1 原型完成。


一个文件不应定义多个组件。Lit 组件和 React island 组件遵守和前端其他部分

Widget workspace 可以复用：

- 共享的 TypeScript API 合约；

- server-only helper；
- 把 Main/Dashboard Tailwind 配置作为运行时样式源。

## 安装合约

公开的安装片段应保持小且稳定：

```html
<script
  async
  src="https://groupher.com/widget/v1.js"
  data-widget-key="widget_public_example"
></script>
```

Loader 读取自己的 `data-*` 属性，注册 `<groupher-widget>`，并在
`document.body` 下挂载一个实例。

命令式 API 与 queue 兼容，以便 loader 还没准备好时发出的命令能被重放：

```html
<script>
  window.GroupherWidget =
    window.GroupherWidget ||
    function () {
      ;(window.GroupherWidget.q = window.GroupherWidget.q || []).push(arguments)
    }
</script>
<script async src="https://groupher.com/widget/v1.js"></script>
<script>
  GroupherWidget('boot', {
    widgetKey: 'widget_public_example',
  })
</script>
```

必需的 v1 命令：

```text
boot(config)
open(view?)
close()
toggle()
update(context)
shutdown()
```

示例：

```js
GroupherWidget('boot', {
  widgetKey: 'widget_public_example',
  position: 'bottom-right',
})

GroupherWidget('open', { view: 'changelog' })

GroupherWidget('update', {
  url: window.location.href,
  title: document.title,
})
```

`boot` 对 community Widget 是幂等的。`shutdown` 移除 DOM、listener、observer、
定时器以及任何已挂载的 React editor root。

## 构建合约

Vite 构建两层运行时：

```text
stable loader
  /widget/v1.js

cacheable assets
  /widget/assets/widget-runtime.<hash>.js
  /widget/assets/widget-runtime.<hash>.css 或内联到 Shadow 的 CSS
  /widget/assets/rich-editor.<hash>.js
  /widget/assets/rich-editor.<hash>.css 或内联到 Shadow 的 editor CSS
```

Stable loader 应只包含：

- 命令队列接管；
- 配置校验；
- 运行时 base URL 解析；
- custom element/运行时 import；
- 重复加载保护；
- 致命加载错误上报。

Loader 不能包含 Rich Editor 或 content-rendering 应用。

构建产物要求：

- `v1.js` 拥有稳定的非 hash URL；
- 所有运行时 chunk 使用 content hash；
- 生成 source map，用于 Groupher 自己的错误诊断；
- 产物不依赖 Node.js 或 Next.js 运行时；
- 构建输出机器可读的 manifest；
- demo HTML 使用已构建的产物，而不是 source import；
- 构建产物可由一个 workspace 命令复现。

建议的 scripts：

```json
{
  "scripts": {
    "dev": "vite",
    "build": "tsc --noEmit && vite build",
    "preview": "vite preview",
    "type-check": "tsc --noEmit",
    "test": "vitest run"
  }
}
```

具体的 script 名称应在实施开始时与 workspace 约定保持一致。

## 部署合约（v2）

生产 v2 需要一个稳定的公开脚本 URL 和一个 asset 目录。Hosting provider 是
实现选择；URL 合约不能依赖它。

逻辑生产路由：

```text
https://groupher.com/widget/v1.js
https://groupher.com/widget/assets/*
https://groupher.com/api/widgets/v1/*
```

Gateway 或公开入口可以把这些 path 转发到独立的 static 和 API origin。当
Groupher 把 asset 移动到 Vercel、Cloudflare、对象存储或其他 CDN 之间时，
客户无需修改自己的安装片段。

缓存：

```text
/widget/v1.js
  Cache-Control: public, max-age=300

/widget/assets/*.<hash>.js
/widget/assets/*.<hash>.css
  Cache-Control: public, max-age=31536000, immutable
```

部署必须先发布 hash asset，再替换 `v1.js`。这可以避免新 loader 引用尚未
可用的 chunk。

静态 asset 可以使用宽松的跨域读头，因为它们是公开的构建产物。REST API 必
须单独校验持久化的 Widget 状态和请求 Origin。

## 后端边界（v2）

Widget 使用专属的 REST API。浏览器代码不能直接调用内部 GraphQL schema。

建议的 Phoenix 路由前缀：

```text
/api/widgets/v1
```

Widget 属于现有 CMS 领域，因为它的 v1 行为读取 community 内容、遵循
community 展示设置，并创建 Groupher Post。仅凭 transport 或 script 边界
无法证明一个独立顶层 `GroupherServer.Widgets` context 的合理性。

使用这些后端归属边界：

```text
GroupherServer.CMS.Widgets
  Read
  Write
  Bootstrap
  Feedback

GroupherServer.CMS.Model.CommunityWidget
cms.community_widgets
```

`CommunityWidget` 独立于 `CommunityDashboard`：

```text
Community
  has_one :dashboard, CommunityDashboard
  has_one :widget, CommunityWidget
```

Dashboard 是管理面，而不是 Widget 数据的所有者。不要把 Widget 字段加到
`CommunityDashboard`，也不要恢复那些仅供 demo 用的 `widgetsPrimaryColor`、
`widgetsThreads`、`widgetsSize` 前端字段作为后端合约。

REST API 层拥有：

- 公开 `widgetKey` 查询；
- Widget 启用状态；
- allowed-origin 校验；
- community 解析；
- DTO 投影；
- 分页限制；
- guest session 处理；
- 基础限流；
- Post 创建编排；
- 未来加入截图时的 asset/upload 集成。

REST controller 调用 `CMS.Widgets`，后者可以把内容生命周期工作委托给现
有的 CMS context。它不能重复 Post、Changelog、Doc 或 Article 的生命周期
逻辑。

Dashboard 管理面使用已鉴权的 GraphQL 查询和 mutation。外部浏览器代码使用
受限的 Widget REST API。两种 transport 共享 `CMS.Widgets` 作为它们各自
的领域边界。

## 最小 REST API（v2）

### Bootstrap

```text
POST /api/widgets/v1/bootstrap
```

请求：

```json
{
  "widgetKey": "widget_public_example",
  "page": {
    "url": "https://customer.example/pricing",
    "title": "Pricing"
  },
  "visitorId": "visitor_local_id"
}
```

响应：

```json
{
  "widget": {
    "publicId": "widget_public_example",
    "enabled": true,
    "content": {
      "enabledViews": ["home", "posts", "changelog", "docs", "feedback"],
      "defaultView": "home"
    },
    "appearance": {
      "primaryColorSource": "community",
      "primaryColorOverride": null,
      "launcherPosition": "bottom-right",
      "launcherSize": "medium",
      "panelStyle": "drawer"
    }
  },
  "community": {
    "slug": "example",
    "title": "Example",
    "logo": "https://..."
  },
  "session": {
    "token": "short_lived_guest_session"
  },
  "home": {
    "posts": [],
    "changelogs": [],
    "docs": []
  }
}
```

Bootstrap 可以包含 Home 所需的小段首页数据，避免立即发起第二次请求。较大
或非默认视图使用 content 端点。

### Content

```text
GET /api/widgets/v1/content?type=post&page=1&pageSize=5
GET /api/widgets/v1/content?type=changelog&page=1&pageSize=5
GET /api/widgets/v1/content?type=doc&page=1&pageSize=5
```

响应：

```json
{
  "entries": [
    {
      "ref": "public_article_ref",
      "title": "Example title",
      "digest": "Short summary",
      "publishedAt": "2026-08-06T00:00:00Z",
      "url": "https://groupher.com/example/post/..."
    }
  ],
  "page": {
    "number": 1,
    "size": 5,
    "totalCount": 20,
    "hasMore": true
  },
  "viewAllUrl": "https://groupher.com/example/posts"
}
```

DTO 刻意排除了较大的 Main article fragment、viewer reaction 状态、Dashboard
字段和应用专属的 layout 数据。

### Feedback

```text
POST /api/widgets/v1/feedback
```

请求：

```json
{
  "title": "Checkout button is difficult to find",
  "body": "[{\"type\":\"p\",\"children\":[{\"text\":\"...\"}]}]",
  "page": {
    "url": "https://customer.example/pricing",
    "title": "Pricing",
    "capturedAt": "2026-08-06T00:00:00Z"
  }
}
```

响应：

```json
{
  "post": {
    "ref": "public_article_ref",
    "title": "Checkout button is difficult to find",
    "url": "https://groupher.com/example/post/..."
  }
}
```

服务端：

```text
通过 public ID 解析 CommunityWidget
  -> 校验 Widget 状态和 Origin
  -> 校验 guest session
  -> 首次提交时创建或复用 guest user
  -> 校验 Rich Editor body
  -> 在配置的 feedback community/thread 中创建 Groupher Post
  -> 返回公开 Post reference 和 URL
```

客户平台账号和 Groupher 登录都被延后。v1 的 guest model 刻意很窄：

- guest user 仅在首次成功提交时创建；
- 打开 Widget 不会创建 Groupher user；
- guest identity 通过短期 Widget session 限定范围；
- 生产级的 claim/merge 和 SSO 规则属于后续文档。

## Community Widget 模型（v2）

v1 每个 community 仅支持一个 Widget：

```text
Community
  has_one :widget, CommunityWidget
```

在出现独立 per-site 内容、外观、生命周期或分析的真实需求之前，不要引入
`has_many :widgets`。同一配置下的多个允许 hostname 由 `allowed_origins`
处理。

概念模型：

```text
cms.community_widgets
  id
  community_id
  public_id
  enabled
  feedback_thread

  content
    enabled_views
    default_view

  appearance
    primary_color_source
    primary_color_override
    launcher_position
    launcher_size
    panel_style

  access
    allowed_origins

  inserted_at
  updated_at
```

`public_id` 在不受信任的浏览器代码中标识 Widget；绝不要暴露 community 数据
库 ID。它不是 secret。授权仍依赖服务端 Widget 状态、Origin 校验、session
校验、限流和请求的操作。

嵌套的 `content`、`appearance` 和 `access` 组是 Widget 配置合约。具体的
数据库表示可以根据校验和查询需求使用 Ecto embeds 或显式字段，但拥有它的
schema 仍是 `CommunityWidget`，而不是 `CommunityDashboard`。

v1 可以为 `/home` 的开发和端到端测试 seed 一个 `CommunityWidget`。

## Dashboard 配置合约（v2）

完整的管理员配置 UI 仍延后，但其产品和数据边界已经固定，因此不会继续沿
用旧的 Widgets demo。

使用：

```text
menu:   Widgets
route:  /dashboard/widgets
unit:   DashboardThread/Widgets
```

- Rich Editor 获得焦点时，提交操作不能被键盘遮挡。

section 渲染嵌套卡片。

## 2026-08-08 全链路 Review 记录

### 结论

v1 前端雏形已经完成。当前真实入口是 TanStack Dashboard 的
`/:community/dash/widgets`；兼容的 Next 页面为
`/:community/dashboard/widgets`。两个入口都通过 `~/platform` 的共享
`Script` 能力加载 Widget loader，不再各自维护手写脚本注入逻辑。

访问真实入口时的链路如下：

```text
Dashboard widgets route
  -> WidgetPreviewLoader
  -> /widget/v1.js
  -> 本地失败时回退 http://localhost:5173/v1.js
  -> loader command queue
  -> 带 hash 的生产 runtime / 开发态 src/main.ts
  -> <groupher-widget>
  -> Shadow DOM launcher
  -> Lit Drawer 和 mock 数据
```

后端 API、真实反馈提交和身份体系仍属于 v2，不是 v1 未完成项。

### Review 中发现并修复的问题

- Dashboard 实际使用 TanStack 路由，原实现只接入了未被真实地址使用的 Next
  页面；现已同时接入真实路由和兼容页面。
- 页面自行创建和重试 `<script>`，与平台能力重复；现已抽成共享
  `WidgetPreviewLoader`，并使用 `~/platform` 的 `Script` 适配器。
- TanStack `Script` 适配器缺少完整的 load/error 和卸载处理；现已补齐事件
  清理、延迟加载取消、重复脚本复用和未完成脚本移除。
- 开发态 loader 从 Dashboard 跨源加载后错误地按宿主域名解析 runtime；现由
  `/v1.js` 记录自身 origin，并显式启用开发服务器 CORS。
- 开发态动态导入 loader 时构建期 runtime 常量不可用；现增加开发态
  `/src/main.ts` 安全回退，生产 build 仍替换为带 hash 的 runtime 文件。
- loader 在脚本声明式 boot 和预加载命令之间的顺序不稳定；现先执行脚本
  boot，再按顺序回放队列，使后续 `open`、`update` 和 `shutdown` 保持预期语义。
- Dashboard 同时通过脚本 dataset 和公开 API 启动会重复 boot；现由共享 loader
  只发送一次 API boot，脚本 dataset 自启动能力仍保留给普通外部页面。
- Dashboard 卸载时闭包可能仍调用旧的队列 stub，导致 Widget 元素残留；现始终
  读取当前公开 API 后发送 `shutdown`。
- runtime 加载失败后无法重试；现会清空失败的 Promise，后续命令可重新加载。
- Widget 切换 `widgetKey` 或 mock 模式时可能显示旧社区数据；现会重置数据状态，
  同时保留打开状态、当前视图和页面上下文。
- Home 每次重新打开都会重复请求；现会复用已经 ready 的数据。
- 异步请求在切换视图或销毁后可能回写旧状态；Home、内容和 Feedback 请求现均有
  AbortController 与请求序号保护。
- mock 内容和反馈成功态生成了无效假链接；现无真实 URL 时渲染纯文本，不再使用
  `href="#"` 或宿主相对链接。
- Feedback 浏览器原生校验会遮蔽组件错误态，提交过程中也可以继续编辑；现由组件
  统一展示校验信息，并在提交期间禁用输入。
- 命令解析接受模糊数字布尔值和无效 update；现只接受明确的 mock 值，并校验
  `title`、`url` 字段。
- 公共组件、平台适配器和公开解析/请求函数已补充职责注释。
