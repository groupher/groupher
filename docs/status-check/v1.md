# Groupher Status V1

> 状态：监控边界、Cloudflare 链路、Gatus/Fly V1 配置和 Fly 实例已落地；`status.groupher.com` DNS/TLS 仍待切换
>
> 公开地址：`https://status.groupher.com`
>
> 监控服务：Gatus，独立部署到 Fly.io

## 目标

Groupher 的前端、后端和基础服务分布在 Cloudflare、Vercel 和 Fly.io。生产状态页需要回答两个不同问题：

1. 每个子应用自身是否可以正常响应。
2. 用户从 `groupher.com` 进入后，DNS、Cloudflare Public Edge Router 和下游子应用组成的完整链路是否正常。

状态页用于公开展示关键产品能力的当前状态和近期可用性。它不是日志平台、APM、资源监控或完整业务测试系统。

## 决策

- 使用开源版 [Gatus](https://github.com/TwiN/gatus)，自行部署和维护。
- Gatus 独立部署到 Fly.io，不与正在被监控的入口层或业务子应用共用进程。
- `status.groupher.com` 默认公开，只展示产品级名称和状态，不公开内部拓扑、平台诊断域名和敏感响应内容。
- 历史检查结果使用 SQLite，数据库文件放在 Fly Volume 的 `/data` 目录，不额外引入 PostgreSQL。
- Fly Machine 保持常驻，不能因无流量自动停机，否则 Gatus 无法按固定周期主动检查其他服务。
- 监控同时包含“直连组件检查”和“经过 Public Edge Router 的公共链路检查”，两者不能互相替代。
- 本地直接运行 Gatus 原生二进制，不依赖 Docker；Dev Hub 负责进程管理和打开入口，状态展示仍使用 Gatus 自带 UI。

## 为什么选择 Gatus 和 Fly.io

Gatus 使用 Apache License 2.0，可以免费自托管，也可以在遵守许可证和 NOTICE 要求的前提下修改代码。它没有自托管席位费；Groupher 需要承担的是运行基础设施和自身运维成本。许可证以仓库中的 [LICENSE](https://github.com/TwiN/gatus/blob/master/LICENSE) 为准。

Gatus 的 endpoint、group、说明文字、颜色和部分页面信息可以通过配置调整，足够支撑首版 Groupher Status。若要完全改变页面结构和交互，需要维护自定义 CSS 或 fork 前端；首版不做深度 UI 定制。

Fly.io 比 Vercel 更贴合 Gatus 的运行模型：一个常驻容器持续执行 scheduler，并把 SQLite 文件写入持久化 Volume。部署在 Cloudflare Container 并非错误，但 Groupher 的公共入口本身大量依赖 Cloudflare；将 Status 放在 Fly 上，可以在 Cloudflare 故障时保留一个独立观察面。这是额外收益，不代表监控平台必须做到绝对独立。

## 整体结构

```text
                           直连组件检查
                      ┌──> Public Edge Router /health
                      ├──> Phoenix /health
                      ├──> Auth /health
Gatus on Fly.io ──────┼──> Community direct origin /health
  + SQLite Volume     ├──> Dashboard direct origin /health
  + status UI         ├──> Dash Cloudflare origin /health
                      ├──> Apply Cloudflare origin /health
                      ├──> Press /health
                      └──> 其他独立 HTTP 服务 /health

                           公共链路检查
                      ┌──> groupher.com/
                      └──> groupher.com/<代表性 Community 路由>
                                  │
                                  v
                  DNS -> Cloudflare Public Edge Router -> 子应用
```

Gatus 不会自动发现 Fly、Vercel 或 Cloudflare 上的应用。所有检查目标、周期、成功条件和告警规则都需要显式写入配置文件。

## 当前生产入口

当前生产入口要区分“物理部署”和“逻辑职责”：

- **Public Edge Router**：独立 Cloudflare Worker `edge-router`，通过 Worker Routes 接管
  `groupher.com/*` 与 `www.groupher.com/*`；canonical service id 为 `edge-router`。
- **Landing**：独立 Worker Static Assets 项目 `landing`，由 Router 通过 Service Binding
  调用；本身通过首页 smoke check 验证。
- **Community / Auth**：独立 Worker，由 Router 通过 Service Binding 调用，同时保留各自的
  direct domain 用于定位故障。
- **Hono Gateway**：`infra/gateway` 只保留本地 Node 开发能力，不承接生产公共流量，也不进入生产 Status。

`groupher.com/health` 只证明 Router handler 正常，不能证明 Service Binding 下游或 Landing
资源可用。Status 必须分别检查 Edge Router health 和 Website smoke。Hono Gateway 的健康
状态与当前生产状态无关。

截至 2026-08-10，Dash Worker 已部署到 `dash.groupher.com`。Dash 是独立产品域名；
`/:community/dash/*`、`/:community/dashboard/*` 和 `/health/dash` 在 Public Edge Router 上均为
`404`，不属于公共链路。Dash 的 health 和页面 smoke 直接使用 `dash.groupher.com`。

## 两层检查

### 1. 直连组件检查

Gatus 直接请求每个子应用自己的稳定 origin 或自定义域名下的 `GET /health`，不经过 Cloudflare Public Edge Router。

这一层用于定位故障：

- Public Edge Router 正常，但 Community 直连失败：Community 自身或其部署平台异常。
- Public Edge Router 失败，但其他服务直连正常：Cloudflare 入口或 Router 自身异常。
- Phoenix 直连失败：API 服务或其必要依赖异常。

如果所有健康检查都经过 Public Edge Router，Router 一旦故障，所有子应用会同时显示异常，无法定位真正的故障点。

`/health` 必须保持低成本、无鉴权、无副作用，并遵守 [health.v1 contract](../contract/health.md)。它只做快速、可解释的存活或必要依赖检查，不执行完整 OAuth、文档转换、批量查询等高成本业务流程。

### 2. 公共链路检查

Gatus 另外请求少量真实用户入口。这些请求必须使用生产公共域名并经过 Cloudflare Public Edge Router，用来覆盖：

- DNS 和 TLS 证书；
- Cloudflare 公共入口；
- Public Edge Router 是否可达；
- host/path 分流规则；
- 目标子应用是否能返回可用页面。

如果只检查子应用直连地址，可能出现 Community 和 Dash 都正常，但 `groupher.com` 的 DNS、
证书或 Public Edge Router 路由已经损坏，而状态页仍然全绿。

## 故障判断

| 直连检查 | 公共链路检查 | 优先判断                                               |
| -------- | ------------ | ------------------------------------------------------ |
| 正常     | 正常         | 服务和入口链路正常                                     |
| 正常     | 失败         | DNS、TLS、Cloudflare Public Edge Router 或分流规则异常 |
| 失败     | 失败         | 目标子应用或其部署平台异常                             |
| 失败     | 正常         | 检查地址、健康接口或监控条件可能配置错误               |

## 首版监控清单

精确的 direct origin 必须在部署 Gatus 前根据各平台当前生产配置确认，不能把临时 Preview URL 写进长期监控。

下面的监控清单是目标状态。稳定 origin 和 smoke URL 仍需在各部署完成后以公网响应确认。

### 组件健康检查

| Status 展示名称    | 检查目标                                | 方式     | 备注                                                        |
| ------------------ | --------------------------------------- | -------- | ----------------------------------------------------------- |
| Public Edge Router | `https://groupher.com/health`           | 公共入口 | 返回 `service: edge-router`；检查 Cloudflare Worker handler |
| API                | `https://api.groupher.com/health`       | 直连     | Phoenix                                                     |
| Authentication     | `https://auth.groupher.com/health`      | 直连     | Auth                                                        |
| Community          | `https://community.groupher.com/health` | 直连     | `frontend/community`；目标社区页面服务                      |
| Dashboard          | `https://dashboard.groupher.com/health` | 直连     | 独立产品域名，不经过 Public Edge Router                     |
| Dash               | `https://dash.groupher.com/health`      | 直连     | 独立产品域名，不经过 Public Edge Router                     |

`document-converter`、`content-import`、`inspire-me` 等服务只有在生产中作为常驻 HTTP 服务，并且故障会影响公开产品能力时才加入 Status。纯内部或非关键服务可以保留告警，但不一定公开展示。

### 公共链路检查

首版控制在 2～4 个代表性 URL：

| Status 展示名称 | 检查目标                       | 验证内容                                                       |
| --------------- | ------------------------------ | -------------------------------------------------------------- |
| Website         | `https://groupher.com/`        | Landing 公共入口                                               |
| Community       | 一个稳定的公开 Community 页面  | Cloudflare Router 到 Community 的分流与页面响应                |
| GraphQL API     | 一个低成本、无副作用的公开查询 | Cloudflare Router 的 GraphQL facade 到 Phoenix；第二阶段再加入 |

公共页面检查首版只验证 HTTP 状态和响应时间。需要检查页面内容时，只匹配一个稳定、不含用户数据的标记，避免 UI 文案调整造成误报。

## Gatus 配置基线

仓库中的 [`ops/status/config.yaml`](../../ops/status/config.yaml) 已按前述清单配置生产 endpoint；本地配置位于 [`ops/status/config.local.yaml`](../../ops/status/config.local.yaml)。下面保留配置形态作为阅读基线：

```yaml
storage:
  type: sqlite
  path: /data/gatus.db

alerting:
  discord:
    webhook-url: ${GATUS_DISCORD_WEBHOOK_URL}

endpoints:
  - name: Public Edge Router
    group: Public Ingress
    url: https://groupher.com/health
    interval: 1m
    conditions:
      - '[STATUS] == 200'
      - '[BODY].schemaVersion == health.v1'
      - '[BODY].service == edge-router'
      - '[BODY].status == ok'
      - '[RESPONSE_TIME] < 2000'
    ui:
      hide-url: true
      hide-hostname: true
      hide-port: true
    alerts:
      - type: discord
        enabled: true
        failure-threshold: 3
        success-threshold: 2
        send-on-resolved: true

  - name: Public Website
    group: Public Paths
    url: https://groupher.com/
    interval: 2m
    conditions:
      - '[STATUS] == 200'
      - '[RESPONSE_TIME] < 3000'
```

生产配置的检测频率按部署形态分层，而不是所有 endpoint 统一使用 30 秒。原因是
`/health` 请求本身也是一次真实的公网请求：对于 Vercel Serverless 应用，高频检查会
增加 Function invocation 和执行用量，可能降低冷启动概率，但不能保证实例持续 warm；
对于 Cloudflare Worker、Fly 常驻服务和公共入口，检测频率主要影响故障发现速度，不需要
用心跳来维持进程热状态。

当前生产架构的推荐列表如下：

| 检查目标                 | 部署形态                        | 推荐频率 | 选择理由                            |
| ------------------------ | ------------------------------- | -------- | ----------------------------------- |
| Public Edge Router       | Cloudflare Worker / 公共入口    | 1 分钟   | 较快发现 DNS、TLS、路由和入口故障   |
| API                      | Fly.io / Phoenix 常驻服务       | 1 分钟   | 核心后端，需要较快发现故障          |
| Authentication           | Cloudflare Worker               | 2 分钟   | 核心能力，但不需要高频保活          |
| Community                | Cloudflare Worker               | 2 分钟   | 目标社区页面服务                    |
| Dashboard                | 独立产品 origin                 | 5 分钟   | 与公共入口解耦，降低无意义探测开销  |
| Dash                     | Cloudflare Worker               | 2 分钟   | Worker 不存在传统 Vercel 冷启动问题 |
| Content Delivery / Press | Fly.io 常驻服务                 | 1 分钟   | 适合较高频探测                      |
| Asset Delivery           | Cloudflare Worker               | 2 分钟   | 检查公共读取入口即可                |
| Public Website           | edge-router + landing Worker    | 2 分钟   | 迁移后检查用户真实访问链路          |
| Dash Product Route       | Cloudflare Worker custom domain | 2 分钟   | 检查 Dash 独立产品入口              |

因此，Cloudflare/Fly 核心服务使用 1–2 分钟，独立 Dashboard 使用 5 分钟，公共页面使用
2 分钟。旧 Main 不属于生产依赖，也不进入公开 Status 配置。

- 连续失败 3 次后告警，降低瞬时网络波动造成的噪声。
- 连续成功 2 次后恢复，并发送 resolved 通知。
- `/health` 响应时间阈值先设为 15 秒，页面阈值先设为 10 秒；当前公网 API 偶发需要数秒，首版先避免把可用服务误报为故障，再根据真实分位值收紧。
- `limited` 或 `down` 都不视为完全正常；首版统一以 `status == ok` 为绿色。
- 本地 `config.local.yaml` 保留 30 秒频率，便于开发时快速发现服务启动和停止；该频率不用于生产保活，也不代表生产推荐值。

Dev Hub 与 Gatus 对 `limited` 的消费语义有意不同：Dev Hub 把 `limited` 视为仍可接收核心流量，因此保持 ready；Gatus V1 把它视为非绿色并触发降级告警。Gatus 的 success/failure 展示无法完整表达 `ok / limited / down` 三态，首版采用保守映射。后续如果希望 `limited` 保持绿色，可以改成 `[BODY].status == any(ok, limited)`，但这会在公开状态页隐藏降级状态。

Condition 整条表达式使用 YAML 引号；右侧字符串 operand 按 Gatus DSL 使用裸值，
例如 `"[BODY].status == ok"`。YAML 外层引号不会成为 condition operand 的一部分。

告警渠道和接收人作为部署 secret/config 管理，不把 webhook、token 或邮箱凭证提交到仓库。

告警配置分为两层：

- 顶层 `alerting` 配置 provider 和发送凭证，例如 Discord webhook、Slack webhook、SMTP、Telegram bot token 或 PagerDuty integration key。
- `endpoints[].alerts` 配置哪些 endpoint 使用哪个 provider，以及 failure threshold、success threshold 和 resolved 通知规则。

本地配置不定义 `alerting` 和 `endpoints[].alerts`，因此不会向正式渠道发送开发环境告警。生产凭证通过 Fly Secret 注入为环境变量，Gatus 配置只引用变量名。

## 本地运行

本地直接运行 Gatus 原生二进制，不使用 Docker。Gatus 已将自己的 UI 静态资源打包进二进制，启动后直接访问其独立页面。

以下 `ops/status/config.local.yaml` 是本地配置；生产镜像使用 `ops/status/config.yaml`。

安装：

```bash
go install github.com/TwiN/gatus/v5@v5.36.0
```

启动：

```bash
GATUS_CONFIG_PATH="$PWD/ops/status/config.local.yaml" \
  "$(go env GOPATH)/bin/gatus"
```

访问：

```text
http://127.0.0.1:8080
```

正式接入 Dev Hub 时固定一个经过验证的 Gatus v5 版本，不在每次启动时执行 `go install @latest`。找不到本地二进制时，Dev Hub 将服务标记为 unavailable 并给出安装提示。

原生进程可以直接请求 Groupher 的本地 listener，不需要 Docker 的 `host.docker.internal`：

```yaml
storage:
  type: sqlite
  path: .tmp/status/gatus.db

endpoints:
  - name: Main
    group: Frontend
    url: http://127.0.0.1:3000/health
    interval: 30s
    conditions:
      - '[STATUS] == 200'
      - '[BODY].schemaVersion == health.v1'
      - '[BODY].service == main'
      - '[BODY].status == ok'
```

本地和生产中由同一 runtime 承载的服务保持相同的 endpoint 名称、group 和判断条件，只区分 URL、storage path 和 alerting。Hono Gateway 可以继续由 Dev Hub 管理，但它不进入面向生产的 Gatus endpoint 清单。Gatus 支持在配置文件中引用环境变量；对其他少量环境差异优先使用环境变量，不复制整套判断规则。

## Dev Hub 接入

Dev Hub 只负责 Gatus 的进程生命周期和页面入口，不重复实现 Gatus 的状态 UI，也不通过 iframe 嵌入页面。

```text
Dev Hub
  ├─ start / stop / restart Gatus
  ├─ 展示 Gatus 进程日志
  ├─ Open Local Status -> http://127.0.0.1:8080
  └─ Open Production Status -> https://status.groupher.com

Gatus UI
  └─ 展示 endpoint 状态、响应时间和历史记录
```

接入规格：

- 扩展 Dev Hub service group：`frontend | backend | infra`。
- 注册 `service id: gatus`，归属 `infra`，不放入 Frontend 或 Backend。
- 使用原生 Gatus 二进制作为 managed process，不通过 Docker 启动。
- `appUrl` 使用 `http://127.0.0.1:8080`。
- readiness 使用 `http-status` 检查 Gatus 自己的 `/health`，不要求它返回 Groupher `health.v1`。
- Gatus 不属于任何业务应用的 required 或 optional dependency；业务服务启动不依赖监控服务。
- Infra Drawer 同时提供 Local Status 和 Production Status 链接。
- 本地 Gatus 默认不发送告警；未启动的业务服务显示红色属于正常开发状态。

Dev Hub 对配置了 `url` 的 managed service 默认验证 Groupher `health.v1`。Gatus 自身 `/health` 不属于该协议，因此 `gatus` 服务显式使用 `readiness: http-status`，不伪造 `service: gatus` 响应，也不只依赖端口监听。

## 数据与持久化

首版不需要独立数据库：

```text
Gatus process
    |
    v
/data/gatus.db       Fly Volume
```

SQLite 保存检查结果和状态历史。Fly Volume 负责 Machine 重启或重新部署后的持久化。

边界如下：

- Fly Volume 绑定单一区域和单台写入实例，首版只运行一个 Gatus 实例。
- 不把 Gatus 横向扩容成多个同时写同一个 SQLite 文件的实例。
- 定期备份 Volume 或 SQLite 文件；状态历史可以丢失，但监控配置必须保存在 Git 中。
- 日后只有在需要多实例、高可用或更长历史保留时，才考虑外部 PostgreSQL。

## 公开范围

`status.groupher.com` 建议公开。公开状态页只显示用户能理解的产品能力：

- Website
- Community
- Dashboard
- Dash
- API
- Authentication
- Content Delivery
- Asset Delivery

不公开以下内容：

- Fly/Vercel/Cloudflare 内部项目名和临时域名；
- direct origin 的完整 URL；
- IP、端口、区域、版本 SHA 和内部依赖拓扑；
- health body、异常堆栈、告警 webhook 和运维备注。

Gatus 配置中隐藏 URL 和 hostname。更详细的故障定位通过 Fly 日志、平台控制台和后续 APM 完成，而不是放在公开状态页。

## 部署到 Fly.io

Gatus 适合以单个常驻容器运行：

```text
Fly app: groupher-status
region: 选择靠近主要用户或被监控服务的区域
machine count: 1
volume mount: /data
custom domain: status.groupher.com
auto stop: disabled
auto start: enabled
```

当前实例已创建：`groupher-status`，`sin` 区域单 Machine，`gatus_data` 1 GB Volume，临时访问地址为 `https://groupher-status.fly.dev`。自定义域名证书已在 Fly 创建，仍需完成 DNS 验证。

后续修改 `ops/status/config.yaml`、`Dockerfile` 或 Fly 配置后，从仓库根目录执行：

```bash
make be.status.deploy
```

不修改这些文件时无需重复部署；Gatus 会在 Fly Machine 中持续运行并按 interval 检查 endpoint。

当前 Fly 给出的 DNS 验证记录为：

```text
CNAME status.groupher.com -> rolpgx6.groupher-status.fly.dev
TXT   _fly-ownership.status.groupher.com -> app-rolpgx6
```

如果 Cloudflare 使用代理（橙云），先保留 ownership TXT，并在切换后执行 `fly certs check status.groupher.com --app groupher-status`；验证通过后再按需要开启代理。

成本主要来自常驻 Machine，其次是少量 Volume；健康检查请求和公开状态页的流量通常很小。具体价格随 Fly 当前计费变化，不在仓库文档中写死金额，部署时以 [Fly.io Pricing](https://fly.io/docs/about/pricing/) 为准。

Vercel 不作为首选承载平台：Gatus 是常驻进程，需要后台定时调度和本地持久化文件；Vercel Functions 是按请求执行的无状态模型，不能直接保留一个持续运行的 Gatus scheduler 和 SQLite Volume。若部署到 Vercel，需要把定时任务、存储和 UI 拆开重写，失去直接使用 Gatus 的简单性。

## 上线步骤

1. 部署 Dash Cloudflare Worker，并将 `dash.groupher.com` 绑定为独立产品域名。
2. 确认 Public Edge Router 对 `/:community/dash/*`、`/:community/dashboard/*` 和
   `/health/dash` 保持 `404`。
3. 为实际服务 payload 增加 conformance test；不能只验证 schema fixtures。
4. 盘点各子应用当前生产 direct origin，确认每个 `/health` 的 `service` 值。
5. 在仓库中创建 `ops/status/`、Gatus 本地/生产配置和 Fly 部署文件。
6. 创建 Fly app 和 Volume，将 Volume 挂载到 `/data`。
7. 配置告警 secret，并禁止 Machine 自动停机。
8. 绑定 `status.groupher.com`，完成 DNS 和 TLS 验证。
9. 验证每个直连组件检查，再验证 Cloudflare Public Edge Router 公共链路检查。
10. 重启或重新部署 Gatus，确认 SQLite 历史仍然存在。
11. 人工制造一个安全的测试失败，确认 failure、恢复和 resolved 通知完整工作。

## 上线阻塞项与待确认项

上线阻塞项：

- `yarn contract:health` 当前只验证 fixtures；需要把实际 HTTP producer 的 payload 纳入 conformance test。

其余待确认项：

- Community、Dashboard 和 Assets 的最终生产 direct origin 仍需在部署后由 Gatus 持续验证。
- 选择一个稳定、公开且不依赖用户数据的 Community smoke URL。Dashboard、Dash、Apply 使用
  各自独立子域名，不增加 `groupher.com` 下的公共链路检查。
- 告警渠道及接收人。
- SQLite 历史保留和备份周期。
- `status.groupher.com` 的 DNS/TLS 绑定和告警 webhook 仍需完成；Fly app 与 `gatus_data` Volume 已创建。
